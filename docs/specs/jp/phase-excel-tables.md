# Phase Excel-Tables: Excel の表をテーブルとして解釈する — 実装仕様書

> **目標**: Excel（XLSX・XLS）のシートを Interpret ステージでテーブルとして解釈し、CSV/TSV と
> 同じプレビュー Parquet とスキーマを作る。以降は表プレビュー・行レベル差分・OData・MCP の
> `/query` にそのまま乗る。**どこを表として読むかは「読み方の指示」で表し、素直な表だけを規則で
> 自動にする。ほかは規則と AI の案を人が確定する。** 設計判断は ADR-057 を正とする。

## 0. この仕様書で決めること

ADR-057 が「実装仕様書で決める」とした事項と、本仕様書の答え。

| ------------------------------------------ | -------------------------------------------------------------------------------- | ----- |

## 1. 前提

- **ADR-057 のスパイクは済んでいる。** 規則と AI の案の当たり方、人が確かめた 54 枚の正解、
  罫線の効き方は ADR-057 コンテキスト 7 にある。評価セットはリポジトリの外にある（§12）
- **XLSX のセルの格子の読み取りは、別の PR で入る**（`interpret/table/xlsx-grid.ts`）。セルの
  位置・型・生の値、結合、非表示の行と列、ウィンドウ枠の固定、オートフィルター、印刷タイトル、
  罫線を返す
- **ADR-046**: 解釈は版のバイト列から決定的に行う。同じ版を読み直せば同じ答えが出る
- **ADR-059**: 重い解釈は worker の子プロセス（heavy）で行う。Excel の格子の読み取りもそこで行う
- **Versioning ii-c**: 確定値（主キー・確定型）は `resource.column_settings` に置き、版に凍結し、
  版の同一性の入力になる。読み方の指示も同じ扱いにする
- **ADR-072**: 確定は管理画面の「表の設定」タブで、主キー・確定型と同じ下書きに入る

## 3. 読み方の指示のデータ形

### 3.1 形

```ts
/** One table read off a workbook (ADR-057 §決定 2). */
interface TableReading {
  /** A name for the table, unique within the resource. Default: the sheet's name. */
  name: string
  /** The sheet, by name. */
  sheet: string
  /** Top-left corner of the range, header included (A1 notation). */
  from: string
  /** Bottom-right corner (A1 notation): of the version it was read on (§3.3). */
  to: string
  /** Rows from the top of the range that are header. */
  headerRows: number
  /** Names that replace the ones joined from the header, one per column. */
  columnNames?: string[]
  /**
   * Settled only: the header band's text, row by row, as it was when settled.
   * What finds the table again in a later version (§3.3).
   */
  header?: string[][]
  /**
   * Settled only: the one-cell row just above the header band (a table's name such
   * as "＜第一審＞"), when there is one. Tells apart tables with the same header (§3.3).
   */
  title?: string
}
```

- 規則・AI・人が、すべてこの形を出す
- **一覧で持つ。当面は 1 件だけ許す。** ADR-057 決定 7 のとおり、1 リソースから複数の表を出すのは
  別の ADR で扱う。そのときに確定値の形を変えずに済むよう、最初から配列にする
- `name` は、将来の複数の表で、版をまたいで同じ表を指すための足場である。当面は表示にだけ使う

### 3.2 置き場所

| 場所                                               | 誰が書くか | 中身                                                                 |
| -------------------------------------------------- | ---------- | -------------------------------------------------------------------- |
| `resource.column_settings.readings`                | 人（API）  | 確定した読み方の指示。**無い、が普通の状態**（主キー・確定型と同じ） |
| `resource_version.settled_reading`（新設、jsonb）  | worker     | 版を作ったときの確定した指示の写し。使えたかどうかによらず凍結する   |
| `resource_version.reading`（新設、jsonb）          | worker     | その版を実際に読んだ指示と、出どころ（`rules` / `settled`）          |
| `resource_version.reading_proposal`（新設、jsonb） | worker     | 素直な表の条件に外れたときの、規則の案と当たった理由（§8.3）         |

- **版の同一性**（`VersionIdentity`）に 5 つ目の入力 `settledReading` を足す。版の側は
  `settled_reading`（作ったときの確定した指示の写し）、リソースの側は `column_settings.readings`。
  **実際に読んだ指示（`reading`）とは比べない。** 確定した指示が見つからずに規則で読んだ版や、
  表にできなかった版（§10.2・§10.3）でも、作ったときの確定した指示は写しておく。そうしないと、
  リソースに残る確定した指示と版の側が一致せず、同じファイルを取り直すたびに版が増え続ける
  （確定型の `settled_types` と同じ持ち方）
- 比べるときは `name`・`from`・`to` を除く。名前を変えても読み方は変わらず、範囲は版ごとに
  取り直すので（§3.3）、版によって違ってよい
- **規則が出した指示は、版の同一性に入れない。** 規則は同じバイト列から同じ指示を出すので、
  入れても変わらない。規則を直したときに、既存の版がすべて新しい版になるのを避ける
- 確定した指示は、確定型と同じく、API の適用で `column_settings` に書き、版が 1 つ増える

### 3.3 版ごとに範囲を取り直す（2026-11-23 決定）

毎月行が増える Excel を、同じ URL で取り直す使い方がある。範囲を行番号で固定すると、**増えた行が
黙って読まれなくなる。** 右端（年度の列が増える横持ちの表）も同じで、「いつまでも残り続ける誤り」に
あたる。表題の行が 1 行増えるだけでも、固定した範囲は見出しを取り違える。

**そこで、範囲は版ごとに取り直す。素直な表かどうかの判定も、版ごとにし直す。** 確定した指示は
「どの範囲か」ではなく、「どの表か」と「どう読むか」を持つ。

| 確定した指示が持つもの       | 版ごとに取り直すもの             |
| ---------------------------- | -------------------------------- |
| シートの名前                 | 範囲の上端（見出しの帯を探して） |
| 見出しの帯の文字（`header`） | 左端と右端（見出しの帯の幅）     |
| 見出しの行数                 | 下端（データの終わり）           |
| 列名                         |                                  |

版を読む順は次のとおり（§7.1）。

1. 確定した指示があれば、そのシートで見出しの帯の文字を探す（§5.7 で正規化して比べる）。
   確定した指示が表の名前の行（`title`）を持てば、見出しの帯のすぐ上の名前も合うものに限る。
   **合う所が 2 つ以上あれば、表にせず要確認にする**（同じ見出しの表が並ぶシートで、並び順が
   変わると別の表を読みかねない）。1 つだけ見つかれば、そこを上端とし、左右の端は見出しの帯の幅、下端は規則の案の作り方（§8.1）で
   データの終わりを決める。確定した列名と見出しの行数で読む
2. 見つからなければ、または確定した指示が無ければ、素直な表の判定（§5）をする。素直なら規則で読む
3. どちらでもなければ表にしない（§10.2）。前の版が表だったなら要確認にし、前の版の表を出し続ける
   （§10.3・§10.4）

**確定するとき、その範囲が取り直せるかを確かめる。** 人が選んだ範囲を、その版で上の 1 の手順で
取り直し、同じ範囲になることを画面で確かめる（§9）。ならないとき（途中の空行の先まで選んだ、
など）は、人に範囲か見出しを直してもらう。取り直せない範囲を確定すると、次の版で黙って違う
範囲を読むためである。

## 4. セルの格子

### 4.1 XLSX

別の PR で入る `xlsxGrid`。シートごとに、行の流れ（セル・罫線）と、読み終えた後のレイアウト
（結合・非表示・枠の固定・オートフィルター）を返す。

### 4.2 XLS（PR 1-b）

`legacy/xls.ts` の `xlsSheets` を広げ、`xlsxGrid` と同じ `GridRow` を返す。

- セルの位置と型: `LABELSST`・`LABEL`・`RSTRING`（文字列）、`NUMBER`・`RK`・`MULRK`（数値）、
  `BOOLERR`、`FORMULA`（計算結果。文字列の結果は直後の `STRING` レコード）
- 日付: セルの `XF` から書式の番号を引き、`FORMAT` レコードの書式コードを `dateKindOf` に通す。
  1904 年基準は `DATEMODE` レコード
- 結合: `MERGEDCELLS`。非表示の行: `ROW` の `fDyZero`。非表示の列: `COLINFO`
- 枠の固定: `WINDOW2` の `fFrozen` と `PANE`。印刷タイトル: `NAME` の組み込み名 `Print_Titles`
- 罫線: `XF` の線の種類（4 ビット × 4 辺）。種類の番号は XLSX と同じ 13 種類に対応する
- Excel のテーブル（ListObject）とオートフィルターは読まない（ADR-057 決定 8）

### 4.3 どこで読むか、どこまで読むか

- 格子の読み取りは heavy の子プロセスで行う。新しい要求 `read-grid` を足す
- **上限は今のまま**（`MAX_PARQUET_SOURCE_SIZE`、100MB）。XLSX の展開後の大きさと結合の数には、
  格子の読み取りが既に上限を持つ（ZIP のエントリ数、`GRID_MAX_MERGES`）
- **PR 1-d の中で、worker の条件でメモリを測る。** 標本の最大のブックと、合成した 100MB の
  XLSX・XLS で、heavy の子プロセスの最大の RSS を見る。heavy の上限（`HEAVY_PROCESS_MB`）を超える
  なら、Excel 用の上限（展開後のバイト数かセルの数）を足す
- 判定（§5）に要るのは、行ごとのセルの数・型と、表の上下の数十行である。**格子の全体をメモリに
  持たない。** 行の流れを 1 回読みながら、判定に要る数え上げと、表の候補の行だけを残す

## 5. 素直な表の判定（Step 1）

**迷ったら自動にしない。** 誤って表にすると、見出しが 1 行ずれただけで全部の行が壊れ、行レベル
差分は全行の変更を報告する（ADR-057 コンテキスト 3）。素直な表を見逃しても、Step 2 で人が
1 回確定すれば済む。手順は「外れる兆候が 1 つでもあれば外す」形にする。

### 5.1 シートを 1 枚に絞る

各シートを次のどれかに分ける。

| 分類     | 条件                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------- |
| 空       | 値のあるセルが無い                                                                              |
| 表でない | グラフのシート、値のあるセルが 20 未満、値が 1 セル以下の文字の行が 6 割以上で数値の列が 2 未満 |
| 非表示   | タブが非表示（`hidden`・`veryHidden`）。作成者が見せないことにしたシートは候補にしない          |
| 候補     | ほかのすべて                                                                                    |

候補が 0 枚なら `no-table`、2 枚以上なら `multiple-sheets` で外す。しきい値はスパイクの分類に
合わせた値で、§12 の評価で確かめる。

ブックが暗号化されていれば、シートを読めないので `encrypted` で外す。

### 5.2 表の本体を決め、その上と下を確かめる

値が 1 セル以下の行を上と下から飛ばすだけでは、2 セル以上を使う表題や注記が、見出しやデータの
行に取り込まれる。**先に表の本体を決め、その外側を確かめる。**

1. 空行でシートをかたまりに分ける。値が 2 セル以上の行をいちばん多く持つかたまりを、表の本体の
   候補にする。同じ数のかたまりが 2 つ以上あれば外す（`multiple-tables`）
2. 本体の外（上と下のほかのかたまり）に、値が 2 セル以上の行があれば外す（`title-or-footer`）。
   値が 1 セル以下の行だけなら、表題・注記として範囲の外に置く
3. 本体の中で、先頭の値が 1 セル以下の行は表題として飛ばす（空行を挟まない表題）。末尾の値が
   1 セル以下の行は注記として飛ばす
4. 本体の中で、表題の次の行を見出しの候補にする（§5.3）
5. **本体の末尾の行を確かめる。** データの 9 割以上が数値か日付である列で、末尾の行が文字（値なしの
   印を除く）を持てば、空行を挟まない注記か合計の説明と見て外す（`title-or-footer`）

表題の行の結合は許す。表題より下（見出しを含む）の結合は §5.4・§5.5 で扱う。

**残る誤り。** すべての列が文字の表（施設の一覧など）で、表題が見出しと同じ幅で、空行を挟まずに
見出しのすぐ上にあると、型で見分けられず、表題を見出しと読む。§5.4 の Excel の設定（枠の固定・
印刷タイトル）があれば外れる。標本の範囲では見ていない形で、まれと見る。起きても、人が読み方を
確定すれば、以後はその指示で読む（§3.3）ので回復できる。

### 5.3 見出しを 1 行と決める

表題の次の行を見出しとし、次をすべて確かめる。

| 条件                                                       | 外れたときの理由   |
| ---------------------------------------------------------- | ------------------ |
| 表の左端から右端まで、見出しのセルがすべて埋まる           | `header-blank`     |
| 正規化した名前が重複しない（§5.7）                         | `header-duplicate` |
| 見出しのセルがすべて文字である（数値・日付・真偽値が無い） | `header-not-text`  |

年を列に並べた横持ちの表は 3 つ目で外れる。外れてよい（統計表であり、Step 2 の対象）。

表の左端と右端は、見出しとデータを合わせた幅で取る。左上の空いた行見出しの列や、右の欄外のメモは、
見出しの外にはみ出すので `header-blank` で外れる（§5.5 の `not-rectangular` にも当たる）。

### 5.4 見出しが本当に 1 行かを確かめる

2 行目の見出しをデータの最初の行と取り違えるのが、いちばん害の大きい誤りである。次のどれか
1 つでも当てはまれば `multi-row-header` で外す。

- **列の型が合わない**: データの最初の行が、ある列で文字なのに、その列の残りのデータの 9 割以上が
  数値か日付である
- **結合がある**: 見出しの行か、データの最初の行に、結合がかかる
- **Excel の設定と合わない**: ウィンドウ枠の固定の行、または印刷タイトルの最後の行が、見出しの
  行と違う（どちらも無ければ確かめない）

Excel の設定は、範囲を決める手がかりとしては使わず、外す理由としてだけ使う。スパイクで単独の
当たり方は 7〜9 割だった。

### 5.5 データの中身を確かめる

データの最初の行から最後の行までで、次を確かめる。

| 兆候                                                    | 理由                |
| ------------------------------------------------------- | ------------------- |
| 範囲の中に結合がある                                    | `merged-cells`      |
| 見出しの列の外（左右）に値がある                        | `not-rectangular`   |
| 値が 1 セルだけの行がある（区分の行）                   | `section-rows`      |
| 見出しの行の文字の 8 割以上が、下の行か右にもう一度並ぶ | `multiple-tables`   |
| 計算結果を持たない数式がある                            | `uncached-formulas` |

- 区分の行（「〈資産の部〉」など）は、Step 2 では範囲の中に残す。素直な表の条件からは外す
- 見出しの繰り返しは、評価で誤報なく 17 枚を拾えた規則である。表が複数ある・折り返し・
  ページごとの見出しの繰り返しの兆候になる
- 途中に空行のある表は、いったん外す側に置く。空行の先が同じ表の続きか別の表かを、規則では決めきれない。
  空行の先のデータは §5.2 の 1・2 で外れる（`title-or-footer`。かたまりが同じ大きさなら `multiple-tables` にも当たる）
- 非表示の行と列は、条件にしない。範囲の中にあれば読む（ADR-057 決定 6）

### 5.6 最低限の大きさ

2 列以上、データ 1 行以上。満たさなければ `too-small`。1 列の表は、表題の行と区別できない
（`countTitleRows` と同じ理由）。

### 5.7 見出しの名前の正規化

重複の判定と、列名として書き出す前に、次を当てる。

- 前後の空白（全角を含む）を除く。セルの中の改行は空白 1 つにする
- 英数字と記号は NFKC で半角にそろえる（比べるときだけ。列名は元の文字のまま書く）
- 重複の判定では、英字の大文字と小文字を区別しない（`ID` と `id` は同じ名前）。DuckDB は列名を大文字と小文字を区別せずに比べ、重なった列の名前を変える

### 5.8 理由

`NoTableReason`（`resource_version.no_table_reason`、varchar(32)）に次を足す。

| 理由                | 意味                                                         | デジタル庁のルール |
| ------------------- | ------------------------------------------------------------ | ------------------ |
| `encrypted`         | ブックが暗号化されている（開くときのパスワード）ので読めない |                    |
| `no-table`          | 表の候補のシートが無い                                       |                    |
| `multiple-sheets`   | 表の候補のシートが複数ある                                   | L1-02              |
| `title-or-footer`   | 表の上か下に、表題・注記と言えない行がある                   | L1-04              |
| `header-blank`      | 見出しに空のセルがある                                       | L1-05              |
| `header-duplicate`  | 見出しの名前が重複する                                       | L2-03              |
| `header-not-text`   | 見出しに数値や日付がある                                     |                    |
| `multi-row-header`  | 見出しが 2 行以上ある                                        | L2-03              |
| `merged-cells`      | 範囲の中に結合がある                                         | L1-12              |
| `not-rectangular`   | 見出しの列の外に値がある                                     | L1-03・L1-04       |
| `section-rows`      | データの途中に区分の行がある                                 |                    |
| `multiple-tables`   | 1 シートに表が複数ある（見出しが繰り返される）               | L1-02              |
| `uncached-formulas` | 計算結果を持たない数式がある                                 | L2-06              |
| `too-small`         | 2 列未満か、データの行が無い                                 |                    |

- **版の `no_table_reason` には 1 つだけ書く。** 上の表の順で、最初に当たったもの
- `multiple-sheets` と `encrypted` のときは、判定するシートが 1 枚に決まらないので、ほかの理由は数えない
- **当たったものすべては `reading_proposal.reasons` に書く**（§8.3）。どの条件で多く外れるかを
  数え、Step 2 の案の出発点にする
- ルールの ID は表示の層で添える（ADR-057 決定 5）。判定には入れない

## 6. 中間 CSV と `interpretCsv`

### 6.1 書き出し

読み方の指示の範囲を、UTF-8 の中間 CSV に書き出す（ADR-057 決定 6）。

- 1 行目は列名。素直な表では見出しの行の文字、Step 2 以降はつないだ列名か人が直した列名
- 2 行目以降は、データの最初の行から範囲の最後の行まで。**範囲の中の行は 1 つも落とさない**
- 値は生の値。日付は ISO 8601。数式は計算結果
- 結合セルは、データでは左上のセルだけが値を持つ（素直な表では範囲に結合が無い）
- 非表示の行と列も書く
- 中間 CSV は作業ファイルで、保存しない

### 6.2 `interpretCsv` に足す指定（PR 1-c）

```ts
type CsvStructure =
  | { inferred: { skipRows: number } }
  /** Where the table is was decided before the CSV was written: read it as written. */
  | { given: { textColumns: readonly string[] } } // §6.3
```

`given` のとき:

- 表題の行の走査をしない（読み飛ばす行は 0）
- 1 行目をヘッダーと明示する（`header = true`）
- 区切り・引用符・エスケープを `,`・`"`・`"` に固定する。自分で書いたファイルなので推定に任せない。値がみな `'` で囲まれていると `'` を引用符と、`;` が `,` より多いと `;` を区切りと取り違える
- **末尾の注記の推定（`settleSignOffs` と末尾の行の除去）をしない。** 値の少ない末尾の行を
  注記とみなす推定は、幅の広い表の「合計」と金額だけの行を落としうる

型の推定・確定型の適用・値なしの印・文字列表記の数値・表のプロファイルは、これまでどおり行う。
CSV の動きは変えない（`given` を渡すのは Excel の経路だけ）。

### 6.3 文字列のセルだけの列

Excel では、`00123` のようなコードを文字列のセルとして入れることが多い。中間 CSV にすると、
この区別が消え、sniffer が数値と推定して先頭の 0 を落とす。

**データの値のあるセルがすべて文字列のセルである列は、`types` の初期値として文字列（VARCHAR）を
渡す。** 人が確定型を置いた列は、確定型を優先する。文字列表記の数値（ii-c）の判定は文字列の列に
働くので、`1,234` のような値は従来どおり数えられる。

## 7. パイプラインへの組み込み（Step 1）

### 7.1 Interpret ステップ

今は XLSX・XLS を `isDocumentFormat` の分岐で文書として扱い、テキストを抽出して終わる。
これを次のようにする。

1. 文書のテキストの抽出は今のまま行う（全文索引は変えない、ADR-057 決定 8）
2. 続けて、heavy の子プロセスで格子を読み、§5 の判定を行う
3. 素直な表なら、中間 CSV を書き、`interpretCsv`（`given`）で Parquet とスキーマを作る
4. 外れたら、`NO_TABLE` と理由、`reading_proposal` を版に書く

ブックの取得は 1 回で、表とテキストの両方がそれを読む。表を読む途中で失敗しても、ステップは失敗に
しない。警告をログに残し、テキストの抽出に進む（表が読まれる前と同じく、文書として残る）。

確定した読み方の指示があるリソース（Step 2 以降）は、§3.3 の順で読む。確定した見出しが見つかれば
その指示で、見つからなければ素直な表の判定に戻る。

### 7.2 既存の版を解釈し直す（PR 1-e）

2 つの経路が要る。層 2 の定期再投入だけでは、公開のプレビューは変わらない。

| 経路                                | 何が変わるか                                                                                                                                                                                                                                       |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 層 2 の定期再投入（`lakeLoadable`） | `lakeLoadable` に `xlsx`・`xls`（`WORKBOOK_FORMATS`）を足すと、スキーマの無い既存の Excel の版をすべて拾い、版の `schema` を書いて層 2 に入れる。**一時の Parquet を公開用に保存せず、`resource_pipeline` の `previewKey` とスキーマも更新しない** |
| リソースの再処理                    | 最新の版について Interpret をやり直し、公開用の Parquet を保存して `resource_pipeline` を更新する。プレビュー・OData・MCP はこちらを読む                                                                                                           |

- **最新の版は、管理者が形式を選んで再処理する。** 「リソースの処理状況」の再処理で形式を選べる
  （既定はすべて、`POST /admin/jobs/enqueue-all` の `formats`）。Excel だけを選ぶと、Excel のリソースを
  保存済みのファイルから作り直し、検索の索引は空にしない。更新で自動には積まない。版は増えない
  （バイト列も確定した指示も変わらない、ADR-046）
- `TABLE_SOURCE_FORMATS` には足さない。そこは CSV・JSON の経路に回す形式で、ブックは格子から読む
- 格子が読めないブックは版に何も書かないので、定期再投入では取り込みの失敗として数え、上限の回数で
  `ingest-failed` にする。数えないと毎時拾い直す
- 古い版のスキーマと層 2 は、定期再投入に任せる
- **入れる前に、件数を数える。** demo の各サイトで、Excel のリソースの数と、`active` の版の数と大きさの
  合計を出し、再処理と定期再投入が何時間で終わるかを見積もる

### 7.3 フォーマットで分岐している所

ADR-057 決定 9 のとおり、Excel については「版にスキーマがあるか」で分岐する。

## 8. 規則の案（Step 2）

### 8.1 案の作り方

素直な表の条件に外れたシートについて、規則が読み方の指示の案を作る。手がかりは ADR-057 決定 4 の
順（行の型の並び、Excel の設定、見出しの帯の結合の形、合計・注記・単位の語）。スパイクの規則
（評価セットの `rules.py`）を TypeScript に移す。

行の型の並びと別の手がかりが一致した案は、「確からしい案」として示す。

移植でスパイクの使い方をそのまま写し、決定 4 の文言と次の 2 点が違った。スパイクの使い方を
正とする（当たり方の数字はこの使い方で測った。2026-11-23）。

- **Excel のテーブル（ListObject）は手がかりにしない。** 格子の読み取りはテーブルを読まない。
  標本で 3 本しかなく、効いたのは 1 枚だった
- **オートフィルターは、データの最初の行を決める多数決に加える。** 枠の固定・印刷タイトル・
  結合の帯と同じく、2 つ以上が同じ行を指せば行の型の並びより優先する。左右の端には使わない

移した規則は、人が確かめた正解 111 枚のうち 88 枚で一致した（スパイクは 89 枚。違う 1 枚は
Excel のテーブルを手がかりにしていたもの）。確からしい案は 45 枚に付き、40 枚が正解だった。

### 8.2 列名のつなぎ方（2026-11-23 決定）

複数行の見出しを、1 つの列名にする。

- 上から順に、親と子をつなぐ。**区切りは `_`**（JSON の入れ子の列名と同じ、ADR-063 決定 10）
- 結合セルの値は、結合の範囲のすべての列に渡す
- **上と同じ部分は重ねない。** 縦の結合や、上と同じ文字が下に書かれた列は 1 つにする
  （「区分_区分」にしない）
- 空の部分は飛ばす。**部分が 1 つも無い列は、列の文字（`A`、`B` …）を名前にする**（左上の空いた
  行見出しの列など）。言語によらず、人が直せる
- つないだ名前が重複したら、2 つ目から `_2`、`_3` を付ける

区切りは `_` のほかに、空白・`／`・`・` が候補だった。`_` は SQL・OData の列名にそのまま使え、
JSON の表と揃うので、ひとまず `_` にする。

### 8.3 矩形 1 つでは表せない形

見出しや注記が範囲の途中にもう一度出るもの、列を横に折り返したもの、段組は、範囲と見出しの
行数ではどう選んでも正しい表にならない（ADR-057 コンテキスト 7）。

- 規則は、これらと「名前を持つ表が縦や横に並ぶ」形（最初の表だけを読めば正しい）を見分けられない。
  どちらも見出しが範囲の外にもう一度出る（§5.5）。見出しの繰り返しに当たった 17 枚のうち 11 枚は、
  規則の最初の表の案が人の正解と同じだった
- **そこで、最初の表の案は出し、「見出しが繰り返されています。最初の表だけの案です。折り返しや
  段組なら表にできません」と添える**（2026-11-23 決定）。罫線の見える画面（§9）で、人が形を判断する
- 理由（`multiple-tables`）は版に記録する
- 人が範囲を選んで確定することは止めない（最初の表だけを読む、など）
- 折り返しを戻す指定、同じ形のかたまりを積む指定は作らない。どのくらい求められるかを、
  この理由の件数で数えてから判断する

### 8.3.1 案の記録

`resource_version.reading_proposal`（jsonb）に、worker が書く。

```ts
interface ReadingProposal {
  /** The rules' proposal, absent when the shape cannot be expressed (§8.3). */
  rules?: TableReading & { likely: boolean }
  /** Every reason the sheet missed the plain-table conditions (§5.8). */
  reasons: NoTableReason[]
  /** AI's proposal (Step 3), with whether it agrees with the rules'. */
  ai?: TableReading & { kind: string; agrees: boolean }
}
```

人が確定したとき、案と確定値が一致したかを監査ログに記録する。一致の割合は、自動にする範囲を
広げるかの材料になる（ADR-057 未決事項 1）。

### 8.4 格子の成果物

確定の画面は、セルの値・結合・罫線を描く（§9）。これを worker が作り、ストレージに置く。

- **画面を開いたときに作る。** 素直でない Excel の版すべてに作ると、開かれない版の分まで
  ストレージを使う。「表の設定」タブを開くと、API がジョブ `excel-grid` を積み、worker が版の
  バイト列から格子を読んで書く。2 回目からは置いてあるものを使う
- 形: シートごと、500 行ごとのかたまりを JSON にして zstd で圧縮する。画面はスクロールに合わせて
  かたまりを取りに行く
- 中身: セルの表示用の値（生の値。日付は ISO）、結合、罫線（線の種類）、非表示の行と列
- 版のバイト列は変わらないので、作り直しは要らない。版がパージされたら一緒に消す

## 9. 確定の画面（Step 2）

「表の設定」タブ（ADR-072）に、「読み方」の欄を足す。ADR-057 決定 10 のとおり、スパイクで作った
確認ページの形をそのまま製品にする。

- 罫線を線の種類（細・中・太・二重・極細・点線・破線）で描き分け、結合セルを結合した形で出す
- セルを選ぶと、番地と結合の範囲を示す。Shift で範囲を選び、選んだ範囲を指示の範囲にできる
- 結合セルを枠で示す切り替え
- 規則の案（と AI の案）を枠で示し、選べるようにする。案が無いときは理由を示す
- 見出しの行数と列名（つないだ名前を初期値に、直せる）を選ぶ
- 確定の前に、選んだ範囲をその版で取り直した結果を示す（§3.3）。選んだ範囲と違えば、確定させない
- 原本の描画（ADR-065）は並べて見せるだけにする
- 主キー・確定型と同じ下書きに入り、1 回の適用で 1 つの版になる

**罫線は、Excel の表示に忠実でなければならない。** 太さの違う線を同じ線で出すと、区切りを
読み違える。画面に入れる前に、数枚を Excel の表示と並べて見比べる。結合セルの周りの線は、
結合の左上のセルの書式で描く Excel の挙動に合わせる。

## 10. 確定値の適用（Step 2）

### 10.1 適用

確定型の適用（ii-c §8.2）と同じ。

- API が `column_settings.readings` を書く。版の同一性が変わるので、同じバイト列から版が 1 つ増える
- 新しい版は、確定した指示で読む（§7.1）。`reading.source` は `settled`
- 読み方が変われば列が変わるので、主キー・確定型の列名が新しい列に無くなることがある。画面は、
  適用の前にそれを示す（確定型の「確定した列が無い」と同じ扱い）

### 10.2 確定した見出しが見つからないとき

次の版で、確定した見出しの帯が見つからないことがある（§3.3）。

| 場合                                     | 扱い                                                                 | 理由               |
| ---------------------------------------- | -------------------------------------------------------------------- | ------------------ |
| 素直な表として読める                     | 規則で読み、表にする。確定した指示が使われなかったことを要確認にする |                    |
| シートが無い                             | 表にしない。要確認にする                                             | `reading-no-sheet` |
| 見出しが見つからない、または複数見つかる | 表にしない。要確認にする                                             | `reading-mismatch` |

- 合わない指示のまま読むと、見出しの行がデータに混ざる・列がずれるなど、表そのものが壊れる。
  確定型と違い、取り込みを続けるより、表にしないほうが害が小さい
- 要確認は、型の変化と同じく、リソース一覧の点と「表の設定」タブに出す（ii-c §8.7）
- 人が指示を直せば、版が 1 つ増えて読み直される。直さずに「この版は表にしない」で受け入れる
  こともできる
- 列が増えた・減ったときの扱いは §10.2.1

#### 10.2.1 列が増えた・減ったとき

列の追加・削除は ii-a からスキーマ差分として記録しているもので、壊れた状態ではない。見出しの帯を
帯の全体の一致で探すと、列が 1 つ増えただけで見つからなくなる。**照合は列ごとに行う。**

- 確定したときの見出しの帯を、列ごとの名前（帯を上からつないだ名前、§8.2）の並びとして持つ
- 新しい版で、見出しの帯の候補（上端から見出しの行数ぶんの行）ごとに列の名前をつなぎ、確定した
  並びが**順序を保って**現れるかを見る。間に新しい列が挟まってもよい
- **見つかったとみなす条件**: 確定した列の半分以上が、順序を保って現れる。そのうち左端の列
  （行の見出しの列）を含む
- 範囲の左端は、見つかった左端の列。右端は、見出しの帯で左から続く見出しのセルの右端まで広げる
  （右に足された列を含める）
- 条件を満たす場所が 2 つ以上あれば、§3.3 のとおり要確認にする
- 確定した列名は、照合で対応した列に当てる。新しい列は見出しからつないだ名前にする
- **列が増えただけなら、表にして要確認にしない。** 減った列があれば、表にしたうえで要確認にする
  （その列が主キーや確定型を持っていたかもしれないため）

### 10.3 素直な表が、更新で素直でなくなったとき

確定した指示を持たず、規則で自動に表になっていたリソースでも、取り直した版が素直な表の条件に
外れることがある（表の下に注記が 2 セルで書かれた、見出しに空のセルができた、など）。

- **自動のままでは読まない。** §5 の条件を緩めて読むと、迷ったら自動にしないという原則が崩れる
- その版は表にせず（`NO_TABLE` と理由）、**前の版が表だったことを要確認にする**。リソース一覧の点と
  「表の設定」タブに出す（ii-c §8.7）
- 放っておくと、プレビューは原本の描画に戻り、層 2 は表の版を受け取らなくなり、OData の利用者は
  更新を受け取れない。黙って起きると「いつまでも残り続ける誤り」になるので、知らせる
- 回復は 1 回の確定で済むようにする。確定の画面は、前の版を規則が読んだ指示（見出しの帯の文字と
  見出しの行数）を新しい版で探して取り直した範囲を、最初の案として出す。見つからなければ、
  規則の案（§8.1）を出す。人が確定すれば、以後は確定した指示で読む（§3.3）

### 10.4 要確認のあいだ、前の版の表を出し続ける（2026-11-23 決定）

URL から取り直すリソースは、人が見ていないときに更新される。§10.2・§10.3 で新しい版を表に
できなかったとき、表を止めると、プレビューは原本の描画に戻り、OData と MCP は「表が無い」で
断り、BI ツールの更新は失敗する。人が直すまで、使っている人のすべてが止まる。

**そこで、要確認のあいだは、前に表だった版の表を出し続ける。**

- 新しい版は層 1 にふつうに入る（版は増え、正本は最新になる）。表にできなかった理由と要確認を
  その版に記録する。層 2 には入らない
- プレビュー・OData・MCP の `/query` は、前に表だった版の Parquet とスキーマを出す
- **古い表を出していることを隠さない。** リソースのページに「表は版 N のもの。最新の版 M は表として
  読めていない（理由）」と、最新でないことが一目で分かる表示を出す。API の応答には、最新でない
  ことのフラグを載せる（`stale: true` と、表の版 `tableVersion`・最新の版 `latestVersion`・理由
  `staleReason`）。プレビュー・リソースの取得・MCP の `/query` の応答に共通に置く。OData は応答の
  中で知らせる手段が乏しいので、フィードの説明（`$metadata` の注釈）に載せる
- 人が指示を直す（または素直な表に戻る）と、最新の版が読まれ、出す表も最新に戻る
- 出し続けるのは、**前の版が表で、新しい版が要確認の理由で表にならなかったときだけ**である。
  最初から表でないリソースや、大きすぎるなどの理由で表にならなかった版では、今のまま表を出さない

今の読み手は、表が最新の中身を表していることを条件にしている（`describesLiveContent`、
リソースのハッシュと解釈したもののハッシュの一致）。この条件に、「前に表だった版を、要確認の印と
ともに出している」という状態を足す。解釈の結果（`resource_pipeline` の `previewKey` とスキーマ）を
前の版のまま残し、どの版のものかを記録する形にする。CSV でも同じことが起きうるが、本フェーズでは
Excel に限る。

## 11. AI の案（Step 3）

ADR-057 決定 11 のとおり。

- 入力は、スパイクで使ったテキストの形（先頭 35 行・末尾 10 行・途中の疎な行、先頭 14 列と末尾
  2 列、行ごとのセルの数、結合、Excel の設定、格子の全体から数えた事実）。**罫線は渡さない**
- 出力は `kind`・`range`・`headerRows`・`columnNames` の JSON。`kind` に、矩形 1 つでは表せない形
  （`repeat`・`fold`・`columns`）を足す。評価で、規則が見落とす複数の表を拾えた
- 形の確かめと検算（範囲のすぐ外に同じ形の行や列が続いていないか）を通らない案は捨てる
- モデルは ADR-040 の提案と同じ設定（`AI_SUGGEST_MODEL` など）を使う。小さいモデルで足りる
- 呼び出しは、版を作ったときでなく、「表の設定」タブを開いたときに行う（§8.4 と同じジョブ）。
  開かれない版の分まで費用を使わない
- 使った量は AI の使用量の記録に入れる

## 12. 評価

- 評価セット（標本・正解・スパイクの規則・採点の道具）はリポジトリの外に置く。公開データだが、
  生データはコミットしない
- §5 の規則を TypeScript に移したら、標本の全シート（XLSX 790、XLS）に当て、次を出す
  - 素直な表と判定したシートの数と割合（スパイクでは XLSX のブックの 25〜33%、XLS の 2%）
  - **素直な表と判定したシートを、すべて人が見る。** 誤りは 0 であることを求める。1 件でも
    あれば、その兆候を外す条件に足す
  - 外れたシートから無作為に数十枚を見て、取りこぼしすぎていないかを確かめる
- 単体テストは、合成した XLSX・XLS で、§5 の各条件の当たる場合と外れる場合を書く
- Step 2 の画面ができたら、AI が付けたままの正解 58 枚を、その画面で人が確かめる。自動にする
  範囲を広げる条件（ADR-057 未決事項 1）は、それが済むまで決めない

## 13. 影響と移行

- `resource_version` に `reading`・`reading_proposal`・`settled_reading` を足す（Step 1 で `reading_proposal`
  の `reasons` だけ、Step 2 で残り）
- `NoTableReason` に §5.8 と §10.2 の値が加わる。管理画面の理由の表示に文言を足す
- `VersionIdentity` に `settledReading` が加わる（Step 2）
- `TABLE_SOURCE_FORMATS` に `xlsx`・`xls` が加わり、既存の Excel の版が定期再投入で解釈し直される
  （§7.2）
- 層 2・OData・MCP は Parquet とスキーマを見るので、変更は要らない見込み。PR 1-d で、表になった
  Excel が層 2 に入り、OData で読めることを結合テストで確かめる
- `docs/pipeline.md` §10（フォーマット別の処理）に Excel の行を足す

## 14. やらないこと・後で判断すること

- 自動にする範囲を広げる（規則と AI の案が一致したら自動、など）: 正解の残りを確かめてから
- 1 リソースから複数の表を出す: 別の ADR
- 同じ形のシートを縦に積む、折り返しを戻す: Step 2 の後、件数を見てから
- Excel のテーブル（ListObject）を手がかりにする: 標本で 3 本しかなかった
- 太字・塗り・列幅・線の色を画面に出す: 要ると分かってから
- AI に表そのものを書かせる: しない（ADR-057 決定 11）
- **要確認を編集者に知らせる仕組み**: 今は管理画面の印だけで、メールなどで知らせる仕組みが無い。
  URL から自動で更新するリソースでは、誰も気づかないまま古い表が出続けうる。型の変化の要確認とも
  共通の課題として、別に扱う
