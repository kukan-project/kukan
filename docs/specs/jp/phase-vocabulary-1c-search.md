# Phase Vocabulary-1c: 語彙による検索の絞り込み — 実装仕様書

> **目標**: 表の列の語彙（ADR-073）で、データセットを探せるようにする。検索画面に「地域」と
> 「列の意味」の 2 つの絞り込みを置く。**語彙の機能は試験的（experimental）として出す。**
> 設計判断は ADR-073 を正とする。

## 1. 前提

- **ADR-073 段階 1a・1b は実装済み。** プロファイルの列に `vocabulary`（概念・体系・表現・
  一致率・階層ごとの一致数・時点）があり、公開ページと「表の設定」タブに出ている
- **語彙はサイトが束を有効にしたときだけ動く**（設定 `vocabulary-packs`、既定は空）。束を
  有効にしていないサイトでは、本フェーズの絞り込みは出ない
- **検索の文書に、語彙は入っていない。** リソースの文書にあるのは列名（`columns`、全文検索用の
  text 型）だけで、プロファイルの役割・値・語彙は入らない
- **プロファイルだけが変わっても、検索の文書は書き直されない。** 未反映フラグ
  （`resource.doc_sync_due_at`）が立つのは、Interpret で列名が変わったときだけである
  （`step-tracker.ts` の `movePointers`）。語彙の読み直し（`rebuildOnly`）でも同じ
- **リソースからデータセットへ件数をまとめる前例は、形式の絞り込みである。** OpenSearch は
  `children{resource}` → `terms` → `parent{resource}`、PostgreSQL は結合と
  `COUNT(DISTINCT package.id)`

### 1.1 確定事項

| #   | 論点                     | 決着                                                                                                              |
| --- | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 1   | 絞り込みの種類           | **「地域」と「列の意味」の 2 つ。** どちらも同じ索引の項目から出せる                                              |
| 2   | 「全国」のまとめ方       | **最上位の区域（都道府県）が 40 以上の列は「全国」とし、都道府県ごとには数えない**（§4.2）                        |
| 3   | 対象にする語彙           | **確定した語彙だけ**（`alternatives` の無いもの）。候補が複数の列は数えない                                       |
| 4   | 試験的の扱い             | 絞り込みの見出しに「試験的」の印を付ける。API の説明にも、形が変わりうると書く（§8）                              |
| 5   | CKAN 互換 API            | **本フェーズでは出さない。** `fq` への対応は後続（§9）                                                            |
| 6   | データセットのメタデータ | **本フェーズでは扱わない。** データセットに対象地域を持たせるのは別に検討する。持たせたら同じ「地域」に足す（§9） |

## 2. 用語

| 用語         | 意味                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 区域         | 語彙の体系の項目（今は全国地方公共団体コード、ADR-073 §9 の後は標準地域コード）                  |
| 最上位の区域 | 区域の親をたどった一番上。日本の束では都道府県                                                   |
| 当たった区域 | 確定した語彙の列で、値が当たった区域の一覧（コードの列はコード、名称の列は名称から決まった区域） |
| 全国の列     | 当たった区域の最上位が 40 以上ある列                                                             |

## 3. プロファイルに当たった区域を記録する（worker）

今のプロファイルは、階層ごとの一致数（`levels`）と時点（`periods`）だけを持ち、当たった区域
そのものを持たない。索引にはそれが要る。

- `columnVocabularySchema` に **`places: string[]`**（当たった区域のコード、重複なし・並べ替え済み）と
  **`roots: string[]`**（その最上位の区域のコード）を足す。どちらも任意（古いプロファイルには無い）
- あわせて **`kind: 'code' | 'name'`**（表現の種類）を足す。索引の `vocab_meanings`（§4.1）は種類で
  分けるが、プロファイルが持つのは表現の ID（`code6`・`name` など）だけで、束ごとに違う。PostgreSQL の
  代わりの経路（§4.4）はプロファイルの jsonb だけから組み立てるので、種類はプロファイルに要る
- コードはどれも束の正規のコード（日本の束では検査数字付きの 6 桁、`130001`）で持つ。索引も API も
  この形にそろえる（§4.1・§5.1）
- **`places` は列全体から作る。** 判定は標本（`INFERENCE_RULES.corroboration.sampleRows`、10,000 行）を
  使うことがあるが、区域の記録に標本を使うと、標本に出なかった区域が抜け、その区域の絞り込みから
  データセットが漏れる
  - コードの列: 列全体の異なる値（判定の 1 段目で読んだもの）から作る
  - 名前の列: 一意な名前は、列全体の異なる値から作る。同名の多い名前を隣のコードの列で決めた列は、
    判定のあとで、その名前の行だけを全行から読み直した（コード、名前）の組で決める。組の数は、
    同名の多い名前の数とコードの異なる値の数で抑えられる
- 記録するのは確定した語彙だけ。候補が複数の列には付けない
- 大きさの上限: `places` は `INFERENCE_RULES.maxValues`（5,000）が上限になる。全国の表で約 1,900 件、
  コード 6 文字で 12KB ほど。`resource_pipeline.profile`（jsonb）に収まる
- 最上位は核の `ancestorsOf` から求める（国に固有の規則を置かない、ADR-073 §8）。区域が最上位
  そのもの（都道府県の列）なら、それ自身を最上位とする
- **規則の版（`RULES_VERSION`）を上げる。** 既存の表は読み直されて `places` が付く

## 4. 検索の索引

### 4.1 リソースの文書に足す項目

| 項目             | 型        | 中身                                                                                                                              |
| ---------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `vocab_meanings` | keyword[] | `<概念>:<種類>` の一覧。例: `admin-area:code`、`admin-area:name`。「列の意味」の絞り込みに使う                                    |
| `area_roots`     | keyword[] | 最上位の区域のコード。全国の列は `*`（全国）だけを入れる。「地域」の 1 段目に使う                                                 |
| `area_places`    | keyword[] | 当たった区域のうち、最上位の区域そのものを除いたもの（その下の区域だけ）。全国の列は入れない。「地域」の 2 段目（市区町村）に使う |

- 1 つのリソースに語彙の列が複数あれば、和集合をとる
- 最上位の区域は `area_roots` にだけ入れる。都道府県の列（東京都だけの列など）は `area_roots` に `130001` が入り、
  `area_places` には何も入らない。2 段目に「東京都」が市区町村と並んだり、`area_place` に最上位の区域を
  指定できたりしないようにするため
- 項目の名前は `vocab_` / `area_` で始め、今の項目とぶつからないようにする
- **マッピングは足すだけ**なので、`ADDITIVE_PROPERTIES` に入れる（`ensureWritableIndex` が
  最初の書き込みの前に `putMapping` する）。既存の文書は、§5 の読み直しか
  「検索インデックスの再構築」で埋まる

### 4.2 「全国」の扱い

- 最上位の区域が 40 以上の列（47 都道府県のほとんどを覆う表）は「全国」とし、`area_roots` には
  `*` だけ、`area_places` には何も入れない
- 理由: 全国の表を都道府県ごとに数えると、どの都道府県で絞っても全国の表が並び、その地域に
  固有のデータが埋もれる。「全国」を選べば全国の表は見つかる
- 割り切り: 「東京都」で絞った人に、東京都の行を含む全国の表は出ない。結果の画面の「全国」の
  件数で気付けるようにする（§6）
- しきい値（40）は `INFERENCE_RULES` ではなく、索引を組む側の定数（`NATIONWIDE_ROOTS`）に置く。
  国によって最上位の数が違うので、束ごとに持たせる余地を残す（今は日本だけなので定数でよい）

### 4.3 文書の書き直し

- **語彙から作る項目が変わったら、リソースの未反映フラグを立てる。** `movePointers` の条件
  「列名が変わった」に、「列の語彙が変わった」を足す。比べるのは、プロファイルの列の `vocabulary` の
  一覧（jsonb）そのものである（`profileVocabularies`、列名の `schemaColumnNames` と同じ形）。一致率だけが
  変わったときにも立つが、余分な同期が 1 回増えるだけで、同じ SQL 文の中で比べられる
- パージ・巻き戻しで派生物を消すとき（`discardDerivedArtifacts`）は、プロファイルも消えるので、
  同じ文の中で未反映フラグを立てる
- 版の採用（`resource-version-service.ts`）には足さない。版の採用は列名を書き換えるが、プロファイルには
  触れないので、語彙の項目は変わらない
- 語彙の読み直し（`refresh-vocabulary-profiles` → `rebuildOnly`）は、この条件で検索の文書まで届く

### 4.4 PostgreSQL の代わりの経路

- 索引の表は持たない。`resource_pipeline.profile` を結合して、jsonb から読む
- 絞り込み: `EXISTS`（リソースと結合し、`profile -> 'columns'` の要素の `vocabulary` を見る）。
  §4.1 と同じ値を SQL で作る関数を 1 つにまとめ、絞り込みと件数で共用する
- 件数: 形式の絞り込みと同じく、`COUNT(DISTINCT package.id)`
- 代わりの経路は小さなサイト向けなので、jsonb の展開の重さは受け入れる。遅ければ、後で
  生成列か索引を足す

## 5. 検索 API

### 5.1 絞り込みの条件

| 条件         | 例                        | 意味                                       |
| ------------ | ------------------------- | ------------------------------------------ |
| `area`       | `area=13`、`area=*`       | 最上位の区域（都道府県）で絞る。`*` は全国 |
| `area_place` | `area_place=131016`       | 当たった区域（市区町村）で絞る             |
| `meaning`    | `meaning=admin-area:code` | 列の意味で絞る                             |

- どれも繰り返し指定でき、同じ条件の中は **または**（形式の絞り込みと違う。地域は「東京都か
  神奈川県」と選ぶのが自然なため）、条件どうしは **かつ**
- `area` は都道府県のコードを 2 桁でも 6 桁でも受ける（`13`・`130001`）。中では束の正規の
  コード（`130001`）にそろえてから、索引の `area_roots`（同じ形、§3）と照らす。`area_place` も同じ
- 下書きの一覧（`my_org` など DB 検索の経路）では、他の絞り込みと同じく断る

### 5.2 件数（facets）

- `include_facets=true` の応答に、`areas`（最上位の区域ごと、`*` を含む）と `meanings` を足す
- 「地域」の 2 段目（市区町村）は、`area` を指定したときだけ返す（`area_places`、選んだ都道府県の
  下の区域に限る）。全国の約 1,900 件を毎回返さないため
- ただし、`area_place` で選ばれている区域は、`area` が無くても必ず件数として返す。選んだ市区町村が
  画面から消えて、絞り込まれたまま外せなくなることを防ぐ（§6 の外し方と二重に守る）
- 件数の名前（「東京都」「千代田区」「行政区域のコード」）は API が付ける。区域の名前は、有効な
  束の登録簿から引く（`@kukan/vocabulary` の `registryFor`）。束に無いコードはコードのまま返す
- ハイブリッド検索の `mergeFacets` と、`PackageService.enrichFacets` は、今は 5 つの絞り込みに
  決め打ちしている。新しい 2 つを足す。`enrichFacets` の「0 件の値も並べる」は、地域には
  当てはめない（47 都道府県を 0 件で並べない）

## 6. 画面

```
┌ 絞り込み ─────────────────┐
│ 🗾 地域  試験的            │
│  ☐ 全国 (37)               │
│  ☐ 東京都 (128)            │
│  ☐ 大阪府 (64)             │
│  もっと見る…               │
│   └ 東京都を選ぶと:        │
│      ☐ 千代田区 (12)       │
│      ☐ 中央区 (9) …        │
│                            │
│ 🔗 列の意味  試験的        │
│  ☐ 行政区域のコード (52)   │
│  ☐ 行政区域の名前 (88)     │
│ 🏢 組織 …                  │
└────────────────────────────┘
```

- `dataset-filters.tsx` に `FilterSection` を 2 つ足す。件数が 0 なら、その絞り込みは出さない
  （束を有効にしていないサイトでは、どちらも出ない）
- 見出しに「試験的」の小さな印を付ける（`Badge variant="outline"`）。説明は title で出す
- `dataset-list.tsx` の `filterParams`（絞り込みのリンクが引き継ぐ条件）と、SSR の `filterKeys` に
  `area` / `area_place` / `meaning` を足す
- 「地域」は、都道府県を選ぶと、その下に市区町村の件数を出す（§5.2）
- 都道府県を外すリンクは、その下で選ばれている `area_place` も一緒に外す。都道府県だけを外すと、
  市区町村の条件だけが URL に残り、結果は絞られたままになる
- **検索結果の各行の語彙のバッジは、段階 2 に回す**（§9）。検索の応答はデータセット単位で、
  リソースの語彙をまとめて返す経路が今は無い

## 7. テスト

- worker: `places` / `roots` の記録。全国の表（最上位 40 以上）、都道府県の列、名称の列（同名を
  コードで決めた区域を含む）、候補が複数の列（記録しない）。`kind` の記録。標本の行数を超える表で、
  標本に出なかった区域も `places` に入ること（同名の名前を隣のコードで決めた列を含む）
- 索引の組み立て: §4.1 の 3 項目。和集合、全国の扱い
- 未反映フラグ: 語彙だけが変わったときに立ち、変わらなければ立たない
- 検索アダプター（OpenSearch と PostgreSQL の両方）: `area` / `area_place` / `meaning` の絞り込みと
  件数。同じ条件の中は「または」、条件どうしは「かつ」
- API: 件数の名前、2 段目は `area` 指定時だけ、束に無いコード。`area=13` と `area=130001` が同じ
  結果になること
- 画面: 件数 0 で出ない、試験的の印、都道府県を選ぶと市区町村が出る、リンクが条件を引き継ぐ、都道府県を
  外すとその下の市区町村の条件も外れる
- API: `area` の無い要求でも、`area_place` で選ばれた区域が件数に入る
- sql-shape の結合テストに、PostgreSQL の新しい SQL を足す

## 8. 試験的であることの示し方

- 画面: 絞り込みの見出しに「試験的」の印（§6）。管理画面の「列の語彙」のカードにも同じ印を付ける
- API: 新しい条件と件数の説明（OpenAPI の description）に「試験的。形が変わりうる」と書く
- リリースノート: 「試験的な機能」として載せる
- ADR-073 のステータスは「提案」のまま
