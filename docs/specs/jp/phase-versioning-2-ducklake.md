ブロックは、いずれも決定ではない。

## 2. 段階分け（本フェーズは一度に全部を実装しない）

行レベル差分の価値は「主キーなしの追加/削除サマリ + スキーマ変化検知」だけで大半が得られる。
主キー MERGE・型降格 UX は上に積む拡張とし、以下の順で段階導入する。

| 段階                    | 内容                                                                                                       |   主キー    | 型降格 UX  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- | :---------: | :--------: |
| **ii-a（MVP）** ✅ 完了 | DuckLake ingest + 主キーなし差分（追加/削除行・行数）+ スキーマ変化検知 + 差分 API + **差分 UI（管理者）** |      –      |     –      |
| **ii-b**                | 主キー指定（リソース設定・手動）→ `MERGE` による**変更行**追跡。列スキーマ履歴                             |  手動指定   |  記録のみ  |
| **ii-c**                | 型降格の選択肢提示 UX、AI による主キー候補・型提案（ADR-040 拡張）                                         | AI 候補提示 | 選択肢提示 |

**ii-a を最小の縦切りとして先に通す**（実データで ingest→差分が成立することを確認する）。
以降は需要とスパイク結果を見て積む。

### 2.1 用語: 「行レベル差分」と「差分サマリ」

ADR-043 の 3 段フォールバック（§7）に従い、UI・ドキュメントで次を区別する。混同すると
「ii-a で変更行が見えるはず」という誤解を生む。

| 用語                           | 段         | 内容                                             | 提供段階 |
| ------------------------------ | ---------- | ------------------------------------------------ | -------- |
| **差分サマリ**（単に「差分」） | 主キーなし | 追加・削除の**行数**とサンプル行。変更は数えない | ii-a     |
| **行レベル差分**               | 主キーあり | 行を主キーで同定し、追加・削除・**変更**を追跡   | ii-b     |

ii-a の画面表現では「行レベル差分」を使わず「差分」と呼ぶ。行の同定を行っていないため、
「変更 N 行」に相当する指標も出さない（§7-2）。

## 3. アーキテクチャ概要

```
層2（本仕様書）: DuckLake（表形式リソースのみ、CSV/TSV・≤50MB から）
  カタログ    既存 PostgreSQL 内の専用スキーマ（例: ducklake）  ← DuckLake 拡張が管理、Drizzle 対象外
  データ      既存バケットの専用 prefix（例: lake/）             ← Parquet 実体、不変・追記のみ
  テーブル    res_{resourceId のハイフン除去}                    ← resource.id から機械導出
  版対応      resource_version.ducklake_snapshot_id             ← 「リソースの版 ↔ DuckLake スナップショット」

  === ingest（Worker、Phase i の Version 捕捉の後段）===
  Fetch → Extract（型推論, ADR-029）→ Version（層1捕捉, Phase i）→ Lake（層2 ingest, 新設）→ Index
    Lake ステップ: 表形式リソースの新版を DuckLake テーブルにコミットし、
                   得たスナップショット ID を resource_version に記録

  === 差分参照（API、新設）===
  GET /resources/:id/versions/:v/diff?from=      ← サーバー組み立ての固定クエリのみ（DuckLake アクセスあり）

  === クエリ（既存, ADR-032）===
  POST /resources/:id/query                       ← ユーザー/AI の生 SQL。DuckLake に触れない（無変更）
```

**DuckLake は層1から再構築可能な派生インデックス**（ADR-043）。カタログ・データが壊れても
全リソースの再 ingest で復元できる。正本は層1の版ファイル。

## 4. Step 1 — DuckLake 統合基盤（`@kukan/lake` パッケージ）

DuckLake に触れるコードを 1 パッケージに隔離する（ADR-005 の思想。api=読み取り / worker=書き込み
以外から DuckLake に触れさせない）。

1. **接続**（DuckDB セッションで ATTACH）:

   ```sql
   ATTACH 'ducklake:postgres:host=<pg> dbname=<db>' AS lake (
     DATA_PATH 's3://<bucket>/lake/',
     METADATA_SCHEMA 'ducklake'
   );
   ```

   - カタログは意味層と同一 PostgreSQL に同居（差分・版対応と JOIN 可能な一枚岩）。
     DuckLake カタログ表は **Drizzle のマイグレーション対象外**
   - ATTACH の接続文字列は **libpq の keyword 形式**（`host=… dbname=…`）であり URL ではない
   - ストレージ接続: S3StorageAdapter と同じ資格情報・エンドポイントを DuckDB の S3 secret に
     流し込む。**MinIO は `URL_STYLE 'path'` + `USE_SSL false` + `ENDPOINT host:port` が必須**
     （`S3_ENDPOINT` の URL から host:port と ssl 可否を分解する）。AWS S3 では endpoint を省く
   - 拡張 `httpfs` / `postgres` / `ducklake` は `INSTALL` + `LOAD` で読み込む（スパイクで
     オフライン環境でも成功を確認済み）

2. **テーブル命名**: `res_{resourceId のハイフン除去}`。`resource.id` から機械導出でき逆引きも一意。
   人間可読名は DuckLake に持ち込まない（リソース改名を物理層に波及させない）
3. **書き込みはカタログ全体で直列化**: `pg_advisory_xact_lock(LAKE_INGEST_LOCK_KEY)` を取り、
   「ロック取得 → DuckLake トランザクション → 意味層更新（`resource_version`）→ コミット」を
   1 ジョブハンドラで行う。**1 版更新 = 1 DuckLake トランザクション**（複数テーブルをまたぐ
   コミットはしない → 版とスナップショットの対応を単純に保つ）。

   リソース単位ではなくカタログ全体なのは、**スナップショット ID がカタログ共通の連番**で、
   コミットしたスナップショットを「読み直した最大値」で同定しているため。2 つの ingest が
   並行すると互いの ID を観測し得る。ingest はリソースの内容が変わったときだけ走るので、
   直列化のスループット代償は同定の確実さに見合う。テーブル単位で ID を属性取得できるように
   なれば、ロックは不要になる（将来の改善余地）

4. **障害時の整合**: リコンシリエーションは**両方向**を見る。

   - **意味層に対応行のないスナップショット**（DuckLake コミット済み・意味層未更新の瞬間に
     落ちた）は「未確定」。監査ログに記録して放置（未参照スナップショットは無害、後述の
     expire で自然回収）または expire する
   - **版行が名指ししていて解決しないスナップショット**は `ducklake_snapshot_id` を null 化し、
     §7 の 3 段フォールバックへ縮退させる。**解決しない**には 2 通りある — カタログにその
     スナップショットが無い（既に expire 済み）、**カタログにはあるがファイルが無い**
     （cleanup / 孤児掃除 / ライフサイクルが消した後）。**後者はファイルの実在確認が要る**
   - **テーブルの現在内容が読めるかを、列を読んで確かめる。** 版行の null 化は意味層の
     ポインタを外すだけで、欠損ファイルを掴んだテーブル自体は直らない。**`count(*)` では
     判定できない**（カタログ統計から答えるので通ってしまう）。そして**現在 head は版行が
     名指ししていないことがある**ので、版行を全部確認しても head の破損は見つからない —
     **この確認は版ではなくテーブルに対して行う**。読めないテーブルの直し方は 2 通りあり、
     どちらを採るかは**最新の健全な層 2 版があるか**で決まる（§11-5。live 版ではない）

   後ろ 2 つが要る理由と実測は §11-5。

## 5. Step 2 — Lake ingest ステップ（Worker）

`apps/worker/src/pipeline/steps/lake.ts` を新設し、`processResource` の **Version ステップの後**に
挿入する（層1の版が確定してから層2へ）。

- **対象**: 表形式（CSV/TSV・≤50MB、現行の Parquet 生成対象と同一）。それ以外はスキップ。
- **入力**: Version ステップが今回新しい版（vN）を捕捉した場合のみ動く。Extract の型推論結果
  （`ResourceSchema`）を列型として使う。
- **ingest ロジック**（段階で深くする）:
  - **ii-a**: 版ごとに **テーブルへ全行を投入**（主キーなし＝全行置換）。DuckLake の
    コピーオンライトで変わらないファイルは版間共有され、書き込みは差分コスト。
  - **ii-b**: 主キー指定ありなら `MERGE`（後述 §7）で行単位に反映。
- **スナップショット記録**: コミットで得た `snapshot_id` を `resource_version.ducklake_snapshot_id`
  に書く。以後「版 vN の読み取り」= `SELECT ... FROM lake.res_x AT (VERSION => snapshot_id)`。
- **非クリティカル**: Lake ステップの失敗はステップに記録するがパイプライン全体は継続する
  （層1の版・プレビュー・検索は動く）。層2は後から再 ingest で追随できる。

### 5.1 DB スキーマ追加（`resource_version`）

Phase i の `resource_version` に列を追加する（Drizzle マイグレーション）:

- `ducklake_snapshot_id BIGINT`（表形式版のみ非 null。層2の版の指し先）
- （ii-b）主キーは**リソース設定側に現在値、版側に使った値**（`lake_key_columns`）を持つ（§6.1）。

  > 当初ここには「版側には不要」と書いてあった。**§6.1 がこれを覆す** — 版ごとに差分の意味論が
  > 違う以上、どの版がどのキーで取り込まれたかは版側にしか書けない。

### 5.1.1 同一リソースの並行実行

`resource_pipeline` は SQS のメッセージ単位で起動し、パイプライン全体を同一リソースで
直列化する仕組みは無い。重複メッセージや連続更新で 2 つの実行が重なり得る。

**実行ごとに書き込み先を分ける**: リソース本体のキーは実行固有
（`resources/{packageId}/{resourceId}.{writeToken}`）とし、`resource.storage_key` が現在の
内容を指すポインタになる。ポインタ・`hash`・`size` は**同一文で**動かし、移動は
「実行開始時に読んだポインタ値のままであること」を条件とする。これにより、どの実行が
どの順で完了しても行は自分が指すオブジェクトを記述する。条件を満たさなかった実行は
自分のバイト列がもう内容ではないと分かるので、以降のステップを行わない。

置き換えられたオブジェクトは削除せず `orphaned_object` に積み、スイープが保持期間後に
消す（§ プレビューと同じ機構）。

**版の確定は直列化する**: 「版番号の決定 → 版ファイルへの copy → 版行の挿入」を
`pg_advisory_xact_lock(hashtextextended('resource_version:' || resourceId, 0))` の下で、
**1 つのトランザクション上で**行う（`PipelineContext.createVersion`）。これが無いと 2 実行が
同じ vN を選び、一意制約により片方の行だけが残る。

ロック中の問い合わせは**必ずそのトランザクションの接続で行う**。ロックを保持したまま
プールへ別接続を要求すると、保持数がプール上限に達した時点で相互待ちになる（worker の
プール上限は 3）。移行も同じロックを取り、ロック内でポインタが動いていないことを
再確認してから copy する。

**アップロードのハッシュは worker が計算する**: `upload-complete` はサイズだけを記録し、
hash は null のままにする。版の変更ゲートと版行の hash はこれに依存するため、Fetch が
必ず実体から計算する（クライアントが「以後版を作らせない」を選べてしまうため）。

copy 後のハッシュ検証は不要になった。copy 元は実行固有キーで誰も書き換えないため、
Extract が読んだバイト列・Fetch が計測したハッシュ・版が保持するバイト列は同一である。
`sourceHash` の突き合わせも版の確定には要らない（プレビューがどの内容を描いているかの
判定にのみ使う。§5.2）。

### 5.2 既存データの取り込み（一度きりの移行に同梱）

層2は新しく取り込まれる版から効くため、そのままでは既存リソースは差分の対象にならない。
Phase i の一度きりの移行（管理画面の導線）に層2の取り込みを同梱して解決する:

1. **層1**: 版が無いリソースの現行ファイルを v1 として copy + 版行を作成（既存の動作）
2. **層2**: 表形式リソースの**現在の版**を DuckLake に取り込み、snapshot を記録（新規）

**なぜ現在の版だけか**: プレビュー Parquet は版ごとに保存されず常に最新版の内容を持つ。
したがって過去版を遡って取り込むことはできない。現在の版だけが取り込め、以後その版と
次の版の間から差分が出る。

プレビューのキーはパイプライン実行ごとに一意にする
（`previews/{packageId}/{resourceId}.{writeToken}.parquet`）。読み手は
`resource_pipeline.preview_key` のポインタを辿るので、一度解決したオブジェクトが後続実行に
書き換えられることがない。置き換えられたキーは `orphaned_object` テーブルに積み、
保持期間（既定 1 時間）を過ぎたものを**毎時のスイープジョブ**が削除する — ポインタ更新の
直前に旧キーを解決したリクエストを切らないため。ライブ本体のキーも同じ表と同じスイープで
回収する（ADR-043、リソース本体の実行固有キー化）。

**どの版に紐付けてよいかの判定**: Extract は生成したプレビューと一緒に、その元になった
バイト列のハッシュを `metadata.sourceHash` に記録する。移行はこれが版のハッシュと
一致する場合だけ取り込む。版のハッシュや Extract ステップの成否では不十分で、移行は
現行ファイルから版を*作る*ため両者のハッシュは必ず一致してしまう（ファイル差し替え後、
パイプラインが queued の間は古いプレビューが残っている）。

**導入前のプレビューには `sourceHash` が無く、それこそが移行の対象**なので、次の弱い条件に
フォールバックする: パイプラインが `complete`（新しいファイルの背後で再キューされていない）
かつ版がリソースの現行内容であること。記録済みハッシュが閉じている窓＝「差し替え済みで
まだパイプラインが走っていない」は、この `status` 条件が排除する。

取り込みは 1 セッションで直列に行い、advisory lock はリソースごとに取る（移行中ずっと
ロックを保持するとパイプライン側の取り込みを止めてしまうため）。1 件の失敗は他を巻き込まない。

管理画面の移行カードは、層1（版なし）と層2（未取り込み）の**両方の残件数**を表示し、
どちらも 0 になったら消える。

## 6. Step 3 — 確定スキーマ層と主キー指定（ii-b）

### 6.1 推定スキーマと確定スキーマの分離

現在 KUKAN が持つ列スキーマは**すべて推定**（ADR-029 の型推論の産物）であり、人が確定・上書き
する経路がない:

| 層                        | 保存先                                                                                    | 書き手                     | 上書き規則                       |
| ------------------------- | ----------------------------------------------------------------------------------------- | -------------------------- | -------------------------------- |
| **推定**（システム）      | `resource_pipeline.metadata -> 'schema'`（最新）/ `resource_version.schema`（版ごと凍結） | worker（Extract・Version） | 再実行のたびに再計算・上書き     |
| **確定**（人）★ ii-b 新設 | `resource_column`（列単位の確定メタデータ）                                               | 管理者（UI 経由）          | 人の決定。パイプラインは触らない |

**主キーは推定の産物ではなく人が確定したスキーマ情報**であり、ii-c で管理者が選ぶ確定型も同じ
性質を持つ。両者を同じ確定層に置くことで、(a) 推定の再計算が人の決定を壊さない、(b) 主キーと
確定型が別々の場所に散らない、という2点を同時に満たす。

#### 確定層は「設定」と「使った規則」の組である

**設定を現在値だけで持つと、過去の版がどう取り込まれたかを誰も答えられない。** これは
このリポジトリが既に 2 回答えを出している形で、`format` と `schema` がどちらも
「リソースが現在の規則を持ち、版は自分が作られたときの規則を持つ」対になっている
（`resource_version.format` のコメント、ADR-046 §6 — リソースのラベルは編集できるので、
現在のラベルで確定済みの bytes を解釈すると**適用されたことのない規則で読む**ことになる）。

|                | どこ                                                                    | 何                               |
| -------------- | ----------------------------------------------------------------------- | -------------------------------- |
| 設定（現在値） | リソース側（下記）                                                      | 以後の版に適用する主キー・確定型 |
| 使った規則     | `resource_version` に 1 列追加（例 `lake_key_columns`、null = keyless） | **版の作成時に凍結した**キー列   |
| 解釈の結果     | `resource_version.schema`（既存）                                       | 版ごとに凍結                     |

**版側が要る理由は 3 つある。** (a) 差分が変更行を出せるのは両側が同じキーで取り込まれたとき
だけで、途中でキー指定が変われば境界で意味論が切り替わる。(b) 差分の意味論が版ごとに違う以上、
どの版がどう取り込まれたかは版側にしか書けない（1 リソースが v1〜v5 は keyless、
v6 以降 keyed は普通に起こる）。(c) キー指定変更の履歴そのもの。

**確定型は版側に足さなくてよい。** 確定型がゲートの 3 つ目の入力になれば（後述）、確定型を
変えると新しい版が立ち、その版の `resource_version.schema` が確定型込みの解釈結果として
凍結される。主キーだけが自分の記録場所を要るのは、`schema` に主キーの宣言が無いためである
（`ResourceColumn.unique` は「候補として提示できるか」を計算した値であって、人が指定したか
どうかではない）。

### 6.2 設定の置き場所（ii-b で決める）

列単位に、人が確定した情報だけを持つ（推定値は複製しない — 推定は上記の推定層から読む）:

- 列の同定（`name`）
- 主キー構成列か（複数列可）
- 確定型（ii-c。未設定なら推定に従う）
- 将来: 説明・別名・機微フラグ等、人が与える列メタデータの置き場所

**名称は決めていない。** `resource_column` は素直だが、`packages/shared` の `ResourceColumn`
が既に**推定**列の型（`resource_version.schema` の jsonb 要素）であり、並ぶと型がその
テーブルの行を表すと読める。§6.1 が分けようとしている推定と確定を、名前が混ぜてしまう。
`resource_column_setting` 等を含めて着手時に決める。

候補と検討状況:

| 案                                 | 評価                                                                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **専用テーブル**                   | 列単位の一意制約を DB で担保でき、横断クエリが素直。将来の列メタデータが育つならこれ                                                      |
| **`resource` の専用 jsonb カラム** | 1:1・全体読み・全体書きなら十分。書き手は人だけなので混在しない（`pending_metadata` 等の前例あり）                                        |
| ~~`resource_pipeline.metadata`~~   | パイプライン**未実行だと行が無く**設定できない。worker が `\|\|` でマージ書き込みする領域に人の決定を同居させると、産物の再計算で壊れうる |
| ~~`resource.extras`~~              | cron の health-check 運用値と混在し、列単位の粒度を持てない                                                                               |

**決め手は「列ごとに独立して読み書きするか」である。** そして下記の「確定操作は 1 版に
まとめる」制約が、テーブル側の根拠を 1 つ削っている — 書き込みは最初からまとめてであり、
読みも主キーは列の集合として ingest 時に丸ごと読む。ii-b が必要とするものだけなら jsonb
カラムで足り、テーブルは ii-c 以降の列メタデータへの賭けになる。

### 6.3 確定型を導入したときの表示経路への影響（ii-c の論点）

現行の列型表示は**すべて推定ベース**であり、確定層を持ち込むと以下の 3 経路すべてに
「確定型があればそれを優先する」判断が要る:

| 経路                                              | 実体                                       | 出所                           |
| ------------------------------------------------- | ------------------------------------------ | ------------------------------ |
| リソース詳細の列一覧（`useParquetSchema`）        | プレビュー Parquet のフッターを Range Read | **推論結果で焼かれた Parquet** |
| `GET /:id/schema`（MCP `get_resource_schema` 兼） | `resource_pipeline.metadata -> 'schema'`   | 推定スキーマ                   |
| 版履歴の列スキーマ                                | `resource_version.schema`                  | 版ごとに凍結した推定           |

とくに**プレビュー Parquet は推定型で物理化されている**ため、確定型が推定と食い違う場合に
「Parquet を焼き直す（再 Extract）」か「表示層だけ確定型で上書きする」かの判断が必要になる。
ii-c 着手時に決める（ii-a/ii-b では確定型を持たないため発生しない）。

### 6.4 主キーの扱い

- **管理者が UI で主キー列を任意指定**（複数列可）。指定があれば Lake ingest が `MERGE` 経路に
  切り替わる。**ii-b は手動指定のみ**。
- **主キー指定の変更は版を作る。** 版は「その bytes を、この解釈で読んだもの」であり
  （ADR-046 決定 3）、キーは解釈の一部である。bytes は動かないので新しい版は**同じ内容の複製を
  所有する**（ADR-046 §3 の規則がそのまま働く — 既に持たれているオブジェクトは複製する）。
- したがって**境界は版そのものである。** 「以後の版から適用」の「以後」はその版自身から始まり、
  過去版の差分意味論は遡って変わらない。
- 候補の算出は済んでいる。ADR-046 の解釈が列ごとに `distinctCount` と `unique`
  （全行が非 null かつ相異なる）を出して `resource_version.schema` に凍結しているので、
  ピッカーが候補を出すのに新しい計算は要らない。**ただしこれは単一列キーまで**である
  （下記「複合キー」）。

> **当初は「主キー指定そのものは版を作らない」と書いていた。** 正本 2 つ（ADR-046 決定 3、
> ADR-043 §1-4 の注）がどちらも逆を言っており、**同じ §6 の中の UI 節（§6.5）ですら
> 「複数列をまとめて選び、1 回の適用で 1 つの版にする」と書いていた** — 孤立していたのは
> この一文のほうである。

#### 凍結は版の作成時に行う

**`lake_key_columns` は Version ステップが書く。Lake ステップではない。** 版行を作った瞬間の
リソース側の設定値をそのまま写し、Lake は**版行から読む**。リソース側の現在値は見ない。

**版が生まれる道は 2 つあり、どちらもこの規則 1 つで足りる。** 内容が届いたとき（キーはその
時点の設定値）と、キー指定が変わったとき（キーは新しい設定値）である。

**Lake 実行時の現在値を読んではならない。** Version と Lake は非同期で、失敗した取り込みは
掃き出しが後から再実行する（§14.1）。キーの変更は版を作るので、**その版が取り込まれる前に
さらにキーが変われば、また別の版が立つ** — 現在値を読むと、既に作られている版が自分の番号と
違う世代のキーで取り込まれる。版に凍結してあれば、掃き出しが何時間後に走ろうと同じキーで入る。

**これはこのリポジトリが 2 度出している答えと同じ形である。** `resource_version.format` が
「リソースのラベルは編集できるので、現在のラベルで確定済みの bytes を解釈すると**適用されたことの
ない規則で読む**ことになる」という理由で版側に凍結されており（ADR-046 §6）、`schema` も同じ。

#### キー変更版が層 2 に着いたときに何が起きるか

**直前の版が層 2 に入っていれば、内容は動かない。** その版の bytes は直前の版と同じなので、
新しいキーで `MERGE` しても値の述語が全て false になり、削除側も一致しない。**1 スナップショットを
消費して、行は 1 つも書かれない。** そのスナップショットが「ここからキー体系が変わった」という
境界の記録になる。

**入っていなければ普通に書く。そしてそれがキー修正の通常経路である。** 直前の版が
`key-missing` / `key-not-unique` で断られていれば、層 2 の現在内容は**もっと古い版**である。
そこへ新しいキーで同じ bytes を載せれば、`MERGE` は現在内容との実差分を書く — 書かれる量は
「キーが壊れていた区間で内容がどれだけ動いたか」であって、キー変更そのものの代償ではない。
**「キー変更版は必ずゼロ書き込み」と考えてはならない。**

**新しいキーがその内容で一意でなければ、その版は層 2 に入らない**（`key-not-unique`、§6.6）。
版そのものは成立している（層 1 にあり、ダウンロードできる）ので、失うのはその版を端点とする
行レベル差分だけである。**キーの指定が妥当かは、適用前に確認画面で見せる** — 版を作ってから
断るのは、操作者にとって「適用したのに効かない」と区別が付かない。

#### キー列は NULL を含んではならない

`MERGE` の `ON` は `=` であり `NULL = NULL` は成立しない。NULL を持つ行は既存行に**永久に
マッチせず**、版ごとに再挿入される。テーブルの中でキーがキーでなくなり、以降の版では
1 つのソース行が複数の対象行に一致して両方が更新されるため、**行レベル差分は以後ずっと
狂う**（実測: `merge.ducklake.test.ts`）。

`IS NOT DISTINCT FROM` を使えば NULL 同士をマッチさせられるが採らない。「2 つの unknown は
同じ行」はデータに対する主張であり、ADR-043 が退けた「推測による偽の変更履歴」そのものである。
公開者が「NULL は 1 つの値」を意図しているなら、センチネル値で表明すべきことである。

判定根拠は `resource_version.schema` の `nullable` / `nullCount` で、**追加計算は要らない**。

#### 複合キー

- `MERGE` は複合キーを受ける（`ON t.a = s.a AND t.b = s.b`。実測済み）
- **成分のいずれかが `nullable` なら不可。** 組み合わせの一意性とは独立した条件であり、
  一方から他方は導けない（個々が非ユニークな 2 列が組では一意、が複合キーの典型）
- **凍結スキーマは組み合わせの一意性を答えられない。** 持っているのは列ごとの
  `distinctCount` だけである。複合キーの検証は実データに対して行う必要がある
- `count(DISTINCT a, b)` は**バインダエラー**になる。`count(DISTINCT (a, b))` か
  `SELECT count(*) FROM (SELECT DISTINCT a, b …)` を使うこと

#### 検証はどこで、破れたらどうするか

|                | 判定の時点                 | 破れたときの扱い                                                 |
| -------------- | -------------------------- | ---------------------------------------------------------------- |
| **キー設定時** | 現行版のスキーマ           | **エラー。設定させない**。同期的で人がいて、内容が懸かっていない |
| **取り込み時** | その版のスキーマと実データ | **その版を層 2 に取り込まず、理由を記録する**                    |

**版そのものは拒否しない。** キー列の NULL は公開者のデータの性質であって、システムのエラー
ではない。内容は正当で、動かないのは行対応付けだけである。版を拒否すれば、公開者が更新した
つもりでいる横でリソースが古い内容を配信し続けることになり、差分が得られないより悪い。
キー指定は解釈の補助であって、データとの契約ではない。

**キーレスへは降格しない。** キーあり履歴の中に 1 版だけ全行置換を混ぜると、その版の差分は
全行が delete + insert として描画される。実際は 1 行のキーが空いていただけなのに「全行が
変わった」という**偽の履歴を事実として提示する**ことになる。取り込まない方が正直である。

- **ii-c**: ADR-040 の AI 提案基盤に「主キー候補提示」を追加（列のユニーク率・null 率を
  決定的に算出 → 候補提示、断定しない）。確定は常に人が行う。

### 6.5 確定型は版のゲートの 3 つ目の入力になる（ii-c、着手前に読むこと）

版とは「**このバイト列を、この読み方で**」である（ADR-046 §3 / §6）。現在の
`decideVersionCreate` が見ているのは**ハッシュとフォーマットの 2 つ**で、確定型は入っていない。

**そのまま確定型を入れると記録が壊れる。** 確定型を変えてもハッシュもフォーマットも動かない
ので版が立たず、`resource_version.schema` だけが上書きされ、「その版が何と読まれたか」を
版が答えられなくなる。確定型は人が決めた読み方であり、フォーマットと同じ性質を持つので、
**ゲートの 3 つ目の入力にする**必要がある。

#### 確定操作は 1 版にまとめる必要がある

これが UX を決める。確定型の変更は**バイト列を変えない**ので、live のオブジェクトを既存の版が
所有している状態にあたり、版の作成は必ず**複製経路**を通る（ADR-043 §1 — 誰も持っていない
オブジェクトは取り、既に持たれているものは複製する）。

つまり **1 回の確定 = 版 1 つ + 同じバイト列の複製 1 つ**である。管理者が 5 列を 1 列ずつ
確定していけば、版が 5 つと複製が 5 つ積み上がる。

したがって UI は「列ごとに即時確定」ではなく、**複数列をまとめて選び、1 回の適用で 1 つの版に
する**設計にする。この制約は置き場所（§6.2）の選択より先に決まっており、列単位の部分更新を
そもそも望まないことを意味する。

### 6.6 取り込まなかった理由を版に記録する（ii-b で新設）

**取り込みが版を断ったら、その理由を専用の列に記録する。** 掃き出しはそれを読んで対象から外す。

- 列: **`lake_ingest_reason`**（`key-missing` / `key-null` / `key-not-unique`。取り込めた版と
  未処理は null）
- 書き手: **Lake ステップ**。解釈が書く `no_table_reason` には触れない
- 掃き出し: 「`no_table_reason IS NULL AND lake_ingest_reason IS NULL`」を条件に加える
- **自動でクリアしない。書き込み一度きり。** キー指定の変更でもクリアしない（下記）

**理由は 3 つで、検査は取り込みの前に全部済ませる。**

| 理由             | 条件                                                       |
| ---------------- | ---------------------------------------------------------- |
| `key-missing`    | 版のスキーマに**キー列が無い**（後続版で削除・改名された） |
| `key-null`       | キー列に NULL がある                                       |
| `key-not-unique` | キーの組が一意でない                                       |

**`key-missing` を独立の理由として持つ必要がある。** 版が凍結したキー列が、その版の内容に
存在しないことは普通に起きる — 公開者が列を落とす・改名するだけでよい。**このまま `MERGE` を
発行すると binder error になり、理由が記録されないまま毎時再試行される**。それは
`lake_ingest_reason` が防ぐために作られた事故そのものである（下記「6.6 の理由」）。

**検査は版の凍結スキーマ（`resource_version.schema`）に対する列名の照合**で足り、内容を読む
必要がない。3 つのうち唯一、取り込み経路を開く前に答えが出る。

以下は理由である。

#### 6.6 の理由

**掃き出しが永久にリトライするのを止めるための機構である。** `pendingLakeIngestQuery` は
「active・`ducklake_snapshot_id` が null」の版を拾う。キー列の NULL で取り込まなかった版は
その条件に永遠に該当し続け、毎時 queue されては毎回スキップされる。#423 で
`pendingLakeIngestQuery` と ingest 側の順序チェックを揃えたのと同じ形の事故である。

既存の `NoTableReason`（`no-columns` / `too-many-columns` / `too-large`）が今それを免れて
いるのは、**すべて凍結スキーマに対する述語として書けている**からである（列数・サイズ）。

**キーの検証はこの形に乗らない。** `key-null` は述語化できるが、`key-not-unique` は
できない — 凍結スキーマは列ごとの `distinctCount` しか持たず、複合キーの組み合わせの
一意性を答えられない（§6.4）。理由ごとに掃き出しの `WHERE` を伸ばしていく形は、ここで
行き止まりになる。

したがって **`resource_version` に理由を記録し、掃き出しは「理由が記録済みの版」を除外する**。

**ただし既存の `no_table_reason` に相乗りさせてはならない。** この列は解釈が書くもので、
**再解釈が表を見つけたらクリアされる**（`recordVersionSchema` が「無し」を null と綴る。
`build-context.ts` にその理由が書いてある）。キー不正の理由を同じ列に置くと、再解釈のたびに
消える。しかも書き手が違ううえに、2 つの経路で**順序が逆**である:

| 経路                            | 順序                                                | 相乗りさせた場合           |
| ------------------------------- | --------------------------------------------------- | -------------------------- |
| 本経路（`process-resource`）    | Interpret で記録 → **後で** Lake ステップが取り込む | 書く場所が無い             |
| リトライ（`retry-lake-ingest`） | 取り込む → 記録                                     | 直後に null で上書きされる |

**発見した者が自分の列に書く。** 既存 3 理由は述語のままでよく（動いている）、
`no_table_reason` を保存するかどうかはこの列とは独立に決めてよい。

**この列は自動でクリアしない。書き込み一度きりである。** 解釈と違って、同じバイト列を何度
取り込み直してもキーが不正なら毎回同じ理由になるので、消して掃き出しに再挑戦させる意味が無い。

**キー指定の変更でもクリアしない。** キーを変えれば**新しい版が立つ**（§6.4）ので、その版が
新しいキーで取り込まれる。断られた過去版まで遡って入れ直すのは「過去版の差分意味論は遡って
変えない」に反し、v1..v4 が旧キー、v5 が新キーという層 2 の中で、v4 → v5 の差分だけが
キー体系をまたぐことになる（§7 の 1 段目がその境界を縮退として扱う）。

**したがって断られた版は層 2 に入らないままになる。** 失うのはその版を端点とする行レベル差分
だけで、§7 の 3 段フォールバックが受け止める（内容は層 1 にあり、ダウンロードも一覧も無傷）。
**キー設定を直した後で過去版も入れ直したい場合は、運用者が明示的に再投入する** — 自動で
起きてはならない操作なので、入口を作るかは §14.1 の判断にする。

## 7. Step 4 — 差分抽出（3段フォールバック）・差分 API・差分 UI

ADR-043 §3-6 の 3 段フォールバックを実装する。

1. **両端が同じキーで取り込まれている** → **両端の内容をそのキーで突き合わせる**。
   `AT (VERSION => …)` で from / to の内容を出し、主キーで `FULL OUTER JOIN` して
   **追加・削除・変更**を数える。変更の判定は非キー列の `IS DISTINCT FROM`（取り込み側の
   述語と同じ形。`keyed-load.ts`）。**`table_changes` は使わない** — 下記「差分は端点の
   突き合わせで出す」。

   **判定は「両端にキーがあるか」ではなく「両端の `lake_key_columns` が一致するか」である。**
   §6.1 が言うとおり変更行を出せるのは同じキーで取り込まれたときだけで、キー指定が変われば
   境界で意味論が切り替わる。**異なるキーの両端は 2 段目へ縮退する**（`keyed: false`）— 別々の
   同定規則で数えた「変更行」は、どちらの規則にも属さない数である。片端だけキーがある場合も同じ。

2. **主キーなし・または両端のキーが違う** → 全行置換 + 統計サマリ（「N 行中 x 行追加・y 行削除」）。行の対応付けは
   行内容ハッシュの一致のみで判定し、**「変更行数」は数えない**（主キーなしで変更と追加+削除は
   区別できない。推測で偽の変更履歴を作らない）。
3. **スキーマ変更**（列の増減・型変化）→ 行差分を放棄し、**新版 + スキーマ変更の記録**とする。

**差分 API（新設）**: `GET /resources/:id/versions/:v/diff?from=<v'>`（既定 `from` = 直前版）。

- 返却: `{ keyed, addedRows, removedRows, changedRows?, schemaDiff, sampleRows }`。
  **`keyed` は ii-a で先に入れてある**（常に `false`）。`changedRows` の不在だけでは
  「キーが無いので測っていない」と「キーがあって変更ゼロ」を区別できないためで、ii-b は
  `keyed` の型を広げて `true` と `changedRows` を返す。
- **SQL はサーバーが組み立てる固定クエリのみ**（パラメータは版番号のみ）。ユーザー/AI の生 SQL は
  DuckLake に触れない（ADR-032 のサンドボックスは無変更、§10）。
- 可視性チェックは ADR-017/032 と同じ経路。第一の消費者は管理者（品質・監査）。

#### 差分は端点の突き合わせで出す

**`table_changes` はイベントログであって差分ではない。** 数が合わない理由は 2 つあり、
どちらも `DISTINCT rowid` では直せない — あれは §11-2.1 の 2 文形が同じ行を複数回報告する
（[ducklake#1387](https://github.com/duckdb/ducklake/issues/1387)）ための重複排除であって、
意味的に相殺すべきイベントには効かない。以下の数字はすべて重複排除を掛けたあとの値である。

- **始端が inclusive。** `table_changes(from, to)` は `from` 自身が書いたイベントを含む。
  **既定の隣接版でも狂う** — 2 万行 × 100 版で v99 → v100 の真値 200 変更に対し 300。
  **これは仕様どおりで、ドキュメントに明記されている**（"two bounds: the start snapshot and
  the end snapshot (inclusive)"）。上流に言うことは無く、**イベントログの境界を差分の境界と
  読んだ我々の側の誤り**である
- **範囲でイベントが相殺されない。** 行が変わって元に戻る・追加されて削除される形は、端点間では
  差分ゼロだが、イベントとしては両方が残る。v1=(1,a) → v2=(1,b),(2,x) → v3=(1,a) では v1 と v3 が
  完全に同じなのに 追加 1・削除 1・変更 1。各版が 100 行変えて次の版が戻す形（2 万行 × 100 版）
  では、v0 → v100 の真値 100 変更に対し **10000**

**端点の突き合わせは正しく、しかも速い**（2 万行・100 版・ローカルカタログ）:

| 差分                 | `table_changes`（始端補正済み） | 端点 `FULL OUTER JOIN` |
| -------------------- | ------------------------------: | ---------------------: |
| 隣接（v99 → v100）   |                         26.3 ms |            **20.4 ms** |
| 100 版離れ（v0→v100) |                         38.9 ms |            **15.2 ms** |

イベント数は版の距離に比例し、端点比較は行数にしか比例しないので、**範囲が広がるほど差が開く**。
差分 API は既定こそ直前版だが `from` を取るので、広い範囲は普通に来る。

**副産物として、差分 API は ducklake#1387 に依存しなくなる。** §11-2.1 の `DISTINCT rowid` は
取り込みの検証で使う知見として残るが、§7 の設計はそれを前提としない。

**そして ii-a の実装は既にこの形である。** `buildDiffQuery`（`packages/lake/src/diff.ts`）は
両端を `AT (VERSION => …)` で開き、±1 マーカーを付けて畳んで net を取る — `table_changes` は
一度も使っていない。ii-b が変えるのは**畳む単位だけ**で、「行の全内容」から「宣言された主キー」に
なり、net が 0 でないキーのうち両側に居るものが変更行になる。**この節が退けているのは、実装では
なく本仕様の設計メモのほうである**（上の 1 段目は当初 `table_changes` と書いていた）。

**全列が主キーの表では「変更」は定義上起こらない。** 突き合わせる非キー列が無いので、
追加と削除だけになり `changedRows` は常に 0 になる。取り込み側も同じ理由で更新句を持たない
（`keyed-load.ts`、§11-2.4）。

### 7.1 差分 UI（管理者、ii-a に含む）

Phase i で作った版履歴 `apps/web/src/components/dashboard/dataset/resource-version-history.tsx`
（リソース編集内の版一覧: 版・作成日時・サイズ・由来・パージ）を拡張する。新規画面は作らない
— 版の隣に差分があるのが最も自然な導線であり、Phase i の資産をそのまま活かせる。

- **各版の行から「前版との差分」を開く**（行の展開、または差分ボタン）。開いたときに初めて
  `GET /versions/:v/diff` を呼ぶ**オンデマンド取得**とする。一覧描画時に全版ぶんの差分を
  取ると、版数 × DuckLake クエリが走って重い。
- **表示内容**: `+N 行 / −N 行` のサマリ、スキーマ変化（列の増減・型変化）のバッジ、
  サンプル行（追加・削除の代表数行）。主キーあり（ii-b）では変更行も表示する。
- **主キーなし段では「変更」を表示しない**（§7 の 2 段目のとおり、追加と削除の区別しかできない）。
  UI 上も「変更 N 行」という嘘の指標を出さない。
- **非表示条件**: 表形式でない・層2未 ingest・パージ済みの版は差分を出さず、理由を示す
  （「この版は表形式ではありません」「この版はパージ済みです」）。
- 閲覧者向けの公開ページでの差分表示は Phase iii（§15）。ii-a はダッシュボード内に閉じる。

### 7.2 内容の移動は版の発行として行う（ii-b の前提）

**版行の `ducklake_snapshot_id` は書き込み一度きりにする。** その版の内容を保持している
スナップショットを指し、以後どの操作も書き換えない。

決定は 4 つある。**根拠は当初のものから差し替わっている**（下記）。

1. **版行の `ducklake_snapshot_id` は書き込み一度きり。** どの操作も書き換えない
2. **巻き戻しは「戻す」ではなく「その内容をもう一度発行する」。** 対象版の内容を持つ新しい版を作る
3. **内容を動かす操作は取り込み経路を通す。** `CREATE OR REPLACE` で動かさない。動かした先を版行に
   書き戻さない。パージの降ろしと `standOnBase` も同じ（どちらも公開ではないので版は作らない）
4. **`superseded` は廃止。** live は「パージされていない最上位の版」。`restoreTo` が `superseded` を
   拒む規則（redo 禁止）も同時に落ちる

以上が決定である。以下は根拠で、読み飛ばしても実装はできる。

#### 7.2 の根拠（実測）

> 🔴 **当初この節が挙げていた第一の根拠は、もう成立しない。** 「書き換えると `table_changes` が
> 黙って空を返す」— `standLakeTableOn` が巻き戻し先の版に新しいスナップショット ID を上書きすると
> 版番号の順序（1 < 2）とスナップショットの順序（6 > 5）が逆転し、`table_changes(6, 5)` が
> **エラーではなく 0 行**を返す、というものである。観測自体は正しい（逆向きの
> `table_changes(5, 6)` は 10 行返る）。
>
> **§7 が差分を端点の突き合わせに変えた時点で、この壊れ方に到達する経路が消えた。** 端点比較は
> スナップショット ID の大小に依存しない。実測（3 行の表、v1 の記録を 1 → 3 に上書きして v2 = 2
> と逆転させた状態）:
>
> | 差分              | 端点 `FULL OUTER JOIN`            | `table_changes` |
> | ----------------- | --------------------------------- | --------------- |
> | 上書き後（3 → 2） | `added 1 / removed 1 / changed 1` | **0**           |
> | 上書き前（1 → 2） | `added 1 / removed 1 / changed 1` | —               |
>
> **端点比較は上書きされた ID でも正答する。** したがって以下は、この節の決定を**別の根拠で**
> 立て直したものである。残った根拠は 2 つで、**どちらも「差分が静かに壊れる」より弱い**。

**第一に、`CREATE OR REPLACE` での内容移動は ii-b が退けた書き込み経路そのものである。**
テーブルの現在内容を丸ごと書き直すので、全ファイルが入れ替わる — §11-2.4 が「述語つき
`MERGE`」を選んだのは、これが追記主体のデータで 315 倍の書き込みになるからである。巻き戻しが
公開のたびに全テーブル複製を層 2 に書くことになり、**取り込み経路を通せば差分書き込みで済む**。

**第二に、`superseded` の廃止は差分とは独立に正当化できる**（下記）。ADR-044 残課題 7
（層 2 に入る前に降ろされた版は二度と入れない）は、状態が存在することそのものから来る欠陥である。

**そして書き込み一度きりは、独立の決定ではなく帰結である。** 巻き戻しが版を発行するなら、
新しい版は発行時に自分のスナップショットを一度だけ受け取る — **書き戻す対象がそもそも無い。**

**以上を踏まえて、巻き戻しは「戻す」ではなく「その内容をもう一度発行する」形にする。** v1 へ戻す操作は
v1 の記録を触らず、**v1 の内容を持つ新しい版 v(N+1) を発行する**。スナップショットは版の発行順に
振られ、書き換えられない。**差分はこの順序に依存しないが**（上記）、スナップショット ID が版の
発行順に並ぶこと自体は、取り込みの順序チェックと保守関数が読む性質として残る。

**副次的に、既知の劣化も消える。** 巻き戻しを `CREATE OR REPLACE TABLE … AT (VERSION => …)` で
行うと change feed からは全行 insert に見える（§14.0）。発行として行えば通常のキー付き取り込み
経路（述語つき `MERGE`）を通るので、**巻き戻しを跨ぐ差分が正しい行差分になる**。同じ内容移動を
2 通りで測った（3 行の表、v3 = v1 の内容の再発行）:

| 差分                        | 版の発行として行う                                       | テーブル書き換えで行う |
| --------------------------- | -------------------------------------------------------- | ---------------------- |
| v2 → v3（巻き戻しそのもの） | `delete=1 insert=1 update_preimage=1 update_postimage=1` | `insert=3`             |
| v3 → v4                     | `update_preimage=1 update_postimage=1`                   | —                      |
| v1 → v4（巻き戻しを跨ぐ）   | `delete=2 insert=2 update_preimage=3 update_postimage=3` | —                      |

**層1に新しい仕組みは要らない。** `resource_version.storage_key` は「その版が所有するオブジェクト、
既に他の版が所有していればコピー」という規則で既に動いており（ADR-046 §3）、解釈変更で内容が
動かなかった場合に使っているのと同じ形である。

**規則は巻き戻しに限らない。** テーブルの現在内容を動かす操作は他に 2 つあり、どちらも同じ扱いに
する — **`CREATE OR REPLACE` で動かさない。動かした先を版行に書き戻さない。**

- **パージ**（§9.1 手順 4）: 層 2 が立っている版を消して、層 2 の戻り先へ降ろす。降ろし先の版の
  内容を取り込み経路で載せ直す。版の発行ではない（パージは公開ではない）ので、着地したスナップショットは
  どの版行からも名指しされない — **§11-3 が「最新スナップショットは常に残す」でこの場合を既に
  扱っている**
- **`standOnBase`**（取り込み前の自己修復）: 同じく載せ直しで、基底版の記録は触らない

**`superseded` は不要になる。** これは状態の削減ではなく、**その状態が担っていた計算が消える**
ことによる。現在の巻き戻し（v1..v5 が `active`・live = v5 で v2 へ戻す）はこう動く:

```
1 トランザクション:
  a. stepOffAbove(below = 2)
     UPDATE resource_version SET state = 'superseded'
      WHERE state = 'active' AND version > 2     ← v3・v4・v5 が同時に落ちる
  b. restoreLiveFromVersions
     → newestActiveVersion（state='active' の最大版）が a の結果 v2 を返す
     → live ポインタを v2 のオブジェクトへ
```

**`superseded` は「差し戻された記録」ではなく、`newestActiveVersion` に v2 を答えさせるための
作業変数である。** ポインタを動かす前に付けるのはそのためで、実装のコメントも「戻る前に降りる —
復帰先は目的地以下で最も新しい `active` 版なので、その上は全部その集合から抜けている必要がある」と
書いている。版が前に進むならこの探索自体が無い。運用者が v2 を名指しし、その内容を新しい版として
発行するだけなので、**絞る集合が存在しない。**

**したがって live の規則は一文になる — パージされていない最上位の版。** `stepOffAbove` は消え、
`newestActiveVersion` は `purged` / `purging` を除くだけになる。

**代償は、パージの復帰先が変わること。** v5 → v2 と巻き戻して v6 を発行した後で v6 をパージすると、
live は **v2 ではなく v5** に戻る（現在は v3..v5 が `superseded` なので v2 まで飛ぶ）。履歴を素直な
追記ログと見れば「最上位を取り除いたら 1 つ前の公開状態に戻る」であり、時系列としてはこちらが正直で
ある。**脇へ避けたはずの内容が現行に戻りうる**ことは変わらないので、状態に埋めるのではなく
**パージの確認画面に出す** — 「live は v5（公開日、YYYY-MM-DD に差し戻し済み）に戻ります」。
確認画面は既に戻り先を扱っている（§9.6）。

**到達性は変わらない。** `superseded` な版は現在もダウンロードでき（`getDownloadTarget` が拒むのは
`purged` だけ）、版履歴にも並ぶ。この状態が外していたのは「最新版番号」のラベル
（`latestLiveVersionAgg`）と復帰先だけである。**「二度と配ってはならない」なら操作はパージであり、
巻き戻しではない。**

**`restoreTo` の「redo は無い」規則も落ちる。** 現在 `superseded` な版は復帰先に指定できないが、
これは巻き戻しが版を**振り直す**からこその制約だった。版が前に進むなら「その内容をもう一度発行する」
に曖昧さは無く、拒む理由が無い。

**対価は 2 つ。** 巻き戻しのたびに版番号と層1のオブジェクトが 1 つ増える（往復すれば線形に増える）。
そして **ADR-044 はリリース済み**（v0.11.x）なので、契約の変更と、既にスナップショットを
書き換えられている版の扱いを決める必要がある。

## 8. Step 5 — 型判定と「型の降格」の選択肢提示（ii-c）

解釈は各版で列の型を推論する（`integer` / `float` / `boolean` / `string` / `date` /
`timestamp`。ADR-046 以降は DuckDB の sniffer が担い、`date` / `timestamp` はそこで加わった）。
版をまたぐと推論型が変わることがある（例: v1 で全行整数だった列 `amount` に、v2 で `"N/A"` や
桁区切り `"1,234"` が混入 → v2 は `string`）。これは**列の型降格**（integer → string）であり、
DuckLake 上はスキーマ変化 = §7-3 の「差分放棄・新版」に落ちる。

- **ii-a/b**: 型変化は**スキーマ差分として記録するだけ**（自動で降格を受け入れて新版）。
- **ii-c（選択肢提示 UX）**: 差し替え確認時に「列 `amount` の型が integer → string に変わります」を
  提示し、管理者に選ばせる:
  1. **降格を受け入れる**（列を string 化して取り込む。既定・安全）
  2. **該当行をエラーとして扱う**（型を維持し、外れ値行を差分の「不整合」として提示）

  型の**昇格**（string → integer、全行が整数化した）も同様に検知できるが、既存データを壊さない
  よう既定は「変えない」。UX は Phase iii の差し替えフローと統合する。

型の昇格/降格の格子（どの型からどの型へ動けるか）と、その判定を決定的に行う関数は
`packages/shared` に置き、Extract の推論と差分の両方から使う。

## 9. Step 6 — パージの層2波及

Phase i のパージ（sysadmin 限定・墓標方式・ADR-028）に、表形式リソースの層2の扱いを足す。

**パージが主張するのは取得不能であって、層2のバイト列の消去ではない。** 層ごとに何をするかは
次のとおりで、**層2だけが「消す」ではない**。

| 層                        | パージがすること                      | 保証                    |
| ------------------------- | ------------------------------------- | ----------------------- |
| 層1（正本オブジェクト）   | `storage.delete`                      | **物理削除**            |
| 層3（プレビュー Parquet） | `deleteMany`                          | **物理削除**（※）       |
| 検索インデックス          | 破棄                                  | **物理削除**            |
| 層2（DuckLake）           | `ducklake_snapshot_id` を null 化     | **製品から到達不能**    |
| 層2の Parquet             | expire → `cleanup_old_files` を試みる | **無し（best effort）** |

**※ 層3の「物理削除」は現在のプレビューについてである。** 途中の版が作って既に park 済みの
プレビューは、パージが早めないので**最大 1 時間 + sweep 周期のあいだ残る**（§9.8）。層3は削除
ベクタを持たないので消せる — 消せないのではなく、**まだ即時に消していない**。残課題 §14.1-7 で
パージ時の即時 sweep を入れて表どおりにする。

**層2のバイト列消去はリソース単位では保証できない。** DuckLake のスナップショットはカタログ全体の
系列で、1 つのスナップショットが**その時点の全テーブルの状態**を記述する。したがって別リソースの
ために保持しているスナップショットが、対象リソースのファイルを参照し続ける（§9.2 に実測）。
`expire` + `cleanup_old_files` は**解放できる分だけ解放する容量回収**であり、消去の手段ではない。

**そのうえで「削除」とは呼ばない。** 層2の Parquet には行が残りうるので、UI・監査ログとも
**「物理削除済み」と表現せず、層2に残存し得ることを明記する**（§9.5 / §9.6）。**消えていない
ものを「削除しました」と報告することが、この節が防ごうとしている唯一の失敗である。**

**DuckLake 管理外でデータディレクトリの prefix を消すことは禁止する。** カタログは消えた
ファイルを知らないままになり、他リソースのタイムトラベルや保守関数が参照切れに当たる。
**層2に対する書き込み経路は DuckLake だけである。**

### 9.1 版のパージ

**管理者が版を指名し、取得できなくする。範囲ではなく 1 版が単位である。**

1. 版を `purging` で claim する（ADR-028 の durable claim。`purgedAt` / `purgedBy` /
   `purgeReason` をこの時点で行に記録する）
2. **層1の bytes を消す**（`storage.delete`）— live ポインタを動かす**前**。中断が「live が
   消えたオブジェクトを指す（配信不能）」側に倒れるようにするため
3. **対象が live に立っていた版のときだけ**、派生物を捨てる（プレビュー・検索インデックス・
   再生成要求）— 同じ理由でポインタ移動前。**中間版では捨てない**。プレビューと検索は
   live の内容を表しており、中間版のパージはそれを変えないからである（§9.8）。
   **確認画面の文言もここで分岐する**（§9.6）
4. **層2を降ろす**（`purgeFromLake`）— **層2がその版に立っているときだけ**、**層2の戻り先**の
   内容を**取り込み経路で載せ直す**、戻り先が無ければ `DROP TABLE`。**着地した
   スナップショットは版行に書き戻さない**（§7.2。降ろしは公開ではないので新しい版も作らない —
   その最新スナップショットは §11-3 が残す。**現状はまだ書き戻している** — §7.2 の実装が
   ii-b の作業だからである）。そのうえで **`reclaimInSession`**
   （生存版が名指ししていないスナップショットを expire → `cleanup_old_files(cleanup_all => true)`）
5. live ポインタを**層1の戻り先**へ動かす
6. 墓標行を残し、`ducklake_snapshot_id` を null 化する

**手順 4 と 5 の戻り先は別物である。** 同じ「直前の生存版」ではない。

|                                  | 戻り先の定義                                                                     |
| -------------------------------- | -------------------------------------------------------------------------------- |
| **層1（手順 5、live ポインタ）** | パージされていない最上位の版                                                     |
| **層2（手順 4）**                | **`active` な**版のうち、**`ducklake_snapshot_id` が非 null かつ解決する**最上位 |

**混同すると、通常のパージで層2の現在内容を恒久的に失う。** v1 が取り込み済み、v2 は live だが
未取り込み（大きすぎる・表形式でない・ii-b ではキー不正）、v3 が取り込み済み、という状態で v3 を
パージすると: 層1は v2 へ戻ってよいが、**層2は v1 へ戻すべき**である。層1の戻り先で層2を降ろすと
「v2 はスナップショットを持たない → 戻り先なし → `DROP TABLE`」になる。しかも `DROP` は生存版の
`ducklake_snapshot_id` を null 化しないので、**掃き出しも拾わない**
（`ducklake_snapshot_id IS NULL` が条件）。§11-5 の復元と同じ恒久的損失である。

**ただし `DROP` が失うのは現在内容だけである。** 保持スナップショットのタイムトラベルと両端差分は
**`DROP` を跨いで読める**（expire + cleanup 後も、同名でテーブルを作り直した後も。実測を
`maintenance.ducklake.test.ts` で固定した）。失われるのは head であり、それを戻す者が居ないことが
恒久性の理由である。

**`DROP` してよいのは、層2の戻り先が 1 つも無いときだけである。** そして
**戻り先の候補があって全部が解決しないときは、`DROP` ではなく失敗させる** — その状態で落とすと
版行は解決しない id を持ち続け、掃き出し（`IS NULL` が条件）が拾わないので誰も直せない。
§11-5 が求める修復（解決しない id の null 化）は未実装なので、版を `purging` に残して運用者に
見せるほうが正しい（残課題 15）。

**`superseded` な版は戻り先ではない。** reclaim の retained 集合はそれらのスナップショットも
保持するので**差分は読める**が、内容としてテーブルに戻すのはリソースが降りた行を現在内容に戻すこと
であり、`standOnBase` と巻き戻しの追随が打ち消しているものそのものである。

**戻り先が無いときに落とすのはパージだけである。** パージには取得できなくする義務があるので落とし、
空のテーブルが「層2に現在内容が無い」という事実を述べる。**巻き戻しは同じ状態でも落とさない** —
撤回した版は `purged` ではないので取得できなくする義務が無く、live が無い以上テーブルの現在内容を
解決する読み手も無い（ADR-043 §5）。**落とせないからではない**（`DROP` は履歴を損なわない）。
残るのは ii-b の前提で、残課題 16 にある。

**降ろすかどうかも live では決まらない。** 層2は取り込みに成功した最新の版に立っているので、
その版と live は**両向きにずれる** — live 版が層2に入っていないことがあり、上位版が層2に
入っていなければ**中間版が層2の頂点**になる。後者で降ろさないと、パージした行がテーブルの
現在内容として残り、ii-b の `MERGE` は次の版をその上に載せる。判定は「その版のスナップショットより
上のスナップショットを持つ版が他に無いか」であって、ポインタへの問いではない。

**expire は行う。ただしそれが「取得できなくする」を担っているのではない。** 担っているのは
`ducklake_snapshot_id` の null 化で、差分もタイムトラベルも版行からスナップショットを引くため、
**null にした時点でその版を端点とする経路が全て消える**。expire のほうは、どの版も名指ししなく
なったスナップショットを溜めないための後始末である。

**retained 集合の計算に特別扱いは要らない。** 手順 4 の時点で対象の行は `purging` で、reclaim の
retained 集合は**まだ生きている版行**から引き直されるので、そのスナップショットは自然に未参照として
読まれる（`purged` も同様）。集合の定義は「**パージされていない版**」であって「現行の版」ではない —
差分は両端の版をスナップショットに解決して読むので、現行でない版を落とすと比較が壊れる
（`lake-reclaim.ts` がこの集合の実装で、現在は `active` と `superseded` を採る。§7.2 を降ろすと
`superseded` が消えるので `active` だけになる）。

**expire が層2のバイト列に届くとは限らない。理由は 2 つあり、どちらも設計上の性質である。**

- **merge が履歴を指し替える。** 取り込みが `merge_adjacent_files` を回すので、その版の差分ファイルは
  既に統合ファイルへ畳まれ、カタログ行ごと消えていることが多い。統合ファイルは N より前の保持
  スナップショットが参照し続けるため解放されない（§11-2.3）
- **スナップショットがカタログ全体のものである。** 別リソースのために保持しているスナップショットが、
  対象リソースのファイルを参照し続ける（§9.2）

**したがって手順 4 の expire + cleanup は best effort の容量回収であり、消去の保証ではない。**
失敗しても、届かなくても、パージは完了する — 完了を決めているのは手順 6 の null 化である。

### 9.2 層2のバイト列は、リソース単位では消せない

**DuckLake のスナップショットはテーブル単位ではなくカタログ全体のものである。** どのテーブルへの
コミットも新しいカタログスナップショットを作り、そのスナップショットは**その時点の全テーブルの
状態**を記述する。したがって、あるリソースのために保持しているスナップショットが、別のリソースの
ファイルを参照し続ける。カタログのメタデータにそのまま出る（実測、`a` を作成 → `b` を作成 →
`b` に追記 → `a` を `DROP`）:

```
file 0  table=a  alive for snapshots [1, 4)
file 1  table=b  alive for snapshots [2, ∞)
file 2  table=b  alive for snapshots [3, ∞)
```

`b` が必要とする 2 と 3 は、そのまま `a` のファイルの生存区間の中にある。**`a` を `DROP` して
`b` の保持集合で expire しても、`a` の行はディスクに残る**。

**この事実はテストで固定してある** — `purge.ducklake.test.ts` の
「leaves one table's rows on the disk because another table needs the snapshots」。対象行 10 → 10、
`b` にあたるテーブルの履歴まで捨てて初めて 0 になり、そのとき `b` の内容自体は残る（自分の
ファイルは自分を名指ししたスナップショットより長生きする）。**DuckLake がファイルの生存区間を
テーブル単位にしたらこのテストが落ちる。そのときが保証を見直せる日である。**

**`DROP` して層1から作り直しても消えない。** 作り直しは新しいファイルを書くだけで、古いファイルを
掴んでいるのは他リソースの保持スナップショットだからである。§9.9 に「テーブルを `DROP` して層1から
作り直せば消える」とあるのは**単一テーブルのカタログでの測定**で、本番のカタログ構成では成立しない。

**「その区間だけ余分に失効させる」も成立しない。** 汚染ファイルを解放するには、その生存区間に
入るスナップショットを全部失効させる必要があり、そこには**無関係なリソースの生存版が名指しして
いるもの**が含まれる。実測（4 リソースが 8 版ずつ交互に公開）では、最も広い区間に生存版の
スナップショットが 28 個入り、**うち 21 個・3 リソース分が他リソースのもの**だった。区間に公開した
すべてのリソースが対象になるので、リソース数と公開頻度に比例して増える。

失うものは正確に言えばパージではない — 他リソースの層 1 は無傷で、壊れるのは層 2 の差分と
タイムトラベルである（§4-4 が `ducklake_snapshot_id` を null 化し、§7 の 3 段フォールバックへ縮退）。
それでも**無関係なリソースの履歴機能を犠牲にして 1 リソースのバイト列を消す**取引であり、採らない。

**この結合は DuckLake の欠陥ではなく、機能である。** カタログ全体のスナップショットが実装して
いるのは**マルチテーブルの原子性と、時点をそろえた読み取り**である。実測: 2 つのテーブルへの書き込みを
1 トランザクションで囲むとスナップショットは 1 つしか消費されず、**どのスナップショットへ
タイムトラベルしても中途半端な状態は観測できない**（片方だけ更新された状態がどの版にも無い）。
Iceberg / Delta はスナップショットがテーブル単位なので、2 つのテーブルを同じ時点で結合するには
アプリ側が対応表を持つ必要がある。カタログが本物の SQL データベースであることの見返りが、これである。

**そして我々はそれを使っていない。** 層 2 はリソースごとに 1 テーブルで、複数テーブルを 1 つの
トランザクションで書くことも、テーブルをまたいで結合することも無い。**使っていない保証のために、
欲しい粒度（リソース単位の保持と消去）を失っている**という取引になっている。粒度を取り戻すには
カタログをリソース単位に割るしかないが、カタログは PostgreSQL のスキーマ 1 組なので、リソース数だけ
スキーマが増え、クエリごとに ATTACH が要り、`connection.ts` のインスタンスキャッシュが効かなくなる
（ADR-041 の接続数バジェットとも衝突する）。**採らない。**

**バイト列を消す手段が無いわけではないが、製品機能としては提供しない。** live を畳んでから
その前を expire すれば消える（実測）。ただし expire はカタログ単位なので**全リソースが層 2 の
履歴を失い**、掃き出しがその全部を再取り込み対象として拾う。1 リソースの要請で払う代償ではない。
手順と実測は §9.7 に置く。

**DuckLake 管理外で prefix を消すことは禁止する**（§9 冒頭）。安く見えるが、カタログは消えた
ファイルを知らないままになり、他リソースのタイムトラベルと保守関数が参照切れに当たる。

**これで失うものを明示しておく。** KUKAN は層2について「バイト列を消した」と言える操作を持たない。
層2の行に到達できるのは DB とストレージの両方に到達できる者だけで、製品の経路は §9.1 の null 化で
閉じているが、**それは到達不能であって消去ではない**。この線引きは §9.5 の意味論と §9.6 の UI 文言、
そして監査ログの表現に、そのまま降りる。

### 9.3 範囲の判断

**単位は 1 版だが、範囲は運用者が判断する。** 多くの場合 N から live までになる。

**上端は計算できない。** 削除要請は自然言語で来る。その内容が版のどこに、どの形で含まれるか
（言い換え、部分一致、関連情報）を突き合わせるのは人間の判断であり、範囲は片端しか指名できない。
**N も判断である。**

**気づかないまま版が進むのが普通である。** 要請は内容が出てからしばらく後に来るので、問題の行は
N から live まで連続して乗っていて、**live が現行として持っている**と考えるのが既定である。

**live が現行として持つ行は、パージでは扱えない。** live が配信しているものを消すのは削除ではなく
**内容の変更**であり、別の操作である。live まで含めるなら、live は直前の生存版へ戻る（層1の既存
動作。生存版が無ければリソースは空になる）。

**中間版の単独パージは、内容が後続に引き継がれていないときだけ意味を持つ。** 版 N の内容が版 N+1 に
生きていれば、N+1 も同じものを持っている。**確認画面で N → N+1 の差分を見せる** — 問題の行が
「削除された」として現れていなければ後続に生きているということで、範囲を広げる必要がある。
警告文より確実な歯止めになる。

### 9.4 履歴の見え方

将来、パージされていない版は一般利用者にも見せる。取り下げた版は**欠番として、取り下げた事実
とともに見せる**。

```
版 7   2026-08-01   1.2 MB   [ダウンロード] [差分]
版 6   2026-07-01   1.2 MB   [ダウンロード] [差分]
版 5   ——           取り下げ（2026-07-15）
版 4   2026-05-01   1.1 MB   [ダウンロード] [差分]
```

**番号は詰めない。** `version` は resource ごとの連番で `(resource_id, version)` に一意制約が
あり、URL や引用で外部から参照される。詰めれば別の版を指す。そして番号が飛ぶ以上、行ごと隠しても
**欠番は見える** — 隠して得られるのは理由が分からないことだけである。

**差分は構造的に安全側へ倒れる。** `ducklake_snapshot_id` が null なので、取り下げた版を端点と
する差分は計算できない。一方その前後（版 4 → 版 6）は両端のスナップショットが健在なので計算
できる。版 6 の履歴表示は「**直前の生存版からの変更**」になり、そう明示する。§7 の 3 段
フォールバックに落ちる必要はなく、参照先を繰り上げるだけである。

**墓標に出すのは日時・理由・実行者に限る。** `hash` は内容の指紋なので、表示すると内容の同一性を
照合できる。`size` も情報を持つ。取り下げ理由が個人情報事故なら伏せる。

**差し戻された版は取り下げとは別物で、内容は健在である。** 同じ「現行ではない」でも表示を分ける。
§7.2 を降ろすと差し戻しは新しい版の発行になるので、この区別は状態ではなく**その版の由来**として
持つ（「版 8 は版 5 の内容を再公開したもの」）。

### 9.5 意味論

「パージ対象版が書いた行でも後続版で現行のままなら層2に残る」は我々が実装する条件ではなく、
参照の有無から自動的にそうなる。**版のパージが主張するのは取得不能であって層2の消去ではない**
ので、この性質はそのまま受け入れる。UI 文言は「この版を取得できなくします」であり、「この版だけが
持っていた行データを消します」ではない。

**保証語を使わない。** 仕様・UI・監査ログのいずれでも、パージを**「物理削除済み」「完全に削除」
と表現しない**。層1・層3・検索インデックスは実際に消えるので個別には「削除」と言えるが、
**操作全体の結論としては言えない** — 層2に行が残りうるからである。監査ログには操作と対象と
時刻を記録し、結果は「取得不能にした」と書く。**どの層が消えてどの層が残るかは §9 冒頭の表が
正本である。**

### 9.6 UI と復旧手順

パージは**戻せない**。層1の bytes を消すので、その版の内容は製品のどこからも取得できなくなる
（層2の行は残るが、製品からは到達できない）。誤って公開した内容を差し替えたい場合の手順は
こうなる。

```
1. live をダウンロードする（必要なら）   ← 飛ばすと取り返せない
2. 対象の版をパージする                  → live は直前の生存版へ（無ければ空）
3. 修正版をアップロードする
```

確認画面が扱うのは、消える版、live の戻り先（または空になること）、現在の内容が必要なら先に
ダウンロードするよう促すこと、**層2に行が残る旨**、そして §9.3 の後続版チェック（N → N+1 の
差分）である。**最後の 1 つだけが未実装で、残課題 14 にある。**

**文言は「対象が live か」で決まる。版の数でも版の順序でもない。** 手順 3 のとおり派生物を捨てる
のは live 版のパージだけで、中間版ではプレビューも検索インデックスも触らない。

| 対象             | 起きること                                                 |
| ---------------- | ---------------------------------------------------------- |
| live・他に版あり | 正本・プレビュー・検索を削除。live は戻り先へ              |
| live・唯一の版   | 同上。戻り先が無いのでリソースはファイルのない状態になる   |
| live でない      | 正本のみ削除。プレビューと検索は現行の版を表すので触らない |

**ただし「対象が live か」はクライアントでは答えられない。** live ポインタが名指すのは
オブジェクトであって版ではない。クライアントが代わりに使いたくなる規則は 2 つあり、**どちらも
破れる形がある**（サーバはポインタの所有者で判定しており、それぞれの形に統合テストがある）。

| 規則                     | 破れる形                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 「最上位の版」           | 巻き戻しの後。live の内容が上位の版より下にあるので、**両向きに**誤る               |
| 「最上位の `active` 版」 | パージ実行中。live は `purging` な版に立っており、active な版はどれも live ではない |

**2 つ目は巻き戻しでは破れない** — `stepOffAbove` が上位を `superseded` にするので、巻き戻し後も
「live = 最上位の active 版」は成立する。破るのは**ポインタが動く前の状態**で、パージの claim が
それを作る（ポインタが動くのはワーカーの実行時である）。**active 版の総数で選ぶのも同じ形で誤る。**

**したがって一覧 API が版ごとに `isLive` を返し、確認画面はそれで場合を名指す。** 計算は増えない —
`liveVersion()`（ポインタの所有者を引く）はパージが判断に使っているものそのもので、`purging` も
含めて数える。**`purging` を含めるのは、パージ中の版がポインタを動かすまでは配信されている内容の
ままだからである。**

**名指しても条件付きの言い回しは残す。** 確認画面を開いてから確定するまでに live は動きうる
（別の実行の publish、並行する巻き戻し）。3 分岐は**起きることを先に見せるためのもので、保証では
ない** — 文言はそのことも述べる（`purgeCaseMayMove`）。

**戻り先の版番号もサーバが答える**（`purgeFallsBackTo`）。状態についての問いなのでクライアントでも
書けるが、**書ける規則は「どの版に立ち直せるか」というサーバ側の規則**であり（`newestActiveVersion`）、
そちらが変われば画面は黙って古くなる — そのときクライアントのテストは通り続ける。§7.2 で
`superseded` が復元先になりうる形もあるので、**規則は 1 箇所に置く**。一覧のページングにも依存
しなくなる（残課題 13 の元々の注記）。

**文言の選択はテストで固定する。** `resource-version-history.test.tsx` に 3 分岐それぞれの
テストがあり、**他方の分岐の文が出ていないこと**まで見る — 4 巡で 3 回間違えて 1 度も落ちなかった
のは、どの文が出るかを見るテストが 1 つも無かったからである。

どの場合も「層2に行が残ることがある」は共通で言う。

**現行を差し戻したいだけならパージではなく差し戻し**（ADR-044）を使う。内容が残り、権限も
編集者で足りる（§9.4）。

**実装状況**: 層1のパージ API は**単一版のみ**で、これで足りる。§9.3 のとおり単位は 1 版であり、
複数版に及ぶときはその反復である。`idx_resource_version_one_purging` が同時に 1 版しか `purging` に
できないので、まとめ実行の API を作っても内部は直列に回すことになり、得られるのは呼び出し回数の
削減だけである。**作らない。**

### 9.7 検討して採らなかった形（経緯）

**層2の細粒度パージ**（版を指名して層2からもその行だけを消す）**。** 圧縮を回さない前提なら
成立し、実測でも詰めた — 「live 側から N へ降ろす」
順序にすれば各段が live のパージになり、巻き戻しの
`CREATE OR REPLACE TABLE ... AT (VERSION => 直前版)` が全内容の新ファイルを書くので、汚染行と
現行行が同居していたファイルがそこで `end_snapshot` を得て解放される。差分方式でも追加の手順は
要らなかった（実測: 圧縮あり／なしの両方で汚染行 0、v1..N-1 のタイムトラベル正常）。

**採らなかったのは取り込みが `merge_adjacent_files` を回すからである**（§11-2.1）。merge は統合ファイルの
`begin_snapshot` を最古の元ファイルまで遡らせるので、N より前の保持スナップショットが N 以降の行を
含むファイルを参照し続ける（実測: 通常のパージ後も汚染行 10 が残る）。**タイムトラベルは全版で
正しいままなので、内容を見るテストでは気づけない。**

**`rewrite_data_files` は補完にならない。** merge と違って履歴を指し替えないので細粒度パージと
両立する — が、それは単一テーブルのカタログでの話であり、しかも 2 つの理由で効かない（実測、
追記主体のキー付き取り込み・12 版）:

- **発火しない。** 1 ファイルあたりの削除比が低く（120 行に 5 削除）、既定の 0.95 はもちろん 0.5 でも
  候補ゼロ。0.01 まで下げて 1 件だけ当たり、**ストレージは 24% 増えた**（7.8 → 9.7 kB）。旧形で
  測った「何もしないより悪い」は、キー付き経路でも変わらない
- **発火しても塞いでいる原因が違う。** 本番の形（テーブル 2 枚）では rewrite の有無にかかわらず
  汚染行 10 が残った。解放を止めているのは**別リソースの保持スナップショットがそのファイルの
  生存区間に落ちること**（§9.2）で、テーブル単位の圧縮では動かない
- **容量の道具としても効かない。** 過去を全部 expire したうえで rewrite しても 820 → 788 kB
  （4%）にしかならない（§14.1-8）。ただし**ファイル数は 133 → 19 に落ちる**ので、走査コストの
  道具としてなら余地が残る — バイトは +15% だが、走査はファイル数に比例する（§14.1-9）

**同じ測定で、到達範囲を決めているのは圧縮ではなくパージの範囲だと分かった。** 単一テーブルなら
rewrite の有無によらず消える（汚染行 5 → 0）— 内容が置き換わったところまでを範囲に含めたからで、
§9.3 の「範囲は N から live まで」がそのまま効いている。**後続版が現行として持つ行と同居した 1 版**
だけを指名した場合に消えないのが §9.9 の測定であり、両者は矛盾しない。

修復は 2 つとも実測で成立したが、どちらも入口には置かなかった。

- **N を含む merge 区間のスナップショットも expire する。** `max_file_size` で区間を閉じれば
  巻き添えは最大 K-1 版に収まる（実測で汚染行 0）。採らないのは、1 版の差分サイズがリソースごとに
  桁で違い、**窓を外しても気づけない**からである
- **層1から流し直す。** 一時は第2段として採ったが、**取り下げた** — 作り直しは新しいファイルを
  書くだけで、古いファイルを掴んでいるのは他リソースの保持スナップショットだからである（§9.2）。
  リソース単位では消去にならない

**単一版のパージ。** ある版でしか持たれていない行なら、その版を expire するだけでディスクから
完全に消える — 全書き直し／差分、圧縮あり／なしの 4 通りすべてで確認した。だが内容が 1 版にしか
存在しないのは次の版が即座に書き換えた場合だけで、§9.3 の既定と合わない。

**修正版を先に出し、N..live-1 だけ消す形。** live を残せるので**データ損失がゼロ**になる。実測でも
成立した（v9 を公開 → v5..v8 をパージ → 汚染行 0・live 無傷・v1..v4 のタイムトラベル正常）。
差分方式では live を 1 ファイルに畳む手順（`CREATE OR REPLACE TABLE t AS SELECT * FROM t`）が
追加で要り、飛ばしてもエラーは出ず削除が不完全なまま完了しうる（残課題 §14.1-10）。

**live を畳んでから、その前を expire する。**

**成立する手段はある。ただしカタログ全体を巻き込み、費用も結局は全リソースにかかる。** 手順は 2 段:

1. **対象リソースの live を 1 枚に畳む**
   （`CREATE OR REPLACE TABLE res_x AS SELECT * FROM res_x`。`res_<uuid>` はリソース 1 件の
   テーブル名 — `lakeTableName`）。差分方式ではどのファイルも現行行を抱えているが、畳めば
   **それより前の全ファイルが履歴専用になる**
2. **畳んだスナップショットより前を expire し、`cleanup_all`**

実測（テーブル 2 枚・各 10 版）: 汚染行 5 → **0**、両テーブルの現行内容は無傷（各 700 行）。

**書き込み費用と被害範囲は別々に広がる。**

|                                 | 範囲                 |
| ------------------------------- | -------------------- |
| 書き込み費用（live の畳み込み） | **対象リソースだけ** |
| 失う履歴（expire）              | **カタログ全体**     |

畳むのは消したいテーブルだけでよい。他リソースについては何も消さないので、その現行行は既存
ファイルに入ったままでよく、そのファイルは live のまま（`end_snapshot` が付かない）なので
`cleanup` の対象にならない。**消去そのものの費用は O(対象リソースの live 内容) である。** 他リソースも
畳めばその死んだバイト列も解放できるが、消去の成立には要らない。

**代償はカタログ全体の層 2 履歴である。** expire はカタログ単位なので、**無関係なリソースも
その時点より前へタイムトラベルできなくなる**（実測: `No snapshot found at version 4`）。失うのは
差分とタイムトラベルだけで、層 1 の内容も層 2 の現行内容も残る。§4-4 のリコンシリエーションが
解決できないスナップショット ID を null 化し、§7 の 3 段フォールバックへ縮退する。

**そして復旧は自動で始まる。ここが費用の本体である。** 他リソースの版は**live 版も含めて**
スナップショットを失う（expire する範囲より後に公開された版だけが免れる）。掃き出しの述語は
「`ducklake_snapshot_id` が null で、取り込み済みのより新しい active 版が無い」だから、
**この操作の直後は全リソースの全版がその条件を満たす** — 毎時の掃き出しが全部を再取り込み対象と
して拾う。取り込みが自分のロック下で再評価するのでリソースごとに 1 版入れば残りは除外されて
収束するが、**キューの起点は全版**であり、どの版が先に入るかで最小「リソースあたり 1 版」から
最大「全履歴」まで振れる。**つまり全リソースの再構築は避けられておらず、自動化されて後払いに
なっているだけである。** 実行するなら掃き出しを止めたうえで、復旧の順序を人が決めること。

**それでも製品機能としては提供しない。** 1 リソースの要請で全リソースの履歴を落とす操作を、画面から
押せる形にはしない。**運用上のエスカレーションとして、手順が存在することだけを記録する。**

### 9.8 派生物とバックアップ

**プレビュー Parquet（層3）は版ごとに持たない。** `resource_pipeline.preview_key` は 1 本で、
常に live の内容を表す。実行ごとに新しいキーへ書き、**前のキーは `orphaned_object` に park**
される（`PARKED_UNTIL` = 1 時間、掃除は sweep）。§9.1 の手順 3 は現在のキーを park したうえで
**その場で `deleteMany` する** — park は保険であって手段ではない。プレビュー Parquet は単体の
`COPY … (FORMAT parquet)` 出力であり、**削除ベクタを持たない**（DuckLake のテーブルではない）
ので、オブジェクトを消せば行も消える。

**残る窓**: N..live の途中の版が作ったプレビューは、後続の実行に置き換えられて既に park 済み
かもしれず、パージはそれを早めない。最大 1 時間 + sweep 周期のあいだ、汚染行を含むプレビューが
ストレージに残りうる。**パージ時に当該リソースの park 済みオブジェクトを即時 sweep する**のが
正しい（残課題 §14.1-7）。層3は削除ベクタを持たないので、ここは層2と違って消せる。

物理消滅タイムライン（S3 noncurrent 30 日、ADR-037）は Phase i と同じ。**PG バックアップ
保持期間とは結合しない** — 層1の版ファイル削除が既にそうであり、パージ済みのバイト列を
「どのバックアップから復元されても参照先が壊れないように」生かし続けるのは、パージの目的に対して
逆向きである。復元後に参照先を失ったスナップショットは §4-4 のリコンシリエーションが
null 化し、3 段フォールバックで縮退する（データ消失ではなく差分機能の縮退）。

### 9.9 実機で確認した性質

`packages/lake/src/__tests__/purge.ducklake.test.ts`（DuckDB 1.5.4 / ducklake `d318a545`）。

- expire は**名指しした 1 スナップショットだけ**を対象にできる（明示リスト方式が成立する）
- 🔴 **キー付き取り込みでは、パージが解放できるバイト列は当初の測定より少ない。** 版 2 が書いた
  50 行のうち、後続版が現行として持つのは 25 行。残り 25 行はどこからも参照されないが、**現行行と
  同じファイルに居るので解放されない**（実測 50 → 50）。後続版が削除した行も同様で、テーブルからは
  引けなくなるがファイルには残る（実測 1 → 1、live からは 0 件）。**ADR-043 §5.1 の器の原則が、
  ii-b では例外なく効く。**

  当初これを「対象行が Parquet から物理的に消える」と記録していたのは、**テストが述語なしの
  `WHEN MATCHED THEN UPDATE` を使っていた**からである。その形は一致した全行を書き直すのでファイルごと
  入れ替わり、古いファイルが `end_snapshot` を得て履歴ごと解放される。**採用形（値の述語つき）では
  起きない。** 測った形と出す形が違うと、§9 の到達範囲を実際より広く見積もることになる — 現在は
  `src/keyed-load.ts` の 1 か所からテストもベンチも SQL を取る

- **`merge_adjacent_files` を回した後は細粒度パージが成立しない**（汚染行 10 が残る）。同じ形で
  `rewrite_data_files` を挟んだ場合は成立する（汚染行 0、保持 220 版の内容ダイジェスト一致）。
  両者の差は履歴を指し替えるかどうかで、機構は §11-2.3
- **テーブルを DROP して層1から作り直すと消えた**（汚染行 39 → 0、live 無傷）が、**この測定は
  カタログにテーブルが 1 枚しか無い**。本番の構成（リソースごとに 1 テーブル、カタログは共有）では
  他リソースの保持スナップショットが古いファイルを掴み続けるので成立しない（§9.2）
- **素の `DELETE` が残す削除ベクタの裏の行は、その版を expire しても解放されない**。live が同じ
  ファイルの他の行を持っている限り、その下の履歴を全部 expire しても解放されない。**我々の
  取り込み経路（`MERGE` と `CREATE OR REPLACE`）はこの形を作らない**ので実害は無いが、
  部分更新の文を足すと該当しうる
- **`cleanup_all => true` は省略できない。** 参照が切れたファイルは
  `ducklake_files_scheduled_for_deletion` に載るだけで、既定の `cleanup_old_files` は**何も
  消さない**。expire は「消してよい」と印を付ける操作であって、削除ではない
- パージ後の修正版アップロード（§9.6 step 3）が、消した行を呼び戻さない
- expire したスナップショット ID は**再利用されない**（新しい ID が振られる）
- 細粒度パージを採る場合、**retained 集合を版行から引き直さず名指しだけを expire すると行が残る**
  （3 版以上で顕在化する — 2 版では巻き戻しが最新スナップショットを兼ねるため偶然消える）
- `rewrite_data_files` は書き直した複数ファイルを**1 つに統合する**。既定閾値（0.95）では
  何もしない（§11-2.1）

## 11. 運用

### 11-1 データインラインは無効化する

**データインラインは無効化する**（`data_inlining_row_limit = 0`、カタログに永続化）。
既定では小さい書き込みが Parquet ではなくカタログに入る。行ごとに生存区間
（`begin_snapshot` / `end_snapshot`）を持つので原理的には回収できるはずだが、
**expire がインライン行を回収しない**（ADR-043 §6-1）。実測: 版を expire しても
`end_snapshot` が閉じたインライン行はカタログに残る — **どこからも到達できず、消えてもいない**。

**`ducklake_flush_inlined_data` は解にならない。逆向きである。** 実測では、
**expire 済みの版の行までストレージへ書き出す**（履歴ごと Parquet 化するため、失効した版が
オブジェクトとして復活する）。順序を入れ替えても同じで、先に flush すると全版が生存版の
参照するファイルに入り、expire で解放できない。**インライン行は「ファイルを消す」以外の
回収経路を持たず、唯一ファイル化できる呼び出しが削除を取り消す。** 実際、拡張が公開する
保守関数にインライン行を回収するものは無い（`expire_snapshots` / `cleanup_old_files` /
`delete_orphaned_files` / `merge_adjacent_files` / `rewrite_data_files` /
`flush_inlined_data` のみ）。

上流では [ducklake#1067](https://github.com/duckdb/ducklake/issues/1067) が同じ要望
（`ducklake_cleanup_old_inlined_data` が欲しい）を出し、
[#1145](https://github.com/duckdb/ducklake/pull/1145) で修正済みとして close された。
**しかし #1145 が消すのは孤児になったインライン _テーブル_ であって、生きているテーブルの
中で閉じた _行_ ではない**（#1065 / #1088 の修正）。報告者自身が「テーブルだけか、中の
データもか」と確認しているが回答が無く、#1145 より後の版（`d318a545`）での実測でも行は残る。
上流が行の回収を実装したら見直してよい。

**ii-b でも判断は変わらない。** キー付き `MERGE` は「変更行だけの小さなファイル」を作らない
（下記 2）。小さい表なら**版ごとに表全体が再インライン**され、大きい表なら丸ごと Parquet に
書き直される — キーの有無でインライン化の損得は動かない。

設定は**以後の書き込みにのみ効く**。この変更より前に作られたカタログにインライン行が
残っている場合、それらは回収経路を持たないままになる。該当する環境では lake テーブルを
破棄して層1から再取り込みする（管理画面の全データ削除、または `ducklake` スキーマの
drop + 移行）。ii-a の ingest は本変更と同時期の導入であり、通常は
開発環境の残骸のみが該当する。

### 11-2 コンパクション — ii-a では何も起きない

**コンパクションは ii-a では「やることが無い」。有害だからではない。** 全行置換のため断片化せず、
削除も持たないので、`merge_adjacent_files` も `rewrite_data_files` も候補ゼロ（`[]`）を返す（実測）。
差分は常に 2 ファイルしか読まない（v1→v20 と v19→v20 が同コスト）。**実行しても副作用は無く、
単に何も起きない。**

**版を重ねても統合ファイルは育たない。** 60 版を全行置換して毎版 merge を呼ぶと、live は 1 のまま、
最大ファイルは 0.18 MB で動かず、**スナップショットも 1 つも消費しなかった**（実測）。総容量は
版数に線形（0.175 MB/版）に増えるが、これは履歴の保持であってコンパクションの話ではない。

**「live が常に 1 個」は正確ではない** — `INSERT` は `target_file_size` でファイルを切るので、
テーブルがそれを超えれば 1 版でも複数ファイルになる（実測: target を 256kb に下げると 1 版 2 本）。
**それでも merge は発火しない。** `max_file_size` を 1 GB、`min_file_size`、`max_compacted_files`
と振っても候補ゼロのままだった。**述語そのものは特定していない**が、ii-a が merge を呼び出しても
何も起きないという結論は、テーブルが `target_file_size` を超える側でも成り立つ。

裏返せば、**取り込みの末尾から ii-a を場合分けで外す必要も無い。** キーの有無で呼び分けず、
同じ 1 行を全リソースの ingest に置けばよい。移行期に ii-a と ii-b のテーブルが混在しても、
キー設定が外れても、キー検証に失敗して層 2 に入らなくても、呼ぶ側は何も知らずに済む。

**ii-b では差分方式を採るので、live のファイルは版ごとに増える**（§11-2.4）。ストレージが
2 桁縮む代わりに全走査が版数にほぼ比例する（cold で +0.49ms/版、warm で +0.05ms/版）ため、
**取り込みの末尾で live ファイルが閾値を超えていれば `merge_adjacent_files` を回す**（§11-2.1）。
`rewrite_data_files` は使わない — 追記主体の
データでは効果が乏しく、ストレージをむしろ増やす（§11-2.3）。**merge は層2の履歴を
指し替えるので、パージは §9 の 2 段構成が前提になる。**

**これは「DuckLake が必要に応じて整えてくれる」ではない。** ii-a で断片化しないのは取り込みが
`DELETE` + `INSERT` で表を丸ごと置き換えるからで（`ingest.ts`）、**閾値で発火する自動
コンパクションは無い** —
`DuckLakeTransactionManager` が override するのは `StartTransaction` / `CommitTransaction` /
`RollbackTransaction` / `Checkpoint` だけで、実測でも DETACH + 再 ATTACH、接続の
クローズ + 再オープンのいずれも断片化を残したままだった。

**部分更新の文を混ぜた瞬間に崩れる。** 素の `UPDATE` は 1 文ごとに live ファイルを 1 つ
増やし、**線形に、上限なく**溜まる（実測: 40 回で live 41 ファイル、ディスク上 81）。

### 11-2.1 取り込みの末尾で圧縮する（`MERGE_FILE_THRESHOLD`）

**取り込みの末尾で、live ファイルが `MERGE_FILE_THRESHOLD` 以上なら
`merge_adjacent_files` を回す。** ii-a では候補が無かったが、ii-b の差分方式では効く。周期実行では
なく取り込みジョブに置くので、**周期を選ぶ判断も、別の定期ジョブも要らない**。

**閾値はファイル数で置く。** 走査コストはファイル数にほぼ線形（実測でファイル 1 本あたり
約 0.03 ms、ローカル FS）なので、`file_count >= T` は「走査で読むファイル数を T 以下に保つ」という
目的を直接書いた形になる。周期 K（リソースごとに正解が違う）や `target_file_size`（バイトの
見積もりが要る）と違い、**T はサイズにも更新頻度にも依存しない**。毎回カタログから読むので、
外れようがない。

**既定は `MERGE_FILE_THRESHOLD = 50`、値は ADR-036 のランタイム設定にする**（§14.1-2）。
動かす根拠は 2 つ — 読み手の並列度と、**そのリソースの床**（それ以上は畳めなくなる live 本数）。
**床より下に T を置いた発火はすべて空振り**になるので、動かすならまず床を測る。

以上が決定である。以下は根拠で、読み飛ばしても実装はできる。

#### 11-2.1 の根拠（実測）

**測定は採用形の書き込み経路で行っている** — 述語つき `MERGE` 2 文を 1 トランザクション
（`src/keyed-load.ts`）。以前の数字は `INSERT` + `UPDATE` の 2 文（版ごとに 2 スナップショット、
述語なしなのでファイル全体を書き直す）で取っており、**§11-2.4 が採らないと決めた経路だった**。
書く形が変われば live ファイルの増え方が変わり、閾値の意味も変わる。

**表の走査はすべて `threads` 既定 = コア数で測っている**（MinIO 表は 24、S3 表は 16 と 2）。
**production はこの既定を使わない** — `QUERY_THREADS` / `LAKE_INGEST_THREADS` で 2 に固定するので、
MinIO の行は production より並列度が高い側にある。条件が一致しているのは S3・2 vCPU の行だけである。

**cold と warm を分けて測る。** DuckDB のファイルキャッシュはインスタンス単位なので、走査は
「新しいプロセスの初回」と「同じプロセスの 2 回目以降」で 1 桁違う。**どちらも例外的な場合ではない** —
ii-b は版ごとにファイルを 1 本増やすので、新しい版のファイルはどのプロセスにとっても最初は cold である。
実測（MinIO・24 コア）:

| T      | merge 回数 | merge 累計 | 最悪 live | cold 走査 | warm 走査 |
| ------ | ---------: | ---------: | --------: | --------: | --------: |
| なし   |          0 |       0.0s |       401 |  251.0 ms |   31.4 ms |
| 25     |        131 |      11.0s |    **42** |      45.8 |      13.6 |
| **50** |     **74** |   **6.1s** |    **57** |  **50.5** |  **13.2** |
| 75     |         22 |       2.0s |        75 |      57.2 |      14.9 |
| 100    |         14 |       1.2s |       100 |      69.2 |      16.8 |

**T=25 は床より下にある。** 131 回発火して live は 42 本にしか下がらない — 削除を抱えた統合ファイルは
merge の対象外なので（§11-2.3）、そこから先は畳めない。**下げようのないところで撃ち続けている**
ことになる。キー付き取り込みは版ごとに削除ファイルを作るため、統合ファイルはすぐ対象外へ落ちる。

**したがって既定を 25 から 50 へ上げる。** merge が 44% 減って（131 → 74 回、11.0 → 6.1s）、cold は
10% 増（45.8 → 50.5ms）、**warm は差が無い**（13.6 → 13.2ms、逆転しており誤差）。T=25 の優位は
cold のときだけで、しかもその cold は 3 回測って 43.1 / 45.8 / 93.6ms とばらつく — **単発の cold
走査は 2 倍のばらつきを持つ**ので、この差に既定を賭けない。決定的なのは merge 回数と live 本数で、
どちらもばらつかない。

**床は fixture 依存であり、そこが T を runtime 設定にする理由である。** 床の位置は行の入れ替わり
速度で決まるので、リソースごとに違う。**T を床より下に置いた発火はすべて空振り**になるため、
まず床を測り、その少し上に置く。

S3 の値は warm でしか取っておらず、しかも**旧形の書き込み経路**で測ったものである（測定環境は
撤去済み）。cold は 401 本で warm の 12 倍だったので、下表はいずれも楽観側である。**単価（傾き）
だけが移る量**で、T 別の絶対値は採用形では別になる:

| 環境（warm）            | ファイル 1 本の走査単価 | T=25 の最悪走査 | T=100 の最悪走査 |
| ----------------------- | ----------------------: | --------------: | ---------------: |
| MinIO（loopback）       |              0.049ms/本 |           9.4ms |           13.4ms |
| S3・16 vCPU（同一 VPC） |               0.32ms/本 |          53.4ms |           57.6ms |
| S3・2 vCPU（同一 VPC）  |           **3.11ms/本** |         152.5ms |      **339.9ms** |

**単価を決めているのはストレージのレイテンシではなく、それを隠せるだけの並列度である。** vCPU を
2 → 16 にすると傾きが 9.7 分の 1 になった。同一 VPC の 16 vCPU（0.32ms/本）と、多コアのマシンから
インターネット越し（0.36ms/本）がほぼ同じだったことが、経路長よりコア数が効いていることを示している。

**ただし効いているのはコア数そのものではなくスレッド数で、これは設定できる。** DuckDB の走査は
morsel 駆動のスレッドプールで、非同期 I/O ではない — 同時に飛ばせるレンジ要求の数はスレッド数
そのものであり、既定がコア数なだけである。cold 走査を `SET threads` で振ると、**コア数によらず
8 スレッドで頭打ちになった**（401 本）:

| スレッド | MinIO・24 コア | S3・2 vCPU |
| -------: | -------------: | ---------: |
|        1 |       998.3 ms |  29004.6ms |
|        2 |          502.5 |    15078.8 |
|        4 |          276.7 |     8101.9 |
|    **8** |      **186.6** | **6153.2** |
|       16 |      **172.4** |     6203.0 |
|       32 |          193.8 |     6067.5 |
|      128 |              — |     6926.8 |

MinIO の列は採用形で測り直したもの。S3 の列は旧形のままだが（測定環境は撤去済み）、**曲線の形は
同じ**で、変わるのはファイル数由来の絶対値だけである。

**コア数を超えるスレッドはスイッチングコストにしかならない、とはならなかった。** 走査はレイテンシ
律速であって CPU 律速ではないため、2 vCPU でも 2 → 8 スレッドで 2.45 倍速くなる。頭打ちから上での
劣化は小さく（24 コアで 32 スレッドまで平坦、2 vCPU で 128 スレッドが 32 スレッド比 14% 悪化）、
**利得のほうが 1 桁大きい**。

**頭打ちの正体は特定できていないが、コア数ではない。** 8 で止まるのがコア数 2 でも 24 でも同じ
だった。直列部分が残る形（`S + P/n`）でもない — n=1,4 から当てはめると n=16 は 83ms のはずが実測
155ms で、飽和ではなく上限である。クエリ単位の上限でもない: 同じスキャンを 1 / 2 / 4 本同時に
走らせると総スループットは 5.1 → 6.5 → 7.1 /s にしかならず、**1 本で既にほぼ飽和している**。
`duckdb_settings()` に該当しそうな読み取り側の上限設定は無かった。

**ただし接続の張り直しが単価を押し上げている。** `httpfs_connection_caching` は既定で **false** で、
有効にすると 1 スキャンあたりの TCP 接続が **24 分の 1**（TIME_WAIT の増分で 140 本 → 6 本）、cold 走査が
1.4〜1.75 倍速くなった（MinIO・401 本・16 スレッドで 150 → 88ms）。頭打ちの位置は動かないので
上限そのものではないが、単価には効く（§14.1-2）。`enable_http_metadata_cache` と
`prefetch_all_parquet_files` は差が出なかった。

**したがって「T は読み手の vCPU 割り当てで決まる」は正確ではない。** 決めるのはスレッド数で、
2 vCPU の読み手も `SET threads` で 3.11ms/本 の大半を取り戻せる。**現状の `QUERY_THREADS` /
`LAKE_INGEST_THREADS` はどちらも 2 で、測定した中で最悪の点にある**（§14.1-2）。

**T と `threads` は独立に決められない。** 並列度が低いほど閾値の効きが大きい（MinIO・cold）:

| threads | T=25     | T=100     | 401 本    | T=100 / T=25 |
| ------: | -------- | --------- | --------- | -----------: |
|       1 | 74.7 ms  | 226.1 ms  | 796.8 ms  |         3.03 |
|   **2** | **48.1** | **125.1** | **403.1** |     **2.60** |
|       4 | 33.9     | 74.3      | 225.9     |         2.19 |
|       8 | 32.9     | 56.6      | 153.3     |         1.72 |
|      16 | 35.7     | 59.2      | 155.3     |         1.66 |
|      32 | 35.4     | 57.8      | 154.0     |         1.63 |

**production の threads=2 では T=100 が T=25 の 2.60 倍**で、T を大きくする余地は最も小さい。
threads を 8 に上げれば 1.72 倍まで縮むので、**先に動かすべきは threads のほうである** — T を
上げるより効き（同じ T=25 で 48.1 → 32.9ms）、しかも T と違って merge の回数という対価が無い。
ランタイム設定として T を動かすときは、そのときの `threads` とセットで測り直す。

**T を上げる対価は読み取り、下げる対価は書き込みである。** 200 版での merge は T=50 で 74 回・
6.1s、T=100 で 14 回・1.2s。50 → 100 で書き込みは 5 分の 1 になるが、cold は 50.5 → 69.2ms
（+37%）になる。**50 はどちらの側でも最悪ではない。**

**merge の秒数と走査のミリ秒を同じ土俵で比べてはならない。** merge は版の公開ごとに 1 回だが、走査は
**読まれるたび**である。T を大きくして節約できるのは公開ごとの数ミリ秒で、失うのは読み取りごとの
数十〜数百ミリ秒になりうる。

**環境をまたいだ絶対値の比較には、コア数と cold/warm の両方を揃える必要がある。** ローカル FS
（0.030ms/本、warm）と MinIO（0.049ms/本、warm）は同一マシンなので比較できるが、そこに EC2 の
数字を並べるのは誤りである。

**床は上の表にも出ている。** T=25 の最悪 live が 42 本で、閾値まで下がらない。旧形の測定でも
T を 10 以下にすると live は 11 本で止まった（360 版）。削除を抱えた統合ファイルは merge の対象外
（§11-2.3）なので、そこから先は畳めない。**床より下に T を置いた発火はすべて空振り**である。

**圧縮の価値はファイル数ではなく「ファイルが小さいこと」から来る。** 幅の広いテーブル
（40 万行 × 256B = 110 MB、100 版）では圧縮がほとんど効かない:

| T    | 発火 | merge 累計 |        最悪走査 |
| ---- | ---: | ---------: | --------------: |
| なし |    0 |       0.0s | 201 本 / 45.5ms |
| 1    |  100 |       8.4s |   2 本 / 42.5ms |
| 100  |    2 |       0.2s | 100 本 / 41.7ms |

走査が 110 MB を読むことに支配されていて、ファイル数は誤差である（1 本 550 KB）。軽いテーブルで
55.5 → 7.5ms という差が出るのは 1 本が 1.5 KB しかないからで、**断片化が問題になるのは小さく刻まれた
ときだけ**。大きなテーブルほど圧縮が要るのではなく、逆である。T を大きめに取れば、大きなテーブルで
merge が過剰に働くことも避けられる。

**移らないのは絶対値だけで、形は移る**（走査はファイル数に線形、床がある、大きいファイルでは
バイト支配）。変わるのは次の 2 つの定数だけなので、環境ごとにこれを測れば T は計算で出る:

```
走査 ≈ ファイル数 × 単価 + バイト数 / スループット
merge 1 回 ≈ min(テーブル, target_file_size) / スループット
```

したがって **T は ADR-036 のランタイム設定とし、既定値は環境ごとに測って決める**（§14.1-2）。

**測り直しは `pnpm bench:lake`**（`packages/lake/scripts/bench-compaction.ts`）。上の表を出したのと
同じハーネスで、`--data s3://…` を渡せば MinIO / S3 に対して同じ測定ができる。定数に再導出の手段が
無ければ、その定数は誰にも見直せない。

**構築時間はテーブルサイズに依存しない。** 基底を 2 万 / 20 万 / 200 万行と振っても、毎版 merge（閾値なし）の
構築は 45.8 / 44.5 / 45.7 秒で動かなかった（200 版）。周期実行との差は一貫して merge 1 回あたり
75 ms 程度の固定費で、データ量に比例する項はこの範囲（ディスク上 18 MB まで）では表に出ない。

**これは DuckLake の既定に逆らう設定であり、逆らってよい理由がある。** 1 回の merge が書く量は
`target_file_size`（既定 `1 << 29` = 512 MiB、`ducklake_catalog.hpp`）で決まる:

| テーブル                | 1 回の merge が書く量                             |
| ----------------------- | ------------------------------------------------- |
| target をはるかに下回る | テーブル全体（我々は 18 MB なので 75 ms）         |
| target と同程度         | **テーブル全体**（400 MB なら毎版 400 MB）★ 病的  |
| target をはるかに超える | 端数だけ — 達したファイルは恒久的に候補から外れる |

既定値では病的な帯が 0〜512 MiB の全域になり、中小規模のテーブルの大半がそこに入る。**DuckLake が
「毎コミットで merge」を既定にできないのはこのため**で、我々が平気なのは帯の下端に居るからである。
コミット頻度が版の公開ごと（1 日に数回）である点も効いていて、秒間数百コミットのレイクなら
75 ms の固定費も無視できない。加えて merge は `WriteMergeAdjacent` が元ファイルのカタログ行を
`DELETE` する破壊的な操作で、`ducklake_add_data_files` で登録した外部 Parquet も対象になりうる —
コミットの副作用にはできない性質である。実際 DuckLake は保守を `CHECKPOINT <catalog>` という明示
操作として用意している（§11-2.2）。

**`target_file_size` は通常の書き込みにも効く**（`ducklake_insert.cpp` の
`file_size_bytes = MaxValue(target_file_size, MINIMUM_WRITE_FILE_SIZE)`）ので、下げれば生成される
Parquet も小さくなる。層 2 が数百 MB に達するリソースが現れたらこれを下げて 1 回の書き込み量を
上限する（§14.1-2）。**既定のままで我々の設計と一致する**ので、いま設定する理由は無い。

**見直しの引き金は版の頻度である。** 書き込み増幅は `コミット数 × min(テーブルサイズ, target)` なので、
効いてくるのは分母の頻度のほうで、高頻度 ETL のようにコミットが分・秒間隔なら 75 ms の固定費自体も
スループットの上限になる。この決定は「版 = データの公開で、1 日に数回」を前提にしている。
**外部 URL の定期取得は、その前提を崩しうる製品内の経路である** — 短い周期を設定されたリソースの
内容が毎回変われば版が数分おきに積まれる。そうしたリソースが現れたら、そこだけ周期実行へ落とすか
`target_file_size` を下げる（§14.1-2）。

**もう一つのコストはスナップショット数**で、merge 1 回につき 1 消費する（実測: 722 → 1082）。版行が
名指しするのは取り込み側のスナップショットで、merge のものはどの版行からも参照されない —
§11-3 の失効候補の計算（全スナップショット − 版行が参照する ID − 最新）がそのまま扱える形である。

**`rewrite_data_files` は使わない。** 同じ形で測ると、追記ファイルは削除を 1 件も持たないため
候補に入らず（`GetFilesForCompaction` の `total_delete_count == 0 ||` が閾値判定より先に効く）、
訂正の付いた基底ファイルだけを複製する:

| 圧縮（1200 版）         |   live |       容量 |      全走査 |
| ----------------------- | -----: | ---------: | ----------: |
| なし                    |  2,401 |     4.1 MB |     97.6 ms |
| `rewrite_data_files(0)` |  1,816 | **6.8 MB** |     63.8 ms |
| `merge_adjacent_files`  | **83** |     3.4 MB | **11.3 ms** |

**何もしないよりストレージが増える。** 閾値を上げても解決しない — 0.5 でも 0.95 でも、行政
データの更新頻度では候補が現れない（実測: 300 版・毎版 5 行変更で live 298 → 0.95 では 298 のまま、
0.5 で 245）。閾値は「そのファイルが書かれてから今までに削除された行の割合」であり、差分方式では
**ファイル = 版**なので「その版の変更がどれだけ上書きされたか」を測る。行政データで 95% が
入れ替わることは稀である。

**merge が減らすのはファイル数であって容量ではない。** 内訳（360 版、`parquet_metadata` で
列チャンクとそれ以外に分解）:

| 圧縮      | 総量    | 列チャンク | フッタ等 | 生データ |
| --------- | ------- | ---------: | -------: | -------: |
| なし      | 1.24 MB |    0.94 MB |  0.30 MB |  2.09 MB |
| merge/100 | 1.14 MB |    1.07 MB |  0.07 MB |  2.53 MB |

フッタ等の固定費が 0.30 → 0.07 MB に減る一方、統合ファイルは全世代の行を 1 本で表すため生データが
増える。**差引ほぼ相殺で、価値は走査時間にある。**

**版の保持世代数**（§14.1-8）を入れれば古いスナップショットが失効して差分ファイルも解放され、
統合が本来の意味を持つ。そこまでは、圧縮は**読み取りを買う支出**として扱う。

**ファイル数の内訳**（実測: 20 版・2 万行 → ディスク 59 ファイル）:

| 種類           |  数 | 内訳                                     |
| -------------- | --: | ---------------------------------------- |
| データファイル |  21 | 基底 1 + 版ごとの差分 20                 |
| 削除ファイル   |  38 | **版あたり約 2** — 取り込みが 2 文だから |

削除ファイルが版あたり 2 つになるのは `when_matched` の 1 アクション制約への回避策（upsert と
prune がそれぞれ tombstone を残す）の副作用である。バイト数は基底が支配的なので容量には効かない
が、**オブジェクト数は版あたり約 3 つ**増える。**これらは孤児ではない** — 実測でも
`ducklake_delete_orphaned_files` は 0 件を返す。孤児はカタログが記録していないファイルだけで、
これらは全て記録され参照されている。

**ただし版あたり 2 個のうち 1 個は取り戻せる。** 1 アクション制約が外れて取り込みを 1 文に戻せれば
tombstone が半分になる。`merge.ducklake.test.ts` の該当ケースがその合図を持っている。

**`file_count` はディスク上の総数ではなく「現在のスナップショットで生きている数」である。**
各ファイルは `[begin, end)` の生存区間を持ち、読み取りは要求されたスナップショットを覆う
ファイルにだけ解決される（実測: snapshot 2 で 2 個、11 で 10 個、21 で 20 個）。**古い
スナップショットを保持しているのは、差分とタイムトラベルがそれを読むからで**（`lake-reclaim.ts`）、
失効させれば ADR-043 で作っている機能そのものが縮退する。

### 11-2.2 `CHECKPOINT` を実行してはならない

**lake カタログに `CHECKPOINT` を実行してはならない。** `CHECKPOINT <catalog>` は
`DuckLakeTransactionManager::Checkpoint`（`src/storage/ducklake_checkpoint.cpp`）に入り、
保守関数を固定順で 6 本走らせる:

```
flush_inlined_data → expire_snapshots → merge_adjacent_files
→ rewrite_data_files → cleanup_old_files → delete_orphaned_files
```

6 本のうち 3 本が、我々が条件を決めて呼ぶべきものである。**`expire_snapshots` を引数なしで
呼ぶ** — 我々の失効候補は版行から引き直した明示リストであり（§11-3）、`expire_older_than` が
設定されていれば時刻ベースで走ってしまう。**`flush_inlined_data` を呼ぶ** — インライン行が
残っている環境では失効済みの版をストレージへ書き出す（§11-1）。**`delete_orphaned_files` を
既定の窓で呼ぶ** — 書き込み中のファイルを孤児と読む余地を我々は広めの窓で潰している（§11-5）。

圧縮の 2 本自体はパージを壊さない（§11-2.4 後段）が、上の 3 本を巻き添えにする形で回す理由が
無い。引数なしの `CHECKPOINT` は既定カタログに効くだけで lake には届かない（実測）が、届く
書き方をしないこと。

### 11-2.3 `merge_adjacent_files` と `rewrite_data_files` の分担

**`merge_adjacent_files` と `rewrite_data_files` の分担は「削除を持つか」で決まる。**
規模でも溜まり方でもない（`src/functions/ducklake_compaction_functions.cpp`）。

- `merge_adjacent_files` は**削除を持つファイルを扱わない**
  （`merge_adjacent_files should not be used to rewrite files with deletes`）。
  `target_file_size`（既定 `1 << 29` = 512 MiB、`ducklake_catalog.hpp`）まで小さいファイルを
  積んで 1 つに切り、単体で閾値を超えるファイルは飛ばす。実測: 削除を持たない小ファイル
  40 個 → 1 個
- `rewrite_data_files` は削除を持つファイルが担当で、`delete_threshold`（既定 0.95、
  設定名 `rewrite_delete_threshold`）を超えたものを書き直す。削除ファイルを消せるのは
  こちらだけである

  ii-b が回すのは `merge_adjacent_files` だけである（§11-2.1）。

**両者を分けているのは「置き換えが元と同じ問いに答えられるか」である。**

merge は削除を持たない、row_id が隣接するファイルだけを選ぶので、統合結果は元のファイル群と
**同じ行集合**になる。統合ファイルには行ごとの `snapshot_id` 列が書き込まれ
（`write_snapshot_id`）、カタログの `partial_max` と `SetSnapshotFilter` が古い版に対して後の行を
隠す。**1 本で全世代のビューを再現できる**ので元ファイルは冗長とみなされ、`WriteMergeAdjacent` が
**カタログ行ごと `DELETE`** する（`end_snapshot` で閉じるのではない）。統合ファイルの
`begin_snapshot` が最古の元ファイルまで遡るのは、その穴を埋めるためである。

rewrite は削除を実体化するので出力が元と同じ行集合にならず、古いスナップショットの代役になれない。
だから `WriteDeleteRewrites` は元のデータファイルと削除ファイルを `end_snapshot` で閉じて**残し**、
新ファイルには rewrite 時点の `begin_snapshot` を入れる。**履歴を指し替えない。**

**この差が、パージを §9 の形にしている。** merge を回すと、N より前の保持スナップショットが N 以降の
行を含む統合ファイルを参照し続けるので、**層2から特定の版の行だけを消すことはできない**（実測:
4 版ごと merge・汚染は区間の途中で、細粒度パージの後も汚染行 10 が残る）。カタログを見ると、後の
merge が前の統合ファイルを飲み込むので `begin` は常に履歴の先頭に落ちる:

```
既定                  #9[2..) → #18[2..) → #27[2..)     毎回すべて作り直し
max_file_size 明示    #9[2..)  #18[7..)   #27[12..)     区間ごとに独立
```

**タイムトラベルは全版で正しいままなので、壊れるのは消去の粒度だけで、内容を見るテストでは
気づけない。** だから §9 のパージは**取得不能までを主張し、層2のバイト列消去は保証しない**。

**`rewrite_data_files` を代わりに回す案は採らなかった。** 履歴を指し替えないので細粒度パージが
成立する（実測: 300 版・50 版ごと rewrite・版 220 で汚染 → 汚染行 39 → 0、保持 220 版の内容
ダイジェスト一致）が、**追記主体のデータでは効かない**（§11-2.1 の表）。削除を 1 件も持たない
ファイルは閾値に関係なく候補外で、追記された版がまさにそれである。行が頻繁に使い回される合成
データでのみ有効だった（1000 版・2000 行で live 358 → 8、走査 24.5 → 6.6 ms、ストレージ +10%）。

**`max_file_size` で merge の区間を閉じる案も採らなかった。** 「1 版の差分 < max ≤ K 版の統合結果」に
置けば `begin` の遡りが 1 区間に収まり、巻き添えは最大 K-1 版になる（実測で汚染行 0 まで落ちた）。
採らないのは、1 版の差分サイズがリソースごとに桁で違い、**窓を外しても気づけない**からである。

### 11-2.4 全書き直しではなく差分を採る

**全書き直しか差分かは、我々が述語で選ぶ。差分を採る — ストレージが 2 桁違う。**

`WHEN MATCHED THEN UPDATE` には述語が無いので**一致した全行**を更新し、値が同じ行も更新扱いに
なる。結果としてファイルが丸ごと書き直される。`WHEN MATCHED AND t.c IS DISTINCT FROM s.c THEN
UPDATE` にすると実際に変わった行だけになり、差分ファイル + 削除ファイルになる。`MERGE` と
`UPDATE` の挙動は**同一**で、書き込み経路を決めているのは「その文が何行更新するか」だけである
（[#462](https://github.com/duckdb/ducklake/issues/462) の説明どおり。当初これを DuckLake の
欠陥と見て #1388 に報告したが、比較が不公平だったので取り下げた）。

実測（10 万行、毎版 5 行変更）:

| 版数 | 方式     | live | 削除 | 合計バイト |  全走査 |  点検索 |
| ---: | -------- | ---: | ---: | ---------: | ------: | ------: |
|   30 | 全書直し |    1 |    0 |    38.1 MB |  6.4 ms | 5.15 ms |
|   30 | 差分     |   30 |   29 |    0.93 MB |  8.0 ms | 6.59 ms |
|  100 | 全書直し |    1 |    0 |     125 MB |  6.1 ms | 5.89 ms |
|  100 | 差分     |  100 |   99 |    1.24 MB | 11.2 ms | 6.53 ms |
|  300 | 全書直し |    1 |    0 |     374 MB |  6.1 ms | 5.64 ms |
|  300 | 差分     |  300 |  299 |    2.89 MB | 18.7 ms | 6.69 ms |

- **ストレージは差分が圧倒的**（300 版で 130 分の 1）。全書き直しは版ごとに表全体を複製する
- **全走査は差分が版数にほぼ比例**（+0.04 ms/版）。バイト数ではなくファイルあたりの
  オーバーヘッドで、読むバイト数はむしろ差分の方が少ない
- **点検索はほぼ不変**（統計でファイルを枝刈りするため）

**追記主体のデータでも結論は変わらない**（基底 2 万行・毎版 +200 行追記 + 5 行訂正、360 版）:

| 方式             | live |    バイト数 |     全走査 |
| ---------------- | ---: | ----------: | ---------: |
| 全書き直し       |    2 |  **255 MB** |     6.1 ms |
| 差分（圧縮なし） |  721 |     1.24 MB |    28.7 ms |
| **差分 + merge** |   11 | **0.81 MB** | **6.0 ms** |

**読み取り性能は全書き直しと差分 + merge で同じで、違うのは容量だけ**（315 倍）。追記主体では
版ごとのファイルが `基底 + v × 追記` 行になるので、全書き直しの累計は版数の二乗で伸びる。

**小さいのはデータファイルであって、削除ベクタではない。** 200 版・merge 後の内訳（実測）:

| 種別              | 本数 |     合計 | 1 本あたり |
| ----------------- | ---: | -------: | ---------: |
| データファイル    |  133 | 674.1 kB |    5.07 kB |
| 削除ファイル      |  132 | 145.1 kB |    1.10 kB |
| （参考）全行 1 枚 |    1 | 525.4 kB |          — |

**200 版ぶんの履歴が、テーブル 1 枚のコピーの 1.56 倍**に収まっている。効いているのは 1 版が
約 205 行（追記 200 + 訂正 5）しか書かないことで、全書き直しなら毎版 525 kB を複製する。

**削除ベクタは層 2 の中で最も効率が悪い部分である。** 1 本 1.10 kB のうち中身は 5 行ぶんの位置
情報だけで、残りは Parquet のフッタ固定費である。しかも **`merge_adjacent_files` が畳むのは
データファイルだけ**なので、削除ファイルは版ごとに 1 本ずつ増え続ける（上表の 133 対 132 が
その形）。現在の規模では 18% にとどまるが、**畳まれない側**であることは覚えておく。

**全書き直しなら版はファイルを共有しない。** 各版のファイルが `[v, v+1)` ちょうど 1 スナップショット
幅になるので、merge も `begin_snapshot` の議論も現れない。**それを 315 倍のストレージで買うことに
なるので採らない。**

**ただし、それでも層2の消去は保証できない。** 版がファイルを共有しなくても、スナップショットは
カタログ全体のものなので、**別リソースの保持スナップショットが `[v, v+1)` の中に落ちればその
ファイルは解放されない**（§9.2）。全書き直しが解くのは版どうしの同居であって、リソースどうしの
同居ではない。§9 の非保証は書き込み形態の選択とは独立している。

**差分では 1 つのファイルが複数の版から参照され、消したい行と live で現行の行が同居する。**
実測のカタログ:

```
#13[8..)x15   ← v7 が書いたファイル。汚染 10 行 + 無関係な 5 行
```

この 5 行が現行なので `end_snapshot` が付かず、その版を expire しても解放されない。**これ自体は
DuckLake の欠陥ではない** — v6 の内容は v5 のファイルに依存しているので、黙って解放すれば v6 が
壊れる。解放しないのが正しい。細粒度パージが成立する条件と、それを採らなかった経緯は §9.7。

**古いスナップショットが失効する経路は他に 2 つあるが、どちらも内容を失わない。**
`standLakeTableOn`（巻き戻し・調停）は記録スナップショットを差し替えるので旧 ID が失効するが、
巻き戻しが全内容の新ファイルを書いている。リコンシリエーション（§4-4）は解決できない
スナップショットを null 化するだけで、差分機能が縮退する。

**§7.2 を降ろすと前者は無くなる。** 版行の ID を書き換えないので旧 ID が失効せず、失効候補は
「どの生存版も名指ししていないもの」だけになる — パージの降ろしが着地した最新スナップショットが
その唯一の常連であり、それは上の規則で常に残る。

**版の保持世代数（§14.1-8）を入れると、話が変わる。** 生存版のスナップショットが失効しうるように
なるので、そこで初めて「保持世代の外にある内容が統合ファイルにしか残っていない」状態が生まれる。
実装するなら、層1から層2を復旧できる範囲と揃えて決めること — 保持世代数は、層2の復旧可能範囲も
同時に定義する。

規模の注記: 全書き直しの出力は `CREATE TABLE AS` より嵩む（同じ 10 万行で 842 KB → 1.24 MB、
以後は横ばい）。1 回きりの増分で累積はしないが、版数 × 表サイズで効く。

### 11-3 スナップショット expire

**スナップショット expire**:

- **明示リスト方式**（`versions => [失効候補]`）。失効候補 = 全スナップショット −
  **パージされていない版行**が参照する ID − 最新スナップショット。**基準は「現行かどうか」では
  なく「パージされたかどうか」である** — 差分は両端の版をスナップショットに解決して読むので、
  現行でない版を落とすとその版との比較が壊れる（`lake-reclaim.ts` は現在 `active` と `superseded`
  を採る。§7.2 を降ろすと `active` だけになる）。
  最新スナップショットを常に残すのは、パージがテーブルを降ろした直後は
  どの版行からも参照されない最新スナップショットが現行内容だから。

  `ducklake_expire_snapshots` が受けるのは `versions` / `older_than` / `dry_run` の 3 つで、
  前 2 者は排他である。**「N より新しいものを失効させる」引数は存在しない**ので、範囲は
  リストに展開するしかない。

- **時刻ベース `older_than` は使わない。ただしそれは、この形式が本来用意している保持軸である。**
  スナップショットがカタログ全体のものである以上、意味を持つ軸はグローバルな時間しかない
  （§9.2）。`versions` の明示リスト方式は、**時系列しか持たないモデルにリソース単位の保持を
  表現させている**ことになる。

  それでも採らないのは、我々の方針が「全世代残す」だからである。`older_than` は**更新の止まった
  リソースを巻き込む** — 1 年更新のない版のスナップショットは古いが、その版は現行かもしれず、
  切れば内容は無事でも差分とタイムトラベルを失う。方針が「全部残す」である限り、**時刻は必要性の
  指標にならない**。正しい基準は参照の有無だけである。

  **層 2 に保持方針を入れるなら、そのときは時間で述べること**（§14.1-8）。世代数で述べると
  この関数では実行できず、明示リストを自前で組み立て続けることになる。

- **`expire_older_than` オプションをカタログに設定しない。** これは永続化される既定値で、
  設定すると**引数なしの `ducklake_expire_snapshots()` が時刻ベースで走り出す**。
  `CHECKPOINT` はまさに引数なしで呼ぶ（§11-2.2）。我々の reclaim は常に `versions` を明示し、
  対象が無ければ呼びもしないので影響を受けないが、設定そのものが引き金になる。
- パージジョブの中で、DuckLake ingest ロックを保持したまま実行する。ロックが、
  ingest が DuckLake にコミット済みで版行にまだ記録していない瞬間のスナップショットを
  巻き込むのを防ぐ（DuckLake のコミットは別接続のため、この窓が存在する）。

### 11-4 `parquet_compression` を `zstd` にする

**`parquet_compression` を `zstd` にする**（`CALL lake.set_option('parquet_compression', 'zstd')`）。
DuckLake は設定が無ければ圧縮オプションを渡さないので（`ducklake_insert.cpp` の
`TryGetConfigOption("parquet_compression", ...)`）、**DuckDB の既定 = snappy で書かれる**。
層 3 のプレビュー生成は既に zstd を明示しており（`interpret/csv.ts`）、層 2 だけが既定のまま
だった。

実測（360 版・基底 2 万行、`parquet_metadata` で列チャンクとフッタ等に分解）:

| 設定           |    総量 | 列チャンク | フッタ等 | 圧縮率 |
| -------------- | ------: | ---------: | -------: | -----: |
| 既定（snappy） | 1.24 MB |    0.94 MB |  0.30 MB |  2.23x |
| zstd           | 0.60 MB |    0.30 MB |  0.30 MB |  6.98x |
| merge + zstd   | 0.38 MB |    0.31 MB |  0.07 MB |  8.05x |

**列チャンクが 68% 縮む。** merge が削るのはフッタ等の固定費なので、**両者は別のものを削って
おり効果は加算的**である（1.24 → 0.38 MB）。設定は以後の書き込みにのみ効くので、既存カタログ
のファイルは snappy のまま残る（実害は無い。実測でも 1 つのカタログに 2 コーデックが混在した
状態で読める）。

### 11-5 バックアップ整合

**PG（カタログ + 意味層 + 版対応）が唯一の正で、S3 側リストアは行わない**（ADR-037）。
カタログが PG の中にあるので、PG を時点 T へ戻せば**カタログと意味層は必ず同じ時点で揃う**。
S3 だけが「今」に居る。

**ただし S3 は追記のみではない。** `cleanup_old_files`・`delete_orphaned_files`・パージの
`storage.delete`・ライフサイクルが消す。**そして §9.8 は物理削除を PG バックアップ保持期間に
意図的に結合させないと決めている** — つまり**パージを跨ぐ復元では、カタログが消えたファイルを
指す状態が仕様上必ず起きる**。偶発ではなく設計の帰結である。

**そして null 化だけでは足りない。** `ducklake_snapshot_id` の null 化は**意味層のポインタを
外すだけ**で、欠損ファイルを名指している DuckLake のカタログ行には触らない。**そのテーブルの
現在内容の読み取りが落ちる。**

実測（DuckDB 1.5.4。v1 のカタログを退避 → v2 を投入 → v1 を expire + `cleanup_old_files` →
退避したカタログを現在の data path へ接続）:

```
SELECT count(*) FROM lake.t   → 50        ← 正しい値を返す
SELECT name    FROM lake.t    → IO Error: Cannot open file "…-8050-….parquet"
```

🔴 **`count(*)` は嘘をつく。** カタログの統計から答えるのでファイルに触らない。**行数を数える
健全性チェックは「正常」と報告し、実際の読み取りは全部落ちる。** 検証するなら列を読むこと。

**復旧元は「最新の健全な層 2 版」である。live 版ではない。** 定義は
**「パージされていない版のうち、`ducklake_snapshot_id` が非 null かつ実際に解決する最新の版」**。

**live 版を基準にしてはならない。** live 版が層 2 に入っているとは限らない — キーが不正なら
取り込みは断られ（§6.6）、その版のスナップショットは null のまま、**掃き出しからも
`lake_ingest_reason` で除外される**。v1 が健全・v2 が live で `key-missing` という普通の状態で
live を基準にすると、復旧元が無いまま「null 化 → 掃き出し」へ落ち、**掃き出しはその版を拾わない**
ので何も直らない。層 2 が追随しているのは**取り込みに成功した最新の版**であって live ではない。

**壊れ方は 2 通りあり、直し方が違う。** 分けるのは「**その最新の健全な版があるか**」である。

| 壊れているもの                          | 直し方                                           | 履歴 |
| --------------------------------------- | ------------------------------------------------ | ---- |
| 現在 head だけ（健全な版が 1 つはある） | その版のスナップショットから **head を書き直す** | 残る |
| 健全な版が 1 つも無い                   | 解決しない版行を null 化 → 掃き出しが層 1 から   | 失う |

**2 行目でも直らない版がある。** `lake_ingest_reason` が入っている版は掃き出しの対象外なので、
null 化しても拾われない。**それは正しい** — その版はキーが不正で層 2 に入れないと決まっており、
復元の前からそうだった。テーブルは次に取り込める版が来るまで空のままになる。

**1 行目が既定である。** 現在 head は版行が名指ししていないスナップショットのことがある
（`standOnBase`、パージの降ろし）。**名指されないものは reclaim の対象なので、後から expire +
cleanup で消える** — その状態を含む PG を復元すると、**版行は 1 つ残らず解決するのに head だけが
落ちる**。実測:

```
v1@snapshot 1（版行が名指し）        → 読める
現在 head（無名 snapshot 2）         → IO Error
修復: CREATE OR REPLACE TABLE t AS SELECT * FROM t AT (VERSION => 1)
     → head 復旧、v1 の履歴も読めたまま
```

🔴 **この経路をリコンシリエーションは検出できない。** 版行が指すスナップショットは全部解決するので
null 化する対象が無く、**掃き出しも動かない**（`pendingLakeIngestQuery` は
`ducklake_snapshot_id IS NULL` を条件にしている）。**だから検出は「head の列を読む」でなければ
ならない**（§4-4）。`DROP` して掃き出しに任せる手順は、この場合**何も再取り込みせずテーブルを
恒久的に失う**。

**head の書き直しに `CREATE OR REPLACE` を使うのは、ここだけの例外である。** §7.2 が禁じている
のは**内容の移動**を版の発行以外で行うことで、これは移動ではなく**同じ内容の再現**である。
取り込み経路は使えない — キー付き `MERGE` は対象テーブルの現在内容を読むので、head が読めない
状態では走らない。そして**版行を 1 つも触らない**ので、書き込み一度きりの規則は破れない。

**2 行目では版行のスナップショットを null 化する。これは書き換えではない。** 書き込み一度きりは
「同じ版が別のスナップショットを指すようになること」を禁じる規則である。null 化は**その書き込みを
取り消す**操作で、その版は未取り込みへ戻り、掃き出しが**改めて一度だけ**書く。復旧時の例外では
なく、規則の内側にある。

**どちらでも直らない場合**（live 版の層 1 も無い＝パージ済み）は `DROP` する。そのリソースは
次の版が来るまで層 2 を持たない。**それは復元の失敗ではなく、パージが成功していたということである。**

**層 2 を無条件に丸ごと捨てる契約は採らない。** 壊れているのは欠損ファイルを掴んだテーブルだけで、
無傷の他リソースまで巻き添えにする理由が無い。**単位はテーブル（＝リソース）である** — 版単位の
縮退では足りず、カタログ全体では広すぎる。

### 11-6 `delete_orphaned_files` は cron で掃く

**`ducklake_delete_orphaned_files` は cron の掃き出しで使う**（`sweep-lake-orphans`）。
カタログが追跡していないファイル（Parquet 書き込み後・カタログコミット前の異常終了で残る）
が対象で、expire / cleanup とは守備範囲が違う。書き込み中のファイルを孤児と読まないよう、
`olderThan` の窓を広めに取る。

[ducklake#815](https://github.com/duckdb/ducklake/issues/815)（修正済み。
[#863](https://github.com/duckdb/ducklake/pull/863) が `DATA_PATH` の区切り文字処理を直した）は、
expire 後に `begin_snapshot` を失った**現用ファイル**を孤児と判定して消すというものだった。
パージが expire し cron が掃く我々の運用はその組み合わせそのもので、`DATA_PATH` が末尾
スラッシュ（`lake/`）な点も一致する。回帰を `maintenance.ducklake.test.ts` に置いた —
修正済みだから通るのであって、拡張を古い版へ戻せば落ちる。

### 11-7 検討して採らなかった形（経緯）

**`rewrite_data_files` を 100 版ごと。** 合成データ（2000 行を毎版 20 行ずつ、行が約 100 版で
一巡する形）では効いた — live 358 → 8、走査 24.2 → 7.1ms、ストレージ +10%。K を掃引した結果も
残す（1,200 版・1 万行、圧縮直後と K-1 版後）:

|   K | 直後 scan | 直前 scan | 直前 live |      直前 bytes |
| --: | --------: | --------: | --------: | --------------: |
|  25 |     7.2ms |     8.6ms |        26 |         7.87 MB |
|  50 |     8.7ms |    10.4ms |        51 |         4.92 MB |
| 100 |     6.5ms |    12.5ms |       101 |         3.60 MB |
| 200 |     6.1ms |    17.4ms |       201 | 3.36 MB（最小） |
| 400 |     6.6ms |    32.2ms |       401 |         4.60 MB |

**採らなかったのは、この形が行政データの既定ではないからである。** 行が頻繁に使い回されて初めて
削除比率が上がるが、多くの実データは追記主体で、追記されたファイルは削除を持たない。上表の合成
データが一巡の周期を持っていたことが、`rewrite_data_files` を過大評価させていた。

**ただし「現れない」ではない。** 現行イベント一覧、掲載期限のある告知、空き状況のように、
**行が入れ替わる行政データは一定数ある**。そうしたリソースでは削除比率が上がって候補が現れ、
expire がバイト列を実際に解放する（§14.1-8）。**既定を追記主体に合わせたうえで、外れるリソースは
個別に扱う** — `MERGE_FILE_THRESHOLD` はランタイム設定であり（§11-2.1）、圧縮関数を選んで叩く
入口は §14.1-9 に置いてある。

**`rewrite_data_files` を閾値 0.95 で毎版呼ぶ**（候補が出たときだけ働くので無駄がない、という形）。
**空振りは実際に無料である** — 実測で 300 版・300 回呼んで発火 0、スナップショットも増えない
（候補ゼロの呼び出しはトランザクションを開かない）。**追記主体のデータでは一度も発火しない**ので、
入れても実害は無い。

採らなかったのは、発火する条件下での取引が悪いからである。行の回転が速い形（2000 行・毎版 1%
更新・1000 版）で数えると:

```
呼び出し 1000  発火 310  読んだ 401  書いた 310  うち統合を伴った発火 82
live 353（呼ばなければ 358）  スナップショット +312
```

**発火の 4 分の 3 は 1 本を自分自身に書き直しただけ**でファイル数が変わらない。統合が起きた 82 回を
含めても正味 91 本しか減らず、同じ期間に約 1000 本増えるので走査は 0.8ms しか改善しない。対価は
**恒久的なスナップショット 31% 増**である。毎版という刻みでは候補が 1 個ずつしか現れず、まとめる
相手がいない — 周期を空けて候補を溜めて初めて統合器として働く。

**この関数自体は書き直しではなく圧縮器である。** 名前と説明（「削除の多いファイルを書き直す」）
からは 1 ファイル → 1 ファイルの操作に読めるが、実測では閾値を超えたファイルが複数あると
**まとめて 1 つに統合する**（`files_processed: 3, files_created: 1`）。将来使う場面が出たら
閾値 0 を明示すること（既定の 0.95 では、破棄すべき行を 1 行含むだけのファイルは書き直されない）。

`merge_adjacent_files` との機構の違いは §11-2.3。

## 14. 残課題

### 14.0 ii-b に着手する前に読むもの

ADR-043 残課題 7 が本体。**ii-a が例外的に成立していた前提が 3 つ落ちる**。3 つとも解決済み
（ADR-043 §5 を更新）だが、解いた形が ii-b の設計を縛るので着手前に読むこと。

1. **revert は層2に追随する。** `revertLiveContent` が層2の戻り先のスナップショットへ rollback
   する。**復元先そのものではない** — 復元先が未取り込みなら、取り込み済みの最上位版まで降りる
   （§9.1 と同じ定義。以前は何もせず掃き出しに委ねていたが、復元先が取り込めない版だと
   テーブルが差し戻した行を持ち続ける）。復元先は掃き出しが別途拾う — `pendingLakeIngestQuery` が
   追い越しと見なすのを `active` な上位版だけに変えたので、revert が上位版を `superseded` に
   した時点で復元先が再び未処理として現れる。空にする revert ではテーブルを落とさない — 撤回した
   版は `purged` ではないので取得できなくする義務が無いからで、**落とすと差分が読めなくなるからでは
   ない**（当初その理由を書いていたが、`DROP` は保持スナップショットの読みを損なわない。§9.1 の実測）。
   その結果 head は撤回された行を持ったまま残る（残課題 16）。

   **§7.2 を降ろすとこの機構ごと不要になる。** revert が新しい版の発行になれば層2への追随は
   通常の取り込みそのもので、「追随」という別経路が無い。`superseded` も `stepOffAbove` も消える。

2. **取り込みは土台に立ってから載せる**（`standOnBase`）。当初案は「列が動いたかの判定を
   直前 active 版のスナップショットに向ける」だったが、これは ii-a を壊す — 判定だけ土台に
   向けても書き込み側の `DELETE` + `INSERT` はテーブルの現在内容の列で走るため、head と土台が
   食い違うと INSERT が落ちる。判定ではなく **head そのものを土台に合わせる**。ii-b の `MERGE`
   が必要とするのも判定ではなく土台そのものなので、こちらが本筋である。1 が失敗して残った古い
   head も、次の ingest が土台へ戻してから載せるため自己修復する。
3. **パージは版単位だが、範囲は運用者が判断する。** 差分適用では 1 ファイルに履歴専用行と現行行が
   同居するので、版のパージが層2のバイト列に届くとは限らない。**版のパージは「取得できなくする」
   までを主張し、層2のバイト列消去は保証しない。** 決定と手順は **§9**。

#### ii-b の実装で降ろすこと

**版行のスナップショットを書き込み一度きりにする**（§7.2）。`standLakeTableOn` の呼び出し元 3 つ
（巻き戻し・パージの降ろし・`standOnBase`）から、版行への ID 書き戻しを外す。巻き戻しは
**版の発行**に置き換わるので、`rollbackLakeTable` を使う経路自体が消える。**ADR-044 の改訂が要る**
（§14.1）。**当初この項は「書き換えが 1 度でも起きた版は `table_changes` の端点にできず、失敗が
空の差分として出る」ことを後追い不可の理由にしていた。差分が端点比較になった今、その理由は
無い**（§7.2 の注記）。降ろす理由は §7.2 の 2 つに置き換わり、**後追いにできるかも変わる** —
巻き戻しを版の発行にする変更は ADR-044 の契約変更なので、着手の順序として先に置くだけである。

**`standOn` を `ingestParquetVersion` のシグネチャへ畳む。** 現状 2 の不変条件を守っているのは
呼び出し側（`ingestVersionIntoLake`）であって `ingestParquetVersion` ではない。呼び出し元が
1 つしかない今は安全だが、`MERGE` 用にシグネチャを書き換える際に関数自身の最初の一歩へ畳めば、
「土台に立たせずに載せる」呼び出しが型で書けなくなる。`packages/lake` は版行を見ないまま
（スナップショット番号を受け取って返すだけ）で成立する。

#### 実カタログで確定した `MERGE` の性質

DuckDB 1.5.4 / ducklake `d318a545`。アサーションは
`packages/lake/src/__tests__/merge.ducklake.test.ts` にある — 相手の実装に対する主張なので、
散文で残すと DuckLake の更新で黙って古くなる。

- ✅ **`when_matched` に UPDATE/DELETE を 1 アクションしか置けない**（想定どおり）。エラーは
  `MERGE INTO with DuckLake only supports a single UPDATE/DELETE action currently`。
  `INSERT` はこの数に入らないので、upsert（UPDATE + INSERT）は 1 アクションとして通る
- ❌ **「upsert + `WHEN NOT MATCHED BY SOURCE THEN DELETE`」は 1 文で書けない。** 上の制約に
  そのまま抵触する。**2 文に分ける**こと:

  ```sql
  BEGIN TRANSACTION;
    MERGE INTO … WHEN MATCHED THEN UPDATE … WHEN NOT MATCHED THEN INSERT …;
    MERGE INTO … WHEN NOT MATCHED BY SOURCE THEN DELETE;
  COMMIT;
  ```

  トランザクションで囲めば**スナップショットは 1 つに畳まれる**ので、「1 版 = 1 スナップショット」は
  保てる（ii-a の同形分岐が `DELETE` + `INSERT` を囲っているのと同じ理由・同じ形）

- ✅ **取り込みは履歴に依存しない。** この 2 文の形なら、**取り込み後の内容は直前の状態に依らず
  版の bytes だけで決まる**。v1 を一度も見ていない・キーも共有しないテーブルに同じ版を載せて、
  結果が一致することを確認済み。ii-b 全体がこの性質の上に乗る
- ✅ **`ducklake_table_changes` は `update_preimage` / `update_postimage` を返す。**
  1 文の upsert なら 1 行の変更が 1 組で返る（キーレスの ii-a が出せなかったもの）
- ⚠️ **ただし 2 文の形では、変更行が複数回返る。** delete 側の文が upsert の書いたファイルを
  書き直すため、触っていない行まで再度報告される。**イベントを数えるなら行ではなく `rowid` の
  distinct で数えること**。実測では同一 `rowid` の `update_postimage` が 2 行返った。
  **差分 API はこれに依存しない** — イベントではなく両端の内容を突き合わせるので、
  重複報告も相殺も関係ない（§7「差分は端点の突き合わせで出す」）。ここに残すのは、
  取り込みの検証でイベントを読むときに要るからである。
  再現には**「1 トランザクションに 2 文」と「インライン化 OFF」の両方**が要る（2 文を別
  トランザクションにすると正常、インライン化が既定なら正常）。我々は ADR-043 §6-1 の理由で
  インライン化を 0 にしているため、逃げ道はない。
  [ducklake#1387](https://github.com/duckdb/ducklake/issues/1387) に報告済み
- ⚠️ **キー重複は黙って通る。** 重複キーを含むソースで MERGE は成功し、**片方の行が消える**
  （どちらが残るかも通知もない）。上流で決着済み:
  [duckdb/duckdb#24058](https://github.com/duckdb/duckdb/pull/24058)（マージ済み、v1.5.5 より
  後なので**未リリース**）が「1 つの対象行を 2 回触る `WHEN MATCHED` は cardinality error」と
  定義した。DuckDB 更新後は**投げる**ので、取り込み側にエラー経路が要る。
  [ducklake#520](https://github.com/duckdb/ducklake/issues/520) にも既出で、DuckLake 側の
  回答は「ソースで重複排除せよ」
- 🔴 **その修正でも塞がらない半分がある。** #24058 は `WHEN NOT MATCHED` を対象外と明記して
  いる。**対象に存在しない重複キーは両方 INSERT され**、テーブルの中でキーがキーでなくなる
  （実測）。しかも自己増殖する — 次の版では 1 つのソース行が 2 つの対象行に一致し、両方が
  更新される。**取り込み前検証はバージョンに依らず必須**であり、設定で切れるものではない
- ✅ **複合キーは動く。** `ON t.a = s.a AND t.b = s.b` で両方の半分とも通る。ただし
  `count(DISTINCT a, b)` は**バインダエラー**で、`count(DISTINCT (a, b))` か副問い合わせが要る
- 🔴 **キー列の NULL は永久にマッチしない。** `=` は `NULL = NULL` を満たさないので、
  版ごとに再挿入される。**重複検証はこれを設計として捕まえていない**（`count(DISTINCT)` は
  NULL を数えないので偶然引っかかるだけ）。§6.4 で規則として分離した
- ✅ **削除ベクタ有りテーブルのタイムトラベルは透過。** キー付き取り込みはファイル置換ではなく
  行削除になるが、`AT (VERSION => …)` は前後どちらの版も正しく返す。パージの reclaim と
  差分がこれに依存している
- ⚠️ **版行のスナップショットを書き換えると `table_changes` が黙って空を返す。**
  `standLakeTableOn` は巻き戻し先の版に新しい ID を上書きするので版番号順と逆転し、
  `table_changes(6, 5)` が **0 行**（実測）。エラーではない。**ただし差分はこれに当たらない** —
  端点比較はスナップショット ID の大小に依存せず、上書き後の ID でも正答する（§7.2 に実測）。
  当時これを 🔴 として §7.2 の根拠に置いていたが、**差分を端点比較に変えた時点で到達不能に
  なった**。イベントを読む取り込みの検証には今も効く
- ⚠️ **`CREATE OR REPLACE TABLE` は change feed から「全行 insert」に見える。**
  巻き戻しの追随（`rollbackLakeTable`）がこの形なので、**ii-b の行レベル差分が調停の
  スナップショットを跨ぐと全行が追加として出る**（実測 `insert=3`）。タイムトラベルと後続版の
  差分は無傷なので被害はその 1 スナップショットに閉じる。ii-a の差分は
  `AT (VERSION => …)` + `EXCEPT ALL` で影響を受けない。
  [ducklake#330](https://github.com/duckdb/ducklake/issues/330)（close 済み）で
  maintainer が「別テーブル扱いになる」と述べている挙動の裏返し。close は change feed の仕様
  準拠についてであり、この見え方は現行版でもそのまま（上の実測は `d318a545`）。
  **§7.2 を採れば巻き戻しは取り込み経路を通るので、この経路自体が消える**

0. ✅ **【実装済み】パージの層2の戻り先を層1と別に引く。**

   `executePurge` は live 版のパージで `newestActiveVersion()` を層1にも層2にも使い、その版が
   スナップショットを持たなければ `dropLakeTable` していた。**v1 取り込み済 / v2 は live だが
   未取り込み / v3 取り込み済** で v3 をパージすると、層1は v2 へ戻ってよいが、層2は v1 へ
   戻すべきところをテーブルごと落としていた。「未取り込みの live 版」は ii-b のキー不正を待つ
   までもなく、**大きすぎる版・表形式でない版**で今日成立する。しかも `dropLakeTable` は生存版の
   `ducklake_snapshot_id` を null 化しないので、掃き出し（`ducklake_snapshot_id IS NULL` が条件）が
   拾わない — §11-5 の復元で見つけたのと同じ恒久的損失だった。

   戻り先は `versionsLakeCanStandOn`（`active` かつスナップショット非 null、新しい順）で引き、
   **カタログが解決しないスナップショットは飛ばす**（§11-5 の実測を
   `maintenance.ducklake.test.ts` で固定した）。`DROP` は候補が 1 つも無いときだけで、
   **候補があって全部解決しないときは失敗させる**（§9.1。落とすと誰も直せない）。

   **降ろす条件も「live 版か」から「層2がその版に立っているか」へ変えた**（§9.1）。旧条件は
   両向きに外れており、中間版が層2の頂点のときは内容を動かさず、パージした行がテーブルの現在
   内容として残っていた。

   `lakeOwed` と巻き戻しの reconcile、取り込みの `standOnBase` は同じ関数（`lakeMoveOwed`）で
   問うようにした。**食い違わせてはならない** — 旧 `lakeOwed`
   は層1の版を読んでいたため、live 版が層2に入っていないと「何も owed でない」と**過小報告**し、
   撤回された行がテーブルに残っていても警告も修復入口も出なかった。逆向き（過大報告）は押しても
   消えない修復ボタンになる。テストは `lake-reconcile.integration.test.ts`。

   **`DROP` が失うのは現在内容だけである**（§9.1 の実測）。旧記述の「v1 の履歴ごと消える」は
   誤りで、保持スナップショットの読みは `DROP` を跨いで残る。恒久的なのは head を戻す者が
   居ないことである。

1. **クエリ対象拡大**: 現状 ≤50MB CSV/TSV。上限引き上げ・JSON 等（ADR-032/043 と同根）
2. **圧縮を取り込みジョブに載せる**: §11-2.1 の決定（取り込みの末尾で閾値つきの `merge_adjacent_files`）は
   周期も発火単位も持たないので、**別の定期ジョブを作らない**。載せ先は ingest の末尾で、
   対象はそのリソースのテーブルだけである。カタログ全体を掃く形にすると、更新の止まった
   リソースまで触る。

   **`MERGE_FILE_THRESHOLD` を ADR-036 のランタイム設定にする**（§11-2.1）。既定値 50 は
   採用形の書き込み経路で測り、書き込み側でも読み取り側でも最悪ではなかった値である。**動かす
   根拠は 2 つ** — 読み手の並列度と、**そのリソースの床**（畳めなくなる live 本数）。床より下に
   置いた発火は空振りになるので、まず床を測る。ECS のタスク定義（ADR-031 の環境定義に CPU がある）と
   紐づけて決めるのが筋である。

   測り直しは `pnpm bench:lake` で足りるが、**実運用の読み書き比**が別途要る — merge は公開ごとに
   1 回、走査は読まれるたびなので、比が分かって初めて T の上側が決まる（§11-2.1）。

   **T より先に `QUERY_THREADS` / `LAKE_INGEST_THREADS`（どちらも 2）を見直す。** 走査はレイテンシ
   律速なので、スレッドはコア数を超えて増やす価値がある — 2 vCPU で 2 → 8 スレッドが 2.45 倍、
   頭打ちはコア数によらず 8 だった（§11-2.1）。**2 は測定した中で最悪の点にあり、しかも T より
   効いて対価が無い**（同じ T=25 で 48.1 → 32.9ms、merge の回数は変わらない）。ただし両者は目的が違う:
   `LAKE_INGEST_THREADS` は worker の単独作業なので上げるだけでよいが、`QUERY_THREADS` は
   ユーザー SQL に対する資源上限（ADR-032）であって、上げると同時実行数 × スレッド数が効く。
   **上げるなら「リモートのデータパスのときだけ」が筋**で、ローカル FS では効かない。

   同じ場所で **`httpfs_connection_caching = true` を検討する**（§11-2.1）。既定 false のままだと
   1 スキャンで 140 本の TCP 接続を張り、有効にすると 6 本で cold 走査が 1.4〜1.75 倍速くなる。
   **既定が false である理由は確認していない** — 有効化の前に上流の意図（接続の陳腐化、プロキシとの
   相性）を当たること。1 行で効く一方、無条件に入れてよいとまでは今日の測定では言えない。

   **層 2 が数百 MB に達したら `target_file_size` を下げる**（§11-2.1 の表）。1 回の merge が書く量は
   `min(テーブルサイズ, target)` なので、テーブルが target と同程度の帯だけが病的であり、下げれば
   そこを抜けられる。**周期 K より筋が良い** — K はリソースごとに正解が違うが、これは
   「1 回に書いてよいバイト数」というサイズの言葉なので、テーブルが 1 MB でも 100 GB でも同じ値が
   意味を持つ。値の選定には GB 級の測定が要る（今日測れたのはディスク上 18 MB まで）

6. **墓標が見せるもの**
   - **連続した墓標をまとめる。** 版を続けてパージすれば数十版が `purged` で並ぶ。1 行ずつ出すと
     同じ情報の反復になり、「いつからいつまで出ていた内容が消えたか」まで読み取れる。
     `v10–v60 取り下げ済み` のようにまとめる。API をまとめる必要は無い（§9.6）が、表示は別である
   - **`purgeReason` を版のビューから落とす**（issue #425）。これは ii-b を待たない**現行の露出**である。
     `toView` は size/hash/schema を墓標では伏せているのに `purgeReason` は素通りさせており、
     `GET /resources/:id/versions` は公開リソースなら匿名で読める。削除要請への対応では
     **消すはずだった情報が理由欄に残る**ことすらありうる。UI は表示しておらず（`purged`
     バッジのみ）、説明責任は監査ログ（`auditLog` に実施者・理由・日時）が果たしているので、
     権限で出し分けるのではなく**落とす**。`purgedAt` は残す — 版番号の飛びの説明に要り、
     日時単体では内容を漏らさない

7. **パージ時に park 済みオブジェクトを即時 sweep する**（§9.8）。中間の実行が作ったプレビューは
   置き換え時に `orphaned_object` へ park されるだけで、パージはそれを早めない。1 時間 +
   sweep 周期のあいだ、汚染行を含むプレビューがストレージに残りうる。ii-b を待たない現行の
   窓であり、複数版をまとめて消すと版数ぶん増える
8. **保持世代数を層 1 のバイト列だけに適用する**（差分方式を採るなら、削るべきはここである）。
   層 2 は差分なら 2 桁小さく、層 1 は版ごとに表全体の完全な複製を持つ。**スナップショットは
   全世代残す**ので、生存版の参照が切れず §11-2.4 の危険な順序は到達不能のままである。
   機構は既にある — パージの墓標が「行は残してバイト列を消す」形で、これはその逆（バイト列を
   消して `ducklake_snapshot_id` は残す）。設計が要るのは 3 点:
   - **層 2 が答えられる版だけを対象にする。** 非表形式や `too-large` / `too-many-columns` /
     `no-columns` の版には層 2 が無く、バイト列を消すと内容が完全に失われる。判定材料は
     §6.6 の `no_table_reason` で揃う
   - **「バイト列は無いがデータはある」を表せない。** `state` は 4 値、`storage_key` は
     `NOT NULL`。`purged` の流用はパージの墓標として表示されるので不可。版履歴 UI が
     「ダウンロード不可・差分可」を示せる列か状態が要る
   - **ADR-043 の前提が反転する。** 層 2 は「層 1 から常に再構築可能な派生インデックス」では
     なくなり、古い版については**層 2 が唯一の記録**になる。ADR 側の判断が要る
   - **保持世代数は、層 2 の復旧可能範囲も同時に定義する。** 層 2 の復旧は層 1 から流し直す形しか
     無いので、層 1 を間引いた版は層 2 の行レベル差分が戻らない。矛盾ではなく整合していて、間引いた
     版はそもそも内容をダウンロードできないから両者は同じ範囲で落ちる。**独立には決められない**
     という点だけが制約である
   - **引き金はオブジェクト容量ではなくカタログの行数である。** 差分 + merge では層 2 のバイト列は
     版あたり 3.4 KB しか増えない（200 版で 0.67 MB）。一方カタログは**版あたり約 4.7 行**増え、
     **減らない** — 実測（1 リソース・200 版）で `ducklake_snapshot` 206 行、`snapshot_changes`
     206 行、`data_file` 133 行、`delete_file` 132 行、`file_column_stats` 266 行。merge は
     `data_file` の行を消すが、スナップショットは残す。**これを減らせるのは expire だけである。**
   - **そして expire が減らすのはその行数だけで、バイト数は減らない**（実測）。200 版の履歴で
     最新以外の全スナップショットを expire + `cleanup_all` しても、**820 kB がそのまま残った**
     （スナップショットは 206 → 1）。**追記主体のデータではどのファイルも履歴専用にならない** —
     どの版のファイルも現行行を抱えているので、履歴を消しても解放対象が生まれない。**これは差分方式
     一般の性質ではなく、行の回転速度で決まる** — 行が入れ替わる合成データ（2000 行・毎版 1%・300 版）
     では同じ expire で総ファイル 302 → 100、0.26 → 0.08 MB まで落ちた。実データが追記主体である
     以上こちらが既定だが、回転の速いリソースでは expire にも意味が出る。`rewrite_data_files` を
     挟んでも 820 → 788 kB（4%）で、削除ベクタはほぼ消えるがデータ側が増えて相殺される
     （674 → 774 kB）。**バイトを減らしたいなら live の畳み込みが要る**（§9.2）。層 2 の保持方針は
     容量のためではなく、カタログ行数のためにある
   - **層 2 側にも保持方針を入れるなら、世代数ではなく時間で述べる。** 層 2 の保持単位は
     カタログ全体のスナップショットで、それを切る関数は `older_than`（グローバルな時刻）しかない
     （§11-3）。「各リソースの直近 N 版」はこの軸に写せない — 毎時更新のリソースと年 1 更新の
     リソースで、同じ時刻の線が全く違う世代数になる。**層 1 は世代数、層 2 は時間**と軸を分けるのが
     形式に沿う。層 1 の保持と同じ言葉で書きたくなるが、書ける形が違う

9. **手動バキューム**（管理画面からリソース単位で圧縮を明示実行する）。取り込みごとの
   `merge_adjacent_files` は追記主体のデータに合わせた既定であり、行の回転が速いリソース
   （現行イベント一覧、掲載期限のある告知、空き状況など）では `rewrite_data_files` が効く余地が
   残る。ただし**効くのは候補が溜まった状態のときだけ**で、
   そうなるかは行の回転率に依存する（§11-2.1 の経緯）。自動判定は DuckLake の候補条件を我々の側に
   複製することになり、上流が条件を変えれば静かにずれる — 実際 `total_delete_count == 0` の
   先行判定は読み違えていた。**運用者が「このリソースは重い」と気づいた時点で叩ける入口**があれば
   足りる。閾値と対象関数を選べる形にし、実行結果（`files_processed` / `files_created`）を返す。

10. **修正版先行のパージ（データ損失ゼロ）**（§9.7）。live を残したまま
    N..live-1 だけ消す形で、実測でも成立した。差分方式ではこの形だけ `CREATE OR REPLACE TABLE t
AS SELECT * FROM t` による live の畳み込みが要る — 既定の N..live では巻き戻しが同じ働きを
    するので不要だが、こちらは巻き戻しが走らない。**畳み込みを手順の一部として書くこと。** 飛ばしても
    エラーは出ず、層2に残る行が増えるだけで静かに完了する

11. **ADR-044 の改訂**（§7.2）。巻き戻しを「戻す」から「その内容をもう一度発行する」へ変えるので、
    revert 契約（`restoreTo` + `ifLiveRevision`）と `superseded` の位置づけが動く。決めることは 3 つ:

    - **`superseded` を廃止する**（§7.2）。`stepOffAbove` を消し、live を「パージされていない
      最上位の版」に一本化する。**移行が要る** — 既存の `superseded` 行をどう読み替えるか。
      そのまま `active` に戻すと、過去に差し戻された内容が最上位なら live が動く。**動かさない
      形（既存行は据え置き、新規の巻き戻しから新方式）を既定に置く**のが安全だが、状態が 2 通り
      並ぶことになるので、実データを見て決める。`restoreTo` が `superseded` を拒む規則
      （redo 禁止）も同時に落ちる
    - **既存データの扱い。** ADR-044 は v0.11.x でリリース済みで、既にスナップショットを
      書き換えられた版がありうる。**端点比較はそれらも正しく読める**ので（§7.2 に実測）、
      差分のための移行は要らない。残るのは「書き換えられた版が、書き込み一度きりという新しい
      不変条件を満たしていない」ことだけで、**そのまま据え置いてよい** — 以後書き換えが起きなく
      なれば、その版の ID も動かない
    - **`restoreTo` の応答。** 新しい版番号を返すことになるので、API の互換性を見る

12. **断られた版の明示的な再投入**（§6.6）。`lake_ingest_reason` が付いた版は掃き出しの対象から
    外れたままで、キー設定を直しても自動では戻らない — §6.4 の「キー指定の変更は以後の版から適用」
    に従うためである。過去版も入れ直したいという要求が実際に出るかを見てから、入口を作るか決める。
    作るなら**リソース単位で「この時点のキーで層 2 を作り直す」**の形になり、版ごとに拾うより
    キー体系が揃う。

13. ✅ **【実装済み】パージ確認画面が「対象が live か」を答える。** §9.6 の 3 分岐は成立して
    いなかったので、文言は両分岐を条件付きで述べてごまかしていた。

    版のビュー（`VersionView`）に **`isLive`** と **`purgeFallsBackTo`**（この版をパージしたとき
    配信が戻る版。**live な版にだけ入る** — 他の版のパージでは配信が動かないので、答えを載せると
    起きない移動を名指すことになる）を足した。**確認画面はこの 2 つを読むだけで分岐を決める** —
    どちらの規則もサーバ側にしか無い。判定は `liveVersion()` — ポインタの
    所有者を引くもので、パージが判断に使っているのと同じ読み — で、`active` / `superseded` /
    `purging` を数える。一覧・単一取得・パージ claim の応答すべてが同じ答えを載せる。
    **クライアント側で版番号や active 版の総数から推測してはならない**（§9.6）。統合テストは
    **2 つの形**を固定している — 巻き戻し後（v2 が最上位で live でない、v1 が live で最上位でない）と、
    **live な版に claim が入った状態**（`purging` な v2 が live、active な v1 は live でない）。
    後者が「最上位の active 版」を破る唯一の形で、前者だけでは足りない。

    **一覧とポインタは 1 つのスナップショットで読む**（`repeatable read` の読み取り専用
    トランザクション）。別々に読むと、並行する巻き戻しの前の一覧と後のポインタが混ざり、確認画面が
    「戻り先は v3」と言った直後にパージが v1 へ戻す、という食い違いが起きる。**claim の応答も同じ
    読みで組む** — claim は書き込みで、掴むのは対象行だけなので、その中で残りを読んでも巻き戻しは
    止まらない（ポインタと上位版は別の行である）。claim を確定させてから読み直す。

    **ポインタを誰も所有していない旧データでは、判定は当て推量である**（`liveVersion` の
    ハッシュ一致フォールバック）。それでも表示してよい — **パージも同じ答えで動く**ので、画面は
    「起きること」を正しく述べている。

    **リソースが何も配信していないときは 3 分岐に当てはまる箱が無い。** どの版も
    `isLive: false` になるので「配信中の内容ではない」と言うが、配信中の内容自体が無い
    （空にする巻き戻しの後）。文言は誤りではないが、§9.6 の表に 4 つ目の行を足すかは未決である。

    **`isLive` が入っても条件付きの言い回しは残した。** 確認画面を開いてから確定するまでに live は
    動きうる（別の実行の publish、並行する巻き戻し）。API が答えるのは「今どれが live か」で、
    「確定した瞬間にどれが live か」ではない。3 分岐は起きることを先に見せるためのもので、
    保証ではない — その旨も文言に入れてある（`purgeCaseMayMove`）。

    **3 分岐の文言選択はテストで固定した。** `resource-version-history.test.tsx` に 3 分岐分の
    テストがあり、他方の分岐の文が**出ていないこと**と、共通文（競合の注記・先にダウンロード・
    層 2 に行が残る）が出ていることを見る。**戻り先の規則は統合テストが持つ** — `superseded` や
    `purging` を戻り先に数えないこと、生存版が 2 つあるときは自分以外の最上位を指すこと。E2E
    （`resource-versions.e2e.ts`）にも巻き戻し後の形を足した — live を v2 に置き v3 を
    `superseded` にして、v3 では「配信中の内容ではない」、v2 では「配信は v1 へ戻る」と出ることを
    見る。**版番号の順序はこの形で逆を答える**（`active` 絞りの規則を破るのは上記の claim の形で、
    そちらは統合テストが持つ）。

14. **確認画面の後続版チェック（N → N+1 の差分）が未実装。** §9.3 が「警告文より確実な歯止め」
    として求めているが、現在のダイアログにあるのは警告文と同一ハッシュの通知だけである。
    中間版のパージは**内容が後続に引き継がれていないときだけ意味を持つ**ので、これが無いと
    操作者は「消したつもりで消えていない」に気づけない。差分 API と `VersionDiffPanel` は
    既にあるので、ダイアログから同じ経路を呼べば足りる。

15. **解決しないスナップショットの後始末が無い。** 残課題 0 の実装で、パージは「候補があって
    全部解決しない」ときに失敗して止まるようにした（落とすと誰も直せないため）。**止まったものを
    直す道具は無い** — §11-5 が求める「解決しない `ducklake_snapshot_id` を null 化して掃き出しに
    層 1 から入れ直させる」経路が実装されていない。運用ツールとして要るのは 3 つで、
    どれも ii-b を待たない:

    - **head の健全性検査。** §11-5 のとおり列を読む（`count(*)` はカタログの統計から答えるので
      嘘をつく）。リコンシリエーションは版行の解決性しか見ていない
    - **解決しない版行の null 化。** 掃き出しの入口に戻す唯一の操作。`lake_ingest_reason` が
      付いた版は対象外のままで、それは正しい（§11-5）
    - **巻き戻しと `standOnBase` にも解決性の確認を入れるか決める。** 現在歩くのはパージだけで、
      他の 2 つは記録された id にそのまま乗る。§11-5 の状態では巻き戻しの修復が例外を投げ、
      `lakeOwed` は「owed」と答え続けるので、**押しても消えない修復ボタン**になる（ログには出る）。
      パージと同じ歩き方を入れるか、null 化の運用ツールに任せるかの判断である

16. **空にする巻き戻しの後、head は撤回された行を持ったまま残る。** `lakeMoveOwed` は「既に正しい」と
    「立てる先が無い」を同じ `null` で返し、**巻き戻しはどちらでも何もしない** — 落とす義務が無いこと
    （§9.1）の帰結であり、今日は害が無い（製品の経路で head を解決する読み手は無く、ii-a の取り込みは
    内容を丸ごと置き換える）。**ii-b で 2 つ要る**:

    - **`MERGE` は「土台が無いときは空から始める」を規則として持つ。** `standOnBase` は立てる先が
      無ければ何もしないので、放っておくと撤回された行の上に次の版を載せる
    - **落とす側に倒すなら、修復経路にも入れる。** `repairDerivatives` は空のリソースでは
      `clearEmptied` へ行き、層 2 を一度も見ない。巻き戻しの中だけで落とすと、その 1 回が失敗したとき
      直す入口が無い

17. **層 2 が立っている版の判定は、版行の記録に依存している。** `lakeStandsAhead` は
    「その版より上のスナップショットを持つ版が他に無いか」で答えるので、**取り込みが DuckLake に
    コミットしてから版行に id を書くまでの窓**（`ingestVersionIntoLake`）で落ちたテーブルでは
    外れる。パージは安全側に倒れる — 立っていないものを立っていると読めば内容を落とし、掃き出しが
    層 1 から入れ直す — が、**判定が版行の記録より強くはならない**ことは ii-b の `MERGE` が
    現在内容を土台にする前に見ておくこと。窓を閉じるには取り込みの記録を先に置く（先行記録、
    ADR-045 と同じ形）か、head を読んで確かめる必要がある。

## 15. スコープ外（Phase iii）

- 閲覧者向け「前版からの変更」UI、版指定クエリ
- プレビュー Parquet の DuckLake export への統合（生成経路の一本化）
- MCP 差分ツール（`get_resource_diff` 等）
- Iceberg エクスポート（公開スナップショットの外部エンジン直読み）
