# Phase AI-Summary: リソースの AI 生成抄録 — 実装仕様書

> **目標**: リソースに AI が生成した短い抄録を持たせ、リソースページに表示し、埋め込み
> テキストの材料に加える。**AI の推論はサマリー文の生成に限り、機械が信じる値（列の型・
> 主キー・ヘッダー行の位置）は生成しない。** 設計判断は ADR-053 を正とする。

## 1. 前提

- **ADR-053 のスパイク Phase A・Phase B は実施済み。** 残るのは判定基準 6（nDCG の前後
  比較）で、抄録そのものが要るため本フェーズの実装後に測る（§14）
- **ADR-040（AI メタデータ提案）が材料の組み立て・形式判定・評価ハーネスを持つ。** 抄録は
  これを共有するが、**提案フローの挙動は変えない**
- **ADR-046**: 抄録は版（イミュータブルな正本）から作る。同じ入力からは同じ材料が渡る
- **ADR-044**: 抄録の生成もリソース単位の実行 claim の下で行う
- **ADR-034 / 埋め込みのデバウンス**: 抄録は `embedding_hash` の入力になる。依存の鎖が
  1 本増える（§9）
- **Index ステップが document 形式の抽出テキスト先頭 64KB をストレージに保存済み**
  （`TEXT_HEAD_ARTIFACT_SIZE`、ADR-040 追補）。**PDF の抽出テキストはこれを使い、新しい
  抽出経路は作らない**

### 1.1 確定事項（ADR-053 残課題の決着）

| #   | 残課題                 | 決着                                                                                       |
| --- | ---------------------- | ------------------------------------------------------------------------------------------ |
| 1   | 生成言語               | **ランタイム設定** `ai-summary-locale`（ADR-036）。既定 `ja`。抄録ハッシュに含める（§4.2） |
| 2   | CKAN 互換 API への露出 | **出さない。** KUKAN 独自の `/api/v1` にのみ出す（§10.1）                                  |
| 3   | 「材料が空」の判定     | §7.3 の実値。評価（§14）で調整する                                                         |
| 4   | モデルの指定           | **`AI_SUMMARY_MODEL` で明示する**（既定なし）。推奨は Sonnet 4.6 相当（ADR-053 決定 6）    |
| 5   | 埋め込みの組み立て順   | ADR-053 決定 8 の表どおり。打ち切りは**文単位**（§9.1）                                    |
| 6   | AIAdapter の拡張       | `CompleteOptions.attachments` + `getDocumentInfo()`（§5）                                  |
| 7   | 連結の打ち切り         | **受け入れる。** リソース単位のベクトルは MVP 直後の別フェーズ（§15）                      |

ADR に無い決着が 2 つある。**どちらも ADR 側に追補する。**

| 論点                       | ADR の記述                                | 本仕様での決着                                                                                  |
| -------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------- |
| バックフィルの経路         | 既存の `rebuildOnly` に乗せる（決定 4.1） | **専用のジョブ種別**（§11）。`rebuildOnly` は派生物の全再生成を伴う                             |
| 生成しなかった理由の持ち方 | 列を列挙（影響の節）                      | **`summary` + `summary_meta`（jsonb）の 2 列**（§4）。`HealthCheckState` に倣う                 |
| 有効化の形                 | `AI_SUMMARY_ENABLED`（真偽値、決定 10）   | **`AI_SUMMARY_MODEL`（モデル名。未設定 = 無効）**（§6.1）。決定 10 の理由がモデルにも当てはまる |

#### バックフィルに `rebuildOnly` を使わない理由

`rebuildOnly` は [process-resource.ts](../../../apps/worker/src/pipeline/process-resource.ts) の
再利用判定（`!rebuildOnly && !versionCreated && derivativesDescribe(...)`）を迂回するため、
**Parquet の再生成と DuckLake の再取込（カタログ全体ロック）を全リソース分やり直す**。
抄録に要る材料はストレージと DB に揃っているので、この費用は払わなくてよい。

さらに抄録の生成鍵にはモデル・生成版・ロケールが入るため、**全件生成は 1 回きりの
操作にならない**（プロンプトの調整のたびに走る）。既存の「コンテンツの再処理」に相乗り
させると、そのたびに全文検索が空になる窓が生じる。

キューは増やさない — このキューは既に 9 つのジョブ種別が相乗りしており、埋め込みの全件
再構築（`EMBED_ALL_JOB_TYPE` → `EMBED_JOB_TYPE`）が同じ形を持っている。ADR-053 決定 4.3 の
「専用キューと専用ポーラー」は引き続き後続のままである。

## 2. アーキテクチャ概要

生成の入口は 2 つあり、**処理の実体は 1 つ**（`summarizeResource()`）。

```
増分（ADR-053 決定 4）
[Worker] resource-pipeline ジョブ
  Fetch → Version → Interpret → Lake → Index → Summarize  ← 追加（ベストエフォート）
                                                    └─ 抄録が変わったら
                                                       enqueueEmbeds（デバウンス経由）

バックフィル（§11）
[API] POST /api/v1/admin/generate-summaries
  └─ summarize-all ジョブ
        └─ パッケージごとに summarize-package ジョブ
              └─ 未生成のリソースを 1 件処理 → 残っていれば自分を再投入
                 残り 0 になったら embed-package を 1 回投げて終わる
```

**バックフィルがパッケージ単位の直列チェーンである理由**は 3 つある。

- **可視性タイムアウト。** 1 ジョブ = 1 リソース（3〜11 秒）に収まる。102 本のパッケージを
  1 ジョブで回すと最大 18 分かかり、再配信されて二重に課金される
- **埋め込みの部分反映を防ぐ。** 埋め込みのデバウンスは**先頭側**で、60 秒の窓に入った変更は
  捨てられる（[search-index.ts](../../../packages/api/src/services/search-index.ts) の
  `enqueueEmbeds`）。リソース単位に撒くと、102 本のうち最初の 1 本だけが反映された
  ベクトルで確定し得る。パッケージ単位なら窓に当たらない
- **完了検知が自然。** 残り 0 が終端なので、カウンタもフラグも要らない

## 3. 生成の対象と材料

### 3.1 形式別の材料（ADR-053 決定 3）

> **原本を渡すのは、そうしないと中身が取れないときだけ。**

| 形式                        | 材料                                 | 出所                                |
| --------------------------- | ------------------------------------ | ----------------------------------- |
| CSV / TSV                   | スキーマ（列名 + 型）+ サンプル 5 行 | 版の `schema` + プレビュー          |
| テキスト系                  | ストレージ本体の先頭                 | 版のオブジェクト                    |
| ZIP                         | ファイル一覧                         | Interpret のマニフェスト            |
| GeoJSON                     | 先頭数地物の properties + 地物数     | 版のオブジェクト                    |
| **PDF（テキスト層あり）**   | **抽出テキスト**                     | Index の text-head アーティファクト |
| **PDF（テキスト層が薄い）** | **原本をそのまま渡す**               | 版のオブジェクト                    |
| **XLSX / XLS / DOC / DOCX** | **原本をそのまま渡す**               | 版のオブジェクト                    |
| **画像**                    | **原本を渡す。5MB 超は縮小**         | 版のオブジェクト                    |
| PPT / PPTX                  | **抽出テキスト**（原本は渡せない）   | Index の text-head アーティファクト |

**原本を渡せない形式は抽出テキストを見る。** PPT 系はどのプロバイダの列挙にも無いが、Index は
`isDocumentFormat` の全形式から本文を抽出して保存している。原本が渡せないことは材料が無いこと
を意味しないので、**原本 → 抽出テキスト → 対象外**の順に落とす（ADR-053 決定 3.4 の追補）。
Office 形式そのものは原本渡しのままである。

**PDF の振り分け**は 1 ページあたり文字数で行う。

```
抽出テキストの文字数 / ページ数 >= 100  → 抽出テキスト（material: 'text-head'）
                              < 100  → 原本を渡す（material: 'original'）
ページ数が読めない                      → 原本を渡す
```

ページ数は `pdf-lib` で読む（純 JS、ラスタライザ不要）。抽出テキストは Index が保存済みの
アーティファクトをそのまま使う。**テキスト層があれば抽出テキストが 1.7〜9.3 倍安く、
出力も同等以上**（ADR-053 付録 16）。

### 3.2 上限（ADR-053 決定 3.3 / 3.4）

| 形式                    | 上限                           | 判定           | 超過時                   |
| ----------------------- | ------------------------------ | -------------- | ------------------------ |
| CSV / テキスト / ZIP    | **なし**（原本を渡さない）     | —              | —                        |
| PDF（テキスト層あり）   | **なし**（抽出テキストを渡す） | —              | —                        |
| PDF（原本渡し）         | **16MB**                       | 事前に測れる   | 抽出テキスト or 不可     |
| PDF（原本渡し）         | 50 ページ                      | 事前に測れる   | **先頭 50 ページを渡す** |
| XLSX / XLS / DOC / DOCX | 1MB **+ 送ってエラーで判定**   | 事前に測れない | 不可                     |
| 画像                    | 5MB（API のハード上限）        | 超過は縮小     | 縮小                     |

**PDF のバイト上限は 16MB。** ADR-053 §3.3 の注記のとおり、当初の 4MB は被覆率の数字で、
上限が答えるべき問いのどちらでもなかった。実測では 3MB でも 22.6MB でも入力は 3,158
トークンで不変、22.9MB で拒否される（ADR-053 付録 19）。**バイト数はトークンを買わない。**
16MB が守るのは API の受理限界（約 22.7MB）と worker のメモリだけである。

**ページ数超過は拒否せず、先頭 50 ページを渡す**（ADR-053 §3.7）。トークンはページ数に従う
ので、50 ページの上限がそのまま 1 ファイルの費用の天井である。切って渡す費用は、ちょうど
50 ページの文書を受け入れる費用と同じで、拒否は何も買わない。

**暗号化された PDF は切り詰められない**（ADR-053 §3.8）。`pdf-lib` の `ignoreEncryption` は
構造を解析するが復号しないため、`copyPages` は白紙のページを作る。`isEncrypted` で拒否する
— **ページ数を数えるのは安全、取り出すのは安全でない。**

**サイズ上限はバイナリを渡す形式にのみ適用する。** CSV はスキーマとサンプル行を使うので、
78MB でも材料は一定である。表形式はスキーマの有無で判定する。

**画像は 5MB を超えたら長辺 1600px に縮小して渡す。** `sharp`（libvips）を使う。JPEG は
shrink-on-load が効き、8,256 × 5,504 の写真でピーク RSS が 365MB → 105MB に下がる。
PNG の巨大なものは後続（§15）。

### 3.2.1 テキスト層の判定は読み出し上限を見る

PDF が抽出テキストと原本のどちらを使うかは 1 ページあたりの文字数で決める（閾値 100）。
**ただしその比は、読み出しが上限に達していないときだけ意味を持つ。**

抽出テキストの読み出しは `SUGGEST_TEXT_HEAD_BYTES`（16,384 バイト）で打ち切られる。日本語で
約 5,400 文字なので、総ページ数で割ると **約 54 ページを超える PDF はすべて「薄い」と判定
される** — 中身ではなく上限の大きさを測ってしまう（ADR-053 §3.6 の注記）。

```
上限に達している → テキスト層は濃い（埋めたこと自体が証拠）→ 抽出テキスト
上限未満         → 全文が手元にある → 文字数 ÷ ページ数で判定
ページ数が読めない → 抽出テキスト（自前のパーサが開けなかっただけ）
```

### 3.3 メタデータは文脈として添える（ADR-053 決定 3.2）

リソース自身の材料と**混ぜず**、`datasetContext` として分けて渡す。

```jsonc
{
  "datasetContext": {
    "title": "...",
    "organization": "...",
    "tags": ["...", "..."],
    "notes": "先頭 400 字まで",
  },
  "resource": {/* ADR-040 の serializeResource と同じ形 */},
}
```

`notes` は最も効くが最もオウム返しを招くため上限を置く。**メタデータは文脈であって材料
ではない** — 材料が空のリソースを「メタデータはあるのだから生成できる」とはしない。

## 4. データモデル

### 4.1 列

`resource` に 2 列を足す（28 → 30 列）。内部状態を jsonb に畳むのは `HealthCheckState` と
同じ扱いである。

```typescript
// packages/db/src/schema/resource.ts
summary: text('summary'),
summaryMeta: jsonb('summary_meta').$type<ResourceSummaryMeta>().notNull().default({}),
```

```typescript
export interface ResourceSummaryMeta {
  /** 'ai' = 生成されたもの、'human' = 編集者が上書きしたもの */
  source?: 'ai' | 'human'
  /** 編集者が非表示にした。生成も表示も埋め込みへの投入も止まる */
  hidden?: boolean
  /** 生成元の版（ADR-043）。断り書きに出す */
  version?: number
  /** 何を材料にしたか。断り書きの文言を決める */
  material?: 'schema' | 'text' | 'text-head' | 'original' | 'image' | 'files'
  /** どれだけ読んだか。断り書きが「全 N のうち先頭 M」と言うための数 */
  coverage?: SummaryCoverage
  generatedAt?: string
  /** 生成しなかった理由。画面に出す */
  skipReason?: SummarySkipReason
  // --- ここから下は worker だけが読む。公開射影に出さない ---
  /** モデル ‖ 生成版 ‖ ロケール（§4.2）。書き方が変わったかだけを言う */
  genKey?: string
  model?: string
  /** モデルの自己申告（「材料で説明できたか」）。記録と計測にのみ使う */
  grounded?: boolean
  /** 超過エラーが返した実トークン数。二度目は事前に弾く */
  rejectedTokens?: number
}
```

```typescript
export interface SummaryCoverage {
  /** 読んだ行数・文字数・ファイル名の数・ページ数 */
  read?: number
  /** 材料が総数を知っているときだけ */
  total?: number
}
```

**`coverage` は断り書きのためにある。** モデルは材料に言及することを禁じられている
（ADR-053 決定 2）ので、「全部を読んだ」のか「先頭だけを読んだ」のかは読者から見えない。
その差を述べるのはこの数字の仕事である（§10.3）。

**原本を丸ごと渡したときは `coverage` を持たない。** 「全部」は不在が既に言っている。
一部だけを渡した原本（ページ数超過の PDF）だけが持つ。

**`genKey` / `model` / `grounded` / `rejectedTokens` を公開しない。**
`extras` の `scrubbedExtras` と同じく、公開用の射影を 1 箇所
（`packages/db/src/schema/resource.ts` の `publicSummary` / `publicSummaryMeta`）に閉じ込め、
`summary_meta` を丸ごと返さない。射影に置くのはルートごとの実装漏れを防ぐためで、
**忘れたレスポンスは、誰かが取り下げた文章を公開するレスポンスになる**。

`hidden` と `source` を列に出さないのは、**どちらも WHERE で絞らないから**である。埋め込みの
組み立ても公開射影も行を読んだあとで判断する（§9.1）。

### 4.2 鍵は 2 つ: 版と生成鍵

```
version = 抄録が書かれた版（resource_version.version）
genKey  = モデル ‖ 生成版 ‖ ロケール
```

|                    | 同じ版                       | 違う版   |
| ------------------ | ---------------------------- | -------- |
| **生成条件が同じ** | 何もしない                   | 生成する |
| **生成条件が違う** | `refresh` のときだけ生成する | 生成する |

通常の実行は版だけを見る。書き方が変わったことに反応するのは、管理画面から明示的に
`refresh` を指定したときだけである（§11.2）。**比較するので、二度押しても無料である。**

- **版**: 版が立っているあいだ抄録も立つ。同じ版での再実行（内容の再処理 `rebuildOnly`、
  リトライ、定期再投入）は**費用ゼロ**である

  > **材料そのものをダイジェストにしてはならない。** モデルに渡した事実をハッシュすると、
  > パイプラインの内部改版 — Interpret が列統計を足す、確定済みの版が format を得て振り直される
  > — が、**見積もりに出ないまま全カタログを作り直す**（ADR-053 決定 9）。
  > 同じファイルに対してモデルに見せるものが変わるのはコードが変わったときだけで、それは
  > 自動で反映すべき事実ではなく判断である。

- **生成版**: `SUMMARY_GENERATION_VERSION`（定数）。**同じファイルに対して、モデルに見せるものか
  頼み方が変わる変更を入れる PR で 1 つ上げる** — プロンプトとロケール追補、サイズ・ページ数の
  上限、材料の選び方、抄録に反映したい抽出の改善。リファクタや UI の変更では上げない。
  モデルの切り替えは genKey のもう一方が動くので不要
- **ロケール**: 切り替えると全件が古くなるが、**自動再生成はしない**。混在する期間が生じる
  ことを管理画面に明記する（§10.3）

### 4.3 生成しない条件（ADR-053 決定 5）

| `skipReason`           | 条件                                                          |
| ---------------------- | ------------------------------------------------------------- |
| `disabled`             | `AI_SUMMARY_MODEL` が未設定（**記録もしない**。§7.1）         |
| `provider-unavailable` | `getCompletionInfo()` が null                                 |
| `unsupported-format`   | プロバイダが原本を受け取れず、抽出テキストも無い形式          |
| `too-large`            | サイズ・ページ数の上限超過、`size` が不明                     |
| `rejected`             | 送って `ValidationException`（恒久）。`rejectedTokens` を記録 |
| `no-material`          | 材料が空（§7.3）                                              |
| `not-public`           | パッケージが `active` でない（下書き・非公開）                |
| `hidden`               | 編集者が非表示にした                                          |

**一時的な失敗（スロットル・5xx・タイムアウト）を `skipReason` に書いてはならない。** これは
ステップの失敗として記録し、次の実行で再試行する。

## 5. Step 1: AIAdapter の拡張

`packages/adapters/ai/src/adapter.ts` は今プロンプト文字列しか受け取らない。

```typescript
export interface CompletionAttachment {
  kind: 'document' | 'image'
  /** 'pdf' | 'xlsx' | 'png' … プロバイダの列挙に合わせてアダプタが写す */
  format: string
  /** プロバイダに渡す名前。材料の出所が分かる程度でよい */
  name: string
  bytes: Uint8Array
}

export interface CompleteOptions {
  // 既存のフィールドはそのまま
  attachments?: CompletionAttachment[]
}

/** 原本を渡せないプロバイダでは null（getEmbeddingInfo() と同じ形） */
export interface DocumentInfo {
  documentFormats: string[]
  imageFormats: string[]
  maxImageBytes: number
}
```

`AIAdapter` に `getDocumentInfo(): DocumentInfo | null` を足す。

| アダプタ | `getDocumentInfo()`                                                                 |
| -------- | ----------------------------------------------------------------------------------- |
| bedrock  | `csv/doc/docx/html/md/pdf/txt/xls/xlsx` + `gif/jpeg/png/webp`、`maxImageBytes: 5MB` |
| openai   | **null**（MVP では原本を渡さない）                                                  |
| ollama   | **null**                                                                            |
| noop     | **null**                                                                            |

**プロバイダ名でアプリ層を分岐させない**（ADR-005）。`null` の環境では表とテキストに抄録が
付き、PDF には付かない — 機能の有無ではなく**対応形式の差**として扱う。

### 5.1 エラーの分類

超過と未対応形式は**恒久**、スロットルは**一時**であり、アプリ層がこれを判別できないと
「一時的な失敗を対象外として記録する」事故が起きる（ADR-053 決定 3.4）。アダプタが分類して
投げる。

```typescript
export class AiInputRejectedError extends Error {
  /** 超過エラーが返した実トークン数（`prompt is too long: N > M`） */
  readonly actualTokens?: number
  readonly reason: 'too-long' | 'unsupported-format'
}
```

スロットル・5xx はそのまま throw し、呼び出し側が指数バックオフで再試行する。

## 6. Step 2: shared — 環境変数・ランタイム設定・定数

### 6.1 環境変数（ADR-053 決定 10）

```typescript
// packages/shared/src/env.ts
AI_SUMMARY_MODEL: z.preprocess(emptyAsUndefined, z.string().optional())
```

**モデルの指定が、そのまま有効・無効のスイッチである。** 未設定なら何も書かず、費用も
生じない。**未設定に戻しても既に生成された抄録は消さない。**

**フラグとモデルを分けない。** 2 つは 1 つの判断 —「この配備が抄録にいくら払うか」— であり、
分けると「有効なのにモデル未選択」という、どこかで辻褄を合わせなければならない状態が生まれる。

**そしてモデルの選択は無料の設定ではない。** Sonnet 4.6 と Haiku 4.5 で 3 倍、Nova とは 9 倍
違う。決定 10 が on/off を env に置いた理由（コストを負担するのは配備する側であり、設定する
主体と一致しない）は、**モデルにそのまま当てはまる**。

**allowlist の外のモデルは、既定に差し替えずに拒否する。** 既定とは
`AI_COMPLETION_MODELS` の先頭でしかなく、そこに不適切なモデルが来たときに起きることは
ADR-053 付録 18 が測っている — **出来の悪い抄録ではなく、捏造した抄録が出る。**

### 6.2 ランタイム設定

```typescript
// packages/api/src/services/system-setting.ts
export const AI_SUMMARY_LOCALE_KEY = 'ai-summary-locale'
[AI_SUMMARY_LOCALE_KEY]: { schema: z.enum(['ja', 'en']), default: 'ja' },
```

言語の選択はコストに効かないので、サイト管理者の裁量でよい。**モデルが設定されていない
サイトでは設定 UI に出さない**（§10.3）。非対称は説明が付く — **言語はただ、モデルは金**。

> **worker がランタイム設定を読むのは、これが最初である。** `SystemSettingService` は今 API
> 側だけが使っている。worker は既に `@kukan/api/services/*` を import しているので構造上の
> 無理はないが、先例になる変更として記録しておく。短 TTL キャッシュ付きなので、設定変更は
> TTL 内に伝播する。

## 7. Step 3: Summarize — 処理の実体

`apps/worker/src/pipeline/steps/summarize.ts` に `summarizeResource()` を置き、パイプラインの
ステップとバックフィルのジョブが共有する。

### 7.1 判定の順序

```
AI_SUMMARY_MODEL が未設定              → 何もしない（記録もしない）
getCompletionInfo() が null            → skipReason: 'provider-unavailable'
パッケージが active でない             → skipReason: 'not-public'
summary_meta.hidden                    → skipReason: 'hidden'
summary_meta.source === 'human'        → 何もしない（人手の文を上書きしない）
版 / genKey を比較                     → §4.2 の表のとおり
標準の拒否が同じ版・同じ生成条件で     → 何もしない
材料を組み立てる（形式・上限・成果物）→ 取れなければ skipReason
─────────────────────────────────────
LLM 呼び出し → 書き込み
```

モデルが未設定のときに何も書かないのは、**後から設定したときに再処理で
作れる**ためである（ADR-053 決定 10）。

**材料の判定は種類ごとに、それを書いたステップに問う。** 成果物の出どころが違うためである。

| 材料の種類           | 読むもの              | 健全性を問うステップ |
| -------------------- | --------------------- | -------------------- |
| 表（CSV / TSV）      | スキーマ + サンプル行 | Interpret            |
| アーカイブ（ZIP）    | マニフェスト          | Interpret            |
| 文書（ODT / RTF 等） | 抽出テキスト          | **Index**            |
| テキスト             | 本体オブジェクト      | **どちらも不要**     |

一括で Interpret に問うと 2 つ壊れる。**Index が失敗した実行で、文書が前の版の抽出テキスト
で説明される**（成果物は行に残っている）。そして**解釈が失敗しただけのテキストファイルが
材料なしになる** — 本体は確定した bytes で、どのステップにも依存しない（ADR-046）。

**サンプル行は表の材料ではなく、その補強である。** プレビューが無い CSV でクエリ経路は
拒否を返すが、それはリソースについての事実であって読み出しの失敗ではない。スキーマまで
道連れにしてはならず、呼び出し元に例外を投げてもならない — 提案フローはリソース全体を
メタデータだけに落とし、パイプラインはジョブごと落ちてキューが同じパッケージを再試行し
続ける。

### 7.2 守ること（ADR-053 決定 4.2）

- **DB トランザクションを LLM 呼び出しをまたいで開かない。** claim を取る → コミットする →
  LLM を呼ぶ → 結果を書く。worker の接続プールは `WORKER_DB_POOL_MAX` = 3 しかない
- **可視性タイムアウトを最悪レイテンシ + バックオフより長く取る。** 短いと再配信され、
  **同じ生成に二重に課金される**。現行値を実装時に確認し、必要なら上げる
- **429 には指数バックオフ。** バックフィルでは必ず当たる
- ベストエフォート。**失敗はステップの失敗として記録し、パイプラインを落とさない**

### 7.3 「材料が空」の実値

| 材料           | 空とみなす条件                                  |
| -------------- | ----------------------------------------------- |
| 表             | `schema.columns.length === 0`（スキーマが無い） |
| テキスト・文書 | 空白を除いて `SUMMARY_MIN_MATERIAL_CHARS` 未満  |
| ZIP            | ファイル一覧が 0 件                             |
| 画像           | 空にならない（原本がある）                      |

評価（§14）で調整する。**この値は「理由付きで表示されているリソースが多いか」という観測点
にもなる**（ADR-053 決定 5）。

### 7.4 再利用の判定はステップ自身が行う

パイプラインは Interpret / Index を `derivativesReused` でまとめてスキップするが、
**Summarize はこれに乗らない**。自前のハッシュで判断する。

これにより、**機能を有効にしたあとの通常のパイプライン実行がそのままバックフィルになる** —
内容が変わっていないリソースでも、抄録が無ければ生成される。

## 8. Step 4: 材料の組み立てとプロンプト

### 8.1 材料の組み立ては `suggest/` から切り出す

材料の組み立ては今 [metadata-suggest-service.ts](../../../packages/api/src/services/metadata-suggest-service.ts)
の private メソッドに閉じている。`packages/api/src/services/suggest/materials.ts` に
`collectResourceMaterial()` として切り出し、worker から呼べるようにする。

**挙動不変のリファクタとして独立したコミットにする。** `readSampleRows` /
`readTextHead` / `readArtifactTextHead` / `readZipFileList` をそのまま移す。

### 8.2 プロンプト

`packages/api/src/services/suggest/summary-prompt.ts`（新規）。ADR-040 の
`buildResourceSystemPrompt` には手を入れない。

- **`GROUNDING_RULES` は既存を共有する**（固有名詞は材料か既存メタデータに根拠を持つ）
- **長さは字数ではなく文数で指示し、理由を添える。** 「3〜4 文」「検索用のベクトルに載せる
  予算があるため」。Phase B では字数指示が 6 件中 5 件で超過し、文数は 6/6 守られ、目的を
  添えると平均 353 字 → 295 字に縮んだ
- **材料を超えた言明を禁じる。** とくにサンプル 5 行から導かれる期間・件数・最大最小
- **専門用語・行政用語には利用者が使う日常語を括弧で併記させる**
- **`datasetContext` の役割を指定する** — 文脈と固有名詞の根拠に使い、メタデータの言い換えに
  終始しない
- **ロケール別の追補ブロックを持つ。** 共通部は英語で書き、`ja` / `en` それぞれの言語事情
  （日常語の併記の書き方など）を追補する。**追補を変えたら `SUMMARY_GENERATION_VERSION` を上げる**

出力は強制 JSON。

```typescript
{ summary: string, groundedInMaterial: boolean }
```

`groundedInMaterial` は**記録と計測にのみ使う**。Phase A でスキャン PDF を小型モデルに渡した
とき、読めていないのに「読めない」とは言わなかった — **このフラグは捏造を捕まえられない**
（ADR-053 決定 5）。経路の切り替えには使わない。

## 9. Step 5: 埋め込みへの投入

### 9.1 組み立て順（ADR-053 決定 8）

[embed-package.ts](../../../apps/worker/src/embed/embed-package.ts) の
`buildEmbeddingText` を差し替える。**既存の要素は落とさない。**

| 順  | 内容                                |
| --- | ----------------------------------- |
| 1   | title / notes / tags / セクション名 |
| 2   | **抄録の連結（1 本 200〜300 字）**  |
| 3   | リソース名                          |
| 4   | リソースの description              |

- `EmbedSource.resources` に `summary` を足し、クエリで `resource.summary` と
  `resource.summaryMeta` を選ぶ
- **`hidden` の抄録は入れない。** 行を読んだあとで TypeScript 側で落とす（WHERE は要らない）
- **打ち切りは文単位。** 現在の `slice(0, MAX_EMBED_TEXT_LENGTH)` は文の途中で切る。抄録は
  「。」で完結している（実測 18/18）ので、末尾の文を丸ごと落とす

### 9.2 依存の鎖

```
リソースの中身が変わる → 抄録が再生成される → 埋め込みテキストが変わる → 再埋め込み
```

増分側は Summarize が抄録を書いたときに `enqueueEmbeds`（デバウンス経由）を呼ぶ。
バックフィル側は §11 のチェーンが終端で 1 回だけ投げる。

**機能を有効にした時点で全パッケージの埋め込みハッシュが変わる。** 無効のサイトでは何も
変わらない。

### 9.3 キーワード索引にも入れる（ADR-053 決定 8.1）

抄録は**ベクトルだけでなくリソース文書にも**入れる。決定 3.2 が日常語を括弧で併記させるので、
その語彙は語の一致で引ける — 人の書いた説明が両方を綴ることは稀で、抄録が無ければ存在しない。

| 変更箇所                 | 内容                                                |
| ------------------------ | --------------------------------------------------- |
| `ResourceDoc`            | `summary?: string` を足す                           |
| OpenSearch マッピング    | `kuromoji_analyzer` のテキスト項目として追加        |
| リソースの検索フィールド | `['name^3', 'description^2', 'section', 'summary']` |
| `resourceDocColumns`     | `publicSummary`（非表示なら null になる射影）を選ぶ |

**重みは name と description の下に置く。** 生成された文が人の書いたものを上回ってはならない。

#### 書き込む経路が無いことが要点

**Summarize は Index の後に走る。** Index が書いた文書は抄録を持たないリソースを記述して
おり、その後に戻ってくるものが無い — つまり黙っていれば抄録は**永久に索引へ入らない**。

3 つの経路で `sync-resource-doc` ジョブを投入する。

| 経路                   | 投入する位置                      |
| ---------------------- | --------------------------------- |
| パイプラインのステップ | 埋め込みの enqueue と同じ場所     |
| バックフィルの走査     | 1 件ごと（ベクトルは終端で 1 回） |
| 編集者の上書き・非表示 | `PUT /resources/:id/summary`      |

**直接書かずにジョブにするのは、再試行の持ち主を決めるためである。** 文書を古くする書き込みと
再試行できる主体が一致しない — Summarize は Index の後に走るベストエフォートのステップなので、
索引が一時的に落ちれば失敗が記録されて実行は完了し、**二度と問い直されない**。編集の経路も
同じで、同じ要求を送り直しても何も変わらないため再実行の引き金が無い。

キューに載せれば再試行はキューが持つ。この鎖の他のすべての再試行が既にいる場所であり、
**索引の瞬断でパイプラインの実行を失敗させずに済む**（例外を再送出する案の欠点）。

**結果によらず投入する。** 文書は行についての言明なので、動いていなくても言い直すのが正しく、
書いた直後に同期が失敗すると次の実行では `unchanged` になって二度と直らない。

**非表示のときに特に効く。** 公開射影は非表示の抄録を文書から落とすので、落とさない文書は
**誰かが取り下げた文章が検索に答え続ける**ことになる。

## 10. Step 6: API と Web

### 10.1 公開 API（`/api/v1` のみ）

リソースの表現に抄録を足す。**CKAN 互換ルート（`ckan-compat.ts`）には出さない。**

```jsonc
"summary": {
  "text": "…",           // hidden / 未生成なら null
  "source": "ai",
  "version": 3,
  "material": "text-head",
  "generatedAt": "2026-09-13T…",
  "skipReason": null      // 生成しなかった理由
}
```

`publicSummary()` 1 箇所で組み立てる（§4.1）。

### 10.2 編集者の操作

`PATCH /api/v1/resource/:id/summary`

- **上書き**: 本文を書き換え、`source: 'human'` にする。以後 AI は上書きしない
- **非表示**: `hidden: true`。表示も埋め込みへの投入も生成も止まる
- 権限はリソースの編集権限と同じ

### 10.3 Web

- **リソース詳細ページ（SSR）**に抄録。**読む前に AI 生成と分かる見出しを付ける**

  画面上の呼称は「**AI による説明**」とする。「抄録」は ADR・仕様・型が使う正確な語だが
  司書の語彙であり、カタログの読者に負わせるものではない。「説明」はどれだけを圧縮したかを
  何も主張しない点でも都合がよい — 多くは一部から書かれ、それは下の行が述べる。

  見出しはバッジとして本文の**上**に置く。後ろの脚注は、既に疑っていた読者にしか見つから
  ない。

- **どれだけ読んだかを本文の下に書く**（`material` と `coverage` から文言を選ぶ）

  > 列の構成と、全 163 行のうち先頭 5 行を読みました。この説明は、このファイルの v3 から
  > AI が生成しました（2026/09/13）

  **版はリソースの版であってプロンプトの版ではない。** 読者に見えるのは前者だけである。

- **版が古くなったら、そう言う**。版番号だけでは、履歴を開いて比べた読者にしか分からない

  > ※ このファイルは現在 v5 です。説明は更新されていません。

- **免責を最後に置く**。断り書きの仕事はさせない — 何から作られ、どの版かは上の行が述べる

  > ※ 内容の正確性・最新性を保証するものではありません。正式な内容は原本のファイルを
  > ご確認ください。

- **生成しなかった理由**を `skipReason` ごとの文言で表示する

  > このファイルはサイズ上限を超えるため、説明を生成していません

  **「使えない」と「使わない」を分ける** — `provider-unavailable` と `disabled` は別の文言に
  し、`suggest/availability.ts` の語彙に揃える

- **ダッシュボードのリソース編集**に上書き・非表示
- **人手の説明が既にあるリソースでは AI 文を主役にしない**（`description` の下に置く）
- **管理画面の設定**に生成言語（モデルが設定されているときだけ表示）。変更時は
  「既存の抄録は全件生成するまで元の言語のままです」を添える。env の値は site ルートの
  capability（`suggest` の availability と同じ形）で web に渡す

## 11. Step 7: バックフィルと管理画面

### 11.1 ジョブ種別

```typescript
// packages/shared/src/pipeline-types.ts
export const SUMMARIZE_ALL_JOB_TYPE = 'summarize-all' as const
export const SUMMARIZE_PACKAGE_JOB_TYPE = 'summarize-package' as const
```

| ジョブ              | payload                          | すること                                                                                     |
| ------------------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| `summarize-all`     | `{ refresh }`                    | `active` かつ非公開でないパッケージごとに `summarize-package` を撒く                         |
| `summarize-package` | `{ packageId, after?, refresh }` | 次の **1 件**を処理し、`after` を進めて自分を再投入。尽きたら `embed-package` を投げて終わる |

**1 ジョブ 1 完了にする。** 100 件のパッケージを 1 ジョブで回すと 20 分走って可視性
タイムアウトで再配信され、**すべての完了に二重に課金される**。

**`after` は `resource.id` の昇順カーソル。** 済みの印をどこにも持たないので、途中で死んだ
鎖はボタンを押し直せば再開する。抄録が既に材料を説明しているリソースは材料の読み出しだけで
完了せず、それが**鎖を何度でも安全に始められる**理由でもある。

**埋め込みは最後に 1 回だけ投げる。** デバウンスは先頭エッジなので、リソースごとに投げると
100 件のうち最初の 1 件でパッケージのベクトルが確定してしまう。

**他の実行が掴んでいるリソースは飛ばさず待つ。** 掴んでいる実行がステップまで到達すれば
自分で抄録を書くが、Fetch が失敗すれば到達しない。飛ばすと、誰かが頼んだ生成から静かに
落ちる。

- リソース単位の claim（ADR-044）はパイプラインと同じく取る
- ハッシュ一致はスキップされるので、**途中で落ちてもボタンを押し直せば続きから**
- パッケージ間は並列、パッケージ内は直列 — プロバイダのレート制限にも優しい

### 11.2 管理画面

`/dashboard/admin/site`（サイト管理）に **「AI による説明の生成」** のカードを置く。
生成に使うモデルを選ぶ「生成AI利用モデル」の直下で、そのモデルの料金で出した概算を読む
ことになる。検索インデックスの操作群とは別 — 作り直すのは索引ではなく、AI が書いた説明
そのものだから。インデックス管理の「埋め込みベクトルの再生成」は**今のまま無料の操作
として残す** — そこに抄録生成を混ぜると、埋め込みモデルを替えただけで全件に LLM 課金が
走る。

カードの見出しは「一括生成」とする。リソースは登録時に Summarize ステップで自動的に
説明が付くので、ここは通常経路ではない — 設定を入れる前からあるリソースと、書き直しが
要るものだけを相手にする保守の操作である。

**操作は 2 つある。金額が違う理由も違うので、分けて出す。**

| 操作               | 対象                                                 | ジョブ                             |
| ------------------ | ---------------------------------------------------- | ---------------------------------- |
| **不足分を生成**   | 抄録がまだ無いリソース                               | `summarize-all { refresh: false }` |
| **すべて作り直す** | それに加えて、別のモデル・生成版・言語で書かれたもの | `summarize-all { refresh: true }`  |

**生成版を上げるとカタログ全体が一度に古くなる。それを請求書で知る人がいてはならない。**
だから見積もりは操作ごとに別々に出し、**それぞれのボタンのすぐ上に置く**。

```
GET /api/v1/admin/summary-estimate
→ {
    model, locale,
    fill:    { resources, estimatedInputTokens: { low, high }, estimatedOutputTokens, estimatedCostUsd },
    refresh: { …同じ形… },
    skipped: { tooLarge, unsupportedFormat, noMaterial },
  }
```

**入力トークンは幅で出す。** ここから見えない唯一の入力が PDF のページ数であり、PDF の
トークンはページ数に従うためである。下限は抽出テキスト、上限はページ上限。

**金額も出す**（ドル、モデルの記録済みレート）。出力トークンも含める — 小さなファイルの
カタログでは**出力が請求の 3 分の 1** を占めるので、入力だけの提示は大きく過小になる。
レートは `global.*` と `jp.*` を区別する（後者は地理限定で +10%）。

**見積もりの母集団は走査と一致させる。** 走査は `hash` に一致する active な版を必要とする
ので、版を持たないリソースは**決して訪れない**。数えれば、誰もしない作業に金額を付けること
になる。同じく、**成果物がその都度確認される** — スキーマの無い表、抽出テキストの無い
文書は数えない。記録済みのスキップ理由ではなく成果物を見るのは、解釈をやり直して
スキーマが生まれても版は上がらないためで、版に固定すると**発生する作業を隠す**。過小に
見せるのは、過大より悪い方向である。

**対象外の件数も、抄録の無いリソースの中で数える。** ボタンの下に並ぶ行なので「押しても
対象にならない件数」と読まれる。カタログ全体で数えると、**既に抄録があるファイル**まで
「サイズ上限超過」に入る — テキスト層から抄録を得たサイズ超過の PDF がまさにそれだった。

モデルが未設定のサイトではカードを出さない。**使用モデルと生成言語をカードに読み取り専用で
表示する**（埋め込みの再生成カードが `embedModel` を出しているのと同じ形）。完了後に埋め込みも
作り直されることをボタンの説明に書く。

**見積もりが出るまでボタンは押せない。** 件数が 0 のときも押せない — 何も起きない操作を
押せる状態にしておく意味がない。

## 13. テスト戦略

| 種別     | 対象                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| ユニット | 材料の振り分け（PDF の 1 ページあたり文字数、上限、形式）、ハッシュの入力、スキップ理由の決定 |
| ユニット | 埋め込みテキストの組み立て順と**文単位の打ち切り**、`hidden` の除外                           |
| ユニット | アダプタ: Converse の入力形状を pin、エラーの分類（恒久 / 一時）                              |
| ユニット | 公開射影が `hash` / `rejectedTokens` を返さないこと                                           |
| 統合     | Summarize ステップ（生成 / スキップ / 失敗しても後続に影響しない）、`source: 'human'` の保護  |
| 統合     | バックフィルのチェーン（再投入、終端での embed 投入、途中再開）                               |

## 14. 判定基準（ADR-053）

実装後に測り、**数値は ADR-053 に記録する**（正本は ADR 側）。

1. **材料を超えた言明が 0 件**（期間・件数・固有名詞）
2. **図表主体の PDF が読めているか**
3. **自己申告フラグと人の判断の一致率**
4. 上限超過・材料が空のリソースに**生成を試みていない**こと
5. **抄録として成立していること**（文が途中で切れていない）
6. **検索の質が悪化していないこと** — `pnpm eval:search` の前後比較

抄録を入れる前の基準線（2026-09-12 実測、キーワードのみ → ハイブリッドの overall nDCG）:

| 環境     | 基準線        | 埋め込み        | 読み方                     |
| -------- | ------------- | --------------- | -------------------------- |
| ローカル | **38% → 82%** | Titan v2        | **悪化していないかの確認** |
| demo     | **29% → 87%** | Cohere embed-v4 | **本番構成での効果**（正） |

**モデルが違うので絶対値は比較しない。** 各環境の前後差だけを見る。あわせて**出力に日常語が
含まれているか**を計測項目として持つ。

## 15. スコープ外（後続）

ADR-053「MVP の後に検討すること」のうち、本フェーズで着手しないもの。

- **リソース単位のベクトル** — MVP の直後に入れる。連結の打ち切り（10% のパッケージ）と、
  異質な表を 1 本のベクトルに平均する問題は、粒度でしか解けない
- **Office 形式の抽出テキスト** — PDF と同じ比較をしてから判断する
- **PDF のページ抜粋**、**Office の事前推定**、**Excel の格子**
- **PNG の巨大な画像**（ディスク経由への切り替え）
- **専用キューと専用ポーラー** — 着手の判断材料は「アップロードの処理が目に見えて遅く
  なったか」
- **モデルの振り分け**（テキスト主体は小型、スキャンは上位）
- **有効・無効の二層化**（env を天井とし、ランタイム設定から下げる方向にだけ動かす）
- **多言語の抄録**（ja / en を両方作る）— コストが倍になる
- **値の生成**（型・主キー・ヘッダー行・シート構造）— 仕様書 §14.1-4 の枠
