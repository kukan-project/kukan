# ADR-034: メタデータのベクトル検索（セマンティック検索・AI 向けデータセット発見）

## ステータス

**承認（Accepted）** — 全決定を実装済み（Phase 5a）。埋め込みモデルの選定と類似度
しきい値はゴールデンセット評価で確定した（後述「評価結果」、2026-07-07）。

## コンテキスト

現行の検索は BM25（OpenSearch）/ ILIKE + 全文検索（PostgreSQL）によるキーワードマッチであり
（ADR-009）、次の限界がある:

- **語彙の不一致**: 「ごみ収集」で検索しても「廃棄物」と書かれたデータセットがヒットしない。
- **自然文クエリに弱い**: 「子育て支援の施設はどこ?」のような文での検索に対応できない。
- **AI エージェントからの発見**: ADR-032 の MCP 基盤により AI エージェントがカタログを探索する
  ユースケースが確立した。エージェントは自然文でデータセットを探すため、キーワード一致のみでは
  「探索 → スキーマ → クエリ」ループの入口（発見）がボトルネックになる。

そこで、メタデータ（package の title / notes / tags に所属リソースの name / description を
連結したテキスト）を埋め込みベクトル化し、BM25 と融合したハイブリッド検索を導入する。
リソースメタデータを含めるのは、BM25 側が既に kukan-resources インデックスを検索対象に
含めており（ADR-025）、ベクトル側だけ対象を狭めると「リソース名でしかヒットしない
データセット」がセマンティック検索で見つからない非対称が生じるため。主目的は**検索・発見の精度向上**であり、**AI/MCP エージェント向けの
データセット発見**を一級のターゲットとする。

対象範囲は段階的に広げる:

- **v1: package 単位のベクトルのみ**（1 package = 1 ベクトル、数千〜数万件規模。ベクタ数が
  小さく、厳密検索でも成立する）。リソースメタデータは package のテキストに連結して含め、
  リソース単位の独立ベクトルは作らない
- **後続フェーズ候補: リソース抽出コンテンツ**（kukan-contents 相当）。ただし**テキスト系
  （PDF 等）に限定**する。CSV/TSV 等のテーブルデータは埋め込みによる意味検索が効きにくく、
  こちらは ADR-032 のスキーマ + クエリ経路が担当領域である。

### 前提知識: 埋め込みモデルと生成 AI モデルは独立

埋め込みベクトルは**埋め込みモデルごとに固有**であり、モデル間に互換性はない（次元数も
ベクトル空間の幾何も異なる。共通で使える標準ベクトル形式は存在しない）。一方、検索結果を
消費する**生成 AI（Claude/GPT/ローカル LLM 等）側に埋め込みモデルを合わせる必要はない** —
生成 AI が読むのは検索が返すテキストであり、ベクトルには触れない。したがって:

- クエリと文書は**同一の埋め込みモデル**で埋め込む必要がある（環境内で閉じていればよい）。
- 埋め込みモデルの変更 = **全件再埋め込み + インデックス再構築**。
- MCP を叩いてくる生成 AI が何であるかは埋め込みモデル選定に影響しない。

## 検討した選択肢

### 1. 埋め込みモデルの配備方式

#### 方式 U: 統一セルフホスト

オープンウェイトモデル（bge-m3 等）を両環境でセルフホストする。オンプレは Ollama、
AWS は ECS Fargate 上の Ollama / HuggingFace TEI コンテナ。埋め込みモデルは小さく
（bge-m3 で 568M パラメータ）CPU 推論で実用になるため技術的には成立する。

- 利点: 全環境で検索品質が同一、評価が 1 モデル分で済む、モデル廃止リスクなし。
- 欠点: **AWS に常時起動の推論サービス（Fargate タスク）が 1 つ増える**。

#### 方式 D: 環境別分離（採用）

| 環境          | 埋め込み手段                                                  | 備考                             |
| ------------- | ------------------------------------------------------------- | -------------------------------- |
| AWS           | Bedrock（Titan Embeddings v2 / Cohere embed-multilingual v3） | 従量課金・インフラ追加ゼロ       |
| オンプレ/閉域 | Ollama（bge-m3 第一候補 / multilingual-e5 次点）              | ローカル完結・外部送信なし       |
| AI なし環境   | NoOp → **ベクトル検索無効・BM25 のみに degrade**              | 検索機能自体は全環境で動作を維持 |

- 利点: **新規インフラ（Fargate タスク）を増やさない**。既存 AIAdapter の各実装
  （bedrock / ollama / noop）の延長で実現できる。
- 欠点: 環境間でベクトルの互換性がなく、評価が 2 モデル分になる。
  - ただし**インデックス互換性は実運用で不要**（各デプロイは自前の検索バックエンドに
    インデックスを持ち、環境間でベクトルを持ち運ぶ場面がない）。
  - 評価コストはゴールデンセット評価の**スクリプト化**で 2 モデル目以降を安価にする。

> **決定**: 「新規 Fargate タスクを増やさない」を制約とし、**方式 D（分離）を採用**。
> 方式 U は将来 AWS 側で精度・コスト要件が変わった場合の乗り換え先として温存する。

#### モデル選定の基準（優先順）

1. **ハードフィルタ**: デプロイ環境で動くこと（Bedrock 提供 / Ollama 実行可）、
   日本語 retrieval 性能（JMTEB の Retrieval スコアで比較。平均スコアではなく検索タスクを見る）、
   商用利用可能なライセンス（ローカルモデル。e5 系・bge-m3 は MIT）。
2. **比較基準**: 入力トークン上限（PDF コンテンツを見据えると 8192 対応が有利）、
   次元数（インデックスサイズ・メモリに直結。1024 以下が無難。Matryoshka 対応なら縮小余地）、
   コスト（クエリ側は検索毎に発生）、クエリ埋め込みレイテンシ、
   非対称検索プレフィックス（e5 の `query:`/`passage:` 等）、提供の継続性（deprecation = 全件再埋め込み）。
3. **最終判断はゴールデンセット評価**（後述）で行い、ベンチマークは絞り込みにのみ使う。

### 2. ベクトルの保存先

#### 方式 B: バックエンド別（各検索バックエンドが自前でベクトルを持つ）

| バックエンド | 方式               | 備考                                                                              |
| ------------ | ------------------ | --------------------------------------------------------------------------------- |
| OpenSearch   | k-NN（knn_vector） | HNSW はオフヒープメモリを消費。小規模インスタンスでは注意。                       |
| PostgreSQL   | pgvector           | Aurora Serverless v2 対応済。オンプレは Docker イメージを pgvector 同梱版へ変更。 |

- 利点: 検索と融合が各バックエンド内で完結する（OpenSearch は search pipeline まで使える）。
- 欠点: ベクトル実装が 2 つ必要。OpenSearch k-NN（HNSW）はオフヒープメモリを消費し、
  過去の小インスタンスでのヒープ枯渇障害の教訓と相性が悪い。OpenSearch のインデックス
  再構築時にはベクトルの再投入も必要になる。

#### 方式 P: pgvector 一本化（採用）

ベクトルは全環境で PostgreSQL（pgvector）に置き、OpenSearch は BM25 + ファセット専任の
ままとする。ベクトルは package テーブルの列として Drizzle スキーマで管理し、モデル名・
次元数・コンテンツハッシュを同じ行に持つ。

- 利点:
  - **ベクトル検索の実装が全環境共通**になる。環境差はキーワード側（既存のまま）に限定され、
    実装・テスト量がほぼ半減する。
  - OpenSearch のメモリサイジングを変更しなくてよい（k-NN のオフヒープ消費を回避）。
  - 埋め込み更新がメタデータと**同一 DB でトランザクショナル**（OpenSearch への二重書き込み
    不要）。OpenSearch の rebuild でもベクトルは失われない。
  - drizzle-orm は pgvector の `vector` 型をサポートしており、マイグレーションは既存フローのまま。
- 欠点 / トレードオフ:
  - AWS 構成ではハイブリッド融合がストア横断になり、**RRF をサービス層で実装**する
    （OpenSearch の search pipeline は使わない）。ただし PG フォールバック環境はどのみち
    手動 RRF なので、融合ロジックを全環境共通にできる利点と裏表。
  - 検索 1 回あたり OpenSearch + PG の 2 クエリになる（並列実行し、支配項はクエリ埋め込みの
    レイテンシなので体感影響は軽微）。
  - ベクトル検索側にも可視性フィルタが必要（PG アダプターの `SearchFilters` WHERE 実装を流用）。
  - 検索負荷が本体 DB に乗る。v1 のメタデータ規模では誤差だが、後続フェーズの PDF コンテンツ
    埋め込み（ベクトル数が 2〜3 桁増え HNSW が必要になる）まで PG に載せるかはその時点で再評価する。

> **決定**: PG/Aurora 側にリソース余裕があること、実装の共通化メリットが大きいことから
> **方式 P（pgvector 一本化）を採用**。v1 の対象（package メタデータ）はベクタ数が小さいため
> HNSW インデックスは張らず、フィルタ + 全件距離計算（exact search）で運用する。

### 3. 埋め込み生成のタイミング

- **文書側**: メタデータ CUD 時の BM25 インデックス更新（API ルート・同期）はそのまま維持し、
  **埋め込み生成は QueueAdapter 経由の非同期ジョブ**とする（結果整合）。埋め込みは外部 API
  呼び出しを含みレイテンシ・失敗モードがあるため、リクエストパスに含めない。
  再埋め込みスキップのため**原文のコンテンツハッシュ**を保存する。
- **クエリ側**: 検索リクエスト毎に埋め込みが必要（+100〜300ms）。**lru-cache でクエリ埋め込みを
  キャッシュ**する（ADR-004 のユーティリティをそのまま使用）。

### 4. BM25 との融合（ハイブリッド検索）

- BM25（OpenSearch / PG 全文検索）とベクトル（pgvector）をそれぞれ top-k 取得し、
  **サービス層で RRF（Reciprocal Rank Fusion）により融合**する。方式 P によりストアを
  跨ぐため OpenSearch の search pipeline は使わず、融合ロジックは全環境共通とする。
- **完全一致クエリ（データセット名・組織名そのまま）の精度をベクトルが下げ得る**のが既知の
  失敗パターン。融合重みはゴールデンセットで検証し、劣化を検知できるようにする。
- ベクトル検索は top-k しか返さないため、`total` の意味・ページネーション・ファセット集計
  （OpenSearch/BM25 側の集計に残す）・ハイライト非対応（ベクトルヒットに `<mark>` は
  付かない）の扱いを実装時に整理する。

### 5. 評価: ゴールデンセット

クエリと正解データセットのペア（20〜50 問）を人手で作成し、Recall@10 / nDCG@10 を
スクリプトで計測する。クエリ種別として**類義語・自然文・完全一致を必ず混在**させる
（完全一致は劣化検知用）。用途はモデル比較・融合重みチューニング・回帰テストの 3 つ。
分離配備（方式 D）のため AWS 用・オンプレ用の 2 モデルに対して同一セットで実行する。

## 決定

1. **目的**: メタデータのセマンティック検索と AI/MCP エージェント向けデータセット発見。
   v1 は package 単位のベクトルのみ（title / notes / tags + 所属リソースの name / description
   を連結）。リソース CUD 時も親 package を再埋め込みする。
2. **配備は方式 D（環境別分離）**: AWS = Bedrock、オンプレ = Ollama、NoOp 環境 =
   ベクトル検索無効（BM25 のみへ degrade）。新規 Fargate タスクは増やさない。
3. **ベクトルストアは方式 P（pgvector 一本化）**: 全環境で PostgreSQL に保存し、OpenSearch は
   BM25 + ファセット専任を維持する。ハイブリッド融合はサービス層の RRF で全環境共通とする。
4. **ベクトル検索はオプショナル機能**として設計する。SearchAdapter に capability を持たせ、
   埋め込み不可の環境でも検索機能は BM25 のみで完全動作する。
5. **クエリと文書は同一埋め込みモデル**。ベクトルと併せて**モデル名 + 次元数を記録**し、
   不一致を検出可能にする。モデル変更時は全件再埋め込み（rebuild フロー拡張）。
6. **文書側埋め込みは非同期**（QueueAdapter 経由・結果整合）、**クエリ側埋め込みは
   lru-cache でキャッシュ**する。
7. **AIAdapter の `embed()` を拡張**する: バッチ埋め込み、クエリ用/文書用の区別
   （モデル別プレフィックス吸収）、モデル名・次元数の公開。アダプターは既存 4 つの
   範囲内であり ADR-005 に抵触しない。
8. **導入前にゴールデンセット評価を実施**し、モデル選定と融合重みを数値で決定する。
   完全一致クエリの劣化がないことを出荷条件とする。
9. **リソースコンテンツ（PDF 等テキスト系）の埋め込みは後続フェーズ**とし、本 ADR の
   範囲外とする。テーブルデータ（CSV/TSV）は埋め込み対象にしない（ADR-032 の担当領域）。

## 影響

- **packages/adapters/ai**: `embed()` の拡張（バッチ・用途区別・モデルメタデータ公開）。
  bedrock / ollama 実装に埋め込みモデル設定を追加。noop は「埋め込み不可」を明示。
- **packages/adapters/search**: ベクトル検索は PostgreSQL 側（pgvector）にのみ実装し、
  可視性フィルタは既存の `SearchFilters` WHERE 実装を流用。OpenSearch 実装は BM25 +
  ファセット専任のまま変更最小。ハイブリッド融合（RRF）はアダプターの上のサービス層に
  置き、全環境共通とする。capability（ベクトル検索可否）を公開。
- **DB / インフラ**: package テーブルにベクトル列とモデル名・次元数・コンテンツハッシュを
  追加（Drizzle マイグレーション）。オンプレ PostgreSQL イメージを pgvector 同梱版
  （`pgvector/pgvector:pg16`）へ変更（compose.yml）。alpine → Debian ベースへの変更で
  collation 実装が変わるため、既存環境は pg_dump/restore または REINDEX が必要
  （開発環境はボリューム再作成で可）。Aurora は拡張有効化のみ（`CREATE EXTENSION vector`）。
  OpenSearch のサイジング変更は不要。
- **worker / queue**: 埋め込み生成ジョブの追加（メタデータ CUD → キュー投入 → 埋め込み →
  ベクトル列更新）。バルク再埋め込み（rebuild）コマンドの拡張。
- **compose.yml（Ollama）**: Ollama をオプショナルサービス（profiles）として追加し、
  **開発とオンプレで同一構成**にする（dev/prod パリティ。埋め込みは CPU 推論で足りるため
  GPU 設定は不要）。閉域網では `ollama pull` が使えないため、モデルは**オフライン配送**が
  必要（モデル格納ボリュームの事前配布、またはモデル同梱イメージの配布）。
- **セキュリティ/データ主権**: AWS 環境ではメタデータが Bedrock へ送信される（AWS 内で完結）。
  閉域網では Ollama によりローカル完結し、外部送信は発生しない。
- **運用**: 埋め込みモデルの変更手順（再埋め込み）とゴールデンセットの保守が新規の運用項目。

## 評価結果（2026-07-07）

ゴールデンセット（各環境39クエリ = exact / synonym / natural 各13問 + 正解なしクエリ
3問によるノイズ測定）で計測した Recall@10 / nDCG@10。数値は「キーワードのみ →
ハイブリッド」。ゴールデンセット自体はデプロイ固有データのためコミットしない
（`golden-queries.example.yaml` 参照）。

### オンプレ（ローカル実データ166件、bge-m3 @ 0.45）

| type             | R@10                  | nDCG          |
| ---------------- | --------------------- | ------------- |
| exact            | 100% → 100%（無退行） | 100% → 100%   |
| synonym          | 0% → 96%              | 0% → 79%      |
| natural          | 15% → 90%             | 15% → 66%     |
| **overall nDCG** |                       | **38% → 82%** |

### AWS（demo 全国自治体データ181件、モデル対決）

|                            | **Cohere Embed v4 @ 0.3（推奨）**                | Titan v2 @ 0.15（デフォルト） |
| -------------------------- | ------------------------------------------------ | ----------------------------- |
| synonym R@10               | **74%**                                          | 72%                           |
| natural R@10               | **71%**                                          | 66%                           |
| exact R@10                 | 85%（無退行）                                    | 85%                           |
| overall nDCG               | **75%**                                          | 70%                           |
| 正解なしクエリの擬似ヒット | 0〜1件                                           | 1件                           |
| 導入摩擦                   | Marketplace 購読（管理者 invoke 1回 + 伝播待ち） | なし（自動有効化）            |
| 価格 / 1M トークン         | $0.10                                            | $0.02                         |

- **類似度しきい値はモデルごとに分布が別物**で流用不可（bge-m3 の関連ペア 0.47〜0.62 に
  対し、Titan v2 は 0.05〜0.25、Cohere v4 は 0.15〜0.4 に相当質量が分布）。スイープ測定で
  「上限性能の 97〜99% を維持しつつ正解なしクエリが沈黙する」点を採用: bge-m3 = 0.45、
  Titan v2 = 0.15、Cohere v4 = 0.3。実測値は AI アダプターが内部保持し
  （`EmbeddingInfo.recommendedMinSimilarity`）、env で上書き可能。
- **結論**: オンプレ = bge-m3（確定）。AWS デフォルト = Titan v2（摩擦ゼロ優先）、
  品質優先なら Cohere Embed v4 をオプトイン推奨（特に質問文 +5〜12pt）。
  モデル変更時はゴールデンセットで要再測定。
- Cohere v3・multilingual-e5 は入力トークン制限（512）が連結テキスト（〜8K 相当）に
  不足するため対決前に除外。Cohere v4（128K）でこの制約は解消された。

## 残課題（未解決事項）

1. ~~**モデルの最終選定**~~ → **解決済み**（上記「評価結果」。オンプレ = bge-m3、
   AWS = Titan v2 デフォルト / Cohere Embed v4 推奨オプトイン）。
2. ~~**ゴールデンセットの作成**~~ → **解決済み**（ローカル39問 + demo 39問。
   デプロイごとに作成・非コミットの運用で確立）。
3. **融合パラメータの確定**: しきい値は解決済み（評価結果参照）。RRF の k 値（=60）と
   レッグ重み付けは既定のまま — 質問文でキーワードレッグがノイズになる場合の
   重み付き RRF は将来のチューニング候補。
4. **UI の扱い**: ベクトルヒットのハイライト非対応をどう見せるか、`matchSource` の拡張。
5. **PDF コンテンツ埋め込み**（後続フェーズ）: チャンク設計・スケール・コスト試算。
   ベクトル数が 2〜3 桁増えるため、pgvector（HNSW 追加）か OpenSearch k-NN への分離かを再評価。
6. **関連データセット推薦**: 同じベクトルを流用した「似ているデータセット」表示
   （オフライン類似度計算のみで実現可。検索統合とは独立に着手可能）。
7. **閉域網へのモデル配送手順**: ボリューム事前配布かモデル同梱イメージかの確定と、
   導入手順書への落とし込み。
8. **管理画面からのハイブリッド検索停止**: 品質劣化・コスト異常時に sysadmin が UI から
   ベクトル検索を一括停止できる運用スイッチ。プロバイダ障害はクエリ埋め込みの
   タイムアウト + BM25 フォールバックで自動 degrade するため対象外（env による
   停止スイッチは検討の上不採用とした）。
