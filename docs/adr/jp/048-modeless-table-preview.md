# ADR-048: テーブルプレビューの一枚化 — 閲覧は Range 配信、対話はクライアント計算

## ステータス

**提案（Proposed）** — スパイク実測済み（2026-08-31、判定: **条件付き Go**。
実測結果の節を参照）。承認をもって ADR-016 を置換する（DuckDB-WASM の採用自体は
維持し、「解析モード」トグルと全量バッファ登録の 2 決定を覆す）。

## コンテキスト

### 1. 「解析モード」は実装都合の区分で、ユーザーの概念モデルに対応していない

テーブルプレビューには現在 2 つの表がある:

- **デフォルト**: hyparquet による軽量表示。フッターと表示中ページの row group だけを
  Range Read で取得する（ADR-017 のプロキシ `/preview` が 206 を返す）
- **解析モード**（Switch トグル、ADR-016）: DuckDB-WASM がプレビュー Parquet
  **全量**を `fetch` + `registerFileBuffer` で取り込み、ソート・フィルター・検索を
  クライアント側 SQL で行う

トグルは「重い WASM ロードを opt-in にする」という実装都合であり、ユーザーから見れば
「同じ表が 2 つあり、片方でしか並べ替えができない」状態である。さらに ADR-032 の
`/query` は Data API として常時公開されているため、「解析できるかどうか」をトグルが
仕切っているわけでもない。表にサーバークエリ由来の対話機能を足す構想を取ると、
トグルの説明は完全につかなくなる。

### 2. 前提の整理 — この判断で動かないもの

検討の過程で確認した、本 ADR が**変更しない**事実:

- **プレビュー Parquet は廃止できない。** プレビュー配信用のファイルではなく、
  正本の解釈結果（ADR-046）であり、ADR-032 サンドボックスの入力であり、
  主キー事前チェック（ADR-043 ii-b）の読み先でもある。WASM の有無と独立に残る
- **`/query` はトグルと無関係に匿名公開されている。** 可視性チェックと SQL 長上限、
  セマフォ（同時 1・キュー 8・15 秒）だけで守られており、これで足りている。
  WASM は攻撃面を減らす防波堤ではなく、**善意の対話バーストをサーバーから逸らす
  QoS 弁**である
- **`QUERY_MAX_CONCURRENT = 1` はオフロード前提で成立している。** 直列化は最小
  デプロイ（web コンテナ 512 MB）のメモリ予算から来ており、それが許容できたのは
  人間の対話トラフィックが設計上 `/query` に到達しないから。表 UI をサーバークエリに
  載せ替えるなら、この前提ごと作り直しになる
- **DuckLake は対話計算の基盤ではない。** ADR-043 の lake 読みは 1 スロット共有の
  低頻度操作向けであり、プレビュー・explorer の代替エンジンにはならない

### 3. Parquet 上限を引き上げる可能性と、全量登録の寿命

プレビュー Parquet の生成上限（現在 100 MB）を将来数百 MB へ引き上げる可能性がある。
全量バッファ登録はこの世界で線形に劣化する — が、これは ADR-016 の**実装上の選択**
（「httpfs の追加 WASM ロードを回避」）であって WASM の制約ではない。DuckDB-WASM には
拡張なしでファイルを URL として登録し Range Read でアクセスする組み込み機構
（`registerFileURL` + HTTP プロトコル）があり、受け側の `/preview` は hyparquet の
ために既に 206 + `Content-Range` を実装済みである。Parquet は列指向なので、
URL 登録ならソート 1 回の転送は理論上「対象列のチャンク + 表示ページ」に収まる。

## 検討した選択肢

### A) WASM を排除し、表の対話をサーバー `/query` に載せる

- 良い点: エンジンがサーバー側 1 つに見える。結果行しか転送しないため低速回線に強い
- 問題点:
  - サーバー側エンジンは MCP / Data API のためにどのみち残るが、対話バーストを
    受けるには実体化キャッシュ・同時実行引き上げ・善意ユーザー向け流量制御の
    3 点が前提になる
  - 最小構成（512 MB）では同時実行をほぼ上げられず（256 MB × 2 で容器いっぱい）、
    閉域網・小規模オンプレというデプロイターゲットと最も相性が悪い
  - フィルター適用中のページ送りはすべてクエリになるため、per-query 全量実体化の
    現行方式のままでは成立しない

### B) WASM に一本化する（hyparquet 廃止）

- 問題点:
  - リソースページを開いただけの閲覧者全員がエンジン + Parquet の取得を払う。
    最高頻度・最低関与の経路に最大コストを置く形で、上限引き上げと真っ向から衝突
  - サーバー側エンジンは残るため「エンジンを 1 つにする」効果もない
- 不成立

### C) トグルを廃し、対話の瞬間にクライアント計算へ暗黙切替する — 採用（提案）

- 未操作の閲覧は hyparquet の Range 配信のまま（スロット消費ゼロ）
- ソート・フィルターに初めて触れた時点で DuckDB-WASM を裏で起動し、以降その表は
  クライアント側 SQL で動く。エンジンの切替は実装詳細に沈む
- 登録を `registerFileURL`（Range 読み）に変えることで、上限引き上げ後も対話
  コストが全量転送に戻らない
- 現状のコスト構造では新たな崖を作らない: いまの明示トグルも ON の瞬間に同額
  （エンジン + 全量）を払っており、暗黙切替が変えるのは金額ではなく枠付けだけ。
  URL 登録はむしろ金額を下げる

## 決定（提案）

**テーブルプレビューを一枚の表に統一し、「閲覧 = Range 配信 / 対話 = クライアント計算」
で分離する。**

1. **「解析モード」トグルを廃止する。** `sessionStorage` + `useSyncExternalStore` の
   モード管理も除去する
2. **未操作の表示経路を `/query` に通さない。** 初期表示・スキーマ・素のページ送りは
   hyparquet の Range Read のまま。未操作の閲覧者は何人来ても DuckDB スロットにも
   実体化にも触れない — この不変条件が最小構成の成立条件である
3. **初回の対話で DuckDB-WASM を暗黙起動する。** 起動中も表は hyparquet 表示のまま
   操作を受け付け、クリック済みの操作意図はキューして準備完了時に適用する。
   スピナーで表を塞がない
4. **ファイル登録は `registerFileURL`（HTTP、Range 読み）を基本とする。** 小さい
   ファイルは全量バッファの方が往復が少なく速い可能性があるため、サイズしきい値
   （初期表示の HEAD で全長は既知）による使い分けをスパイクの実測で決める
5. **サーバー側は現状維持を境界として明記する。** `/query`・サンドボックス・
   `QUERY_MAX_CONCURRENT` は触らない。プレビュー Parquet の生成・保持も不変。
   過去版への SQL（特権エクスポート → サンドボックス方式）は別 ADR とする

## スパイク（承認の前提となる検証）

タイムボックス 2 日。計測ハーネスは `spike/adr-048/` に置く（合成データ・バンドル・
結果 JSON は生成物としてリポジトリに含めない）。実測結果は後述。

### 検証項目

| #   | 問い                                 | 既知の背景                                                                                                                                     |
| --- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Q1  | `/preview` の Range 実装と噛み合うか | 地雷 2 つ確認済み: suffix 形式 `bytes=-N` を 416 で弾く / 終端なし `bytes=N-` を 1 MB に切り詰める（要求全長を期待するクライアントだと壊れる） |
| Q2  | HEAD 応答で Range 対応と判定されるか | DuckDB-WASM は `Accept-Ranges` / `Content-Length` を見て判定し、不可なら**黙って全量ダウンロードにフォールバック**する                         |
| Q3  | ソート 1 回の実転送量                | 理論上は対象列の圧縮チャンクのみ。`ROW_GROUP_SIZE 5000` では row group 数が多く、フッターメタデータ自体の取得コストも計測対象                  |
| Q4  | 操作の繰り返しで再フェッチが起きるか | バッファキャッシュ挙動は未知。ソート後のページ送り連打が毎回列全読みなら実用にならない                                                         |
| Q5  | ブラウザのヒープピーク               | ソート中間結果。デスクトップで 1.5 GB 以内を目安                                                                                               |
| Q6  | row group 粒度の影響                 | 5000 行刻みと 10 万行刻みの 2 変種で Q3/Q4 を比較。大ファイル時代に Interpret 側の `ROW_GROUP_SIZE`（ADR-014）を見直すかの材料                 |

### 手順

1. **準備**: Interpret と同条件（zstd、row group 5000）で 300〜500 MB の合成 Parquet を
   生成。row group 10 万行の変種も作る
2. **フェーズ 1 — 互換性の切り分け**: suffix 対応・要求全長を返す理想的な Range
   サーバーで素の挙動を計測（Q2〜Q5）。全量フォールバックの検出を最優先する
3. **フェーズ 2 — 実プロキシ**: `/api/v1/resources/:id/preview` に向けて同計測。
   Q1 の地雷が踏まれるかを確認し、必要なサーバー修正を列挙する（修正は本実装
   スコープ）
4. **計測シナリオ**（各変種）: メタデータ読み / `COUNT(*)` / 数値列ソート + 先頭
   ページ / 文字列列ソート / 等値・ILIKE フィルター / ソート結果のページ送り 5 回 /
   同一ソート再実行。各シナリオでリクエスト数・総転送バイト・所要時間・ヒープ
   ピークを記録

### 判定基準

- **Go**: 全量フォールバックなし、ソート 1 回の転送 ≦ 対象列圧縮サイズの 1.5 倍程度、
  ページ送りが列の再読みにならない、一般的な回線（50 Mbps 想定）で操作 3〜5 秒以内、
  ヒープ 1.5 GB 以内 → 本 ADR を承認へ更新し実装に進む
- **条件付き Go**: 転送量は良いが再フェッチが多い → サイズしきい値ゲート（小は
  バッファ全量、大のみ URL）で方針維持
- **No-go**: 全量フォールバックが回避不能、またはページ送りが実用速度に達しない →
  本 ADR を取り下げ、選択肢 A（サーバークエリ + 実体化キャッシュ + 同時実行
  引き上げ）を別 ADR で設計し直す

### 実測結果（2026-08-31）

環境: ループバック（RTT ≈ 0。実網では往復回数 × RTT が加算される）、headless
Chromium、duckdb-wasm 1.33.1-dev57.0、合成 Parquet 6,000,000 行 × 7 列
（zstd、rg5000 = 406 MB / rg100k = 396 MB、ソート対象 `num_a` 列の圧縮サイズ
18.8 MB → 基準値 1.5 倍 = 28 MB）。

**前提の実測（Q2・全量フォールバック）:** 現行と同じ登録（設定なし）では、理想
サーバー相手でも**初回クエリで常に全量ダウンロード**になる（1 リクエスト・387 MB）。
Range モードは `db.open()` の filesystem 設定
（`reliableHeadRequests: true` 等）**と** `registerFileURL` の `directIO: true` を
両方明示して初めて活性化した。なお `allowFullHTTPReads: false`（厳格モード）は
このビルドではリクエストを発行せずに open 自体が失敗する — dev リリース由来の
挙動依存があり、実装時にバージョン更新と回帰確認が要る。

**フェーズ 1（理想 Range サーバー、Range モード）:**

| シナリオ                                     | rg5000（転送 / リクエスト数） | rg100k（転送 / リクエスト数） | 判定基準                 |
| -------------------------------------------- | ----------------------------- | ----------------------------- | ------------------------ |
| メタデータ読み                               | 0.91 MB / 4                   | 0.06 MB / 4                   | ✓ 劇的に安い             |
| COUNT(\*)                                    | 0 MB / 2                      | 0 MB / 2                      | ✓                        |
| 等値フィルター                               | 0.41 MB / 11                  | 21.3 MB / 13                  | ✓                        |
| ILIKE フィルター                             | 0.28 MB / 7                   | 9.9 MB / 13                   | ✓                        |
| `SELECT *` ソート（Top-N 直行）              | 162 MB / 571                  | 372 MB / 44                   | ✗ ほぼ全量               |
| `SELECT *` ページ送り（1 回毎）              | 158〜277 MB / 2128〜5604      | 374〜378 MB / 37〜484         | ✗ 毎回再転送             |
| **ソート列のみ投影（2 フェーズ読みの前段）** | **4.5 MB / 238**              | **18.0 MB / 61**              | **✓ 基準 28 MB 以内**    |
| 同・再実行（キャッシュ検証）                 | 7.4 MB / 385                  | 18.6 MB / 63                  | △ クエリ間キャッシュなし |

- **`SELECT *` の Top-N ソートをそのまま投げると成立しない**（遅延実体化が効かず
  ほぼ全量転送、しかもページ送りごとに再転送）。**ソート列だけを投影して行位置を
  確定させ、表示行を別クエリで取る「2 フェーズ読み」なら基準内**に収まる。
  min/max 統計の枝刈りは細かい row group ほど効く（rg5000 で 4.5 MB まで低減）
- **クエリ間キャッシュは存在しない**（Q4）。操作 1 回あたり列サイズ相当
  （5〜19 MB）の再転送が発生する。50 Mbps 想定で 1〜3 秒 — 実用域だが低速回線では
  つらい。実網ではリクエスト数 × RTT も加算され、rg5000 の数百〜数千リクエストは
  破綻要因（RTT 30 ms なら 238 req ≈ 7 秒）。row group は数万行への引き上げが
  必要（Q6。rg100k は 61 req で済むが転送は 18 MB に増える — 中間値の探索は実装時）
- メモリ（Q5）: Chromium 全プロセス RSS は Range モード 0.6〜1.9 GB、全量バッファ
  1.2〜1.6 GB で同水準。基準 1.5 GB の縁にあり、モバイルはしきい値ゲートが前提

**フェーズ 2（`/preview` 忠実エミュレーション、Q1）:** Range モードは**全滅**
（全クエリが `No magic bytes found at end of file` で失敗）。原因は確定していて、
duckdb-wasm はサイズ調査に `HEAD` + `Range: bytes=0-` を投げ、応答の
`Content-Length` をファイル全長と解釈するが、現行実装は終端なし Range を 1 MB に
切り詰めるため**ファイルサイズが 1 MB と誤認され、フッターを誤った位置に読みに
行く**。suffix 形式（`bytes=-N`）は duckdb-wasm は使用せず、416 地雷は踏まれ
なかった（仕様堅牢化としての修正は望ましい）。全量バッファモードは素通しで動く。

### 判定: 条件付き Go

「転送量は基準内・再フェッチは残る」— 判定基準の条件付き Go に該当する。
承認・実装の前提条件:

1. **`/preview` の Range 実装修正（必須）**: 終端なし Range に全長を応答する
   （少なくとも HEAD。1 MB 切り詰めは GET のページング用途に限定する）。
   suffix 形式対応もあわせて行う
2. **explorer のクエリ規約として 2 フェーズ読みを実装する**: `SELECT *` +
   ORDER BY を直行させない。ソート列投影で行位置を確定 → 表示行を取得
3. **サイズしきい値ゲート**: 小ファイルは従来どおり全量バッファ（現行実装と
   同挙動）。しきい値はネットワーク実測を踏まえ実装時に決める
4. **`ROW_GROUP_SIZE` の見直し**（ADR-014 詳細補足）: 5000 行は枝刈り最良だが
   リクエスト数が実網で破綻する。数万行域で転送量と往復数のバランスを取る
5. **duckdb-wasm のバージョン更新と回帰確認**: Range モードの活性化条件が
   dev ビルドの実装詳細に依存している

**実機確認事項（本実装時）**: 実スタックの `/preview` は HEAD 応答に
`Content-Length` を返すか（本スパイクはエミュレーションで、Hono + ストリーム
応答の実挙動は未確認）。hyparquet が本番で動作している事実と突き合わせる。

## 影響

- `apps/web`: トグル UI と `sessionStorage` モード管理の除去。hyparquet 側の表と
  data-explorer 側の表は現在別コンポーネントのため、「同じ表がデータソースだけ
  替わる」形への統一が必要（行番号・主キーマーク・数値右寄せ等の表示仕様を両経路で
  揃える）
- `packages/api`: `/preview` の Range 実装修正が**必須**と実測で確定（終端なし
  Range への全長応答・suffix 形式対応。詳細は実測結果の節）
- `apps/worker`: `ROW_GROUP_SIZE` の見直しが**必要**と実測で確定（5000 行のままでは
  実網のリクエスト数が破綻。ADR-014 の詳細補足で対応可能な範囲）
- プレビュー Parquet の生成上限の引き上げは、本スパイクの実測を材料に別途判断する

## 残課題

1. 過去版への SQL 実行（特権エクスポート → サンドボックス方式）は別 ADR で決める。
   エクスポートした版 Parquet を `/preview` 相当で配信すれば、本 ADR の一枚の表で
   過去版も探索できる（合流点になる）
2. 対話開始前のエンジン先読み（表ヘッダへの pointerenter 等をシグナルにした
   ウォームアップ）は本実装時に検討する。ページ表示と同時の先読みは全閲覧者に
   コストを課すため行わない
