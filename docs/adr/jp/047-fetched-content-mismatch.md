# ADR-047: 取得内容が宣言と食い違うとき、正本を差し替えない

## ステータス

**提案（Proposed）**

外部 URL から取得したものが、そのリソースが宣言している種類と明らかに食い違うとき、
**版を作らずに失敗させる**。正本は登録された URL の側にあるので、バイトを手元に
残す必要はない。あわせて、**成功した取得も含めてリダイレクトの発生を記録し、可視化する** —
転送が起きている時点で登録 URL は既に古く、直すべき対象だからである。

ADR-043（版）・ADR-046（正本と解釈の分離）・ADR-044（巻き戻し）にまたがる判断のため、
実装より先に決めておく。

## コンテキスト

### 1. サイト閉鎖時の一括転送は、例外ではなく通常運用

公開データの配信元が改組・統合・閉鎖されるとき、旧ドメインの全 URL を新サイトのトップへ
一括で転送する設定は珍しくない。`/data/foo.csv` も `/data/bar.csv` も、区別なく
`https://newsite.example.jp/` に飛ぶ。

このとき起きているのは「リソースの移転」ではなく「**リソースの消失**」である。転送先には
そのデータが無い。にもかかわらず HTTP としては 200 が返る。

### 2. いまの経路は、これを最後まで通す

1. ヘルスチェックが HEAD を送り、リダイレクトを追従して 200 を得る
2. **200 なので `health_status = 'ok'` を記録する**（`head-request.ts`）
3. 転送先の `etag` が保存済みのものと異なるため `changed = true`
4. `changed` がパイプラインを起動する（`check-batch.ts`）
5. Fetch は `content-length` しか見ないので、HTML をそのままダウンロードする
6. ハッシュが違うので**新しい版が作られる**。版は ADR-043 により恒久的に残る
7. ライブポインタが移動し、Index が HTML 本文を検索インデックスへ投入する

結果、CSV として登録されたリソースが HTML のトップページになる。検索結果にはその HTML の
文言が出る。プレビューとスキーマは失われるか、意味を成さないものになる。

### 3. ヘルスチェックが引き金を引いている

3 と 4 に注意したい。ヘルスチェックは「リンクは健全」と記録したうえで、**その健全さの根拠
（検証子が変わった）をもって再取得を発注している**。監視のつもりの機構が、破壊の起点になる。

検証子を返さない配信元でも、一定間隔の全件再取得があるため、遅れて同じ経路を通る。

### 4. 設計はこの失敗形を知っているが、気づく仕組みがない

パイプラインには既にこう書かれている（ADR-044 §4）。

> _for a resource reverted because its URL served the wrong thing that run publishes it again_

「URL が違うものを出した」という概念があり、巻き戻しの導線もある。しかも単純な再試行が
**間違ったものを再公開してしまう**ことまで警告している。

**事後の取り消しはあるが、事前の検知がない。** これが埋めるべき穴である。

### 5. ADR-046 との緊張

ADR-046 は「正本を先に確定し、その解釈は後」と決めた。バイトだけで版が決まるので、失敗した
ステップを後から同じ結果でやり直せる。

ところが「このバイトは明らかにこのリソースではない」という判断は**解釈の側にある**。
判定できる頃には版が既に存在している。この ADR は、その順序を崩さずに正本を守る方法を決める。

## 判定に使える信号

| 信号                                                  | 強さ                   | 費用         | 誤検知                                                                                                 |
| ----------------------------------------------------- | ---------------------- | ------------ | ------------------------------------------------------------------------------------------------------ |
| **本文の先頭が `<!DOCTYPE html` / `<html`**           | 最強                   | ほぼ無料     | ほぼ無い。CSV / JSON / XML / GeoJSON を宣言したリソースが HTML なら、まず間違い                        |
| **リダイレクト先のパス崩壊**（`/data/foo.csv` → `/`） | 強                     | 無料         | 少ない。`/opendata/2026/foo.csv` への移動とは明確に区別できる                                          |
| Content-Type と宣言フォーマットの不一致               | 中                     | 無料         | **多い**。自治体サーバーは CSV を `text/html` や `application/octet-stream` で返すことが常態化している |
| **多数のリソースが同一 URL へ収束**                   | 最強（人間が使う判断） | 要バッチ集計 | ほぼ無い。50 件が同じ先に飛べば個別の移転ではない                                                      |
| サイズ・ハッシュの変化                                | 使えない               | —            | 通常の更新と区別できない                                                                               |

**Content-Type 単独を門にしてはならない。** 正常な配信元を大量に止める。

先頭バイトの検査とリダイレクトの形、この 2 つで実用上の大半を捕まえられる。収束の検出は
per-fetch では成立しないので、別立てにする。

## 検討した選択肢

### A) 現状維持

取得したものをそのまま正本にし、おかしくなったら巻き戻す（ADR-044 §4）。

事後の巻き戻しは、**気づいた場合にしか働かない**。データカタログにおける「静かに内容が
入れ替わる」は、気づかれないまま利用者に配られる種類の壊れ方である。版は恒久的に残るため、
巻き戻しても記録は残り続ける。採らない。

### B) Fetch で止める（Version の前）

宣言フォーマットと先頭バイトが矛盾したら、版を作る前に `error` で終える。

**外部 URL のリソースは、正本が向こう側にある。** KUKAN が持つのは複製であって唯一の写しでは
ないので、失敗した取得のバイトを手元に残す理由が無い。中身を見たければ URL を開けばよい。
この点はアップロードのリソースと決定的に違い、そちらは KUKAN の複製が唯一の正本なので同じ
議論は成立しない — ただしアップロードはリダイレクトしないので、この ADR の対象外である。

`error` は既存のリソース一覧・パイプライン一覧にそのまま現れる。**運用者が何もしなくても
目に入る。**

### C) 版は作るが、ライブポインタを動かさない

バイトは記録して失わない。リソースは従来の内容を保ったまま、「取得したものが宣言と食い違う」
状態を提示して運用者に判断させる。

**発見されない。** 保留された版は、それを探しに行った人にしか見えない。カタログの表示上は
何も起きていないのと区別がつかず、内容は古いまま配られ続ける。「静かに壊れる」を避けるための
決定が、別の「静かに滞留する」を生む。

保留状態を表す新しい値、それを一覧に出す導線、保留版を live に昇格させる操作 — **B が必要と
しないものを 3 つ必要とする。**

そして採用の意味づけが歪む。配信元が本当に HTML に切り替えたのなら、正しい対処は
「HTML の版を CSV というラベルのまま採用する」ではなく、**宣言フォーマットを直すこと**である。
C の昇格操作は、誤ったラベルを温存したまま前に進む道を用意してしまう。

### D) ヘルスチェックだけ直す

`ok` を返さないようにすれば再取得が起動しない、という発想。

半分しか効かない。検証子を持たない配信元は定期的な全件再取得の対象で、そちらの経路が残る。
利用者が手動で再処理を押す経路も残る。ヘルスチェックの修正は必要だが、それだけでは足りない。

## 決定

### 1. 取得内容が宣言と食い違うとき、版を作らずに失敗させる（選択肢 B）

live 側は従来の内容を保ち、パイプラインは `error` で終える。理由は「取得したものが宣言と
食い違う」と、実際に何が来たか（最終 URL、判別した種類）を添える。

**バイトは残さない。** 正本は登録された URL の側にあり、必要なら取りに行ける。恒久的に残る
版（ADR-043）を、採用しないと決めたものに対して作る理由が無い。

配信元が本当に別の種類に切り替えていた場合の対処は、**宣言フォーマットを直して再処理する**。
これは既存の操作だけで済み、新しい導線を要さない。そしてラベルと中身を一致させるという、
本来行うべき修正でもある。

**この判断はリダイレクトを伴った取得に限らない。** 配信元が同じ URL で中身を差し替えた場合も
同じ扱いでよい。リダイレクトは最も起きやすい経路だが、原因ではない。

アップロードのリソースは対象外である。リダイレクトしないうえ、KUKAN の複製が唯一の正本なので
「取りに行ける」が成り立たない。

### 2. 判定は先頭バイトとリダイレクトの形で行う

- 宣言フォーマットがテキスト系（CSV / TSV / JSON / GeoJSON / XML / MD）で、取得した先頭が
  HTML と判別できるとき
- 取得がリダイレクトを伴い、最終 URL がファイル名を失っている（パスが `/` に崩れている）とき

Content-Type は**判定の補助**に留め、単独では門にしない。

判定は Fetch が持つ。版の作成条件（ADR-046 決定 3）には影響させない — バイトと解釈条件が
同じなら版は増えない、という規則はそのまま。

ADR-046 の「層 1 は解釈を含まない」とは衝突しない。ここで決めているのは**何を版に書くか**では
なく**そもそも版を作ってよいか**であり、判定結果は版のどこにも記録されない。層 1 は解釈を
含まないままである。

### 3. ヘルスチェックは最終 URL を記録し、`ok` を細分する

いまは最終 URL をどこにも残していない。**運用者が「実際にどこへ飛んでいるか」を見る手段が
無い。** リダイレクトを追従した場合の最終 URL を記録する。

200 で着地しても、上記の食い違いが見えるときは `ok` と区別する状態を持つ。`error` ではない —
正当な移転の可能性があり、人の判断が要る。

**`changed` による再取得の発注は、この状態では行わない。** 引き金を止める。

### 4. リダイレクトは、成功していても記録して見せる

**転送が起きているなら、登録 URL は既に古い。** とくに 301 / 308 は「恒久的に移動したので
参照を更新せよ」という意味そのものである。いまのカタログはそれを黙って肩代わりし、
毎回の取得で余分な往復を払い続け、しかも運用者にその事実を伝えていない。

失敗していなくても記録する。取得ごとに残すのは次の 3 つ。

- **最終 URL**（決定 3 と同じもの）
- **ホップ数**
- **恒久（301 / 308）を含むか**

そのうえで「URL が転送されているリソース」の一覧を持つ。恒久を含むものを上位に置くが、
**一時的な転送も隠さない**。302 を恒久移動に使う配信元は珍しくなく、状態コードだけでは
選別できない。`http` → `https` や apex → `www` のような、修正が一意に決まるものも同じ一覧に出る。

**URL の自動書き換えは行わない。** 利用者が入力したメタデータをカタログが黙って書き換える
のは、この ADR が防ごうとしている「静かに置き換わる」と同じ種類の失敗である。提示するに留め、
適用は人が決める。

### 5. 追従回数は減らさない

「転送されているなら直すべき」から「追従をやめる」へは進まない。上限を下げても、動いていた
リソースが理由の説明なく失敗に変わるだけで、URL を直す動機にはならない。`http` → `https` →
`www` → 実パスのような正当な連鎖は 3 ホップを容易に超える。

**梃子は可視化の側にある。** 追従は続け、起きていることを見せる。

### 6. 収束の検出は後段に置く

「多数のリソースが同一 URL へ収束している」は最も確度の高い信号だが、1 件の取得からは
判定できない。最終 URL を記録したうえで、集計する仕組みを別に持つ。

この ADR では記録までを決め、検出の実装は残課題とする。

決定 4 と同じデータで足りる点に注意したい。**一括転送は「多数のリソースが同一の最終 URL に
集まる」、サイト移転は「同一ホストの別パスに集まる」**であり、どちらも最終 URL を記録して
（元ホスト → 先ホスト）で束ねれば同じ一覧から出てくる。別々の機構を作る必要はない。

## 影響

- **カタログの正本が、配信元の都合で静かに置き換わらなくなる。** これが主目的
- **失敗は既存の一覧にそのまま現れる。** 新しい状態も、新しい画面も要らない
- 誤判定の可能性がある。配信元が本当に別の種類に切り替えた場合、**宣言フォーマットを直して
  再処理する**という一手間がかかる。ラベルと中身を一致させる修正なので、手間としては正しい向き
- 取得したバイトは残らない。中身を確かめたい運用者は URL を開く。外部 URL のリソースに限った
  決定なので、これが成り立つ
- ヘルスチェックの状態が増えるため、DB の値域と UI の表示に変更が要る
- **リダイレクトの記録が全リソースに付く。** 最終 URL・ホップ数・恒久の有無で、1 リソース
  あたり数十バイト。取得のたびに更新されるので、書き込みは増えるが取得 1 回につき 1 行
- 転送されているリソースの一覧は、**運用者にとって新しい仕事**になる。放置しても壊れないが、
  溜まると意味を失う。既存のヘルスチェック結果の画面に同居させるのが自然
- 先頭バイトの検査は Fetch がストリームを流す途中で行えるので、追加の読み取りは発生しない

## 残課題

- **失敗理由の粒度**。`error` の文面に留めるのか、機械可読な理由コードを持つのか。
  一括転送の検出（下記）は、後者があると集計しやすい
- **収束の検出**。同一の最終 URL に何件が集まったら一括転送と見なすか。閾値は運用で決まる
- **URL 更新の提示のしかた**。一覧から一括で適用できるべきか、1 件ずつか。恒久（301 / 308）に
  限って一括を許す案はあるが、302 を恒久移動に使う配信元がある以上、状態コードだけを根拠に
  自動化するのは危うい
- **判定の対象フォーマット**。PDF や画像は先頭バイトで判別できるが、HTML に化けたときの
  実害はテキスト系ほど大きくない。どこまで広げるか
- **ZIP の中身**。ZIP を宣言したリソースが HTML を返す場合、マニフェスト生成が失敗するので
  既存の経路で検出される。改めて扱う必要があるか要確認
