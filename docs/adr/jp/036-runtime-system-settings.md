# ADR-036: DB バックエンドのランタイムシステム設定

## ステータス

**承認済み（Accepted）**

## コンテキスト

KUKAN の設定はこれまですべて環境変数（起動時固定）で、値を変えるには再デプロイが
必要だった。大半の設定はそれで正しい（インフラと不可分、変更頻度が低い）が、
**運用中に反復調整するタイプの設定**にはこの方式が合わない。

最初の具体例がベクトル検索の類似度下限（similarity floor、ADR-034）で、

- モデル・実データ依存のため、ゴールデンセット評価（`pnpm eval:search`）を
  回しながら反復的に調整する運用になる
- demo のようにデプロイ経路がリポジトリ外にある環境では、env 変更のたびの
  再デプロイで調整の回転が極端に遅くなる

一方、管理画面（sysadmin 専用）は既に存在するが、ランタイムに変更可能な設定を
保持する仕組み（設定テーブル・設定 API）はなかった。

## 決定

### `system_setting` テーブルによるランタイム設定基盤

汎用の key/value テーブル（`key` varchar UNIQUE + `value` jsonb）を新設し、
`SystemSettingService` 経由で読み書きする。

- 読み取りは **lru-cache（TTL 30秒）** 経由。書き込んだインスタンスは即時反映、
  他のインスタンス（ECS の複数タスク）は TTL 内に収束する
- 全設定はサービス内の**レジストリ**（キー + Zod スキーマ + 既定値）に宣言し、
  型付きの汎用 `getSetting` / `setSetting` でアクセスする。不正値・欠損は
  **既定値に退化**する（500 にしない）。設定の追加はレジストリへの1エントリで済む
- 変更は sysadmin 専用の**汎用 API** 経由でのみ行い、`audit_log` に記録する
  （entityType `system_setting`、`{ key, value, previous }` 形式）:
  - `GET /api/v1/admin/settings` — 全設定の現在値
  - `PUT /api/v1/admin/settings/:key` — レジストリのスキーマで検証して保存。
    **設定を追加しても API 変更は不要**（レジストリ1エントリ + 管理 UI のみ）
  - 例外は計算済みコンテキストを返す読み取り専用の
    `GET /api/v1/admin/settings/vector-search` のみ（env + AI アダプター +
    検索 capability の融合はレジストリからは導出できない）

### env とランタイム設定の使い分け

すべての設定をランタイム化するわけではない。基準は次のとおり。

| 設定の性質                                           | 置き場所                    |
| ---------------------------------------------------- | --------------------------- |
| インフラと不可分（接続先、IAM と連動、モデル選択等） | env / CDK（従来どおり）     |
| 運用中に反復調整し、失敗してもすぐ戻せる             | `system_setting` + 管理画面 |

env / コード側に基準値が**ある**設定は、「置き換える」のではなく
「**基準値の上に重ねる**」形にして優先順位の衝突を避ける（例: しきい値の
目盛りオフセット）。基準を持たない純粋なコンテンツ型の設定（例: 検索例クエリ）は、
ランタイム設定を唯一の置き場とする。将来の候補（`registrationEnabled` の DB 化等）も
同じテーブル・同じサービスに載せる。

## 適用例

最初の適用として、検索に関する3つの設定を管理画面
（`/dashboard/admin/site`）から変更可能にした。

### セマンティック検索のオン/オフ（`semantic-search-enabled`）

ハイブリッド検索のベクトル脚のグローバルキルスイッチ（既定 on）。埋め込み
プロバイダ障害時や品質検証時に、再デプロイなしでキーワード検索のみへ退避できる。
オフ時はクエリ埋め込みごとスキップするため、プロバイダ課金も発生しない。

### 検索例クエリ（`search-example-queries`）

検索ボックス下のクエリ例チップ。カタログの中身に合わせて運用中に育てる
コンテンツであり、ブランドアイデンティティよりお知らせに近い。これに伴い
`brandConfig.searchExampleQueries`（ADR-023）は**廃止**し、置き場を管理画面に
一本化した（二重管理を避ける。フォークは次回アップグレード時に brand 設定から
管理画面へ値を移す）。未設定・空リストはチップ非表示。

### しきい値の目盛り調整（`vector-similarity-notches`）

類似度下限を基準値の近傍で調整する。「重ねる」原則の具体化でもある。

- 保存するのは絶対値ではなく**基準値からの目盛りオフセット**（整数 ±4、
  1目盛り = 0.025）のみ。実効値はクエリ時に `基準値 + 目盛り × 0.025`
  （[0, 1] にクランプ）で計算する。基準値の解決順は従来どおり
  （env `SEARCH_VECTOR_MIN_SIMILARITY` > モデル実測推奨値 > 0.45）
- **モデル変更に対して安全**: しきい値はモデルごとに分布が別物（ADR-034:
  Titan v2 = 0.15 / Cohere v4 = 0.3 / bge-m3 = 0.45）で、絶対値を保存すると
  モデル切り替え後に誤適用される。「基準より1目盛り緩め」という相対指定は
  モデルが変わっても意味が保たれ、無効化ロジックが不要
- **可動域が構造的に制限される**: 自由入力だと 0.9（全滅）や 0（フィルタ無効）を
  設定できてしまうが、±4目盛り（±0.10）なら最悪でも「少し緩い / 厳しい」に
  収まる。各モデルの推奨値は「上限性能の 97〜99% を維持する点」（ADR-034）と
  して選ばれており、実運用の調整はその近傍で足りる
- 適用は `searchByVector` の per-call 引数（オフセット）で行い、アダプターは
  ステートレスのまま。目盛り 0（未設定）は従来と完全に同一の動作

なお**埋め込みモデルの選択は管理画面に載せない**。IAM の `bedrock:InvokeModel`
が設定済みモデルの ARN に限定されている（env と IAM の乖離防止のため意図的）、
Marketplace モデルは購読手順が必要、切り替えると全件再埋め込み完了まで
ベクトル検索が停止する — いずれも「インフラと不可分」側の設定であり、
管理画面はモデル情報（embeddingKey・基準値・出所）の表示のみ行う。

## 結果

- ランタイム設定の基盤（テーブル・サービス・監査）が整い、以降の設定追加は
  レジストリへの定義（キー + スキーマ + 既定値）の追加だけで済む
- sysadmin は類似度下限を再デプロイなしに ±0.10 の範囲で調整できる
  （反映は最大30秒）。本格チューニングは従来どおり `pnpm eval:search` で行い、
  UI は「評価で決めた値を即時反映する」役割に限定される
