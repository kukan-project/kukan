# ADR-069: 共有 OpenSearch ドメインのサイト間分離を FGAC で強制する

## ステータス

**提案（Proposed）** — 2026-10-21

AWS の共有 OpenSearch ドメイン（ADR-041）で FGAC（Fine-Grained Access Control）を有効にする。各サイトの
タスクロールに、自サイトのインデックス（`<prefix>-search*`）だけを許可する。マスターユーザーは
IAM ロールにし、ロールの割り当ては共有スタックが環境定義のサイト一覧から作る。Docker Compose
（開発・オンプレ・閉域網）には影響しない。

ADR-041 §トレードオフの「OpenSearch のサイト間分離は規約ベース」を、AWS では強制に変える
（ADR-041 の拡張）。

> **この ADR は Claude Code で設計会話をもとに起こした草案である。** 権限の正確な一覧と
> blue/green 更新の所要時間は、実装時に demo（マルチサイト）で確かめる。

## コンテキスト

### 1. 今の分離

タスクは自分のタスクロールで SigV4 署名し、ドメインポリシーはアカウントの署名付きプリンシパルだけを
通す。各サイトのタスクロールには、ドメイン全体への `es:ESHttp*` を付ける。署名のない
リクエスト（VPC の中からの SSRF を含む）は拒否される。

ただし、通ったリクエストはドメイン全体に届く。サイト A のタスクロールで、サイト B のインデックスを
読み書きできる。B の非公開・下書きのデータセットのメタデータや、抽出テキストも含まれる。サイト間の
分離は、インデックス名の接頭辞（`kukan-<env>-<site>`）という命名規約だけである。

### 2. 守るもの

- **乗っ取られたコンテナ**：サイト A のコンテナが乗っ取られた場合（RCE、ECS Exec など）、A のロールの
  認証情報でほかのサイトのインデックスに届く。
- **アプリの不具合**：インデックス名の接頭辞の取り違えやワイルドカードの検索で、ほかのサイトの文書に
  届く。
- **監査**：FGAC の監査ログで、誰がどのインデックスを触ったかが残せるようになる（有効にするかは別に
  決める）。

ADR-041 は「同一運用主体のサイト群のみ共用する」と割り切った。この前提なら、上積みは小さい。サイト A が
乗っ取られた時点で、同じ運用者のサイト B も実質的に危ないからである。運用主体の違うサイトを同じ
ドメインに載せるなら必須になる。

### 3. FGAC の性質

- 暗号化（保存時・ノード間）と HTTPS の強制が前提になる。今のドメインはどれも満たしている。
- 作成後のドメインでも有効にできる。**一度有効にすると無効に戻せない。** 有効にすると blue/green
  更新が走る。更新中もドメインは使える。
- 有効にした時点で、ロールの割り当て（OpenSearch のロール ← IAM ロールの ARN）が無い IAM
  プリンシパルは、署名していても 403 になる。
- ロールと割り当ては、セキュリティ API（`_plugins/_security/api/…`）で作る。CloudFormation の
  リソースは無い。

### 4. アプリが使う API

インデックスはすべて `<prefix>-search` の別名と、その実体（`<prefix>-search-<6 桁>-<ランダム>`）である。
アプリは次の API を使う。

- **インデックスへの操作**：検索・取得、書き込み、別名の付け替え、マッピングの追加、作成・削除。
- **複数インデックスにまたがる操作**：`_msearch`・`_mget`・`_bulk`。FGAC では対象のインデックスごとに
  権限を確かめる。
- **クラスタへの操作**：`_reindex`、タスクの取得・取り消し、`_cat/indices`。

## 検討した選択肢

### A) IAM のリソースのパスでインデックスを絞る — 不採用

ドメインポリシーやタスクロールのポリシーの resource に、`domain/<name>/<prefix>-search*` を書く方式である。
ただ、複数インデックスにまたがる API は、本文で対象を指定するので、パスで絞っても確実には効かない。
分離の手段にならない。

### B) 内部ユーザー（パスワード）で認証する — 不採用

マスターユーザーやサイトのユーザーを、OpenSearch 内部のユーザーで持つ方式である。パスワードの管理と
ローテーションが増えるうえ、§コンテキスト 1 の SigV4 と二重になる。

### C) ロールの割り当てを各サイトのスタックのカスタムリソースで作る — 不採用

サイトのスタックが、自分のタスクロールの ARN でロールと割り当てを作る方式である。サイトを足すと、
そのデプロイで割り当てができる。ただ、マスターとして署名する Lambda を共有スタックに置き、その
ServiceToken を SSM 経由でサイトに渡す必要があり、スタックをまたぐ部品が増える。

### D) ロールの割り当てを共有スタックが環境定義のサイト一覧から作る — 採用（提案）

タスクロールに決まった名前を付け（`resourceName` の規則で `kukan-<env>-<site>-web-task` など）、共有
スタックが環境定義の `sites[]` から ARN を組み立てて、全サイトのロールと割り当てを作る方式である。

- 部品は共有スタックのカスタムリソース 1 つで済む。
- 割り当ては、ロール本体より先に ARN の文字列として作れる。
- サイトの増減は共有スタックの更新になる。パイプラインは共有スタックを先に流すので、手順は増えない。

## 決定（提案）

### 1. FGAC を有効にする

- 共有ドメインで `fineGrainedAccessControl` を有効にする。
- 内部ユーザーのデータベースは使わない。
- 監査ログは今回は有効にしない（費用と保持を別に決める）。

### 2. マスターユーザー

- 共有スタックに、マスター用の IAM ロール（`kukan-<env>-search-admin`）を作る。
- このロールは、ロールと割り当てを作るカスタムリソースの Lambda の実行ロールにする。運用者が手で
  調べられるように、信頼ポリシーにはアカウントも入れる。自分の IAM ポリシーで `sts:AssumeRole` を
  許された人（AWS アカウントの管理者）が引き受けられる。こうした管理者はもともとドメインの設定を
  書き換えられるので、新しく広がる権限は小さい。KUKAN のタスクロールには引き受ける権限を持たせない。
- Lambda は VPC の中で動かし、OpenSearch の SG に通す。

### 3. サイトごとのロール

サイトごとに OpenSearch のロール `kukan-<env>-<site>` を 1 つ作る。

- **インデックスの権限**：`<prefix>-search*` に、読み書き・別名・マッピング・作成・削除。
- **クラスタの権限**：
  - `_msearch`・`_mget`・`_bulk`（クラスタでの許可と、インデックスごとの確認の両方が要る）
  - `_reindex`
  - タスクの取得・取り消し
  - `_cat/indices`

  正確な一覧は、実装時に demo で確かめて決める。タスクの取り消しはクラスタ単位なので、ほかのサイトの
  reindex を取り消せてしまう。これは受け入れる。読み書きには届かないからである。

### 4. ロールの割り当て

- web と worker のタスクロールに、決まった名前を付ける（`kukan-<env>-<site>-web-task` /
  `-worker-task`）。名前を付けるとロールが作り直されるので、最初のデプロイではタスク定義も更新される。
- 共有スタックのカスタムリソースが、`sites[]` から両方の ARN を組み立て、`kukan-<env>-<site>` に
  割り当てる。
- サイトを外したときは、そのロールと割り当ても消す。インデックス本体の扱いは、サイトの撤去手順に従う。
- シングルサイト（`KukanStack`）も同じ部品を使う。サイトは 1 つ、接頭辞は `kukan` である。
- FGAC を既存のドメインで有効にすると、AWS はドメインポリシーが通すプリンシパルを `default_role` に
  割り当てる。これが残ると分離が効かないので、カスタムリソースが毎回その割り当てを消す。
- 名前を付けた IAM ロールは、アカウント全体で一意である。そのため**環境名は AWS アカウントの中で一意に
  する**（リージョンが違っても同じ名前は使えない）。使われている名前でデプロイすると、ロールの作成で
  失敗して止まる。大文字と小文字だけが違う環境名は、synth で止める。

### 5. ドメインポリシー

アカウントの署名付きプリンシパル（`AccountRootPrincipal`）のままにする。FGAC はその内側で、インデックス
ごとの許可を決める。

### 6. 移行

- 共有スタックのデプロイで FGAC が有効になり、blue/green 更新が走る。割り当てを同じデプロイで作るので、
  名前の付いたタスクロールで動くタスクは、更新が終わった時点から通る。
- サイトのデプロイでタスクが入れ替わるまで、古いタスク（名前の無いロール）は 403 になり、公開側の
  検索は 503 になる。SigV4 署名への移行と同じ止まり方なので、2 つを**同じリリースに入れ、止まる時間を
  1 回にまとめる**。
- デプロイの後、各サイトで「コンテンツ再索引」を 1 回実行する。その間に失敗した本文の索引は、自動では
  追いつかないものがあるからである。
- 一度有効にすると戻せない。問題が起きたら、ロールの権限を広げて直す。
- ドメインの更新の後でデプロイが失敗すると、CloudFormation は FGAC を無効に戻そうとして失敗し、
  共有スタックが `UPDATE_ROLLBACK_FAILED` で止まる。ドメインを飛ばして巻き戻しを続ける手順を、
  デプロイの仕様書に書く。

## 影響

- **infra**：
  - 検索のコンストラクトに、FGAC とマスター用のロール、カスタムリソース（Lambda と、VPC・SG の設定）を
    足す。
  - web・worker のタスクロールに名前を付ける。
  - テストとスナップショットを更新する。
- **アプリ**：変更しない（署名は入っている）。
- **Docker Compose**：変更しない（security plugin は無効のまま）。ADR-041 のとおり、規約による分離のまま
  である。
- **リリースノート**：破壊的変更として、デプロイ中の 503、デプロイ後のコンテンツ再索引、FGAC は戻せない
  ことを書く。

## 残課題

- 権限の正確な一覧（demo で確かめる）。
- blue/green 更新の所要時間と、CloudFormation がその完了を待つ時間。CloudFormation の
  タイムアウトにかからないかを確かめる。
- 監査ログを有効にするか（費用と保持期間）。
- 運用者が VPC の中から OpenSearch に届く経路（今は踏み台が無い）。
- 環境をまたいで使用量を見る管理サイトを作るときは、インデックスの統計だけを許す観察用のロールを、
  同じ割り当ての仕組みに足す（マスターは使わせない）。
