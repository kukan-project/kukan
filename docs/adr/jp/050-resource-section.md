# ADR-050: リソースのセクション分け（`position` は 1 本のまま、`section` は表示ラベル）

## ステータス

**承認（Accepted）** — 2026-09-09 実装。

1 つのデータセットに多くのリソースを入れるとき、リソースを**フォルダー的にまとめて
見せる**手段を用意する。ただしツリー構造は持たず、リソースに `section` という
文字列ラベルを 1 本足すだけにとどめる。並び順は既存の `position`（データセット内の
連番）が唯一の正で、`section` は並び順に一切関与しない。表示は `position` 順に
並べたうえで、**同じ `section` が続いている区間**を 1 つのセクションとして見せる。
これにより CKAN 互換 API の `resources` 配列（`position` 順のフラット配列）は形も
順序も変わらず、`position` の決め方にも手を入れない。

## コンテキスト

### 現状

リソースはデータセットに対してフラットで、`resource.position`（整数、データセット内で
0 からの連番）による順序だけを持つ。`position` を書く経路は
`PUT /api/v1/packages/:id/resources/reorder` だけで、アクティブな全リソース ID の
順列を受け取り、データセット単位の advisory lock で直列化する。create / update の
バリデーターに `position` は無く、CKAN 互換ルートはすべて読み取り専用である。

公開ページはリソースを `position` 順の単純なリストとして縦に並べ、絞り込みも検索も
無い。管理画面は同じ順序をドラッグ & ドロップで並べ替える。リソースの URL は
`/dataset/:name/resource/:id` の ID ベースで、分類に依存しない。

CKAN 由来の `resource_type` 列は DB と API にあるが、管理画面のフォームにも一覧にも
出ていない。CKAN 本体でもこの列は自由文字列で語彙が定義されておらず、コアの
入力フォームからはコメントアウトされている（表示に効くのは `listing` / `service` /
`api` の 3 値だけ）。「種別」の軸は存在するが、意味は KUKAN が与えるしかない。
本 ADR ではこの列に触れない。

### 「リソースが多い」の 4 類型

同じ「多い」でも中身が違い、正しい受け皿も違う。

| 類型                 | 典型例                                   | セクションが答えか | 既存の受け皿                                                                   |
| -------------------- | ---------------------------------------- | ------------------ | ------------------------------------------------------------------------------ |
| 時系列で分かれている | 2020.csv 〜 2025.csv、月次ファイル       | いいえ             | 同一系列なら版（ADR-043）、別物なら年度別データセット + グループ               |
| 軸で分かれている     | 都道府県別 47 ファイル、施設種別ごと     | **はい**           | 無し。本来は 1 ファイル + 区分列だが、提供元の都合で分割が動かせないことが多い |
| 本体 + 付随文書      | データ本体、項目定義書、コード表、README | 種別で足りる       | `resource_type`（語彙を KUKAN が決めれば使える。本 ADR の対象外）              |
| 同一データの別形式   | 同じ内容の CSV / JSON / XLSX             | いいえ             | 並列の distribution として横に並べる                                           |

セクションが唯一の答えになるのは「軸で分かれている」型だけである。この ADR は
その 1 類型に払う最小の費用を決める。

### 外部契約

- CKAN の `package_show` は `resources` を `position` 順のフラット配列で返す。CKAN
  本体もフォルダー概念を持たず、初期にあった `resource_group` は廃止されて以来
  フラットのままである。KUKAN の CKAN 互換 API はこの形を返しており、ckanapi 等の
  クライアントがそれを前提にしている
- CKAN はリソースの未知キーを resource extras として保存する。KUKAN を CKAN から
  ハーベストした場合、リソースに足したスカラーは extras として残る
- DCAT 3 / DCAT-AP 3.0 に Distribution 同士を束ねる語彙は無い。`dcterms:hasPart` は
  `dcat:Resource`（Dataset 等）に定義されており、Distribution は対象外。DCAT が
  用意しているのは「データセットを分ける」側の語彙だけで、入れ子データセット
  （`dcterms:hasPart`）、`dcat:DatasetSeries`、束ねて 1 配布物（`dcat:packageFormat`）
  の 3 つがそれぞれ「軸で分かれている」「時系列で分かれている」「まとめて落としたい」
  に対応する

## 検討した選択肢

### A) 絞り込みのみ（DB 変更なし）

リソース一覧に名前の部分一致と形式フィルタを足す。数十件までなら「分けたい」の
実態は「探したい」であることが多く、これで消える要望は多い。ただし「軸で分かれて
いる」型の**まとまりとして見せたい**要望には答えない。本 ADR と独立に実施できる。

### B) 命名規約による自動グルーピング（DB 変更なし）

リソース名の `/` や共通接頭辞から見出しを自動生成する。データを持たないので取り消しは
容易だが、規約が守られない瞬間に見出しが崩れ、崩れたことを誰も検知できない。
運用者に規約を強いる割に、守られている保証が無い。

### C) ラベル列 1 本

リソースに文字列ラベルを 1 本足す。並び順との関係で 3 通りある。

**C-1) `position` をセクション内連番にする（却下）** — 順序が (section, position) の
2 軸になる。CKAN 互換出力の `position` が `0, 1, 0, 1, …` になり、`position` 順に
並べるクライアントで順序が壊れる。セクション自身の順序を持つ列も別に要る。

**C-2) `position` は 1 本、ラベルは連続を強制する（却下）** — 「同じラベルの
リソースは `position` 上で連続する」を不変条件として持ち、reorder で違反を拒否し、
create と update のラベル変更でリソースをセクション末尾へ移して再採番する。CKAN
互換の順序は保てるが、`position` を書く 3 経路すべてに手が入り、セクションが「集合」
として振る舞うぶんの契約（400 になる順列、黙って動く位置）を抱える。

**C-3) `position` は 1 本、ラベルは表示専用（採用）** — ラベルは並び順に一切関与
しない。表示は `position` 順に並べたうえで、同じラベルが**続いている区間**を 1 つの
セクションとして見せる。間に別のラベル（または未分類）が挟まれば、同じ名前の
セクションが改めて現れる。セクションは「集合」ではなく「区間」であり、状態は
各リソースのラベル以外に何も無い。`position` の書き手は今のまま reorder だけで、
create / update は列を 1 つ増やすだけになる。

### D) `resource_folder` テーブル（却下）

任意階層のツリーを持つ。得られるのは入れ子表示だけで、代わりに次を抱える:

- `resources` 配列の外に構造を持たせることになり、CKAN 互換の形を保てない
- 空フォルダー・改名・パッケージのパージ（ADR-028 / ADR-039）と CASCADE・移動時の
  排他というライフサイクルが増える
- フォルダーが「もの」として見えた瞬間にフォルダー単位の公開制御を求められるが、
  権限はデータセット単位（ADR-039 の下書きも同様）で、現行モデルに存在しない

入れ子が本当に要るなら、それはデータセットを分ける合図として読む。DCAT の立場も
同じで、Distribution が多くて分けたいなら子データセット（`dcterms:hasPart`）に
分けるのが標準側の答えである。

## 決定

C-3 を採用する。

### 名前は `folder` ではなく `section`

要望は「フォルダー的な」ものだったが、フィールド名と UI 文言は **`section` /
「セクション」**にする。`folder` は入れ物・階層・「中に入れる」を連想させ、本 ADR が
否定した「もの」としてのフォルダー（入れ子、フォルダー単位の権限）を名前が暗示する。
`section` は「見出しで区切られた区間」で、C-3 の意味そのもの — 同じ名前が再登場
しうること、集合ではないこと — を名前が担う。標準語彙に Distribution のまとまりを
表す語は無く（外部契約の節）、どの名前を選んでもサイトローカルな名前になるので、
設計との一致だけで選ぶ。

### データモデル

- `resource.section TEXT NULL`。null が未分類
- **`/` を階層の区切りとして予約する。** 公開ページは 3 段まで入れ子で描き、管理画面は
  `/` 入りの名前をパス全体で 1 本の見出しに出す（下記「公開ページの階層表示」）
- 正規化: `/` で分割し、各セグメントの前後空白を除去し、空セグメント（先頭・末尾の
  `/`、`//`）を捨てて `/` で結合し直す。結果が空なら null。長さ上限は `name` に
  準じて実装時に決める
- **不変条件は 1 つ: 同じ名前は連続した 1 区間にしか付かない。** 同名の区間が離れて
  2 つできる書き込みは拒否する — reorder は `sections` の有無によらず並びの結果を、
  create / update は `section` の文字列も `null` での解除も検証する。
  C-2 との違いは、行を動かして直すのではなく**検証で止める**こと。区切り線 UI は
  区間を分断する操作を持たないので、止める入口は名前の入力だけで足りる。守るのは
  サービス層で、position の advisory lock の中で検証する — UNIQUE 制約では「連続」を
  表せず、trigger は Drizzle の管理外になるため、DB 制約は置かない
- セクションに独立した状態（順序・説明・ID）は無い

### 表示規則

リストは**2 階層の木を 1 列で描いたもの**である。リソースはデータセットのルートに
いる（`section` が null）か、1 つのセクションの中にいるかのどちらかで、3 階層目は
無い。セクションの中にあるリソースは**全員がそのラベルを持つ**。

`position` 順に並べ、次の規則で描く。

- `section` が null でなく、直前のリソースと `section` が異なるとき、そのリソースの
  前にセクション見出しを立てる
- `section` を持つリソースは**インデントして描く**。ルートのリソースはインデント
  しない。1 列に 2 階層を描く以上、どちらの階層にいるかは字下げで示すしかない
- `section` が null のリソースはインデントが戻り、直前のセクションはそこで閉じる
- 同じ名前の見出しは 1 データセットに 1 つ（前項の不変条件）。万一データが重複を
  持っていれば（検証導入前のデータ、直接の DB 操作）、隠さずそのまま 2 つ描く

```
pos 0  section=null   住所一覧.csv
pos 1  section=資料   ── 資料 ──
                        項目定義書.pdf
pos 2  section=資料     コード表.csv
pos 3  section=null   施設一覧.csv       ← インデントが戻る = ルート
pos 4  section=補足   ── 補足 ──         ← 別のセクション
                        README.md
```

### 公開ページの階層表示

公開ページは `/` をそのまま入れ子として描く。表示規則の一般化で、直前のリソースと
セグメント列を先頭から比較し、最初に食い違った深さから下の見出しを開く。区間の
意味は変わらず（`2024/東京都`, `2025/東京都`, `2024/大阪府` と並べば `2024` は 2 回
現れる）、深さごとにリソースを字下げする。親の区間が無いまま `セクション1/中身1`
だけがあるときは、親見出し `セクション1` を子のパスから合成して出す（データには
存在しない）。見出し要素は深さに応じて `h3`, `h4`, … とし、文書のアウトラインが
実体になるので、ツリーロールは要らない。

**管理画面は平ら**なまま、`/` 入りの名前を 1 本の見出しとして扱う。編集側まで入れ子に
すると区切り線が多段になり、操作が増える。表示する深さは **3 段まで**とし、4 段目
以降は 3 段目のラベルに `/` ごと畳んで出す（`a/b/c/d` は `a` › `b` › `c/d`）。データは
全パスのまま保存し、畳むのは描画だけである。3 段を越えたくなったら、それはデータ
セットを分ける合図として読む（前節の D 案の却下理由と同じ）。

### 書き込み経路

- **reorder**: 位置の扱いは変更なし。契約に**任意の `sections`** を足す。
  `resourceIds` だけの body はそのまま有効。`sections` を付けるなら**全アクティブ
  リソースを 1 回ずつ**挙げ、順序と同じトランザクションで丸ごと確定する（差分にすると
  同時編集で行単位の後勝ちになり、誰も見ていない分割区間ができる）。ここに乗せる理由は 2 つ:
  `PUT /resources/{id}` は URL リソースのパイプラインを再実行するが、見出しは
  他所のサイトを取り直す理由にならない。そして区間はラベルと順序の両方で決まるので、
  2 回の呼び出しに割ると、間に入った読み取りが誤った見出しの下にリソースを見せる
- **create**: `section` を受け付けて保存するだけ。位置は今のまま末尾
  （`MAX(position) + 1`）。末尾に入る以上そこは末尾の階層なので、管理画面は
  その階層のラベルを添えて POST する
- **update**: `section` を受け付けて保存するだけ。位置は動かさない。**省略時は保持**し、
  null で解除する — ラベルは reorder 側で配置されるもので、無関係な編集の副作用で消えて
  はならない（`extras` と同じ扱い）。フォームからの
  編集はこの経路を通る（リソース自体を編集しているので、パイプラインの再実行は
  従来どおり起きる）

### API

- REST: `resource` の入出力に `section` を足す。create / update body で受け付ける
- CKAN 互換: 各リソースに `section` を追加フィールドとしてそのまま載せる。配列の
  形と順序は不変。未知のフィールドはクライアント側で無視されるか、CKAN に
  ハーベストされれば resource extras として残る
- `position` の意味も書き手も変えない

### 管理画面

編集はリソースの属性としてではなく、**区切りの操作**として行う。「リソースを追加」の
隣に「セクションを追加」を置き、リソース個別のフォームには `section` を出さない。
1 行ずつラベルを打たせると、見出しの下にあるのに入っていないリソースが簡単にでき、
「セクション」という言葉と操作がずれる。

- **セクションを追加**: 名前を入力すると、すべての行の下に見出しが立つ。見出しは
  そこからドラッグで好きな位置に置ける（行と同じく上下ボタンは持たない）。メンバーのいない見出しは
  同時に複数あってよい
- **名前の入力で重複を止める**: 追加・改名で既存のセクション名を入れると「同じ名前の
  セクションが既にあります」と出て保存できない。区切り線 UI で同名の区間が離れて
  できる経路はここだけなので、サーバー側の検証は保険になる
- **名前の編集中は配置操作をロックする**: 編集対象は位置でなく見出しの id で持つが、
  編集している間に行が動くと、確定した名前がどの区間に付くのか読めなくなる
- **置いた見出しは、その下のルートのリソースを引き取る**: 文書の見出しと同じ読み方で、
  見出しより下・次のセクションの手前までがそのセクションになる。下にルートの
  リソースが無い位置（末尾、または別のセクションの直上）に置いたときだけ、メンバーの
  いない見出しのまま残る。メンバーのいないセクションは保存しない（データモデルに
  存在しないため）— ブラウザ内の状態として持ち、リソースが入った時点で実体になる
- **見出しは区切り線で、動かしても行は動かない**: 見出しを下げると通り過ぎた自分の
  メンバーは直前のセクションに移る（上がルートならルートに出る）— 区切り線より上の
  行は上の見出しのものなので。上げると通り過ぎたルートの行が入る。新しく置くと下の
  ルートの行を全部取る。この 3 つは「区切り線から次のセクションの手前までが自分の
  もの」という 1 つの規則で、`position` は一切変わらず所属だけが変わる
- **別のセクションの途中に置くと、そこで分割する**: 置いた位置から次の見出しの手前
  までが自分のものになり、上半分は元のセクションに残る。**見出しの真上に置いても何も
  取らない**（空の見出しの真上でも同じ） — 分割は先頭行より下でしか起きず、セクションを上から丸呑みすることは
  できない。他のセクションが空にすることはできず、空にするのは自分の解除か、自分の
  区切り線を下げ切ったときだけである
- **最後のメンバーを離した見出しは空の見出しとして残る**: 名前が 1 段下げすぎた
  だけで消えるのは不親切なので、メンバーのいない見出し（保存されない）に戻る
- **末尾に足したものは末尾の階層に入る**: 新規リソースもドロップしたファイルも、
  最後の行と同じセクション（追加直後の見出しがあればそれ）を引き継ぐ
- **ドラッグは直前の行の階層を継ぐ**: セクションのメンバーの下に落ちればそのセクション、
  ルートの行の下ならルート、先頭ならルート。最上部へ動かすのが、ルートへ戻す確実な道。
  **見出しの上に落とせばその区間の 1 番目**になる — 直前の行から読める階層は区間の外側
  なので、1 番目に入る意思はこれでしか伝えられない
- **行をセクションから出すには**: 見出しを下げるか、行を見出しより上へドラッグする。
  行ごとの「出す」ボタンは置かない — 出すのは簡単でも戻すのが難しく、対にならない
- **見出しの改名・解除**: その区間の全行を書き換える。同じ名前が離れた場所にもある
  場合、そちらは動かさない（区間であって集合ではないため）
- 上記の編集はどれも「並び順を保存」でまとめて確定する。reorder 1 回で、順序と
  変わったラベルが一緒に確定する
- 折りたたんでも DOM には全件出す（SSR / クローラー）
- セクションは URL に入れない。リソース URL は ID ベースのままにする

### 検索と MCP

- セクション名は検索語として効く。ADR-025 のリソース子ドキュメントに `section` を
  持ち（`name` / `description` より低い重み）、PostgreSQL フォールバックの ILIKE と
  ADR-034 の埋め込みテキスト（重複を除いたラベルを 1 行）にも入れる。「都道府県別」
  「議事録」のような分類語は、リソース名に書かれていなくても探せる。スコアは子文書の
  `score_mode: max` なので、区間の全リソースに付いた名前が件数分加算されることはない。
  検索結果カードでは、セクション名だけで一致したリソースはセクションごとに 1 行
  （先頭のリソース + 「他 N 件」）に畳み、行数は 5 件で打ち切る。何に一致したか
  （`matchedOn`）と一致総数（`matchedResourcesCount`、確定できなければ下限）は OpenSearch・PostgreSQL の
  両アダプターが返し、アダプターが運ばなかった分は「他 N 件」に数える（畳んだ行を隠すときは
  その行が代表する全件を数える）。運ばれなかった分がある、本文一致が上限に達した、
  運ばれなかったメタデータ一致と本文一致の重複が判定できない — のいずれかで総数が
  確定できないときは、件数を下限（「以上」）として出す
- 導入済みの検索インデックスには、`section` のマッピングをプロセス最初の書き込みの前に
  足す（追加は冪等。拒否されたら警告に留めて書き込みは止めない）。検索経路は
  マッピングに触れない。インデックスの再構築は埋め込みの再生成も enqueue する
- MCP は `get_dataset` で公開ページと同じ見出し（`/` の入れ子も同じ深さ、3 段まで）を
  字下げ付きで挟み、`get_resource` は `Section:` 行で出す。見出しの定義は公開ページと
  同じ `@kukan/shared` の関数で、2 つは 1 つの定義の描き分け

### やらないこと

- セクションでのファセット・絞り込みは持たない。検索語として効くだけで、
  「このセクションだけ」を切り出す条件にはしない
- セクション単位の権限・公開制御は持たない。UI 文言の時点で「表示上の区切り」と
  言い切る
- 版（`resource_version`）には `section` を凍結しない。リソースの属性であって
  内容ではない
- `resource_type` には触れない。将来 KUKAN が語彙を与えるなら、種別（データ /
  文書 / API）は `resource_type`、まとまり（都道府県別・年度別）は `section` と
  役割が分かれ、両方同時に使える

## トレードオフ

- **同じ名前を離れた 2 箇所に置くことはできない。** 意図的に同名を使い分けたい場合
  （上下に「参考資料」など）は名前を変える。`/` の入れ子では「2024/東京都」と
  「2024/大阪府」は別の名前なので、離れて置けば公開ページの親見出し「2024」は 2 回
  出る — 完全一致の名前だけを対象にした限界で、親の一意性は残課題
- **DCAT では落ちる。** `section` はサイトローカルな表示情報で、DCAT 出力には
  乗らない。これは名前を何にしても同じで、仕様の限界である。将来 DCAT を真面目に
  出すなら、同じ `section` の Distribution を 1 つの子 Dataset にまとめて
  `dcterms:hasPart` で親にぶら下げる展開が自然に書ける（`/` の階層はそのまま
  `hasPart` の連鎖になる）。CKAN へのハーベストでは extras として残る
- **`/` が使えない。** セクション名に `/` を含めたい場合は区切りとして解釈される。
  予約しない選択もあったが、後から予約すると既存データの意味が変わるので、最初から
  予約する
- **セクションで探せない。** 検索・ファセットに使えないのは意図した制限で、A 案の
  絞り込みで補う

## 残課題

1. **A 案（絞り込み）を先に入れるか、同時に入れるか。** 本 ADR と独立で費用が
   小さい。先に入れて要望が残るかを見るのが本来の順序だが、要望の類型が「軸で
   分かれている」と分かっているなら同時でよい
2. **セクション名の正規化の範囲。** `/` 分割と空白除去は決定に含めた。大文字小文字・
   全角半角の同一視は、実装時に既存データの実態を見て決める
3. **セクションを丸ごと別の場所へ運ぶ操作は無い。** 見出しは区切り線なので、大きな
   セクションの順序を変えるには行を 1 つずつ動かすことになる。複数行の選択と一括
   移動を入れるなら、それは見出しとは独立した行の操作として足す
4. **管理画面の階層表示。** 公開側は入れ子だが、管理側は平らで `/` 入りの名前を
   そのまま見せる。編集操作を入れ子にする要望が出たら別途判断する
5. **親の一意性。** `/` の入れ子で、同じ親を持つ子が離れて置かれると親見出しが
   2 回出る。完全一致の名前だけを検証しているためで、親の接頭辞まで対象にするなら
   規則の定義から要る
