# ADR-025: OpenSearch parent-child インデックスへの統合

## ステータス

**承認済み（Accepted）** — 2026-05-31

ADR-021（判断 1）を置換する。

## コンテキスト

現在の検索は 3 つの OpenSearch インデックスで構成されている：

- `kukan-packages` — データセットメタデータ（title, name, notes, organization, tags 等）
- `kukan-resources` — リソースメタデータ（name, description, section, format, packageId）
- `kukan-contents` — リソースコンテンツ全文（extractedText, resourceId, packageId）

`msearch` で 3 インデックスを並列検索し、アプリケーション層でパッケージ単位にマージしている。
この設計には以下の問題が確認された：

### 問題 1: ファセットカウントの不整合

aggs（集計）はパッケージインデックスの検索結果にのみ基づく。
リソース名やコンテンツでマッチしたパッケージはマージ後に追加されるため、
ファセットの件数に反映されない。

例: パッケージの title に「東京観光」がなくリソース名に含まれる場合、
検索結果には表示されるがファセットカウントは 0 件になる。

### 問題 2: ファセットフィルタの未適用

リソース/コンテンツ検索にはファセットフィルタ（organization, tags 等）が適用されず、
フィルタ条件に合わないパッケージが検索結果に混入する。

### 問題 3: マージロジックの複雑さ

`mergeResourceHits`, `mergeContentHits`, `fetchPackagesByIds` など約 200 行のマージロジックが必要。
スコアリング、ページネーション、ハイライトの整合性維持が困難。

## 検討した選択肢

| 方式                     | 概要                                                            | メリット                                                             | デメリット                                                                 |
| ------------------------ | --------------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| A. 2段階検索             | Phase 1 で packageId 収集、Phase 2 で ids+filter+aggs           | インデックス変更不要                                                 | スコアリング・ハイライト・ページングの整合性が取れない                     |
| B. パッケージに非正規化  | リソース名をパッケージドキュメントに埋め込む                    | 検索が単一クエリ（リソース名まで）                                   | リソース更新時にパッケージ再インデックス。コンテンツは別インデックスのまま |
| **C. parent-child 統合** | 単一インデックスに join フィールドで 3 ドキュメントタイプを統合 | 全問題を根本解決。1 クエリで検索・aggs・ハイライト・ページングが完結 | 再インデックス作業。同一シャード制約                                       |

## 決定: 方式 C — parent-child インデックスへの統合

### インデックス構造

```
kukan-search (単一インデックス)
  ├── type: "package"   (parent)
  │     title, name, notes, organization, tags, formats, ...
  ├── type: "resource"  (child of package)
  │     name, description, section, format
  └── type: "content"   (child of package)
        extractedText, resourceId, contentType
```

OpenSearch の join フィールドは 1 階層のみサポートするため、
resource と content は両方 package の子としてフラットに配置する。
content は論理的には resource の子だが、grandchild（package → resource → content）は
OpenSearch では不可。代わりに `resourceId` フィールドを保持し、
リソース単位の操作（deleteContent, getContentChunks 等）は term フィルタで対応する。

### 検索クエリ例

```json
{
  "query": {
    "bool": {
      "should": [
        { "multi_match": { "query": "東京観光", "fields": ["title", "notes"] } },
        {
          "has_child": {
            "type": "resource",
            "query": { "multi_match": { "query": "東京観光", "fields": ["name", "description"] } }
          }
        },
        {
          "has_child": { "type": "content", "query": { "match": { "extractedText": "東京観光" } } }
        }
      ],
      "minimum_should_match": 1,
      "filter": [{ "terms": { "organization": ["my-org"] } }]
    }
  },
  "aggs": {
    "organizations": { "terms": { "field": "organization" } }
  }
}
```

### 利点

- 検索・ファセット・フィルタ・ページングが 1 クエリで完結
- マージロジック（`mergeResourceHits`, `mergeContentHits`, `fetchPackagesByIds`）が不要に
- ファセットカウントが全ソース（パッケージ + リソース + コンテンツ）のマッチを正確に反映
- フィルタがパッケージレベルで一元適用される

### 制約・注意点

- **同一シャード制約**: 子ドキュメントは親と同じシャードに配置される（`routing` パラメータで制御）
- **ドキュメント数**: パッケージ数 × (リソース数 + チャンク数) に増加するが、数万パッケージ規模なら問題なし
- **子ドキュメントの更新**: リソース/コンテンツの追加・削除時に `routing=packageId` が必要
- **再インデックス**: 既存 3 インデックスからの移行が必要
- **inner_hits**: リソース/コンテンツのハイライトを取得するには `has_child` + `inner_hits` を使用

### 節の重み — 本文はデータセット自身の説明を上書きしない

検索は 3 つの節を `should` で足す。パッケージ自身、リソースのメタデータ（`has_child:
resource`）、リソースの本文（`has_child: content`）である。子の節はどちらも
`score_mode: 'max'`、つまり**最良のチャンク 1 つ**がその節のスコアになる。

当初はメタデータと本文を同じ重み（0.4）に置いていた。これが壊れる。本文は千件の自由回答の
うち 1 件に語が現れれば最大スコアを取り、抄録で主題として述べている文書と同じ重みで競う。
実際に「お年寄り」の 1 位は、自由回答 1 行に「年寄りには」を含むだけの水道の意識調査だった。

**本文の重みを下げる。** ゴールデンセット（開発カタログ、168 パッケージ、2026-09-17）で、
他を固定して本文の重みだけ掃いた結果:

| 本文の重み | `word` nDCG（キーワード脚） | 融合後 |
| ---------- | --------------------------: | -----: |
| 0（無効）  |                         62% |        |
| 0.05       |                         67% |        |
| 0.15       |                         67% |    71% |
| 0.25       |                         64% |        |
| 0.4        |                         54% |    66% |

**切るのではなく下げる。** 0 にすると 5 ポイント落ちるので、本文は寄与している。ただし
データセット自身の説明を上書きしてはいけない。0.05 と 0.15 は同値なので、本文の信号をより
多く残す 0.15 を採った。`exact` はどの条件でも 100%、`synonym` と `natural` も不変である。

**`score_mode` は答えではない。** もう一方の候補として測ったが、`sum` は `exact` を
87% まで落とす — 名前を繰り返す長い文書が、その名前を持つデータセットを抜くからである。
`avg` は誤差の範囲だった。

### 本文のクエリ側 — 依頼表現だけを落とす

メタデータは `kuromoji_query_analyzer`（`ja_stop` + `ja_request_words`）で検索するが、
本文（`extractedText`）はこれを使わない。`ja_stop` は kuromoji 同梱のフィルタで、
「こと」「もの」「ため」「する」を落とす。メタデータは検索されるために書かれた文なので
それで困らないが、**本文は文書自身の言葉**であり、「こと」が探している当のものである
ことがある。

一方で、依頼表現は落とさなければならない。`operator: 'and'` は全トークン一致を要求する
ので、「〜を教えてください」の語がそのまま**文書が含んでいなければならない語**になる。
実測（開発カタログ、968 チャンク）:

| クエリ                               | 現行 | 依頼語だけ落とす |
| ------------------------------------ | ---: | ---------------: |
| 防災の取り組み                       |   23 |               23 |
| 防災の取り組みについて教えてください |    4 |               23 |
| 子育ての支援制度                     |  222 |              222 |
| 子育ての支援制度を教えてください     |   42 |              222 |

**依頼語を足しても件数が変わらなくなり、素の問いは動かない。** そこで本文には
`ja_request_words` だけを持つ `kuromoji_content_query_analyzer` を当てる。

**全語一致をやめる案は測って見送った。** `minimum_should_match` はキーワード脚を
44% → 50% に上げるが、融合後は overall 88% → 87%、`synonym` 94% → 88% と下がる。
メタデータが当たらない問いでは緩めた本文一致がキーワード脚の上位を占め、RRF がそれを
1 位票として数えるためである。加えて一致チャンクが増えるとその一つ一つに 500KB の
チャンクへのハイライトが走り、評価実行中に親サーキットブレーカーが 8 回作動した
（上限 2040MB、平常時 352MB）。最小構成はこの半分のヒープしかない。

### 解析設定の更新（インデックス名の別名化）

アナライザーはインデックス作成時に固定される。kuromoji の設定（ストップワード、
品詞フィルタ）を変えても、稼働中のデプロイでは既存インデックスの解析は変わらない。
再構築（ドキュメントの再投入）も、投入先が同じインデックスであれば解析は古いままで、
効かない。

そこで検索インデックスは **別名（alias）の後ろに置く**。実体は
`<prefix>-search-000001` のような連番で、アプリケーションが読み書きするのは常に別名
`<prefix>-search` である。解析設定を更新したいときは、次の連番でインデックスを作り、
`_reindex` で全ドキュメントを写し、別名を差し替える。`extractedText` は `_source` に
入っているため、OpenSearch 側で解析し直すだけで済み、外部 URL の取得・テキスト抽出・
埋め込み生成は一切走らない（コンテンツ再処理が時間単位なのに対し、秒単位で終わる）。

判断:

- **自動移行はしない。** 別名より前に作られたデプロイはそのまま動く。移行は全ドキュメントの
  コピーであり、プロセスが起動したという理由で始めてよい操作ではないので、
  管理者の明示的な操作（`POST /admin/search/reanalyse`）の中でだけ行う。更新後に
  一度だけ必要な作業なので、置き場所はダッシュボードの移行通知（バージョンの補完と
  同じ形）で、解析が古い間だけ出て、終わると消える。
- **差し替えは原子的。** `_reindex` が 1 件でも失敗したら新インデックスを捨て、稼働中の
  インデックスには触れない。成功時は `updateAliases` の 1 リクエストで remove と add を
  同時に行うため、検索が空を返す瞬間が無い。別名より前のデプロイでは、同名のインデックスを
  同じアクション列の `remove_index` で落とすので、初回移行も原子的である。
- **検出できるのは解析設定だけ。** マッピングの食い違い（既存フィールドの型やアナライザー
  変更）は、この判定では出てこない。直し方は同じ（作り直す）なので、必要になったら判定を
  広げる。
- **コピー中の書き込みは失われるので、同じジョブの中で索引を直してから終わる。**
  `_reindex` の開始後に別名へ入った更新は新インデックスに含まれない。取りこぼしのうち
  2 つは、古いだけでは済まない。

  - 「公開→非公開」を落とすと**非公開のデータセットが検索から返り得る**。可視性を決めて
    いるのは索引の `private` フィールドで、API は検索結果を DB で再検証しない。
  - 削除されたリソースのコンテンツが残る。コンテンツは**リソースではなくパッケージの子**
    なので、リソースが消えても生きている親から chunk に届いてしまう。
  - コピー中に別のワーカーが書いたコンテンツが消える。行の `contentIndexed` は真のまま
    なので、通常の実行は「もう索引済み」と判断して書き直さない。差し替えだった場合は、
    置き換えられたはずの古い本文がコピー経由で戻ってくる。ワーカーは複数台に伸びるので、
    これは例外的な状況ではない。

  どちらも後続ジョブではなくこのジョブの中で直す。キューに積むと、混雑している間は索引が
  嘘をついたまま使われ、その後続がデッドレターへ落ちれば恒久化するからである。ジョブは
  メタデータ再構築（DB から読み直し、書く前に消すので削除も反映）と、DB に無いリソースの
  コンテンツ削除を行い、それが終わるまでメッセージを完了扱いにしない。再配送されたときは
  解析設定が既に最新なのでコピーを飛ばし、修復だけをやり直す。**どこからどこまでを直すかは
  ジョブではなくインデックスが覚える** — コピーの開始時刻を新インデックスの `_meta` に書き、
  修復が終わったら完了印を押す。ジョブはキューのメッセージで、最初の試行を何も知らない
  プロセスへ再配送され得るが、直す対象であるインデックスは残るからである。コピー中に Index
  ステップが終わったリソースは、**古い chunk をその場で消してから** `contentIndexed` を
  取り下げて保存済みファイルから再実行する（取得は走らない）。消さずにキューへ預けると、
  置き換えられたはずの本文が滞留中ずっと引けてしまう。窓はコピーの長さなので対象は数件で、余分に選んでも要らない再構築が 1 件増える
  だけである。

  再構築の実行そのものは別のジョブなので、修復済みの印を押した時点ではまだ走っている。
  それが失敗した場合に残るのは**欠落であって露出ではない**。しかも所在が分かる — 実行は
  リソースのパイプライン行に `error` を記録し、それが管理画面のジョブ一覧に出て、隣に
  再実行がある。行の `contentIndexed` も偽のままなので、欠落はキューだけでなく DB に
  残る。デッドレターを覗く運用は要らない。

  なお判定そのものが取れないとき（クラスタに届かない等）は、画面は黙ってよいが**ジョブは
  失敗させる**。「分からない」を「最新」と読むと、再解析をしていないメッセージを完了扱いに
  してしまう。

  検索側で DB を再検証する案もあるが、検索 1 回ごとに DB 往復が増えるため、ここでは採らない。

- **メッセージは処理中ずっと保持する。** コピーは大きなカタログでは分単位になり、キューの
  可視性タイムアウトより長い。放置すると同じメッセージが別のワーカーへ渡り、最後は作業が
  走ったままデッドレターへ落ちる。キューアダプタが、ハンドラの実行中に可視性を延長する
  （上限つき — 応答しなくなったワーカーが claim を失う性質は残す）。
- **宛先の名前は試行ごとに違う。** 同じ名前を導出する 2 つの試行は「どちらが持ち主か」を
  合意しなければならず、マーカーもリースも実行中タスクの照会も、一方が他方の作業中の
  インデックスを消せる窓を残す。名前が違えば、その問いが要らない。各試行は自分の
  インデックスを埋め、どれがカタログになるかは別名の差し替えが決める。
- **差し替えは条件付き。** `remove` に `must_exist` を付ける。付けないと、既に動いた別名を
  外そうとした 2 番目の試行は**黙って何もせず**、`add` だけが通り、別名が 2 つの
  インデックスに跨る。その状態は書き込みを一切受け付けない（"no write index is defined"）
  ので、索引付けが静かに止まる。`must_exist` があれば 2 番目は 404 で弾かれ、アクション列
  全体が拒否される。
- **別名が動いたあとは、新インデックスを誰も消さない。** 差し替え後に残るのは旧インデックス
  の掃除だけで、その失敗は置き去りのインデックスであって障害ではない（次回の一掃が片付ける）。
  応答だけ失われた差し替えは、まだ適用されるかもしれない。後片付けで「自分の宛先」を消すと、
  別名がこれから指すインデックスを消すことになる。別名を読み直して確かめる手も**効かない** —
  差し替えが landing する直前に読めば旧インデックスが返り、その答えを根拠に消した先が、まさに
  別名の移り先だからである。消してよいのは、差し替えをまだ頼んでいないときと、クラスタが
  4xx で**はっきり断った**ときだけ。タイムアウト・接続断・5xx では放置し、次回の一掃に任せる。
- **死んだ試行のインデックスは、年齢だけで片付ける。** 名前が試行ごとなので、落ちた実行の
  宛先は誰も再利用しない。コピーの期限より古いものは、終わった試行のものである。それより
  若いものは、まだ動いているかもしれない。
- **バッチは 10 件。** 2026-09-17 計測: 1 バッチ 50 件（500KB チャンク換算で 15MB が
  同時に在庫）だと 285MB のインデックスのコピーでヒープ 80%、1.8gb の親サーキット
  ブレーカーに対し 1.6gb に達し、並走する検索が 503 で弾かれる。最小構成の
  `t3.small.search` はその半分のヒープしかない。

### 移行計画

1. 新しいインデックスマッピング定義（join フィールド + kuromoji analyzer）
2. `OpenSearchAdapter` の CRUD メソッドを新構造に対応
3. 検索メソッドを `has_child` クエリに書き換え（マージロジック削除）
4. マイグレーションスクリプト作成（3 インデックス → 1 インデックス）
5. 管理画面の reindex 機能を新構造に対応
