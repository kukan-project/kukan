# ADR-064: サイト全体のカスタムメタデータを key-value でランタイム設定に置く

## ステータス

**提案（Proposed）** — 2026-10-10

サイト全体で使う任意の値（人口・世帯数・基準日・キャッチコピーなど）を、**key → 値**のフラットな
組として `system_setting`（ADR-036）に置き、管理画面から sysadmin が編集する。値の種類は数値・
文字列（言語別の文字列を含む）・日付の 3 つ。公開の設定 API に載せ、本体とブランドの両方が同じ読み出し口から使う。
key の意味は、それを読むコンポーネントが決める。

## コンテキスト

### 1. きっかけ

自治体のカタログでは、トップページに人口・世帯数・人口動態のような「サイトを代表する数字」を
並べることが多い。

| 人口          | 世帯          | 人口動態（前月比） |
| ------------- | ------------- | ------------------ |
| 123,456       | 123,456       | -12                |
| 令和8年6月1日 | 令和8年6月1日 | 令和8年6月1日      |

値は**月に一度程度**変わる。数字に限らず、キャッチコピーや問い合わせ先の電話番号のように、
ブランドのデザインに差し込みたい「サイトの値」は他にもある。

### 2. 今の置き場所では合わない

- **ブランド（ADR-023 / ADR-042）**: `brand-config.ts` はビルド時に固定される。値を 1 つ直す
  たびにビルドとデプロイが要る。更新するのは自治体の担当者で、フォークのコードを触る人ではない
- **お知らせ**: 題名と日付の一覧で、個々の値を名前で取り出す形をしていない
- **ブランドのコンポーネントに直書き**: brand-config と同じく、値の更新がデプロイになる

ADR-036 は「基準を持たない純粋なコンテンツ型の設定は、ランタイム設定を唯一の置き場とする」と
決めており、`search-example-queries` を brand から管理画面へ移した前例がある。

### 3. 用途を先に決めない

最初の用途はトップページの数字だが、出したい値の種類と組み合わせはサイトごとに違う。用途ごとに
型（「指標」＝ラベル・値・単位・基準日の組など）を作ると、新しい用途のたびに本体の変更が要る。
置き場所は汎用にし、組み立ては読む側に任せる。

## 検討した選択肢

### A) `brandConfig` に置く — 不採用

値の更新がビルドとデプロイになる（コンテキスト §2）。

### B) 用途別の型（「指標」の配列：ラベル・値・単位・基準日・出典）— 不採用

本体の標準コンポーネントがそのまま描けるのは利点だが、数字の帯以外の用途に使えない。
基準日を持たない値や、文字列の値、複数の指標で共有する基準日のような形のたびに型を足すことになる。

### C) 値に表示用の属性を付けた key-value（`{ value, label?, unit?, asOf? }`）— 不採用

B より汎用だが、属性の選び方が数字の帯に寄っている。どの属性が要るかは用途で変わり、
結局は読む側が決める。属性も別の key として持てば足りる。

### D) 値だけのフラットな key-value — 採用

`population = 123456`、`population-as-of = "2026-06-01"` のように、1 つの key に 1 つの値。
単位や基準日も、必要なら別の key にする。各項目は値の種類（数値・文字列・日付）を持つ。ADR-036 の基盤（レジストリ・汎用 API・監査ログ・
30 秒のキャッシュ）にそのまま乗る。

## 決定（提案）

### 1. 設定キーと値の形

設定キーは `site-metadata`。値は項目の配列で、各項目は key・値の種類・値を持つ。

```typescript
// key: ^[a-z0-9][a-z0-9-]{0,63}$, unique within the list
type SiteMetadataEntry =
  | { key: string; type: 'number'; value: number }
  | { key: string; type: 'text'; value: LocalizedText } // string | { ja?: string; en?: string }
  | { key: string; type: 'date'; value: string } // YYYY-MM-DD
```

- 既定値は空配列
- 項目は 100 件まで。文字列は 1 言語あたり 1,000 字まで。数値は有限の値に限る
- 配列で持つのは、管理画面での並びを保つため（jsonb のオブジェクトはキーの順を保たない）。
  意味上の順序はない

**値の種類を項目に明示する。** JSON には日付の型が無く、日付と文字列は値の形からは見分けられない。
管理画面で選んだ種類をそのまま保存し、保存時はその種類のスキーマで値を検証する。

**数値と文字列を分けて持つ。** 数値は桁区切り・小数桁・符号を表示側がロケールに合わせて描ける。
`"123,456"` のように文字列で入れると英語表示で桁区切りを変えられないため、数として扱う値は
数値で入れる。

**日付は日付型として持つ。** 値は ISO 8601 の日付（`YYYY-MM-DD`）で、保存時に実在する日付か
確かめる（`2026-6-1` や `2026-02-30` は断る）。時刻は持たない。月次の基準日には日付で足り、日時が
要るようになったら種類を足す。表示側が和暦・西暦を選んで整形する（§4）。「令和8年6月1日」と
文字列で保存すると、英語表示や西暦表示に戻せない。

**言語で変わる文字列は言語別に持てる。** `{ ja: '探す・見る・ダウンロードする', en: 'Find, view, download' }`。
言語で変わらない値（電話番号など）は単なる文字列でよい。

### 2. key の意味は読む側が決める

本体は key の意味を持たない。どの key を何に使うかは、それを読むコンポーネント（ブランドの
`TopPage` など）が決める。

- 表示場所を示す属性は持たせない。どこに何を出すかは、コンポーネントが key で選ぶ
- 管理画面で key を変えたり消したりすると、それを読む表示からその値が消える（エラーにはしない）。
  読み出しの関数は、key が無いときや型が想定と違うとき `undefined` を返す
- **`kukan-` で始まる key は本体の予約とする。** 本体が将来、特定の key に意味を持たせる
  （たとえば標準のトップページで読む）ときのために空けておく。ブランドとサイトはそれ以外を使う

### 3. 公開の読み出し口

既存の `GET /api/v1/site/settings` に `metadata` を足す。応答では、引きやすいように
key をキーとするオブジェクトにし、値の種類は返さない
（`{ "population": 123456, "population-as-of": "2026-06-01", ... }`）。日付は ISO の文字列で返す。
種類まで返すと、ブランドが値ごとに種類を外す手間が増えるため。日付として扱うかは読む側が
`metadata.date(key)` で決める（保存時に日付型で検証済みの値なら必ず読める）。

**すべて公開される。** 匿名で読める API に載るので、公開してよい値だけを入れる。管理画面の
カードにその旨を書く。

### 4. web 側の部品

本体に置き、本体のページからもブランドからも使う。

- **読み出し**: サーバーコンポーネントから使う `getSiteMetadata()`。1 リクエストの中で
  `site/settings` を 1 回だけ読む（React の `cache`）。トップページが既に読んでいる
  `site/settings` と同じ読み出しを共有する
- **型付きの取り出し**: `metadata.number(key)`、`metadata.text(key, locale)`（言語別の文字列を
  解決する）、`metadata.date(key)`（保存時と同じ規則で、実在する ISO の日付のときだけ返す。
  日付型の項目なら必ず読める）
- **整形の部品**: 数値をロケールに合わせて描く `SiteNumber`（`signed`、`fractionDigits`）、
  日付を描く `SiteDate`（`calendar`: `'japanese'` / `'gregory'`、既定は日本語表示なら和暦、
  英語表示なら西暦。`Intl.DateTimeFormat` の `ja-JP-u-ca-japanese`）、文字列を表示言語で解決して
  描く `SiteText`。どれも key を `name` で受け取り（`<SiteNumber name="population" />`。`key` は
  React が props として予約している）、値が無いときや種類が違うときは何も描かない

本体の標準のトップページは、今は何も読まない。読む key を本体が決めたときに `kukan-` の key で
読む（残課題）。

### 5. 編集

- 管理画面の `/dashboard/admin/site` にカードを 1 枚足す。編集できるのは sysadmin のみ
  （ADR-036 の汎用 API `PUT /api/v1/admin/settings/site-metadata`）
- 行ごとに key、値の種類（数値 / 文字列 / 言語別の文字列 / 日付）、値を入れる。日付は日付の入力欄で入れる。
  行の追加・削除・並べ替え
- 変更は既存の仕組みで `audit_log` に残る（`{ key, value, previous }`）

### 6. 反映までの遅れ

新しい手当てはしない。現状の各層の保持時間は次のとおり。

| 層                                        | 保持時間                          |
| ----------------------------------------- | --------------------------------- |
| API プロセス内の設定キャッシュ            | 30 秒（保存を受けたタスクは即時） |
| CloudFront の HTML キャッシュ（AWS のみ） | 60 秒（ログイン中は通らない）     |

匿名の閲覧者に届くまで、AWS では最大で約 90 秒、Docker Compose では最大 30 秒。月次の値には
十分短い。sysadmin が保存直後に見ると、セッション cookie で CloudFront を通らないため反映済みに
見えるが、匿名の閲覧者にはまだ古い値が見えることがある。管理画面のカードにその旨を書く。

全ページで読んでも 30 秒のキャッシュに当たるため、ヘッダーやフッターで使っても負荷はほぼ増えない。

## 影響

- `system_setting` のレジストリに 1 キー、`site/settings` の応答に 1 欄、管理画面にカード 1 枚、
  web に読み出しと整形の部品が増える。テーブルの追加・マイグレーションはない
- ブランドは、値の更新のためにビルドし直す必要がなくなる
- key の意味が本体に無いので、検証は値の種類と長さまで。「`population-as-of` を日付型で入れたか」は
  確かめない（文字列で入れても、実在する ISO の日付なら `metadata.date(key)` で読める。
  `2026-02-30` のような文字列は読まない）
- MCP と CKAN 互換 API には出さない。必要になったら別に判断する

## 残課題

1. **本体が意味を持つ key**（`kukan-` 接頭辞）。標準のトップページで数字の帯を出すなど、
   本体が読む key と形を決めるとき
2. **値をカタログのリソースから自動で取る**。人口の統計はたいてい同じサイトにデータセットとして
   公開されており、手入力の値はいずれ公開データとずれる。ADR-032 のクエリ基盤で、指定した
   リソース・列の最新の行から値を取り、key の値を置き換える。表の形がサイトごとにまちまちなので、
   指定の仕方と取れなかったときの扱いを決めてから
3. **日時の種類**。時刻まで要る値が出てきたら、`datetime` の種類を足す
