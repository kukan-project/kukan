# ADR-046: 正本の確定と、その解釈の分離

## ステータス

**提案（Proposed）**

正本ファイルの複製（層 1）を、それを解釈する処理より**先**に確定させる。型推定・Parquet 生成・
DuckLake 取り込みは 1 つの再実行可能なステージにまとめ、DuckDB 上で行う。版は「その bytes を
この解釈で読んだもの」と定義し、解釈が変われば版が上がる。

ADR-043 の残課題「プレビュー Parquet の統合（層 3）」を回収する。

## コンテキスト

### 1. 一番死にやすいステップの後ろに、一番失いたくない書き込みがある

現在の順序は Fetch → Extract → Version → Lake → Index である。Version（正本の複製 = 層 1）が
Extract の後にあるのは、**Extract が出す列スキーマを版行に焼き付けたい**という一点のためである。

しかし Extract は実行中で最も重い。CSV/TSV では入力を 50MB に制限したうえで、

```ts
const text = bufferToUtf8(fileBuffer, encoding) // UTF-8 文字列
Papa.parse(text) // 全行を string[][] に展開
buildColumns(headers, dataRows) // 型付き列データ
parquetWriteBuffer({ columnData }) // Parquet バッファ
```

と JS ヒープ上に**入力の数倍**を確保する。入力サイズは制限しているが、展開後は制限していない。

**この死に方は決定的である。** 同じファイルなら毎回同じ量を確保するので、SQS が再配信しても
同じ場所で落ちる。`maxReceiveCount` に達すれば DLQ へ行き、**その内容は層 1 に一度も入らない**。
再配信は一過性の障害しか救わない。

層 1 は全フォーマット共通の、唯一再生成できない資産である。それが**派生物の生成失敗に道連れに
される**のは順序の問題であって、必然ではない。

### 2. プレビュー Parquet が層 2 への唯一の橋になっている

層 2（DuckLake）は、その版の bytes を読める形で持つ複製がプレビュー Parquet しか無いため、
そこからしか取り込めない。結果、取り込みに失敗した版はプレビューを指し続ける必要がある
（`resource_version.lake_source_key`、ADR-043 §6-6）。

この 1 本のポインタのために、以下が必要になった。

- 取り込み延期時にポインタを立て、旧キーを同じ文で park する
- 取り込み成立時にポインタと snapshot id を同じ文で入れ替える
- 追い越しで拒否したときにポインタを外して park する
- 孤児スイープの参照確認にこの列を加える
- 取り込み済み・パージ済みの版に立たないよう条件を付ける
- 毎時、キューが落とした分を DB から拾い直す

**版ファイル自体が読めるなら、これは 1 つも要らない。** 版ファイルは不変で
`resource_version.storage_key` に指されており、再取り込みはいつでも読み直せる。守るべき
一時的なポインタが存在しない。

### 3. 不変の行に、可変の判断が載っている

`resource_version.schema` は捕捉時に焼き付けられる。だが利用者に主キーやカスタム型を
割り当てさせるなら、**捕捉時点でスキーマは確定しない** — その時まだ選んでいない。

割当を後から変えられるようにすると、不変行に可変の値が載る。主キーを変えるたびに新しい版を
作るか、不変性を破るかの二択になる。**どちらを選ぶかは「版とは何か」の答え次第**であり、
それを決めていなかったことが問題の正体である。

## 検討した選択肢

### A) 現状維持

順序も焼き付けも変えない。

- **利点**: 変更が無い。スキーマは insert 1 回で書ける
- **欠点**: 上の 3 つがすべて残る。特に主キー割当の UI が作れない

### B) Version を前に出すだけ

順序を Fetch → Version → Extract → Lake → Index にし、スキーマは Extract 後に UPDATE する。

- **利点**: 小さい。層 1 の耐久性という一番の問題が消える
- **欠点**: insert と UPDATE の間で死ぬと**スキーマが永久に null の版行**が残る。内容は
  変わっていないので次の実行も捕捉せず、既存行に後からスキーマを付ける経路も無い。修復パスを
  もう 1 つ作ることになる。プレビュー依存も焼き付けの問題も残る

### C) 解釈を 1 ステージに集約し、DuckDB で行う

順序を Fetch → Version → Interpret → Index とし、Interpret が型推定・Parquet 生成・層 2
取り込みを 1 つの DuckDB セッションで行う。

- **利点**: OOM 経路が消える（`COPY (SELECT * FROM read_csv(...)) TO ... (FORMAT parquet)` は
  ストリーミング）。層 2 が版ファイルを直接読めるのでプレビュー依存が消える。ステージが
  再実行可能なので、主キーを変えたら**そこだけ**走り直せる
- **欠点**: 型推定が ADR-029 の自前実装から DuckDB の sniffer に変わる。DuckDB の `read_csv` は
  **Shift_JIS を読めない**（utf-8 / utf-16 / latin-1 のみ）ため、エンコーディング検出と
  UTF-8 変換は手前に残る

## 決定

**C。** あわせて「版とは何か」を定める。

```
Fetch ─→ Version ────────────→ Interpret ──────────────→ Index
        層 1 確定（全形式）    DuckDB 1 セッションで
        bytes のみ、解釈なし   型推定 → Parquet → 層 2 取り込み
                              ↑ 主キー/型の割当で、ここだけ再実行
```

### 1. 層 1 は解釈を含まない

Version は Fetch の直後、最も軽い処理（サーバーサイドコピー + insert）で確定する。全フォーマット
共通であり、テーブル形式かどうかに関心を持たない。

キル時の扱いは変わらない。版 insert は claim を条件にしているので（ADR-044 §4）、止められた
実行は順序に関わらず版を残さない。**順序ではなく claim が決めている。**

### 2. 解釈は 1 つの再実行可能なステージ

型推定・Parquet 生成・DuckLake 取り込みは同じ入力（版ファイル）から同じ DuckDB セッションで
行う。3 つが同じ解釈を共有することが保証され、途中で失敗しても入力が不変なので何度でも
やり直せる。

**再実行の単位が「解釈」になる。** 失敗した取り込みをやり直すときも、利用者が主キーを変えた
ときも、走るのはこのステージだけで Fetch は動かない。前者は版を増やさず、後者は増やす
（次項）— 違うのは入力ではなく、解釈が変わったかどうかである。

### 3. 解釈が変われば版が上がる

版を「その bytes」ではなく**「その bytes を、この解釈で読んだもの」**と定義する。主キーや型の
割当を変えることは新しい版を作ることであり、既存の行は書き換えない。

不変行に可変の判断を載せる問題は、これで消える — **何も変異しない**。主キーの変更履歴が版履歴に
そのまま残るので、いつ誰が解釈を変えたかも監査ログと版の両方から辿れる。版行の外に置き場所を
新設する必要も無い。

捕捉時にスキーマが確定しない点は変わらないので、版行への書き込みは Interpret の後になる。
B の欠点（永久に null）はここでは欠点にならない — **未割当は正常な状態**であり、埋める導線が
UI に存在するからである。

**bytes は複製する。** 解釈だけが変わった版も、自分の版ファイルを持つ。同じオブジェクトを 2 つの
版で共有すれば複製は避けられるが、**「1 版 = 1 オブジェクト」はパージが依存している不変条件**で
ある。共有すると、v2 のパージが v3 の bytes を消すか、あるいは消さずに終わる — 法的削除が
削除しないという最悪の結末になる。50MB の複製は、その危険と引き換えにするには安い。

副作用が 2 つある。**内容ゲートは解釈変更を捕捉しない** — `decideVersionCapture` は最新 active 版
とハッシュを比べるので、bytes が同じなら捕捉しない。解釈変更はパイプラインではなく利用者の操作
から入る別の導線になる。そして**同じハッシュを持つ版が複数存在するのが正常になる**。ハッシュから
版を引く箇所（差し戻しの起点、取り込み待ちの版）は最新の 1 件を採るので、そのままで正しい。

### 4. `lake_source_key` は撤去する

層 2 が版ファイルを直接読むようになれば、コンテキスト 2 に挙げた機構は全て不要になる。
取り込みに失敗した版は「snapshot id を持たない active な版」であり、それだけが再取り込みの
条件になる。毎時のスイープはその条件で拾えばよい。

### 5. エンコーディングは手前に残す

`Encoding.detect()` による判定と UTF-8 変換は DuckDB に渡せない。ストリーミングで変換した
オブジェクトを Interpret の入力にする。日本語 CSV を扱う以上ここは譲れない。

## 影響

- **耐久性**: 決定的な Extract 失敗（OOM、壊れた CSV）でも層 1 が残る。DLQ に行くのは解釈だけ
- **機構が 1 つ減る**: `lake_source_key` とその一生（延期・park・参照確認・毎時スイープ）
- **メモリ**: JS ヒープに全行を展開しなくなる。`MAX_PARQUET_SOURCE_SIZE`（50MB）の見直しが可能
- **DB**: 版行の `schema` は残り、主キー・型上書きもそこへ入る。新しいテーブルは要らない
- **ストレージ**: 解釈だけを変えた版も自分の版ファイルを持つため、同じ bytes が複製される
- **移行**: 既存の版は `schema` を持ったままでよい。`lake_source_key` は撤去時に落とす

## 残課題

1. **型推定の同等性**: DuckDB の sniffer が ADR-029 の自前推定と日本語 CSV でどう違うか未測定。
   差が大きければ、推定だけ自前を残して Parquet 生成のみ DuckDB に寄せる折衷もありうる
2. **解釈変更の導線**: 内容ゲート（`decideVersionCapture`）を通らないので、版番号の採番と
   claim の取り方を利用者操作の側で決める必要がある。連続して主キーをいじったときに版が
   増えすぎないか（下書き中は確定させない等）も UX の論点
3. **Interpret の再実行導線**: キューのジョブ型を新設するか、既存のパイプラインジョブに
   「解釈だけ」のモードを持たせるか
4. **プレビュー Parquet の位置づけ**: 解釈の産物として残すのか、層 2 から都度生成するのか
   （ADR-043 残課題「層 3」の本体）
