# ADR-065: Office 文書の原本を ibisOffice でブラウザに描く（サーバーで文書を開かず、ブラウザでも隔離した iframe で描く、提案）

## ステータス

**提案（Proposed）** — 2026-10-11（2026-10-27 に選択肢 I を追加、2026-10-29 に I を実測し、
決定を F から I に改めた）

Office 文書（XLSX・XLS・DOCX・PPTX・PPT）を、Microsoft の Office Online Viewer に頼らずにも
見られるようにする。**ibisOffice（Rust を WebAssembly にしたオフィススイート）を web に同梱し、
閲覧者のブラウザの中で原本を描く。** 描くのは WebGPU、使えなければ WebGL2。サーバーは文書を
開かず、worker にも成果物にも何も足さない。web は自前の起動ページから `/preview` のバイト列を
渡す。ibisOffice は sandbox を付けた iframe（opaque origin）の中で動かし、KUKAN の
Cookie・API・親のページに届かないようにする。重すぎる文書は、ibisOffice の WASM のメモリに
上限を掛けて中で止め、抽出テキストに切り替える。Office 5 形式の「原本」のタブは既定で
ibisOffice にし、サイトの環境変数 `OFFICE_PREVIEW_VIEWER`（既定 `ibis-office`）を
`office-online` にしたサイトだけ今までどおり Office Online Viewer にする。DOC は ibisOffice が
開けないので、`ibis-office` のサイトでは抽出テキストとダウンロードになる。

当初は F（worker の LibreOffice で PDF にする）を仮の決定としていた。F は信頼できない文書を、
資格情報とネットワークを持つ worker で開く。設定（リンクの読み込みやマクロの停止）だけでは
守り切れず、変換を秘密情報もネットワークも持たない実行環境に分ける必要があった。I を同じ
サンプルで測った結果（§実測の「ibisOffice（I）」）、I はその分離もイメージの +1.1 GB も版ごとの
変換も要らず、日本語は端末の MS 書体で描かれ、GPU の無い端末でも WebGL2 で表と文書を操作
できた。I に足りないもの（DOC、均等割り付け、半角の英数字の書体、閲覧専用の作り込み）は
上流に要望を出した。

ブラウザの中で描くほかの方式は採らない。LibreOffice の WebAssembly ビルド（ZetaOffice）は
ページ全体のクロスオリジン分離、起動 1 回分で 50 MB の転送（キャッシュは 20 分）、1 GB の WASM メモリが要り、配布物に
CJK フォントが無く日本語が描けない。DOCX・PPTX だけを描く軽いライブラリ（docx-preview・
pptx-renderer）は、Office の公開データの 99 % 以上を占める XLS・XLSX に効かない。自前の
グリッド描画と LibreOffice の HTML 書き出しは、神エクセルの要件（罫線・結合・セルからあふれる
文字）で落ちる。

## コンテキスト

### 1. 今の原本プレビューは公開サイトでしか動かない

`OfficeOnlinePreview`（`apps/web/src/components/preview/resource-preview.tsx`）は
`https://view.officeapps.live.com/op/embed.aspx?src=<ファイルの URL>` を iframe に出す。
Microsoft のサーバーがそのファイルを取りに来る方式なので、

- インターネットから届かないサイト（手元の環境、LGWAN などの閉域網）では表示できない
- 非公開のデータセットのファイルは表示できない（取りに来られない）
- 10 MB まで（`OFFICE_PREVIEW_LIMIT`）
- ファイルの中身が Microsoft に渡る

閉域網まで対応するという KUKAN の方針と噛み合わない。抽出テキストのプレビュー（2007 年より前の
古い形式も対象）はどの環境でも出るが、原本の見た目は出ない。

### 2. Office Online Viewer を選んだ理由は、神エクセルの忠実度

自治体の公開データの表計算は、見出しが多段に結合され、罫線で枠が組まれ、表題や注記が
狭い列に置かれて隣のセルへあふれている — いわゆる神エクセルが多い。これを**原本どおりに**
見せることが原本プレビューの価値で、罫線の太さ・結合・あふれた文字の 3 つが崩れると
「違うものを見ている」ことになる。Office Online Viewer はここが正確だった。置き換えは
同じ忠実度でなければならない。

### 3. ほかの形式の原本は、すでに自前で出している

| 形式    | 原本の見せ方                                                    |
| ------- | --------------------------------------------------------------- |
| PDF     | `/preview` を iframe で（ブラウザの PDF 表示）                  |
| 画像    | `<img>`                                                         |
| 一太郎  | EZPZ File JTD（WebAssembly）でブラウザ内に描く — ADR-051 決定 7 |
| CSV/TSV | Parquet を Range 配信して表に — ADR-048                         |
| Office  | **Office Online Viewer（外部）**                                |

Office だけが外部サービスに残っている。

### 4. Office の公開データは、ほとんどが表計算である

e-Gov データポータルの資源を形式で数えると（`resource_search?query=format:<FMT>`、2026-10-11）:

| 形式 |    件数 |
| ---- | ------: |
| XLS  | 137,876 |
| XLSX |  13,067 |
| DOC  |      61 |
| DOCX |      31 |
| PPTX |      35 |

**XLS と XLSX で 99.9 %**、しかも古い XLS が XLSX の 10 倍ある。Office の原本プレビューの
価値は、ほぼ表計算（それも Excel 97–2003 形式）で決まる。文書とスライドは少ない。

### 5. ブラウザで描くなら、前提が 3 つある

- **クロスオリジン分離**: LibreOffice の WASM ビルドは pthread を使うので `SharedArrayBuffer`
  が要り、それには**最上位の文書**に `Cross-Origin-Opener-Policy: same-origin` と
  `Cross-Origin-Embedder-Policy: require-corp` が要る。分離した iframe を普通のページに
  入れても足りない（実測 — 下記）。KUKAN のリソースページは地図タイル（OSM・国土地理院）や
  ブランドの埋め込みを持ち、COEP はそれらにも CORP か CORS を要求する
- **閉域網での配置**: CDN に頼らず、KUKAN 自身が静的ファイルを配れること
- **フォント**: 日本語の文書は、描く側に CJK フォントが無ければ豆腐になる

### 6. 既にある部品

- Interpret は版ごとに「解釈」の成果物を書く（ADR-046）。文書テキスト（`text.ndjson.zst`）、
  表の Parquet、ZIP のマニフェスト。原本の PDF も同じ置き場に収まる
- `/preview` は `resolvePreviewTarget` で版ごとの成果物を選び、Range 配信する。PDF は
  この経路で iframe に出ている
- XLS は自前の BIFF 読み手、XLSX は officeparser が、シートの一覧と使用範囲を変換前に
  読める。表計算の書き出し方の判定と、シートタブの名前はここから取れる
- worker の重い処理は子プロセスで行う（ADR-059）。外部の実行ファイルを時間と資源の上限付きで
  走らせる場所はそこに近い

## 検討した選択肢

### A) Office Online Viewer のまま

費用は無いが、§1 の 4 つの制約が残る。閉域網・非公開データに原本プレビューが無いままになる。

### B) LibreOffice をブラウザで動かす（ZetaOffice / LOWA）

LibreOffice を WebAssembly にしたものを CDN（または自前配置）から読み、Qt のキャンバスに
描く。6 形式すべてを LibreOffice の忠実度で描ける。ただし実測で次が分かった。

- 最上位の文書にクロスオリジン分離が要る。分離無しでは `SharedArrayBuffer is not defined`
  で起動しない。**分離した iframe を分離していないページに入れても同じ**。KUKAN で使うなら
  リソースページ全体を分離するか、別タブの専用ページで開くことになる
- 起動 1 回分の応答は CDN から **50 MB（brotli 圧縮後）**。CDN の `Cache-Control` は
  `max-age=1200` で、ブラウザのキャッシュが効くのは 20 分、過ぎれば読み直し（計測は応答の
  大きさを数えたもので、キャッシュが効いたかは区別していない）。展開後は `soffice.wasm` 154 MB + `soffice.data`
  95 MB
- 起動時に **1,024 MB の WASM 線形メモリ**を確保する
- 配布物に **CJK フォントが無い**。日本語はすべて豆腐で描かれた（レイアウトは正しい）。
  自前ビルド（LOWA）でフォントを同梱するか、起動前に仮想 FS へフォントを書く必要があり、
  どちらも数十 MB が転送に加わる
- ZetaOffice はオープンベータで、製品版の条件が未確定。自前ビルドは Qt 5 + Emscripten の
  固定版を要し、LibreOffice の更新に追従する負担が大きい

### C) 軽いライブラリでブラウザに描く（docx-preview・pptx-renderer）

DOCX は docx-preview（Apache-2.0、21 KB gz + jszip 28 KB gz）、PPTX は @aiden0z/pptx-renderer
（Apache-2.0、452 KB gz、echarts 込み）で HTML/SVG に描く。実測では公開サンプル 23 件すべてを
描き、DOCX は 0.5 秒以内、9 MB・112 枚の PPTX でも 2.5 秒。忠実度は様式・報告書・スライドで
十分に高いが、

- **XLS・XLSX・DOC・PPT には効かない**（§4 の 99.9 % が対象外）
- DOCX の改ページは Word が書く `lastRenderedPageBreak` 頼みで、位置指定やタブ揃えの表は
  行がずれる（16 件中 1 件）。古い PPTX の Wingdings の箇条書き記号は文字（`n`・`l`）で出る
- 描いた HTML をページに置くので、sandbox 付き iframe での隔離が要る（一太郎は canvas に
  描くので要らなかった）

形式ごとに描き手が違うと、表示の癖も違う。

### D) 自前のグリッドの成果物（セル・結合・書式）を web で描く

Interpret がシートごとにセルの値・結合・列幅・罫線・塗りを成果物に書き、web が仮想化
グリッドで描く。LibreOffice が要らず、表計算らしい操作（タブ・スクロール）が自然に付く。
しかし §2 の忠実度を自前で出すには、XLS（BIFF の XF・FORMAT・MERGEDCELLS・COLINFO）と
XLSX（`styles.xml`）の書式を読み切り、罫線の種類（細・太・二重・破線・斜線）、縦書き、
縮小表示、**あふれた文字**を Excel と同じ規則で組む描画器を書くことになる。実装量と
忠実度の両面で分が悪い。

### E) LibreOffice の HTML 書き出しを sandbox 付き iframe で見せる

LibreOffice Calc の HTML 書き出しはシートごとの `<table>` で、罫線（上下左右を別々に、
太さ付き）・結合・塗り・太字は残る（実測 — 下記）。ただし **Excel 特有の「セルからあふれる
文字」が再現されない** — A 列の長い表題が狭い列幅で縦に折り返される。神エクセルの表題と
注記はこの書き方なので、§2 を満たさない。図形の斜線は画像として別の位置に出る。大きな
シートは DOM がそのまま膨らむ（43 万セルで高さ 24 万 px）。

### F) worker の LibreOffice で PDF にし、PDF を描いて見せる（当初の仮の決定、I に改めた）

Interpret が原本を LibreOffice（headless）で PDF に変換し、版の成果物として書く。
6 形式すべてが 1 つの描き手（LibreOffice のレイアウトエンジン）で、B と同じ忠実度 — あふれた
文字も斜線も正しい（実測） — ただし描くのはサーバーで一度だけ。閉域網でも、非公開でも、
サイズ上限は KUKAN が決める。クライアントには何も足さない。

表計算を「紙面」にしてブラウザの PDF ビューアに渡すのは筋が悪い — シートの切り替えも
横スクロールも失う。だから表計算は**1 シート = 1 ページ**で書き出し、web が pdf.js で
ページをシートのタブとして描く。費用は worker イメージ（+1.1 GB）、版ごとの変換時間と
PDF の保存量、変換プロセスのメモリ、web の pdf.js。

### G) Office Online Viewer の自前版を置く（Collabora Online）

LibreOffice を中身とする Collabora Online（CODE、MPL-2.0）を閉域網に置き、KUKAN は WOPI の
2 エンドポイント（CheckFileInfo・GetFile）と iframe を足す。対話的な閲覧（本物のシートタブ・
スクロール・ズーム）が得られ、UX は今の Office Online Viewer にいちばん近い。代わりに
常駐サービスが 1 つ増える（イメージ 1.5〜2 GB、メモリ 1 GB 級）。Compose 構成では現実的
だが、AWS のマルチサイト構成（ADR-041 / ADR-049）では Fargate サービスがもう 1 本になる。
**対話的な閲覧が要件になったときの選択肢**として記録し、今は採らない。

### H) XLSX を表として解釈する（ADR-057）

「素直な表」の XLSX をテーブルとして解釈し、CSV と同じ表プレビューに乗せる。これは
**データとして触れる**ための経路で、原本の見た目の代わりにはならない（見出しが多段の表、
帳票、注記は落ちる）。本 ADR と直交する。F が「見た目」、H が「データ」。極端に大きな
統計表は F の対象外にし、H に任せる。

### I) ibisOffice をブラウザで動かす — 採用（提案、2026-10-27 に追加、2026-10-29 に実測）

ibisOffice（株式会社アイビス、2026-10-12 公開、v0.8 系）は、Rust で書いたオフィススイートを
WebAssembly にし、WebGPU（使えなければ WebGL2）で描く。B と同じく「ブラウザの中で描く」方式だが、B で落ちた条件の
いくつかを満たす。公開されている資料とコード、および §実測の「ibisOffice（I）」で分かったことは
次のとおり。

- **形式**: DOCX・XLSX・PPTX を描く。旧形式 XLS（BIFF8）は内部で XLSX に読み替える読み手が
  あり（`crates/ibis-pptx/src/xls.rs`、値・書式・罫線・結合・列幅・印刷設定）、PPT の読み手も
  ある。**DOC は開けない** — Web 版の入口は .docx・.xlsx・.pptx と、中身で判る XLS・PPT
  だけを受け取り、DOC を渡すとエラーを出さずにスタート画面（新規作成・開く…）になる。変換
  パネルにある .doc の取り込みは、本文のテキストを取り出すだけ（上流に要望済み、
  ibisjp/ibis-office#71）。描画は Office が書き出した PDF との画素比較で 7 万件以上試験して
  いるとされる（開発元の数字）
- **サーバーで開かない**: 描くのは閲覧者のブラウザなので、F で問題になっている「信頼できない
  文書を、資格情報とネットワークを持つ worker で開く」ことが起きない。worker には何も足さず、
  F で前提になる変換の分離も要らない。文書の解析が閲覧者のタブの中に移るので、守りは
  ブラウザのサンドボックスと、配信元の CSP になる。`connect-src 'self'` を付けても動き、
  73 件のどれも外部へ取りに行かなかった
- **埋め込み**: `www/` を静的ファイルとして配り、`view=1` で読み取り専用、`menuBar=0`・
  `toolBar=0` で枠を消せる（公式の埋め込みの説明にある引数）。CDN に頼らず閉域網でも配れる。
  開く文書は `?open=<URL>` で渡せるが、これは説明に無い playground の引数で、**どの URL でも
  ブラウザから取りに行く**（相手が CORS を許せば外部も開く）。KUKAN のオリジンで他人の文書を
  開かせるリンクが作れるので、CSP の `connect-src 'self'` で絞るか、`?open=` を使わず
  バイト列を `run()` に渡す。CSP で止めたときは「起動しています…」のまま止まり、エラーが
  出ない。`view=1` でも DOCX だけは閲覧モードの情報バーと、押しても何も起きない
  「編集に切り替える」ボタンが出る（ibisjp/ibis-office#72）
- **クロスオリジン分離は要らない**: 公開の playground は COOP/COEP を付けずに動いている。
  B の最大の障害（ページ全体の分離が地図タイルとブランドの埋め込みに波及する）が無い
- **転送量**: WASM は展開後 63 MB、gzip で 16.5 MB（B の 50 MB の約 1/3）。自前で配るので
  `Cache-Control` を長くでき、2 回目以降は読まない
- **ブラウザ**: WebGPU を優先し、アダプタが取れなければ **WebGL2 に自動で切り替えて**描く
  （gpui-pre-web の `platform.rs`）。GPU を止めた Windows の Chrome（GPU の無い仮想デスクトップ
  の代わり）でも DOC 以外の 61 件すべてを WebGL2 で描け、表と文書は滑らかに操作できた（§実測）。ただし
  `main.js` は `navigator.gpu` が無いブラウザでは WebGL2 を試さず「WebGPU に対応していません」
  と出して止まる。Firefox は未確認
- **フォント**: Web 版は日本語のフォントを同梱しない。日本語・全角文字はブラウザの
  Canvas 2D に文書の指定（ＭＳ 明朝 など）の名前で頼んで描くので、Windows の端末なら
  本物の MS 明朝・MS ゴシックで描かれる。ただし**半角の英数字は同梱の IBM Plex Sans** で
  描かれ、指定のフォントが端末にあっても使われない（上流に要望済み、ibisjp/ibis-office#73）。
  表計算の値の多くは半角の数字なので、書体と幅が原本と違う
- **ライセンス**: AGPL-3.0-only と商用のデュアルライセンス。KUKAN も AGPL-3.0 なので、
  改変せずに同梱してソースの所在を示せば条件は満たせる。外部からの PR は受け付けていない
- **成熟度**: 公開から 2 週間、v0.8 系。読み取り専用での埋め込みは用意されているが、
  閲覧専用のビルド（編集機能を除いた小さな WASM）は無い

F と比べると、worker のイメージ（+1.1 GB）、版ごとの変換時間と PDF の保存、変換の分離が
すべて要らなくなる。代わりに閲覧者の端末に WebGPU か WebGL2 と数十 MB の初回転送を求め、描画の
忠実度を外部の若いプロジェクトに預ける。表計算はシートのタブ・スクロール・ズームが最初から
付くので、F の残り（pdf.js のシートビューア）も要らない。

見た目の忠実度・起動時間・メモリ・外部取得は §実測の「ibisOffice（I）」のとおり。

## 実測（2026-10-11、I は 2026-10-29）

### サンプル

e-Gov データポータルの公開ファイル（PDL1.0 / CC BY）を CKAN API で形式ごとに拾った 73 件:
DOC 12・DOCX 16・PPTX 7・XLS 16・XLSX 16、PPT 6（ポータルに小さな PPT が無いので、拾った
PPTX を LibreOffice で PPT に保存したもの。PowerPoint 製でない）。最大は PPTX 8.8 MB・112 枚、
XLSX 1.4 MB・43 万セル。計測のハーネスは `spike/adr-065/` に置く（サンプルと結果は含めない）。数値は本 ADR を正本とする。

### 軽いライブラリ（C）

Chromium（Playwright）、描画時間はライブラリの呼び出しの前後。

| 形式 | 描けた | 描画時間 中央値 / 最大 | DOM ノード 最大 |
| ---- | ------ | ---------------------: | --------------: |
| DOCX | 16/16  |         50 ms / 454 ms |           7,465 |
| PPTX | 7/7    |      190 ms / 2,071 ms |          22,714 |

### ZetaOffice（B）

CDN（`cdn.zetaoffice.net/zetaoffice_latest/`）から読む。回線は数百 Mbps。

| 項目                                       |                                 値 |
| ------------------------------------------ | ---------------------------------: |
| 起動（コールド / ウォーム）                |                    5.1 秒 / 4.4 秒 |
| CDN からの応答（起動 1 回分、6 応答）      |                    50 MB（brotli） |
| WASM 線形メモリ（起動直後）                |                           1,024 MB |
| 分離無しの最上位ページ                     | 起動せず（`SharedArrayBuffer` 無） |
| 分離した iframe を分離無しのページに入れる |                         同じく不可 |
| 開けた                                     |                           73/73 件 |

### 表計算の書き出し方（F の肝）

通常の書き出しは、ファイルに保存された Excel の**印刷設定**（用紙・拡大縮小・印刷範囲・
タイトル行・非表示の行列）に従って改ページする。`SinglePageSheets` は拡大縮小も改ページも
無視し、使用範囲の大きさのページを 1 シートに 1 つ作る。

| サンプル           | 通常: ページ数 / サイズ | 1 シート 1 ページ: 寸法（pt） / 実寸 / 時間 / サイズ |
| ------------------ | ----------------------: | ---------------------------------------------------: |
| 43 万セルの表      |         8（A4） / 16 MB |   9,266 × 10,401 / 約 3.3 m × 3.7 m / 18 秒 / 0.5 MB |
| 4.5 万セルの縦長表 |        215（A4） / 9 MB |  126 × 14,384 / 幅 4 cm × 高さ 5 m / 5.6 秒 / 1.1 MB |
| 1 列 1.1 万行      |       18（A4） / 2.4 MB |          394 × 13,434 / 高さ 4.7 m / 1.0 秒 / 0.5 MB |
| 35 シートの集計表  |      64（A4） / 11.5 MB |         700〜1,480 × 880 / A3 前後 / 2.6 秒 / 0.7 MB |

- 通常の書き出しは、作者が印刷用に整えていれば読め、整えていなければ縦に細切れになる。
  43 万セルの表は「1 ページに収める」設定が効いて極小文字の 8 ページになった
- 1 シート 1 ページは、ページが **14,400 pt（PDF 仕様の実用上限、約 5 m）付近**まで伸びる。
  4.5 万セルの表が 14,384 pt で止まっているのは切り詰めに見えるが、縮尺が掛かったのか下が
  切れたのかは未確認
- **PDF の容量は使用範囲の寸法に依らない。** ベクターなので描いたオブジェクトの数で決まり、
  1 シート 1 ページは通常の書き出しより桁違いに小さい（43 万セルで 16 MB → 0.5 MB）。
  通常の書き出しが膨らむのはページごとに資源が繰り返されるためと見ているが、中身は未確認。
  容量が本当に膨らむのは画像・図形の多いシートで、それはどちらでも同じ
- 大きさは worker 側の問題ではなく、**ブラウザで巨大な 1 ページをどう描くか**の問題である。
  pdf.js がページを描く計算量とキャンバスのメモリは、見えている領域の広さとそこに含まれる
  オブジェクト数で決まる
- `SinglePageSheets` は**文書単位**の指定で、シートごとには選べない

### ibisOffice（I）

同じ 73 件を、ibisOffice 0.8.4 の Web 版（playground と同じ `app/`）で開いた。KUKAN が配る
ときと同じく自前のサーバーから配り（gzip、`pkg/` は 1 年の `Cache-Control`）、文書は同じ
オリジンから渡す。`view=1&menuBar=0&toolBar=0`、1280 × 860。時間はナビゲーションの開始から、
起動は `run()` が戻るまで、描き終わりは最初の描画のあと 300 ms 描画が止んだ時点（カーソルの
点滅で描き直しは続く）。2 つの条件で測った:

- **実 GPU**: Windows 11 の Chrome 156、NVIDIA の GPU（Ampere 世代）。描画は WebGPU
- **GPU 無し**: 同じ Chrome を `--disable-gpu` で起動（GPU の無い仮想デスクトップの代わり）。
  WebGPU のアダプタは取れず、描画はすべて WebGL2（ソフトウェア。DOC の 12 件は開けない）

- **見た目**: 神エクセルの斜線・二重線・結合・縦書き、ウィンドウ枠の固定、XLS のシートの
  タブは原本どおりに出た（目視、画素比較はしていない）。日本語は閲覧者の端末のフォントで
  描かれ、半角の英数字は IBM Plex Sans になる（§I）。ただし**横位置の均等割り付けが効かず**、
  中央揃えと同じ位置に詰めて描かれる（XLS・XLSX とも、ibisjp/ibis-office#75）。官公庁の表の
  見出しや項目名によく使われる書式で、ここは F（LibreOffice）が原本どおり
- **F との見比べ**: 同じサンプルの F の PDF と並べると、書体（F はすべて Noto Sans CJK の
  ゴシック体、I は Windows なら本物の MS 明朝・MS ゴシック）と斜線の罫線（F の PDF に見当たらない
  サンプルがある）は I が原本に近く、均等割り付けは F が原本どおり
- **描き終わりは GPU にあまり依らない**。時間の多くは文書の読み込みとレイアウトで、GPU の
  有無が効くのはスクロールなど操作中の滑らかさ。ホイール 30 回を、実 GPU はどの形式も
  入力どおりの約 3 秒でこなした。GPU 無しでも表と文書は約 3 秒（15 fps 前後）で追いつき、
  スライドは 4.5〜10 秒かかった。なお、フラグで WebGPU をソフトウェア（SwiftShader）に
  強制すると WebGL2 より遅く、同じ操作に 12〜60 秒かかった（Linux の Chromium 151）
- **スライドは重い**。WASM メモリが最大 545 MB（GPU 無しでは 805 MB）、renderer と GPU の
  プロセスがそれぞれ 800 MB 前後（GPU 無しでは 1,100 MB 前後）になる。表と文書は、実 GPU
  では 200〜400 MB に収まる（GPU 無しでは GPU のプロセスが 694 MB になった XLS がある）
- **DOC** は 12 件ともスタート画面になった（§I）
- **画像の画素数**（`media/` の画像の縦横の合計）は、最大が 61.8 MP（スライド、40 枚）、
  1 枚の最大が 2.6 MP だった。WASM メモリが最も大きかった 545 MB のスライドは、画像が合計 7.2 MP で、
  メモリの大きさと画素数は対応しなかった
- **隔離した iframe**（`sandbox="allow-scripts"`、文書は `postMessage`）でも、WebGPU・WebGL2
  とも同じく描けた。iframe の中からは Cookie・localStorage・親の DOM が SecurityError になり、
  外部への取得は CSP で止まった。opaque origin なので、配布物には
  `Access-Control-Allow-Origin: *` が要った
- **同じサーバーへの取得**は、iframe の JS からは失敗に見えても、**リクエストはサーバーに届く**
  （CORS が止めるのは応答を読むことで、送ることではない）。サーバー側で記録すると、
  `connect-src 'self'` のままでは、親のページの Cookie が SameSite=Lax なら Cookie 無しで、
  SameSite=None なら **Cookie 付きで**届いた。`connect-src` を ibisOffice の配布物のパスに
  絞ると、何も届かなかった
- **iframe 自身の遷移**は CSP の `connect-src` では止まらない。iframe の中から
  `location.href` で別オリジンへ遷移させると、URL に載せた文書の先頭のバイト列が外部役の
  サーバーに届いた。親のページに `frame-src 'self'` を付けると、同じ遷移は「frame-src に
  反する」として止まり、何も届かなかった（Chromium 151）。`frame-src` を起動ページのパスに
  絞ると、同じオリジンの別の URL（`/whoami?document=…`）への遷移も止まった
- **WebRTC** は sandbox の iframe の中でも使える。起動ページ自身のコードから
  `RTCPeerConnection` で TURN 役の UDP の受け口へ問い合わせると、パケットが届いた。一方、
  iframe の中の `eval`・`new Function` は CSP（`'unsafe-eval'` 無し）で EvalError になった。
  起動ページで WebRTC の関係のものを消すと、子 iframe を作ってその中から取り出し直そうと
  しても SecurityError になった（Chromium 151）
- **DNS の先読み**。起動ページにあとから `<link rel="dns-prefetch">` を足して、文書の中身を載せた
  ような名前を問い合わせさせても、Chromium 151 では名前の解決が起きなかった（ネットワークの記録
  で確かめた）。ふつうのページで同じことをしても起きなかったので、`X-DNS-Prefetch-Control: off`
  の効き目はこの試し方では確かめられない。ヘッダーは、ほかのブラウザや版のための守りとして付ける
- **取り込む関数の汎用の橋**。ibisOffice の WASM が取り込む JS の関数（809 個）に WebRTC の
  ものは無いが、`globalThis` を得るもの、`Reflect.get`・`Reflect.set`、任意の関数を呼ぶ
  `call`、`createElement`・`appendChild` があり、組み合わせれば `eval` 無しで JS の API の
  ほとんどに届く。取り込む `eval` は CSP で止まる
- **隔離した iframe はキャッシュが効かない**。起動ページ（opaque origin）が WASM を取ると、
  開くたびにサーバーへ取りに来た（2 回開いて 2 回）。同じ WASM をふつうのページで開くと、
  2 回目はキャッシュから読んだ（2 回開いて 1 回）
- **WASM のメモリの上限**。起動ページで WASM のメモリの宣言に最大値を書き足して起動すると、
  上限 64 MiB で 43 万セルの表（上限なしでは 223 MB を使う）は、タブを落とさずに
  `RuntimeError: unreachable` で止まり、親に失敗として伝わった。上限 256 MiB では、重いスライド
  （上限なしでは 545 MB を使う）も 229 MB に収まって描けた。上限なしの WASM は、余裕が
  あれば多めに確保していたと見られる

I は F の費用（イメージ +1.1 GB、版ごとの変換と PDF、変換の分離）をすべて無くし、実 GPU の

（書体・斜線）と操作の軽さでも I が上回る。ブラウザの中でも sandbox の iframe で隔離できる。
I の不足は上流に要望を出したうえで受け入れ、サイトごとに Office Online Viewer へ戻せる設定を逃げ道に残す。
I が行き詰まったとき（上流が止まる、閉域網の端末で描けない）の次の手は F で、
本 ADR の F の実測と残課題はそのために残す。

## 決定（提案）

### 1. ibisOffice の Web 版を、改変せずに web から配る

ibisOffice の Web 版（`pkg/` の JS と WASM、アイコンなどの資産）を、KUKAN の web と同じ
オリジンの静的ファイルとして配る。パスに版を含め（`/vendor/ibis-office/<版>/`）、1 年の
`Cache-Control`（immutable）と `Access-Control-Allow-Origin: *`（隔離した iframe から読む
ため、決定 2）を付ける。実行時は CDN に頼らないので、閉域網でも同じに動く。

**取得元**。上流のリリースに添付された Web 版（`ibisOffice-<版>-Web.zip`、0.8.5 から。要望
ibisjp/ibis-office#76 に応えて付いた）を使う。KUKAN のリポジトリには zip を置かず、版と SHA-256 を書いた
`apps/web/vendor/ibis-office/manifest.json` を置き、web の dev とビルドのスクリプトが zip を
取って照合し、`apps/web/public/vendor/ibis-office/<版>/` に展開する（どちらも gitignore）。上流は
公開したリリースのファイルを変えないとしているが、頼らずに SHA-256 で照合する。動いている
サービスは GitHub に行かない。展開した 3,000 余りのファイル（WASM は 65 MB）はリポジトリにも
turbo のキャッシュにも入れない。

zip をコミットしないのは、上流の版の進みが速く（公開から 2 週間余りで 0.8.5）、版を上げるたびに
約 32 MB が履歴に残り続けるため（0.8.4 だけは、リリースに Web 版が無かったので tar.gz を
コミットした時期があり、履歴に残っている）。代わりに、ビルドは GitHub に届く必要がある。
届かない閉域網では、同じ zip を先に `apps/web/vendor/ibis-office/` に置けば取りに行かない。

上流がリリースやリポジトリを消すことへの備えは置かない。起こる確率は低く、起きても動いている
サイトとビルド済みのイメージはそのまま動き、手元に zip があれば作り直せる。対応するソースを案内
できなくなるので、別のソースを用意できなければ、既定のビューアを Office Online Viewer に戻す。
サイトは `OFFICE_PREVIEW_VIEWER=office-online` でいつでも避けられる。写しを保つ手間（本体だけで
なく gpui のサブモジュール 6 つも要る）に見合わない。

**配信**。CloudFront に `/vendor/ibis-office/*` の振る舞いを足し、長期のキャッシュで、Cookie とロケールを
キーにしない（今は HTML の振る舞いに落ち、5 分で切れ、ログインした閲覧者は毎回 web まで
取りに来る）。WASM は前もって圧縮せず、Next がその場で gzip して返す（0.8.4 の実測で 63 MB が 16.4 MB）。
CloudFront は 10 MB を超えるものを自分では圧縮しないが、gzip された応答をエッジでキャッシュする。
前もって圧縮すれば brotli で 10.1 MB まで減るが、`Accept-Encoding` で配るファイルを選ぶ仕組みが
要り、減るのは閲覧者ごとの初回の取得だけ（1 年キャッシュされる）なので、今は入れない（残課題 5）。
Compose の Caddy の圧縮の対象にも wasm を足す。

**ライセンスと表記**。一太郎の EZPZ（ADR-051）と同じく、`LICENSE`・`NOTICE`・`SOURCE` を
並べて置く。zip に入っていない `LICENSE`・`NOTICE` と、`SOURCE` はリポジトリに置く。`SOURCE` には、
元の zip と、対応するソース（上流のタグとサブモジュールのコミット）を書く。ibisOffice は AGPL-3.0-only と
商用のデュアルライセンスで、KUKAN も AGPL-3.0 なので、改変せずに配り、上流の `LICENSE`・
`NOTICE` を保ち、対応するソースを手に入れられるようにすれば条件を満たす。AGPL は、ソースが
どこに置かれていても手に入る状態を保つ責任を配る側に課す。上流が消えたときの扱いは、上の
取得元の項のとおり。

ibisOffice の `NOTICE` には AGPL-3.0 第 7 条(b) の追加の条件があり、ibisOffice を組み込んだ
サービスは画面に「Powered by ibisOffice」と表示し、https://github.com/ibisjp/ibis-office への
リンクを付けなければならない（`docs/TRADEMARK.md` で必須とされる）。埋め込みではメニュー
バーを消すので、ibisOffice 自身の「このアプリについて」は見えない。そこで KUKAN が「原本」
タブのビューアのそばにこの表示とリンクを出す。一太郎のプレビューが「Powered by EZPZ File」を
出しているのと同じ形で、文字だけを使い、ibisOffice のロゴは使わない（名前とロゴは商標）。

### 2. 隔離した iframe で起動し、文書はバイト列で渡す

ibisOffice の `index.html`・`main.js` は使わず、配りもしない（`?open=` の URL をそのまま開く
playground を KUKAN のオリジンに置かないため）。web に小さな起動ページを置き、`pkg/` の
`init`・`set_embed_options`・`run` を直接呼ぶ。起動ページは **`sandbox="allow-scripts"` の
iframe**（`allow-same-origin` を付けない）に入れる。文書は信頼できない入力で、ibisOffice の
解析に不具合があっても、iframe の中から KUKAN のオリジンの権限を使えないようにするため。

**守りの前提**。ibisOffice の WASM が取り込む JS の関数には、`globalThis` を得るもの、
`Reflect.get`・`Reflect.set`、任意の関数を呼ぶ `call`、`createElement`・`appendChild` などの
汎用の橋がある（§実測）。WASM を乗っ取られれば、`eval` が無くても iframe の中の JS の API の
ほとんどを呼べる、と考える。守りは「取り込む関数が少ないこと」ではなく、次の仕組みに置く。

- **起動ページ**
  - 静的なファイルにし、リダイレクトせず、どのクエリでも同じ 200 を返す。クエリで振る舞いを
    変えない（`frame-src` はパスでしか絞れないので、iframe の中のコードは起動ページの同じ
    パスに好きなクエリを付けて遷移し直せる）
  - 応答ヘッダーの CSP に `sandbox allow-scripts` を入れる。iframe の外で直に開かれても
    opaque origin で動き、KUKAN の本物のオリジンの権限を持たない
  - 文書を受け取るのは、`window.parent !== window` で、メッセージが `isTrusted` で、`source`
    が `window.parent` のときだけ
  - ibisOffice が呼ぶ 2 つの関数（`ibisOfficeEmbedAction`・`ibisOfficePickFile`）は、何も
    しない関数として定義する（上流の `main.js` はダウンロードのバイト列を親に送る）
  - ibisOffice を読む前に、WebRTC の関係のもの（`RTCPeerConnection` など）を消す。静的な
    `import` は本文より先に評価されるので、消してから `import()` で読む
  - **WASM のメモリに上限を掛ける**（決定 3）
- **起動ページの CSP は、起動ページと ibisOffice の配布物のパスだけを許す**（`'self'` 全体に
  しない）。CORS は応答を読ませないだけで、リクエストは KUKAN に届き、セッションの Cookie が
  SameSite=None なら Cookie も付く（§実測）。今の KUKAN のセッションの Cookie は Better Auth の
  既定の Lax だが、それに頼らない。DNS の先読みも止める（`X-DNS-Prefetch-Control: off`）。
  `<A>` は起動ページと `/vendor/ibis-office/<版>/` のパス

  ```
  sandbox allow-scripts; default-src 'none'; script-src <A> 'wasm-unsafe-eval';
  connect-src <A>; img-src <A> data: blob:; style-src 'unsafe-inline';
  font-src <A> data:; frame-ancestors 'self'
  ```

- sandbox には `allow-scripts` だけを付け、`allow-top-navigation`・`allow-popups`・
  `allow-forms` は付けない。親のページの遷移、新しいウィンドウ、フォームの送信は、どれも
  外へ出る経路になる
- **iframe 自身の遷移も止める**。`connect-src` は通信だけを止め、iframe が `location.href` で
  自分を外部の URL へ遷移させること（URL に文書を載せて送れる）は止めない（§実測で再現した）。
  そこで親のページの CSP に `frame-src` を付け、iframe の中身を起動ページのパスに絞る。
  `frame-src` は**全ページに**付ける。データセットへはホームや検索のカードから Next の
  `<Link>` で移ることが多く、App Router はページを移っても文書を作り直さないので、効くのは
  最初に開いた文書の CSP になる（データセットのページだけに付けると、ほかのページから入った
  ときに効かない）。`OFFICE_PREVIEW_VIEWER` は実行時の変数なので、ビルド時に決まる
  `next.config.ts` の `headers()` ではなく、middleware で**リクエストごとに**出す。許すのは
  起動ページのパス、同じオリジンの PDF の表示（`/api/v1/resources/…/preview`）、それに
  `office-online` のサイトでだけ Office Online Viewer のホスト（`ibis-office` のサイトで許すと、
  iframe の中のコードが Microsoft のビューアに外部の URL を渡して、そのサーバーに取りに行かせ
  られる）。今の web の iframe はこの 2 つ（PDF の表示と Office Online Viewer）だけ
- **親の受け渡し**
  - 文書は親が `/preview` から取り、バイト列とファイル名を `postMessage` で渡す。`?open=` は
    使わない — どの URL でも取りに行く引数で、KUKAN のオリジンで他人の文書を開かせるリンクが
    作れてしまう（§I）
  - **ibisOffice の WASM も親が取って渡す**。隔離した iframe（opaque origin）からの取得は
    ブラウザの HTTP キャッシュに残らず、開くたびに 16 MB を取り直す（§実測）。親が取れば
    キャッシュが効く。起動ページの JS（170 KB）だけは iframe が読む
  - 1 つの iframe に文書を 1 回だけ渡し、遷移し直したページが `boot` を知らせても送り直さない
    （送り直すと、乗っ取ったコードが遷移を繰り返して文書を少しずつ持ち出せる）
  - 親は `source` が自分の iframe のメッセージだけを受け、`boot`・`ready`・`error` 以外は捨てる
- `set_embed_options` は閲覧専用（`view`）、メニューバーとツールバー無し、閉じる・ダウンロード
  無し。ダウンロードは KUKAN のリソースページのものを使う
- `main.js` の WebGPU の有無の確かめ（`navigator.gpu` が無いと止まる）は持ち込まない。
  ibisOffice は WebGPU が使えなければ自分で WebGL2 に切り替える。どちらも使えずに `run()` が
  失敗したら、起動ページが親に知らせ、親は抽出テキストのタブに切り替える
- **それでも残るもの**。WebRTC は消してあり、子 iframe を作って取り出し直す道は Chrome では
  SecurityError で塞がっている（§実測）。ほかのブラウザの振る舞いや、まだ知らない経路は、
  WASM を完全に乗っ取られることが前提になるので受け入れる。持ち出せるのは、その閲覧者が
  見てよい 1 つの文書に限られる

### 3. 「原本」のタブを既定で ibisOffice にし、同時に 1 つだけ動かす

XLSX・XLS・DOCX・PPTX・PPT の「原本」のタブを ibisOffice にする。原本を描くビューアは
web の環境変数 `OFFICE_PREVIEW_VIEWER` で選ぶ。

| 値                    | 原本を描くもの                       |
| --------------------- | ------------------------------------ |
| `ibis-office`（既定） | ibisOffice（ブラウザの中で描く）     |
| `office-online`       | Office Online Viewer（今までどおり） |

値で選ぶのは、描き手を足すとき（たとえば F の PDF）に値を増やせば済むようにするため。
Office Online Viewer を別の変数で切り替えることはしない — `ibis-office` のときは Office
Online Viewer を使わず、閉域網でも外へ取りに行かせない。既存のサイトは、上げると既定で
ibisOffice に変わる（公開の DOC は原本が見られなくなる）ので、リリースノートに書く。

| 形式                                       | `ibis-office`（既定）          | `office-online` |
| ------------------------------------------ | ------------------------------ | --------------- |
| XLSX・XLS・DOCX・PPTX・PPT                 | 原本: ibisOffice、抽出テキスト | 今までどおり    |
| DOC                                        | 抽出テキストとダウンロード     | 今までどおり    |
| 描く前の確認に通らない文書                 | 抽出テキストとダウンロード     | 今までどおり    |
| ファイルを取り込めていないリンクのリソース | 抽出テキスト（あれば）とリンク | 今までどおり    |

- **非公開・下書きのデータセットでも原本を出す**。今は、非公開のデータセットの Office 文書は
  抽出テキストだけになっている（Office Online Viewer は Microsoft のサーバーがファイルを
  取りに来るので、非公開のファイルを渡せない）。ibisOffice は、閲覧を許された利用者の
  ブラウザが `/preview`（ダウンロードと同じ権限の確かめ）から取って描くので、文書は外へ
  出ない。`ibis-office` のサイトでは、見られる利用者（ログインして権限のある人）には非公開・
  下書きでも原本を出す
- **主な守りは、WASM のメモリの上限**。ibisOffice は完全なオフィススイートで、読める形式も
  画像の種類も（ICO・TGA・PNM・HDR・EXR やアニメーションまで）KUKAN の読み手より多い。描く
  前に KUKAN がそれをすべて数えるのは無理なので、数え上げはしない。代わりに、起動ページが
  WASM を組み立てる前に、そのメモリの宣言に最大値を書き足す（wasm32 で、宣言に最大値が
  無い）。画像でもフォントでも中身の重さでも、何が原因でもそれ以上は確保できず、ibisOffice
  は中で失敗して止まり、親は抽出テキストに切り替える。§実測では、上限 64 MiB で 43 万セルの表を
  開くとタブを落とさずに `RuntimeError` で止まり、上限 256 MiB でも重いスライド（上限なしでは
  545 MB を使った）は上限の中に収まって描けた。上限は 1 GiB を目安に、実装のときに測って
  決め、コードの定数にする
- **描く前の確かめは、安くて確実なものに絞る**（ZIP 爆弾と、取る前の無駄を防ぐ）
  - 取る前に、リソースの情報にある大きさか `/preview` の `Content-Length` が 64 MB を超えて
    いれば取りに行かない。取るときも流しながら数え、64 MB を超えた時点で打ち切る
  - 宣言された形式ではなく、取ったバイト列の先頭の署名で分ける（新しい形式のファイルが
    古い拡張子で公開されることはよくあり、`formats.ts` も XLS・PPT に ZIP の署名を認める）。
    ZIP（`PK\x03\x04`）か複合文書（`D0 CF 11 E0`）でなければ渡さない
  - ZIP は、作りが素直なものだけを通す。目次（central directory）の終わり（EOCD）がファイルの
    末尾に 1 つだけで注釈が空、ローカルの見出しが先頭から隙間なく並び目次と一致する、暗号化
    したエントリーと同じ名前のエントリーが無い、エントリーが 10,000 以下。読み手によって
    見え方が変わる細工（目次を 2 つ持つ、前後に余分なバイトがある）を通さないため
  - ZIP は Web Worker の中で各エントリーを流しながら展開し（`DecompressionStream`）、出てきた
    量だけを数えて中身は捨てる。展開後の合計が 64 MB を超えた時点、または 10 秒を過ぎた時点で
    打ち切る。目次に書かれたサイズは信じない
  - 複合文書は、大きさと署名のほかは確かめない。中の作りの細工は、WASM のメモリの上限で
    受け止める
- **64 MB の根拠**。表と文書は XML が中身の大半で、WASM メモリは展開後の大きさのおよそ
  15 倍で増えた（43 万セルの表で 16 MB → 223 MB、文書で 3.2 MB → 52 MB、§実測）。64 MB なら
  WASM メモリでおよそ 1 GB の見込みで、公開サンプルの最大（16 MB）の 4 倍の余裕がある。倍率は
  2 件から見積もっただけなので、実装のときに大きめの公開 XLSX で測り直す
- **それより先は抑えない**。WASM の外で使うメモリ — ibisOffice がブラウザの画像の読み手に
  渡して展開させる分と、GPU のメモリ — は、WASM の上限が効かない。描き切れずにメモリが
  尽きると閲覧者のタブが落ち、GPU のプロセスはタブの間で共有されるので、ほかのタブの描画も
  一時的に乱れうる（ブラウザは GPU のプロセスを自分で立て直す）。KUKAN のデータや権限には
  届かない。ファイルを置けるのは公開の権限を持つ人に限られ、落ちた文書は次の項の印で 2 回目
  からは開かないので、ここは受け入れる
- **落ちた文書は次から開かない**
  - 描き始める前にその文書の**版**の印を localStorage に付け、描き終わったら消す。次に開いた
    とき印が残っていれば（前回は描き終わらずにタブが落ちた）、抽出テキストのタブから開く。
    「原本」のタブは押せば試せるように残す
  - 描き終わりは、起動ページが `run()` のあと最初の描画を見て親に知らせる。決めた時間
    （30 秒を目安）の間に知らせが無ければ、親は iframe を外して抽出テキストに切り替え、印は
    残さない（落ちてはいないため）
  - 描き終わる前に KUKAN が自分で iframe を外したとき（別のリソースやタブへ移った）と、ページを
    離れるとき（`pagehide`）も印を消す — 落ちたときにはどちらも起きない
  - 同じ文書を 2 つのタブで開いても取り違えないよう、印はタブごとに別のキー（版とタブの ID の
    組）で置き、描いている間は数秒おきに時刻を書き足す（生きている合図）。消すのは自分のタブの
    印だけにする。ほかのタブの印でも時刻が新しければ描いている最中とみなし、途絶えて古く
    なった印だけを落ちた印とみなす
  - 隠れているタブ（後ろで開いた、など）では描画もタイマーも止まり、合図が途絶えて見える。
    印を付けるのはタブが見えているときだけにし、隠れたら描き始めを待たせる
  - sessionStorage にしないのは、落ちたタブを閉じて開き直すと消えてしまうため。印には 1 日の
    期限を付け、過ぎたらまた原本から試す。ストレージが使えないブラウザでは印を使わずに動く。
    印はその閲覧者のブラウザだけに置き、サーバーには記録しない
- WASM は「原本」のタブを開いたときに初めて読む（初回 16 MB、以後は親のキャッシュ）
- **ibisOffice は同時に 1 つだけ動かす**。データセットのページは、一度開いたリソースの
  プレビューと、一度開いたタブを残す作りになっている（Office Online Viewer を読み直さないため）。
  ibisOffice は 1 つで数百 MB〜1 GB を使うので、この例外にする。別のリソースやタブに移ったら
  iframe を外してメモリを返し、戻ったら起動し直す（WASM は親のキャッシュから渡し、iframe の中で
  組み立て直す）
- 抽出テキストのタブは残す。キャンバスに描く原本は読み上げられないので、支援技術で読むのは
  こちらになる

### 4. worker・成果物・既存データには何も足さない

描くのは閲覧のたびにブラウザの中なので、Interpret のステップも成果物も無い。既存のリソースは
再処理なしで、`ibis-office` にしたときから原本が見られる。F のための LibreOffice は worker
イメージに入れない。F を前提にした実装（`OFFICE_PDF_ENABLED`、`/preview?view=print`、
`soffice` の子プロセス）は作らない。

### 5. 採らないもの

- **F（LibreOffice の PDF）**: §F・§判定のとおり。I が行き詰まったときの次の手として残す
- **ZetaOffice / LOWA**: §B のとおり。ページ全体のクロスオリジン分離は、地図タイルと
  ブランドの埋め込みに波及する
- **docx-preview / pptx-renderer**: 動くことは確かめたが、ibisOffice で DOCX・PPTX も描ける
- **自前グリッド・HTML 書き出し**: §D・§E のとおり、神エクセルの忠実度で落ちる
- **Collabora Online**: §G のとおり。対話的な閲覧が要件になったときに再検討する
- **ibisOffice での編集**: 閲覧専用で埋め込む。編集は ADR-007 の Data Editor の範囲

## 影響

- **web**: 隔離した iframe の起動ページ（静的なファイル、CSP の `sandbox`、WASM のメモリの
  上限を書き足して組み立てる）、親が文書と WASM を取って渡す受け渡し、描く前の確かめ（Web
  Worker）、落ちた文書の印、「原本」のタブの切り替え、同時に 1 つだけ動かす扱い（一度開いた
  ものを残す今の作りの例外）、全ページの `frame-src`（middleware でリクエストごと）、
  ビューアのそばの「Powered by ibisOffice」とリンク
- **環境変数**: `OFFICE_PREVIEW_VIEWER`（web、`ibis-office` / `office-online`、既定
  `ibis-office`）を `packages/shared/src/env.ts` に定義し、Compose と CDK（サイトごと）から渡す
- **ビルド**: 上流の zip を取って照合し展開するスクリプト、Dockerfile の web ステージ
  （イメージ +65 MB）
- **配信**: CloudFront の `/vendor/ibis-office/*` の振る舞い、Compose の Caddy の圧縮の対象に wasm。
  ADR-068（web を Lambda で動かす案）では、関数の zip が WASM の分だけ大きくなり、キャッシュに
  外れた取得は Lambda の応答になる
- **api・worker**: 変更なし（`/preview` は今のまま）
- **文書**: 管理者ガイド（`OFFICE_PREVIEW_VIEWER` の設定、対応ブラウザ）、
  リリースノート（既定が ibisOffice に変わる、公開の DOC は原本が見られなくなる）、CLAUDE.md の
  マトリクス（プレビュー表示の列）、サードパーティの表記

## 残課題

1. **上流の不足**: DOC を開けない（ibisjp/ibis-office#71）、`view=1` でも DOCX に閲覧モードの
   情報バーが出る（ibisjp/ibis-office#72）、半角の英数字が IBM Plex Sans になる
   （ibisjp/ibis-office#73）、均等割り付けが効かない（ibisjp/ibis-office#75）。直ったら
   版を上げる。#71 が入れば
   DOC も原本のタブに移す
2. **閲覧専用の作り込み**: `view=1` でも表計算のシート追加の「+」やスライドのノート欄が出る。
   閲覧専用のビルド（編集機能を除いた小さな WASM）があれば転送量も減る。上流の様子を見て要望する
3. **`navigator.gpu` の無いブラウザ**: 起動ページは WebGPU の有無で止めないので、WebGL2 で
   描けるはずだが、Firefox と古い Safari では未確認
4. **メモリの上限の値と、WASM の外のメモリ**: 上限は 1 GiB を目安に実装で測って決める。
   ibisOffice がブラウザの画像の読み手に渡して展開させる分と GPU のメモリは上限が効かず、
   落ちた文書の印で受け止める（決定 3）。落ちる文書が目立つなら、ほかの手を考える
5. **開いた直後のコストと端末**: XLS が先頭のデータセットを開くだけで、16 MB の転送と数百
   MB のメモリを使う。スマートフォン（タブのメモリの上限）や通信量を節約する設定（Save-Data）
   のときは、「原本」を押してから開く形にすることを考える。スマートフォンでは測っていない。
   初回の WASM の転送（gzip で 16.4 MB）が問題になれば、前もって圧縮する（brotli の品質 11 で
   10.1 MB。CloudFront を通らない配置では zstd も。CloudFront は zstd を扱わない）
6. **版の追従**: Dependabot は追えないので、`manifest.json`（版と SHA-256）と `LICENSE`・
   `NOTICE`・`SOURCE` は手で上げる。上流の更新の頻度が高い（公開から 2 週間で 0.8.4）ので、手順を
   スクリプトにする。上げるときは、メモリの上限の書き足しが効くか、`'unsafe-eval'` 無しで
   描けるか、消す WebRTC の関係のもので足りるかを確かめる
7. **残る持ち出しの経路**: WASM を完全に乗っ取られた場合、取り込む関数の汎用の橋から JS の
   API のほとんどに届く。WebRTC は消し、子 iframe からの取り出し直しは Chrome では塞がって
   おり、DNS の先読みは止める（決定 2）。ほかのブラウザの振る舞いや、まだ知らない経路は
   受け入れている。ブラウザが CSP の `webrtc` ディレクティブなどで経路を閉じられるように
   なれば、それも足す
8. **言語**: 起動ページは上流の `index.html` の言語の判定を持ち込まないので、ibisOffice の
   画面の文言（情報バーなど）が KUKAN の表示言語に合わないことがある。言語の渡し方を決める
9. **ファイルを取り込めていないリンクのリソース**: `/preview` が返せないので、`ibis-office`
   のサイトでは原本を出せない（Office Online Viewer は外部の URL を直接渡していた）
10. **F に戻るとき**: F を採るなら、変換を秘密情報もネットワークも持たない実行環境に分ける
    （Compose は `network_mode: none` の専用コンテナ、AWS は IAM ロールを持たず送信を禁じた
    別サービス）。§F の実測と §表計算の書き出し方は、そのときの前提として残す
