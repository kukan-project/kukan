# ADR-040: AI メタデータ提案（提案型・オンデマンド生成）

## ステータス

**承認済み（Accepted）**

## コンテキスト

メタデータの品質はカタログの発見性を左右するが、記入の負担は大きく、
説明文が 1 行だけ・タグが無いデータセットが生まれやすい。AI による支援を
入れる土台は既に揃っている。

- `AIAdapter.complete()` がインターフェースとして定義済み・未実装
- `package` テーブルに `aiSummary` / `aiTags` 列が予約済み（未使用）
- ADR-032 で CSV/TSV の列スキーマが DB に永続化され、ADR-014/029 で
  Parquet プレビューが Storage に存在する
- ADR-039 の draft 導入により「ファイルをアップロードし、内容を見てから
  メタデータを書く」file-first フローが成立した

一方、素材の取得には環境差の罠がある。パイプラインが抽出したリソース
テキストは OpenSearch 環境では `kukan-contents` インデックスに入るが、
**PostgreSQL フォールバックでは `indexContent()` が no-op であり、抽出
テキストはどこにも保存されない**。検索インデックスを生成素材にすると
オンプレ環境で機能しなくなる。

## 検討した選択肢

### A) 完全自動型 — 公式メタデータ（notes / tags）を自動で書き換える

- 問題点: データカタログの provenance（誰が記述したか）を壊す。
  誤生成がそのまま公開される。不採用

### B) 別枠自動型 — パイプラインで自動生成し `aiSummary` / `aiTags` に保存

- 良い点: 放置データセットにも効く。予約済み列の設計意図とも一致
- 問題点: 全リソース処理時に LLM コストが常時発生する。「AI 生成」で
  あることの表示・検索上の扱いなど UX 設計が必要
- 判断: 初版では採らず、**将来の拡張として温存**する（列も温存）

### C) 提案型 — 手動トリガーで生成し、人が確認して採用 — 採用

- 生成はユーザーがボタンを押したときだけ（コスト予測可能）
- 提案はどこにも永続化せず、採用された値だけが通常の更新として保存される
  （human-in-the-loop、DB 変更ゼロ）

## 決定

**同期・ステートレスな提案 API を新設し、編集フォームからオンデマンドで
呼び出す。生成素材は検索基盤に依存せず、DB と Storage 原本から
オンデマンドに組み立てて使い捨てる。**

### 1. API

- `POST /api/v1/packages/{id}/suggest-metadata` を新設
- 同期呼び出し・ステートレス。提案は永続化しない（採用は通常の
  PATCH / PUT で行われる）
- 権限は package 更新権限と同一（draft は ADR-039 の creator 規則に従う）
- ユーザー単位のレート制限を設ける（LLM コストの上限管理）

### 2. 生成対象と応答形式

- `title` / `notes` / `tags` / 各リソースの `name`・`description` を
  **1 回の LLM コールで一括生成**する（コスト・レイテンシとも有利）
- 応答は JSON とし、Zod で検証する（パース失敗時は 1 回リトライ）
- UI はフィールド単位で「採用」を選べるため、生成粒度を分ける必要はない。
  既存メタデータの上書きは慎重であるべきなので、採用トグルは**全フィールド初期 OFF
  （オプトイン）**とする。採用したフィールドは適用前にインラインで直接編集もできる
  （タグはフォームと同じカンマ区切り）
- リソースは UUID ではなく 0 始まりのインデックスで参照し、応答は各インデックス
  必須キーのオブジェクトとする。小型ローカルモデル（4〜8B）は大きなプロンプト内で
  36 文字の UUID を破損させ配列を丸ごと落とすことがあるため、文法側で 1 リソース
  1 提案を強制する

### 3. 生成素材 — 検索インデックスに依存しない

| 素材                                      | 取得元                              | 対象フォーマット |
| ----------------------------------------- | ----------------------------------- | ---------------- |
| 既存メタデータ（title, notes, tags 等）   | DB                                  | 全部             |
| リソース名・format・サイズ                | DB                                  | 全部             |
| 列スキーマ（ADR-032）                     | `resource_pipeline.metadata.schema` | CSV / TSV        |
| サンプル行（先頭数行）                    | Parquet プレビュー（Storage）       | CSV / TSV        |
| 先頭 N KB のテキスト                      | Storage 原本（`downloadRange`）     | テキスト系       |
| 抽出テキスト先頭（2026-07-15 追記）       | Index ステップ成果物（Storage）     | PDF / Office 系  |
| マニフェストのパス一覧（2026-07-15 追記） | マニフェスト JSON（Storage）        | ZIP              |

- オンデマンド抽出するのはテキスト先頭 N KB のみで、**生成後は捨てる**
  （新たな保存・invalidation なし。常に現物と一致し、OpenSearch /
  PostgreSQL の環境差も生じない）
- 列スキーマと Parquet サンプル行は Extract ステップの**既存の永続成果物を
  読むだけ**であり、提案のための新たな生成・削除は行わない（プレビュー
  機能の成果物の借用。したがって CSV/TSV のサンプル行は Extract 完了が
  前提となる）
- `detectEncoding` を worker から shared へ移動して共用する。Range 読みの
  末尾で欠けたマルチバイト文字は除去する（既存の UTF-8 置換文字
  U+FFFD の末尾除去と同じ扱い）
- リソースは形式によらず全て name・description のスロットを与える（非表形式の
  PDF・Excel・画像もファイル名から名前を提案でき、description は content が無い
  場合ファイル名・フォーマットから推論する）。content（列スキーマ・サンプル行・
  先頭テキスト）は抽出可能なリソース（パイプライン完了 + CSV/TSV・テキスト系）に
  のみ付与し、content 抽出可能なものを優先してスロットに割り当てる
  （PDF / Office 系・ZIP は 2026-07-15 追記で content 対象に加えた）
- ZIP のマニフェスト（central directory がファイル末尾にあり先頭読みでは
  取れない）は初版では扱わない（2026-07-15 追記で対応）

### 4. `AIAdapter.complete()` の実装

ADR-034 と同じ配備パターンで4実装を提供する。

| 環境        | 実装                                             |
| ----------- | ------------------------------------------------ |
| AWS         | Bedrock Converse API（既定 Amazon Nova Lite 系） |
| オンプレ    | Ollama（日本語対応モデル）                       |
| OpenAI 互換 | Chat Completions                                 |
| AI なし     | NoOp — capability を返さず機能自体を非表示       |

- `GET /api/v1/site` の capability に提案可否を追加し、フロントは
  ボタンごと出し分ける（ベクトル検索対応状況の公開と同じパターン）
- 生成モデルは embedding とは**別モデル**とする（embedding 用の bge-m3 /
  Titan / Cohere は埋め込み専用であり生成に使えない）。設定は二層に分ける:
  **プロバイダ**（Bedrock / Ollama / OpenAI / NoOp）は資格情報・インフラ
  構成と一体のため環境変数、**モデル ID** は ADR-036 のランタイム設定とし
  管理画面（sysadmin）から再デプロイなしに切り替えられるようにする
  （未設定時はプロバイダ別の既定モデル）。embedding モデルが保存済み
  ベクトルとの整合性制約からランタイム変更できないのと異なり、生成モデルは
  提案を永続化しないため切り替えが安全に成立する。管理画面には接続テスト
  （小プロンプトの試行）を添え、未有効化・未 pull のモデル ID を即時検知
  できるようにする
- ランタイム設定の**候補**は環境変数 `AI_COMPLETION_MODELS`（カンマ区切り・
  先頭が既定）で全プロバイダ統一とする（2026-07-14 補足）。これはデプロイが
  **利用を承認したモデルの allow-list** であり、そのまま管理画面ピッカーの
  選択肢になる。サーバー側で利用可能でも（Ollama の pull 済み・OpenAI 互換の
  提供モデル）、リストに無いモデルは候補にしない — 「利用可能」と「利用承認」
  は別の判断であるため、サーバー列挙は行わない。リスト外の invoke は
  Bedrock では IAM（CDK がリストちょうどに付与）が、他プロバイダでは
  解決時の allow-list 検証が止める。Docker Compose では ollama-init が
  同じリストを pull するため、候補＝実行可能が起動時に揃う
- モデル選定は実装時に実測で確定する。**多言語対応を優先する**（日本語が
  当面の主対象だが海外展開を視野に入れるため、特定言語向けファイン
  チューンモデルは採らない）。既定: **Bedrock は Amazon Nova Lite 系**
  （実測で品質が基準を満たしたため、多言語・コスト・レイテンシのバランスに
  優れる低コストの Nova を既定に採用。Converse API の tool use で
  JSON 出力を強制。`jp.` クロスリージョン推論プロファイルで推論を
  東京/大阪リージョン内に閉じられるため国内データ処理要件にも対応可能。
  より高い品質が必要なら Claude Haiku 系以上を completionModels に
  追加してオプトインできる）、
  **Ollama は Gemma 4 系（E4B〜）**（140+ 言語、
  Apache 2.0、CPU 効率の良い実効パラメータ設計。structured outputs で
  JSON を強制）。日本語品質を最重視する環境向けの代替候補は Qwen3 系
  instruct。評価は ADR-034 と同様に小規模なゴールデンセット（既知の
  良メタデータを持つデータセット数件）で生成品質と JSON 準拠を確認する
- あわせて**既存データのサンプリングで品質を実測**する。主目的は品質の
  確認であり、**品質が基準を満たすモデルのうち最も低コストなものを採用する**
  （例: Nova Lite 級で品質が十分なら Haiku より優先する）。サンプルは
  フォーマット構成（CSV 主体・テキスト系・リソース無し）と規模が偏らない
  よう層化して選ぶ。副次的に、実在データの素材を組み立てたときの入出力
  トークン量の分布からコストとレイテンシも実測する（利用頻度が事前に
  読めないため、単価表ではなく実測で見積もる）
- CPU-only 環境（LGWAN 等）では実効 4B クラス（Gemma 4 E4B 等）を推奨する。
  CPU 推論は 1 回の提案に数十秒〜数分かかり得るため、suggest エンドポイントの
  タイムアウトはリバースプロキシ（Caddy 等）を含めて長めに設定する
  （実装時の確認事項）

### 5. タグの統制

素朴に生成させると free tag が氾濫する（孤立タグ GC の負荷にもなる）ため、
プロンプト側で制約する。

- サイト内の既存タグ（使用頻度上位 N 件）を候補としてプロンプトに渡し、
  「原則この中から選ぶ。適切なものが無い場合のみ新規タグを最大 2 個まで」
  と指示する
- 提案タグ数は合計 5 個程度を上限とする
- 候補の範囲（サイト全体か組織内か）は実装時に評価して決める

### 6. 入口と UI

- **入口①: draft ウィザード（ADR-039）** — リソース処理完了後、空の
  フォームに対して生成。file-first フローの中核
- **入口②: 公開済みデータセットの編集フォーム** — 現在値をプロンプトに
  含め、「空欄は埋め、既存の記述は尊重して不足を補う」改善案として生成
- UI は現在値と提案を並べて表示し、フィールドごとに採用する共通
  コンポーネントとする（新規では現在値の列が空になるだけ）
- リソース未処理のデータセットではボタンを disabled にする。生成は手動
  トリガーのみだが、**UI は利用を誘導する**: リソースが無い・未処理の間は
  「リソースをアップロードすると AI がメタデータを提案できます」の旨を
  disabled ボタンに添えて表示し、パイプライン処理の完了時には「AI に
  メタデータを提案させますか？」の誘導を表示する（いずれも LLM 呼び出しは
  クリックまで発生しない）
- 生成言語はサイトロケール準拠とする（ソース言語の自動判定は行わない）

## 結果

- メタデータ記入の負担が下がり、説明文・タグの充実度が上がる
- 提案は永続化されないため、DB マイグレーション・キュー・worker の
  変更が不要（`detectEncoding` の shared 移動を除きサーバー側は
  API パッケージに閉じる）
- NoOp 環境（AI なし）では機能が現れないだけで、他機能に影響しない
- LLM 呼び出しは手動トリガーのみのため、コストはレート制限で上限管理できる

## 追記: PDF / Office / ZIP のコンテンツ素材対応（2026-07-15）

将来の拡張としていた「ZIP マニフェスト・Office 系フォーマットの素材対応」を、
PDF を加えて実装に格上げする。

前提となる事実: worker の Index ステップ（ADR-021）は検索エンジンの有無に
関わらず officeparser によるテキスト抽出を毎回実行しており、PostgreSQL
フォールバックでは `indexContent()` が no-op のため結果を捨てている。
つまり抽出は既に全環境で走っていて、永続化の追加コストは実質ゼロである。
Parquet プレビューと同じ「パイプラインの永続成果物の借用」（§3）を
document 系と ZIP に広げる。

1. **worker（Index ステップ）**: document 系（officeparser が対応する
   PDF / DOCX / XLSX / PPTX / ODT / ODP / ODS / RTF。レガシー
   DOC / XLS / PPT は引き続き対象外）の抽出テキスト先頭 64KB を
   `previews/{packageId}/{resourceId}.txt`（UTF-8）として Storage に保存し、
   キーとサイズを `resource_pipeline.metadata`（`textHeadKey` /
   `textHeadBytes`）に記録する。suggest 側は DB の記録だけを信頼して
   読み、存在確認の往復や stale 成果物の誤読を避ける
2. **state ゲートの再構成**: これまで Index ステップは package が active で
   なければ丸ごとスキップしていた（draft をコンテンツ検索に出さない —
   ADR-039）。これを、抽出 + 成果物保存は draft でも実行し、検索エンジンへの
   投入だけを active でゲートする形に改める。AI 提案の主戦場は draft 編集
   （入口①）であり、publish するまで PDF/Office の素材が無いのでは
   本末転倒になるため。deleted / purging はこれまでどおりステップ全体を
   スキップする
3. **api（素材収集）**: document 系はこの成果物の先頭 N KB を、テキスト系の
   `downloadRange` と同型に読む。ZIP は Extract ステップ既存のマニフェスト
   JSON（`previewKey`）からパス一覧を読み、バイト数・エントリ数で
   クランプして素材化する（ZIP は worker 側の変更なし）

補足:

- 保存 64KB > 読み出し N KB（現行 16KB）とするのは、suggest 側の
  プロンプト予算を将来広げたとき、保存済みリソースの再処理なしに
  追従できるようにするため
- 文字コード判定は不要: officeparser はフォーマット内部構造から文字列を
  取り出すため（DOCX/XLSX 内部 XML は仕様上 UTF-8、PDF はフォントの
  エンコーディングマップをパーサーが解決）、抽出結果は常に JS 文字列で
  ある。成果物は UTF-8 で書き、suggest 側もテキスト系と異なり
  `metadata.encoding` / `detectEncoding` を参照せず **UTF-8 固定で
  デコード**する（JSON/GeoJSON の扱いと同じ）。64KB 切り詰めは既存の
  `truncateToByteLimit` と同様にマルチバイト文字の途中切断を除去する
- 素材の取得元は Storage 成果物 + DB のままであり、検索基盤に依存しない
  原則（§3）と OpenSearch / PostgreSQL の環境差なしは維持される。
  suggest 時の追加ダウンロード・パースも発生しない
- 成果物の本文を `resource_pipeline.metadata` に直接入れない理由:
  metadata は encoding 参照などで複数の API パスが丸ごと SELECT しており、
  リソースあたり数十 KB の膨張が無関係なクエリに波及するため
- クリーンアップ: フォーマット変更で document 系でなくなった場合は
  metadata のキーを null で上書きする（jsonb マージはキー削除が
  できない）。Storage 上の旧成果物は Parquet プレビューと同じ扱い
  （同名キーの上書き・package purge 時の `deleteByPrefix` で削除）

## 将来の拡張（本 ADR のスコープ外）

- 別枠自動型（選択肢 B）: `aiSummary` / `aiTags` への自動生成と
  「AI 生成」表示。列はこの用途のために温存する
- 品質監査（ADR-006, `qualityScore`）との連携: 説明が薄い・タグが無い
  データセットを検出し、編集画面の AI 提案へ誘導する導線
