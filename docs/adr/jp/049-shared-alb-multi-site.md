# ADR-049: マルチサイトの ALB 統合（サイト別 ALB → 共有 ALB + ヘッダールーティング）

## ステータス

**承認（Accepted）** — 2026-09-08 実装。ADR-041（マルチサイトデプロイ）を置換せず**拡張**する。
ADR-041 が整理表で「中間（段階的最適化）: ALB はまずサイト別、ホストベース
ルーティングによる共用は第二段階」として先送りした項目の、第二段階を確定する。

## コンテキスト

ADR-041 の原則は「時間課金される『箱』は共有、データと名前空間を持つ『論理
リソース』はサイト別」である。ALB は前者に該当するが、実装の第一段階では
SiteStack 側に置いた。現状 `WebServiceConstruct` がサイトごとに internal ALB を
1 本作り、CloudFront が VPC origin でそこへ入る（ADR-027）。

### ALB はサイト増分固定費の 4 割を占める

ap-northeast-1、$1=¥152、730h/月、scale=small（web 0.25 vCPU/0.5 GB × 1 タスク、
worker 0.25 vCPU/1 GB × 1 タスク）での概算:

| 項目                                | 単価      | サイトあたり月額 |
| ----------------------------------- | --------- | ---------------- |
| ALB 固定費                          | $0.0243/h | **$17.7**        |
| Fargate web（最小 1 タスク）        | —         | $11.3            |
| Fargate worker（最小 1 タスク）     | —         | $13.3            |
| Secrets Manager（auth + サイト DB） | $0.40/個  | $0.8             |
| **サイト追加の限界固定費**          |           | **約 $43**       |

ALB を 1 本に統合したときの削減:

| サイト数 | 現状（ALB 合計） | 統合後 | 削減（月）         |
| -------- | ---------------- | ------ | ------------------ |
| 2        | $35.5            | $17.7  | $17.7（約 ¥2,700） |
| 5        | $88.7            | $17.7  | $71（約 ¥10,800）  |
| 10       | $177             | $17.7  | $160（約 ¥24,300） |

LCU は使用量課金なので総量は変わらないが、低トラフィックのサイトが各々「最大次元の
丸め」を払わずに済むぶん微減する。ルール評価次元（1 LCU = 1000 evaluations/s）は
想定サイト数では誤差。ALB の急なスパイクに対するウォームアップも、集約したほうが
有利に働く。

### ルーティングキーの前提が ADR-041 当時から変わっている

ADR-041 は「ホストベースルーティング」を想定していたが、その後 ADR-027 で
CloudFront が前段に入り、`CdnConstruct` は `ALL_VIEWER_EXCEPT_HOST_HEADER` を
使っている。オリジンに届く Host は**ビューアのホストではなく VPC origin の
ドメイン名（ALB の DNS 名）**であり、Host ベースのルーティングはそのままでは
成立しない。成立させるには 3 つの behavior すべてのオリジンリクエストポリシーを
`ALL_VIEWER` に変える必要があり、さらに独自ドメインを持たないサイト
（`*.cloudfront.net` で公開する形）ではルーティングキーがディストリビューション
再作成で変わる。

## 検討した選択肢

### A) 現状維持（サイト別 ALB）

分離は最強で、1 サイトの ALB 設定ミスが他サイトに波及しない。ただし ADR-041 の
共有原則に照らすと、Aurora / OpenSearch / VPC を共有しておきながら ALB だけを
サイト別に持つ理由がない。サイト数に比例して $17.7/月が積み上がる。

### B) 共有 ALB + Host ヘッダールーティング

ADR-041 の当初想定。オリジンリクエストポリシーを `ALL_VIEWER` に変更し、
ビューアの Host をオリジンへ透過させる。ルーティングキーが「サイトの公開ドメイン」
という素直な形になる反面、上述のとおり CloudFront 設定の変更を伴い、独自ドメインを
持たないサイトで不安定になる。キャッシュキーへの影響（Host をキャッシュポリシーに
含めるかどうか）も検討事項として残る。

### C) 共有 ALB + オリジンカスタムヘッダールーティング（採用）

CloudFront のオリジン定義に `X-Kukan-Site: kukan-<env>-<site>` を付与し、ALB の
リスナールールを `http-header` 条件で分岐させる。オリジンリクエストポリシー・
キャッシュポリシー・CF Function は一切触らない。ドメインの有無に依存しない。

### D) CloudFront も 1 ディストリビューションに統合

CloudFront には時間課金がないため削減効果がない一方、IP 制限・Basic 認証
（CF Function）・WAF・キャッシュポリシーはディストリビューション単位であり、
統合するとサイト別のエッジゲートを失う。不採用。

### E) ALB を廃す（NLB 置換 / CloudFront から直接 ECS）

CloudFront VPC origin のエンドポイントは ALB / NLB / EC2 インスタンスに限られ、
ECS サービスへ直接は向けられない。NLB は ALB と同水準の時間課金で、かつ L7 の
ヘッダー条件を持てないため統合の受け皿にならない。不成立。

## 決定

**選択肢 C を採用する。ALB と CloudFront VPC origin を SharedStack に移し、
ターゲットグループとリスナールールを SiteStack に置いて、オリジンカスタム
ヘッダーでサイトへ振り分ける。**

1. **SharedStack**: internal ALB 1 本、HTTP:80 リスナー（`open: false`、
   デフォルトアクションは 404 の固定応答）、`cloudfront.VpcOrigin` 1 個
2. **SiteStack**: `ApplicationTargetGroup` 1 個 + リスナールール 1 本
   （条件 `http-header X-Kukan-Site = kukan-<env>-<site>`）。ヘルスチェック・
   オートスケーリングはサイト別のまま
3. **ルーティングキーはオリジンカスタムヘッダー**。値はサイトキー
   （`envPrefix()` の結果）。ALB は internal かつ SG が CloudFront マネージド
   プレフィックスリスト限定（`NetworkConstruct`）なので、**このヘッダーは分離キーで
   あってセキュリティ境界ではない**。オリジン検証を兼ねさせない
4. **リスナールールの優先度は `sites[]` のインデックスから採番しない** — サイトの
   削除・並べ替えで既存サイトの優先度がずれ、直列デプロイ（ADR-041）の途中で
   重複が生じてデプロイが落ちる。既定は**サイト名の安定ハッシュ（FNV-1a、
   1000–49999）**とし、`SiteConfig.albPriority` で明示上書きできる（明示値は
   1–999 のみ受け付け、派生帯と構造上衝突しない）。`validateSites()` が有効値の
   一意性を検証し、衝突時は**追加した側**に明示指定を求めるエラーを出す（実装時に「必須の明示宣言」から緩和 —
   既存の `sites: [{ name }]` 形の設定・文書・テストを壊さないため）
5. **VPC origin は共有側に 1 個だけ置く。** サイトごとに作ると同一 ALB に対して
   ENI 群が重複し、アカウントの VPC origin クォータ（既定 25、引き上げ可）を
   サイト数分消費する。共有側の制約は「同一 VPC origin に関連付けられる
   Distribution 50（引き上げ手段なし）」で、これが 1 環境あたりのサイト数上限になる
   （スケール上限の節）
6. **単一サイト形状（`KukanStack`）は無変更。** `WebServiceProps` に任意の
   `sharedListener` を足し、未指定なら現行のコードパス（自前 ALB + `addTargets`）を
   そのまま通す。構築ツリーのパスが変わらないため、単一サイトのゴールデン
   スナップショットは 1 行も動かない（ADR-041 のドリフトガードを維持）

### スタック間参照（SSM、ADR-041 の方式を踏襲）

CloudFormation Export ではなく SSM パラメータで疎結合にする。

| パラメータ                 | 用途                                                      |
| -------------------------- | --------------------------------------------------------- |
| `alb/listener-arn`         | SiteStack がリスナーをインポートしてルールを足す          |
| `alb/dns-name`             | CloudFront オリジンの `DomainName`（VPC origin でも必須） |
| `cloudfront/vpc-origin-id` | SiteStack が VPC origin をインポートする                  |

### CDK 上の確定事項（aws-cdk-lib 2.268 で確認済み）

- **インポート済みリスナーでは `addTargets()` が例外になる**。`ApplicationTargetGroup`
  を SiteStack 側で明示生成し、`addTargetGroups(id, { targetGroups, priority,
conditions })` で紐付ける。条件を付けるときは `priority` が必須
- **`scaleOnRequestCount` は共有 ALB 上のターゲットグループでも成立する**。CDK は
  TG の `LoadBalancerArns` 属性を `Fn::Split` で分解してリソースラベルを組むため、
  SSM 由来のトークン ARN でも解決できる
- **VPC origin のインポートは `cloudfront.VpcOrigin.fromVpcOriginId()` +
  `origins.VpcOrigin.withVpcOrigin(origin, { domainName, customHeaders })`**。
  インポートしたオリジンは `domainName` 属性を持たないため、ALB の DNS 名を
  明示で渡す（上表の `alb/dns-name`）
- **セキュリティグループは引き続き `NetworkConstruct` が単一の管理点**。SiteStack は
  ALB / web SG を `mutable: false` でインポートしているため、リスナールール生成や
  ECS サービスの TG 登録が SG を書き換えることはない

## スケール上限（サイト数を増やしたとき、何が先に効くか）

**共有 ALB 自体は上限にならない。** 既定クォータはルール 100/ALB・ターゲットグループ
100/ALB・ターゲット 1000/ALB（いずれも引き上げ申請可）で、1 サイトの消費は
「ルール 1 + TG 1 + `web.maxSize` ターゲット」である。scale=small なら素で 100 サイト
前後まで載る。

先に効くのは次の制約であり、いずれも本 ADR で悪化しない（VPC origin は改善する）。

| 制約                                                                                                                                                        | 効き始める規模                                                   | 対処                                                                                                                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DB 接続数**（`dbPool.webMax × web.maxSize + dbPool.workerMax × worker.maxTasks` の総和 vs `max_connections`）                                             | **最初に当たる。** ADR-041 が synth 時に検証し警告・エラーを出す | maxACU 引き上げ（静的パラメータのため「ACU 変更 → 全インスタンス再起動 → サイト追加」の二段階）、プール縮小、共有クラスタの分割                                                     |
| **CloudFront のアカウント単位クォータ**: キャッシュポリシー 20 / CloudFront Functions 100 / ディストリビューション 500（既定値、引き上げ申請可）            | キャッシュポリシーが概ね **20 サイト**で当たる                   | `HtmlCachePolicy` の値はサイト非依存なので、環境で 1 つに共有できる（残課題 3）。CF Function は IP 制限・Basic 認証の内容がサイト別で共有できないため、100 サイト時点で引き上げ申請 |
| **同一 VPC origin に関連付けられる Distribution: 50**（既定値、**引き上げ手段なし**）— 全サイトが環境の共有 VPC origin を使うため、**1 環境のサイト数上限** | **50 サイト**（硬い上限）                                        | `validateSites` が 51 サイト目で synth エラー。超える場合は環境（共有クラスタ）を分ける                                                                                             |
| **共有 OpenSearch のシャード数・ヒープ**                                                                                                                    | medium 以上でも数十サイトで再検討                                | ADR-041 の同居ポリシー（SLA の近いサイトだけを共用、超えたら別ドメインへ退避）                                                                                                      |
| **パブリックサブネットの IP**（/24 × 2 AZ ≈ 500、ローリング更新中は倍化）                                                                                   | 100 サイト規模                                                   | サブネット CIDR の拡大（VPC 再作成を伴うため、大規模化が見えた時点でブルーグリーン）                                                                                                |
| **直列デプロイの所要時間**（ADR-041）                                                                                                                       | サイト数に比例                                                   | dev のサイト数を絞る。Wave 並列化は接続数バジェットを複数サイト同時更新分に改めるのが前提                                                                                           |

ALB の LCU にはルール評価次元（1 LCU = 1000 evaluations/s）がある。ルールは優先度順に
評価されるため 1 リクエストあたり平均 N/2 回で、50 サイト・100 req/s なら 2500
evaluations/s = 2.5 LCU 相当になる。ただし LCU は 4 次元の最大値で課金されるため、
その規模では通常は処理バイト数・アクティブ接続数の側が上回り、支配的にはならない。

VPC origin をサイト別に作らない（決定 5）ことで、アカウントの VPC origin クォータと
ENI の重複はサイト数に依存しなくなる。代わりに「同一 VPC origin あたり 50 Distribution」
が 1 環境の硬い上限になる — `validateSites` が synth 時にエラーにする。

## トレードオフ

- **エッジのセキュリティ境界は動かない**: WAF は ADR-027 で CloudFront
  （`CLOUDFRONT` スコープ、`KukanGlobalStack` が us-east-1 に作成し
  `CdnConstruct` が `webAclId` で紐付け）に一本化済みで、ALB には association が
  ない。IP 制限・Basic 認証（CF Function）も含め、サイト別のエッジゲートはすべて
  共有 ALB より**上流のディストリビューション単位**に残る。ALB を共有しても審査点は
  サイトごとに独立したままで、共有 ALB に届く時点で既に通過済みのトラフィックである
- **爆発半径の共有**: ALB 1 本の障害・設定ミスが全サイトへ波及する。Aurora /
  OpenSearch を共有している時点で同じ性質であり、ADR-041 の同居ポリシー
  （SLA 要求が近いサイト同士だけを共用する）がそのまま適用される
- **デプロイ結合は片側だけ**: ルールと TG は SiteStack にあるため、**サイトの追加・
  削除で SharedStack に触れない**。逆に ALB 自体（リスナー、SG、属性）の変更は
  全サイト同時になる
- **観測性の粒度**: ALB 単位のメトリクス（`RequestCount`、`TargetResponseTime`）が
  サイト混在になる。サイト別は TargetGroup ディメンション経由で取れる。将来
  アクセスログを有効にする場合は 1 バケットに混在し、`target_group_arn` フィールドで
  分離する
- **サイト間の相互影響**: 1 サイトの異常トラフィックが ALB のスケーリング中に
  他サイトのレイテンシへ影響しうる。逆に平常時は集約による事前ウォームアップが効く
- **クォータ**: ルール 100/ALB、ターゲットグループ 100/ALB、ターゲット 1000/ALB
  （いずれも引き上げ申請可）。想定サイト数に対して十分な余裕がある
- **可逆性は保たれる**: 特定サイトを専用 ALB へ戻すのは「TG を新 ALB に付け替え +
  CloudFront オリジン差し替え」で済み、ADR-041 の「同居は不可逆な決定ではない」
  性質を壊さない
- **優先度は共有リスナー上のデプロイ時資源**: `validateSites` が見られるのは設定上の
  最終状態だけで、稼働中のルールが持つ値は見えない。**稼働中サイトの優先度を別の
  稼働中サイトの値に付け替える**（入れ替え）と、直列デプロイで先に更新される
  スタックが `PriorityInUse` で失敗しロールバックする。また `sites[]` から外した
  サイトのスタックを destroy していなければ、そのルールは共有リスナーに残り続け、
  同じ値に解決する新サイトのデプロイを塞ぐ（サイト削除は「スタックの destroy →
  設定から除去」の順）
- **共有 ALB の置換は全サイトに波及する**: 共有 ALB（リスナー）が置換されると
  各サイトのルールは連鎖削除され、SiteStack を直列で再デプロイするまで応答しない。
  VPC / クラスタと同じく「置換しない箱」として扱う

## 移行

稼働中のマルチサイト環境には既存 ALB があるため、切り替えを伴う。

1. **SharedStack に ALB + VPC origin + SSM を追加してデプロイする。** 既存サイトは
   無変更・無停止（新しい ALB は誰も向いていない状態で立つ）
2. **サイトごとに直列で切り替える**（ADR-041 の直列デプロイ前提のまま）。
   検証用サイト → 本番サイトの順とする

**切替デプロイには数分間の 503 リスクがある。** CloudFormation は ECS サービスの
ターゲットグループ差し替えと CloudFront ディストリビューションの更新の順序を
保証しないため、旧 ALB から切り離された後・新オリジンが伝播する前の窓が開きうる。

- **IP 制限や Basic 認証で閉じた検証環境**: メンテナンス時間帯での一発切替でよい。
  切り戻しは revert 再デプロイ（ALB の再作成に数分）
- **公開中の本番サイト**: 二段階が必要になる。(a) 新 TG を追加登録して旧 TG と
  両系待受にし、CloudFront オリジンを共有 VPC origin へ切り替える、(b) 別デプロイで
  旧 ALB と旧 TG 登録を落とす。ECS サービスは複数のロードバランサーを登録できるため、
  (a) の間は旧経路が生きたままになる。**この二段階は未実装**（残課題 4）— 本 ADR の
  実装時点で共有 ALB 導入前のマルチサイト環境は閉じた検証環境だけであり、一時
  フラグと二重登録のコードを本体に残す価値がなかった。公開サイトを載せたまま
  切り替える必要が生じた時点で、一時的な `SiteConfig` フラグとして実装する

切替の運用注意（`docs/specs/jp/phase4-deploy.md` にも記載）:

- サイトスタックは新しい SSM パラメータ（`alb/*`, `cloudfront/vpc-origin-id`）を
  デプロイ時に解決するため、**SharedStack を先に更新するまでサイト単体の
  `cdk diff` / `cdk deploy` は失敗する**（パラメータ未存在）
- pipeline は `sites[0]` から順に切り替える。切替順を選びたい（検証サイト → 本番
  サイト）場合は、pipeline に流す前に手動で切り替えておく
- 切替後に旧 ALB / VPC origin が削除されたことを確認する。CloudFormation は
  クリーンアップ段階の削除失敗をスタック失敗にせず、残った資源は孤児になる

## 影響

- `infra/lib/shared-stack.ts`: ALB・リスナー・VPC origin・SSM パラメータ 3 本の追加
- `infra/lib/site-stack.ts` / `composition.ts`: 共有リスナーと VPC origin の
  インポート、`SiteSurface` への受け渡し
- `infra/lib/constructs/web-service.ts`: 任意の `sharedListener` 分岐
  （未指定時は現行パスのまま）
- `infra/lib/constructs/cdn.ts`: 任意の VPC origin インポートとオリジンカスタム
  ヘッダー
- `infra/lib/config.ts`: `SiteConfig.albPriority`（任意）と `resolveAlbPriority()`、
  `validateSites()` での一意性検証
- `infra/lib/constructs/shared-alb.ts`: ALB・リスナー・VPC origin をまとめた
  `SharedAlbConstruct`（新規）
- `infra/lib/__tests__/`: マルチサイトのスナップショット更新（単一サイトは不変で
  あることがガード）。ルール優先度重複の synth エラーテストを追加
- `docs/specs/jp/phase4-deploy.md` / `en`: マルチサイト構成手順に共有 ALB と
  `albPriority` を追記

## 残課題

1. **worker の共有化**（ADR-041 が将来最適化としている、SQS メッセージへのサイト
   識別子付与 + 接続の動的解決）。本 ADR 適用後のサイト増分固定費 $25 のうち
   $13.3 が worker タスクであり、次に効く一手になる
2. **ALB アクセスログ**の有効化は本 ADR のスコープ外。有効にする場合は共有バケット
   1 本 + `target_group_arn` によるサイト分離を前提とする
3. **`HtmlCachePolicy` の環境内共有**。値がサイト非依存であるにもかかわらずサイト別に
   作っており、CloudFront のアカウント単位クォータ（既定 20）に約 20 サイトで当たる。
   本 ADR とは独立に実施できる小さな変更で、実装時に同一 PR で片付けるかは判断する
4. **公開サイト向けの二段階切替（両系登録の一時フラグ）は未実装**。必要になった時点で
   実装する（移行の節）
5. **非 AWS 環境（Docker Compose）は影響なし**。ADR-041 のとおりエッジは Caddy 1 本の
   バーチャルホストで、そもそも統合済みである

## 関連

- ADR-041（マルチサイトデプロイ）: 本 ADR はその「第二段階」を確定する拡張。置換ではない
- ADR-027（CloudFront 再導入）: VPC origin と `ALL_VIEWER_EXCEPT_HOST_HEADER` が
  ルーティングキー選択の前提
- ADR-020（Web = ECS Fargate + ALB）: ALB を自前管理する構成そのものは維持する
- ADR-031（マルチ環境デプロイ）: 環境ごとに共有 ALB が 1 本になる
- ADR-042（マルチブランドビルド）: サイト別の web イメージは変わらず、ALB の共有と直交する
