# ADR-051: 一太郎文書のテキスト抽出（自前の複合文書パーサ、Ver.8 以降の非圧縮のみ）

## ステータス

**採用（Accepted）** — 2026-09-11 起案、2026-10-08 実装に合わせて改訂し採用。

一太郎文書（`.jtd` / `.jtt`）の**本文を抽出し、ほかの文書と同じ文書テキストの成果物に書く**。
抽出は既製のライブラリに頼らず、複合文書（OLE2）コンテナを読む小さなパーサを worker に置く。
対象は一太郎 Ver.8 以降の非圧縮形式に限り、圧縮形式（`.jtdc` / `.jttc`）と Ver.7
以前の形式は対象外とする。**原本の見た目のプレビューは作らない**。抽出したテキストの
プレビューは、ほかの文書と同じく出る。

> **起案時からの改訂（2026-10-08）。** 起案のあと、文書の本文は Interpret が抽出して
> 位置付きの成果物（`text.ndjson.zst`）に書き、Index・text head・抽出テキストの
> プレビュー・MCP の本文取得がそれを読む形に変わった。また古い Office 形式の
> 抽出で、複合文書を読む自前の部品ができた。これに合わせて次を変えた。
>
> - 抽出の置き場所は Index の officeparser の差し替えでなく、Interpret の文書テキスト抽出（決定 2）
> - npm の `cfb` は足さず、古い Office と共有する自前の複合文書の読み手を使う（選択肢 B）
> - 本文の範囲は `TextV.01` の長さで決め、レコードは長さで読み飛ばす（決定 3）。OpenJTD の
>   仕様ノート RFC 0003 の起案後の観察による
> - 読み仮名・テンプレートの指示文は、その場でなく行の末尾に置く（決定 5）
> - 解析サイズの上限は一太郎だけには置かない（決定 6）
> - 抽出テキストのプレビューは出す（決定 7。残課題 4 が解消）

## コンテキスト

### 現状

一太郎は日本の官公庁・自治体で現役であり、様式や公開文書が `.jtd` で配布されている。
KUKAN は今これを次のように扱っている。

- 拡張子 `jtd` は `FORMAT_MAP` に無い。フォーマット名は既定の大文字化で `JTD` になり、
  MIME は `application/octet-stream` になる
- Index ステップの `getContentType` はどの述語にも当たらず `null` を返す。コンテンツ
  索引に載らず、フォーマットが変わったときの後始末だけが走る
- text-head 成果物ができないので、AI メタデータ提案（ADR-040）の材料にもならない
- プレビューは「利用できません」になる

アップロードもダウンロードも通る。**中身が読めないだけ**の状態である。

### 既存の document 経路

PDF / DOCX / XLSX / PPTX / ODT / ODP / ODS / RTF は `ContentType` が `document` で、
Index ステップが officeparser でテキストを抜き、先頭 64 KB を text-head 成果物として
ストレージに書き、本文を 500 KB ごとに分割して検索エンジンへ投入する。下書きの
データセットでは検索投入を止めて成果物だけを作る（ADR-039 / ADR-040 追記）。

officeparser は一太郎を**明示的に拒否する** — 対応形式の一覧を挙げて例外を投げるので、
形式を足すだけでは経路に乗らない。抽出関数を差し替える必要がある。

### 形式

Ver.8 以降の `.jtd` は複合文書（OLE2 / CFB）である。

- 本文は `DocumentText` ストリームにあり、先頭に `SsmgV.01` の署名を持つ
- 文字は UTF-16BE。制御コード `0x001F` の後がテキストラン、`0x001D` から `0x001E` が
  差し込み文字（ルビの親文字、差し込み欄など）
- 符号化が形式で決まっているので、CSV や TXT と違いエンコーディング検出は要らない
- 新しい版はレイアウト枠の文字を `LayoutBoxText` に分ける。一太郎 2022 で作られた
  帳票では、見出しの一部がこのストリームにしか無かった

一方、Ver.7 以前（`.jbw` / `.jfw` など）は複合文書ですらない別形式で、先頭が `DOC\0`、
本文は Shift_JIS の平文である。圧縮形式（`.jtdc` / `.jttc`）は複合文書の中に LHA の
lh5 で圧縮した複合文書が入る二重構造になる。

### 既製の抽出手段が無い

| 手段              | 状況                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| Apache Tika       | 対応形式一覧に一太郎が無い                                                                      |
| LibreOffice       | 入力フィルタを持たない。OpenOffice 用拡張は 2009 年更新の Windows 専用で、近年の版では動かない  |
| xdoc2txt          | Windows 専用。商用利用は作者への連絡が必要                                                      |
| OpenJTD（`rjtd`） | Apache-2.0 の Rust 実装。2026 年 6 月に始まった逆解析プロジェクトで、本文抽出は動くが層は未解読 |

Linux のサーバーで動く既製品は無い。変換系（一太郎本体、一太郎ビューア、商用の
PDF 変換 API）はすべて Windows と一太郎ライセンスを前提とする。

### 測ったこと

公的機関が公開している `.jtd` 5 本（一太郎 2004 世代 4 本、一太郎 2022 世代 1 本）で、
npm の `cfb`（Apache-2.0、依存 2 個、展開 370 KB）を使う試作と OpenJTD の `rjtd cat`
を比較した。空白を除いた文字バイグラムでの一致は次のとおり。

| サンプル      | 再現率 |   精度 |
| ------------- | -----: | -----: |
| 2004 世代 (1) |  100 % |  100 % |
| 2004 世代 (2) | 97.5 % | 99.7 % |
| 2004 世代 (3) | 81.0 % | 97.0 % |
| 2004 世代 (4) |  100 % | 99.8 % |
| 2022 世代     | 96.2 % | 79.2 % |

再現率の欠けは差し込み文字の選別規則の差である。2022 世代の精度が低いのは、試作が
`LayoutBoxText` も読んでいる分で、欠落ではなく上積みである。処理時間は常駐プロセス
内で 80〜100 KB あたり 0.4〜0.8 ミリ秒で、ダウンロードや索引投入に対して無視できる。

抽出結果には書式データ由来のバイナリがテキストランとして混ざる。これは OpenJTD でも
同じ割合で混入し、「`0x001F` の後を本文とみなす」という規則そのものの限界である。
仮名・漢字・全角・ASCII の比率が半分未満の行を捨てる方式を試したところ、次のように
分離できた。

| サンプル      | 残った文字 | 捨てた文字 | 残ったノイズ |
| ------------- | ---------: | ---------: | -----------: |
| 2004 世代 (1) |        304 |          0 |            1 |
| 2004 世代 (2) |        621 |         82 |            0 |
| 2004 世代 (3) |        132 |          1 |            0 |
| 2004 世代 (4) |        326 |         92 |            0 |
| 2022 世代     |        419 |         35 |            1 |

捨てられたのは同じ並びを繰り返すバイナリ行だけで、本文は 1 行も失われなかった。
しきい値を 0.5 から 0.8 まで振っても結果は変わらない。ノイズ行の妥当文字率がほぼ 0、
本文行がほぼ 1 で、間に広い余白があるためである。

## 検討した選択肢

### A) 対象外のまま、拡張子だけ登録する

`FORMAT_MAP` と MIME を足して「一太郎」と表示できるようにし、索引は入れない。費用は
ほぼ無いが、一太郎で配られた文書は全文検索に一切出てこないままになる。カタログとして
「持っているのに探せない」状態が続く。

### B) 自前の複合文書パーサを置く（採用）

複合文書を開き、`DocumentText` と `LayoutBoxText` を読む関数を worker に置く。起案時は
npm の `cfb` を足す想定だったが、古い Office 形式（XLS・DOC・PPT）の抽出のために自前の
複合文書の読み手（`legacy/compound-file.ts`）ができたので、それを共有し、依存は足さない。
形式の解読は OpenJTD の公開仕様ノートに依拠し、独自に逆解析はしない。

### C) OpenJTD を WASM か外部プロセスで使う

抽出品質は同等（上の測定は OpenJTD を基準にしている）。ただし Rust 1.88 以上の
ビルド環境か 3.7 MB の WASM を持ち込むことになり、バージョン 0.0.1 のプロジェクトに
パイプラインを依存させる。抽出規則そのものは数十行で、借りる価値が依存に見合わない。
公開仕様ノートを参照する形で成果だけを借りる。

### D) Windows の変換サーバーで PDF 化してから索引する

一太郎と商用の PDF 変換 API を入れた Windows Server を別に立て、worker から変換を
依頼する。見た目の再現が要るならこれしかないが、一太郎と変換 API のライセンス、
Linux 一本だったデプロイに Windows が増えること、変換 API が一太郎を直列にしか
扱えないことを抱える。索引だけが目的なら費用が釣り合わない。

## 決定

B を採る。以下を決定に含める。

### 1. 対象は Ver.8 以降の非圧縮形式に限る

`.jtd` と `.jtt` を扱う。`.jtdc` / `.jttc` と Ver.7 以前は**拡張子とフォーマット名だけ
登録し、抽出はしない**。理由は形式が別物だからである。圧縮形式は LHA lh5 の展開器が
Node.js に無く、Ver.7 以前は複合文書ですらない。登録だけ先にするのは、少なくとも
「これは一太郎である」と表示でき、後から抽出を足すときに既存データの意味が変わらない
ためである。

### 2. ほかの文書と同じ文書テキストの成果物に書く

`isDocumentFormat` に `jtd` / `jtt` を加える。Interpret が文書テキストの成果物を書き、
Index（`ContentType` は `document`）、text head（AI メタデータ提案と抄録の材料）、下書きでの
扱い、抽出テキストのプレビュー、MCP の本文取得が**すべて既存のまま**それを読む。新しい
`ContentType` は足さない — 検索側から見て PDF と一太郎を区別する理由が無い。

AI メタデータ提案の対象に自動的に入るのは**意図した効果**である。

成果物の位置情報はページも見出しも持たない 1 ブロックになる。ページの区切りや段落の
見出しを示す情報は別のストリームにあり、まだ解読されていない。

### 3. 読むストリームは `DocumentText` と `LayoutBoxText` の 2 つ

`LayoutBoxText` を読むのは、新しい版の帳票で見出しがそこにしか無いためである。
両方を連結して 1 本のテキストとして扱い、順序は `DocumentText` を先にする。

読み方は OpenJTD の仕様ノート RFC 0003 に従う。

- ストリームの先頭が `SsmgV.01` で、`TextV.01` の区画があれば、その後の 4 バイト
  （ビッグエンディアン）が本文の長さ（UTF-16 単位）を示す。**本文はその長さで終わり**、
  後ろの書式の区画は読まない。区画が無い古い版は、ストリーム全体を下の規則で読む
- 本文は `0x001F` の後から次の制御コードの手前まで。改行・CR・タブでは途切れない
- `0x001C` から始まるレコードは、2 単位目が種類、3 単位目が `0x001F` までの長さを示す。
  **レコードは長さで読み飛ばす** — 引数には印字できる値も `0x001D` も入るので、制御コードを
  一つずつ見る読み方では書式が本文に混ざる
- 文字以外のレコードが本文の間にあれば、表のセルの区切りとしてタブにする。`0x000E`（表の行）と
  `0x000C`（改ページ）は改行にする

### 4. 行単位の妥当性フィルタで書式データを落とす

抽出した各行について、空白を除いた文字のうち**日本語の文書に使われる範囲に入る
比率が 0.5 未満なら、その行を捨てる**。範囲は ASCII、記号（句読点・矢印・丸数字・罫線・
図形）、CJK の記号・仮名・漢字（拡張と BMP の外を含む）、全角・半角形である。起案時の
「仮名・漢字・全角・ASCII」に記号を足したのは、丸数字や罫線だけの行が本文から落ちないため
である。文字単位ではなく行単位にする理由は 2 つある。

- 文字単位で落とすと、本文中に紛れた記号や外国語をも削る。行単位なら、実際に
  ギリシャ文字を含む本文は残り、バイナリだけの行が消える
- 中黒（`・`）と長音記号（`ー`）は Unicode の Script 属性が Common で、片仮名として
  扱われない。Script 属性による判定は本文を壊す。**符号位置の範囲で判定する**

しきい値 0.5 は測定で得た余白の中央を採ったもので、0.5〜0.8 のどこでも結果は同じ
である。長さ付きの区画を読む新しい版では、決定 3 の読み方で書式はほぼ混ざらず、
このフィルタが効くのは主に区画の無い古い版である。

### 5. 差し込み文字は索引に含め、読み仮名は行の末尾に置く

差し込みは種類 1 のレコードで、`0x001D`〜`0x001E` の区間に文字を持つ。4 単位目が 0 なら
表に見える文字（ルビの親文字、差し込み欄の「○○○」など）、1 なら読み仮名かテンプレートの
指示文である。KUKAN は**選別して捨てず、両方を索引に入れる**。ただし後者は**その場に置かず、
行の末尾に回す**。その場に置くと「午后の授業」が「午后ごごの授業」になり、語句での検索に
当たらなくなるためである。行の末尾にあれば、読み仮名でも検索に当たる。

### 6. 一太郎だけの解析サイズの上限は置かない

複合文書の解析はファイル全体をメモリに載せる。起案時は一太郎だけに解析の上限を置く
つもりだったが、抽出は重い処理の子プロセス（ADR-059）で行い、取得上限（100 MB）と
本文の総量の上限（`DOCUMENT_TEXT_MAX_BYTES`、256 MB）がすべての文書にかかる。一太郎の
帳票は 1 MB 以下が通例で、形式ごとの上限を足す理由が無くなった。

### 7. 原本のプレビューは作らず、抽出テキストのプレビューを出す

原本の見た目を再現する手段は現時点で無い。OpenJTD の PDF 出力は白紙（内容ストリームが
白い矩形のみ）、SVG 出力は行送り固定のテキスト流し込みで、罫線も枠も出ない。帳票が中心と
いう一太郎ファイルの性質を考えると、罫線の無いプレビューは原本と別物に見える。

抽出したテキストは、ほかの文書と同じく「抽出テキスト」のプレビューで見せる。起案時は
「別の判断」としていた（残課題 4）が、文書テキストの成果物とそのプレビューが全文書に
共通の仕組みになったので、一太郎だけ外す理由が無い。罫線の無いテキストであることは、
ほかの文書の抽出テキストと同じである。

## トレードオフ

- **形式仕様が確定していないものに依存する。** 依拠しているのは観測に基づく公開
  仕様ノートであり、ジャストシステムの仕様書ではない。未知の版で抽出が崩れる可能性が
  あり、そのときは静かに文字数が減る形で現れる。テストは固定の入力に対する回帰しか
  見られない
- **表の構造は失われる。** 帳票のセルは文字列として順に並ぶだけで、行と列の関係は
  残らない。全文検索には足りるが、表として使うことはできない
- **ノイズは完全には消えない。** 行単位フィルタを通しても、本文に紛れた 1〜2 文字の
  記号は残る。検索の邪魔にはならないが、AI 提案の材料には雑音として入る
- **圧縮形式が残る。** `.jtdc` は一太郎 10 以降で選べる保存形式で、配布物に混ざる
  可能性がある。対象外にした以上、利用者には「一太郎（圧縮）は索引されない」ことが
  見える必要がある

## 影響（実装した場所）

- `packages/shared/src/formats.ts`: `FORMAT_MAP` と `MIME_MAP` に `jtd` / `jtt`（および
  対象外として `jtdc` / `jttc`）。MIME は `application/x-js-taro` — IANA 登録は無いが、
  PRONOM と Apache の慣例で使われている。`isDocumentFormat` に `jtd` / `jtt`、
  `FORMAT_SIGNATURES` に複合文書の署名
- `apps/worker/src/pipeline/interpret/document/legacy/jtd.ts`（新規）: 複合文書から本文を
  取り出す純関数。Buffer を受けて文字列を返し、ストレージにも DB にも触らない
- `apps/worker/src/pipeline/interpret/document/document-text.ts`: 形式で分岐し、一太郎を
  上の関数に回す
- `apps/worker/src/__tests__/`: 抽出の単体テスト。**入力はテスト内で組み立てる** —
  署名・長さ付き区画・レコード・差し込み・書式の区画を持つ複合文書を組み立てれば、
  第三者の文書をリポジトリに置かずに規則を固定できる
- `packages/shared/src/__tests__/formats.test.ts`: 述語の追加分
- `CLAUDE.md`: パイプライン フォーマット別処理マトリクスに行を足す

実ファイルでの確認（2026-10-08）: 北海道・埼玉県・徳島県が公開している様式 21 本
（長さ付き区画のある版 15 本、無い版 6 本）で、すべてから本文が取れた。書式由来の
雑音が残ったのは、記号フォントのチェック印が文字として入っている 1 箇所だけだった。

## 残課題

1. **圧縮形式を後から足すか。** lh5 の展開を自前で書くか、対象外のままにするかは、
   実際に `.jtdc` が持ち込まれる頻度を見てから決める。構造は公開仕様ノートにある
2. **Ver.7 以前を後から足すか。** 本文が Shift_JIS の平文なので抽出の実装自体は軽い
   が、Ver.8 の登場から 29 年経っており、実ファイルでの検証ができていない
3. **ページと見出し。** 成果物は位置情報の無い 1 ブロックになる。ページの区切りや
   段落の書式は別のストリーム（`DocumentTextPositionTables` など）にあり、解読が進めば
   PDF と同じくページや見出しで引けるようにできる
4. **原本をブラウザで描く手段。** 起案のあと、一太郎をブラウザだけで表示するオープンソースの
   エンジン（WebAssembly、MIT）が公開された。罫線の表やルビも描くが、始まったばかりの
   プロジェクトである。試作して表示の質・大きさ・CSP への影響を確かめ、採用するなら決定 7 を
   改訂する
5. **利用者への見え方。** 一太郎が索引される形式であること、圧縮形式が対象外で
   あることを、どこでどう伝えるか
