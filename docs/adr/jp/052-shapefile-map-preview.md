# ADR-052: シェープファイルの地図プレビュー（ZIP 内の SHP を GeoJSON として解釈する）

## ステータス

**提案（Proposed）— 着手を保留**

大規模なシェープファイルの扱い（出力の上限、上限に当たったときに打ち切るか簡略化するか、
産物を GeoJSON のままにするか空間索引を持つ形式に替えるか）が決まるまで実装しない。
本 ADR は検討と実測の記録として残す。

シェープファイル一式を収めた ZIP を、Interpret ステージで **GeoJSON に解釈して
プレビュー生成物として書き出す**。表示は既存の GeoJSON 地図プレビューに載せる。
解釈は pure JavaScript（shpjs の `parseShp` / `parseDbf`）で行い、DuckDB spatial は
採らない — 日本の公開データに多い CP932 の属性を復号できないためである。
ZIP からの取り出しは既存の yauzl に寄せ、**文字コードの決定は KUKAN 側に置く**。

正本（アップロードされた ZIP そのもの）には手を触れない。GeoJSON はあくまで
プレビューであり、ADR-046 の言う「解釈」の産物である。

## コンテキスト

### 1. シェープファイルは 1 ファイルではない

シェープファイルは `.shp`（幾何）・`.shx`（索引）・`.dbf`（属性）・`.prj`（座標系）・
`.cpg`（属性の文字コード）という複数ファイルの束で、単独の `.shp` だけでは属性も
座標系も分からない。このため配布は ZIP でまとめられる。

KUKAN のリソースは 1 リソース = 1 オブジェクトなので、**入口は必ず ZIP** になる。
拡張子 `.shp` のファイルが単体で登録される経路も理屈の上ではあるが、その場合は
属性も座標系も無いため、地図にする価値がほとんど無い。本 ADR は ZIP だけを扱う。

### 2. いまの ZIP 経路が出すもの

Interpret の ZIP 分岐（`apps/worker/src/pipeline/steps/interpret.ts`）は
`extractZipManifest`（`interpret/zip.ts`、yauzl で中央ディレクトリだけを読む）で
ファイル一覧を作り、JSON をプレビュー生成物として書く。中身は展開しない。

結果として、シェープファイルの ZIP を登録すると
`townarea.shp` `townarea.dbf` `townarea.prj` … というファイル名が並ぶ画面で終わる。
地理データだと分かっていても、カタログの側からは中身が見えない。

### 3. 既にある部品

新しく作らなくてよいものが揃っている。

| 部品             | 実体                                                                 | 本 ADR での使い道                        |
| ---------------- | -------------------------------------------------------------------- | ---------------------------------------- |
| 地図プレビュー   | `geojson-preview.tsx` / `geojson-map.tsx`（Leaflet、OSM/地理院切替） | 表示はそのまま流用                       |
| 生成物の書き出し | `getPreviewKey` + `putObject`（Interpret）                           | GeoJSON を書く                           |
| 生成物の配信     | `GET /api/v1/resources/:id/preview`（Range 対応）                    | 生成した GeoJSON を返す                  |
| 文字コード検出   | `encoding-node.ts` の `detectEncoding` / `bufferToUtf8`              | `.dbf` の属性の文字コードを決める        |
| ZIP の読み取り   | `interpret/zip.ts`（yauzl）                                          | `.shp` / `.dbf` / `.prj` / `.cpg` を取る |

ただし 1 つだけ噛み合っていない箇所がある。既存の GeoJSON プレビューが読むのは
`GET /api/v1/resources/:id/json` — **ライブオブジェクトそのもの**であって、生成物では
ない。シェープファイルの地図は生成物を読む必要があるため、読み出し側に手が要る。

### 4. 日本の公開データの実情

3 つの現実が、ライブラリ選択をほぼ決めてしまう。

**属性の文字コード。** `.dbf` の属性が CP932（Shift_JIS）であることが多い。`.cpg` が
無い配布物もあり、あっても中身は `CP932` / `932` / `SJIS` / `Shift_JIS` と揺れる。
なお `CP932` と `932` は WHATWG の encoding ラベルではないので、
`new TextDecoder('CP932')` は `RangeError` を投げる（実測）。ラベルの正規化が要る。

**座標系。** 緯度経度（JGD2011 = EPSG:6668、旧 JGD2000 = EPSG:4612）と平面直角座標系
（EPSG:6669〜6687 の 19 系）が混在する。GeoJSON（RFC 7946）は WGS84 と決まっている
ので、平面直角座標系のデータは**再投影しないと地図に載らない**。

**`.prj` の欠落。** 座標系が書かれていない配布物がある。緯度経度なのか平面直角座標系の
どれなのかは、ファイルだけからは確定できない。

## 検討した選択肢

### A) DuckDB spatial に読ませる

worker は既に DuckDB を積んでおり（ADR-043 層 2）、拡張はイメージビルド時に事前
INSTALL する仕組みが Dockerfile にある（閉域網対応）。`spatial` を 1 語足すだけで
`ST_Read` が使え、`/vsizip/foo.zip/layer.shp` で ZIP 内を直読みできる。
`.prj` から EPSG コードを自動認識し、`ST_Transform` で WGS84 化する。速い。

**採らない理由は 1 つだけ、しかし致命的である。CP932 の属性を復号できない。**
`.cpg` を置いても `open_options := ['ENCODING=CP932']` / `['ENCODING=SHIFT_JIS']` を
渡しても文字化けする（実測）。書き込み側も `cannot convert to CP932` で落ちるため、
同梱の iconv に日本語コードページが入っていない。幾何だけを DuckDB に読ませ、属性は
別途 `.dbf` を自前で読む折衷も考えられるが、**GDAL の行順と `.dbf` のレコード順を
突き合わせる保証**が要り（`ST_Read` は FID を返さない）、静かに属性がずれる形の事故を
招く。速度のために払う代償として重すぎる。

### B) ZIP の展開は既存の yauzl、解釈は shpjs の `parseShp` / `parseDbf` — 採用

shpjs（MIT、6.2.0）は ZIP を丸ごと受け取るトップレベル API のほかに、
`parseShp(shp, prj)` と `parseDbf(dbf, cpgLabel)`、`combine([geom, props])` を
**名前付きエクスポートしている**。これにより、

- ZIP の展開は既存の yauzl に寄せられる（ZIP を読む場所が 1 か所に保たれる）
- **文字コードのラベルを KUKAN 側で決めて渡せる** — 既存の chardet ベースの検出が効く
- `.prj` の解釈と WGS84 への再投影は shpjs が proj4 で行う

なおトップレベル API 経由（`shp(buffer)`）だと文字コードは ZIP 内の `.cpg` だけで
決まり、介入点が無い。また shpjs の dist ビルド（ESM バンドル）は `self` を前提に
しているため Node では読み込み時に落ちる。`lib/index.js`（package の `import` 条件が
指す正規の入口）は落ちない。**名前付きエクスポートを使う経路は、この 2 つの地雷を
どちらも踏まない。**

### C) ブラウザ側で変換する

shpjs は元々ブラウザ向けであり、ZIP をダウンロードしてクライアントで GeoJSON に
するのは最も実装が少ない。しかしパイプラインを通らないので、**生成物が残らない**。
閲覧のたびに ZIP 全体（上限 100MB）を転送して毎回変換することになり、サイズ超過の
判定も、解釈の失敗の記録も、再実行もできない。既存のプレビューがすべて
「Interpret が作った生成物を配る」形になっているのに、ここだけ別の形になる。

### D) 対応しない

シェープファイルの ZIP はファイル一覧のままにする。地理データを扱うカタログとして
機能が欠けるが、上記 3 つの現実（文字コード・座標系・`.prj` 欠落）の受け皿を持つ
までは、中途半端な地図はかえって誤解を招く、という立場はあり得る。

## スパイク（2026-09-11 実測）

選択肢 A と B の分かれ目が「日本語属性を復号できるか」だけだったため、
合成した検証データで両方を通した。

**検証データ。** DuckDB spatial の GDAL ドライバで EPSG:6677（JGD2011 平面直角座標系
IX 系）の点 3 件を書き出し、属性に日本語（東京都庁 / 浅草寺 / 羽田空港）を入れた。
CP932 の `.dbf` は、UTF-8 で書かれた `.dbf` のレコード領域を固定長を保ったまま
バイト単位で再エンコードして作成した。規模の測定には、5 頂点のポリゴン 50,000 件
（`.shp` 6.8MB + `.dbf` 10.2MB、ZIP 1.5MB）を使った。

| 検証項目                            | A: DuckDB spatial                    | B: shpjs（名前付きエクスポート）           |
| ----------------------------------- | ------------------------------------ | ------------------------------------------ |
| `.prj` からの再投影（6677 → WGS84） | ✅ 正しい座標                        | ✅ 同上（A と 1e-14 まで一致）             |
| UTF-8 属性                          | ✅                                   | ✅                                         |
| **CP932 属性**                      | ❌ `.cpg`・`open_options` とも効かず | ✅ ラベルを渡せば正しく復号                |
| ZIP 内の直読み                      | ✅ `/vsizip/…`                       | —（yauzl で取り出す前提）                  |
| 50,000 ポリゴンの解釈               | 157ms                                | 492ms                                      |
| 出力 GeoJSON                        | 幾何のみ 11.5MB                      | 属性込み 20.7MB（RSS 248MB）               |
| Node での読み込み                   | —                                    | `lib/index.js` は可、dist は `self` で不可 |

**判定。** 速度差（157ms 対 492ms）は、パイプラインの 1 ステップとしては
どちらも無視できる範囲にある。文字コードだけが実質的な差であり、B を採る。

**あわせて分かったこと。**

- ZIP 1.5MB が展開後 17MB、GeoJSON 20.7MB になった（**約 13 倍**）。合成した単純な
  ポリゴンでこれなので、実データの行政区域（1 ポリゴンが数百頂点）ではさらに膨らむ。
  入口のサイズだけでは出力の大きさを予測できない
- `.prj` が無い場合、DuckDB は CRS を `null` として返し、shpjs は投影座標のまま
  （`[-8000, -34000]`）を返す。どちらも「分からない」ことは分かる
- `TextDecoder` は `Shift_JIS` / `SJIS` を受け付け、`CP932` / `932` を拒否する

スパイクの検証物はコミットしない（数値は本 ADR が正本）。

## 決定（提案）

### 1. シェープファイル ZIP を Interpret で GeoJSON に解釈する（選択肢 B）

ZIP の中央ディレクトリに `.shp` があり、**同名の `.dbf` が揃っている**ものを
シェープファイル ZIP とみなす。`.shx` は解釈に使わないので必須としない。
判定はファイル名だけで行い、`resource.format` 列には触らない（CKAN 互換 API の
外部契約であり、利用者の入力でもある。中身の判定をそこに書き戻さない）。

### 2. 部品の取り出しは既存の yauzl、解釈は shpjs の名前付きエクスポート

`extractZipManifest` と同じ場所に、必要なエントリだけを展開する経路を足す。
展開するのは `.shp` / `.dbf` / `.prj` / `.cpg` の 4 つだけで、ZIP 内の他のファイルは
読まない。展開後の合計バイト数には上限を置く（決定 6）。

### 3. 文字コードは `.cpg` → `.dbf` からの検出 → UTF-8 の順で決める

1. `.cpg` があれば、その中身を WHATWG のラベルへ正規化して使う
   （`CP932` / `932` → `shift_jis` など。既存の `bufferToUtf8` が持つ正規化と
   同じ語彙を共有する）。正規化できないラベルは無かったものとして扱う
2. `.cpg` が無い、または使えないラベルだったときは、`.dbf` のレコード領域を
   `detectEncoding`（chardet + 日本語再検証）にかける。**ヘッダーではなくレコード
   領域を渡す** — DBF のフィールド名は 10 バイトの ASCII に限られ、日本語の証拠を
   持たないため
3. どちらも決まらなければ UTF-8

### 4. 再投影は `.prj` を proj4 に渡す。`.prj` が無いときは座標の範囲で決める

`.prj` があれば、その WKT をそのまま shpjs（proj4）に渡して WGS84 に変換する。

`.prj` が無いときは、**座標系を推測しない**。`.shp` のヘッダーが持つ bbox が
経度緯度の範囲（|x| ≤ 180 かつ |y| ≤ 90）に収まるなら緯度経度系とみなしてそのまま
出す（JGD2011 / JGD2000 と WGS84 の差はプレビュー用途では無視できる）。
収まらなければ平面直角座標系であり、19 系のどれかは確定できないので、
**地図を作らず理由（`crs-unknown`）を記録して、ファイル一覧の表示に留める**。

### 5. 生成物は 1 本の GeoJSON。ZIP の中身一覧はその中に畳む

プレビュー生成物のキーはリソースごとに 1 本しかない（`resource_pipeline.preview_key`）。
シェープファイル ZIP では、そこに GeoJSON を書く。ZIP に何が入っていたかは、
FeatureCollection の **foreign member**（RFC 7946 §6.1 が明示的に許す追加メンバー）
として同じ生成物に畳む。

```json
{
  "type": "FeatureCollection",
  "features": [...],
  "kukan:source": {
    "layer": "townarea",
    "crs": "EPSG:6677",
    "encoding": "Shift_JIS",
    "featureCount": 120000,
    "truncated": true,
    "layers": ["townarea", "buildings"],
    "files": [{ "path": "townarea.shp", "size": 6800000 }, ...]
  }
}
```

これにより、マニフェストと地図のどちらを捨てるかという選択を回避できる。
`kukan:` 接頭辞は、GeoJSON をそのままダウンロードした利用者の道具が
このメンバーを無視することを期待した名前空間である（RFC 7946 はパーサーが
未知のメンバーを無視することを求めている）。

### 6. 上限は「入力の展開後サイズ」と「出力の地物数・バイト数」の二重で置く

| 段階         | 上限                   | 超えたとき                             |
| ------------ | ---------------------- | -------------------------------------- |
| 展開後の入力 | `.shp` + `.dbf` 100 MB | 解釈しない（既存の取得上限と同じ数字） |
| 出力の地物数 | 50,000 件              | 先頭から打ち切る                       |
| 出力バイト数 | 10 MB                  | 先頭から打ち切る                       |

出力側はどちらか先に当たった方で打ち切り、`kukan:source.truncated` を立てて
**打ち切られたことを画面に出す**。黙って一部だけ見せない。
出力バイト数の 10MB は、既存の `JSON_PREVIEW_LIMIT`（`/json` が返す上限）に揃える。

入口の ZIP は小さくても出力が大きくなる（実測で約 13 倍）ため、入口のサイズだけを
見た上限では足りない。上限を出力側に置くのはそのためである。

### 7. 複数レイヤは名前順の先頭 1 つだけを地図にする

1 つの ZIP に複数の `.shp` が入っていることがある。地図にするのは名前順の先頭 1 つ
とし（ZIP 内の並び順は作成ツール依存で決定的でない）、残りのレイヤ名は
`kukan:source.layers` に出す。レイヤの切り替えは本 ADR では作らない。

### 8. プレビューの選択は「生成物の種類」で行う

フロントエンドの `resource-preview.tsx` は、いま `format` だけで表示を選んでいる。
シェープファイル ZIP は `format` が `ZIP` のままなので、この分岐では地図に辿り着けない。
リソースの取得レスポンスに**プレビュー生成物の種類**（`zip-manifest` / `geojson` 等）を
足し、ZIP のときはそれで分岐する。CSV が `schema` の有無で表を出しているのと同じ形に
なる。

地図プレビュー側は、生成物を読む経路（`/:id/preview`）に対応させる。既存の GeoJSON
リソース（ライブオブジェクトを `/json` で読む）との違いは、読む先だけである。

## 影響

- **worker**: 依存に shpjs が増える（推移的に proj4 / parsedbf。いずれも MIT）。
  Interpret の ZIP 分岐が 2 本に分かれる
- **shared**: シェープファイル ZIP の判定、`kukan:source` の型、地図を作らなかった
  理由（`crs-unknown` など）の型が増える
- **api**: プレビュー生成物の種類をリソース取得レスポンスに足す
- **web**: ZIP のときの分岐、地図プレビューの読み出し先
- **既存の ZIP プレビュー**: シェープファイルでない ZIP の挙動は変わらない
- **DB**: 新しい列は要らない。既存の `preview_key` と、解釈の理由を記録する既存の
  枠組みに載る

再実行の性質は ADR-046 のまま変わらない。GeoJSON は版（イミュータブルな正本）から
作られるので、同じ入力からは同じ生成物が出る。

## やらないこと

- **属性の全文検索**（ADR-021 の枠）。`.dbf` の属性を検索インデックスに入れない
- **属性テーブルの Parquet 化**。表プレビューや `/query`（ADR-032）に載せれば
  「地図 + 表」になるが、幾何列の扱いを決める必要があり、本 ADR の範囲を超える
- **GeoPackage / FlatGeobuf / KML などの他形式**。DuckDB spatial は読めるので、
  文字コードの問題が無い形式については別の判断があり得る
- **座標系の自動推測**（平面直角座標系の系番号の当てずっぽう）
- **正本の変換**。アップロードされた ZIP は ZIP のまま。GeoJSON は生成物である

## 残課題

1. **Leaflet の描画上限は未計測である。** 上限の 50,000 地物を実際に描けるかは
   確かめていない。実データで確認し、必要なら canvas レンダラー（`preferCanvas`）へ
   切り替えるか、地物数の上限を下げる
2. `.cpg` も `.dbf` の検出も外したときの挙動（UTF-8 で読んで置換文字だらけになる）を、
   画面にどう出すか。既存のテキストプレビューの文字化けの扱いと揃える
3. 打ち切り（`truncated`）が起きたとき、**どの地物が残ったか**をユーザーに説明する
   文言。「先頭 5 万件」は元データの並び順に依存するため、意味のある部分集合とは
   限らない
4. `.shp` 単体で登録されたリソースの扱い。現状は対象外だが、幾何だけの地図を出す
   価値があるかは別途
5. ZIP 内の `.shp` と `.dbf` のレコード数が食い違う配布物の扱い（shpjs の `combine` は
   短い方に合わせて属性を空にする）
