# ADR-043: リソースバージョニングと行レベル差分（DuckLake）

## ステータス

**承認済み（Accepted）** — 層 1 実装完了（2026-07-25）、層 2 ii-a 実装完了（2026-07-27）。
ii-b（主キー指定による変更行追跡）以降は残課題

リソースの正本データに「版」を導入し、表形式リソースについては版間の行レベル差分・
タイムトラベル・列スキーマ変更履歴を提供する設計。テーブルフォーマットとして
DuckLake（カタログ = 既存 PostgreSQL）を採用する。

## コンテキスト

本 ADR 以前の KUKAN では、リソースの正本ファイルは固定ストレージキー
（`resources/{packageId}/{resourceId}`、`getStorageKey()`）へ**上書き**アップロードされ、
旧版は残らない。プレビュー Parquet（ADR-014 / ADR-029）も最新版から丸ごと再生成される
使い捨ての派生物であり、「このデータセットは前回の更新で何が変わったのか」に答える手段が
**メタデータにもデータ本体にも存在しない**。

CKAN でも同様にリソース履歴は弱く、更新のたびに旧データが失われる（または利用者が
手動で「2024年版」「2025年版」を別リソースとして並べる）運用が常態化している。
定期更新されるオープンデータ（施設一覧、統計、予算等）では、

1. **管理者**が「更新で何行増減したか・列が変わっていないか」を確認したい（品質管理・監査）
2. **閲覧者**にも「前版からの変化」を提示する意義がある（更新内容の透明性）
3. **列スキーマの変遷**（列の追加・削除・型変化）を追跡したい

というニーズがある。ADR-032 で「AI が自律的に探索・集計できるデータ基盤」への転換を
図った延長として、**版と差分を一級市民にする**ことが本 ADR の目的である。

### 前提となる現状

- スキーマは `resource_pipeline.metadata.schema` に**最新版のみ**永続化（ADR-032 Part A）
- サーバーサイドクエリは Parquet をインメモリ実体化 → 外部アクセス全面禁止という
  強いサンドボックスで成立している（ADR-032 Part B）。この隔離モデルは維持する
- S3 バージョニングは有効（バックアップ用途、noncurrent 30 日で自動失効。ADR-037）だが、
  アプリ層は `VersionId` を扱わず、**アプリの版管理としては使えない**（後述の選択肢 D）

## 検討した選択肢

### 版の実現方式

- **A) DuckLake（採用）**: テーブルフォーマット。メタデータ（スナップショット・ファイル一覧・
  削除情報・統計）を SQL DB に格納するため、**カタログを既存 PostgreSQL に同居**でき、
  新規インフラが不要。スナップショット・タイムトラベル・`table_changes()`（行レベル CDC）・
  列スキーマ進化を標準提供する。v1.0（2026-04）で後方互換保証付きの本番対応仕様となり、
  カタログは SQLite / PostgreSQL / DuckDB をサポート、Iceberg 互換の削除ベクタを持つ。
  KUKAN は既に DuckDB をサーバー・ブラウザ双方で運用しており（ADR-016 / ADR-032）、
  スタック追加が最小で済む。
  参照: <https://ducklake.select/> / <https://duckdb.org/docs/stable/core_extensions/ducklake>
- **B) Apache Iceberg / Delta Lake**: 業界標準だが、カタログ（REST catalog / Hive metastore 等）の
  追加運用が必要で、メタデータ解決が多段ファイル読みになる。オンプレ・閉域網に追加
  コンポーネントを持ち込むことになり、「アダプターを増やさない」思想（ADR-005）にも反する。
- **C) PostgreSQL に行データを版付きで格納（CKAN DataStore 型）**: ADR-032 で却下した方式の
  版付き変形。スキーマ可変・大量リソースで重く、DB が肥大化する。却下。
- **D) S3 オブジェクトバージョニングの流用**: 既に有効だが、これは**バックアップ機構**であり
  （noncurrent 30 日失効、オンプレ MinIO では未設定）、版の列挙・参照・差分の基盤にならない。
  アプリの版管理には使わない。
- **E) ファイルレベルの版保持のみ（DuckLake なし）**: 版ファイルを immutable に残すだけ。
  実装は最小だが行レベル差分・スキーマ履歴が得られず、動機 1〜3 の大半に答えられない。
  ただしこれは A の**土台（層1）としてそのまま含まれる**。

### 行レベル差分の意味論

- **A) 3 段フォールバック（採用）**: 主キーの有無・スキーマ変化に応じて差分の粒度を落とす
  （決定 §3）。主キーがない場合に無理な行対応付けを行わず、**推測による偽の変更履歴を作らない**。
- **B) 全リソースで行ハッシュによる対応付けを試みる**: 「変更された行」を常に推定できるが、
  主キーなしのデータでは追加+削除と変更を区別できず、誤った履歴を提示するリスクがある。却下。

## 決定

**3 層構造で版と差分を導入する。**

```
層1: 正本バージョンファイル（全フォーマット対象）
     各版が所有するオブジェクト — 通常は live のもの、既に所有済みなら同じ形の鍵への複製
     — immutable、resource_version で管理
層2: DuckLake（表形式リソースのみ）
     1 リソース = 1 テーブル。行レベル差分・タイムトラベル・列スキーマ履歴
     カタログ = 既存 PostgreSQL、データファイル = 既存 S3/MinIO
層3: プレビュー Parquet
     層1の版を解釈した産物（ADR-046）。「DuckLake 最新スナップショットからの export」へ
     置き換えるかは未決（ADR-046 残課題 4）
```

**DuckLake（層2）は層1から常に再構築可能な派生インデックス**と位置づける。正本は層1の
版ファイルであり、DuckLake カタログ・データファイルは全リソースの `reprocess` で再生成できる。
これによりフォーマットの将来リスク（乗り換え・破損）はプレビュー Parquet と同じクラスに収まる。

### 1. 層1 — 正本バージョンファイル

1. **対象は全フォーマット**（PDF・画像・ZIP 等も含む）。表形式でなくても
   「いつ・誰が・何に差し替えたか」の履歴は成立する。
2. 内容が届いたら（アップロードの昇格、または Fetch の取得）、版を作る。
   **版は自分が名指す bytes を所有する** — パージがそれを消すので、他が同じファイルを
   describe している間は消せない（ADR-046 §3）。したがって規則は所有で決まる:
   **誰も持っていないオブジェクトはそのまま自分のものにし、既に持たれているものは複製する。**

   |            | 鍵                                           | 誰が指すか                     |
   | ---------- | -------------------------------------------- | ------------------------------ |
   | live       | `resources/{packageId}/{resourceId}.{token}` | `resource.storage_key`         |
   | 版（通常） | live と同じ鍵                                | `resource_version.storage_key` |
   | 版（複製） | 同じ形の新しい鍵                             | `resource_version.storage_key` |

   通常は取得が書いたばかりのオブジェクトを誰も持っていないので、そのまま所有する。
   複製になるのは **live が動かないとき**だけである — アップロードは鍵を使い回し、巻き戻しは
   live を版のオブジェクトへ戻すので、そこで解釈だけが変わると前の版のファイルを指してしまう。
   **複製したときは live もその鍵へ移す。** 「live は最新 active 版のオブジェクトを名指す」は
   パージが依存している前提で、置き去りにすると古い版のパージが live の実体を消す。

   **どちらの鍵も書いた 1 回ごとに固有の UUID を持つが、要る理由は逆である。**

   - **live 鍵は動く。** リソースが持つ live 鍵は常に 1 つだが、内容が変わるたびに別の鍵になる。
     旧鍵は回収予約され、スイープが消す。UUID は**動いた先が前と別のオブジェクトである**
     ことを保証する
   - **版鍵は動かない。** 1 つの版は 1 つの鍵を持ち、書かれたあと二度と変わらない。UUID が
     要るのは**やり直しのため**である — v5 の作成が途中で失敗して再試行するとき、版番号だけ
     から鍵を作ると、放棄されたオブジェクトと同じ鍵に書くことになる。その鍵はスイープが
     消そうとしている最中かもしれず、**行が指した直後に消される**（ADR-045 §3）

   鍵を計算し直す読み手は 1 つも無く、全員がポインタ列を辿る。だから書き込みが失敗しても、
   そのとき live だったオブジェクトは標的ですらないので無傷で残る。

   **「仮キーへ書いてから `v5` へリネームする」では解けない。** S3 にリネームは無く copy +
   delete になるので手数が増えるうえ、**競合が消えずに最終手順へ移る**だけである — `v5` も
   書く前に先行記録が要り（ADR-045）、行の insert 前に落ちた試行が `v5` を孤児として残せば、
   再試行はやはり同じ `v5` に書く。スイープの「参照を確認 → 削除」の窓が同じように開く。
   試行ごとに別の鍵へ書くことが、**書き手が判定中の鍵を名指しできない**という性質を与えていて、
   それがこの確認を安全にしている。

   代償は鍵の可読性である（バケットを見ても v5 がどれか分からない）。効くのは手作業の調査時
   だけなので、必要なら鍵の形ではなく**管理画面で `storage_key` を見せる**方で足す。

   **版を作る**とは、この「オブジェクトを所有して番号を振る」ことだけを指す（コード上は
   `createVersion`）。
   内容は一切読まない — テーブルかどうかも見ない（ADR-046）。

   **引き金は問わない。** bytes が変わったから作る場合も、bytes は同じで解釈条件だけが変わった
   から作る場合も（ADR-046 決定 3）、動作はこの 1 つである — 解釈だけが変わった版も自分の
   版ファイルを持つ（同 §3）。違うのは §1-4 の判定が「作る」と答えた理由だけである。

   **版が存在し始めるのは、複製したときではなく行が入ったときである。**

   ```
   1. 判定    直前の版とハッシュか format が違うか、live ポインタは今も自分のものか
   2. 所有    誰も持っていなければ live の鍵をそのまま名指す → 行を入れて終わり
              既に持たれていれば: 先行記録（ADR-045）→ 複製 → 1 トランザクションで
              行を入れ、live をその鍵へ移す
   ```

   通常は 2 の前半で終わる。複製する経路だけが先行記録を要し、そこでは**行と live の移動が
   同じトランザクション**に入る — 行だけが残って live が前の版を指すと、次にどちらをパージしても
   正本を失うためである。

   複製した直後にあるのは「台帳に載った書きかけのオブジェクト」でしかない。行が入る前に落ちれば
   その鍵は参照ゼロのまま期限切れになり、スイープが回収する — **その版は一度も存在しなかった
   ことになる**。したがって「番号を振る」は**行に番号が入ること**を指し、複製した鍵の中の `v5` は
   行が決めた番号の写しにすぎない。鍵を見て版番号を決める読み手は 1 つも無い。

   **複製が既定でなくなった経緯は残課題 10 にある。** 当初は内容が届くたびに live オブジェクトを
   専用の prefix へ複製していた。複製は歴史的経緯であって設計上の必然ではなく — live オブジェクトも
   書き換わらないので、版が約束する bytes は今ある場所のままで不変である — 実装して規則を所有で
   書き直した。live が動かない経路（アップロードの鍵の使い回し、巻き戻し）だけが複製に残っている。

3. `resource_version` テーブル（Drizzle 管理）を新設する:
   - `id` (UUID), `resource_id` (FK), `version` (連番), `storage_key`, `size`, `hash`,
     `origin` (`upload` | `fetch`),
     `state` (`active` | `purging` | `purged` | `superseded`),
     `created_by`, `created` / `updated`
   - 列スキーマのスナップショット（当該版の `metadata.schema` 相当）と、
     層2のスナップショット ID（表形式のみ、後述）もここに紐づける
4. **同じものを同じ規則で読むだけの差し替えは版を作らない**: 最新の active 版と
   **ハッシュも format も一致**するなら新版を発行せず、確認日時のみ更新する。

   > 当初は「ハッシュ一致なら作らない」だった。ADR-046 決定 3 が版を「その bytes を、この解釈で
   > 読んだもの」と定義したため、**解釈条件が変われば bytes が同じでも版を作る**。版を作る時点で確定する
   > 解釈条件は今のところ format だけで、ゲートもそれを見る（ADR-046 §6）。
   >
   > 主キーや列型の割当を変えることも決定 3 では版を作ることになるが、**それは版を作る時点でまだ存在しない**ため、
   > この判定ではなく利用者操作の側から入る別導線になる（ADR-046 残課題 2、未実装）。

#### 1.1 `state` の遷移

1 つの版は 2 つの実体でできている。

|                | 実体                            | 役割                                                                                    |
| -------------- | ------------------------------- | --------------------------------------------------------------------------------------- |
| **版定義**     | `resource_version` の 1 行      | その版が何か — 番号・状態・ハッシュ・サイズ・スキーマ・format・どのオブジェクトを指すか |
| **版ファイル** | その版が所有する 1 オブジェクト | その版の中身（bytes）                                                                   |

**版を消す操作は版パージだけで、そのパージも版ファイルしか消さない。** `state` は版定義に載るので、
パージ済みの版も「誰が・いつ・なぜ消したか」を答え続ける（＝墓標）。巻き戻し（ADR-044 §4）は
どちらも消さず、資格を落とすだけである。

ただし**この不変条件が成り立つのは、そのリソースが生きている間だけ**である。リソース削除・
パッケージ／組織パージでリソースそのものが消えると、`resource_version.resource_id` の
`ON DELETE CASCADE` で版定義も一緒に消える。墓標が答えるのは「このリソースのこの版はなぜ消えたか」で
あって、リソースごと消えた後まで残るものではない。

版定義が**生まれる**のは版を作るとき（§1-2）だけで、作る側は 2 つある — 差し替えや取得で
内容が直前の版と変わったときのパイプラインと、版を 1 つも持たない既存リソースに v1 を与える
既存リソースへの**移行（v1 付与）**である。

**以下は版 1 つを追った図である**（リソースではない）。v1 も v7 も同じように `active` から始まり、
その後 `state` が動くのは次の 4 通りだけである。

```
      この版が作られた（§1-2）
       │
       ▼
  ┌────────┐                      ┌────────────┐
  │ active │ ──── 巻き戻し ─────▶ │ superseded │
  │        │ ◀─── 復元に失敗 ───── │            │
  └────────┘                      └────────────┘
       │                                   │
       └────────────────┬──────────────────┘
                        │ パージ要求（sysadmin 限定・理由必須・監査ログ）
                        ▼
                  ┌─────────┐
                  │ purging │  durable claim（ADR-028）。worker が波及先を消す。
                  └─────────┘  失敗しても戻らず、同じ状態から再試行する
                        │ 層1・層2・派生物すべてを消し終えた
                        ▼
                  ┌─────────┐
                  │ purged  │  終端。墓標として行だけが残る
                  └─────────┘
```

`active → superseded` になるのは、巻き戻しの**戻り先より上にある版**である。巻き戻しは
「最新の active 版」へ着地するので、上を残したままだとそちらへ着地してしまう。

`purging` から戻る経路は無い。パージは「途中で諦めない」機構であり、戻せる状態にすると
**法的削除が完了しないまま成功を報告しうる**。

| 状態         | live 候補 | 版ファイル | 層 2 スナップショット | 個別パージ |
| ------------ | :-------: | ---------- | --------------------- | :--------: |
| `active`     |     ○     | あり       | 保持                  |     ○      |
| `superseded` |     ×     | あり       | 保持（差分は取れる）  |     ○      |
| `purging`    |     ×     | 削除中     | 失効させる            |     —      |
| `purged`     |     ×     | 無し       | 無し                  |     —      |

- **`superseded` も個別にパージできる。** 出すべきでなかった内容から作られた版は巻き戻しを
  生き延びるので、消す経路が閉じてはならない
- **`superseded` のスナップショットは保持する。** 差分は 2 つの版をそれぞれの snapshot へ解決して
  読むため、巻き戻しが外した版の分を失効させると比較できなくなる（§6-4）
- **`purging` は保持しない。** パージは自分の実行の中から失効処理を呼び、行を `purged` にする
  前に通る。途中の行を残すと**パージ対象のファイルがディスクに残る**（§6-4）

### 2. 外部 URL リソース — 観測ベースの版

アップロードと外部 URL では版の意味論が異なる。外部 URL の版は
「**取得（Fetch）時点でこう見えた**」という観測記録であり、上流の全変更を捉える保証はない。

1. パイプラインの Fetch 実行時（手動 reprocess、将来の定期再取得）、取得内容が最新の active 版と
   **ハッシュか format のどちらかで違う**場合のみ `v{n}` として層1に保存する（§1-4 と同じゲート）。
   どちらも同じなら版を作らず確認日時のみ更新する。
2. 版の `origin` を `fetch` とし、UI / API では「取得時点のスナップショット」であることを
   明示する（欠測があり得る履歴だと利用者に誤解させない）。
3. 定期再取得は本 ADR のスコープ外とする。将来、quality パッケージのリンク監視
   （既に外部 URL を定期巡回する）に変化検知を相乗りさせる拡張が自然（残課題）。

### 3. 層2 — DuckLake と行レベル差分

1. **構成**: カタログは既存 PostgreSQL 内の専用スキーマ（例: `ducklake`）に置く。
   カタログテーブルは DuckLake 拡張が管理し、**Drizzle のマイグレーション対象にしない**。
   データファイルは既存バケットの専用 prefix（例: `lake/`）に置く。
2. **書き込みは worker 専任**とし、テーブル単位で直列化する。web プロセスに DuckLake の
   書き込み経路・ネイティブ依存の追加負荷を持ち込まない（ADR-032 の配置判断と同型）。
   DuckLake に触れるコードは専用モジュールに隔離し、他所から DuckDB API を直接呼ばない。
3. **DuckDB はストレージへ直接読み書きする**（httpfs / S3 API）。storage アダプタの例外だが、
   **S3 互換だからではない** — それを理由にすると `resources/` も `previews/` も同じく
   S3 互換であり、アダプタの存在理由が消える。**アダプタがこの読み方を表現できない**からである。
   `download` はオブジェクトを丸ごと `Readable` で返す一方、DuckDB は Parquet のフッタを読んで
   必要な row group と列だけを範囲 GET し、それを多数のファイルへ並行に行う。アダプタ越しでは
   全ファイルを丸ごと落とすことになり、DuckLake を使う理由自体が消える。ADR-005 の原則を
   緩めるのではなく、**インターフェースが表現できないことによる例外**である。

   範囲は DuckLake 自身の `DATA_PATH`（`lake/` prefix）に限る。`resources/` と `previews/` は
   アダプタ経由のままで、Interpret も版ファイルを `storage.download` で落として
   からローカルのパスを DuckDB へ渡す。境界を保つのは prefix ではなく**モジュール**であり、
   DuckDB を開くのは `packages/lake` だけである（前項）。

   代償は **S3 接続設定の二重化**である。DuckDB は自前の secret を要求するため、
   `S3StorageAdapter` が env から導く設定（エンドポイント、path-style、SSL、静的キーか
   credential chain か）を `packages/lake` も同じ env から導き直す。真実は 1 つだが導出箇所は
   2 つあり、片方だけ変えると dev だけ、あるいは AWS だけが壊れる（残課題 11）。

4. **1 リソース = 1 テーブル**。パイプラインに Version ステップを追加し、その版を解釈した
   結果を列型として ingest する。対象は現行の Parquet 生成対象と同じ
   **CSV / TSV・≤50MB**から開始する（上限拡大は残課題）。

   > 当初は Extract の型推論（ADR-029 の自前実装）の結果を使う設計だった。ADR-046 で
   > 解釈が 1 ステージ（Interpret）にまとまり、型推定は DuckDB の sniffer に移っている。

5. **スナップショットとの対応**: DuckLake のスナップショットはカタログ全体で単調増加するため、
   コミットごとに得たスナップショット ID を `resource_version` に記録し、
   「リソースの版 ↔ DuckLake スナップショット」の対応を KUKAN 側で持つ。
6. **差分抽出は 3 段フォールバック**:
   - **主キーあり** → `MERGE` による行単位差分。追加・削除・**変更**行が区別され、履歴が最小コストで残る。
     主キー列はリソース設定で管理者が任意指定する（v1 は手動指定のみ。AI による主キー候補提案は
     ADR-040 の提案基盤への将来拡張とする）。
   - **主キーなし** → 全行置換 + 統計サマリ（「N 行中 x 行追加・y 行削除」）。行の対応付けは
     行内容ハッシュの一致のみで判定し、**「変更行数」は数えない**（主キーなしで変更と追加+削除は
     区別できない。推測で偽の変更履歴を作らない）。
   - **スキーマ変更**（列の増減・型変化）→ 行差分を放棄し、新版 + スキーマ変更の記録とする。
7. **列スキーマ履歴（動機 3）**: DuckLake カタログが列の追加・削除・型変更をスナップショット
   境界付きで保持するため、表形式リソースのスキーマ変遷は追加実装なしに照会できる。
   `resource_pipeline.metadata.schema` は従来どおり「最新版のキャッシュ」として維持する。
   非表形式リソースの「変更履歴」は層1（版・サイズ・ハッシュ・日時）で足りる。

### 4. 公開経路とサンドボックス分離

ADR-032 のサンドボックスは**無変更で維持**する。使い捨ての DuckDB へ Parquet を読み込み、
**読み込み終えてから外部アクセスを閉じて設定を封じる**ため、それ以降ユーザー SQL が触れられるのは
読み込み済みのテーブルだけになる。DuckLake へ届く手段はそこに残らない（ADR-032 §4）。

その上で、DuckLake へのアクセス可否で経路を分ける:

| 経路                                | SQL の出所                                                           | DuckLake アクセス                    |
| ----------------------------------- | -------------------------------------------------------------------- | ------------------------------------ |
| 版一覧・差分 API（新設）            | **サーバーが組み立てる固定クエリのみ**（パラメータは版番号等に限定） | あり                                 |
| `/query` / `query_resource`（既存） | ユーザー / AI の生 SQL                                               | **なし**（上のサンドボックスのまま） |

- 新設 API（案）: `GET /resources/{id}/versions`（版一覧）、
  `GET /resources/{id}/diff?from=&to=`（追加/削除/変更行数・スキーマ差分・サンプル行）。
  可視性チェックは ADR-017 / ADR-032 と同じ経路を通す。
- 既存クエリ経路の拡張は「`version` パラメータを受けたら当該版の Parquet を実体化する」に
  留める。ユーザー SQL が DuckLake カタログ・データファイルに触れることはない。
- 差分の第一の消費者は管理者（品質管理・監査）だが、公開リソースの差分サマリは閲覧者にも
  提示する（版の可視性はリソース本体と同一）。MCP ツール化（`get_resource_diff` 等）は
  需要を見て追加する（残課題）。

### 5. パージ（法的削除）

版単位の完全削除。ライセンス・個人情報・誤掲載等で**過去版の内容を消滅させる**ための機構であり、
通常の削除（リソース delete）とは独立に提供する。

1. **権限は sysadmin 限定**。理由の入力を必須とし、監査ログに記録する。
2. **墓標方式**: `resource_version` の行は残し（いつ・誰が・なぜパージしたか）、内容のみを
   全波及先から消す。`state: active → purging → purged` の非同期遷移
   （ADR-028 の durable claim パターンを踏襲、worker が実行）。
3. **波及先**:
   - 層1: その版が所有するオブジェクトを削除する。1 版 = 1 オブジェクト（ADR-046 §3）なので
     他に記述しているものは無い。**削除が先で、ポインタの巻き戻しは後**である — 途中で中断すると
     live は「消えたオブジェクト」を指す（配れない）状態になり、法的削除としてはそちらが安全
   - 層2: 該当スナップショットを expire し、それによって参照ゼロになったファイルを
     `ducklake_cleanup_old_files` で物理削除する。**ファイルの書き直しは行わない** —
     全行置換ではファイルの生存区間が版境界と一致するため、expire が
     ファイル全体を解放する。該当版へのタイムトラベルは不能になる（それが目的）
   - 派生物: 当該版由来のプレビュー Parquet、**本文先頭のテキストヘッド**（ADR-040）、
     OpenSearch のリソースコンテンツインデックス（ADR-021、パージ対象が最新版の場合）。
     テキストヘッドは `metadata` 内のポインタに指されるため孤児スイープが引き取らない —
     パージが自分で消さなければ、内容の抜粋がバケットに残り AI 提案の経路から読める
4. **物理消滅のタイムライン**（AWS）: パージ実行でアプリ層からは即時不可視（全ロール）。
   S3 バージョニングの noncurrent 版はライフサイクル（30 日、ADR-037）で自動失効し、
   AWS Backup の復旧ポイントは保持期間満了で消滅する。**「パージ後、最大 30 日 +
   バックアップ保持期間で物理消滅する」ことを仕様として明文化**する。
   残置期間中の noncurrent 版へはアプリにコードパスが存在せず、KUKAN のどのロールからも
   到達できない（到達可能なのは AWS IAM を持つインフラ運用者のみ）。
   オンプレ（MinIO、バージョニング未設定）では削除は即時消滅であり、残置問題は存在しない
   （バックアップの扱いは導入団体の運用に依存する旨を注記）。

**パージが消せるのは、その版が持つ複製だけである。** 版はバイト列と読み方の組で立つ
（ADR-046 §3 / §6）ので、内容が変わらないままフォーマットのラベルが訂正されれば、同じバイト列が
2 つのオブジェクトとして存在し、それぞれ別の版が所有する。1 つのオブジェクトを 2 版で共有すれば、
片方のパージがもう片方の内容を持っていく — 鍵が書き込みごとに別なのはそのためである（ADR-045）。
その代償として、**パージした内容が別の版番号からそのまま取得できる**状態が起こりうる。

他の版も消すかどうかは別の正本についての判断であり、自動では消さない。欠けていたのは削除機構では
なく判断材料なので、**パージ確認ダイアログが同じ内容を持つ他の版を名指す**。名指すのは `active` と
`superseded` の版だけである — 墓標は内容を持たず、既に `purging` の版は同じく破壊される途中なので、
「残る版」として挙げれば、そのリソースが今は受け付けない 2 件目のパージへ操作者を送ることになる。

**この提示は版一覧が全件であることに依存している。** 同内容かどうかは一覧が各版について返す `hash`
を突き合わせるだけで分かり、サーバーへの追加問い合わせも索引も要らない。一覧をページングするなら
判定はサーバー側へ移す必要がある（残課題 13）。

**層 2 の現在内容が追随するのは「取り込まれた最新の版」であって、live 内容ではない。**
パージは live 版を消すときテーブルを直前版の状態に戻すが、巻き戻し（ADR-044 §4）は版を
残すため戻さない — 巻き戻したあとも、層 2 は撤回された版の内容を持ったままになる。
これは層 2 が層 1 の版履歴の写像であることの帰結であり、不整合ではない。その内容まで
消したいならパージを使う（3 段ラダーの上の段がそれである）。

#### 5.1 器の原則

**DuckLake は行を消せない。消せるのはファイルである。** パージが「この版の行を消した」と
言えるのは、消すべき行がファイルにちょうど収まっていて、そのファイルに他の版の行が
入っていないときだけである。

この「まとめてしか捨てられない単位」を以下**器**と呼ぶ。実体は Parquet データファイル 1 つ
である（インラインを有効にすればカタログ上のインラインテーブルも器になるが、無効化して
ある — §6-1）。

パージが安く済むかどうかは、**複数の版の行が 1 つの器に同居しているか**だけで決まる。
同居していなければ、その版の器を expire して cleanup すれば終わる。同居していれば器ごと
しか捨てられないため、**同じ器に入っていた生存版を層1から作り直す**しかない。

> 紛らわしいが、**版をまたいで同じ行があること自体は問題ではない**。v1 と v2 で変わらなかった
> 行は現行データであり、v1 をパージしても消さない（消してはならない）。問題なのは、消すべき
> 行と残すべき行が**同じファイルに入っている**ことである。

同居が生じる条件は 2 つで、どちらも代償は「層1から作り直す」という同じ形になる。
違うのは作り直す範囲だけである。

| 共有が生じる条件                            | パージの代償             |
| ------------------------------------------- | ------------------------ |
| compaction が版をまたいで統合（§6-2）       | 統合された全版の再構築   |
| 差分適用で 1 ファイルに履歴行と現行行が同居 | パージ版以降の再取り込み |

**インラインテーブルを無効化したのは、この代償が 3 つの中で最も高いからである**（§6-1）—
有効なら expire も cleanup もインライン行に届かず、回収手段は `DROP TABLE`、すなわち
全版の再構築しか残らない。

**全行置換だけが器を共有しない。** だからこそパージが expire + cleanup の 2 手で済む。
実測でも一致した — compaction 済み・インライン有効のいずれでも「直前版の状態に戻す +
後続版のみ再ロード」は失敗し、全版再構築だけが成功する。

**主キーの有無は版ごとの状態であり、フェーズではない。** 主キーは後から設定でき、外すことも
できるため、1 つのリソースの履歴に「主キーなしで取り込まれた版」と「主キーありで取り込まれた版」が
混在しうる。したがって**全行置換は主キーあり差分の縮退形**として扱い、パージ機構は
リソース単位ではなく**版の区間ごとに**選ぶ。ある版が器を共有しているかは
`ducklake_data_file` の生存区間から判定でき、アプリ側の状態を増やす必要はない。

現時点で全ての版が全行置換なのは、キー指定 UI がまだ無いためにすぎない。キー指定を
導入した時点で、同じカタログに両方の形が現れる（残課題 7）。読み取り性能のための統合と
パージの安さが同じ器を奪い合う、という緊張もそこから始まる。

### 6. 運用 — データインライン・compaction・スナップショット保持

1. **データインラインは無効化する**（`data_inlining_row_limit = 0`）。DuckLake は既定で
   小さいテーブル（実測 10 行以下）の行を Parquet ではなくカタログに格納する。

   これは**小口・高頻度の書き込みのための書き込みバッファ**である。数行のコミットごとに
   Parquet を作れば小ファイルが積み上がり、読み取りがファイル数ぶんのメタデータ解決を払う
   （Iceberg / Delta 系の代表的な弱点）。ファイルを作らなければその問題は起きず、
   オブジェクトストレージへの往復も省け、書き込みが 1 つの DB トランザクションに収まる
   — カタログを SQL DB に置く DuckLake の利点を、データ本体まで押し進めた形である。
   溜まった行は後から `ducklake_flush_inlined_data` が Parquet へ落とす想定で、
   狙いは streaming ingest や 1 行ずつの INSERT / UPDATE にある。

   **KUKAN にそのワークロードは無い。** 書き込みは版ごとに 1 回の全行置換で、小口でも
   高頻度でもない。狙いの前提が当たらないので利益はほぼ無く、以下の代償だけが残る。
   表現自体は行ごとに `begin_snapshot` / `end_snapshot` を持つため、**原理的には
   ファイル単位より細かい粒度で回収できる**。問題は実装がそれを行わないことにある:
   - **インライン行は回収されない**。ある行を観測できるスナップショットが全て expire された
     後も PostgreSQL に残り続け、`expire_snapshots` も `cleanup_old_files` も削除しない。
     どこからも到達できないのに消えない、という状態になる（ドキュメントは
     inlined data が Parquet と「格納場所が違うだけ」と述べているが、この点で挙動は異なる）。
   - `ducklake_flush_inlined_data` は回避策にならない。書き出しはするが、インラインテーブルの
     MVCC 構造をそのまま材化するため **全版の行が 1 ファイルにまとまる**。生存版がその
     ファイルを参照するので、結局パージ対象の行を消せない。
   - 非インラインなら、全行置換が版ごとに独立したファイル（生存区間が互いに素）を
     生むため、expire がファイル全体を解放する。

   加えて **flush は自動では起こらない**。閾値は「1 回の insert あたり」の判定であり
   （公式の説明も _"Maximum amount of rows to inline in a single insert"_）、累積では
   効かない。バッファとして使う側なら 1 回の insert が小さいのは前提なので、そこは
   想定どおりである — ただし**溜まりすぎを止める仕組みが無い**。
   `auto_compact` はスケジューラではなく、メンテ関数をテーブル指定なしで
   呼んだときの対象に含めるかを決めるだけである。実測では 1 行ずつ 15 回 INSERT した後に
   1 行ずつ 15 回 UPDATE しても Parquet は 1 つも作られず、インライン行は 30 行まで
   積み上がった（生存 15 行に対し、旧行バージョン 15 行が回収されないまま残る）。

   構造としては、インラインテーブルは**常に compaction 済みのファイルと同じ状態**にあり、
   §5.1 の器の原則がそのまま当てはまる（器 = テーブル、代償 = 全版の再構築）。
   ii-b で採りたい「パージ版より前は触らない」最適化が、インラインを有効にすると使えない。

   したがってこれは表現の優劣ではなく、**狙いの外で使ったときに露出する実装の穴**への
   対処である。**上流が expire 時のインライン行回収を実装したら、この判断は見直してよい**。
   設定はカタログに永続化する（ATTACH オプションはセッション限りで、別経路の接続に
   保証が依存してしまう）。

2. **compaction の要否は書き込み形態で決まる**（これもフェーズの属性ではない）。
   全行置換では live なデータファイルが 1 つの版の出力に収まり、**版数に比例して増えない**。
   差分も常に 2 版分しか読まないため、版が何個あってもコストは一定である
   （実測: 21 版で v1→v20 と v19→v20 が同コスト）。統合する対象が無いので
   `ducklake_merge_adjacent_files` は何もしない（`[]` を返す）。

   キー付き差分を受け取り始めたリソースでは live ファイルが版ごとに増えるため、compaction が
   有効になる（実測: 501 ファイル → 1、スキャン 3.9 倍。全版を保持したまま実行でき、
   時間旅行も保たれる）。

   ただし**パージとの緊張がある**。版をまたいでファイルを統合すると、§5.1 の器が生まれ、
   パージが同じ器の生存版まで巻き込む。全行置換しかしていないリソースに対しては、
   利益が無く代償だけがあるため実行しない。

3. **スナップショット / 版の保持世代数**: ランタイムシステム設定（ADR-036）として持ち、
   sysadmin が変更できるようにする（既定は無制限とし、ストレージ逼迫時に絞る運用を想定）。
   期限切れスナップショットの expire も同じメンテジョブで行う。

   > **未実装。** 既定が無制限なので、実装しないことと既定のままの挙動が一致しており、
   > 導入を急ぐ理由が無かった。したがって**現在、版が世代数で落ちることはない** — 版ファイルが
   > 消えるのは版パージ・パッケージ／組織パージ・孤児スイープ（放棄された試行の回収）の
   > 3 経路だけである。次の 4 が説明する snapshot の失効は、保持世代数とは無関係に
   > 「生存している版が参照しているか」だけで決まる。

4. **expire は明示リスト方式**（`versions => [...]`）。

   > **expire とパージは別物である。** expire は DuckLake のスナップショットをカタログから
   > 外す**掃除**で、対象は層2だけ、それ自体はファイルを消さない（参照をゼロにするだけで、
   > 消すのは `cleanup_old_files`）。パージは版の内容を全波及先から消滅させる KUKAN の操作で
   > （§5）、その一手として expire を呼ぶ（§5-3）。**expire は道具、パージは意図**である。
   > 掃除としての expire は生存版が参照しないスナップショットを落とすだけなので、単体では
   > 何の内容も失われない。

   失効候補 = 全スナップショット −
   **生存している版**（`state` が `active` または `superseded`）が参照する ID −
   最新スナップショット。時刻ベースの `older_than` は使わない（ID がカタログ共通の連番の
   ため、更新されていない版の参照先まで巻き込む）。最新スナップショットを常に残すのは、
   パージがテーブルを直前版の状態に戻した直後は、どの版からも参照されない最新スナップショットが
   現行内容だから。

   **`active` だけでは足りない。`superseded`** — 巻き戻しが戻り先より上から外した版 —
   のスナップショットも残す。スナップショットは「現在内容であること」より長生きするからである:
   差分は 2 つの版をそれぞれのスナップショットへ解決して両方を読むため、外した版の分を
   失効させると、その版との比較ができなくなる。逆に `purging` は `purged` と同じく
   除く。版パージは自分の実行の中からこれを呼び、行を `purged` にする前に通るので（その書き込みが
   snapshot も null にする）、途中の行を残すと**パージ対象のファイルがディスクに残り**、
   パッケージ／組織パージ以外に届く経路が無くなる。

5. **孤児ファイル**: DuckLake は Parquet を書いてからカタログにコミットするため、その間の
   異常終了で追跡されないファイルが `lake/` に残る。expire も cleanup も対象にしない
   （`ducklake_delete_orphaned_files` の担当）。ストレージのリークであり正しさには影響しない。

6. **取り込みを延期した版が必要な Parquet を自分で指す仕組み（`resource_version.lake_source_key`）
   — 撤去済み（ADR-046 §4）。**

   層 2 が版ファイルを直接読み、再取り込みが解釈のやり直しになったため、**守るべき一時的な
   ポインタがそもそも生まれなくなった**。列と、それが必要としていた一生（延期・回収予約・
   参照確認・毎時スイープ）をまとめて落としている（マイグレーション 0027 で追加、0028 で削除）。

   > **何を解いていたか**（記録として残す）。取り込みに失敗した版は再投入ジョブとしてキューに
   > 残るが、キューのメッセージは**孤児スイープから見えない参照**であり、そのとき使った
   > プレビューは差し替え後に回収予約されてスイープに消える — その版は二度と層 2 に入れなく
   > なる。そこで「必要としている版がある」ことを列で表明し、スイープの参照確認
   > （ADR-045 §3）が見る 6 つ目の源とした。時計を持ち込まないので DLQ 送りでも取りこぼさず、
   > キューのメッセージが唯一の記録でもなくなる、という利点があった。
   >
   > 代償は、ポインタを外す 3 経路（取り込み成立・追い越しによる恒久的拒否・実体喪失）の
   > **すべてで、外すのと同じ文でキーを回収予約しなければならなかった**ことである。版が
   > 指している間、スイープはそのキーを「参照済み」と読んで台帳の記録の方を消すため、
   > 回収予約せずに外すとポインタも記録も持たないオブジェクトが残る（ADR-045 §3 の但し書き）。

## 影響

- **DB**: `resource_version` テーブル追加（Drizzle）。DuckLake カタログ用スキーマが
  同一 PostgreSQL 内に増える（DuckLake 拡張管理、Drizzle 対象外）
- **Worker**: パイプラインに Version ステップ追加（層1保存・ハッシュゲート・DuckLake ingest・
  差分抽出）。compaction / expire / パージ実行のメンテジョブ追加。`@duckdb/node-api` 依存が
  worker にも入る
- **API**: 版一覧・差分・パージのルートとサービス追加。既存 `/query` に `version`
  パラメータ拡張。web プロセスに DuckLake 書き込み経路は追加しない
- **ストレージ**: 層1は版ごとに 1 オブジェクト増える — 各版が所有するもので、live の複製は
  生じない（版がそれを名指すため）。保持世代数設定で制御。`lake/` は差分コスト（変わらない
  ファイルは版間で物理共有）
- **セキュリティ**: DuckLake に触れる SQL はサーバー組み立てのみ。ADR-032 のサンドボックスは
  無変更。パージは sysadmin 限定 + 監査ログ
- **後方互換**: 既存リソースは次回差し替え時から v1 が発行される。既存のダウンロード・
  プレビュー経路は無変更

  > 当初は「既存分を一括で埋めることはしない」（ADR-029 / ADR-032 と同じ方針）としていたが、
  > **1 度きりの移行（v1 付与）を実装した**。次の差し替えを待つと、それまでに
  > 差し替えられたリソースは**旧内容を層 1 に残さないまま上書きされる** — 版管理を入れた目的が、
  > 導入直後に一番失われやすい内容に対してだけ働かない。管理画面から起動し、版を持たない
  > リソースの現行ファイルをそのまま v1 として名指す（まだ誰も所有していないので複製しない）。
  > 実行 claim を取る（ADR-044 §1）。

## 残課題（未解決事項）

1. **定期再取得**: 外部 URL の変化検知を quality パッケージのリンク監視に相乗りさせ、
   変化時に再取得キューへ投入する拡張
2. **対象の拡大**: DuckLake ingest の上限（現行 Parquet 生成と同じ ≤50MB）の引き上げ、
   JSON 等への対象拡大（ADR-032 残課題 1 と同根）
3. **マルチサイト（ADR-041）**: DuckLake カタログをサイト単位で分けるか、単一カタログ +
   テーブル名 prefix か。接続数バジェットへのカタログ接続の算入
4. **プレビュー Parquet の統合（層3）**: プレビューを「DuckLake 最新スナップショットの
   export」に置換し、生成経路を一本化する
5. **MCP ツール化**: `get_resource_diff` / 版指定つき `query_resource` 等、AI エージェント
   向けの版・差分アクセス
6. **主キー列の AI 提案**: ADR-040 の提案基盤に主キー候補提案を追加し、主キーあり差分
   （MERGE 段）への昇格を支援する
7. **ii-b のパージ機構（昇格の前提条件）**: 主キーあり差分に移ると §5 のパージが成立しなくなる。
   後追いの課題ではなく、**昇格前に解決すべき前提**として扱う。§5.1 の器の原則が
   ii-a の例外を失い、常に適用されるようになる、というのが問題の本体である。
   - 差分適用では 1 つのファイルに「履歴専用の行」と「まだ現行の行」が同居するため、
     expire + cleanup ではファイルを解放できない。`ducklake_rewrite_data_files` も解に
     ならない（新ファイルを作るが、保持中のスナップショットの参照先を貼り替えないので
     旧ファイルが残る）。
   - 有効なのは**版単位の再書き出し**: パージ対象の直前版の状態に戻し、後続版のみ層1から
     再取り込みする。前方の版は自分のファイルを持つため触れなくてよい。
   - compaction 済みなら前方の版も器を共有するので全版の再構築になる。読み取り性能と
     法的削除コストのトレードオフであり、「差分保持期間を過ぎた版だけ compaction する」
     案が有望だが未検証。
   - 意味論も変わる: パージ対象版が書いた行でも、後続版で現行のままなら**消えない**
     （現行データであり消してはならない）。UI 文言はこれを反映する必要がある。
   - 1 つの版が複数の DuckLake スナップショットにまたがる（文ごとに 1 つ）ため、expire 対象を
     `resource_version.ducklake_snapshot_id` だけで組むと取りこぼす。
   - DuckLake は PRIMARY KEY / UNIQUE 制約を持てない。主キーは MERGE 条件に使う論理キーとなる。
   - **巻き戻しは層2に追随しない。** `purgeFromLake` を呼ぶのはパージだけで、巻き戻しは
     呼ばない。v3 から v2 へ戻したあと、テーブルの現在内容は v3 の行のままである。
     ii-a では無害だが、それは全行置換だからではなく **diff が現在内容を見ないから**である
     （両側を各版のスナップショットへ解決し、列もスナップショットごとに describe する）。
     ii-b では `MERGE` の相手がテーブルの現在内容そのものなので、**merge 元が撤回済みの版に
     なる**。スキーマが版間で変わっていれば対象列すらずれる。
   - 同じ理由で、ingest が「列が動いたか」を**テーブルの現在内容と比べて**判定している点も
     ii-b では成立しない。ii-a は枝の選択を誤っても全行を書くので結果が正しくなるだけで、
     判定根拠は巻き戻し後に既に間違っている。
8. **IAM の厳密化**: タスクロールの `s3:GetObjectVersion` / `s3:DeleteObjectVersion` を
   明示 Deny し、パージ残置期間中の noncurrent 版アクセスを IAM レベルでも遮断する
   （現状はコードパス不在による遮断のみ）
9. **Iceberg エクスポート**: 公開スナップショットの Iceberg 形式提供（外部エンジンからの
   直接読み取り）。DuckLake は Iceberg 互換の削除ベクタを持つため変換コストは限定的
10. ~~**live を版へのリンクにする**~~（§1-2）: **完了**。版の誕生から先行記録と複製が消え、
    通常経路では 1 文になった（所有済みオブジェクトから作る場合は残る）。実装して分かったことを
    2 つ記す。
    - **不変性は理由にならない** — live オブジェクトも書き換わらない（§1-2）
    - **パージはむしろ共有の方が素直だった** — 版とその live 複製は当時も同じ 1 回の操作で消えており
      （版ファイルを削除し、旧 live 鍵を回収予約する）、1 つにすれば消し忘れる余地が減る。
      戻しに失敗しても「live が消えたオブジェクトを指す＝配れない」という、法的削除に
      とって安全な向きに倒れる
    - **「1 版 = 1 オブジェクト」は規則を書き直して保つ** — 「各版は自分が live だった時点の鍵を
      持つから共有は生じない」は**成り立たなかった**。live が動かない経路がある（アップロードは
      鍵を使い回し、巻き戻しは live を版のオブジェクトへ戻す）ので、そこで解釈だけが変わると
      2 つの版が同じファイルを指す。規則を原因ではなく所有で書けば一様になる —
      **版は誰も持っていないオブジェクトを自分のものにし、既に持たれているものは複製する。**
      複製が残るのはその 1 経路だけで、内容が変わる通常の経路からは消える

    - **巻き戻しの 2 段構えは分けて畳めない。** copy が消えると `stepOffAbove` と publish の間に
      アプリケーション側の seam が無くなり、ロールバック経路に外から失敗を注入できなくなる。
      検証できないコードを残すことになるので、リンク化と同じ変更で畳んだ。畳み方は SQL の
      統合ではなく**トランザクション**である — 両方とも DB 書き込みになった以上それで足り、
      `publishLiveContent` の回収予約の規則を複製せずに済む
    - **回収予約の述語だけを先に入れることはできない。** 当時は live が `resources/`、版が
      専用 prefix と鍵が必ず異なったため、リンク化前の述語は一度も発火しない

    代償のうち実際に効いたのは「live の指す先が 2 種類」と「回収予約の述語 1 つ」。
    **前者は後に解消した** — 複製先を live と同じ形の鍵にしたので、live の指す先は 1 種類に戻った。
    版専用の prefix は複製経路だけが使う残りとなり、名前が実態（版ファイルの大半は live の鍵の
    まま）を否定していた。鍵は「どこに属し、どの書き込みか」しか持てない — 何であるかは書かれた
    時点でまだ決まっていない。
    「変化なし再取得の後始末」は publish の順序を動かしたときに要るもので、それは別（残課題 12）

11. **S3 接続設定の導出が 2 箇所ある**（§3-3）: DuckDB は自前の secret を要求するため、
    `S3StorageAdapter` と `packages/lake` が同じ env から独立に設定を導いている。
    片方だけ変えると片方の環境だけが壊れ、しかも壊れるのは lake 経路だけなので気づきにくい。
    導出を 1 つの関数にまとめ、アダプタと DuckDB の双方がそれを読む形が素直
12. **publish を版の作成より後ろへ動かす**（§1-2）: 残課題 10 でリンク化は済んだが、Fetch は
    今も**版を作る前に** live を publish する。順序を変えれば §1-2 の表のうち「版を持たない live」が
    3 つ消える（巻き戻し直後・変化なし再取得・キルされた実行の残す実体）。
    引き換えに、変化なし再取得の後始末が要る — Fetch は毎回新しい鍵に書くので、版にならなかった
    鍵を捨てないと節約が消える。**リンク化とは独立に効く**ので分けた
13. **版一覧をページングするなら、同内容の提示を一緒に動かす**（§5）: パージ確認ダイアログが
    同じ内容を持つ版を名指せるのは、一覧が全件返るからである。版が増えて一覧をページングすれば、
    画面が持っているのはリソースの版の一部になり、別ページにいる同内容の版を見落とす。
    その時点で判定はサーバー側へ移り、リソースとハッシュの索引が要る。
    **見落としても画面は静かに「他に無い」と言うだけである** — 失敗が出るのは法的削除の側なので、
    ページングを入れる側がこの提示も一緒に移すこと
