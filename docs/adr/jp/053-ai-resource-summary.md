# ADR-053: リソースの AI 生成抄録 — 推論はサマリー文に限る

## ステータス

**提案（Proposed）** — スパイク Phase A・Phase B とも実施済み（付録）。残るのは nDCG の前後
比較（判定基準 6）で、これは抄録の実装後にローカルと demo でそれぞれ測る。

リソースに、AI が生成した短い**抄録**を持たせる。書誌でいう抄録 — 原本を開かずに中身を
判断できるよう内容を短く正確に表した文であり、検索のための二次資料でもある（JIS X 0813）。
**この 2 つの目的が、そのまま本 ADR の目的である。** **表示が主目的で、
検索の埋め込みへの投入は副産物**である。そして **AI の推論はサマリー文の生成に限り、
機械が信じる値は生成しない** — 列の型も、主キーも、ヘッダー行の位置も、AI に決めさせない。

この線を引くことで、抄録は「可逆で、劣化が緩やかで、他の何もそれに依存しない」成果物に
なる。パイプラインの決定論（ADR-046）も、行レベル差分の土台（ADR-043）も、一切揺らさない。

**本 ADR は MVP を定義する。** 表とテキストは既にある材料を使い、PDF・Office 形式・画像は
原本をそのまま渡し、上限を超えるものは扱わない（決定 3）。生成はパイプラインの最後の
ステップで行う（決定 4）。抜粋・変換・経路の振り分けは、
必要が観測されてから着手する（「MVP の後に検討すること」）。

## コンテキスト

### 1. いま、カタログから中身が見えない

リソースの中身がカタログ側から見えない状態が 2 つの形で現れている。

**表示。** PDF や Office 文書のリソースページは、実質ダウンロードリンクだけである。
何が書かれた文書なのか、開くまで分からない。Excel も同じで、CSV 経路に入らないため
プレビューもスキーマも無い。

**検索。** 埋め込みの材料は `buildEmbeddingText`
（`apps/worker/src/embed/embed-package.ts`）が組み立てる
`title` + `notes` + `tags` + 各リソースの `name` / `description` だけである。
自治体のデータセット名は事務的で（`年齢別推計人口【年齢5歳階級別、年齢3区分別】`）、
利用者が使う生活語（「お年寄り」「小さい子」）からの距離が遠い。公開データカタログで
検証したところ、キーワードが一致する語では意味検索が効く一方、言い換えでは届かない。

この 2 つは同じ欠落の別の面である。**中身を言葉にしたものが、どこにも無い。**
実測すると、埋め込みの材料は**平均 196 字**しかなかった（付録 3）。語彙の不足というより
**材料そのものの不足**である。

### 2. 表と文書で、事情が違う

表データには構造が既にある。Interpret が確定した列名と型（`対象者数（人）`、`受診率（％）`）
そのものが中身を表す語なので、**埋め込みテキストに列名を足すだけで語彙が手に入る**。
推論は要らない。

文書にはその構造が無い。そして埋め込みは 8,000 字で切られる（`MAX_EMBED_TEXT_LENGTH`）
ので、200 ページの PDF を入れる方法が原理的に存在しない。**文書に対して、要約は
「言い換え」ではなく「圧縮」という本来の仕事をする。** ここでは要約が唯一の経路になる。

本 ADR は主に後者に払う費用を決める。前者（列名・組織名を埋め込みテキストに含める）は
推論コストゼロで実装できるので、本 ADR とは独立に進めてよい。

### 3. ADR-040 との関係

ADR-040 の AI メタデータ提案は**提案型**である。人がボタンを押したときだけ生成し、
人が承認して初めてメタデータになる。材料の組み立て
（`packages/api/src/services/suggest/prompt.ts` の `ResourceMaterial`）も、
形式別の判定も、そこに揃っている。

足りないのは**自動であること**だ。抄録は、人が押さなくても付いていなければ意味がない。
そして自動化した瞬間に、提案型が持っていた 3 つの前提が消える。

- **同意** — 人が押す行為が、外部 AI に中身を送ることへの同意を兼ねていた
- **承認** — 人が確認しないまま文章が公開ページに出る
- **責任** — 誰も直さない文章がカタログに残り得る

本 ADR はこの 3 つに明示的に答える（決定 5・7・9）。

### 5. 測定が前提を覆した

決定を書いたあとにスパイク Phase A・Phase B を実行し、**8 つの前提が覆った**。本文の各決定は
実測後のものである。根拠はすべて付録に置く。

| 当初の想定                                 | 実測                                                                                | 帰結                                                                              |
| ------------------------------------------ | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |

| Excel は PDF より一桁安い                  | 同一内容で CSV 5,253 / XLSX 5,250 トークン。**どの形式も 1 文字 ≒ 1 トークン**      | 「安い」は圧縮バイトで比べた誤り（付録 8）                                        |

| 文書は常に原本を渡すのが良い               | テキスト層があれば**抽出テキストが同等以上で 1.7〜9.3 倍安い**                      | 材料をテキスト層の有無で分けた（付録 16・決定 3.6）                               |

## 決定（提案）

### 1. 目的は抄録。表示が主で、埋め込みは副産物

「AI が説明をつける」には性質の違う 3 つが同居している。

| 案               | 内容                       | 表示   | 失敗の代償                       |
| ---------------- | -------------------------- | ------ | -------------------------------- |
| (a) 抄録         | このファイルは何か         | する   | 小さい（本体を開けば分かる）     |
| (b) 検索の裏方   | 埋め込みの材料としてのみ   | しない | 見えない（誰も誤りに気づけない） |
| (c) 読み解き補助 | 読み方・注意点・インサイト | する   | 大きい（材料が主張を支えない）   |

**(a) を採る。** 失敗が一番安く、効果が一番確実で、(b) は無料でついてくる。
(c) は要求される品質が一段上がるのに、材料は先頭数 KB とサンプル数行しかない。
**材料が支えられない主張を書かせる構図**になるため採らない。

(b) を単独で採らないのは、**隠れた AI テキストは誤りを誰も指摘できない**からである。
表示すれば、間違っていれば報告が来て、編集者が直せる。可監査性は表に出したほうが高い。
実際、生成した抄録が**リソース名の誤りを指摘した**例がある（付録 6）。

**インサイトは埋め込みに入れない。** 「少子高齢化の進行が読み取れます」のような文は
どのデータセットにも当てはまる語を混ぜ込むので、再現率を上げても適合率を落とす。
書かせるのは**中身と、生活語への言い換え**である（決定 3・8）。

### 2. AI の推論はサマリー文の生成に限る

> **AI の出力を、人の確認なしに機械が使うのは、説明文とその埋め込みだけ。**

この書き方は ADR-040 の既存の提案フロー（人が承認するもの）を否定しない。
承認を挟むものは従来どおり、挟まないものは説明文に限る。

**列の型・主キー・ヘッダー行の位置・シート構造の確定は、本 ADR では生成しない。**
それらは仕様書 §14.1-4（主キー/型の AI 提案、ADR-040 拡張）の枠に属し、
提案 → 人の確認 → 確定値としての永続化という別の骨格を必要とする。

理由は決定論である。パイプラインは同じ入力から同じ解釈が出ることを前提に組まれている
（ADR-046）。推論を解釈経路に置くと、同じファイルから毎回違うスキーマが出得る。
**ヘッダー行の判定が再実行で 1 行ずれれば、行レベル差分（ADR-043 層 2）は全行が
変更されたと報告する。** 値に委ねるなら、推論を残さず決定を残さなければならない。

**代償を明記する。Excel はデータとして使えるようにならない。** 構造化された答えを
受け取らないなら、XLSX にスキーマも Parquet も生まれず、表プレビューにも `/query`
（ADR-032）にも MCP にも乗らない。「何のデータか分かる」だけで、「データとして触れる」
わけではない。使えるようにする話は §14.1-4 の枠で別途判断する。

### 3. 材料 — 表とテキストは既存の材料、文書と画像は原本

原則は 1 行で書ける。

> **原本を渡すのは、そうしないと中身が取れないときだけ。** テキスト層のある文書も、表も、
> 既にある材料のほうが安く、しかも同等以上に読める。中身の量が事前に読めないものは、
> 投げてエラーで判定する。

#### 3.1 形式別の材料

| 形式                        | 材料                                    | 追加実装 |
| --------------------------- | --------------------------------------- | -------- |
| CSV / TSV                   | スキーマ（列名 + 型）+ サンプル 5 行    | なし     |
| テキスト系                  | ストレージ本体の先頭                    | なし     |
| ZIP                         | ファイル一覧                            | なし     |
| GeoJSON                     | 先頭数地物の properties + 地物数        | 小       |
| **PDF（テキスト層あり）**   | **抽出テキスト**（3.6）                 | 小       |
| **PDF（テキスト層が薄い）** | **原本をそのまま渡す**（3.6〜3.8）      | 小       |
| **XLSX / XLS / DOC / DOCX** | **原本をそのまま渡す（3.4）**           | 小       |
| PPT / PPTX                  | **抽出テキスト**（原本は渡せない、3.4） | 小       |
| **画像**                    | **原本を渡す。5MB 超は縮小**（3.4）     | 小       |
| 上限超過・サイズ不明        | **生成しない**（決定 5）                | —        |

表とテキストは既存の材料（ADR-040 の `ResourceMaterial`）がそのまま使える。**表は原本を
渡さない** — 日本語 CSV は 1 KB あたり 700〜860 トークンで 474KB からコンテキストを超え、
スキーマ + サンプル行の 10 倍かかる（付録 7）。列名と数行で残りは推測できる。

PDF はテキスト層の有無で材料を分ける（3.6）。**抽出テキストが十分にあるならそちらが安く、
しかも同等以上に読める** — 実測で 1.7〜9.3 倍の差がついた。薄いときだけ原本を渡し、その
場合は Bedrock の Converse も Anthropic の Messages API も PDF を文書として受け取り、
ページの画像化はプロバイダ側が行う。追加の実装は判定と受け渡しだけで、**MVP の実装面積は
小さい**。

#### 3.2 メタデータは必ず添える。ただし材料ではなく文脈として

ファイルの中身だけでは抄録は書けない。**固有名詞の根拠**（ファイルに自治体名が無ければ
「○○市の」と書けない）、**文脈**（どのデータセットの中の 1 ファイルか）、**重複の回避**
（`notes` の繰り返しをしない）の 3 つに、データセットのメタデータが要る。

ところが現在の `buildResourceUserContent`（`suggest/prompt.ts`）が第 1 段に渡すのは
`name` / `description` / `format` / `size` / `columns` / `sampleRows` / `textHead` / `files`
だけで、**データセットのタイトルも組織名もタグも入っていない**。ADR-040 の
`GROUNDING_RULES` は「固有名詞は材料**または既存のメタデータ**に根拠を置け」としているが、
その既存メタデータが届いていない。

ADR-040 がこれを渡していないのは意図的だと考えられる — データセットのタイトルを見せると
**全リソースがその言い換えになる**（オウム返し）。したがって、

- **`datasetContext` として明示的に分けて渡す。** リソース自身の材料と混ぜない
- 中身は**タイトル・組織名・タグ・`notes` の先頭数百字**（`notes` は最も効くが最も
  オウム返しを招くため上限を置く）
- 役割を指定する — **文脈と固有名詞の根拠に使う。メタデータの言い換えに終始せず、この
  データセットの中でこのファイルが何を担っているかを書く**（主題に触れること自体は
  自然でよい。決定 8）
- **専門用語・行政用語には利用者が使う日常語を括弧で併記させる。** 埋め込みは語彙の距離を
  縮めるが**ゼロからは作らない**。文書側に日常語が現れないと生活語のクエリは届かない。
  明示併記させた抄録は 8 クエリすべてで類似度が高く、生活語クエリでは +10pt 前後だった
  （付録 6）

コストは 1 リソースあたり数百トークンで、無視できる。

**メタデータは文脈であって、材料ではない。** 上限を超えたリソースを「メタデータはあるの
だから生成できる」とはしない。既に画面に出ている情報の言い換えに抄録の価値はなく、
材料のない作文は幻覚の温床になる。

#### 3.3 上限はバイト数とページ数の二重で置く

**トークン数はページ数で決まる。** テキスト PDF もスキャンも 1 ページ ≒ 1,600〜3,000
トークンで、本文の量にはほとんど依存しない（付録 2）。バイト数はトークンの予測子に
ならず、4MB 以下に 467 ページの PDF があった。

- **バイト数: PDF 16MB / Office 1MB** — ダウンロード前に `resource.size` で判定できる
  第一の門。**当初 4MB としたのは誤りだった**（下の注記）
- **PDF のページ数: 50 ページ。** API のハード上限は **100 ページ**（`A maximum of 100 PDF
pages` で拒否される）。50 で PDF の 90% を拾い、100 にすると対象率 4 ポイント増に対して
  平均コストが 1.2 倍、30 に下げると対象率が 70% に落ちる（付録 2）。**超過したファイルは
  拒否せず、先頭 50 ページを渡す**（下の注記）

> **注記（実装時に改訂、2026-09-15）— バイト上限は費用を守っていない**
>
> 当初の 4MB は「別カタログの PDF の 87% が収まる」という**被覆率**の数字だった。これは
> 上限が答えるべき問いのどちらでもない。
>
> 実測した（付録 19）。Sonnet 4.6 でページ数を 2 に固定し、描画されないストリームで
> バイト数だけを膨らませたところ、**3MB でも 22.6MB でも入力は 3,158 トークンで不変**、
> 22.9MB で `Input is too long for requested model.` として拒否された。
>
> **バイト数はトークンを買わない。買うのはページ数であり、それは既にページ上限が縛って
> いる。** バイト上限が実際に守っているのは 2 つだけである。
>
> 1. API の受理限界（実測 約 22.7MB）
> 2. worker のメモリ — ページ数を数えるためにファイル全体を保持する
>
> したがって **PDF は 16MB** とする。1 に対して要求の残り（システムプロンプトと利用者
> コンテンツ）の余地を残し、2 に対して十分小さい。
>
> **4MB が実際に失っていたのはスキャンである。** 38 ページ・6.9MB の意識調査報告書は
> テキスト層が 37 文字（すべて改行）で、3.6 が定めた「薄いときは原本」の経路しか持たない。
> それをバイト数だけで拒否していた。16MB でこの資料は抄録を得た。
>
> **Office の 1MB は据え置く。** そちらは根拠が別で、いまも生きている — XLSX は原本の
> バイト数がそのままトークンに効き、1.5MB が 91.9 万トークンに達する（付録 11）。PDF と
> 違って中間のページ表現を持たないためである。

**上限はコストで決まる。被覆率では決まらない。** 上限なしでは 1 リソースあたりの平均が
23k トークンまで上がり、上限を置くと 4k に下がる（コストの節）。

**入力トークンの上限を指定する API パラメータは存在しない。** Converse の
`inferenceConfig` は `maxTokens`（**出力**の上限）・`temperature`・`topP`・`stopSequences`
の 4 つだけで、Anthropic の Messages API の `max_tokens` も出力専用である。入力側を抑える
手段は 3 つしかない。

| 手段             | 効き方                       | 精度                                 |
| ---------------- | ---------------------------- | ------------------------------------ |
| モデルの選択     | コンテキスト長がそのまま天井 | ハード。ただし世代と紐づく（決定 6） |
| バイト上限       | ダウンロード前に判定できる   | 形式による（付録 8）                 |
| アプリ側での推定 | 送信前に自前で見積もる       | 形式ごとに実測済み（下表）           |

| 形式           | 推定式               | 実測                    |
| -------------- | -------------------- | ----------------------- |
| PDF            | **ページ数 × 2,500** | 1,985〜3,078 tok/ページ |
| CSV / テキスト | 文字数 × 1           | 0.99 tok/字             |
| XLSX           | 文字数 × 1           | 1.08〜1.22 tok/字       |

**PDF は pdf-lib でページ数を読めば純 JS で推定できる。** CSV とテキストは原本を渡さない
ので無関係である。**XLSX / DOC だけが、事前推定にファイルを開く必要を残す** — そこは
3.4 のとおりエラーで扱う。

#### 3.4 Office 形式は原本渡し。超過はエラーで弾く

**XLSX / XLS / DOC / DOCX は PDF と同じく原本を渡す。** 実測では DOCX 22KB が 761 トークン、
92KB が 14,491、DOC 46KB が 682 と安い（付録 11）。神エクセル（帳票・レイアウト用途）も、
原本を渡すならモデルがレイアウトごと見るため、**表として解釈する必要がない** — スキーマを
作ろうとして壊れる問題は起きない。

**残る問題は、事前にトークン量を測れないことである。** XLSX は ZIP 圧縮された XML で、
ファイルサイズから中身の量が読めない（1 KB あたり 8〜1,445 字、191 倍の開き。付録 8）。
事前推定にはファイルを開く必要があり、そのコストは MVP では払わない。

**したがって、投げてからエラーで判定する。**

| エラー                                               | 意味         | 扱い                                  |
| ---------------------------------------------------- | ------------ | ------------------------------------- |
| `ValidationException` / `document.format` の検証失敗 | 形式が未対応 | **恒久**（形式単位）                  |
| `ValidationException` / `prompt is too long: N > M`  | 大きすぎる   | **恒久**（リソース単位。N を記録）    |
| `ThrottlingException` / 429 / 5xx                    | 一時的       | **リトライ**（決定 4.2 のバックオフ） |

**超過エラーは実トークン数を返す**（`prompt is too long: 919286 tokens > 200000 maximum`）
ため、**失敗した試行そのものが測定になる**。記録すれば二度目は事前に弾ける。
拒否は 2.9〜4.2 秒で返り、`ValidationException` は推論前の拒否なので課金されないと
考えられる（請求で確認する）。

**一時的な失敗を「対象外」として記録してしまわないこと**が実装上の要点である。

**PPT / PPTX は API が受け取らない。** Bedrock Converse の `DocumentFormat` は
`csv / doc / docx / html / md / pdf / txt / xls / xlsx` の 9 種で、PPT 系を含まない
（`@aws-sdk/client-bedrock-runtime` の `models/enums.d.ts`）。これは選択ではなく能力の
問題であり、3.5 の能力照会がそのまま処理する。

**ただし、原本を渡せないことは材料が無いことを意味しない。** Index ステップは
`isDocumentFormat` の全形式（PPTX を含む）から本文を抽出して保存しており、実カタログの
PPTX には 1,955 バイトのテキストが既にあった。決定 3.6 が「テキスト層があれば抽出テキストの
方が同等以上に読める」と結論した以上、**原本が渡せない形式こそ抽出テキストを見るべきである。**

> **原本を渡せる形式は原本を渡し、渡せない形式は抽出テキストを見る。どちらも無いときだけ
> 対象外とする。**

これは当初「PPT 系は対象外」としていた判断を狭めるものである。当初の理由は「API が受け取らない」
であり、それは**原本について**の事実でしかなかった。抽出テキストの経路は決定 3.6 で後から
確立されたため、取りこぼしていた。

**Office 形式そのものは原本渡しのままとする**（3.6）。抽出テキストに切り替えるかは同じ比較を
してから決める話であり、ここで変えているのは「原本を渡せないとき何もしない」だけである。

**画像も原本を渡す。ただし上限の性質が違う。** Converse は `gif / jpeg / png / webp` を
受け取り、**トークン数は画素数で決まってファイルサイズと無関係**である — 8,256 × 5,504 の
写真を 1600px に縮小すると 1,697 トークンで、**PDF 1 ページ（2,500）より安い**（付録 13）。

上限は **API のハードな 5MB**（`image exceeds 5 MB`、モデル非依存）である。**これは
トークンを抑えるための上限ではなく、API が受け取らないという制約**であり、PDF や Office の
バイト上限とは性質が異なる。

**5MB を超える画像は、長辺 1600px に縮小して渡す。** 対象カタログの画像 19 件は 7.1〜9.7MB
で全て 5MB を超えるため（付録 9）、縮小しなければ画像は 1 件も扱えない。

縮小は**全面展開を伴わない**。JPEG は shrink-on-load（libjpeg の DCT 段階での縮小）が効き、
8,256 × 5,504 の写真でピーク RSS が **365MB → 105MB** に下がる（付録 13）。130MB の
フルサイズのビットマップを一度も作らないためである。Node では `sharp`（libvips）が同じ
ことをし、libvips 自体もストリップ単位で処理する。**対象カタログの画像はすべて JPEG**
なので、実ケースの 100% でこれが効く。

費用は **`sharp` の依存 1 つ**（prebuilt バイナリが配布されており、ビルド環境の要求は
増えない）と数行の実装である。パイプラインの並列度は `p-limit` で絞られているため、
同時に走る縮小は数件に収まる。**ディスク経由（`streamToTempFile`）は、
PNG の巨大なものが実際に問題になってから**でよい — PNG には shrink-on-load に相当する
仕組みがない。

**エラー経路が保証するのは実行可能性であって、コストではない。** 天井はモデルの
コンテキスト長であり（決定 6）、バイト上限が唯一の事前の防波堤である。**Office の
バイト上限は PDF より低く 1MB とする** — 実測で 1.5MB の XLSX が 91.9 万トークンに
達しており、1M コンテキストのモデルでは成功して 1 ファイルで $2〜$4.6 かかる（付録 11）。

#### 3.5 プロバイダの能力はアダプタに問う

`getEmbeddingInfo()` が null を返し埋め込みが skip される先例と同じ形で、**「この形式を
文書として渡せるか」をアダプタに問う**。プロバイダ名でアプリ層を分岐させないので、ADR-005
の原則は保たれる。AIAdapter の interface は現在プロンプト文字列しか受け取らないため、
**文書を渡せるよう拡張する**（影響の節）。

**対応形式はプロバイダで差が出る。** Ollama や NoOp の環境では文書を渡せないため、
CSV とテキスト系には抄録が付き、PDF には付かない。**機能の有無ではなく対応形式の差**として
扱い、隠さずに示す。

#### 3.6 PDF はテキスト層の有無で材料を分ける

**1 ページあたりの文字数が十分なら抽出テキストを渡し、薄いときだけ原本を渡す。** 閾値は
100 字/ページとする（決定 5 の判定と同じ信号を使う）。

Phase B で 9 件の PDF を両方の材料で生成し、比較した（付録 16）。

| 1 ページあたり文字数 |     原本の入力 | 抽出テキストの入力 |     倍率 | 判定                       |
| -------------------: | -------------: | -----------------: | -------: | -------------------------- |
|                **0** |          8,234 |                359 |     22.9 | **原本のみ可**             |
|   344〜2,074（8 件） | 3,987〜128,154 |      2,390〜15,060 | 1.7〜9.3 | **抽出テキストが同等以上** |

**テキスト層があるなら、原本を渡す価値はない。** 44 ページの統計資料では原本が 128,154
トークンかかったのに対し抽出テキストは 13,723（9.3 倍）で、**出力は抽出テキストのほうが
具体的だった**（原本側が触れなかった「警察署ごと」「市区町村別の事故率」に言及）。目次の
資料でも同様で、**テキスト層には目次がそのまま入っているのに、原本渡しはページ画像から
読み直している**。

**テキスト層が空のときだけ逆転する。** そのとき抽出テキストの側は「テキストの抽出が
できなかったため、具体的な内容を確認することができない」と正しく申告し、**捏造しなかった**。
原本渡しの側は町別人口表を正確に読み、世帯数まで拾った。

この変更でコストが下がる。demo カタログの PDF 47 件は **1.63M → 0.53M トークン（-68%）**、
カタログ全体で中型モデル **$8.51 → $6.30** になる（付録 16）。

**Office 形式は原本渡しのままとする。** 同じ比較を行っていないためであり、抽出経路
（officeparser）はワーカーに既にあるので、後続で測って判断する。

> **注記（実装時に改訂、2026-09-15）— 「1 ページあたりの文字数」は読み出し上限で割っては
> いけない**
>
> 抽出テキストの読み出しは 16,384 バイトで打ち切られる（ADR-040 の
> `SUGGEST_TEXT_HEAD_BYTES` を流用）。それを**文書の総ページ数**で割ると、日本語では
> 約 5,400 文字 ÷ ページ数になり、**約 54 ページを超える PDF はすべて「薄い」と判定される**。
> 中身とは無関係に、上限の大きさを測っているだけだからである。
>
> 467 ページの下水道事業年報がこれに当たった。実際のテキスト層は **1 ページあたり 1,034
> 文字**で閾値の 10 倍あるのに、11 文字/ページと判定されて原本に回された。
>
> **したがって比は、読み出しが上限に達していないときだけ判断に使う。** 上限まで埋まって
> いるなら、テキスト層が濃いことはそれ自体で実証されている。
>
> **そしてこの誤判定は「安全側に倒れる」ものではなかった。** 当初のコメントは「誤差は
> 原本を送る側に倒れる — 何でも読める経路だから」と書いていたが、その年報の原本渡しは
> 「有効なテキストや図表を抽出することができなかった」と返した。原本は**何でも読める経路
> ではない**（次の注記）。
>
> **残された論点: 16KB という読み出し上限そのもの。** これは ADR-040 が提案生成のために
> 決めた値で、抄録が流用している。575,761 文字の年報から 6,198 文字を読むのは目次と総説の
> 途中までで、抄録は成立するが全体像としては目次に依存する。抄録に適した値は別に測るべき
> である。

#### 3.7 ページ数を超えた PDF は、先頭 50 ページを渡す

当初は拒否としていた。**それは何も買っていなかった。**

トークンはページ数に従うので、50 ページという上限が**そのまま 1 ファイルの費用の天井**で
ある。50 ページに切って渡す費用は、ちょうど 50 ページの文書を受け入れる費用と同じである。
拒否して得たものは無く、失ったのは**抄録の価値が最も高い資料**だった — 467 ページの
下水道事業年報、165 ページと 135 ページの調査報告書は、いずれも沈黙していた。

**読者に伝えるべきは、一部しか読んでいないという事実である。** 決定 7 の注記には既に
その場所がある（`coverage`）。全体を渡した原本は `coverage` を持たず、一部を渡した原本は
持つ、という形で区別する。

材料ダイジェストにもページ上限を含める。上限を引き上げたとき、**古い上限で書かれた抄録が
作り直される**ためである。全体を渡した原本のダイジェストは動かさない。

#### 3.8 暗号化された PDF はページを取り出せない

`pdf-lib` の `ignoreEncryption: true` は、保護された文書の**構造を解析するが復号はしない**。
ページ数を数えるには足りるが、`copyPages` でページを取り出すと、暗号化されたままの
コンテンツストリームが鍵を持たない新しい文書へ渡り、**全ページが白紙になる**。

575,761 文字を持つ 467 ページの年報から、白紙 50 ページを作って送ってしまった。モデルは
正しく「抽出できなかった」と申告した。

**数えるのは安全、取り出すのは安全でない。** `isEncrypted` で切り詰めを拒否する。

なお **Index ステップの `officeparser` は同じファイルから 575,761 文字を抽出できている。**
空パスワードの暗号化（権限制限のみ）を正しく扱うためで、抽出テキストの経路はこの種の文書でも
成立する。3.6 の判定を直した結果、この年報は抽出テキストの経路を通るようになった。

### 4. 生成はパイプラインの最後のステップで行う

**MVP では、抄録の生成をパイプラインのステップとして Fetch → Interpret → Index → Lake の
後に置く。** 別ジョブにはしない。

理由は 3 つある。

- **原本が手元にある。** Fetch が取得した直後なので、別ジョブにするとストレージから
  **もう一度ダウンロードする**ことになる
- **再生成のトリガーがそのまま使える。** 抄録を作り直すのは材料が変わったときであり、
  それは**パイプラインが走るときと同じ**である。別ジョブにすると、同じ条件を自前の
  ハッシュ判定で再現することになる
- **バックフィルの経路が既にある。** キューのメッセージは `{ resourceId, rebuildOnly }` を
  受け取り、`rebuildOnly` は外部 URL を取りに行かずに再処理する。埋め込みの全件再構築が
  既にこれを使っており、**抄録の全件生成も同じ経路に乗る**

そして **SQS キューをサイトごとに 1 本増やさずに済む**（CDK と compose の両方に手が入る）。

#### 4.1 成立させるための 3 つの条件

1. **ベストエフォートにする。** LLM の失敗は理由を記録し、**ステップを失敗させない**。
   これで「AI が落ちると Index が落ちる」という依存が生まれない
2. **ステップの最後に置く。** 遅延も失敗も上流に影響しない
3. **バックフィルは既存の `rebuildOnly` に乗せ、静かな時間帯に流す。** 数千リソースで
   1 時間前後パイプラインを占有するが、**埋め込みの全件再構築が既に同じ性質**であり、
   運用の作法も同じである

#### 4.2 それでも守ること

- **DB トランザクションを LLM 呼び出しをまたいで開いたままにしない。** claim を取る →
  コミットする → LLM を呼ぶ → 結果を書く。ワーカーの接続プールは `WORKER_DB_POOL_MAX` = 3
  であり、待ち時間ぶん接続を握るとワーカー全体が止まる
- **可視性タイムアウトを LLM の最悪レイテンシより長く取る。** 実測は 3〜11 秒だが
  （付録 14）、スロットルからの再試行を含めた最悪値で取る。短いと再配信され、**同じ生成に
  二重に課金される**。版に紐づくハッシュで結果は冪等だが、トークン代は戻らない
- **429 には指数バックオフで応じる。** バックフィルでは必ず当たる

DuckLake のカタログ全体ロックとは交差しない。抄録の生成は lake に触れない。

#### 4.3 実行予算の分離は後続に置く

**代償は、リソース単位の実行 claim（ADR-044）を 3〜11 秒ぶん長く握ることと、アップロードの
処理と同じ並列度の枠を共有することである。** パイプラインは既に fetch + interpret + lake で
数秒〜数十秒その claim を握っているため、増分は 2〜5 割にとどまる。

これが問題になったときに、専用キューと専用ポーラーへ分ける（「MVP の後に検討すること」）。
**着手の判断材料は「アップロードの処理が目に見えて遅くなったか」**であり、決定 5 の
「理由を画面に出す」と同じく観測に基づいて決められる。

### 5. 生成しない条件を明示し、理由を画面に出す

| 条件                     | 判定                                                                       |
| ------------------------ | -------------------------------------------------------------------------- |
| 上限超過・サイズ不明     | `resource.size`。**バイナリを渡す形式にのみ適用する**（画像は API の 5MB） |
| 対象外の形式             | PPT 系、プロバイダが受け取れない形式（決定 3）                             |
| **送ってみて拒否された** | **`ValidationException`。恒久の失敗として記録する**（決定 3.4）            |
| 材料が空                 | CSV でスキーマが取れていない、テキストが空                                 |
| 非公開・下書き           | `state = active` のパッケージに属するリソースのみ                          |

**サイズ上限はバイナリを渡す形式にのみ適用する。** CSV はスキーマとサンプル行を使うので
**ファイルサイズに関係なく生成できる** — 対象カタログには 4MB 超の CSV が 10 件（最大 78MB）あるが、
材料は一定である。表形式はスキーマの有無で判定する。

**いずれの場合も、理由を画面に出す。**

> このファイルはサイズ上限を超えるため、説明を生成していません

黙って無いのと理由が書いてあるのとでは、カタログとしての受け取られ方が違う。そして
**これがそのまま「上限超過への対処が必要か」の観測点になる** — 理由付きで表示されている
リソースが多ければ、後続に着手する根拠になる。

**非公開・下書きのリソースの中身を、人の操作なしに外部 AI へ送らない。** 埋め込みが
「下書きは公開時に埋め込む」（ADR-039）としている線と同じである。下書きに説明が欲しい
場合は、ADR-040 の手動提案（人が押す = 同意）を使う。

**モデルの自己申告も記録する。** 出力（強制 JSON）に「材料で説明できたか」のフラグを 1 つ
足す。10 トークン程度でただである。ただし**このフラグは捏造を捕まえられない** — スキャン
PDF を小型モデルに渡すと、読めていないのに自信を持って中身を作り、「読めない」とは言わな
かった（付録 5）。MVP では経路の切り替えに使わず、記録と計測に使う。

**「使えない」と「使わない」は別の状態として扱う。** AI アダプタが NoOp の環境では機能が
存在せず、決定 10 で無効にしている場合は意図的に使っていない。画面の文言を分け、
`suggest/availability.ts` の語彙に揃える。

### 6. 生成はリソース単位の一段だけ。既定は上位モデル

リソース 1 本 = 1 完了で抄録（200〜300 字）を作る。**データセット単位の統合生成は行わず、**
埋め込みにはパッケージの抄録を**連結して**入れる（決定 8）。

ADR-040 は二段構成（リソースごとの生成 → データセットの統合）を採るが、本 ADR は第 1 段
だけを使う。連結なら**データセットあたり 1 回の LLM 呼び出しが消え**、統合（圧縮）で
削られる**各ファイル固有の語彙が残る** — 生活語の問題に効くのはまさにその語彙である。
1 回のコンテキストが上限に収まるため、閉域網の小さいローカルモデルでも成立する。

**ただし、すべてのパッケージには収まらない。** 対象カタログには **102 本のリソースを持つ
パッケージ**があり、300 字の抄録を連結すると **294 パッケージ中 28 件（10%）が 8,000 字を
超える**（付録 15）。超過分は決定 8 の組み立て順で末尾から切られるため、**それらのリソースの
抄録はパッケージのベクトルに届かない**（リソースページには出る）。

**MVP はこの打ち切りを受け入れる。** 現在の埋め込み材料は平均 196 字なので、末尾が切れても
**今よりはるかに厚い**。後退するものはない。

**そして統合生成でも解決しない。** 超過するパッケージは同じ物の繰り返しではなく、**一つ
ずつ主題の違う表が百枚**並んでいる（付録 15）。統合は圧縮なので、各表に固有の語彙はどちらに
しても削られる。**百の主題を 1 本のベクトルに畳むこと自体が問題**であり、これは粒度の話で、
決定 8 のリソース単位のベクトルでしか解けない。MVP の直後にそれを行う。データセット単位の
統合生成は、それが入った**後**でなお必要なら再考する。

**モデル選択は、コストの判断であると同時に正しさの門である。** ただし理由は
「スキャンだから」ではない — **資料が判読しやすいかを事前に判別できないから**である。

Phase B で、テキスト層がゼロの PDF を**小型モデルが正確に読んだ**（付録 16）。Phase A で
同じ小型モデルが捏造した資料（昭和 9 年の旧字体・縦組み）とは、資料の性質が違った。
今回のものは `Microsoft: Print To PDF` 由来で、**抽出できないだけで中身は鮮明な現代の活字**
である。

> **「0 字/頁」は「スキャン画像」を意味しない。** 抽出の失敗と、判読の困難さは別の軸である。

1 ページあたりの文字数はテキスト層の有無しか教えず、**画素の読みやすさは分からない**。
したがって原本を渡す経路では、**判別できない以上は読める側に倒す**。

テキスト層ゼロの資料を読めるかどうか自体は、**モデルの大きさではなく世代で決まった**
（付録 5・12）。

| モデル                     | コンテキスト | スキャン PDF          |
| -------------------------- | -----------: | --------------------- |
| 小型（Haiku 4.5）          |         200k | ❌ 自信を持って捏造   |
| 上位・旧世代（Sonnet 4.5） |         200k | ❌ 捏造（留保は付く） |
| 上位・新世代（Sonnet 4.6） |           1M | ✅ 正しく読む         |

テキスト文書でも新しい世代のほうが項目の網羅性・単位の精度が高く、**日常語の言い換えを
指示なしで出す**（付録 10）。

**Amazon の Nova でも同じ向きが出た。上位・旧世代の Nova Pro が、小型・新世代の
Nova 2.0 Lite より悪い**（付録 18）。Nova Pro は鮮明なスキャンすら読まず、データセットの
メタデータだけから作文した。単価は Sonnet 4.6 の 1/9 だが、**両機種とも採れない**。

**そして現在の Bedrock のラインナップでは、スキャンを読める世代と 1M コンテキストが
一致している。** これが天井の話と絡む — 200k のモデルを選べばコストの天井は 1 リソース
$0.20〜$0.40 に固定できるが、**スキャンを捏造するモデルしか選べなくなる**。

- **既定は、劣化した資料も読める世代のモデルとする。** コスト差は 2,600 件で $12、
  25,000 件で $115 にすぎず、**捏造のほうが重い** — 公開ページに出た嘘の説明は、検索順位の
  劣化と同じく検算されにくい
- **小型モデルは、読めているときでも言明が粗い。** Phase B では同じ資料から「高齢者が
  被害者の**大多数**」と書き、上位モデルは「割合が**類型によって大きく異なる**」と書いた
  （付録 16）。衝突する言明であり、材料を超えているのは前者である
- **読めないモデルをスキャン資料に当ててはならない。** コストのつまみを回した結果として
  捏造が生まれる構成にしない
- **コストの天井を厳しく固定したい配備には、200k のモデルを選ぶ道がある。** ただしその場合は
  スキャンの検知（1 ページあたりの文字数）を実装し、**スキャンには生成しない**ことが条件に
  なる。MVP では採らない（「MVP の後に検討すること」）
- テキスト層の有無による振り分けは、規模が効いてきたときのつまみとして残す

### 7. 表示は断り書き付きで、編集者が握れる形にする

リソースページに表示する。断り書きには **AI が生成したことに加えて、何を材料にしたかと
生成元の版を書く。**

> この説明は、全 87 ページのうち先頭部分と抜粋から AI が生成しました（2026-09-12 の版）

材料の範囲を書けば利用者は何を検算すればよいか分かり、**生成元の版**（ADR-043）を書けば
リソースが更新されたのに抄録が古いまま残っている状態が見える。「AI が生成」とだけ書かれた
古い説明が残るのが、最悪の形である。

**免責文は置く。ただしそれは守りではない。** 公開ページの文章は読み手にカタログの言明として
届くので、「正確性を保証しません」と書けば責任が移るという立て付けは採らない。守るべき線は
文言ではなく、**モデルに何を言わせるか**の側にある（以下の 4 項目）。

その上で、免責文には断り書きが担わない仕事が 1 つある — **原本が正であること**を示すことで
ある。抄録は定義上二次資料であり（JIS X 0813）、それを読んで判断を終えてよいものではない。
これは責任の回避ではなく、抄録が何であるかの説明である。

> ※ 内容の正確性・最新性を保証するものではありません。正式な内容は原本のファイルをご確認
> ください。

**配備先が独自の文言を必要とする場合はブランドの上書き層（ADR-023）で差し替える。**

- **材料を超えた言明を禁じる。** とくにサンプル 5 行から導かれる期間・件数・最大最小は
  ほぼ確実に誤るうえ、最ももっともらしく読める。Phase A では禁じても数量の言明が出た
  （「18 の主要な支出科目」）ため、出力形式の側でも抑える（判定基準 1）
- **長さは字数ではなく文数で指示し、理由を添える。** Phase B の実測では、字数で指示すると
  6 件中 5 件が超過し、**文数（3〜4 文）は 6 件すべてで守られた**。さらに「検索用のベクトルに
  載せる予算があるため」と目的を添えると平均 353 字 → 295 字に縮んだ（付録 16）。
  **字数で機械的に切ってはならない** — 実測 18 件すべてが「。」で完結しており、途中で
  切れるのは切ったときだけである。予算に当たったときは**埋め込みに入れる側で文単位に
  落とす**（決定 8）
- 文書では「読んだ範囲に限る」— 本文に書かれている期間は引用してよい
- 固有名詞は材料か既存メタデータに根拠があるものだけ（ADR-040 の `GROUNDING_RULES`）

**編集者は上書き・非表示にできる。** 既定で表示し、編集者が上書きすれば人手の説明に
昇格する。人手の説明が既にあるリソースでは、AI 文を主役にしない。

### 8. 埋め込みへの投入は、組み替えて足す

**メタデータを置き換えるのではなく、組み替える。** 抄録の連結を `buildEmbeddingText` に
加え、既存の要素は落とさない。**打ち切りは実際には起きていない** — 埋め込みテキストは
平均 196 字・最大 1,254 字で、8,000 字超えは 0 件だった（付録 3）。組み立て順は、リソースが
極端に多いデータセットのための安全網として決めておく。

**予算に当たったときは文単位で落とす。** 字単位で切ると文が途中で終わる。抄録は「。」で
完結しているので（付録 16）、末尾の文を丸ごと落とせば読める文章のまま縮む。
**リソース単位のベクトルに移れば、1 ベクトル = 1 抄録になるのでこの制約自体が消える。**

| 順  | 内容                               | 備考                                     |
| --- | ---------------------------------- | ---------------------------------------- |
| 1   | title / notes / tags               | 現行どおり                               |
| 2   | **抄録の連結（1 本 200〜300 字）** | 新規                                     |
| 3   | リソース名                         | 公式のファイル名。短く特徴的な語彙を含む |
| 4   | リソースの description             | 上限に当たったときに最初に切れる         |

**抄録はベクトルの主成分になる。** 現在の材料が平均 196 字しかないところに平均 3.6 本 ×
300 字を連結するので、埋め込みテキストは数倍になる。効果の見込みは大きい（抄録の語彙の
82〜95% はメタデータに無い — 付録 3）が、**リスクも同じだけ大きい** — 抄録が的外れなら
ベクトルも的外れになり、表示と違って検索順位の劣化は見えにくい。決定 1 で「失敗が安い」
としたのは表示の話である。したがって検索の質が悪化していないことの確認を必須にする
（判定基準 6）。

**繰り返しは無駄ではないが、逓減が大きい。** 埋め込みはトークン埋め込みの平均なので、
ある語の占める割合が増えればベクトルはその方向へ引かれる（重み付け）。ただし既に入っている
語の重み付けは逓減が大きく、組織名や定型句のような**全データセットに共通する語の繰り返しは
識別性を下げる**。言い換えや中身の記述は新しい方向を足すので逓減しない。抄録の 200〜300 字は
**メタデータが言っていないこと**（中身、粒度、対象範囲、生活語の言い換え）に使う。

**抄録は埋め込みハッシュの入力になる。** 埋め込みは組み立てたテキストの SHA-256 で差分を
判定している（`embedding_hash`）ため、依存の鎖が 1 本増える。

```
リソースの中身が変わる → 抄録が再生成される → 埋め込みテキストが変わる → 再埋め込み
```

**機能を有効にした時点で全パッケージの埋め込みハッシュが変わる。** 有効化は「抄録の
バックフィル → 埋め込みのバックフィル」の 2 段になる。埋め込みは LLM を呼ばないので安い。
無効のサイトでは何も変わらない。

**リソース単位のベクトルを持つかは、本 ADR では決めない。** 19 本の異質なリソースを 1 本の
ベクトルに平均すると、どの主題にも似ていない重心になる。抄録は MVP の時点でリソース単位に
存在するため追加の生成コストはゼロで、MVP の直後に A/B できる。ただし検索の問い合わせ経路が
変わるため、抄録の導入とは段を分ける（「MVP の後に検討すること」）。

### 9. 再生成は版に紐づけ、バッチは織り込まない

抄録は独自のハッシュを持ち、**材料（リソースの中身・スキーマ）が変わったときだけ**
再生成する。タイトルを直しただけでは走らない。ハッシュにはモデルとプロンプトの版も含める
（`embedding_model` + `embedding_hash` と同じ形）。全件生成は管理画面
（`/admin/reindex-embeddings` の隣）に置く。

**Batch API（50% 引き）は採らない。** 増分生成には最大 24 時間の遅延があり使えず、
バックフィルでの節約額は Bedrock のバッチ推論経路（S3 マニフェスト入出力、同期呼び出しとは
別 API）を実装・保守する費用に見合わない。将来 10 万件規模で必要になったら、バックフィル
経路だけ足せばよい。

バックフィルで実際に効く制約は金額ではなく、**レート制限・スループット・再開可能性**で
ある。版に紐づけたハッシュがあれば、途中で落ちても生成済みはスキップされる。

### 10. 既定は無効。有効化はサイトの環境変数で行う

自動生成は推論コストを伴い、リソース数に比例して積み上がる。したがって**既定は無効**とし、
有効化はサイトの環境変数で行う。ランタイム設定（ADR-036）には置かない — ランタイム設定は
サイト管理者が変更できるが、**この機能のコストを負担するのはサイトを配備・運用する側**で
あり、設定する主体と負担する主体が一致しないためである。環境変数はマルチサイトでもサイト
個別（ADR-041 の SiteStack）なので、サイト単位の切り替えとしては十分である。

ADR-038 は `REGISTRATION_ENABLED` を廃してランタイム側へ移したが、あれは運用判断であって
コストを伴わない。本 ADR が環境変数を選ぶのは、**負担の所在が異なる**からである。

**そしてその環境変数は、使うモデルの名前そのものとする。未設定が無効を意味する。** 真偽値と
モデル指定を分けると「有効なのにモデル未選択」という、どこかで辻褄を合わせなければならない
状態が生まれる。そして**モデルの選択は無料の設定ではない** — Sonnet 4.6 と Haiku 4.5 で 3 倍、
Nova とは 9 倍違う（付録 18）。上の理由（負担の所在）はモデルにもそのまま当てはまるので、
2 つは 1 つの判断である。**allowlist の外のモデルは既定に差し替えず拒否する** — 既定とは
`AI_COMPLETION_MODELS` の先頭でしかなく、そこに読めないモデルが来たときに出るのは、出来の
悪い抄録ではなく捏造した抄録である（付録 18）。生成言語だけがランタイム設定に残るが、
非対称は説明が付く — **言語はただ、モデルは金**。

**有効化は増分生成のみを開始する。** 全件生成は管理画面からの明示的な操作とし、実行前に
対象リソース数と推定トークン数を提示する。見積もりは形式とサイズ・ページ数から出せる
（コストの節）。

**無効のあいだは何も書かない。** 後から有効にしたときは再処理で作れるので、無効な状態には
費用がかからない。**無効に戻しても、既に生成された説明は消さない。** 生成を止めるだけで
あり、一括削除は別の管理操作として置く。

## コスト

**対象カタログ（2,608 リソース）の実額は $9.66〜$48.30、定常運用は月 $0.97** である
（付録 15。付録 9 は同じカタログの先行測定で、材料の規則を詰める前の値である）。98% が CSV
（中央値 6KB）で PDF も XLSX も無く、材料が小さいため**出力トークンが全体の 4 割**を占める
— このカタログでは入力側の上限より**抄録の長さ**がコストに効く。

以下は形式構成が異なるカタログ向けの一般的な見積もりである。前提: CSV 45% / Excel 20% /
PDF 25% / その他 10%、決定 3 の上限（4MB / 50 ページ）を当てて **1 リソース 4k 入力 /
0.3k 出力**（システムプロンプト込み）。実測では PDF が 1 ページ 2,500 トークン、表は
1〜2k である（付録 2・7）。

| リソース数 | 小型 | 中型 |   上位 |
| ---------- | ---: | ---: | -----: |
| 2,600      |  $12 |  $24 |    $59 |
| 25,000     | $115 | $230 |   $575 |
| 100,000    | $460 | $920 | $2,300 |

上限を置かない場合は 2,600 件で $65 / $121 / $303、25,000 件の中型で $1,160 になる。
**上限がコストの唯一のつまみである**（決定 3）。

定常運用（更新されたリソースのみ）は 1 リソースあたり 0.6〜2.8 セント。25,000 リソースの
カタログで月に 5% が更新されるとして **月 $7〜$35**。

**コストは設計の判断材料にならない。** 最安と最高の差はバックフィル 2,600 件で $12 対 $59
である。品質で選べばよく、決定 6 のとおり既定は上位モデルとする。

プロンプトキャッシュはこの用途では効かない。共有できるのはシステムプロンプト（700 トークン
程度）だけで、材料はリソースごとに異なるためプレフィックスの再利用が原理的にない。

> 単価は Anthropic 第一者 API のレート（2026-06 時点、入力/出力 $/1M: 小型 = 1/5、
> 中型 = 2/10、上位 = 5/25）に基づく。**Bedrock では推論プロファイルの選択で変わる** —
> `global.*`（宛先は全商用リージョン）は第一者と同額、`jp.*` のような地理限定（宛先は
> ap-northeast-1 / ap-northeast-3 の 2 つに固定）は **+10%** である。2026-09-12 の請求で
> 実測した。KUKAN の既定は `jp.*` なので、**上の表を 1.1 倍したものが Bedrock の額**になる。
> 消費税は請求側で別に加算される（配備先の税制による）。Vertex は未確認。

## スパイク

公開データカタログの実データ（298 データセット / 2,608 リソース）を対象に、二段で行う。
**対象は `state = active` のパッケージに属するリソースに限る**（決定 5）。

> **スパイクの全測定は `thinking` なしで行った。** 本 ADR のコスト・所要時間・長さの数値は
> すべてその前提である（付録 17）。

### Phase A — 推論なしで測る（実施済み）

被覆率、バイト数とトークン数の関係、材料が空のリソースの実数を測る。**結果は付録にある。**
一部は別カタログ（604 リソース）での実測であり、対象カタログでの再実行は残っている。

### Phase B — 層化サンプルで実際に生成する（実施済み）

demo カタログの PDF 9 件を 1 ページあたり文字数で層化し（0〜2,074 字/頁）、3 つの軸で
比較した。**結果は付録 16 にある。**

| 軸           | 比較                           | 結果                                                     |
| ------------ | ------------------------------ | -------------------------------------------------------- |
| **材料**     | 原本渡し 対 抽出テキスト       | **テキスト層があれば抽出テキストが同等以上**（決定 3.6） |
| モデル       | 小型 / 上位                    | **世代で決まる。ただし密度では判別できない**（決定 6）   |
| 文章の書き方 | 自然な記述 対 生活語の明示併記 | **抄録 +5.5pt、併記でさらに +1.7pt**（決定 3.2）         |

**材料の軸は決定 3 を変えた。** demo カタログのコストは中型モデルで $8.51 → $6.30 に下がる。

### Phase C — 安いモデルが使えるかを測る（実施済み）

Amazon Nova は単価が一桁安いため、抄録に使えるかを別に測った。**使えない。** document
ブロックは通るが強制 JSON が壊れ、スキャンでは捏造する。**結果は付録 18 にある。**

**残るのは nDCG の前後比較**（判定基準 6）である。埋め込みの類似度では確認したが、
`pnpm eval:search` による比較には抄録そのものが要るため、実装後に行う。

### 判定基準

1. **材料を超えた言明が 0 件**（期間・件数・固有名詞）。1 件でも出れば決定 7 の禁止条項が
   効いていない。Phase A の素のプロンプトでは出た
2. **図表主体の PDF が読めているか** — 抽出テキストで取りこぼす部分を、原本を渡すことで
   拾えているか
3. **自己申告フラグと人の判断の一致率** — モデルが「材料で説明できた」と言ったものを人が
   読んで同意できるか
4. 上限超過・材料が空のリソースに対して**生成を試みていない**こと
5. **抄録として成立していること。** 文が途中で切れていない（実測 18/18 が「。」で完結）。
   字数は目安であり、**リソース単位のベクトルに移った時点で制約としては消える**（決定 8）
6. **検索の質が改善していること。** `pnpm eval:search` のゴールデンセット（ADR-034）で、
   抄録を加える前後の nDCG を比べる。抄録はベクトルの主成分になる（決定 8）ため、
   **悪化していないことの確認は必須**である。あわせて「自然な記述」と「生活語の明示併記」を
   比べ、付録 6 の類似度差を追認する。併記が出るかはモデルと資料に依存する（介護の例では
   出なかった）ため、**出力に日常語が含まれているか**を計測項目として持つ

   **ローカルと demo は別々に測る。** 質問セットは環境ごとに別で（正解のデータセット名が
   環境ごとに違うため、ADR-034 のとおり `golden-queries.yaml` はコミットしない）、
   **埋め込みモデルも違う**。

   | 環境     | 質問セット                 | 規模                   | 埋め込み              | 読み方                             |
   | -------- | -------------------------- | ---------------------- | --------------------- | ---------------------------------- |
   | ローカル | `golden-queries.yaml`      | 39 問 / 168 パッケージ | Titan v2（1024 次元） | **悪化していないかの確認**         |
   | demo     | `golden-queries.demo.yaml` | 39 問 / 184 パッケージ | Cohere embed-v4       | **本番構成での効果**（こちらが正） |

   どちらも exact / synonym / natural を 13 問ずつ持つ。**モデルが違うので絶対値は
   比較しない** — 各環境の前後差だけを見る。

   **抄録を入れる前の基準線**（2026-09-12 実測、キーワードのみ → ハイブリッドの overall
   nDCG。内訳は ADR-034 の「再測定」）:

   | 環境     | 基準線        | exact                         |
   | -------- | ------------- | ----------------------------- |
   | ローカル | **38% → 82%** | 100% → 100%（劣化の余地なし） |
   | demo     | **29% → 87%** | 88% → 98%                     |

   正解データセット名は両環境とも全件が現存している（ローカル 56/56・demo 41/41）ので、
   **セットを作り直さずにそのまま前後比較ができる**。

### 成果物の扱い

数値は本 ADR に記録する（正本はここ）。生成結果の生データはコミットしない。
ハーネスをリポジトリに同梱するかは別途判断する。`pnpm eval:suggest`（ADR-040）が
近い形なので、構造を流用する。

## 影響

- **adapters/ai**: AIAdapter の interface を拡張し、プロンプト文字列に加えて**文書を渡せる
  ようにする**。あわせて「この形式を文書として渡せるか」の能力照会を足す
  （`getEmbeddingInfo()` と同じ形）
- **worker**: パイプラインに抄録のステップが 1 つ増える（最後、ベストエフォート）
- **api**: 抄録の取得・上書き・非表示の経路。材料の組み立ては `suggest/` と共有するが、
  **`buildResourceUserContent` は派生が要る** — 提案フロー（ADR-040）は第 1 段にデータ
  セットの文脈を渡さない設計であり、抄録は渡す設計である（決定 3）
- **web**: リソースページの表示と断り書き、生成しなかった理由の表示、編集者の操作
- **web（管理画面）**: 全件生成の操作と、実行前の見積もり表示
- **db**: 抄録の本文・ハッシュ・生成元の版・生成日時・自己申告フラグを保持する列
- **shared**: 有効・無効の環境変数、上限の定数
- **worker の依存**: `sharp`（画像の縮小。prebuilt バイナリ）
- **既存の ADR-040 提案フロー**: 変わらない。材料の組み立てを共有するだけ
- **パイプライン**: 最後にステップが 1 つ増える。既存の 4 ステップの挙動は変えない

再実行の性質は ADR-046 のまま変わらない。抄録は版（イミュータブルな正本）から作られるので、
同じ入力からは同じ材料が渡る。

## やらないこと（MVP の範囲外）

- **値の生成**（型・主キー・ヘッダー行・シート構造の確定）— 仕様書 §14.1-4 の枠
- **PPT 系の原本渡し**（決定 3.4。API が受け取らない）。ただし抽出テキストからの生成は行う
- **全文 OCR** — 別 ADR の規模
- **インサイトの生成** — 材料が支えない
- **Batch API の採用** — 節約額が実装費用に見合わない（決定 9）
- **下書き・非公開リソースの自動生成** — 手動提案（ADR-040）を使う
- **`thinking` の有効化** — **抄録生成は読解であって推論ではない。** 実測で課金される出力が
  2 倍になり、質は改善しなかった（付録 17）。しかも `effort` を `low` にすると
  **adaptive thinking 自身が思考を切る** — 既定（thinking なし）は、モデルが自分で選ぶ状態と
  一致している。`effort` は thinking の深さのつまみなので、thinking を使わない以上は
  効く対象がない。長さを詰めたいなら決定 7 のとおり**プロンプトで文数と目的を指示する** —
  2 倍よく効いて、追加費用がない

## MVP の後に検討すること

MVP を出してから、**観測に基づいて**着手を判断する。いずれも実装面積が MVP 本体に
匹敵するため、必要が確認されるまで着手しない。

### 材料の経路

- **Office 形式の抽出テキスト** — PDF では抽出テキストのほうが安く同等以上だった（決定 3.6）
  が、Office では同じ比較をしていない。抽出経路（officeparser）はワーカーに既にあるので、
  測って判断する
- **PDF のページ抜粋** — pdf-lib で先頭数ページ + 中間数ページの小さな PDF を組み立てる。
  純 JS でラスタライザ（pdfium / poppler / mupdf）を持ち込まずに済む。上限超過の PDF を
  救う手段
- **Office の事前推定** — XLSX / DOC はファイルを開かないとトークン量が読めず、MVP では
  エラーで弾いている（決定 3.4）。開いて文字数を数えれば事前に判定でき、失敗の往復
  （2.9〜4.2 秒 + アップロード）を省ける。神エクセルの判別（結合セルの比率、数式の有無、
  セルの疎密）自体を材料にする手もある
- **Excel の格子** — シート名を全件 + 先頭数シートを TSV 化し、書式化値・結合セルの前方
  補完・使用範囲のトリム・非表示シートの除外を行う。原本渡しと違い**トークン量をこちらで
  決められる**。素の値では日付がシリアル値 `46000` として渡り、結合セルの空白が「空の列が
  ある」と読まれるため、格子を作るならこの 2 つは必須である
- **PNG の巨大な画像** — JPEG は shrink-on-load でメモリを抑えられるが、PNG には同じ仕組みが
  ない（決定 3.4）。実際に問題が出たら、ディスク経由（`streamToTempFile`）に切り替える
- **抽出テキストの層化サンプル** — 先頭 1 ブロックだと長い報告書で表紙と目次に埋まる。
  先頭・中間・末尾から均等に取る

### 実行予算の分離

- **専用キューと専用ポーラー** — 抄録の生成をパイプラインから切り出す（決定 4.3）。LLM は
  3〜11 秒かかり、数百ミリ秒で終わる fetch や interpret とは 1〜2 桁違うため、同じ並列度の
  枠を共有するとアップロードの処理が待たされる。とくにバックフィルで顕在化する。
  キューはマルチサイトでも既にサイト個別（ADR-041）なので、1 本足す費用は小さい。
  **着手の判断材料は「アップロードの処理が目に見えて遅くなったか」**
- **ECS サービスの分離** — 独立してスケールさせたくなってから。同一イメージで第 2 の
  サービスを立て、無効なサイトでは `desiredCount` を 0 にすれば費用は生じない
- **Lambda への切り出しは主経路にしない** — アプリ層は AWS / 非 AWS で共通という ADR-041 の
  原則に反し、同じロジックに入口が 2 つでき、並列度・リトライ・DLQ の挙動が環境ごとに
  分岐する。しかも律速は計算資源ではなく **DB 接続数とプロバイダのレート制限**で、
  どちらも Lambda では解けない

### コストのつまみ

- **モデルの振り分け** — 1 ページあたりの文字数でテキスト層の有無を判定し、テキスト主体は
  小型、スキャンは上位に振り分ける。節約額は 25,000 件で $109 程度（全件上位 $230 に対して
  $121）。規模が効いてきたときのつまみであり、入れる場合も「スキャンに小型を当てない」
  という向きは崩さない。**振り分け先の候補として Nova を測ったが、画像を見せない材料でも
  材料を超えた言明が出たため現時点では成立しない**（付録 18）
- **推論プロファイルの選択（Bedrock）** — `jp.*` から `global.*` に替えると 10% 下がる。
  ただし**処理先が全商用リージョンに広がり**、AWS の説明によれば入出力が不正利用検知のため
  他リージョンに保存され得る。宛先リストも AWS の都合で増える（地理限定のリストは変わらない）。
  **10% は処理を国内に閉じることの対価**であり、コストだけで選ぶものではない。国内処理を
  約束する配備では採らない

### 品質と範囲の拡張

- **リソース単位のベクトル（MVP の直後に入れる）** — 決定 8 のとおり、順序は決まっている。
  100 前後の異質な表を 1 本のベクトルに平均すると**どの主題にも似ていない重心**になり、
  10% のパッケージでは末尾が打ち切られる（付録 15）。実装上は、ADR-034 のベクトル検索が
  PostgreSQL の pgvector で `package.embedding` を引いているため、リソース単位にすると
  **行数が約 9 倍**になり（ADR-034 は意図的にインデックスを張っていない）、データセットの
  順位を**リソースのスコアから集約**して決める必要が出る。ADR-025 の parent-child は
  キーワード検索側（OpenSearch）の仕組みなのでそのままは使えない
- **データセット単位の統合生成**（ADR-040 の第 2 段）— リソース単位のベクトルを入れた
  あとでも必要なら戻す（決定 6）
- **他形式への展開** — GeoPackage、FlatGeobuf など

### 運用と配備

- **有効・無効の二層化** — 環境変数を天井とし、ランタイム設定（ADR-036）からは**下げる
  方向にだけ**動かせる弁を置く。配備側が許可した範囲で、サイト側が「AI 生成テキストを
  載せない」方針を選べる。上げる方向を環境変数に残す限り後から足せる
- **Excel を LibreOffice headless で PDF 化**し、PDF 経路に合流させる案。形式が 1 本化され
  レイアウトも保たれるが、イメージが数百 MB 増え変換も秒単位でかかる

### 本 ADR と独立に進められるもの

- **表データ向けの安い改善** — 列名・組織名・カテゴリを `buildEmbeddingText` に含める。
  推論コストがかからず、表データの語彙の問題には直接効く

## 残課題（MVP を出すまでに決めること）

1. 断り書きの具体的な文言と、生成言語（ja / en 両方を作るか、既定ロケールのみか。
   両方作るとコストが倍になる）
2. 抄録を `notes` とは別の列に持つとして、CKAN 互換 API に出すかどうか
3. 「材料が空」の判定の実値
4. 上位モデルのうちどれを使うか（Phase B で決める）
5. 埋め込みテキストの組み立て順の具体（決定 8 の連結をどこに挟むか）
6. AIAdapter の interface 拡張の形 — 文書をどう表現し、能力照会をどう返すか。ADR-005 の
   「アプリ層は分岐しない」を保つ書き方を決める
7. 決定 6 の打ち切りをどう扱うか — MVP は受け入れる方針だが、リソース単位のベクトル
   （決定 8）を入れる時期の判断と合わせて決める

## 付録: Phase A の実測（2026-09-12）

別カタログ（604 リソース / 168 パッケージ）で構造を測り、**Bedrock に原本を投入して実トークン
数を実測**した（Converse の document ブロック、ap-northeast-1）。対象カタログでの再実行は
残っている。

### 1. サイズと構造

| 形式 |           件数 | 分布                                                                                              |
| ---- | -------------: | ------------------------------------------------------------------------------------------------- |
| PDF  | 51（4MB 以下） | ページ数 中央値 **2**・p90 45・最大 467。1 ページあたり文字数 中央値 1,071・最小 486              |
| XLSX |             60 | シート数 中央値 1・p90 3・最大 13。セル数 中央値 800・p90 26,502・最大 390,632。非表示シート 6 枚 |

4MB を超える PDF 8 件（最大 52MB）も個別に確認したが、平成 18 年度の下水道事業年報
（498 ページ）でさえ 1,014 字/ページのテキスト層を持っていた。**このカタログの PDF 60 件は
すべてテキスト PDF で、スキャンは 1 件も無い。**

### 2. トークン数はページ数で決まる

| 種別                     | ページ | サイズ | 本文文字数 | 実トークン | 1 ページあたり |
| ------------------------ | -----: | -----: | ---------: | ---------: | -------------: |
| テキスト PDF             |      1 |  131KB |      1,559 |      3,078 |          3,078 |
| テキスト PDF             |      2 |  301KB |      1,665 |      5,012 |          2,506 |
| テキスト PDF             |     40 | 1.08MB |     42,858 |     95,891 |          2,397 |
| テキスト PDF             |     64 |  427KB |     28,802 |    127,041 |          1,985 |
| テキスト PDF             |     67 | 1.67MB |          — |    176,261 |          2,631 |
| **画像のみ（スキャン）** |      5 | 1.67MB |      **0** |      8,019 |      **1,604** |
| 135 / 165 / 467 ページ   |      — |      — |          — |   **拒否** |              — |

**本文が 1,559 字でも 28,802 字でも 0 字でも、トークンはページ数で決まる。** 画像分が
支配的であり、テキスト層が無いスキャンはむしろ安い。抽出テキスト量からの見積もりは
**2〜4 倍の過小評価**になる。

XLSX は 106 セル → 310、3,136 → 8,365、15,160 → 10,969 トークン。**PDF より一桁安い。**

**100 ページが API のハード上限**（`A maximum of 100 PDF pages`）。67 ページは通り、135 /
165 / 467 ページは拒否された。4MB の内側でも到達する。

### 3. 抄録が足す語彙の量

生成した抄録と、そのリソースのメタデータ（リソース名 + データセット名 + 組織名 + タグ）で
文字 bigram を比較した。

| サンプル                     | メタデータ |   抄録 | 新規 bigram |  新規率 |
| ---------------------------- | ---------: | -----: | ----------: | ------: |
| 市民活動団体アンケート       |     101 字 | 265 字 |         165 | **82%** |
| 政治団体名簿（政党支部）     |      29 字 | 171 字 |         118 | **95%** |
| 各会計歳入歳出決算書（歳出） |      54 字 | 226 字 |         171 | **95%** |
| 財政のあらまし               |      74 字 | 196 字 |         133 | **87%** |

**抄録の語彙の 8〜9 割がメタデータに存在しない。** 「決算書　歳出」というリソース名からは、
議会費・福祉保健費・教育費・警察費・国民健康保険事業・都営住宅事業といった語は一切出て
こない。抄録はそれらを出す。

ただし**強いのは専門語彙であって、生活語ではない**。システムプロンプトで「専門用語には
日常語を括弧で添えよ」と明示しても、小型モデルでは 2 回とも併記が出なかった。モデルは
**資料に書かれている語を書く方に強く引かれる**（決定 8、判定基準 6）。

### 4. 原本渡し 対 抽出テキスト（図表主体の資料）

1 ページあたり 308 字のグラフ主体の会議資料（9 ページ）で、同一ファイルを 2 通りで生成した。

|                    | 入力トークン | 出力の要点                                                                           |
| ------------------ | -----------: | ------------------------------------------------------------------------------------ |
| A 原本渡し         |   **16,811** | 「2050年には全国人口の56.7％に達すると予測」（図表由来と見られる数値を 1 点）        |
| B 抽出テキストのみ |    **2,700** | 「人口20万人以上の都市に住む人口の割合が昭和22年の15.3％から平成27年の53.1％へ増加」 |

**B のほうが具体的で、コストは 6 分の 1 だった。** 三大都市圏・東京圏への集中・2 割の無居住化・
札幌仙台広島福岡といった要点は両者とも拾っている。**この 1 件に限れば、原本渡しが 6.2 倍
払って得たものは僅かである。**

中央値の PDF（2 ページ）でも原本 5,000 対テキスト 2,100 で 2.4 倍、40 ページで 2.2 倍。
**テキスト層がまともな文書に対して、原本渡しは 2〜6 倍のコストを払っている。**

これは決定 3 の「原本をそのまま渡す」を揺らす。ただし 1 サンプルであり、この資料は
スライドで要点がテキストボックス（＝テキスト層）に入っていた。**Phase B の筆頭の軸として
検証する。**

### 5. スキャン PDF は読める。ただしモデル次第

国立国会図書館デジタルコレクション pid 1445565（**『大審院判決全集 第1輯』昭和 9 年、
法律新報社**）のスキャン画像 5 ページから、テキスト層ゼロの PDF を組み立てて投入した。

**上位モデル（Sonnet 相当）— 正しく読んだ**

> 大審院における民事・商事関係の判決録を収めた法律報告誌の一号分である。各頁は縦組みの
> 旧字体・片仮名交じり文で印刷されており（略）親族会の同意を得ずに行われた未成年者の
> 不動産取引の効力、債権譲渡契約の解除、扶養方法の選択と民法九六一条の理由の存否、
> 会社公告を要する方法と商法施行法第二条の適用（略）

**小型モデル（Haiku 相当）— 完全に捏造した**

> 本資料は、昭和初期の日本の歴史や社会に関する学術的な論文や記事を集めた文献です。
> （略）政治、経済、文化など多岐にわたるテーマを扱っています。（略）経年による劣化が
> 見られますが、内容は比較的良好に判読できます。

小型モデルは**内容ではなく見た目を説明し、残りを一般論で埋めた**。そして
**「読めません」とは一言も言わなかった。** 決定 5 で「モデルは足りないと言うのが苦手」と
書いた懸念の実例である。自己申告フラグはこの型の失敗を捕まえられない。

### 6. 生活語の明示併記は、埋め込みで測ると効く

「言い換えは埋め込みが橋渡しするから、プロンプトで併記させる必要はない」という推論を、
埋め込みの類似度で直接検証した。同じリソースについて 3 通りのテキストを作り、Cohere
embed-v4（demo の構成）でコサイン類似度を測った。

- **a**: メタデータのみ（現状の `buildEmbeddingText` 相当）
- **b**: a + 自然な記述の抄録
- **c**: a + 生活語を明示併記させた抄録

**子育て施設一覧**（リソース名は誤って「観光施設一覧」）

| クエリ                     |     a |     b |         c |    b−a |         c−b |
| -------------------------- | ----: | ----: | --------: | -----: | ----------: |
| 小さい子を預けるところ     | 0.253 | 0.278 | **0.390** | +2.5pt | **+11.3pt** |
| 子どもの預け先             | 0.281 | 0.331 | **0.429** | +5.0pt |  **+9.8pt** |
| 赤ちゃんを見てもらえる場所 | 0.283 | 0.271 |     0.305 | −1.2pt |      +3.5pt |
| 保育                       | 0.285 | 0.370 | **0.424** | +8.6pt |      +5.3pt |

**介護サービス事業所一覧**（同上）

| クエリ                     |     a |     b |     c |    b−a |    c−b |
| -------------------------- | ----: | ----: | ----: | -----: | -----: |
| お年寄りの介護サービス     | 0.362 | 0.374 | 0.383 | +1.2pt | +1.0pt |
| 高齢者向けの施設を探したい | 0.345 | 0.344 | 0.363 | −0.0pt | +1.9pt |
| 年寄りを預けられるところ   | 0.222 | 0.233 | 0.245 | +1.1pt | +1.1pt |
| 介護                       | 0.338 | 0.371 | 0.383 | +3.3pt | +1.3pt |

**8 クエリすべてで c > b。** とくに本 ADR の出発点そのものの形のクエリ
（「小さい子を預けるところ」「子どもの預け先」）で **+10pt 前後**の差が出た。

理由は出力を見れば分かる。b は「保育施設」「認定公立保育所」「受入年齢」と書き、
**「小さい子」「預ける」という語をどこにも含まない**。c は「保育所（**子どもを預かる施設**）」
「一時預かり（**短期間だけ子どもを預けるサービス**）」と書く。**埋め込みは語彙の距離を
縮めるが、ゼロからは作らない。** 文書側に「預かる」が現れなければ、「預けるところ」との
距離は縮まりきらない。

**ただし条件付きである。** 介護の側は +1〜2pt と小さい。c でも「高齢者（お年寄り）」の併記が
出なかったためで（CSV に「高齢者」の語が無く、モデルは「介護や生活支援を行う施設・事業者」
と書いた）。**指定が効くのは、モデルが実際に適切な日常語を出したときだけ**であり、
指定すれば必ず出るわけではない。

なお b の抄録は、**リソース名が「観光施設一覧」と誤っていることを指摘した**
（「実際の内容は介護サービス事業所の情報です」）。抄録はメタデータの誤りの検出にも効く。

### 7. 表は原本を渡すより、スキーマ + サンプル行が 10 倍安い

対象カタログの CSV を原本のまま Converse に渡して測った。

| ------: | -----: | -----------------------------: | -----: |
|     6KB |     39 |                          5,253 |    859 |
|   145KB |    902 |                         97,273 |    673 |
|   474KB |  2,180 | **拒否**（prompt is too long） |      — |
| 2,779KB | 28,352 |                       **拒否** |      — |

**日本語 CSV は 1 KB あたり 700〜860 トークン**（数値・区切り・コード値がすべてトークンに
なる）。**474KB で既にコンテキストを超える。**

| ---------------- | -----------------: | -----------------------: |
| 送れる件数       |              2,429 |                **2,542** |

| Sonnet 相当      |            $122.82 |               **$18.81** |

**入力は 10.3 倍、そのうえ 4.4% が送れない。** 表は「中身の大部分が反復する値」であり、
**列名と数行を見れば残りは推測できる**。原本を渡す価値は文書に比べて小さい。

### 8. ファイルサイズは、形式によってコストの予測子にならない

同一内容を CSV と XLSX に変換して測ると、**CSV 5,253 トークン / XLSX 5,250 トークン**で
ほぼ一致した。**どの形式でも中身の 1 文字 ≒ 1 トークン**（実測 0.68〜1.22）である。
違うのは「バイト数から中身の量が読めるか」だけである。

| 形式     | 1 KB あたりの中身               |         実測 tok/KB |
| -------- | ------------------------------- | ------------------: |
| CSV      | 871 字でほぼ一定                |                 859 |
| **XLSX** | **8〜1,445 字（191 倍の開き）** | **130 / 401 / 976** |
| PDF      | ページ数次第                    |               約 39 |

XLSX の内訳は、書式主体のもの（84KB・8,989 字 → 130 tok/KB）とデータ主体のもの
（67KB・96,478 字 → **976 tok/KB**）で 7.5 倍違う。**データ主体の XLSX は CSV の 859 を
上回る** — ZIP 圧縮により 1 KB に詰まっている中身が多いためである。

なお同一内容の CSV 6KB が XLSX では 11KB になった。**小さいファイルでは ZIP のオーバー
ヘッド（複数の XML パーツ、sharedStrings、styles）が圧縮の効果を上回る。**

**結論: XLSX にバイト数の上限をかけても意味がない。** 4MB の XLSX は密度次第で 5 万
トークンにも 400 万トークンにもなり得る（決定 3）。

は `maxTokens`（出力）・`temperature`・`topP`・`stopSequences` の 4 つだけである。

### 12. コンテキストの天井はモデルで決まる

91.9 万トークンと判明しているファイルを各モデルに投げ、上限を測った。

| モデル         | 結果                         |
| -------------- | ---------------------------- |
| Haiku 4.5      | 拒否。`> **200000** maximum` |
| Sonnet 4.5     | 拒否（`Input is too long`）  |
| **Sonnet 4.6** | **受理**（919,270 トークン） |
| **Opus 4.7**   | **受理**（919,306 トークン） |

**この検証自体が、議論していたリスクの実例になった** — 1 ファイル 1 回で、2 モデル合わせて
**$8.09** を消費した（請求で確認。Opus $5.06 + Sonnet $3.03）。1M コンテキストのモデルでは、
**バイト上限が唯一の事前の防波堤**である。

そして**スキャンを読める世代と 1M コンテキストが一致している。** Sonnet 4.5（200k・上位
クラス）に付録 5 と同じスキャン PDF を渡すと、**存在しない組織名を作った**

（「思われます」「可能性があります」）、内容は誤りである。**軸はモデルの大きさではなく
世代である。**

### 13. 画像はトークンが画素数で決まる

対象カタログの空中写真（8,256 × 5,504、8.6MB）で測った。

| 入力                   | 結果                                                    |
| ---------------------- | ------------------------------------------------------- |
| 原寸 8.6MB             | ❌ **`image exceeds 5 MB`**（モデル非依存のハード上限） |
| 1600px に縮小（640KB） | ✅ **1,697 トークン**                                   |

**トークン数は画素数で決まり、ファイルサイズと無関係である。** 1,697 トークンは CSV 1 件
（1.5k）と同程度で、**PDF 1 ページ（2,500）より安い**。

**縮小は全面展開を伴わない。** 同じ写真を 1600px に落とすときのピーク RSS を測った。

| 方式                                              | ピーク RSS |
| ------------------------------------------------- | ---------: |
| 素直にデコードしてから縮小                        | **365 MB** |
| **shrink-on-load**（libjpeg の DCT スケーリング） | **105 MB** |

8,256 × 5,504 の RGB ビットマップは 130MB であり、前者はそれを丸ごと持つ。後者は
**フルサイズのビットマップを一度も作らない**。105MB の大半はランタイム自体の
オーバーヘッドである。

生成された抄録（上位モデル、リソース名は「11_〈地区名〉全景」のみ。**固有名は伏せている**）:

> 〈港湾を所管する部局〉が提供する空中写真データセットの一画像で、臨海地区の全景を真上から
> 撮影したものです。画面中央から上部にかけて水路が走り、複数の埠頭や岸壁が水際に沿って
> 配置されています。（略）右側には格子状の住宅街と円形の構造物を含む公園状の緑地が確認できます。
> 左側の海面には船舶が数隻写っており、岸壁にはクレーンや荷役設備とみられる構造物も
> 見られます。

2 例目**だが、正誤の判断には人が要る。

#### モデル — 小型が読めた

**テキスト層ゼロの同じ PDF を、小型モデルも正確に読んだ**（令和 8 年 9 月 1 日、

活字である。**抽出の失敗と判読の困難さは別の軸**であり、1 ページあたり文字数では後者を
判別できない（決定 6）。

ただし小型は**読めていても言明が粗い**。犯罪統計から「高齢者が被害者の**大多数**」と書き、
上位モデルは同じ資料から「割合が**類型によって大きく異なる**」と書いた。衝突する言明で
あり、材料を超えているのは前者である。

| メタデータのみ → 抄録（併記なし）           |                        **+5.5pt** |

個別では「犬の登録ができる病院」が +15.1pt、「自転車の盗難」が +12.2pt と大きい。
一方、併記の上乗せは付録 6（+10pt 前後）より小さかった。**上位モデルは指示がなくても
併記するため**であり（「犯罪率（人口10万人あたりの認知件数）」が併記なしの出力にも現れた）、
**指示が効くのはモデルが自発的に出さないときである**。

| -------------- | ----------------------- | --------------- | -------: | -------: |
| 200〜300 字    | 319 385 391 342 356 297 | 5 6 3 5 5 4     |      5/6 |  **6/6** |
| 3〜4 文        | 361 330 431 329 336 319 | **4 4 4 4 4 4** |      6/6 |  **6/6** |
| 3〜4 文 + 目的 | 219 317 337 291 342 266 | 4 4 3 4 4 4     |  **3/6** |  **6/6** |

**文数は正確に守られ、目的を添えると縮む**（平均 353 字 → 295 字）。そして**実測 18 件
すべてが「。」で完結した** — 文が途中で切れるのは、字数で機械的に切ったときだけである。

### 17. モデル自身が、抄録生成に推論は要らないと判断する

生成の制御に使えそうな Bedrock Converse のパラメータを一通り測った。**効いたのはプロンプト
だけだった。**

| パラメータ          | Bedrock                   | 本 ADR での判断                                               |
| ------------------- | ------------------------- | ------------------------------------------------------------- |
| `maxTokens`（出力） | ✅ 使用中（既定 2,048）   | **暴走の天井**。長さ制御には使わない — 文の途中で打ち切るため |
| 入力トークンの上限  | ❌ 存在しない             | バイト / ページ上限で代替（決定 3）                           |
| `thinking`          | ✅                        | **使わない**                                                  |
| `effort`            | ✅ ただし小型モデルは不可 | `thinking` を使わない以上、**効く対象がない**                 |
| 長さ                | —                         | **プロンプトで文数 + 目的**（決定 7）                         |

#### `thinking` — 抄録は 8% 縮むが、課金は 2 倍

中型モデルで 4 回ずつ。抄録と思考をそれぞれ `CountTokens` で数えて内訳を出した。

|          | 課金される出力 | うち抄録 | うち思考 |
| -------- | -------------: | -------: | -------: |
| なし     |        **236** |      232 |        0 |
| adaptive |        **478** |  **213** |      246 |
| 差       |      **+103%** |  **−8%** |     +246 |

**「考えてから書くと引き締まる」は起きている。** ただし抄録 19 トークンの短縮に 246 トークン
払っており、13 倍の値段である。決定 7 の文数 + 目的の指示は同じ効果を 2 倍の幅（−16%）で、
追加費用なしに出す。

**質でも改善を確認できなかった。** 一般会計 5 行しかない材料から、thinking 側の 1 件が

> 収録されているのは一般会計を含む**複数の会計区分**で、議会費・総務費・民生費など幅広い
> 費目を**網羅**しています

と書いた。どちらも材料にない（判定基準 1）。thinking なしの 3 件はそろって
「**少なくとも** 2024 年度の一般会計を含み」「**サンプルとして確認できる**」と留保していた。
4 対 4 の小標本であり「thinking が幻覚を増やす」とまでは言えないが、**抑える証拠は出なかった**。

対象カタログに当てると出力は 0.77M → 約 1.56M トークン、中型で **$19.32 → $27.1（+40%）**
になる。このカタログは出力が全体の 4 割を占めるため（付録 15）、出力を倍にする変更は重い。

#### `effort` — thinking の深さのつまみである

`inferenceConfig` ではなく `additionalModelRequestFields.output_config.effort` に入れる。
**thinking を切った状態では効かない。** 思考が無いのだから当然で、最初にその条件で測って
「効かない」と結論したのは測定設計の誤りだった。thinking を入れて測り直すと**単調に動く**
（中型モデル、各 3 回の平均）。

| 設定                       | 課金される出力 | 抄録 |     思考 |
| -------------------------- | -------------: | ---: | -------: |
| thinking off / effort なし |            240 |  236 |        0 |
| thinking off / effort low  |            221 |  217 |    **0** |
| thinking off / effort max  |            255 |  251 |    **0** |
| **ON** / effort **low**    |        **230** |  226 |    **0** |
| **ON** / effort medium     |            275 |  224 |       31 |
| **ON** / effort なし       |            482 |  218 |      253 |
| **ON** / effort high       |       520〜550 |  226 |      259 |
| **ON** / effort max        |     989〜1,402 |  200 | 353〜385 |

thinking off の 3 行が 217〜251 の間で揺れているのは effort への反応ではなく**ばらつき**で
ある（思考は全件 0）。

**注目すべきは `ON / low` で思考が 0 になることである。** 課金 230 は thinking なしの 240 と
実質同じで、**adaptive thinking 自身が「この仕事に考える余地はない」と判断して思考を切って
いる**。抄録の長さは `low` から `high` まで 218〜226 とほぼ動かず、`max` だけ 200 に縮むが
課金は最大 6 倍、しかもばらつきが大きい（思考 288〜434）。

> **既定（thinking なし）は、モデルが自分で選ぶ状態と一致している。**

受け付ける値もモデルで違う。**小型モデル（Haiku 4.5）は値そのものを拒否する**
（`This model does not support the effort parameter.`、`jp.` でも `global.` でも同じ）。
中型（Sonnet 4.6）は `xhigh` を拒否し、上位（Opus 4.7）だけが 5 段すべてを受ける。
小型は思考の制御方式も旧世代のままで、`adaptive` を拒否し `budget_tokens` しか受けない。

#### なぜそうなるのか

**抄録生成は読解であって推論ではない。** 材料を読んで 3〜4 文にまとめるだけで、考える余地が
小さい。だから effort を上げても抄録は変わらず、むしろ考えさせると**書いていないことを
埋めにいく**。ADR-040 でも同じ向きの結果が出ている（ローカルモデルで think は 5.4 倍遅く、
品質は悪化）。モデルも世代も違うのに一致するのは、**仕事の性質のほうが効いている**からだと
考えられる。

### 18. Phase C — Nova 系は採れない（2026-09-14）

**単価が一桁違うので測った。** Bedrock の東京リージョンで、抄録に使える Amazon の
モデルと Claude を並べる（AWS Price List API、オンデマンド標準、1M トークンあたり）。

| モデル            |      入力 |      出力 | 世代 | `jp.*` プロファイル |
| ----------------- | --------: | --------: | ---- | ------------------- |
| Nova Micro        |     $0.04 |     $0.17 | 1    | ✗                   |
| Nova Lite         |     $0.07 |     $0.29 | 1    | ✗                   |
| Nova Pro          |     $0.96 |     $3.84 | 1    | ✗                   |
| **Nova 2.0 Lite** | **$0.36** | **$3.01** | 2    | ✓                   |
| Claude Haiku 4.5  |     $1.10 |     $5.50 | —    | ✓                   |
| Claude Sonnet 4.6 |     $3.30 |    $16.50 | —    | ✓                   |

**国内処理を約束する配備で選べる Nova は Nova 2.0 Lite だけである。** 他の 3 つは
`apac.*`（宛先は APAC 全域）しか無く、`global.*` を採らないのと同じ理由で採れない
（コストの節）。Nova Pro は Nova 2.0 Lite より**高い**ので、採用されるとすれば
「明確に良い場合」に限られる。

#### 能力 — document ブロックは通るが、JSON 強制が壊れる

1 ページの PDF を Converse の document ブロックで投げた。

| モデル           | document ブロック | 強制ツール使用による JSON                                      |
| ---------------- | ----------------- | -------------------------------------------------------------- |
| Nova 2.0 Lite    | 通る              | **壊れる。** `toolUse` を返さず、疑似 XML をテキストで出す     |
| Nova Pro         | 通る              | **退化する。** `required` のキーを落とし、表題の複写だけを返す |
| Claude Haiku 4.5 | 通る              | 正常                                                           |

Nova 2.0 Lite の出力は `<tools><__function=resource_abstract>…` という文字列で、使用トークン
数も報告されない。**`toolUse` ブロックを前提にした実装は Nova で必ず失敗する。**

#### トークン数 — Nova 2.0 Lite だけ 6 分の 1

同じ 1 ページ PDF の入力トークン数。

| モデル           | 入力トークン |
| ---------------- | -----------: |
| Nova 2.0 Lite    |      **289** |
| Claude Haiku 4.5 |        1,657 |
| Nova Pro         |        1,741 |

付録 2 は「PDF は 1 ページ 1,985〜3,078 トークン、画像分が支配的」と測っている。
**Nova 2.0 Lite だけが桁違いに安いのは、ページ画像ではなくテキスト層を読んでいるから**と
考えられる。だとすれば、安さとスキャンの読めなさは同じ性質の裏表である。次の測定がそれを
裏づけた。

#### 品質 — スキャンで決着した

テキスト層を持たない同一内容の PDF を 2 通り作り（鮮明な印字 / 低解像度・傾き・網点・低
コントラストの劣化）、実データ 2 件とあわせて 4 モデルに通した。プロンプトは本番と同じ。
正解は要支援 1 = 1,204 人ほか計 10,223 人、居宅 78.4% / 施設 21.6%。

| モデル            | 鮮明なスキャン         | 劣化スキャン           |
| ----------------- | ---------------------- | ---------------------- |
| Nova 2.0 Lite     | 読むが用語が壊れる     | **捏造**               |
| Nova Pro          | **捏造**               | **捏造**               |
| Claude Haiku 4.5  | ほぼ正確（言明が粗い） | ほぼ正確（小さな誤り） |
| Claude Sonnet 4.6 | 正確                   | **全数値を正確に読む** |

**Nova Pro は鮮明なスキャンすら読んでいない。** 数字を 1 つも出さず、「調査項目は健康状態、
生活状況、介護サービスの利用状況など多岐にわたる」「年代別、性別、居住地域別に分類」と
書いた。ページにその記述は無く、**`datasetContext` のタイトルと `notes` だけから作文している**。

**Nova 2.0 Lite は劣化すると崩れる。** 「モニターセンタを介して実施され、回答は紙ベースと
電子ベースの両方で収集された」— 完全な創作である。鮮明な方でも「要介養児」という存在しない
語を作った。

**Sonnet 4.6 は劣化スキャンから 7 区分すべての人数と利用率を拾った。**

**テキスト材料でも Nova は判定基準 1 に触れる。** テキスト層のある統計表の PDF に対し、
Nova 2.0 Lite は「縦軸に人数、横軸に年度を配してグラフ化している」と書いた。材料は数値表で、
軸の記述はどこにも無い。Haiku と Sonnet はどちらも「統計表」と書いている。

#### 抄録が材料について書く（2026-09-14）

実データで出た失敗である。緯度・経度の列について、生成された抄録がこう書いた。

> 緯度・経度列は**サンプル行では**すべて null であった。

**材料に忠実で、読めない。** 読み手はサンプル行の存在を知らず、5 行なのか 500 行なのかも
知らない。163 行のうち 5 行が null でも、残りについて何も言っていない。

決定 7 の禁止条項（材料を超えた言明）は、**言明の根拠**を縛るもので、**言明の主語**は縛って
いなかった。モデルは「サンプル行では」と留保を付けることで、禁止をすり抜けながら無意味な文を
書ける。プロンプトに 1 項目足した。

> **ファイルについて書き、渡された材料については決して書かない。**読み手には読んだ範囲が
> 別に示されるので、「サンプル行」「抽出テキスト」が何を指すか分からない。とくに、渡された
> 行が空だからといって列を空・一定・null と報告してはならない。特徴づけられない列については
> 何も書かない。

**同時に、断り書きが被覆率を答えるようにした。** 決定 7 の例示（「全 87 ページのうち先頭部分
と抜粋から」）は範囲を書く前提だったが、実装が落としていた。材料ごとに読んだ量を記録し、
「列の構成と、全 163 行のうち先頭 5 行を読みました」のように出す。**モデルに材料の話をさせない
なら、その情報は画面が持たなければならない。**

あわせて版の表記を版の履歴に揃え（`v4`）、**生成元の版が現行版より古いときは明示する** —
2 つの数字を読み手に見比べさせるのが、決定 7 の「古いまま残っている状態が見える」の実装として
弱かったためである。

#### Sonnet 5 — 東京では `global` のみ（2026-09-14）

上記のプロンプト（版 2）で、Sonnet 4.6 と Sonnet 5 を同条件で測った。

**まず可用性。** ap-northeast-1 の推論プロファイルに `global.anthropic.claude-sonnet-5` は
あるが、**`jp.` も `apac.` も無い**。価格表には geo 単価が載っているので、値付けは済んでいて
地理限定プロファイルが東京に来ていない状態と見える。

|                    |        入力 / 出力 | 処理先                          |
| ------------------ | -----------------: | ------------------------------- |
| `jp.` Sonnet 4.6   |     $3.30 / $16.50 | ap-northeast-1 / ap-northeast-3 |
| `global.` Sonnet 5 | **$2.00 / $10.00** | 全商用リージョン                |

**4 割安い。** ただし交換しているのは金額ではなく、コストの節に書いた「処理を国内に閉じる」
という性質そのものである。**国内処理を約束する配備では、現時点で選択肢に入らない。**

**品質はほぼ互角で、Sonnet 5 の方が簡潔だった。**

| 材料              | Sonnet 4.6 | Sonnet 5 |
| ----------------- | ---------: | -------: |
| CSV               |     253 字 |   244 字 |
| PDF（テキスト層） |     248 字 |   234 字 |
| スキャン・鮮明    |     243 字 |   205 字 |
| スキャン・劣化    |     290 字 |   212 字 |

**劣化スキャンも Sonnet 5 は正しく読んだ** — 合計 10,223 人、居宅 78.4% / 施設 21.6% まで
拾っている。Nova 2 機種が捏造した条件である。差は具体性の方向に出た。Sonnet 4.6 は数値を本文に
並べ、Sonnet 5 は「それぞれの利用率について解説している」と構造を述べる。検索のベクトルに載せる
目的では語彙が効くので、この差は小さいと見る。

**両モデルとも上の新しい規則を守った。** 8 出力すべてに「サンプル行では」の類は現れなかった。

**`temperature` は Sonnet 5 が拒否する**（`temperature` is deprecated for this model）。
本 ADR の経路も ADR-040 の提案も `temperature` を渡していないため影響は無いが、
`CompleteOptions.temperature` は残っているので、使えば落ちる。

`jp.anthropic.claude-sonnet-5` が来たときに再評価する。

#### 帰結

- **決定 6 は裏づけられ、しかも強まった。** 「軸は大きさではなく世代」— 上位・旧世代の
  Nova Pro が、小型・新世代の Nova 2.0 Lite より**悪い**
- **Nova は採らない。** 画像を見せない材料に限って振り分ける案（「MVP の後に検討すること」）
  も、テキスト材料での捏造があるため現時点では成立しない
- **決定 3.2 の生活語の指示は小型モデルでも効く。** 4 モデルすべてが「高齢者（お年寄り）」
  等を併記した。付録 3 の「小型では併記が出なかった」から改善している
- **文数の指示は 4 モデルすべてが守った**（決定 7）

**単発サンプルであり、ゴールデンセットの評価ではない。** スキャンは合成で、劣化の程度は
1 点しか見ていない。Nova は JSON を返せないため自己申告フラグ（判定基準 3）は測れていない。

### 19. PDF のバイト上限の実測（2026-09-15）

決定 3.3 の 4MB は被覆率から置いた数字で、API の限界を測ったものではなかった。実測した。

**方法。** `jp.anthropic.claude-sonnet-4-6` に、ページ数を 2 に固定した PDF を送る。
バイト数は**どのページも描画しないストリーム**で膨らませる。こうすると 2 つの軸が分離し、
成功しても 1 回あたり 1 セント程度で済む（拒否は課金されない）。

| サイズ   | 結果     | 入力トークン |
| -------- | -------- | -----------: |
| 3.00 MB  | 受理     |        3,158 |
| 5.00 MB  | 受理     |        3,158 |
| 12.00 MB | 受理     |        3,158 |
| 20.00 MB | 受理     |        3,158 |
| 22.30 MB | 受理     |        3,158 |
| 22.60 MB | 受理     |        3,158 |
| 22.90 MB | **拒否** |            — |
| 25.00 MB | **拒否** |            — |

拒否の文面は `Input is too long for requested model.`、分類は `too-long`（決定 3.4 の表）。

**境界は約 22.7MB。** そして**入力トークンが 3.00MB でも 22.60MB でも 3,158 で不変**である
ことが重要で、これは付録 2 の「トークンはページ数で決まる」の直接的な確認になっている。

**結論: バイト上限は費用を守っていない。** 守っているのは API の受理限界と worker の
メモリだけであり、費用を守っているのはページ上限である（決定 3.3 の注記）。

**測定はバイト数のみを変えている。** 実際の要求にはシステムプロンプトと利用者コンテンツが
乗るため、上限が要求全体に掛かっているなら実効値は下がる。16MB という設定はその余地である。
