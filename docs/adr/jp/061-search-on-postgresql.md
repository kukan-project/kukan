# ADR-061: 検索を PostgreSQL に寄せる（パッセージ索引から始め、合格したら OpenSearch を退役する）

## ステータス

**提案（Proposed）— 段階 1（パッセージ索引）で合否を測ってから、退役を判断する** — 2026-10-05

キーワード検索を OpenSearch から PostgreSQL に移す。日本語の形態素解析はアプリ側で行い、
PostgreSQL 標準の `tsvector` と GIN 索引に入れる。順位付けは SQL で組む BM25 とする。
拡張（PGroonga、BM25 系）には頼らないので、RDS / Aurora / Docker Compose で同じ構成になる。

移行は、RAG 向けに新しく作る**本文のパッセージ索引から始める**。パッセージ索引を最初から
PostgreSQL に作り、その評価で合格したら、データセット・リソースの検索も移して OpenSearch を
退役する。合格しなければ、OpenSearch をキーワード検索専用として残す（§段階と合否条件）。

採用されれば ADR-009 を置換し、ADR-021・ADR-025 のうち OpenSearch に依存する部分を置き換える。

## コンテキスト

### 1. OpenSearch が担っていること

- kuromoji による日本語の解析。基本形化、品詞の除外、接頭詞の除外（`ja_prefix`）、
  ストップワード、問いかけの定型句（`ja_request_words`）の除外を、索引側と検索側で使い分けている
- 親子の索引（ADR-025）。データセットを親、リソースのメタデータと本文チャンクを子とし、
  `has_child` の最大スコアでデータセットを並べ、`inner_hits` で一致したリソースを最大 100 件返す
- ハイライト。データセット・リソースのメタデータは検索と同時に、本文は表示後に遅延取得する
- ファセット。形式のファセットは子の集計から数える
- 本文は 500KB ごとのチャンクで入れている（ADR-021）

すでに OpenSearch の外にあるものもある。

- ベクトルは pgvector にある（ADR-034、ADR-054）。BM25 とベクトルの融合（RRF）はサービス層で行い、
  バックエンドに依存しない
- `PostgresSearchAdapter` は、ダッシュボードとベクトル検索のために常に動いている（ADR-013）。
  フィルタ・ファセット・可視性の判定を一通り持つ。テキストの一致だけが ILIKE + pg_trgm（ADR-009）である

### 2. 外にあることの費用

- **固定費。** 規模ごとに t3.small.search、m6g.large.search、m6g.xlarge.search × 2（Multi-AZ）を
  常時動かしている。Compose でもヒープ 2GB のコンテナが要る
- **整合の仕組み。** 索引が DB の外にあるため、次の仕組みを作って保守している
  - 未反映フラグとまとめて反映するジョブ（`sync-search-docs`、`doc_sync_due_at`）
  - リソース文書の同期ロックと CAS
  - 解析の規則が変わったときの索引の作り直しとエイリアスの切り替え
    （`analysisStale` / `reanalyseIndex` / `pendingRepair`）
  - 落ちていたときに 503 を返す処理
- **デプロイの互換性。** マッピングの変更は、稼働中の索引に足せるものと作り直しが要るものに分かれ、
  リリースのたびに確かめる必要がある

ジョブキューは ADR-058 で PostgreSQL に移し、SQS をなくした。検索だけが、DB の外に状態を持つ
最後の基盤として残っている。

### 3. RAG で増えるもの

住民向けの RAG や外部 AI（MCP）から、根拠となる箇所を出典付きで引けるようにする計画がある。
そこで必要になるものは、OpenSearch の外に置いたほうが作りやすい。

- **本文のパッセージ索引。** 見出しとページの境界に沿った 1,000〜2,000 字程度の単位で、
  本文・文脈文・ページ・見出し・埋め込みを持つ。非公開にしたら即時に除き、版を差し替えたら
  旧版を残さない。OpenSearch では §2 の整合の仕組みを、パッセージ用にもう一度作ることになる
- **サイトごとに定義する拡張メタデータでの絞り込み。** 資料の種別、募集・縦覧の期間、対象の町丁目
  などを使う。OpenSearch では、共有ドメインのマッピングがサイトごとの項目の分だけ増え、
  項目を変えるたびに索引を作り直すことになる
- **同義語・地名辞書による検索時のクエリ展開。** 辞書を更新しても、索引の作り直しは要らないことが
  条件である。AWS の OpenSearch で検索時の同義語を使うには、カスタムパッケージの配布と再読み込みが
  要り、サイト単位の運用とは相性が悪い
- **生成 AI を呼ばない、MCP のパッセージ取得。** AI を使わない環境（閉域網を含む）ではベクトルが
  ないので、**キーワード検索の質がそのまま RAG の質になる**

### 4. PostgreSQL 側の制約

- **RDS / Aurora で使える拡張に、PGroonga も BM25 系（pg_search、pg_textsearch、vchord_bm25）もない。**
  日本語向けで使えるのは pg_bigm だけである（2026-10 時点の AWS の拡張一覧）
- 標準の全文検索は日本語を分割しない。`to_tsvector` のパーサは、空白のない日本語の連なりを 1 語として扱う
- `tsvector` の大きさは 1MB が上限で、位置情報は 16,383 で頭打ちになる。500KB のチャンクを
  そのまま入れると上限に近づく
- `ts_rank` / `ts_rank_cd` には IDF がない。どの文書にも出る語と珍しい語を同じ重さで数える
- `ts_headline` は自分のパーサで本文を区切り直すので、アプリ側で分割した語の境界とは合わない
- **BM25 の上位 k 件を効率よく取る仕組みがない。** Lucene は block-max WAND で、該当が何十万件でも
  上位だけを取れる。GIN 索引は「含むかどうか」しか答えないので、BM25 で並べるには候補を全部
  採点し直すことになる

### 5. 想定する規模

リソースが数十万件になるサイトを想定する。次の仮定で、パッセージは数百万行になる。

- 30 万件のうち、本文を持つ文書が半分
- 1 文書あたり 30 パッセージ
- 1 パッセージあたり 1,500 字

この仮定での目安は次のとおり。

| 対象                                      | 行数      | 容量の目安 |
| ----------------------------------------- | --------- | ---------- |
| メタデータ（データセット・リソース）      | 数十万    | 数百 MB    |
| パッセージの本文（圧縮後）                | 約 450 万 | 約 10GB    |
| `tsvector` と GIN 索引                    | 約 450 万 | 10〜15GB   |
| ベクトル（halfvec 1024 次元）と HNSW 索引 | 約 450 万 | 25GB 前後  |

メタデータの検索は、この規模でも PostgreSQL にとって小さい。重いのはパッセージで、課題は 2 つある。

- **よくある語だけの検索（「計画」「令和6年度」など）。** 候補が数十万行になり、§4 の
  採点し直しが秒単位になりうる
- **ベクトルのメモリ。** HNSW 索引はメモリに載らないと遅い。ただしベクトルは ADR-034 の方針で
  pgvector に置くので、この費用は OpenSearch を残しても変わらない

## 検討した選択肢

### A) OpenSearch を続け、RAG も OpenSearch に載せる

今の解析とスコアリングをそのまま使える。代わりに、パッセージの整合の仕組み、サイトごとの
マッピング、同義語の配布を OpenSearch 向けに作ることになる。パッセージのベクトルは ADR-034 の方針で
pgvector に置くので、DB の増強は避けられない。BM25 用にもう 1 部コピーを持つ形になり、固定費も残る。

### B) PGroonga

形態素解析（TokenMecab）、ハイライト、同義語展開（`pgroonga_query_expand`）がそろっている。
しかし RDS / Aurora では使えない（ADR-009 で却下した理由と同じ）。全環境で使うには
PostgreSQL を自前で運用することになり、バックアップ・PITR・フェイルオーバー（ADR-037）を
作り直す必要がある。オンプレだけで使うと、検索の実装が OpenSearch / PGroonga / ILIKE の 3 つになる。

### C) pg_bigm を中心にする

RDS / Aurora で使え、言語に依存しない。しかし形態素の区切りがないので、語の境界をまたぐ部分一致を
拾える代わりに、語として意味のない一致も拾う（「京都」で「東京都」）。1 文字の検索には索引が効かず、
IDF も持たない。Compose では pg_bigm 入りの
DB イメージが要る（ADR-009 で中間層として却下した理由）。部分一致を補う手段としては残す（§残課題）。

### D) 形態素解析をアプリ側で行い、標準の `tsvector` と自前の BM25 で検索する — 採用（提案）

拡張が要らず、すべての環境で同じ動きになる。解析器と辞書（IPADIC）を今の kuromoji に揃えれば、
今の解析の規則をそのまま持ち込める。IDF とハイライトは自前で組む必要があり、その質と速さが
この選択の成否を分ける。だから段階を踏んで測る。

## 決定（提案）

### 1. 解析はアプリ側で行う

- Node の形態素解析器で、索引する文と検索語の両方を分割する。辞書は IPADIC とし、今の kuromoji と揃える
- 規則は今の解析をそのまま移す。基本形化、品詞の除外、`ja_prefix`、検索側だけの `ja_stop`
  （メタデータのみ）と `ja_request_words` である
- 分割した語を `to_tsvector('simple', …)` で `tsvector` にし、GIN 索引を張る。検索語は
  `to_tsquery('simple', …)` の AND で組む（今の `operator: and` と同じ）
- **解析器の選定は段階 1 で行う。** 候補は kuromoji.js と Lindera である。基準は次の 3 つ
  - OpenSearch の kuromoji の既定の search モード（複合語も分割する）と同じ分割ができるか
  - web（small 構成で 512MB）に辞書を載せられるメモリ量か
  - 保守が続いているか

### 2. 順位付けは SQL で組む BM25 とする

- 語ごとの出現文書数（df）、文書の長さ、平均の長さを表に持つ
- GIN 索引で候補を絞ってから、候補だけを BM25 で採点し直す
- 項目の重み（今の `title^3 name^2` など）は、項目ごとの `tsvector` か `setweight` で表す
- §コンテキスト 4 の上位 k 件の問題には、次の順で対処する
  - 検索語のうち最も珍しい語（df が最小の語）の候補だけを GIN で引き、残りの語はその中で確かめる
  - 組織・種別・期間などの絞り込みを先に当て、候補を減らす
  - それでも候補が多いときは候補数に上限を設け、ベクトル側の結果と RRF で補う。
    品質がどこまで落ちるかは評価で測る
- df は定期的にまとめて更新してよい。文書が少し増えても IDF はほとんど動かない

### 3. 本文はパッセージ単位で持つ

- `resource_passage`（仮）に、本文、文脈文、ページ、見出し、版、`tsvector`、埋め込みを並べて持つ
- 500KB チャンクの索引は、段階 3 でパッセージに置き換える。§4 の `tsvector` の上限は、
  パッセージの大きさなら問題にならない
- ハイライトは、該当するパッセージを検索語と同じ解析器で区切って、アプリ側で付ける

### 4. ベクトルは halfvec と HNSW 索引にする

パッセージ単位にすると、ベクトルの本数はリソース単位の 2〜3 桁上になる。全件走査ではなく、
HNSW 索引で引く。

絞り込みを付けたときに件数が欠けないかを確かめる。pgvector の iterative scan が
RDS / Aurora の版で使えるかは、段階 1 で確認する。

§コンテキスト 5 の規模では、そのままだと 32GB 級の DB が要る。次の手段を組み合わせて
メモリを減らし、どれを採るかは段階 1 の計測で決める。

- 次元を減らす（512 / 256 次元を出せるモデルを使う）
- 二値量子化（`bit` 型とハミング距離）で候補を取り、元の精度で並べ直す
- パッセージにするのは文書だけとする。CSV などの表は `query_resource`（ADR-032）に任せる

### 5. 検索用の列は、元のデータと同じトランザクションで書く

可視性の変更、削除、版の差し替えは、検索用の列やパッセージの行にもその場で反映される。
退役後は、§コンテキスト 2 の整合の仕組みをなくす。解析の規則を変えたときの再解析は、
DB の中での再計算として残る。

### 6. 拡張メタデータと辞書は PostgreSQL だけで作る

拡張メタデータの絞り込みと、同義語・地名辞書によるクエリ展開は、OpenSearch 側には作らない。
段階 1 の結果が不合格で OpenSearch を残すことになった場合も、絞り込みは DB 側の候補の絞り込みとして
組み合わせる。

### 7. 負荷を DB で受け止める

- MCP と公開検索 API のレート制限を、退役の前提条件とする
- 検索のクエリには `statement_timeout` を付ける。規模によっては検索をリーダーへ逃がす
- small 構成（`db.t4g.micro`）では、パッセージのベクトル検索は提供しない。
  どの規模から提供するかは段階 1 の計測で決める

## 段階と合否条件

### 段階 1: パッセージ索引を PostgreSQL に作る

OpenSearch と並行して動かす。データセット・リソースの検索は OpenSearch のままとする。

合否条件は次のとおり。

- `pnpm eval:search` にパッセージ単位の評価（Recall@k / nDCG）を足し、**AI ありと AI なしの両方で**測る。
  AI なしでの値を、OpenSearch にパッセージを入れた場合（kuromoji + BM25）と比べる
- 本文の厚い環境で、検索の p95 レイテンシを測る
- DB のサイズ、メモリ、全件の再処理にかかる時間の増え方を測る
- **規模の計測。** 実データは数万件規模なので、合成データでパッセージを 500 万行まで増やして測る
  - 検索の p95 を、よくある語だけの検索と、珍しい語を含む検索に分けて測る
  - ベクトルの次元と量子化の組み合わせごとに、メモリと再現率を測る
  - 全件の作り直し（形態素解析、GIN 索引、HNSW 索引）にかかる時間を測る
- 規模の合格基準（数十万リソースで p95 が何秒以内か）は、段階 1 の開始前に決める

### 段階 2: データセット・リソースの検索を移す

合否条件は、ゴールデンセットの overall が今の OpenSearch から許容幅以内に収まることとする。
許容幅は段階 1 の開始前に決める（案: 3 ポイント）。

### 段階 3: OpenSearch を退役する

次のものをなくす。

- OpenSearch アダプター
- CDK のドメインと Compose のサービス
- 整合のジョブと未反映フラグ
- `SEARCH_TYPE`

環境差がなくなるので、ADR-005 の原則に従い、検索のアダプター境界も外す。

### 不合格のとき

不合格の主な原因として想定されるのは、次の 2 つである。

- AI なしでのキーワード検索の質
- 数十万リソース規模での、よくある語だけの検索の速さ（§コンテキスト 5）

どちらも PostgreSQL の最も弱い部分であり、不合格は十分ありうる結果として扱う。その場合は
OpenSearch をキーワード検索専用として残し、パッセージを OpenSearch にも入れる。BM25 の上位 k 件を
効率よく取る拡張が RDS / Aurora で使えるようになったら、改めて評価する。

段階 1 で作るパッセージの表とベクトルは、そのまま使える。

## 影響

- **費用。** OpenSearch のドメインの固定費がなくなる。代わりに DB の増強が要る。
  規模ごとの差し引きは段階 1 の計測をもとに出す
- **マルチサイト。** DB を共有するサイト同士で、パッセージ索引と検索の負荷が互いに響く。
  これは今の OpenSearch の共有ドメインと同じ構図である。数十万件のサイトだけ DB を分けられるかは
  残課題とする
- **既存の環境の移行。** パッセージと検索用の列は、DB と正本から作り直せる（全件の再処理）。
  ドメインの削除はリリースノートで予告し、退役のリリースで行う
- **Compose。** OpenSearch のコンテナがなくなり、メモリの要件が下がる
- **管理画面。** 索引のブラウザ（索引の統計、文書の閲覧、チャンクの一覧）は作り直す

## 残課題

- 解析器の選定（§決定 1）
- 1 文字の語や、形態素の境界をまたぐ部分一致の扱い。pg_bigm を補助に使うか、ILIKE のままにするか
- df の更新のタイミングと、サイトをまたいで集計しないための単位
- CKAN 互換 API の `q`（今もキーワードとして扱っており、変わらない）
- 規模ごとの費用の試算
- 該当するデータセットが数万件になったときのファセットの集計。データセットの行に形式などの配列列を
  持たせて数える形への切り替え
- 大規模なサイトだけ DB を分けるかどうか（ADR-041）
