# ADR-035: セマンティックバージョニングとリリースノート

## ステータス

**承認済み（Accepted）**

## コンテキスト

KUKAN はこれまで明示的なリリースを行っておらず、バージョンタグも
CHANGELOG も存在しなかった（全 package.json が初期値 `0.1.0` のまま）。
最初の公開リリースにあたり、以下を決める必要がある。

1. バージョン番号の付け方と bump（引き上げ）の判定方法
2. リリースノートの作成方法と品質基準
3. リリース成果物（タグ・CHANGELOG・GitHub Release）の形

コミット件名は既に CI で Conventional Commits（英語）に統一されており
（`feat` / `fix` / `docs` … + breaking は `!` マーカー）、バージョン判定と
リリースノートの機械的な材料は揃っている。一方、コミット件名の羅列だけでは
「このリリースで何が変わり、利用者に何が嬉しいのか」が伝わらない。

## 決定

### 1. セマンティックバージョニング（プロダクト単位・単一バージョン）

[Semantic Versioning 2.0.0](https://semver.org/) に従う。KUKAN はアプリケーション
として一体でデプロイされるため、バージョンは**リポジトリ全体で単一**とし、
ルート `package.json` の `version` と git タグ `vX.Y.Z` で管理する。
workspace 内の各パッケージは private（npm 非公開）のため個別バージョンを
維持管理しない。

bump は前回タグ以降のコミット件名（Conventional Commits）から自動算出し、
リリース担当が必要に応じて上書きできる。

| 前提       | breaking（`!`） | `feat` | それ以外 |
| ---------- | :-------------: | :----: | :------: |
| 0.x の間   |      minor      | minor  |  patch   |
| 1.0.0 以降 |      major      | minor  |  patch   |

- squash 運用ではコミット本文に `BREAKING CHANGE:` footer を書けないため、
  **breaking change の宣言は件名の `!` マーカーに一本化**する。
- `1.0.0` は正式 GA（全フェーズ完了・本番実績）まで取っておく。
  初回リリースは実装の到達度を反映して `v0.7.0` とする。

### 2. リリースノートは AI ドラフト + 人間レビュー（英日併記）

リリースノートはコミット件名の機械的な羅列ではなく、**AI（Claude）が
コミット履歴・差分を材料にドラフトし、リリース PR で人間がレビュー・修正**する。

- **英語 + 日本語併記**。国内自治体等の利用者と海外 OSS 利用者の両方に届ける
  （ドキュメントサイトの日英対応と整合）。
- 構成: Highlights（読み物としての要約）+ Features / Bug Fixes 等の分類リスト
  （コミット件名 + PR 番号）。
- AI ドラフトは事実誤認がありうるため、**レビューなしで公開しない**。
  リリース PR のレビューがそのままリリースノートのレビューを兼ねる。

### 3. リリース成果物とフロー

```
リリース PR（version bump + CHANGELOG.md 更新、develop 向け）
  → レビュー・マージ
  → main へ反映 + vX.Y.Z タグ
  → タグに対応する GitHub Release を作成（本文 = CHANGELOG の該当セクション）
```

- `CHANGELOG.md` をリポジトリルートに置き、リリースごとにセクションを先頭追加する
  （[Keep a Changelog](https://keepachangelog.com/) に準拠した `## [X.Y.Z] - YYYY-MM-DD`
  見出し）。リポジトリ内で履歴が完結し、GitHub Release はその写しとなる。
- GitHub Release の本文は CHANGELOG の該当バージョンのセクションから自動抽出する。
  プレリリース（`v1.0.0-rc.1` 等、`-` を含むタグ）は prerelease フラグ付きで作成する。

## 検討した代替案

### release-please（Google）

リリース PR の作成・更新まで全自動化できるが、リリースノートが
コミット件名の機械的な羅列になり品質目標を満たさない。また develop/main の
二段ブランチ + fast-forward 運用への適合に設定の作り込みが必要で、
挙動がブラックボックス化する。**不採用**。

### semantic-release

push 起点の完全自動リリース。バージョンや文面に人間が介入する余地がなく、
AI ドラフト + レビューの方針と両立しない。**不採用**。

### changesets

パッケージごとの独立バージョニングと npm publish に最適化されたツール。
KUKAN は単一バージョンのアプリケーションで npm 公開もないため過剰。**不採用**。

### GitHub 自動生成リリースノート

追加ツール不要だが PR ベースの生成で品質が低く、CHANGELOG.md も残らない。**不採用**。

## 結果

- 利用者はタグ・GitHub Release・CHANGELOG.md でバージョンと変更内容を追える。
- バージョン判定は Conventional Commits から機械的に導出でき、恣意性が排除される
  （上書きは可能だが根拠がリリース PR に残る）。
- リリースノートの品質を AI ドラフトで担保しつつ、公開前レビューを必須にすることで
  事実誤認の公開を防ぐ。
- breaking change の見落としリスクが PR タイトルの `!` 付け忘れに集中する。
  レビュー時に API・スキーマ変更の有無を意識する必要がある。
