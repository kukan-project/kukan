# ADR-059: worker の重い処理を、使い回す 1 つの子プロセスで行う

## ステータス

**承認済み（Accepted）** — 2026-10-01、実装 2026-10-02

ADR-032 残課題 2 で web のリソースクエリに採った子プロセス（選択肢 C）を、worker の重い処理へ広げる。
ADR-058 §7 の重い区間（`heavySection`）の中身は、この子への依頼と、プロセス内に残る層 2 の取り込みになる。

## コンテキスト

### 1. 1 つのファイルで worker ごと落ちる

worker は重い計算を自分のプロセスの中で行っている。

- テキスト抽出（Index）：PDF・DOCX・XLS・PPTX などを officeparser で、XLSX を自前の流し読みで読む
- 解釈（Interpret）：CSV/TSV を DuckDB（ネイティブアドオン）で Parquet にし、型を推定する

どちらかが大きなファイルでメモリを使い切ると、worker ごと落ちる。small・medium の worker は 1 GB の
コンテナで、Node のヒープの上限は 560 MB である。落ちたときに起きるのは次のことである。

- ジョブのリースとリソースの claim が期限切れになるまで待ってから再試行され、同じファイルの同じ場所で
  また落ちる。`dead` になるまで、そのたびにタスクが落ちる
- 同じ worker で並行に動いていた無関係なジョブも巻き込まれ、試行回数が増える（ADR-058 §7 で 1 台の中の
  並行数を既定 3 にしたので、巻き込む数も増えた）
- 同期の CPU 処理が長く続く間は、リースの延長・`/health`・`/wake` が応答しない

### 2. 軽くできるところは軽くした

- PDF：ページ範囲ごとに読み、pdf.js が描画のためだけに作るグリフのパスを止めた。図表の多い 1.7 MB の
  PDF で、文書全体で 3.4 GB → 366 MB
- XLSX：シートの XML を流して読むようにした（21 MB で 1.4 GB → 27 MB）
- DuckDB：解釈と層 2 の取り込みに上限（512 MB）を付け、重い区間を同時に 1 本にした（ADR-058 §7）

それでも残るものがある。

- DOCX は officeparser のまま。ヒープは展開後の `document.xml` の約 60 倍で、実際の自治体の文書 39 件では
  最大 293 MB だった。書き直して同じテキストを出すには、段落番号・脚注・テキストボックス・結合セルなどを
  扱う約 1,200 行の大半を作り直すことになるので見送った
- XLS・PPTX など、officeparser に残した形式は量っていない
- DuckDB はネイティブのメモリを使うので、上限を超えた分は Node のヒープではなくコンテナの OOM で落ちる

軽くすることは落ちる確率を下げるだけで、落ちたときの巻き込み方は変わらない。

### 3. 子プロセスに分ければ、障害の単位を分けられる

- Fargate の cgroup は v1 で（プラットフォーム 1.4.0、demo で確認）、`memory.oom.group` が無い。OOM killer は
  コンテナのプロセスをまとめて落とさず、`oom_score` の最も高い 1 つを落とす
- worker 本体（PID 1）の `oom_score_adj` は Fargate が −998 にしている。子が自分で +1000 に上げれば、
  OOM の対象は確実に子になる（上げる方向は権限なしでできる）
- Node のヒープの上限で落ちる場合も、子なら子のヒープで子が落ちるだけで、親は残る
- web のリソースクエリでは、この形がすでに動いている（ADR-032 残課題 2、`query-process.ts`）

### 4. 1 件ごとに子を起動すると遅い

small と同じ 0.25 vCPU のコンテナで、親から子を起動して準備完了の合図が返るまでを測った。

| 子が読み込むもの                 | 0.25 vCPU | 手元（制限なし） |
| -------------------------------- | --------- | ---------------- |
| 何もしない                       | 約 0.1 秒 | 約 0.02 秒       |
| officeparser                     | 約 0.5 秒 | 約 0.07 秒       |
| DuckDB（インスタンスを開くまで） | 約 0.6 秒 | 約 0.1 秒        |

リソース 509 件の全件の再処理なら、CSV 320 件 × 0.6 秒 ＋ PDF・XLSX・XLS・DOCX 237 件 × 0.5 秒
≈ 310 秒の CPU 時間が、1 タスクあたりに上乗せされる。起動は CPU を使い切る処理なので、small では並行数を
上げても縮まない。web のクエリは 1 回ごとに起動しても人の操作 1 回あたりの誤差で済むが、worker は件数が多い。

## 検討した選択肢

- **A) 今のまま（プロセス内 ＋ 重い区間を 1 本）**: 費用はゼロ。落ちる確率は下げたが、落ちたときの巻き込み方は
  変わらない
- **B) 1 件ごとに子を起動する（web のクエリと同じ）**: 作りは単純で、1 件ごとにメモリを全部返す。起動の費用
  （§4）が件数ぶん乗る
- **C) 危ない大きさのファイルだけ子にする**: 費用は数件分で済む。ただ境目を形式ごとに決める必要があり、
  境目の下で落ちれば A と同じになる。DOCX は展開後の `document.xml` の大きさで見積もれるが、DuckDB や
  ほかの形式には同じ物差しが無い
- **D) 子を起動したまま使い回す（採用）**: 起動の費用は最初の 1 回だけ。すべての重い処理を子に通せる
- **E) 複数のリソースを 1 つのジョブにまとめる**: 起動の費用は割れるが、リソース単位の claim と再試行
  （ADR-044）の作りと合わない
- **F) 別のコンテナ（サイドカー）に分ける**: cgroup で上限を厳密に守れるが、タスク定義・メモリの割り当て・
  通信が増える。small の 1 GB を 2 つに割ると、どちらも窮屈になる

## 決定

worker は重い処理専用の子プロセスを 1 つ持ち、起動したまま使い回す（D）。

### 1. 子がすること

- テキスト抽出（officeparser・PDF・XLSX の流し読み）と、CSV/TSV の解釈（DuckDB）
- ローカルのファイルを受け取り、ファイルと JSON を返すだけの計算にする。DB・ストレージ・OpenSearch・claim は
  親が持つ
- 子は一度に 1 件だけ扱う。今の重い区間（同時に 1 本）と同じ絞り方で、子への依頼が区間の中身になる
- 層 2 の取り込みはプロセス内に残す。DuckLake のカタログの認証情報が要り、子に秘密を渡すことになるため。
  そのインスタンスには、メモリ・スレッド・カタログ接続の上限が付いている

### 2. 子が落ちたら、その 1 件の失敗にする

子は一度に 1 件しか扱わないので、子が落ちた原因はその 1 件に決まる。その 1 件を「大きすぎて処理できない」と
して記録し、run は他の失敗と同じように先へ進む（タスクは落ちず、再試行も繰り返さない）。次の依頼で子を
起動し直す。

- 子のメモリは匿名メモリ（`RssAnon`）で測る。RSS は node 本体や DuckDB のライブラリなどファイルに対応した
  ページ（約 90 MB）まで数え、コンテナには一度しか課金されないそれを子の予算から差し引くことになる
- 使い回していた子が予算を超えたとき、またはカーネルに落とされたときは、新しい子で 1 回だけやり直す。前の
  依頼で抱えた分も予算に数えられるので、その 1 件のせいと言えるのは新しい子が落ちたときだけ
- 「大きすぎる」とするのは、子が自分の予算を超えたとき、カーネルに落とされたとき（SIGKILL）、ヒープを
  使い切ったとき（SIGABRT）に限る。コンテナ全体の上限に近づいて止めたときは、親のほかのジョブも原因に
  なりうるので一時的な失敗とし、版には記録しない。子の予算をコンテナの上限から親の取り分を引いた値に
  収めてあるので、大きすぎるファイルは先に子の予算に当たる
- 解釈：表が無い理由を `out-of-memory` として版に記録する。記録しないと、毎時の定期再投入が同じ版を
  渡して、そのたびに子を落とす。サイズの上限による `too-large`（保存せず、上限から毎回導く）とは分ける。
  こちらは動いたタスクの大きさについての事実なので、大きいタスクへ移したサイトが読み直す版を探せる
- テキスト抽出：Index ステップの失敗として記録する。前に索引した内容はそのまま残る

### 3. 子を止める・起動し直すとき

| いつ                                                   | 何をするか                                                                                                                                                                                               |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 依頼の途中で、子の匿名メモリが予算を超えた             | 子を止める。使い回していた子なら新しい子で 1 回やり直し、新しい子でも超えたら「大きすぎる」                                                                                                              |
| 依頼の途中で、コンテナ全体のメモリが上限に近づいた     | 子を止め、親が使っていない層 2 のインスタンスを閉じてメモリを返させ、新しい子で 1 回やり直す。それでも足りなければ一時的な失敗とし、版には記録せず、ジョブを失敗にしてキューが待ち時間を置いて再実行する |
| 1 件終わったとき、子の匿名メモリが決めた値を超えている | 子を止める。次の依頼で起動し直す（抱えたメモリを持ち越さないように）                                                                                                                                     |
| 最後の依頼から一定時間（1 分程度）依頼が無い           | 子を止め、読み込んだ分のメモリ（約 70〜100 MB）を返す                                                                                                                                                    |
| 依頼の途中で、その run が claim を失った               | 子を止める（claim は依頼の間、親がメモリと一緒に定期的に確かめる）                                                                                                                                       |
| 待機中の子が落ちていた（カーネルの OOM など）          | 次の依頼で新しい子を起動する（その依頼の失敗にはしない）                                                                                                                                                 |
| 親が SIGTERM を受けた                                  | 新しいジョブを取るのを止めた直後に子を止め、以降の依頼は断る。処理中の 1 件は記録せず、キューが試行回数に数えずに戻して別のタスクが実行する                                                              |
| 親が突然落ちた                                         | 子は IPC の切断を検知して自分で終わる                                                                                                                                                                    |

子の優先度は親と同じにする（web のクエリのように下げない）。依頼は 1 本ずつしか通らないので、1 件が遅れると
その後ろのジョブがすべて遅れる。

始めた・止めた・やり直した・層 2 のインスタンスを閉じたことは、理由とともに worker のログ
（`component: heavy-process`）に出す。値の調整はこのログで行う。

### 4. 子の環境

- 環境変数は許可リストで渡し、秘密は渡さない（ADR-032 と同じ）。worker は信頼できない入力ファイルを解析する
  場所なので、分離はセキュリティ上の利点にもなる
- 子は最初に自分の `oom_score_adj` を +1000 にする
- 一時ディレクトリは親が作って渡し、親が消す（子は途中で止められうるので、自分で後始末できない）
- 子のコードは worker の tsup の別エントリとして `dist` に並べる。web のような
  `QUERY_CHILD_ENTRY` の設定は要らない

### 5. 仕組みの共有

子の起動・RSS の監視・許可リスト・一時ディレクトリの後始末は、web のクエリ（1 件ごとに起動）と worker
（使い回す）の両方が使える形に切り出す。

## 影響

- 1 つのファイルで落ちるのは子だけになり、worker と並行に動いている無関係なジョブは巻き込まれない
- 子が起動している間は、その分のメモリ（約 70〜100 MB）を常に使う。暇になれば返す
- 親と子の間でファイルの受け渡しが増える（テキスト・Parquet は今もファイルに書いているので、増えるのは
  JSON のやり取りだけ）
- 抽出・解釈の結果は変わらない（同じコードを子で動かすだけ）

## 実測（2026-10-02）

small と同じ 1 GB・0.25 vCPU のコンテナで、開発環境のリソース 509 件（CSV 303・XLSX 75・PDF 61 ほか）を
保存済みの内容から再処理した。匿名メモリは cgroup（`memory.stat` の `anon`）を 2 秒ごとに読んだ値。

**層 2 の取り込みなし**

|                             | 変更前（プロセス内） | 変更後               |
| --------------------------- | -------------------- | -------------------- |
| 全件の所要時間              | 872 秒               | 1,116 秒             |
| 匿名メモリ（中央値 / 最大） | 896（平均）/ 992 MiB | 375（平均）/ 749 MiB |
| 900 MiB を超えていた時間    | 61%                  | 0%                   |
| 結果                        | —                    | 変更前と同じ         |

**層 2 の取り込みあり（各リソースの最新の版 273 件を取り込み直す）**

|                                | 変更前（プロセス内）                               | 変更後                     |
| ------------------------------ | -------------------------------------------------- | -------------------------- |
| worker                         | 1,126 秒で OOM により落ちた。残り 231 件は手つかず | 最後まで動いた（2,250 秒） |
| 層 2 の取り込み                | 146 / 273                                          | 273 / 273                  |
| 匿名メモリ（中央値 / 最大）    | 978 / 1,006 MiB                                    | 642 / 959 MiB              |
| 900 MiB を超えていた時間       | 70%                                                | 1%                         |
| 一時的な失敗（コンテナの逼迫） | —                                                  | 1 件（テキスト抽出）       |

変更後の層 2 ありでのログ：子の起動 35 回（うち 27 回は 1 件ごとの起動し直しで、抱えていたのは 24 回が
402〜449 MB、残り 3 回が 539〜625 MB）、コンテナの逼迫で止めたのが 7 回、そのうち 6 回は層 2 のインスタンスを
閉じたやり直しで成功、「大きすぎる」は 0 件、カーネルの OOM は 0 回。

- 変更前は、層 2 がなくても時間の 6 割を上限の手前で動いており、層 2 があると全件の再処理の途中で落ちた
- 変更後は時間が延びる（層 2 なしで +28%）。0.25 vCPU では CPU を使い切っており（`cpu.stat` の
  `throttled_usec` が使用時間の約 8 倍）、子の起動（1 回 1.2〜1.8 秒）と層 2 のインスタンスの作り直しの分が
  そのまま時間に出る。延びの残りの内訳は測っていない
- 子が抱えるメモリは、それまでに扱った最大の依頼の分で止まり、小さい依頼では増えない（50 MB の CSV の
  あとで 377 MB、その後の 1〜5 MB の CSV でも変わらない）
- 親が層 2 のインスタンスを開いたままにすると、親の RSS は層 2 なしの平均 268 MiB から平均 558〜635 MiB に
  上がる。`enable_external_file_cache = false` でもインスタンスはメモリを持ち続ける

## 残課題

1. **予算の値**: 実装は次の値で入れた（`apps/worker/src/config.ts`）。子の予算は、解釈の DuckDB の上限から
   web のクエリと同じ式で求めた 946 MB と、コンテナの上限から親の取り分 300 MB を引いた値の小さい方（1 GB の
   タスクでは 724 MB、匿名メモリで測る）。コンテナに残す余裕 64 MB、起動し直す値 400 MB（匿名メモリ）、
   暇になって止めるまで 60 秒。起動し直しの大半が 402〜449 MB なので、450 MB 程度に上げると起動し直しは
   1 割ほどに減る（1 回 1.5 秒前後）が、待機中の子が抱える分だけ層 2 の取り込みの余裕が減る。本番のログで
   決める
2. **層 2 のインスタンスが抱え続けるメモリ**: 閉じずにメモリだけを返させる方法があれば、作り直しの費用
   （拡張の読み込みと ATTACH）なしで親の取り分を下げられる
3. **時間の延びの内訳**: 子の起動とインスタンスの作り直しで説明できない分（JIT が温まっていない新しい子、
   依頼中のメモリの読み取りなど）
4. **PDF の読み方**: 子へ移すときに、子プロセスで pdf.js を動かすか Poppler の `pdftotext` を呼ぶかを、
   同じ PDF 群でメモリ・時間・抽出品質を測って決める（`pdftotext` は改行・空白の出方が変わるので、
   既存の索引は再処理で揃える）
5. **ZIP のマニフェスト**: 純粋な計算なので子へ移せるが、今のところ重さは問題になっていない
