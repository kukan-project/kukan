# ADR-062: extras のキーと値でデータセットを絞り込む

## ステータス

**提案（Proposed）** — 2026-10-05

データセットの `extras` とリソースの `extras` を検索の索引に入れ、キーと値の組でデータセットを
絞り込めるようにする。ネイティブ API では `extras_<key>=<value>` と `res_extras_<key>=<value>`
をクエリパラメータとし、CKAN 互換 API の `fq` では同じ名前の項目として読む（ADR-060 の拡張）。
値は完全一致で比べる。

## コンテキスト

### 1. extras は返すが、引けない

データセットにもリソースにも `extras` があり、読み取りの応答には載る（リソースは ADR-060 で
書けるようになった）。一方、検索の索引には入っていない。

- リソースの検索文書は `resourceDocColumns` で組み立て、中身は名前・説明・フォーマット・
  セクション・抄録だけ
- データセットの検索文書（`DatasetDoc`）にも extras の項目はない
- PostgreSQL のフォールバック検索も extras を見ない

「更新頻度が月次のもの」「整備単位が市町村のもの」のように、サイトが extras で揃えている
分類では探せない。キーワード検索に値を書いても当たらない。

### 2. CKAN での扱い

CKAN 2.12 の索引（`ckan/lib/search/index.py`、`ckan/config/solr/schema.xml`）では次のとおり。

- **データセットの extras** は、`extras_<key>` という動的項目で必ず索引される。キーは
  `[0-9A-Za-z_-]` 以外の文字を削ってから使う。項目の型は `text`（空白で区切り、小文字化と
  英語の語幹処理をかける）で、完全一致ではない。値は全文検索の `text` 項目にもコピーされる
- **リソースの extras** は、設定 `ckan.extra_resource_fields` に列挙したキーだけが
  `res_extras_<key>` として索引される（既定では空）。データセットごとに、全リソースの値を
  1 つの多値項目に平らにする
- 呼び出し側は `fq=extras_spatial_unit:市町村` のように絞り込む

### 3. extras の値は文字列とは限らない

KUKAN の `extras` は `z.record(z.string(), z.unknown())` で、値には JSON の何でも入る。
キーにも制約がなく、日本語や `.`・`:` を含みうる。

## 検討した選択肢

### クエリパラメータの形

#### A) `extras=key:value` を繰り返す

パラメータ名が固定で、スキーマに書きやすい。ただし、キーに `:` を含むとどこで切るか決まらない。
エスケープ規則を足すと、URL エンコードに重ねてもう 1 層の書き方を覚えさせることになる。

#### B) JSON を 1 つのパラメータで渡す（`extras={"k":"v"}`）

曖昧さはないが、URL として読めず、手で書きにくい。CKAN の項目名とも対応しない。

#### C) `extras[key]=value`（ブラケット記法）

一部のフレームワークの慣習で、Hono は解釈しない。キーに `]` を含むと曖昧になる。CKAN とも
対応しない。

#### D) `extras_<key>=<value>` / `res_extras_<key>=<value>` — 採用（提案）

キーをパラメータ名の側に入れる。URL エンコードだけでどんなキーも表せる。今のネイティブ API の
絞り込みは `res_format`・`license_id` など CKAN の索引の項目名を使っており、それと並ぶ。
CKAN 互換の `fq` でも同じ名前を項目として読めるので、1 つの絞り込みに 2 つの入り口が対応する。

### 索引の持ち方（OpenSearch）

#### a) キーごとの動的項目

キーが増えるたびにマッピングが増え、サイトの入力しだいで上限に当たる。

#### b) `flat_object` 型

マッピングは増えない。ただし、キーをドット区切りのパスとして扱うので、`.` を含むキーと
入れ子のパスを区別できない。

#### c) 組を 1 つの文字列にした keyword の多値項目 — 採用（提案）

キーと値の組を `JSON.stringify([key, value])` で 1 つの文字列にし、keyword 型の多値項目に
入れる。`term` の完全一致で引ける。JSON の配列にするので、キーや値にどんな文字が入っていても
区切りは曖昧にならない。マッピングは 1 項目で固定される。

## 決定（提案）

### 1. クエリパラメータ

`GET /api/v1/packages` に次を足す。

| パラメータ                 | 意味                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| `extras_<key>=<value>`     | データセットの extras で、キー `<key>` の値が `<value>` のもの       |
| `res_extras_<key>=<value>` | いずれかのリソースの extras で、キー `<key>` の値が `<value>` のもの |

- `<key>` は URL エンコードして書く。KUKAN はキーの文字を削らない（CKAN と違う）
- 条件はすべて AND で結ぶ。同じパラメータを繰り返しても AND とする（`tags`・`res_format` と同じ）。
  OR は提供しない
- `res_extras_*` は条件ごとに「どれか 1 つのリソースが満たす」とする。2 つの条件を同じリソースが
  満たすことは求めない。CKAN の平らにした多値項目、KUKAN の `res_format` と同じ意味になる
- キーが空のもの（`extras_=`）は 400 で断る
- 1 リクエストの extras の条件数に上限を置く。値は実装時に決める
- `state=draft` の DB 直読みの経路では、ほかの索引由来の絞り込みと同じく断る

### 2. 値の比べ方

値は完全一致で比べる。大文字小文字の同一視、前後の空白の除去、Unicode の正規化はしない。

索引に入れる値は次のとおり。

| extras の値          | 索引に入れるもの                                |
| -------------------- | ----------------------------------------------- |
| 文字列               | そのまま                                        |
| 数値・真偽値         | JSON の表記（`5`、`true`）                      |
| 配列                 | スカラーの要素をそれぞれ（要素ごとに 1 つの組） |
| オブジェクト・`null` | 入れない                                        |

`extras_n=5` は、値が数値の `5` でも文字列の `"5"` でも当たる。クエリパラメータには型がないので、
索引の側で揃える。

### 3. 索引

- **OpenSearch**: データセットの文書に `extras_pairs`、リソースの子文書（ADR-025）に
  `extras_pairs` を、keyword の多値項目として足す。中身は §2 の規則で作った組の文字列
  （`JSON.stringify([key, value])`）。`extras_<key>` の条件は `term`、`res_extras_<key>` の
  条件は条件ごとの `has_child` で引く
- **PostgreSQL フォールバック**: 索引を持たず、`package.extras`・`resource.extras` を jsonb の
  演算子で直接比べる。§2 の規則（数値と文字列の同一視、配列の要素）に合わせた述語を
  1 か所に置き、両方の条件から使う。検索を PostgreSQL に寄せるとき（ADR-061 段階 2）に、
  組の文字列の配列を GIN 索引付きで持つかどうかを決める
- 旧ヘルスチェックのキー（`LEGACY_HEALTH_EXTRAS_KEYS`）は、読み取りと同じく索引にも入れない
- 非公開・下書きの扱いは、今の検索の可視性の絞り込みがそのまま効く

索引の形が変わるので、リリース後に全件の再索引が要る。

### 4. CKAN 互換の `fq`

`fq` の項目として `extras_<key>` と `res_extras_<key>` を読み、§1 の絞り込みに渡す。

- 値の比べ方は §2 の完全一致で、CKAN の `text` 型の照合（語に分けた一致）とは違う。
  CKAN より狭い結果になりうるが、extras の値は分類のコードや決まった語が多く、語に分けた
  一致を再現する費用に見合わない。この違いは互換 API の文書に書く
- `fq` は `:` で項目と値を切るので、`:` や空白を含むキーは `fq` では書けない。ネイティブ API を
  使ってもらう
- 同じ `extras_<key>` に違う値を 2 つ AND で並べても、`organization` などのように検索せずに
  0 件を返す短絡はしない。値が配列なら両方に当たりうる
- リソースの extras は、CKAN の既定と違って**すべてのキー**を索引に入れる。CKAN では
  `ckan.extra_resource_fields` に書いたキーだけが引ける。KUKAN で引けるものは CKAN の上位集合になる
- CKAN は extras をキー名だけの項目（`spatial_unit:...`）としても索引するが、KUKAN はこれを
  読まない。知らない項目として 409 で断る（ADR-060 §3）

## 影響

- extras で揃えた分類で、データセットを API から絞り込めるようになる
- CKAN のハーベスターや ckanapi から、`fq=extras_*` が使えるようになる
- データセットとリソースの検索文書が大きくなる。extras の量はサイトによって違うので、
  再索引のあとに索引サイズを確認する
- extras を書き換えたときの検索文書の同期には、新しい仕組みは要らない。データセットもリソースも、
  更新のたびに未反映フラグ（`doc_sync_due_at`）を立てており、文書の組み立てに extras を足せば
  次の同期で反映される

## 残課題

1. **キーワード検索（`q`）で extras の値を引くか。** CKAN は値を全文検索の項目にコピーしている。
   入れるなら値だけにしてキーは入れない。順位への影響を検索品質のゴールデンセットで測ってから
   決める。ADR-061 の BM25 の項目設計と一緒に決めるのがよい
2. **ファセット。** 「このキーにどの値が何件あるか」を返すかどうか。キーを指定させる形
   （`facet.field=extras_<key>`）が候補になる
3. **キーがあるかどうかだけの絞り込み**（`extras_<key>=*`）。今回は値としての `*` と区別が
   つかないので提供しない
4. **Web の検索画面と MCP の `search_datasets`** に extras の絞り込みを出すかどうか。
   どのキーを出すかはサイトごとに違うので、サイト設定で選ぶ形になる
5. **値の正規化。** 全角・半角の揺れなどで当たらないとの声が出たら、索引と問い合わせの両方に
   同じ正規化をかけることを検討する
