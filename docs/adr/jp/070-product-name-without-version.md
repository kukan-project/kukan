# ADR-070: 製品名は名乗り、バージョンは未認証の相手に出さない

## ステータス

**採用（Accepted）** — 2026-10-27

公開ページの `<head>` に `<meta name="generator" content="KUKAN">` を出す。製品名だけで、
バージョンは含めない。サイトごとに無効にできる。未認証の相手に届くものには KUKAN のバージョンを
出さない。これにはページ、API、ヘッダー、MCP、worker が外部へ名乗る User-Agent が含まれる。
バージョンを確認できるのは、認証済みのシステム管理者が開く管理画面だけとする。

## コンテキスト

### 1. 製品名を出したい理由

KUKAN を外部のどこが使っているかを把握したい。公開サイトを数えられれば、利用の広がりが分かり、
不具合や脆弱性を知らせる相手を探すときの手がかりにもなる。HTML の `generator` meta は、CMS や
静的サイトジェネレーターがこの目的で使う慣習的な置き場所である。

### 2. バージョンを出したくない理由

- **脆弱性診断の指摘事項になる。** 自治体のサイトが受ける脆弱性診断では「バージョン情報の開示」が
  指摘される。KUKAN を入れたことでサイト側に是正の手間を生ませたくない。
- **未パッチのサイトを特定されやすくなる。** 脆弱性が公表されたとき、版を名乗るサイトは、影響のある版で
  止まっているかどうかを外から一度の取得で判定できる。製品名だけなら、試してみるまで分からない。

製品名とバージョンは分けて扱える。製品名から分かるのは「KUKAN である」ことだけで、
その事実はページの構造やパスからも推測できる。攻撃の的を絞る役に立つのはバージョンの方である。

### 3. 調査した経路（2026-10-27、develop `ac20d9d8`）

| 経路                         | 調査時点                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Next.js の `X-Powered-By`    | ページに `X-Powered-By: Next.js` が付く（版は無い）                                                          |
| Hono・Caddy・CloudFront・ALB | `Server: Caddy`、`Via: … (CloudFront)`、ALB の自前エラーの `Server: awselb/2.0`。いずれも KUKAN の版ではない |
| CKAN 互換 API                | `status_show`（CKAN が `ckan_version` を返すアクション）は実装していない。ほかのアクションにも版は無い       |
| 公開 API                     | `/api/health` は `{status, timestamp}`、`/api/v1/site/settings` にも版は無い。OpenAPI は公開していない       |
| クライアントバンドル         | `NEXT_PUBLIC_*` で版は渡していない。版を読むのは `server-only` のモジュールだけ                              |
| エラーレスポンス             | 想定外の例外は固定文言の 500。スタック、ドライバのメッセージ、OpenSearch の詳細は返さない                    |
| MCP の `serverInfo.version`  | 固定の `1.0.0`。リリースとは連動していない                                                                   |
| **worker の User-Agent**     | **`KUKAN/<version> (+<site>)` を外部のサーバーへ送っていた**                                                 |
| Next.js 本体                 | クライアントのチャンクに `window.next={version:"16.x.y"}` が入る                                             |

worker の User-Agent は、リソースの URL を登録できる人なら誰でも読める。自分のサーバーを指す URL を
登録し、worker に取得させればよい。`nameSiteInUserAgent` を有効にしたサイトでは、サイトの URL と
版が同じヘッダーに並び、「どのサイトがどの版か」がそのまま伝わる。

## 検討した選択肢

### A) 製品名もバージョンも出さない — 不採用

診断の観点では最も手堅い。ただ、利用の把握という目的が果たせない。製品名はページの構造からも
推測できるため、隠しても得るものが小さい。

### B) 製品名もバージョンも出す（`KUKAN 0.39.0`） — 不採用

WordPress などが既定で取ってきた形だが、§2 の 2 点をそのまま抱える。

### C) 製品名は出し、バージョンは出さない。製品名は無効にできる — 採用

利用の把握に要るのは製品名だけで、診断で問題になるのはバージョンだけである。製品名さえ出したくない
サイト（診断で製品名も指摘された、閉じた運用で名乗る理由がない）のために、無効にする設定を置く。

## 決定

### 1. generator meta

- ルートレイアウトの `generateMetadata` で `generator: 'KUKAN'` を返す。値は製品名だけで、版は含めない
- 環境変数 `GENERATOR_META_ENABLED`（既定 `true`）で無効にできる。web が要求ごとに読むので、
  切り替えにイメージのビルドは要らない
- AWS では環境定義の `generatorMeta`（既定 `true`）。`nameSiteInUserAgent` と同じくサイトごとの
  項目で、マルチサイトでは各サイトのエントリに書く。`false` のときだけタスクに
  `GENERATOR_META_ENABLED=false` を渡すので、既定のままのサイトのタスク定義は変わらない
- Docker Compose では `.env`（マルチサイトは `sites/<site>.env`）に書く
- ブランドの設定（`brandConfig`）には置かない。ブランドはビルド時に決まり、同じブランドを使う
  サイト同士で値を分けられないため

切り替えても、CDN がキャッシュしたページには期限が切れるまで古い値が残る。すぐに反映させたい
ときは invalidation する。

### 2. 未認証の相手に版を出さない

- Next.js の `poweredByHeader: false`。版は入っていないが、フレームワークを名乗るだけで読む者がいない
- worker の User-Agent から版を外し、`KUKAN (+<site>)` とする。`robots.txt` が名指しする製品トークンは
  `KUKAN` のまま変わらない。版を読むためにだけ worker のイメージへ同梱していたルートの
  `package.json` も外す
- CKAN 互換 API に `status_show` を足さない。CKAN のクライアントがこれを呼ぶと 400 になる
- 上の状態をテストで固定する。未認証で主要な API（ヘルスチェック、サイト設定、データセット、
  CKAN 互換、サイトマップ、MCP の initialize、各種のエラー）を叩き、ヘッダーと本文にルートの
  `package.json` の版が無いことを確かめる。`X-Powered-By` を付けるのは Next.js だけなので、
  その設定（`poweredByHeader: false`）をテストで固定する

### 3. MCP の `serverInfo.version`

MCP の仕様上、必須の欄である。KUKAN のリリースとは切り離し、**MCP の機能面の版**として扱う
（`MCP_SERVER_VERSION`）。ツールを取り除く・結果の形を変えるときはメジャー、ツールを足すときは
マイナーを上げる。ツールに触れないリリースでは動かない。クライアントはこの値で相手の機能を
判断でき、未認証の相手には KUKAN のリリースが伝わらない。

### 4. 管理者向けの確認手段

既存の仕組みを使う。`/dashboard/admin/site` の「動作中のバージョン」にリリースの版と Node の版が
出る。ルートの `package.json` を `next build` が埋め込み、`server-only` のモジュールだけが読む。
ページはサーバー側で sysadmin であることを確かめる。認証付きの API は新しく作らない。
管理画面で足り、版を返す口を増やすほど、誤って未認証に開く経路が増えるためである。

## 影響

- 公開ページに `<meta name="generator" content="KUKAN">` が加わる（既定）
- 外部のサーバーが受け取る User-Agent が `KUKAN/<version> …` から `KUKAN …` に変わる。User-Agent の
  版で KUKAN を見分けていた取得先は、製品トークンで見分ける必要がある
- ページの応答から `X-Powered-By: Next.js` が消える

## 残課題

1. **Next.js 本体が埋め込む版。** クライアントのチャンクに `window.next={version:"16.x.y"}` が入る。
   Next.js がコードに直接書き込んでいて、設定では消せない。KUKAN の版ではなくフレームワークの版で、
   pnpm patch で消すとアップデートのたびに当て直しが要る。脆弱性診断が見るのはヘッダーと meta が
   中心なので、今は残す。Next.js の脆弱性への備えは、版を隠すことではなく更新を速く当てることで行う
2. **CloudFront・ALB の `Server` ヘッダー。** ALB が自分で返すエラーには `Server: awselb/2.0` が付く。
   CloudFront のレスポンスヘッダーポリシーで消せるが、CloudFront 自身が返すエラーの
   `Server: CloudFront` は消せず、効果が中途半端なので今は扱わない
