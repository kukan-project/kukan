# ADR-038: 初回ユーザーブートストラップとランタイム登録制御

## ステータス

**承認済み（Accepted）**

## コンテキスト

初期インストール時のユーザー作成は、これまで CLI（`pnpm db:create-user`）で
sysadmin を手動作成する運用だった。また、自己登録の有効/無効は環境変数
`REGISTRATION_ENABLED`（起動時固定、デフォルト無効）で制御しており、
切り替えには再デプロイが必要だった。

この構成には2つの問題がある。

- **初期化に DB へ直接アクセスできる端末が必要**: マネージド環境（ECS 等）では
  CLI 実行のための踏み台やタスク実行が必要になり、セットアップの敷居が高い
- **登録可否は運用中に切り替えたい設定**: イベント期間だけ登録を開放する、
  問題発生時に即座に閉じる、といった運用は再デプロイと相性が悪い。
  ADR-036 でも「将来の候補（`registrationEnabled` の DB 化等）」として
  ランタイム設定化を予告していた

## 決定

### 1. 初回ユーザーブートストラップ

**user テーブルの行数が 0 のとき**（削除済みユーザーも行として数える）、
システムは「ブートストラップ中」とみなし、次の2つの特別動作をする。

- 登録可否の設定値に関係なく**自己登録を許可**する
- 最初に登録されたユーザーを **sysadmin に自動昇格**する
  （Better Auth の `databaseHooks.user.create.before` で `role` を注入。
  admin プラグインの before フックは入力データ側を優先してマージするため、
  フック実行順に依存しない）

昇格の判定は行数カウントの再確認ではなく、`system_setting` への一意キー
（`bootstrap-completed`、レジストリ外の sentinel 行）の
`INSERT ... ON CONFLICT DO NOTHING` を **one-shot claim** として行う。
同時サインアップが全員「0人」を観測しても、一意制約により昇格の勝者は
常に1人に限定される（ADR-028 の durable claim と同じ発想）。

昇格は `audit_log` に記録する（entityType `user`、changes に
`{ bootstrap: true }`）。ユーザーが1人でも存在すればブートストラップは
恒久的に終了し、以降は通常の登録制御に従う（プロセス内で正結果を
キャッシュし、以後の COUNT クエリを省略する）。

- **判定は全行カウント**とする。「アクティブユーザー 0」判定にすると、全
  sysadmin 削除時に登録が再開放され次の登録者が sysadmin になる「自己回復」が
  生まれるが、挙動の予測しやすさを優先して採らない。ロックアウト回復は
  従来どおり CLI（`pnpm db:create-user`）で行う
- **claim の残骸は自動回復する**。claim 後・ユーザー作成前に初回登録が
  失敗すると sentinel だけが残るが、「ユーザー数 0 のまま claim が
  60秒超経過」を残骸とみなし、`UPDATE ... WHERE updated < now() - 60s
RETURNING` で**原子的に奪取**して次の登録者が昇格する。60秒未満の
  claim は進行中の並行登録のものとして尊重する（奪取しない）ため、
  競合排除は維持される
- **fresh な claim が存在する間、後続のサインアップは 409 で拒否**する
  （リトライ可能）。ここで通常ユーザーとして作成を許すと、claim 保持者が
  ユーザー作成前に死んだ場合にそのユーザーが「最初のユーザー」となり、
  sysadmin 不在のままブートストラップが終了してしまう。拒否しておけば、
  claim は完了するか 60秒で stale になり奪取可能になるかのいずれかに収束する

### 2. 登録可否のランタイム設定化と環境変数の廃止

`registration-enabled`（boolean、既定 false）を ADR-036 の system_setting
レジストリに追加し、管理画面（`/dashboard/admin/site`）のトグルで切り替える。
環境変数 `REGISTRATION_ENABLED` は**廃止**する。env 側に基準値を残さない
「ランタイム設定を唯一の置き場とする」形は、検索例クエリ（ADR-036）と同じ
パターンである。

`GET /api/v1/site/settings` の `registrationEnabled` は実効値
（ブートストラップ中 || 設定値）を返し、サインアップ UI はこれに従う。
API 側のガード（sign-up エンドポイントの 403）が常に正であり、UI 表示は
共有キャッシュ（ADR-026）の TTL 分だけ遅れて追従してよい。

### 運用上の注意

デプロイ完了から最初の登録までの間は、URL に到達できた人が誰でも sysadmin に
なれる。Gitea 等でも使われる一般的なパターンであり、閉域網では実害はないが、
インターネット公開デプロイでは**デプロイ後すみやかに初回ユーザーを登録する**
運用を前提とする。`pnpm db:create-user` はヘッドレス初期化・ロックアウト
回復用のフォールバックとして存続する。

## 結果

- 新規インストールは「デプロイ → ブラウザでサインアップ → その場で sysadmin」
  で完結し、DB への直接アクセスが不要になる
- 登録可否は管理画面から即時（キャッシュ TTL 内）に切り替えられる
- `REGISTRATION_ENABLED` を設定していた既存環境は、アップグレード後に
  管理画面で一度設定し直す必要がある（DB 設定の既定は無効）
