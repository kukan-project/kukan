# ADR-072: 管理画面のデータセット編集を公開ページの鏡にする（左にリソースの一覧、右にタブ、版が増える操作を分ける）

## ステータス

**提案（Proposed）** — 2026-11-11。

データセットの編集を、公開ページと同じ骨格の画面にする。左にデータセットの中身
（リソースの一覧）、右に選んだもの（データセットかリソース）の編集をタブで出す。
URL は公開ページと対にし（`/dataset/:name/resource/:id` ↔
`/dashboard/datasets/:id/resources/:id`）、どちらからでも同じリソースのまま相手の
ページへ移れるようにする。データセットを開いている間、ダッシュボードのサイドバーは
その一覧に入れ替わる。

保存のしかたは「版が増えない保存」「列の適用」「並び順の保存」の 3 つに分け、
タブごとにどれなのかを画面に書く。列に関する人の決定（主キー・確定型・役割の上書き・
将来の列の説明）は 1 つの「表の設定」タブに集め、まとめて 1 回で適用する。読み方を変える
決定（主キー・確定型）が入っていれば、その適用で版が 1 つできる（仕様書
`phase-versioning-2-ducklake.md` §6.5 の制約をそのまま画面にする）。役割の上書きのように
読み方を変えない決定だけなら版は作らない（ADR-063）。

## コンテキスト

### 現状

リソースの編集は `/dashboard/datasets/:name/edit` の「リソース」カードの中にある。
リソースの表の行を広げ、そのセルの中に次の 4 つを縦に積む
（`resource-list.tsx`、1441 行）。

1. 名前・形式・説明、URL／アップロード、extras —「保存」
2. 主キー（見本の行・確認ダイアログ・取り込み直しのボタンを含む）—「適用」で版が増える
3. 列の役割（ADR-063）— 読むだけ
4. 版の履歴と差分 — 戻す・パージは押した時点で効く

**保存のしかたが 3 種類、区別なく並んでいる。** 1 は版が増えず、2 は版が増え、4 は
押せば効く。どれがどれかは、それぞれの説明文を読まないと分からない。

**同じ列の一覧が 2 枚ある。** 主キーと役割はどちらも列ごとの情報だが、別のパネルに
別の並びで出ている。

**公開ページから編集へは遠回りになる。** 公開ページには、編集できる人にだけ出る処理状況の
ダイアログ（⚙）があり、そこから `edit?resource=:id` へ移るリンクを置いている。名前を
変える・ファイルを差し替える・主キーを決めるには、このリンクを開いてから表の中で
目当ての行を探す。

### これから増えるもの

次はどれも列ごとの、人が決める設定で、置き場所は上の 2・3 の近くしかない。

| 何                         | 出どころ                                    |
| -------------------------- | ------------------------------------------- |
| 確定型                     | 仕様書 §6.5・§8（ii-c）                     |
| 型が変わったときの選択     | 仕様書 §8（ii-c）                           |
| 主キーと型の AI 提案       | 仕様書 §14.1 項目 4（ii-c、ADR-040 の拡張） |
| XLSX の表の範囲            | ADR-057 Step 2（前提が ii-c）               |
| 列の役割の上書き           | ADR-063 の次の段                            |
| 列の説明・別名・機微フラグ | 仕様書 §6.2「将来」                         |

今の形のまま足すと、同じ列を一覧するパネルが表のセルの中に 4〜5 枚並ぶ。そのうえ
仕様書 §6.5 により、確定型の変更は **1 回の適用が版 1 つと同じバイト列の複製 1 つ**に
なる。列ごとに即時確定する UI は採れず、複数の列の変更をまとめて 1 回で適用させる
必要がある。パネルが分かれたままでは、主キーと型を一緒に変えても版が 2 つできる。

### 幅

ダッシュボードは 1200px の枠に 224px のサイドバーを置く。公開ページのリソースの一覧は
左に 320px（`resource-explorer.tsx`）。一覧をサイドバーの横に並べると 3 列になり、
「表の設定」タブの表（列名・推定型・確定型・主キー・役割、将来は説明）に使える幅は 650px
前後になる。

## 検討した選択肢

### A) 今の行展開に足す（却下）

上の「これから増えるもの」で述べたとおり、パネルが積み上がり、まとめて適用する形を
作れない。

### B) リソースごとの専用ページだけを作る（却下）

`/dashboard/datasets/:name/resources/:id` を作り、データセット編集の表からリンクする。
編集の場所は広がるが、リソースの間を移るたびにデータセットの表へ戻ることになり、
並べ替えやセクションの操作（ADR-050）と個々のリソースの編集が別の画面に分かれる。

### C) 公開ページの上で編集する（却下）

公開ページに編集の部品を出し、その場で書き換える。次の理由で採らない。

- **見せるものが違う。** 公開ページは公開された結果を見せる。編集には作業中の状態が
  要る：下書きのデータセット（ADR-039）、処理の失敗、版の差分・戻す・パージ、列の設定。
  版の履歴は公開ページにも出るが、そこで見せるのは一覧であって操作ではない。
- **作り方が違う。** 公開ページは SEO・OGP のための SSR で、ブランドがコンポーネントを
  差し替えうる（ADR-023 / ADR-042）。管理画面は CSR である（CLAUDE.md の使い分け）。
  編集の状態と部品を公開側に入れると、閲覧するだけの人のバンドルが重くなり、差し替えられた
  公開側のコンポーネントとも絡む。

CKAN も公開ページの上では編集させない。データセットのページの「Manage」から
`/dataset/edit/:name` へ、リソースのページから `…/resource/:id/edit` へ、別のページに
移って編集する。

### D) 公開ページの鏡になる編集ページ（採用）

骨格と URL を公開ページと対にし、中身だけを編集用にする。B の利点（場所が広い）を
保ったまま、一覧が常に左にあるので並べ替えと個別の編集が同じ画面にある。C のように
公開ページの作りへ手を入れることもない。

## 決定

### 1. URL を公開ページと対にする

| 公開                                      | 編集                                                   |
| ----------------------------------------- | ------------------------------------------------------ |
| `/dataset/:nameOrId`                      | `/dashboard/datasets/:packageId`                       |
| `/dataset/:nameOrId/resource/:resourceId` | `/dashboard/datasets/:packageId/resources/:resourceId` |

```
 公開ページ                                    編集ページ
┌──────────────────────────────┐            ┌──────────────────────────────┐
│ 区別人口統計          [✎ 管理]│ ─────────▶ │ ← データセット一覧           │
│ ┌────────┐ ┌───────────────┐ │            │ ┌────────┐ ┌───────────────┐ │
│ │一覧    │ │2024年 区別人口│ │            │ │一覧    │ │2024年 区別人口│ │
│ │ ▸2024年│ │  プレビュー   │ │ ◀───────── │ │ ▸2024年│ │ [基本][列]... │ │
│ │  2023年│ │               │ │ 公開ページ │ │  2023年│ │               │ │
│ └────────┘ └───────────────┘ │  を見る    │ └────────┘ └───────────────┘ │
└──────────────────────────────┘            └──────────────────────────────┘
   どちらの矢印も、開いているリソースを保ったまま移る
```

- **編集側はデータセットを ID で指す。** `/dashboard/datasets/new`（作成）と同じ階層に
  データセットを置くので、名前で指すと `new` という名前のデータセット（`slugNameSchema` は
  これを拒まない）が作成ページに解決されてしまう。ID なら作成ページの名前とぶつからない。
  今の編集ページも、名前で開いたあとアドレスバーを ID に書き換えている（`datasetEditPath`）。
  公開側は今までどおり名前で指す。対になるのは URL の構造で、データセットを指す文字列ではない
- 今の `/dashboard/datasets/:nameOrId/edit` は `/dashboard/datasets/:packageId` へ、
  `edit?resource=:id` は `…/resources/:id` へリダイレクトする（名前で来たら ID を引いてから移る）。
  `resourceEditPath`（`apps/web/src/lib/paths.ts`）の呼び出しは 1 か所だけで、そこを差し替える
- `/dashboard/datasets/new`（作成）はこの決定の外に置く。作成が終わったら新しい URL へ移る

### 2. データセットを開いている間、サイドバーをその中身の一覧に入れ替える

```
┌─ ヘッダー ─────────────────────────────────────────────────────────────┐
├────────────────────────┬───────────────────────────────────────────────┤
│ ← データセット一覧     │ 2024年 区別人口         ● 処理済み  v7        │
│                        │                         [公開ページを見る ↗] │
│ 区別人口統計           │ [基本] [列 2] [版 要確認] [処理]              │
│  データセットの情報    ├───────────────────────────────────────────────┤
│                        │ （選んだタブの中身）                          │
│ 統計表            ⋮⋮   │                                               │
│ ⋮⋮ CSV 2024年 区別人口●│                                               │
│ ⋮⋮ CSV 2023年 区別人口●│                                               │
│ ⋮⋮ XLSX 年齢5歳階級別 ●│                                               │
│ 参考資料          ⋮⋮   │                                               │
│ ⋮⋮ PDF 調査票         ●│                                               │
│                        │                                               │
│ [+ リソース][+ セクション]                                             │
│ [並び順を保存]（変更があるときだけ）                                   │
└────────────────────────┴───────────────────────────────────────────────┘
  ● = 処理の状態（下の表）        ⋮⋮ = ドラッグ（ADR-050 の規則）
```

サイドバーを残して一覧を横に並べる形（3 列）と、サイドバーをアイコンだけの帯にたたむ形も
比べた。入れ替えを採るのは次の理由による。

- **公開ページとまったく同じ 2 列になる。** 決定 1 の対が、URL だけでなく見た目でも成り立つ
- **「表の設定」タブの表に一番広い幅を回せる。**
- **データセットを編集している間に、ユーザー管理などの別の画面へ移ることはまずない。**
  全体の移動は「← データセット一覧」とヘッダーから行える

### 3. 左の一覧は ADR-050 の管理画面の規則をそのまま使う

見出しは区切り線として動かす。見出しの上に落とすとその区間の 1 番目に入る。編集は
まとめて「並び順を保存」で確定する。リソースのフォームに `section` は出さない。
**管理画面は平らに**、`/` 入りの名前を 1 本の見出しとして出す。どれも ADR-050 の
決定どおりで、変えるのは置き場所（表の中から左の列へ）だけである。

公開側の一覧は入れ子で、編集側は平らなので、両者は完全には同じ形にならない。編集側を
入れ子にしない理由は ADR-050 のとおり（区切り線が多段になり、操作が増える）。

各行には処理の状態を点で出す。今の表の状態のバッジ（`pipeline-status-badge.tsx`）が出し分けている
区別は、点でもすべて残す。点に置き換えて表をなくす以上、手を入れるべきリソースを一覧から
見つけられなくなってはならない。

| 点の状態 | もとになる状態                                                                                                                    | 見せ方                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 処理済み | `complete` で版ができた                                                                                                           | 成功の色                                                                              |
| 変化なし | `complete` で、中身が同じため版を作らなかった（今のバッジの `storedNoVersion`・「内容が同じため、新しい版は作成されていません」） | 成功の色を薄く。状態名で区別する                                                      |
| 未開始   | `pending`（行はあるが、積まれたものも走ったものも無い終端。ADR-044）                                                              | 枠線だけ（今の表と同じ）。再処理は勧めない（ADR-044 が `cancelled` と分けている理由） |
| 待機中   | `queued`（積まれて順番を待っている）                                                                                              | 枠線だけ（今の表と同じ）                                                              |
| 処理中   | `processing`                                                                                                                      | 主の色、動きあり（今の表と同じ）                                                      |
| 失敗     | `error`                                                                                                                           | 危険の色。今の表と同じ                                                                |
| 取り消し | `cancelled`                                                                                                                       | 注意の色。中身に合う派生物が無いことがある（今の表と同じ）                            |
| 要確認   | 型の変化を確かめる必要がある版がある（ii-c）                                                                                      | 注意の色。失敗・取り消しより弱い                                                      |

色だけで区別させず、点にはそれぞれの状態名をツールチップと読み上げで添える。

### 4. 右はタブで分け、タブごとに保存のしかたを 1 つにする

**データセットを選んだとき**

| タブ       | 中身                                                                                                                                        | 保存                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 基本       | タイトル・URL 名・組織・説明・タグ・ライセンス・extras、AI 提案。下書きでは「保存して公開」と、公開後に検索への反映が失敗したときのやり直し | 版が増えない保存（下書きは公開も） |
| 危険な操作 | 削除・パージ（今の Danger Zone）。削除済みのデータセットでは、元に戻すとパージ                                                              | 押して確認                         |

下書き（ADR-039）では、基本のタブに今の「保存して公開」（`POST /api/v1/packages/:id/publish`）を置く。
公開したあと検索への反映だけが失敗したときに出す、やり直しの帯（今の `PublishSyncBanner`）も残す。
これを落とすと、作った下書きを公開する手段がなくなる。

削除済みのデータセット（今の `?state=deleted` の表示）は、基本のタブを読むだけにし、危険な操作の
タブに「元に戻す」（`POST /api/v1/packages/:id/restore`、非公開にして戻す選択を含む）とパージを
置く。元に戻す操作を落とすと、削除したデータセットを画面から戻す道がなくなる。どちらも組織の
`admin` 以上が要る操作で、確かめるのは API である。

**削除済みのデータセットでは、リソースも読むだけにする。** 左の一覧はリソースを並べて見せるだけで、
選べず、並べ替え・追加もできない。右に出るのはデータセットの基本（読むだけ）と危険な操作だけで、
リソースのタブは開かない。リソースへの書き込みと読み出しの多くは、親のデータセットが有効か下書きの
ときしか通らない（`checkResourcePermission` は `active` と `draft` だけを引く）ので、開けても
保存・列の変更・差分・再処理・削除はすべて「見つからない」で失敗する。今の削除済みの表示も、
リソースを読むだけの一覧で見せている。

**リソースを選んだとき**

| タブ           | 中身                                                                                                                              | 保存                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 基本           | 名前・形式・説明・ソース（URL／差し替え）・extras。その下にリソースの情報（読むだけ、AI の抄録を含む）と削除                      | 版が増えない保存（ソースと形式を除く、決定 6）   |
| プレビュー     | 公開ページと同じプレビュー（下書き・非公開のデータセットでも）。表として読む形式では「表の設定」に入る                            | なし                                             |
| 表の設定       | 上にプレビュー（選んでいる主キーに印）、下に「列の設定」として列ごとの人の決定を 1 つの表に（決定 5）。表として読む形式だけに出す | 列の適用（読み方を変えるなら版が増える、決定 5） |
| バージョン履歴 | 履歴・差分・戻す・パージ・型の変化の確認                                                                                          | 押して確認                                       |
| 処理状況       | 各ステップの状態・再処理（URL の取得し直しは選んだときだけ、決定 7）                                                              | 押して確認                                       |

**表として読む形式では、プレビューを「表の設定」の上に置き、別の「プレビュー」タブは出さない（2026-11-21）。** 列を決めるには値を見る必要があり、もとの「表の設定」は主キーを選ぶための値の見本を持っていて、プレビューとほぼ同じ画面になっていた。見本の代わりに公開ページと同じプレビュー（ページ送り・絞り込み・テキスト表示を含む）を置き、選んでいる途中の主キーに印を付ける。プレビューの下の項目の一覧は、「列の設定」の表と重なるので出さない。内容が前の版のままのプレビューは出さない（前の見本と同じ）。読むだけの人（削除済みのデータセットなど）には「表の設定」が無いので、「プレビュー」タブを残す。列の型は、プレビューの見出しにも添える（公開ページも同じ）

**上の 2 つの表は、置き場所の考え方を示すもので、操作の目録ではない。** 今の編集画面にある操作は、
ここに挙げていないものもすべて新しい画面のどこかに残す。漏れがないかは、Step 1 の実装 PR で今の
画面と 1 つずつ突き合わせて確かめ、移し先もそこで決める。

**どの保存で版が増えるのかを、ボタンの前で分かるようにする。** 今は同じ見た目のボタンが違う結果を
生む。「表の設定」タブは先頭に 1 行で書く（「主キーを変えて適用すると、版が 1 つ増えます」）。
基本のタブは、版が増えるのがソースと形式を変えた保存だけなので、その保存の確認で示し（決定 6）、
先頭には書かない。ほとんどの保存は版が増えず、いつも出す 1 行は読み飛ばされる。

「表の設定」タブを出す条件は、今の主キーの欄と同じ `isTableSourceFormat` にする（保存済みの
形式で判定し、入力中の形式では出し入れしない）。

### 5. 「表の設定」タブは、列の一覧を 1 枚にし、変更を下書きにためて 1 回で適用する

```
 保存: 主キーと型の変更は、まとめて適用すると版が 1 つ増えます
 [✦ 主キーと型を AI に提案させる]
┌──────────┬──────────────┬──────────────┬────────┬────────┐
│ 列       │ 推定型       │ 確定型       │ 主キー │ 役割   │
├──────────┼──────────────┼──────────────┼────────┼────────┤
│ 区コード │ string       │ 推定に従う ▾ │ ☑      │ ID     │
│▌年   AI  │ integer      │ 推定に従う ▾ │ ☑      │ 日付   │ ← 下書きの行は色を付ける
│ 男       │ integer      │ 推定に従う ▾ │ ☐      │ 数量   │
│▌増減率 AI│ string ←float│ decimal    ▾ │ 不可   │ 率     │
└──────────┴──────────────┴──────────────┴────────┴────────┘
┌──────────────────────────────────────────────────────────────┐
│ 変更 2 件（未適用）                          [取消] [適用…]  │
│ 適用すると v8 ができ、同じファイルをこの読み方で取り込み直す │
└──────────────────────────────────────────────────────────────┘
```

- **列を 1 行に、人の決定を列の向きに並べる。** 主キー・確定型・役割を今は別々の
  パネルに出しているが、1 つの表にまとめる。将来の列の説明・別名・機微フラグもここに列として
  足す。XLSX の表の範囲（ADR-057）は表の上に置き、同じ適用に含める
- **変更は下書きにためる。** 行に色を付け、下に件数と適用の結果を出し続ける。適用するまで
  何も保存しない
- **適用の結果は、下書きの中身で決まる。** 「表の設定」タブの決定は、読み方を変えるものと変えないものに分かれる。

  | 決定                        | 読み方   | 適用したとき                                                    |
  | --------------------------- | -------- | --------------------------------------------------------------- |
  | 主キー・確定型・XLSX の範囲 | 変える   | 版が 1 つできる（版の同一性の入力、仕様書 §6.4・§6.5、ADR-057） |
  | 役割の上書き                | 変えない | 版は作らず、その場でプロファイルと索引を作り直す（ADR-063）     |
  | 列の説明・別名・機微フラグ  | 変えない | 版は作らない                                                    |

  下書きに読み方を変える決定が 1 つでもあれば、まとめて 1 つの版にし、読み方を変えない決定も
  その適用に含める。読み方を変えない決定だけなら版は作らない。下の帯と確認の文言もこれに
  従う（「適用すると v8 ができます」か「版は増えません。プロファイルと索引を作り直します」）

- **AI の提案は下書きを埋めるだけにする。** 提案された行には印を付け、適用は人が押す
  （ADR-040 の提案型と同じ）
- **適用の前に確認を出す。**

```
┌─ 列の設定を適用して v8 を作る ─────────────────────────┐
│ ・年: 主キーに加える                                   │
│ ・増減率: 型 推定（string）→ decimal                   │
│ ┌────────────────────────────────────────────────────┐ │
│ │ ファイルの中身は同じです。同じファイルをこの読み方 │ │
│ │ で取り込み直し、新しい版にします。v7 はそのまま    │ │
│ │ 残り、いつでも戻せます。                           │ │
│ └────────────────────────────────────────────────────┘ │
│                                   [戻る] [v8 を作る]   │
└────────────────────────────────────────────────────────┘
```

「表の設定」タブに下書きが残っているあいだは、編集ページを離れるすべての経路で、捨てるかどうかを聞く。
タブの切り替え、別のリソースやデータセットの情報の選択、「← データセット一覧」・公開ページ・
ヘッダーのリンク、ブラウザの戻る・進む、再読み込みとタブを閉じる（`beforeunload`）。下書きは
画面の中にしか無く、保存されていないので、どれか 1 つでも黙って通すと作業が消える。

**この確認は列の下書きに限らない。** 保存していない変更があるあいだは、どれも同じ扱いにする —
基本のタブで入力中のフォーム（データセットとリソースの両方）、まだ保存していない並び順や
セクションの編集（ADR-050 の「並び順を保存」の前の状態）。今の編集画面も、フォームや並び順を
編集しているあいだは行の操作をロックしている。新しい画面は左の一覧が常に見えているので、
ロックの代わりに、別のものを選んだときに捨てるかどうかを聞く。

### 6. ソースと形式は基本のタブに置き、版が増えることを保存の前に示す

基本のタブで版にかかわるのは、ソースと形式の 2 つである。**保存で処理を走らせるのも、この
2 つが変わったときだけにする。**

今の `PUT /api/v1/resources/:id` はこうなっていない。URL のリソースは、名前や説明だけを
変えても毎回処理を積み直す（`settleResourceWrites` は URL が変わったかを見ない）ので、取得した
中身が変わっていれば、名前の保存で版が増える。逆にアップロードのリソースは、形式を変えても
処理を積まないので、形式の変更は次に処理が走るまで版に届かない。どちらも、保存の前に出す
確認と食い違う。そこで次のように変える。

- 処理を積むのは、ソース（URL・種別）か形式が保存の前後で変わったときに限る。アップロードの
  リソースで形式が変わったときも積む
- ただし、保存の後からファイルが届く保存（URL からアップロードへ切り替える、ファイルを差し替える）
  では `PUT` で積まない。今の保存は `PUT` を先に送り、ファイルはその後で送る。`PUT` で積むと、
  ファイルが届く前に古い中身を新しいソースや形式で処理し、要らない版を作る。この場合は今までどおり、
  ファイルの取り込みが終わったとき（アップロードの昇格）に積む
- ADR-050 の「書き込み経路」は、`PUT` が URL のリソースの処理を毎回やり直す前提で書かれている。
  この決定はその前提を変えるので、ADR-050 の該当箇所に注記を足す。並べ替えを `PUT` ではなく
  reorder に載せる ADR-050 の判断は、そのまま成り立つ（見出しを変えても処理は要らない）
- 名前・説明・extras だけの保存では積まない（検索の索引は今までどおり反映する）。URL を
  取得し直したいときは、「処理状況」タブの再処理で「URL からファイルを取得し直す」を選ぶ（`POST /resources/:id/run-pipeline`）

| 変えるもの         | 版                                                                             |
| ------------------ | ------------------------------------------------------------------------------ |
| ファイルの差し替え | 中身が前の版と違えば増える（版のゲートがハッシュで判定する）                   |
| URL                | 取得した中身が前の版と違えば増える。取得が終わるまで分からない                 |
| 形式               | 増える（版の同一性の入力 `sameVersionIdentity` の 1 つで、中身が同じでも立つ） |

形式は読み方なので、「表の設定」タブに寄せる考え方もある。それでも基本のタブに置くのは、形式が
公開ページに出るラベルでもあり、利用者にとってはソースと並べて決めるものだからである。
ソースも同じ理由で、名前・説明と並べて置く。

代わりに、ソースか形式を変えて保存するときは確認を出す。形式は「版が 1 つ増えます」。
ファイルの差し替えと URL は、保存の時点では中身が前の版と同じか分からないので、
「中身が変わっていれば版が 1 つ増えます」と条件付きで書き、版ができたかどうかは処理が
終わってから「バージョン履歴」タブと一覧の点で示す。

### 7. 公開ページから移る入口を見出しの「管理」アイコンにする

- データセットの名前と、開いているリソースの名前の横に、鉛筆のアイコンを置く。「管理」は
  ツールチップと読み上げの名前で、文字では出さない。閲覧するだけの人と見た目を大きく変えない
  ためである。押すと同じタブで編集ページへ移る。出すのは、そのデータセットに
  書き込める人だけにする（データセットの組織で `editor` 以上、sysadmin、下書きの作成者。
  API の書き込みの規則 `packageWriteDenial` と同じ）。セッションのある要求は CDN の
  キャッシュを通らないので（`infra/lib/constructs/cdn.ts` の HTML のふるまい）、出し分けで
  キャッシュは汚れない
- **この判定は `canEditPackage`（`apps/web/src/lib/roles.ts`）で行う。** もとの `canManage` は
  `/users/me/organizations` にその組織があるかだけを見ており、閲覧だけの `member` も含んで
  いた。書き込みは `editor` 以上を要求する（`makePackageAuthorize(db, user, 'editor')`）ので、
  押しても何も保存できない人に ⚙ が出ていた。この ADR の提案中に、今の公開ページと編集ページ
  へ先に入れてある
- 処理状況のダイアログ（⚙）は残し、出す条件も上と同じ判定にする。中にあった編集ページへの
  リンクは、見出しのアイコンと行き先が重なるので外す
- ダイアログと「処理状況」タブの再処理は 1 つのボタンにする。押すと今のファイルから作り直し
  （`rebuildOnly`）、URL のリソースだけ「URL からファイルを取得し直す」を選べる。既定で選ばない
  のは、取得し直すと巻き戻しが打ち消されるからである（ADR-044 §4）。ただしリソースがファイルを
  持っていない（一度も取得できていない）ときは既定で選ぶ。作り直す元が無いからである。持っているかは
  処理状況の API が返す（`has_content`）。画面の操作の履歴では決めない — 読み込み直したときや
  別の管理者が開いたときに、既定が変わってしまうからである

### 8. 狭い画面では一覧を上に重ねる

ダッシュボードのサイドバーは `md` 未満では出していない（ヘッダーのメニューに移る）。
編集ページも同じ境目で 1 列にし、一覧は本文の上に折りたためる形で置く。

API の変更は 2 つある。

- `PUT /api/v1/resources/:id` が処理を積む条件を、ソースか形式が変わったときに絞る（決定 6、Step 1）
- 役割の上書きを書き込めるようにする（決定 5、Step 4）。今の役割は読むだけで、
  `GET /resources/:id/column-roles` しかなく、`column_settings` の書き込み（`columnSettingsBodySchema`）
  は主キーしか受け付けない。役割を足し、書き込んだらその場でプロファイルを作り直して索引を
  更新する（ADR-063）

「表の設定」タブの確定型の適用は、今の主キーの設定と同じ書き込みに確定型を足す形になる（ii-c の仕様で
決める）。

## 段階

| 段階   | 内容                                                                                                                                                                                                                     | 前提   |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------ |
| Step 1 | 新しい URL と 2 列の骨格へ移す。主キーと役割を「表の設定」タブの 1 つの表にまとめ（役割はまだ読むだけ）、主キーを下書き→適用にする。保存で処理を積む条件を絞る（決定 6）                                                 | なし   |
| Step 2 | 公開ページの「管理」アイコン、⚙ のリンクを外す、再処理を 1 つに                                                                                                                                                          | Step 1 |
| Step 3 | ii-c（確定型・型の変化の確認・AI 提案）を「表の設定」タブと「バージョン履歴」タブに載せる                                                                                                                                | Step 1 |
| Step 4 | 役割の上書き（ADR-063 の次の段）。`column_settings` に役割を足す書き込みと、プロファイル・索引の作り直し。「表の設定」タブの役割の欄を編集できるようにする（実装済み、2026-11-21。文字列の列だけ、適用は再処理と同じ道） | Step 1 |

Step 1 では見た目と置き場所を変えるが、できることは増やさない。主キーの適用は今も
「選んでから適用」なので、下書き→適用にしても意味は変わらない。役割は今と同じく読むだけで
並べ、上書きは Step 4 で入れる。保存で処理を積む条件を絞るのは、できることを減らす変更で
ある（名前の保存で URL を取得し直さなくなる）。取得し直す手段は「処理状況」タブの再処理（「URL からファイルを取得し直す」）に残る。

## トレードオフ

- **ダッシュボードの全体の移動が、データセットを開いている間は一手遠くなる。**
  「← データセット一覧」とヘッダーで足りると判断した
- **表で全リソースの状態を一度に見る画面がなくなる。** 一覧の点で代える。並べ替えのために
  表を眺める用途は、左の一覧が引き受ける
- **公開側と編集側で一覧の入れ子が違う**（決定 3）

## 残課題

- データセットの作成（`/new`）を同じ骨格に寄せるか
- 型の変化の確認を「バージョン履歴」タブにどう出すかの詳細は、ii-c の仕様（仕様書 §8）で決める。URL の
  リソースの再取得は人がいないところで起きるので、取り込み時に選ばせる形は成り立たず、
  取り込んだ後に確認する形になる
- 「表の設定」タブの表が横に広がったとき（列の説明などを足したとき）の出し方
