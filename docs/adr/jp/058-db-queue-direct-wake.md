# ADR-058: ジョブキューを PostgreSQL に移し、worker には直接通知する（SQS 廃止）

## ステータス

**承認済み（Accepted）** — 2026-09-27

ADR-002（SQS 採用）を置換する。ADR-022（DB ポーリング、取り下げ）と
ADR-044 の選択肢 C が DB キューを退けた理由（Aurora Serverless v2 の 0 ACU と非互換）は、
本 ADR の通知方式で解消する。

ジョブの正本を PostgreSQL の `job` 表に置き、SQS / ElasticMQ / DLQ を廃止する。
worker は DB をポーリングしない。API がジョブをコミットしたあと worker に**内容のない通知**を
送り、worker は通知を受けたら表が空になるまで処理して、接続を手放して待つ。

## コンテキスト

### 1. SQS は正本の二重化を生んでいる

投入は「`resource_pipeline` を `queued` に upsert → SQS に送信」の 2 段で、
間にトランザクションの境界がない（`packages/api/src/services/pipeline-service.ts`）。
送信の失敗は補償の UPDATE で `error` に戻すが、プロセスが 2 段の間で落ちると
`queued` のまま誰も処理しない行が残る。ADR-022 再検討（2026-07-28）の分類でいう
**B. トランザクション外の副作用**であり、DB キューなら構造的に消える種類の不具合である。

同じ再検討は「B の利点は outbox パターンで移行せずに取れる」と結論したが、outbox は
キュー（SQS）を残したまま DB 側に投入の意図を書き、取りこぼしを定期スイープで拾う
仕組みである。**正本が DB とキューの 2 つになる構造は変わらず、部品は増える。**

### 2. SQS が担っていることは多くない

| SQS の機能         | KUKAN での使われ方                                                                  |
| ------------------ | ----------------------------------------------------------------------------------- |
| 配信               | 14 種のジョブ型、`enqueue` 呼び出しは api / worker に約 30 箇所                     |
| 可視性タイムアウト | 10 分。worker が 2 分ごとに延長、最長 90 分（`packages/adapters/queue/src/sqs.ts`） |
| 遅延配信           | 4 箇所（embed の debounce、claim 待ちの再投入、取得レート制限）                     |
| DLQ                | `maxReceiveCount: 3`、保持 14 日。**読む仕組みもアラームもない**                    |
| キュー長メトリクス | worker のオートスケール（visible + inFlight）                                       |
| 取得               | worker 1 タスクにつき 1 件ずつ直列                                                  |

どれも PostgreSQL の行とタイムスタンプで表せる。優先度・FIFO・ファンアウトは使っていない。

### 3. キューが環境差のアダプターになっている

ADR-005 はアダプターを「環境差があるもの」に限っている。キューはその 1 つで、
開発・オンプレでは ElasticMQ コンテナを 1 つ余計に運用し、AWS 以外のクラウドに
載せる場合はそのクラウドのメッセージングに合わせた実装が新たに要る。PostgreSQL は
すべての環境に既にあり、キューを載せれば環境差そのものがなくなる。

### 4. 過去に DB キューを退けた理由

ADR-022 と ADR-044 選択肢 C の理由は同じで、**worker が DB に「仕事はあるか」と聞き続ける**
（ポーリング・接続保持）ため、Aurora Serverless v2 が 0 ACU に下がらないことだった。
LISTEN/NOTIFY も接続を保持するので同じである。

一方、書き込む側が知らせる分には DB を止めない。ジョブを INSERT する瞬間は
DB がどのみち起きているからである。**止まらない原因は「DB で待つこと」であって、
「DB にキューを置くこと」ではない。**

## 検討した選択肢

- **A) SQS を維持し、outbox を足す**: B の不具合は消えるが、正本の二重化と ElasticMQ は残り、
  outbox 表と再送スイープが増える。
- **B) DB キュー + ポーリング（ADR-022）**: 最も単純だが 0 ACU と非互換。RDS / オンプレ /
  0 ACU を持たないクラウドの DB なら問題はないが、環境ごとに実装を分けることになる。
- **C) DB キュー + 直接通知（採用）**: ポーリングしないので 0 ACU を妨げない。全環境で
  1 つの実装になる。代償は通知の経路（API → worker）を新たに持つこと。
- **D) DB の変更をトリガーに外部メッセージングへ流す**: LISTEN/NOTIFY と論理レプリケーション
  （CDC）は受信側が接続を保持する。トリガーから Lambda を呼ぶ方式（`aws_lambda.invoke`）は
  ロールバックされず、Aurora 専用で、結局 SQS が残る。
- **E) pg-boss 等の既製ライブラリ**: 内部でポーリングするため B と同じ問題を持つ。
  スキーマを独自に管理する点も、Drizzle のマイグレーションと二重になる。

## 決定

選択肢 C を採用する。

### 1. `job` 表が正本

ジョブ 1 件を 1 行とする。列の案:

| 列             | 役割                                               |
| -------------- | -------------------------------------------------- |
| `type`         | ジョブ型（既存の `*_JOB_TYPE`）                    |
| `payload`      | JSONB                                              |
| `run_at`       | この時刻以降に取得できる（遅延配信・再試行の待ち） |
| `priority`     | 取り出しの順（§6）                                 |
| `attempts`     | 取得回数                                           |
| `locked_until` | リース期限。NULL なら未取得                        |
| `locked_by`    | 取得した worker の識別子（延長・完了時の照合用）   |
| `last_error`   | 直近の失敗                                         |
| `state`        | `ready` / `dead`                                   |

- **投入**は INSERT。呼び出し側がトランザクションを渡せば業務データの更新と同じ
  トランザクションに入る（§1 の不具合が消える）。
- **取得**は `FOR UPDATE SKIP LOCKED` で `run_at <= now()` かつリース切れの行を、`priority`、
  `run_at` の順に 1 件取り（§6）、`locked_until` を進めて `attempts` を加算する。
- **延長**は現在の SQS と同じ間隔（2 分ごと、最長 90 分）で `locked_until` を進める。
  処理中は DB が起きているので、延長の UPDATE は 0 ACU を妨げない。
- **完了**は DELETE。SQS と同じく成功したジョブは残さない。
- **失敗**は `last_error` を記録し、`attempts` が上限（現在の `maxReceiveCount` と同じ 3）に
  達したら `state = 'dead'` にする。上限未満なら `run_at` を後ろにずらしてリースを外す。
- **dead** の行は残し、管理画面で見えるようにする。いまの DLQ は誰も読んでいないので、
  失敗が見えるようになる分だけ改善になる。
- **削除（版・組織）のジョブが消えたら積み直す。** 削除は対象を `purging` にしてからジョブが
  進めるので、ジョブが消えると（管理画面での削除、保持期間を過ぎた dead の自動削除）対象は
  `purging` のまま動かなくなり、再要求も受け付けない。毎時の処理で、ジョブが 1 件もない
  `purging` の対象の削除を積み直す。dead のジョブが残っている間は積み直さない（管理画面から再投入できる）

ADR-044 のリソース単位の claim はそのまま残す。キューのリースはジョブ単位、claim は
リソース単位の排他で、対象が違う（リソースに属さないジョブ型が半数近くある）。
リース切れのあとに古い実行が生き残る窓は DB キューにしても残るので、claim の保険は引き続き要る。

### 2. worker はポーリングせず、通知を受けたら空になるまで処理する

```
API     : INSERT job（コミット）→ worker に POST /wake（内容なし、応答を待たない）
worker  : 通知を受ける → 取得できる行がなくなるまで取得・処理 → 接続を手放して待つ
```

- **通知は失われてよい。** 正本は DB にあり、通知は「見に来い」以上の意味を持たない。
  失敗は記録するだけで、投入は成功として扱う。
- **処理中に通知を受けたら**、空にしたあともう一周する（取りこぼし防止のフラグ 1 つ）。
- **起動時に一度空にする。** worker が落ちていた間に届かなかった通知の分はここで拾う。
- **遅延ジョブ**は、worker が取得時に見た最も早い未来の `run_at` にプロセス内タイマーを
  仕掛けて拾う。DB を起こすのはその時刻の 1 回だけである。
- **リース切れの回収**は、遅延ジョブと同じタイマーで拾う。タイマーの時刻は `run_at` と
  `locked_until` の遅いほうの最小値で、クラッシュした worker が持っていたジョブもリースが
  切れた時点で拾われる。生きている worker はリースを延長し続けるので、その間タイマーは
  延長のたびに掛け直されるが、処理中は DB が起きているので 0 ACU は妨げない。
  次の通知・起動時の一括処理と、既存の毎時の cron も拾う（毎時の cron は今も DB を
  起こしているので、新たに 0 ACU を妨げるものは増えない）。
- worker 自身が積んだジョブ（処理中のジョブが積む後続、cron が積むもの）も、web と同じく全台に
  通知を送り、自分のプロセスでも 1 周する。自分だけで 1 周すると、処理中の今のジョブが終わるまで
  積んだ分を抱え込み、空いている他の台は遊んだままになる（SQS のときは空いている台がすぐ取った）。
- **受け取った通知は転送しない。** `/wake` の受信、毎時の 1 周、起動時の 1 周は、自分の
  プロセスで 1 周するだけにする。転送すると、台どうしが通知を送り合い続ける。通知が出るのは、
  1 周の中で走ったジョブが新たにジョブを積んだときだけなので、通知の数はジョブの数で上限が決まる。

待機中に DB 接続を持たないことが要件になる。worker のプールは既定で 10 秒で
アイドル接続を閉じる（`WORKER_DB_POOL_IDLE_TIMEOUT_MS`）。

### 3. 通知の経路

- worker は既に HTTP ポート（`HEALTH_PORT`、ヘルスチェック用）を持つ。`/wake` をここに足す。
- Docker Compose ではサービス名（マルチサイトはコンテナ名）で届く。
- ECS では Cloud Map の DNS で worker サービスに名前を与える。環境に 1 つプライベート DNS
  名前空間（`<env>.internal`）を置き、各サイトの worker がサービス名で A レコードを持つ
  （`kukan-<env>[-<site>]-worker.<env>.internal`）。マルチサイトでは名前空間を共有スタックが持ち、
  SSM パラメータでサイトスタックへ渡す。Service Connect は web の横にプロキシが要り、small 構成の
  web のメモリを削るので採らない。
- web のセキュリティグループから worker のポートへの経路を開く。セキュリティグループは環境内の
  サイトで共有なので、他サイトの worker にも届くが、トークンがサイトごとの秘密から導かれるので
  拒否される。
- 内部専用の共有シークレットで認証する。新しいシークレットは足さず、web と worker が
  既に持っている `BETTER_AUTH_SECRET` から HMAC で導いたトークンを使う（配布・ローテーションの
  対象が増えない）。`/wake` が外部から叩かれても、worker は「表を見に行く」だけで、
  被害は DB を起こすことに限られるが、それでも公開はしない。
- worker が複数台なら通知は全台に送る。web は名前が引ける IP をすべて取り、それぞれに POST する。
  worker は 1 件ずつ処理するので、処理中の台に届いた通知は「終わったらもう 1 周」の予約にしか
  ならない。1 台だけに送ると、その台が長いジョブの最中なら、空いている台があっても新しいジョブは
  そのジョブの終わりまで待つ。空いている台が取り、`SKIP LOCKED` が同じ行の二重取得を防ぐ。
  スケールアウトで起動した台は起動時の一括処理で加わる。

### 4. オートスケールの指標

SQS のキュー長メトリクスは使えなくなる。DB を覗いて件数を数える方式は DB を起こすので採らない。
worker が**処理中に**待ち行数を数え、構造化ログ（CloudWatch Embedded Metric Format、
`KUKAN/Worker` の `JobsWaiting`、次元 `Site`）で出す。

- 数えるのは、すぐ取れる行、リース中の行、失敗して再試行を待つ行の合計（SQS の visible +
  in flight に相当）。リース中の行を数えないと、一度取られた仕事が残っているのに縮小してしまう
- 処理中の台が数えるのはジョブを処理している間だけ（1 周の最初のジョブを取得したとき、以降は
  1 分ごと）。処理中は DB が起きているので、DB を新たに起こすことはない。1 周の最初に必ず数え直すのは、
  待機中の値のまま処理が続くと縮小が走ってしまうため
- 1 周を終えて待機に入った台は、再試行を待つ行のうち誰も握っていないものだけを数えて出す
  （1 周の終わりなので DB は起きている）。他の台が握っている行は握っている台が出す。待機中の台が
  それまで数えると、その台が処理を終えた後も古い値を出し続け、縮小を止めてしまう。意図して
  遅らせた行（debounce）は、まだ仕事ではないので数えない。再試行待ちを数えないと、失敗の波が
  「仕事なし」に見え、仕事を残したまま縮小する
- 各台は 1 分ごとに値を出すので、系列は途切れず、縮小の判断も止まらない
- 処理中の台は表全体の件数を、待機中の台は再試行待ちの件数だけを出すので、Maximum で集約する。段階と閾値（0 で縮小、5 で +1、
  25 で +2、クールダウン 300 秒）は SQS のときのものを引き継ぐ
- カスタムメトリクスは課金されるので、伸縮を設定したサイト（`maxTasks > minTasks`）だけが出す

### 5. ヘルスチェック

現在の worker は「直近 60 秒以内に SQS をポーリングした」ことで生存を示している
（`apps/worker/src/index.ts`）。ポーリングしなくなるので、定義を「HTTP に応答する」だけに改める。
イベントループが止まれば応答できないので、同期処理で固まった場合はこれで検出できる。

- DB への問い合わせを生存の条件に入れてはならない（ヘルスチェックのたびに DB を起こす）
- 処理中のジョブの経過時間も条件に入れない。延長の上限（90 分）を超えたら unhealthy とすると、
  正当に長いジョブがタスクごと止められ、再試行のたびに同じ位置で止められて `dead` になる。
  上限を超えたジョブはリースを手放すので、他の worker（または同じ worker の次の回）が引き継げる

この定義では、非同期の待ちが返ってこない場合（応答しない外部サービスを待ち続ける等）は
検出できない。worker は 1 件ずつ処理するので、1 台構成ではその間キュー全体が止まる。
SQS 時代も受信ループは 1 本で同じ性質だったが、止まる原因の側を塞ぐ：外部への待ちには
時間制限を持たせる（外部 URL の取得、OpenSearch、AI の抄録生成と埋め込み、S3 の接続と無通信）。

### 6. 取り出しの順序（2026-09-29 補足）

移行時点では `run_at` の順だけで取り出していた。そのため、人が待っている仕事が、誰も待っていない
一括処理の後ろに並んだ。「全リソースの再処理」で数百件の `resource-pipeline` が積まれた直後に
編集者がリソースを 1 件更新すると、その run は数百件の後ろに付く。

`job.priority` を足し、`priority`、`run_at` の順に取り出す（同時に積まれて `run_at` が同じものは `id` の順）。基準はジョブの種類ではなく
**誰が結果を待っているか**である。同じ `resource-pipeline` でも、編集者の保存から積まれたものは
人が待っていて、全件ボタンから展開されたものは誰も待っていない。種類で決めると、一括処理から
展開されたジョブも高くなり、効かない。

| 優先度 | 積む側                     | 例                                                                                                                           |
| ------ | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 高     | API の個別操作             | リソースの作成・更新・アップロード・再処理、巻き戻し、主キーの変更、版の削除                                                 |
| 通常   | 上記以外（既定）           | データセットの公開・復元・リソースを含めた作成で配下に積む run、毎時の回収、まとめジョブ、索引消失の復旧ジョブ自体           |
| 低     | 誰も待っていない大量の処理 | 管理者が押した全件処理とそこから展開したもの、全リソースへの展開（索引消失の復旧から展開するものも）、ヘルスチェックの再取得 |

- **既定は「通常」。** 高と低は積む側が明示する。新しい積み場所で指定を忘れても害のない側に倒す
  （API のリクエスト全体を既定で高にすると、全件ボタンで低を忘れたときに一括処理が高で溢れる）。
- **ハンドラの中で積んだジョブは、そのジョブの優先度を受け継ぐ。** 明示しなければ、実行中の
  ジョブの優先度で積む（`AsyncLocalStorage`）。claim 待ち・取得レート制限の積み直し、層 2 の
  取り込み、抄録の連鎖、版の削除後の作り直しが、呼び出し元に手を入れずに元の位置を保つ。
  失敗して再試行を待つジョブは行を書き換えるだけなので、優先度はそのまま残る。
- **`unlessWaiting` で積むジョブは継承せず、指定がなければ「通常」。** 検索文書の同期と埋め込みの
  ような、積んだ人の分ではなく立っている未反映フラグ全部を処理するジョブである。一括処理から継承すると、
  編集者の未反映フラグを抱えたまま一括処理の後ろで待つ。個別操作から継承すると、カタログ全体の
  書き直し（埋め込みの再生成など）の続きが高のまま居座る。通常なら一括処理（低）より先に走るので、
  人の編集は待たされない。キューの側で決めるので、新しいまとめジョブが指定を忘れても同じになる。
- **`unlessWaiting` は、同じ種別・同じペイロードの待機中のジョブを、優先度を問わず代わりとみなし、
  低ければ依頼の優先度まで引き上げる。** 低いまま残すと一括処理の後ろで依頼した側を待たせ、代わりと
  みなさなければ同じ仕事が二度走る（管理画面から低で積んだ再構築の待機中に、索引消失の復旧が通常で
  積む、など）。ペイロードが違えば別の仕事なので代わりにしない（メタデータだけの再構築は、本文まで
  作り直す再構築の代わりにならない）。
- **全リソースへ展開する run は、どこから積まれても「低」。** 検索インデックスの再構築は、索引の
  消失を worker が見つけたときにも積まれる。その復旧ジョブ自体は通常で積み（データセット文書が早く戻る）、
  待機中のものがあれば積まない（1 分ごとの確認が、キューの混む間に何本も積まないように）。全リソースへ
  展開する処理（`PipelineService.enqueueAll`）が常に低で積む。
- 同じリソースの待機中の run はまとめない。`rebuildOnly` の違う run をまとめると「再取得し、
  派生物も必ず作り直す」という新しいモードになる。まとめなくても正しさは壊れず、低い run が
  後でもう一度走る費用だけで済む。
- **エージングは入れない。** 低は、高と通常が空のときにしか進まない。そこで、通常に置くものを
  人の操作の数で決まるもの（公開・復元の展開）と、件数に上限のあるもの（まとめジョブ、毎時の回収）に
  限る。ヘルスチェックの再取得は、5 分ごとに最大 200 件を積みうるので低に置く（通常に置くと、
  1 台で捌ききれない間は全件処理が一切進まない）。エージングは、全件処理の数時間のあいだ人の操作を
  先に通すという目的と両立しない（古くなった低が高を追い越す）。
- 管理画面は待機中のジョブを取り出される順（`priority`、`run_at`、`id`）に並べ、優先度を表示する。
- 打ち切りのジョブを管理画面から再投入しても、優先度は元のまま。元と同じ種類の仕事なので、
  元の位置に戻る。
- 列は PostgreSQL の enum（`job_priority`、宣言順が取り出しの順）。段を足すときは `ADD VALUE ... BEFORE`
  で差し込めば、既存の行の意味は変わらない。

優先度は取り出しの順だけを決める。1 台の worker は今も 1 件ずつ処理するので、処理中の長い
ジョブの後ろでは、高いジョブも待つ。1 台の中で複数のジョブを並行に処理することは別に扱う（残課題 8）。

## 影響

- 廃止: `SQSQueueAdapter`、`@aws-sdk/client-sqs`、ElasticMQ コンテナと
  `docker/elasticmq.conf`、CDK の `QueueConstruct`（キュー・DLQ）とキュー長スケーリング、
  環境変数 `SQS_*`
- `QueueAdapter` は `enqueue` / `process` / `stop` を保ち、`enqueue` にトランザクションを渡す
  引数を足す。コミット後に通知するための `transaction`、まとめて積む `enqueueMany`、管理画面用の
  `countJobs` / `listJobs` / `retryDead` / `deleteDead`、保持期間の `pruneDead` を加える。
  `getStats`（SQS のキュー長）は廃止し、管理画面は `job` 表を直接数える（開いたときだけなので
  DB を起こしてよい）
- ADR-005 の 4 アダプターは 3 つになる（キューは環境差ではなくなる）
- Docker Compose 利用者には環境変数と構成の変更が伴う。リリースノートに移行手順を載せる
- ADR-002 は置換済み、ADR-022 と ADR-044 選択肢 C には本 ADR への参照を補う

## 移行

1 リリースで SQS / ElasticMQ ごと撤去する。キューに残ったメッセージは引き継がない。

- 適用前に、管理画面「ジョブ管理」でキューの待機・処理中が 0 であることを確認してもらう
  （リリースノートに載せる）。確認を前提にすれば、SQS の残りを読むための併存期間は要らない
- ローリングデプロイ中は、古い web がまだ SQS に投入し、新しい worker はもう読まない。
  この数分間に積まれたジョブは失われる。パイプラインは管理画面で `queued` のまま残る行を
  再処理すれば戻る。lake への取り込みと検索文書の同期は、毎時の定期再投入が拾う。
  埋め込みは検索管理の再処理で戻る。版の削除は claim 済みのままジョブが無い状態になるが、
  毎時の処理が積み直す（§1）
- 実際には、古い web の投入の多くは失われる前にエラーになる。AWS では IAM ポリシーの更新が
  ECS サービスの入れ替えより先に済むので、古いタスクは SQS への送信を拒否される。Compose でも
  ElasticMQ がもう無い。その数分間はアップロードの完了などが失敗し得るので、利用の少ない時間に
  適用する（リリースノートに載せる）。SQS の権限とキューを 1 リリース残せば防げるが、そのリリースを
  飛ばしてアップグレードする環境には効かないので、採らない

## 残課題

1. ~~`enqueue` をトランザクションに入れる呼び出し元の洗い出し~~ → パイプライン投入
   （`queued` への更新）、版の削除の claim、lake 取り込みのリース、削除後の再構築は同じ
   トランザクションで積む。組織の削除は claim をジョブ自身が取るので、同じトランザクションに
   入れる更新がない
2. 同一内容のジョブの重複排除。embed の 60 秒 debounce（package 単位の claim）は現状の仕組みで
   足りるか、`job` 表に一意キーを持たせるか
3. ~~`dead` の行の保持期間と、管理画面からの再投入~~ → 管理画面「バックグラウンド処理状況」で状態ごとに一覧し、
   打ち切りのジョブは試行回数を戻して再投入するか削除できる。30 日間動きのないものは毎時の処理で消す
4. ~~Service Connect をマルチサイトでサイトごとにどう名前空間を切るか~~ → §3（Cloud Map DNS、
   名前空間は環境に 1 つ、サイトはサービス名で分ける）
5. ~~待ち行数メトリクスの具体形と、スケールアウトの閾値~~ → §4（閾値は引き継ぐ）
6. 小規模構成（Docker Compose、small）向けに、worker を web の子プロセスとして同居させる
   配置を選べるようにするか。通知がプロセス内の呼び出しになり §3 の経路が不要になる一方、
   メモリの干渉（同じ cgroup）、web と worker の台数の結合、デプロイのたびの処理打ち切り、
   web イメージへのネイティブ依存の流入を伴うため、分離配置を既定とする。
   根は負荷の性質の違いにある。worker は資源を使い切ってキューが積み上がっても、
   遅れるだけで時間が解決する。web は応答が遅れること自体が障害である。
   同居させると、worker が飽和したときの遅れを web が被る
7. Aurora の auto-pause が、プールのアイドル接続を閉じたあと実際に 0 ACU に下がることの実測
   （worker の health check cron の既定 5 分間隔が、既に pause を妨げている可能性がある）
8. 1 台の worker の中で K 本のジョブを並行に処理するか。正しさは複数タスク構成と同じ前提
   （`SKIP LOCKED`、リソースの claim、まとめジョブの advisory lock）で既に成り立つ。メモリを食う
   DuckDB の区間（Interpret、層 2 の取り込み）だけをプロセス内で 1 本に絞る。並行にすると、
   1 台が落ちたときに巻き込まれるジョブが K 倍になる
