# ADR-032: MCP データクエリ基盤（スキーマ永続化 + サーバーサイド DuckDB クエリ）

## ステータス

**承認（Accepted）** — Part A（スキーマ永続化）、Part B（サーバーサイド DuckDB クエリ）ともに実装済み。
クエリ実行プロセスの配置は、計測を経て子プロセス（選択肢 C）に改めた（残課題 2）。

ADR-029「CSV/TSV プレビュー Parquet の列型自動推定」で得られる列スキーマを永続化し、
ADR-016「DuckDB-WASM データエクスプローラー」のクエリ機能をサーバーサイドに展開して
MCP（Model Context Protocol）から利用可能にする設計。

## コンテキスト

KUKAN には既に MCP サーバー（`packages/api/src/mcp/`、HTTP Streamable / ステートレス）があり、
`search_datasets` → `get_dataset` → `get_resource` という**カタログ探索**のツール群を公開している。
しかしツールはいずれも**メタデータ取得で止まっており、データ本体に対する操作ができない**。
AI エージェントから見ると「目次は読めるが本文が読めない図書館」の状態にある。

具体的なギャップは 2 つ:

1. **フィールド（列）が不可視**: リソースの列名・型は、利用者が Parquet をダウンロードして
   初めて分かる。実際には Extract ステップで型推論（ADR-029 `inferColumnType()`）が走り、
   列名・推論型がその瞬間に確定しているにもかかわらず、**結果を永続化せず捨てている**。
2. **サーバーサイドクエリができない**: SQL クエリは現状ブラウザ上の DuckDB-WASM
   （`apps/web/src/hooks/use-duckdb.ts` / `duckdb-sql.ts`）でしか実行できない。
   API・MCP からデータに対して集計・絞り込みをかける手段がない。

この 2 つを埋めると、

```
search_datasets → get_dataset → get_resource_schema → query_resource
```

という**閉じたエージェントループ**が成立し、KUKAN は「AI が自律的に探索・集計できるデータ基盤」へ
質的に変わる。CKAN の DataStore + datastore_search_sql に相当する機能を、
専用テーブル投入ではなく**既存の Parquet プレビューを直接クエリする**形で実現する。

## 検討した選択肢

### スキーマ可視化

- **A) 都度 Parquet フッタから抽出**: クエリ/表示のたびにストレージから Parquet フッタを
  Range 読みして列情報を得る。永続データ不要だが I/O が都度発生し、検索インデックスにも載せられない。
- **B) パイプライン時に永続化（採用）**: Extract で既に確定している列名・推論型を
  `resource_pipeline.metadata` に書き込む。追加コストはほぼゼロで、MCP・UI・将来の列名検索すべてに効く。

### サーバーサイドクエリの実行基盤

- **A) サーバーサイド DuckDB（採用）**: ネイティブ DuckDB で Parquet を直接クエリ。
  フロントの DuckDB-WASM とロジックを共有でき、列指向 Parquet の利点（projection/predicate pushdown）を活かせる。
- **B) PostgreSQL DataStore 方式（CKAN 型）**: リソースごとに Postgres テーブルを作って投入。
  スキーマ可変・大量リソースで重く、「アダプターを増やさない」設計思想（ADR-005）に反する。
- **C) クエリ非対応のまま**: ギャップが残る。却下。

### クエリインターフェース

- **A) 生 SQL（SELECT 限定・サンドボックス）（採用）**: AI は SQL に習熟しており最も柔軟・強力。
  集計・GROUP BY・式を自由に書ける。安全性は実行環境のサンドボックス化で担保する。
- **B) 構造化クエリ（filters/sort/aggregate）**: `duckdb-sql.ts` のロジックを共有しサーバーで SQL に
  コンパイル。攻撃面は小さいが表現力が限定的で、AI の強みを活かせない。

### クエリ実行プロセスの配置

- **A) API（web）プロセス内（当初採用 → C に改訂）**: 実装が単純で、既存の storage アダプタ・認証・可視性チェックを
  そのまま使える。ネイティブアドオン依存とメモリ負荷を web に載せるトレードオフはあるが、
  プレビュー対象は ≤50MB に制限済み（ADR-029）で同時実行を絞れば許容範囲。
- **B) 専用クエリサービス / Worker 側**: 重いクエリを web から隔離できるがコンポーネントと
  デプロイ経路が増える。将来スケールが必要になった時点で切り出す（残課題）。
- **C) web と同じコンテナの子プロセス（採用・改訂）**: リソースクエリだけをクエリごとの子プロセスで
  実行する。コンテナの上限に達したとき落ちるのがクエリ 1 本で済み、web は巻き添えにならない。
  経緯と計測は残課題 2。

## 決定

**2 つの協調した変更を行う。**

### Part A — 列スキーマの永続化

1. Interpret ステップ（`apps/worker/src/pipeline/steps/interpret.ts`）で Parquet を生成する際、
   各列の `{ name, type, nullable, nullCount, stats? }` と `rowCount` を**スキーマとして組み立て**、
   `resource_pipeline.metadata.schema` に保存する。`type` は列の推論型をそのまま用いる
   （`integer` / `float` / `boolean` / `string`。ADR-046 が解釈を DuckDB へ移した際に
   `date` / `timestamp` が加わった）。
   `stats` は数値列（`integer` / `float`）の min/max（非 null 値が 1 つ以上ある場合のみ）で、
   セル変換と同一パスで（追加スキャンなしに）算出する。整数の min/max は INT64 が JS Number の安全域を超えうるため
   **十進文字列**、float は数値で保存する。distinct・合計・平均等は Parquet 統計の対象外のため
   Part B のクエリに委ねる。
2. 対象は **Parquet を生成するフォーマットのみ**（CSV/TSV・≤50MB）。それ以外（PDF・画像・
   大容量 CSV 等）は `schema` を持たない（`null`）。
3. 公開経路:
   - API: `GET /api/v1/resources/{id}/schema` — 可視性チェック後、保存済みスキーマを返す。
     スキーマ未生成（非対応フォーマット / 未処理）は 404 ではなく `queryable: false` を含む明示的レスポンス。
     `queryable` はクエリ実行可否（プレビュー Parquet 実体 + 非空スキーマ + 現在の内容を記述
     〔sourceHash 一致〕）と一致し、スキーマの有無とは独立 — プレビュー削除済み・列ゼロの
     スキーマ・内容差し替え後の残存プレビューでは `schema` を返しつつ `false` になる。
   - MCP: `get_resource_schema` ツール — 列名・型・行数をテキストで返す。クエリ可能な場合のみ
     「`data` という名前のテーブルをクエリする」旨とクエリ例を含める（不可の場合は列一覧のみ）。
4. **後方互換**: 既存リソースは再処理（`reprocess`）で順次スキーマが付与される。一括バックフィルは行わない
   （ADR-029 §7 と同じ方針）。

### Part B — サーバーサイド DuckDB クエリ

1. **ライブラリ**: `@duckdb/node-api`（公式ネイティブバインディング）を API プロセスに追加。
2. **公開経路**:
   - API: `POST /api/v1/resources/{id}/query`（body: `{ sql: string }`）
   - MCP: `query_resource(id, sql)` ツール（`readOnlyHint: true`）
3. ~~**Parquet の取り込み**: storage アダプタでプレビュー Parquet（`preview_key`）を取得し、
   一時ファイルへ書き出す。~~
   **DuckDB がオブジェクトストレージから直接読む（実装で変更）。** バイトの出どころは
   どちらも同じバケットで、取得を SDK にやらせると最大 100MB をコンテナのディスクへ書いて
   読み直す往復が増えるだけだった。**残課題 §4 の一時ファイルキャッシュは、キャッシュする
   相手を失った。**

   > **利用者 SQL を実行するインスタンスに `aws` 拡張を積んではならない。**
   > タスクロール構成で `s3://` を読むには secret が `PROVIDER credential_chain` になり、
   > それを支える `aws` 拡張が要る。この拡張が登録する `load_aws_credentials()` は
   > **ファイルシステム経由の呼び出しではない**ので、下の 4-2 のロックダウンが一切届かず
   > （`enable_external_access` も `lock_configuration` も効かない）、4-3 の SQL 検証も
   > すり抜ける（`\bload\b` は `load_aws_credentials` に一致しない）。実測で、閉じ込めた
   > あとの 1 文がタスクロールのキー ID とセッショントークンを平文で返した。この経路は
   > 公開データセットなら無認証である。
   >
   > **したがって読みは `aws` を要求しない形で行う。** Step 1 は**署名付き URL**
   > （`getSignedUrl`、60 秒）を `read_parquet` に渡し、`httpfs` だけを積む。URL 自身が
   > 認可を運ぶので、インスタンスに資格情報が 1 つも置かれない。
   >
   > **代替として `s3://` + 一時資格情報の直接指定も成立する**（実測: `KEY_ID` / `SECRET` /
   > `SESSION_TOKEN` を渡す secret は `httpfs` だけで作れて読める。`aws` が要るのは
   > `credential_chain` のときだけ）。**署名する主体が Node から DuckDB へ移る**ので、
   > 署名付き URL が乗っている回復動作 — SigV4 はメソッドを署名対象に含めるため GET 用
   > URL への HEAD は 403 になり、DuckDB は `bytes=0-1` のレンジ GET で取り直す — への
   > 依存が無くなる。
   >
   > **それでも署名付き URL を採る。渡すものの大きさが違うからである。** 署名付き URL は
   > 1 オブジェクト・1 メソッド・60 秒の引換券だが、一時資格情報は**バケット全体に署名
   > できる鍵**（タスクロールは `grantReadWrite`）である。どちらも利用者 SQL の前に閉じる
   > ので到達可能性は同じだが、**利用者 SQL を走らせるインスタンスに渡す権限は小さいほど
   > よい**というのが、上の `aws` の一件から得た教訓そのものである。
   >
   > なお一時資格情報を使うなら**使い捨てのインスタンスに限る** — 失効しても DuckDB 側から
   > 更新できないので、プロセス常駐のインスタンス（ADR-043 の lake）では
   > `credential_chain` + `REFRESH auto` が要る。

4. **サンドボックス（本 ADR の核心）**: クエリごとに**使い捨ての DuckDB インスタンス**を作り、
   次の順序で完全に隔離する。
   1. 外部アクセスが有効な状態で、Parquet を**インメモリテーブル `data` に実体化**する
      （`CREATE TABLE data AS SELECT * FROM read_parquet('<tmp>')`）。これ以降ファイルには一切触れない。
   2. 設定をロックダウンする:
      - `SET enable_external_access = false`（ファイル/URL/httpfs/COPY を全面禁止）
      - `SET autoinstall_known_extensions = false; SET autoload_known_extensions = false;`（拡張の取得禁止）
      - `SET memory_limit = '<上限>'; SET threads = <上限>;`（リソース制限）
      - `SET lock_configuration = true;`（以降ユーザー SQL から `SET` で戻せないようにする）
   3. **ユーザー SQL を検証**する（多層防御）:
      - 文を 1 つだけ許可（末尾以外の `;` を禁止）。
      - 先頭キーワードが `SELECT` または `WITH` のもののみ許可。`PRAGMA` / `ATTACH` / `COPY` /
        `INSTALL` / `LOAD` / `SET` / `CALL` / `EXPORT` / `INSERT` / `UPDATE` / `DELETE` / `CREATE` /
        `DROP` 等は拒否。
      - 先頭が `WITH` でも CTE が書き込み文を包む（`WITH x AS (...) DELETE ...`）ケースを防ぐため、
        文レベルの書き込み/DDL キーワードを拒否する（コメント・文字列を除去した上で判定。`replace` は
        SELECT 関数のため除外）。
      - ※ ②のロックダウンにより、検証をすり抜けてもファイルアクセス・DDL/DML・拡張ロードは
        実行できない。検証は防御の一層であって唯一の砦ではない。
   4. **行数・時間の上限**:
      - 結果ストリームを読みながら**最大行数で打ち切る**（クエリ形状に依存しない確実な上限）。
        併せて結果バイト数の上限も設ける。
      - **ウォールクロックのタイムアウト**で接続を `interrupt()` する（DuckDB に SQL レベルの
        statement_timeout がないため、タイムアウトで明示キャンセルする）。タイマーは materialize も
        覆い、巨大/異常な Parquet が接続とセマフォを占有し続けるのを防ぐ。超過は `408`
        （`RequestTimeoutError`）。
   5. クエリ終了後はインスタンスを破棄する。
5. **同時実行とメモリ**: セマフォで同時クエリ数を制限する。1 クエリの `memory_limit` と同時実行数で
   DuckDB のメモリピーク（≈ `memory_limit × 同時実行数`）を境界づける。超過分は `429`
   （`TooManyRequestsError`）を返す（キューイングしない）。**v1 既定は保守的に
   `memory_limit = 256MB` × 同時実行 1**（ピーク約 256MB）で web コンテナ（small=512MB）の OOM を
   避ける。デプロイ scale 連動は残課題。

   **改訂（実測による）: `memory_limit` は 256MB のまま、1 枠の予算は 498MB（上限から算出）。**
   「ピーク ≈ `memory_limit`」は成り立たなかった。1 クエリが増やすプロセスの RSS を、8 万〜128 万行の表に
   ついて読み込み・DISTINCT・全列ソートで測ると、最悪値は **1.3 × `memory_limit` + 165MB** 以下に並んだ
   （128MB → 328MB、192MB → 408MB、256MB → 494MB）。上限の外にあるのは DuckDB 自身の作業用割り当て・
   Parquet の読み込みバッファ・ライブラリ本体である。上限を超える表は一時ディスクへ書き出され、それでも
   収まらない演算子は RSS を増やさずに DuckDB の Out of Memory で失敗する — 上限の内側で失敗する処理は
   拒否であって、コンテナを危うくしない。

   上限は下げなかった。リソースへのクエリだけなら 128MB でもカタログにある規模の表（元 CSV 55MB で測定）
   は通るが、同じ上限を使う版の差分（ADR-043）は、全行を書き換えた 8 万行の表の主キー付き差分が 128MB で
   失敗し、256MB では 32 万行まで通った。OData フィード（ADR-055）のスロット数は、この 1 枠の予算を
   差し引いて決める。予算は上の式の値で、`QUERY_SLOT_RSS_MB` として上限から自動で算出する（差分の実測
   最悪値 486MB もこの線の下）。待ち行列は 16 に深くした — 待ち時間のほうは、クエリ自身のタイムアウトと
   合わせて CloudFront のオリジン応答タイムアウト（30 秒）に達するため延ばせない。

6. **アクセス制御**: プレビュー（ADR-017）と同じ `getByIdWithAccessCheck` を通す。SQL 検証
   （長さ＋read-only）はダウンロード/materialize の**前**に実行し、MCP 経路でも長さ制限を担保する。
7. **クエリ対象の明示**: AI は固定テーブル名 `data` をクエリする。テーブル名・列・型は
   `get_resource_schema` の出力と `query_resource` の説明文に明記し、エージェントが
   スキーマを見てから SQL を書けるようにする。
8. **結果フォーマット**: API は JSON（`{ columns, rows, rowCount, truncated, elapsedMs }`、`rows` は
   列名キーのオブジェクト配列）、MCP `query_resource` は Markdown テーブルを返す。値は JSON 安全な
   形に直列化する（BIGINT 等は文字列）。

## 影響

- **DB**: スキーマ変更なし（`resource_pipeline.metadata` JSONB を拡張するのみ）。
  `metadata.schema` の型を `packages/shared` の Zod スキーマとして定義する。
- **Worker**: `extract.ts` がスキーマを組み立てて返し、`process-resource.ts` が
  `resource_pipeline.metadata` に保存する。型推論はすでに走っているため計算追加はほぼゼロ。
- **API**: `packages/api` に `@duckdb/node-api` 依存と、クエリ実行サービス
  （サンドボックス・セマフォ・タイムアウト）を追加。`RequestTimeoutError`(408) /
  `TooManyRequestsError`(429) を `@kukan/shared` に追加。`/schema`・`/query` ルートと
  MCP ツール 2 種を追加。
- **デプロイ**: `@duckdb/node-api` はネイティブアドオン（in-process。サイドカーではない）。
  `next.config` の `serverExternalPackages` に加えることで Next.js standalone のトレースに `.node` が
  含まれ、**alpine の musl バインディングが解決されるため Docker のベースイメージ変更は不要**
  （`node:24-alpine` で動作確認済み）。メモリ上限はクエリサンドボックス（`memory_limit`）と
  ECS タスク定義の両方で設定する。
  **リソースクエリの子プロセス（残課題 2）は、単独で動く 1 ファイルとして別にビルドする**
  （`query-child.mjs`、esbuild。外部に残る import は `@duckdb/node-api` だけ）。Next は
  `@kukan/api` をソースから束ねるため、子のファイルは standalone 出力に入らず、`import.meta.url`
  から隣のファイルを辿ることもできない（ビルド時に解決を試みて失敗する）。イメージはこのファイルを
  `@duckdb/node-api` が解決できる `.pnpm` 配下に置き、`QUERY_CHILD_ENTRY` でその場所を渡す。
- **セキュリティ**: 生 SQL を外部（AI）に開く口であり、サンドボックスの各設定（特に
  `enable_external_access=false` + `lock_configuration=true`）は必須。レビュー時の重点項目。
- **可観測性**: クエリ SQL・実行時間・打ち切り（行数/時間）をログに出す（ADR-019）。
- **テスト**:
  - SQL 検証関数のユニットテスト（複数文・非 SELECT・コメント偽装・大文字小文字）。
  - サンドボックスの統合テスト（`read_parquet`/`COPY`/`ATTACH`/`INSTALL` が確実に失敗すること、
    行数・タイムアウト上限が効くこと）。
  - スキーマ永続化のパイプライン統合テスト。

## 残課題（未解決事項）

1. **クエリ可能対象の拡大**: 現状 ≤100MB の CSV/TSV のみ。大容量ファイルや JSON 等への拡大
   （上限引き上げ、または raw ファイルへの DuckDB httpfs 直クエリ）。
2. ~~**クエリサービスの切り出し**~~（解決: 子プロセス、選択肢 C）: 負荷増大時に web プロセスから専用サービス / Worker へ分離（選択肢 B）。

   **解決（子プロセスを採用。リソースクエリの経路のみ）。** 選択肢 C として実装し、small 相当
   （512MB / 0.25 vCPU、Docker Compose）で最悪のクエリを流して計測した。以下はその結果と、
   採用に至った検討である。

   **計測（元 CSV 55MB 相当、8 万行 × 42 列の表。変更前 = プロセス内）**

   | 項目                               | 変更前                                         | 子プロセス                     |
   | ---------------------------------- | ---------------------------------------------- | ------------------------------ |
   | 全列ソートを 2 回続けて実行        | **2 回目でコンテナが OOM で終了**（exit 137）  | 2 回とも完了、コンテナは継続   |
   | クエリ後に残る匿名メモリ           | 480〜525MB（プロセスが返さない）               | 約 120MB（子の終了で全部返る） |
   | ピーク（1GB 上限で測定）           | 541〜547MiB                                    | 547〜553MiB                    |
   | 全列ソート単独                     | 5.7 秒                                         | 6.4〜6.7 秒                    |
   | 全列ソート（ページ取得を並行）     | 7.9 秒                                         | 12.1 秒                        |
   | クエリ中のページ応答（`/dataset`） | 中央値 0.19 秒、結果の直列化で 1 回 2.7 秒停止 | 中央値 0.19 秒、最大 0.69 秒   |
   | 子の起動（Node + DuckDB + httpfs） | —                                              | 約 1.0 秒、RSS 105〜114MB      |
   - **決め手は「クエリ後に残るメモリ」だった。** プロセス内の DuckDB が確保したメモリは
     クエリが終わっても web のプロセスに残り、次の重いクエリ（またはページの負荷）でコンテナの
     上限を越える。1 本目では落ちず 2 本目で落ちるので、原因のクエリと落ちたときのクエリが一致しない。
     子プロセスは終了と同時にすべて返す。ピークはほぼ変わらない（+6MB）。
   - **`nice` の効果は測れなかった。** 子は `nice 10` で動くが、SSR のページを 6 本並列で流しながら
     nice 0 / 5 / 10 / 19 を比べると、クエリ中のページ応答（p50 1.10〜1.20 秒、p95 1.81〜1.90 秒）も
     集計クエリの所要時間（4.6〜5.8 秒）も差が誤差の範囲だった。タスクの CPU の割り当て（cgroup の
     quota）が先に効き、その中の配分の差が表に出ない。19 でもタイムアウトは増えなかったので、
     Fargate で効き方が違った場合の保険として 10 を残す。上の表でソートが並行時に延びるのは子の
     起動と CPU の取り合いによるもので、`nice` のせいではない（nice 0 でも 11〜13 秒）。
   - **ページの負荷が高いとき、制約になるのは CPU よりメモリである。** SSR を 6 本さばく間は web
     自身のメモリも増えるので、全列ソートは nice の値によらず予備の手前で止められた（web は落ちない）。
   - **1 クエリあたり 0.6〜1.0 秒遅くなる**（0.25 vCPU での子の起動分）。事前に起動しておく案は
     **採らない**。small で約 110MB を常に持つことになり、それはクエリ 1 本の予算の大半にあたる。
     要るならスケール別に後で足す。
   - **止める判定はコンテナの匿名メモリで行う。** 親は 100ms ごとに cgroup の `memory.stat`
     （`anon`）を読み、上限まで 32MB を切ったら子を `SIGKILL` する。ページキャッシュ（スピル
     ファイルを含む）は OOM killer の前に回収されるので数えない。**子の RSS で判定したら誤った**:
     共有ライブラリのページが web と子で二重に数えられ、512MB では変更前に通っていたソートを
     約 300MB で拒否した。予備を 64MB にしてもソートを拒否し、32MB ではソートが通って DISTINCT は
     拒否された（カーネルの OOM は 0 回）。上限のない環境（上限を設けない Compose）では、子の RSS が
     1 クエリの予算（`QUERY_SLOT_RSS_MB` + 子の基礎分 115MB）を越えたときだけ止める。
   - **カーネルが選ぶのは子である（Docker で確認）。** `oom_score_adj = 1000` の子にメモリを取り
     続けさせると、殺されたのは子だけで（`oom_kill 1`、`oom_group_kill 0`、`memory.oom.group = 0`）、
     web は応答し続けた。Docker はコンテナに `OOMKilled` の印を付けるが、コンテナは止まらない。
     **Fargate（containerd）で `memory.oom.group` が 0 であることは未確認**で、1 ならコンテナごと
     殺される。その場合も親の判定が先に止めるが、確認するまでは親の判定が唯一の防御と考える。
   - **利用者に返すもの。** 親が止めた場合、カーネルが子を殺した場合とも 400（「このサーバーで
     使えるメモリを超えた」、`WHERE` / `LIMIT` / 集計を促す）。タイムアウトは従来どおり子が自分で
     中断して 408、それが届かない場合（ブロックした HTTP 読み取りなど）は親が期限 + 2 秒で止めて 408。
     呼び出し元の切断は即座に `SIGKILL`。
   - **子の環境は許可リスト。** `PATH` / `HOME` / `LD_LIBRARY_PATH` / `DUCKDB_EXTENSION_DIRECTORY`
     等だけを渡し、DB のパスワード・認証の secret・ECS のタスクロール資格情報の取得パスは渡さない。
     読みは署名付き URL（Part B-3）なので、子に資格情報は要らない。`TMPDIR` は親が作った
     ディレクトリを指し、殺された子のスピルファイルも親が消す。
   - **版の差分（ADR-043）はプロセス内に残した。** カタログへの接続を子に渡すことになり、利用者の
     SQL を実行しない（差分は KUKAN が組み立てる SQL だけ）ので、失敗の単位を縮める必要がリソース
     クエリほど高くない。同じ枠（セマフォ）は引き続き共有する。

   以下は採用前の検討（計測前に書いたもの）。

   **検討: 分離の狙いはメモリの節約ではなく、失敗の閉じ込めである。**
   DuckDB はネイティブアドオンとして Node と同じプロセスで動く。インスタンスは使い捨てでも
   プロセスは共有なので、クエリがコンテナの上限に達すると OOM killer が殺すのは web の
   Node プロセス全体で、公開ページも API も巻き添えになる。small（512MB）では、1 枠の予算
   （Part B-5 の 498MB）がそもそも収まらないため、最悪のクエリ 1 本でこれが起きうる。
   分離しても必要なメモリは減らない（子プロセスなら Node 本体の分だけ増える）が、失敗の
   単位をクエリ 1 本に縮められる。

   | 方式                                                                            | 失敗の閉じ込め                                   | メモリ上限                            | 環境を問わない                      | 代償                                                          |
   | ------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------- | ----------------------------------- | ------------------------------------------------------------- |
   | 子プロセス                                                                      | OOM 時に子が選ばれる（`oom_score_adj` を上げる） | 近似（親が RSS を監視して `SIGKILL`） | ○                                   | 起動のたびに Node 本体分のメモリと時間                        |
   | サイドカーコンテナ（ECS のコンテナ単位ハードリミット / Compose の `mem_limit`） | ○                                                | 厳密（cgroup）                        | ○                                   | 常時確保するメモリ。呼び出し口とデプロイするものが 1 つ増える |
   | Lambda                                                                          | ○                                                | 厳密（関数のメモリ設定）              | ×（AWS のみ。ADR-005 の例外になる） | コールドスタート。同期呼び出しは途中で止められない            |
   - **子プロセスには厳密な上限を掛けられない。** cgroup の委譲はコンテナ内では特権を要し、
     `RLIMIT_AS` は V8 と DuckDB のアロケータが先に確保する仮想領域のため実用にならず、
     `RLIMIT_RSS` は Linux では無視される。
   - **CPU は分離しても増えない。** Fargate の vCPU はタスクの cgroup 全体に掛かる quota なので、
     クエリのスレッドが枠を使い切れば web ごと止まる（small は 0.25 vCPU に `threads = 2`）。
     子プロセスなら `nice` で web を優先させられるが、枠そのものは変わらない。
   - **子プロセスは、実体化を省く案の前提にもなる。** Part B-4 の実体化だけで RSS が
     150〜230MB 増える（元 CSV 55MB の表で測定）。Parquet を直接クエリすれば省けるが、利用者
     SQL の実行中もストレージへの経路が開いたままになる。子プロセスの環境から資格情報を外し、
     署名付き URL だけを渡せば、利用者 SQL から届くのはそのオブジェクトだけになる。
   - **対象はクエリ経路に限る。** OData のフィード（ADR-055）はページが軽く（1 ページ 55〜65MB）、
     インスタンスの使い回しで速さを得ているので、プロセス内に残す。版の差分（ADR-043）は
     同じ枠を使うが、カタログへの接続を持つため子プロセスに渡すものが増える。含めるかは実装時に決める。
   - **検討時の見立ては子プロセス。** 「たいていの場合に web を巻き添えにしない」で足りるなら
     子プロセス、「web に一定のメモリを必ず残す」保証が要るならサイドカー。上の計測を経て子プロセスを
     採った。サイドカーは、Fargate で子だけを殺せないと分かった場合の次の手になる。

3. **クロスリソース JOIN**: 複数 Parquet を 1 クエリで結合する（複数テーブル登録）。需要を見て検討。
4. ~~**一時ファイル/インスタンスのキャッシュ**~~（半分解決）: **キャッシュすべき一時ファイルが無くなった** —
   読みはオブジェクトストレージへ直接行く（Part B-3）。残っているのはロック済み DuckDB 接続を
   リソース単位でキャッシュする話で、こちらは同時実行管理が複雑化するため引き続き後続。
5. ~~**結果フォーマット**~~（解決済み）: API=JSON、MCP=Markdown テーブルに決定（Part B-8）。CSV 等の
   追加形式は需要を見て検討。
6. **デプロイ scale 連動の上限**: `memory_limit` × 同時実行数を deployment scale（small/medium/large）に
   応じて env 注入し、medium 以上で同時実行を増やす（v1 は保守的な定数）。
7. **レート制限・課金**: AI からの高頻度・高コストクエリに対するレート制限とコスト可視化。
