# ADR-045: ストレージオブジェクトの先行記録

## ステータス

**提案（Proposed）**

オブジェクトを作る前にその鍵を台帳へ記録し、参照が確定したら消す。異常終了で残った
記録をスイープが回収する。削除は「どのポインタからも参照されていない」ことを確認してから
行い、参照されていた場合は記録の方を消す。回収可能になる時刻は書き手が宣言する。

## コンテキスト

オブジェクトを**作ってから**台帳に記録する順序になっている箇所が 7 つある。その窓で
プロセスが落ちると、**どこからも参照されず、回収経路も持たない**オブジェクトが残る。

| 書き込み                          | prefix       | 参照先                                   |
| --------------------------------- | ------------ | ---------------------------------------- |
| Fetch のダウンロード              | `resources/` | `resource.storage_key`                   |
| Interpret のプレビュー Parquet    | `previews/`  | `resource_pipeline.preview_key`          |
| Interpret の ZIP マニフェスト     | `previews/`  | `resource_pipeline.preview_key`          |
| Index のテキストヘッド（ADR-040） | `previews/`  | `resource_pipeline.metadata.textHeadKey` |
| Version の版コピー                | `versions/`  | `resource_version.storage_key`           |
| 移行（v1 付与）の版コピー         | `versions/`  | `resource_version.storage_key`           |
| 版パージのロールバック復元        | `resources/` | `resource.storage_key`                   |

いずれも「コピー／アップロードが成功し、DB 更新の前に落ちる」窓を持つ。現在のスイープは
`orphaned_object` に積まれた鍵しか消さず、この窓で生まれた鍵はそこに入らない。**永久に残る。**

影響は**ストレージのリークのみ**である。到達不能なオブジェクトが残るだけで、正しさには
影響しない。ただし放置すれば課金され、そして「消したはずの内容が残っている」状態でもある。

### 既にある 3 つの機構

新しく発明する前に、この問題の周辺に何があるかを確認した。**採用すべき形は既にこの
リポジトリの中にある。**

**先行記録（write-ahead）— ブラウザアップロードのみ**。`prepareForUpload` は
`resource.pending_storage_key` を**書いてから** `storage.upload` する。放置された鍵は
`expirePendingUploads` が TTL 経過後に回収する。**7 つのうち唯一この窓を持たない経路**が、
既にこの方式で守られている。

**事後の回収予約 — `orphaned_object`**。書き手が**置き換えた**鍵を積む台帳で、
`sweepOrphanedObjects` が保持期間経過後に drain する。積まれた時点で参照が外れていることが
構成上保証されているため、スイープは無条件に削除してよい。

**reconciliation — `lake/` のみ**。`ducklake_delete_orphaned_files` がカタログとファイル一覧を
突き合わせて未追跡ファイルを消す（ADR-043、24 時間の保持期間つき）。ただしこれは
**DuckDB の組み込み手続き**であって、我々が持っている機構ではない。カタログとファイル配置の
両方を知っている DuckLake だからこそ成立している。

## 検討した選択肢

### A) 先行記録（write-ahead）

アップロードの前に鍵を台帳へ入れ、ポインタが確定したら消す。作りっぱなしの記録が残っていれば
スイープが回収する。

- **利点**: 既存の台帳・スイープ・保持期間をそのまま使える。判定が「**この書き込みは完了したか**」
  という局所的な問いに閉じる。実行パスのコストは INSERT 1 回（消す側は、ポインタを動かす既存の
  文へ相乗りできる — それらは既に `orphaned_object` に INSERT している）
- **欠点**: **失敗の向きが逆転する。** 記録を消し損ねると、スイープが**生きているオブジェクトを
  消す**。リーク（無害）がデータ喪失（深刻）に化ける

### B) ストレージ一覧との定期 reconciliation

prefix 配下を列挙し、どのポインタからも参照されないオブジェクトを回収する。

- **利点**: 実行パスのコストがゼロ。取りこぼしが原理的に無い（一覧が真実）
- **欠点**: 参照元が複数に散っている（`resource.storage_key` /
  `resource.pending_storage_key` / `resource_version.storage_key` /
  `resource_pipeline.preview_key` / `metadata.textHeadKey`）。**将来ポインタ列が 1 つ増えたとき、
  reconciler の更新を忘れるとその参照先が消される。** 網羅性が恒久的な前提になり、
  破れたときの被害はデータ喪失
- 加えて、大規模なバケットでは列挙自体のコストがかかる

### C) 何もしない

リークは正しさに影響しない。ただし ADR-044 で「完全削除を謳った直後に内容が残る」窓を
塞いだばかりであり、**同じ性質の残留を別の原因で許容する**のは筋が通らない。

## 決定

**A を採る。ただし B の確認を削除の直前に置く。**

両案の危険は同じ形をしている — **消す側が「何が参照されているか」を正しく知っている必要がある。**
違いは問いの立て方で、A は「この書き込みは完了したか」に絞り、B は「このオブジェクトは何からも
参照されていないか」という全体不変条件を毎回問う。前者の方が壊しにくい。

そして A の唯一の欠点（記録の消し忘れが致命傷になる）は、**削除の直前に B の問いを一度だけ
挟めば消える**。候補の生成は先行記録が担い（安価・正確・一覧不要）、削除の可否はポインタ照合が
決める（安全）。B を全件スキャンとして走らせるのではなく、**候補に対する述語として使う**。

### 1. 記録の場所

`orphaned_object` をそのまま使う。新しいテーブルは作らない。

積まれる鍵の意味が 2 種類になる（「置き換えられた」と「これから作る」）が、**スイープにとっては
どちらも同じ問い**に還元される — 今このオブジェクトを参照しているポインタはあるか。

### 2. 回収可能になる時刻は、書き手が宣言する

`orphaned_at` と単一の保持期間で判定するのをやめ、**`expires_at` 列を足す**。

同居する 2 種類は、猶予を置く理由が違う。回収予約は「既に解決済みの読み手が読み終わるまで」
（読み手のドレイン）、先行記録は「その書き込みが完了しうる最長時間」（放棄の判定）である。
今はどちらも 1 時間で足りるが、それは値が偶然一致しているだけで、**片方を片方の理由で
調整すると、もう片方まで動く。**

ADR-044 が `CLAIM_STALE_AFTER_MS` を全 claimer で 1 つに揃えたのは、問い**が同じ**だった
ためである。ここは問いが違うので、逆に分ける。列 1 つで足り、スイープは
`expires_at < NOW()` に一様化される。

### 3. スイープの述語

期限を過ぎた鍵について、削除の前に参照元を照合する。5 つある
（ADR-046 が `resource_version.lake_source_key` を撤去した後の数）。

**参照されていれば、消すのはオブジェクトではなく記録の方。** 参照されているということは
その書き込みが完了したということであり、記録が残っているのは消し忘れだからである。記録を
残して次回に持ち越すと、毎時間ずっと再判定され続ける。**この一手が、先行記録の唯一の
危険（消し忘れが生きたオブジェクトの削除に化ける）を自己修復に変える。**

回収予約で積まれた鍵は通常どれにも参照されていないため、この述語はほぼ挙動を変えない
— **先行記録の鍵にとってだけ意味を持つ。**

> **かつて例外が 1 つあった（ADR-046 §4 で解消）。** `resource_version.lake_source_key`
> （ADR-043 §6-6）は**後で外れる**ことを前提とした参照だったため、外す文が同じ文で鍵を
> 回収予約し直す必要があった。さもないとポインタも記録も持たないオブジェクトが残る — この台帳が
> 防いでいるまさにその状態である。「外す」には「別の鍵で上書きする」も含まれた。
>
> 撤去した今、**5 つの参照元はいずれも「後で外れる」ことを前提としていない** — 参照がその
> オブジェクトより長生きする設計のものは無い。ただし**外す文と同じ文で回収予約する規則そのものは
> 使われている**：巻き戻しとパージが派生物（プレビュー・テキストヘッド）を捨てるとき、ポインタを
> 外して鍵を回収予約するのを 1 文で行い、そのあとで削除する（ADR-044 §4）。削除が失敗しても
> スイープが回収する。新しくその種の参照を足すなら、この規則がそのまま要る。

### 4. 記録を消す場所

ポインタを動かす文に相乗りさせる。それらの文は既に `orphaned_object` へ INSERT しており
（置き換えた鍵の回収予約）、同じ文に DELETE を足すだけで済む。**新しい往復は増えない。**

版定義の insert（パイプライン・移行）だけは現在 `orphaned_object` に触れていないため、
そこには DELETE を足す必要がある。

### 5. `lake/` は対象外

DuckLake の組み込み手続きが既に同じ役割を果たしている（ADR-043）。`lake/` の
ファイル配置とカタログを知っているのは DuckLake であり、こちらから同じことをする理由がない。
**prefix ごとに参照元を差し替える共通機構は作らない。**

## 置き換えないもの

**`pending_storage_key` は残る。**

一見すると本 ADR の先行記録と同じ機構に見える — 実際、ブラウザアップロードが 7 つの窓に
含まれないのはこの列のおかげである。しかしこの列は 4 つの仕事をしており、重なるのは
1 つ目だけである。

| 仕事                                                               | 本 ADR で代替できるか |
| ------------------------------------------------------------------ | --------------------- |
| 回収のための先行記録                                               | できる（重複）        |
| CAS — 「その鍵がまだ pending なら昇格」（ADR-044 §6）              | できない              |
| `pending_metadata`（filename / contentType / name / format）の運搬 | できない              |
| 2 リクエストにまたがるプロトコルの状態（発行した鍵の記憶）         | できない              |

`orphaned_object` が持つのは鍵と期限だけで、リソースとの関連もメタデータも CAS 意味論もない。

そして重なる 1 つ目にしても、猶予が違う。ブラウザアップロードの TTL は **24 時間**で、
遅いクライアントを切らないための値である（サーバ側の書き込みは分オーダーで終わる）。
§2 で `expires_at` を書き手に宣言させるのは、この種の違いを 1 つの定数に押し込めないためでもある。

## 影響

- **DB**: `orphaned_object` に `expires_at` を追加（マイグレーション 1 本。既存行は
  `orphaned_at + 1 時間` で埋める）。スイープの述語にポインタ照合が入るため、
  `metadata->>'textHeadKey'` に式インデックスが要る
- **Worker / API**: オブジェクトを作る 7 箇所に INSERT が 1 回ずつ増える。消す側は既存の文に
  相乗り（版定義の insert 2 箇所だけ新規）
- **運用**: リークが恒久的に残らなくなる。スイープのログに「参照されていたので記録を消した」
  件数が出るため、先行記録の消し忘れが起きていれば観測できる

**差し引き**: 実行パスに 1 往復増える代わりに、回収経路の無いオブジェクトが無くなる。
機構は増えない — 既にある台帳・スイープの上に、列 1 つで乗る。

## 残課題（未解決事項）

1. **既存のリーク**: この ADR は今後の書き込みを守るもので、**既に残っているオブジェクトは
   回収しない**。1 度限りの reconciliation（選択肢 B を手動で 1 回走らせる）が別途要る
2. **照合コストの実測**: 各参照元への照合を 1 バッチ 5000 件に対して行う。インデックスが
   効けば問題ない想定だが、実測していない
3. **`previews/` の 2 種類**: プレビュー Parquet とテキストヘッドは同じ prefix を共有し、
   参照元だけが違う。照合述語は両方を見るため機能上は問題ないが、prefix を分ける方が
   読みやすい可能性がある
