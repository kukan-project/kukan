# ADR-033: 外部 SQL データソース（スナップショット方式 / ライブ proxy 方式の両論併記 + connector 拡張）

## ステータス

**提案（Proposed）** — 本 ADR は方式を確定しない。クエリ実行方式（スナップショット / ライブ）と
connector の配布・課金モデルを**両論併記**で整理し、判断材料を揃えることを目的とする。
ここに記す方針（特に open-core 境界の「推奨案」）は**いずれも暫定**であり、PoC・需要・法務確認を経て
別途確定 ADR ないし本 ADR の改訂で固める。

ADR-032「MCP データクエリ基盤」で確立した「カタログ探索 → スキーマ → クエリ」のエージェントループを、
ファイル（Parquet プレビュー）に限定せず**外部 SQL データベースを KUKAN のリソースとして登録し、
同一の MCP インターフェースからクエリ可能にする**ための設計検討。

## コンテキスト

ADR-032 により、KUKAN は ≤50MB の CSV/TSV を Parquet 化し、サーバーサイド DuckDB（サンドボックス）で
クエリでき、MCP の `get_resource_schema` / `query_resource` から AI エージェントが自律的に集計できる
ようになった。一方で、自治体・企業の実データの多くは**ファイルではなくリレーショナル DB に存在する**。
これらを「ファイルとしてエクスポートして登録し直す」運用は鮮度・手間の両面で現実的でない。

そこで、**外部 SQL データソースを KUKAN リソースとして登録**し、

- 接続情報（ホスト・認証）は**外部に非公開**（API/MCP レスポンスへ一切露出しない）
- KUKAN 経由でサニタイズしてクエリを発行
- MCP からは Parquet リソースと**同一の `query_resource` インターフェース**で扱える

という形を目指す。さらに、DB エンジンごとの connector は**商用販売の余地**があり、
plugin / extension 化（open-core）を視野に入れる。

ADR-032 のサンドボックスの核心は次の2点であった。これは外部 SQL を扱う上での**最大の制約**になる:

- `SET enable_external_access = false`（ファイル/URL/httpfs/COPY を全面禁止）
- Parquet を**インメモリ `data` テーブルへ実体化**してからロックダウン（以降ファイルにも外部にも触れない）

「外部 DB へ生きた接続を張ってクエリする」ことは、この「一度取り込んだら外に出ない」という前提を
**反転**させる。したがって既存サンドボックスをそのまま転用できない点が、本 ADR の中心的な論点である。

## 検討した選択肢

### 1. クエリ実行方式（中心論点・両論併記）

#### 方式 S: スナップショット（ELT）方式

外部 SQL ソースを**新しい Fetch ソース**として扱う。定期的（または手動 reprocess 時）に抽出クエリを
実行し、結果を**プレビュー Parquet と同一形式で materialize**する。

```
SQL接続 + 抽出クエリ ──(定期/手動)──▶ Parquet生成 ──▶ 既存パイプライン(Extract/Index)
                                              └─▶ schema永続化・preview・DuckDBクエリ・MCP すべて無改修で動作
```

- **利点**
  - 新規セキュリティ面が**ほぼゼロ**。クエリ実行・MCP・`query_resource` は ADR-032 のまま動く。
  - 重いクエリは「抽出時に 1 回・サーバー制御下で」しか走らない → 接続先本番 DB への DoS リスクと、
    エンジン別 SQL インジェクション検証の負担が消える（生 SQL を外部 DB に届けないため）。
  - DuckDB の community extension（`postgres_scanner` / `mysql_scanner` / `sqlite_scanner`）で
    主要エンジンは「DuckDB が外部 DB を読んで Parquet を書く」だけで取り込める。
  - 既存の「1 リソース = 1 表形式データ」という不変条件と整合（後述「リソース粒度」）。
- **欠点 / トレードオフ**
  - **鮮度が抽出間隔に依存**（リアルタイムでない）。
  - 大規模テーブルのフル materialize はストレージ・抽出時間を消費（行数/サイズ上限・差分抽出が課題）。
  - 抽出スケジューラ（cron 的トリガ。worker には croner が既にある）が必要。

#### 方式 L: ライブ proxy（federation）方式

KUKAN が**接続先 DB へリアルタイムでクエリを中継**する。ご提案に最も忠実な形。

```
MCP/API query ──▶ KUKAN(検証・サニタイズ) ──ライブ接続──▶ 外部DB ──▶ 結果整形 ──▶ 利用者
```

- **利点**
  - **常に最新**。materialize のストレージ・遅延が不要。
  - 巨大テーブルでも「必要な集計だけ」を DB 側に押し込める（pushdown）。
- **欠点 / トレードオフ**
  - **ADR-032 サンドボックスの前提（外部アクセス禁止）と衝突** → 別個の安全モデルを再設計する必要。
  - **エンジンごとに方言が異なり、「SELECT 限定」保証のコストが跳ね上がる**（DuckDB 一本で閉じていた
    検証ロジックが engine ごとに必要）。
  - **接続先本番 DB への DoS リスク** — AI が重い `SELECT`（全表スキャン・巨大 JOIN）を投げると本番
    OLTP を巻き添えにする。KUKAN 側タイムアウトでは remote 側の負荷は止められない。
  - 接続プール管理、到達性（閉域網では外部 DB が特定サブネットからしか見えない等）、結果サイズ制御。

> **技術メモ**: ライブ方式でも実行エンジンに DuckDB の `ATTACH`（postgres/mysql/sqlite scanner）を使えば
> 方言差をある程度吸収できる。ただし `ATTACH` は `enable_external_access` 系を有効化する必要があり、
> ADR-032 のロックダウンとは**両立しない別経路**になる。同一プロセスに「外部アクセス可の DuckDB」を
> 同居させること自体がリスクなので、ライブ採用時はクエリサービスの**プロセス分離**（ADR-032 残課題 §2）と
> セットで検討する。

#### 方式比較サマリ

| 観点                   | S: スナップショット           | L: ライブ proxy            |
| ---------------------- | ----------------------------- | -------------------------- |
| 鮮度                   | 抽出間隔依存                  | 常に最新                   |
| 新規セキュリティ面     | ほぼゼロ（既存流用）          | 大（サンドボックス再設計） |
| 本番 DB への負荷       | 抽出時 1 回のみ               | クエリ毎・DoS リスク       |
| エンジン別注入検証     | 不要（生 SQL を外に出さない） | 必須・方言差大             |
| ストレージ             | Parquet 分消費                | 不要                       |
| 大規模テーブル         | フル materialize が課題       | pushdown で有利            |
| 既存パイプライン再利用 | 全面再利用                    | ほぼ新規                   |
| MCP インターフェース   | `query_resource` のまま       | 同一に保てる（実装は別）   |

> **推奨（暫定）**: **v1 は方式 S（スナップショット）に倒す**。MCP インターフェースを同一に保てるため、
> 後から方式 L を「鮮度が要るソース向けオプション」として追加しても利用者からは透過的。
> 方式 L は需要が見えてから、プロセス分離・エンジン別検証とセットの別フェーズに置く。
> （本推奨は暫定であり、PoC と需要次第で見直す。）

### 2. リソースの粒度

- **A) 接続そのものをリソースにする**: 1 接続 = 多数のテーブル/ビューを持つ「箱」。
  「1 リソース = 1 表形式データ」という現行の不変条件が崩れ、schema 永続化・preview・query の
  前提が成立しなくなる。**却下寄り**。
- **B) 1 つの抽出クエリ/ビューをリソースにする（推奨・暫定）**: 接続情報は別エンティティ（後述）として
  持ち、リソースはそれを参照しつつ「定義クエリ or ビュー名」を保持する（"virtual dataset"）。
  これにより「1 リソース = 1 表形式データ」が保たれ、ADR-032 の schema/preview/query がそのまま乗る。
  スナップショット方式では「このクエリの結果を Parquet 化」、ライブ方式では「このクエリをラップして実行」
  と、両方式で同じ粒度を使える。

### 3. 接続情報（認証）の管理

KUKAN がこれまで持っていない新しい責務。最低限の要件:

- DB への平文保存は不可。**Secrets Manager / SSM Parameter Store**（AWS）と、オンプレ/閉域用の
  暗号化保管を抽象化する（envelope encryption 等）。アダプタ化の是非は §5 と合わせて判断。
- 接続文字列・認証情報は **API/MCP レスポンスに一切出さない**（schema とクエリ結果のみ返す）。
- 接続先には **read-only・最小権限ユーザー**を要求（特にライブ方式では必須）。
- ローテーション運用を想定。

### 4. スキーマ可視化（ADR-032 Part A との接続）

- スナップショット方式: materialize した Parquet から ADR-032 と同じ経路で `metadata.schema` を得る。
  追加実装ほぼ不要。
- ライブ方式: 接続先の `information_schema` 参照、または定義クエリを `LIMIT 0` 実行して列・型を取得し、
  ADR-032 の schema 形式へマッピングする。

### 5. connector の配布・課金モデル（open-core）と ADR-005 / AGPL

> 本節は「open-core 前提で境界まで今決める」という方針に沿うが、**配布形態とライセンス境界は法務確認を
> 要する暫定案**である。

#### 5-1. ADR-005「アダプターは 4 つだけ」との関係

connector registry は事実上 **5 つ目のアダプタ族**の追加であり、ADR-005 の設計思想からの意図的な逸脱。
本 ADR で **ADR-005 を部分的に拡張する**ことを明記する（ADR-005 のステータスは据え置き、関連 ADR として
相互参照）。逸脱を正当化する根拠は「環境差ではなく**接続先エンジン差**を吸収する別系統の抽象であり、
かつ商用配布の境界を作るための拡張点」であること。

#### 5-2. エンジンの線引き（推奨・暫定）

| 区分           | エンジン                                      | 実装方針                  | ライセンス       |
| -------------- | --------------------------------------------- | ------------------------- | ---------------- |
| 無償・本体同梱 | PostgreSQL / MySQL / SQLite                   | DuckDB scanner で取り込み | AGPL（本体同梱） |
| 商用 connector | Oracle / SQL Server / Snowflake / BigQuery 等 | エンジン固有 SDK で手書き | 別配布・商用     |

**「課金対象 = DuckDB が読めないエンジン」**という線引きが、技術的境界（scanner の有無）と商用境界に
綺麗に一致する点が本案の利点。

#### 5-3. 拡張点とライセンス境界

- `DataSourceConnector` インターフェース（接続・スキーマ取得・抽出/クエリ実行を抽象化）を定義し、
  registry でエンジン名 → connector を解決する。
- **AGPL 上の論点**: AGPL コアに商用クローズド connector を**動的リンク**して配布する形態はグレー〜危険。
  以下のいずれかで境界を明確化する必要がある（**法務確認前提・暫定**）:
  - (a) 拡張点（インターフェース層）を**より緩いライセンス**（例: Apache-2.0）で別パッケージに切り出し、
    そこに対して商用 connector を実装・配布する。
  - (b) connector を**別プロセス/別サービス**として分離し、ネットワーク境界の plugin API（gRPC/HTTP）で
    接続する（リンクではなく通信にすることで AGPL の linking 論点を回避）。
- v1 では**まず拡張点（registry + interface）だけ**を設計・実装し、無償 3 エンジンを載せる。
  商用 connector の実配布は (a)/(b) の確定後。

## 決定

**本 ADR は単一の方式を決定しない（提案段階）。** 以下を「合意された出発点」として記録する:

1. **リソース粒度は方式 B（1 抽出クエリ/ビュー = 1 リソース）**を前提に設計を進める。
2. **クエリ実行方式は S（スナップショット）を v1 の第一候補**とし、L（ライブ）は MCP インターフェースを
   同一に保ったまま後続フェーズで追加可能な拡張として位置づける（いずれも暫定）。
3. **接続情報は秘匿（レスポンス非露出）・最小権限・Secret 保管**を必須要件とする。
4. **connector は open-core を前提**に、`DataSourceConnector` 拡張点と registry を設計する。線引きは
   「DuckDB scanner で読めるエンジン=無償同梱 / 読めないエンジン=商用 connector」を推奨案とする。
   AGPL とのライセンス境界（拡張点の分離ライセンス or プロセス分離 plugin API）は**法務確認後に確定**。
5. ADR-005 を**部分的に拡張**する（connector を 5 つ目のアダプタ族として許容）ことを明記。

確定が必要な残論点は「残課題」に列挙する。

## 影響

- **DB**: 接続情報エンティティ（Secret 参照を持つ）と、リソースの「定義クエリ/ビュー + connector 種別」
  メタデータを追加。接続情報そのものは DB に平文保存しない。
- **packages 構成**: `DataSourceConnector` 拡張点パッケージ（ライセンス境界の都合で別パッケージになりうる）と
  registry を新設。無償 3 エンジンの connector を本体同梱。
- **worker**: スナップショット方式の抽出ステップ（croner による定期トリガ）を追加。
- **API/MCP**: リソース種別が「ファイル」か「外部 SQL」かに関わらず `get_resource_schema` /
  `query_resource` が透過的に動くよう、クエリ実行の分岐をサービス層に閉じ込める。
- **セキュリティ**: 接続情報の秘匿・最小権限・Secret 管理が新規の重点項目。ライブ方式採用時は
  エンジン別 SQL 検証とプロセス分離が追加で必要。
- **ライセンス/事業**: open-core 境界の確定（AGPL とプラグインの関係）はコード以前に法務判断を要する。
- **ADR-005**: 本 ADR により部分的に拡張（connector 族を追加）。

## 残課題（未解決事項）

1. **方式 S / L の最終決定**: PoC（スナップショットで Postgres を 1 ソース取り込み）を経て確定する。
2. **差分抽出 / 大規模テーブル**: フル materialize を避ける増分取り込み（更新列・CDC 等）。
3. **抽出スケジューリング**: 間隔設定・手動トリガ・失敗時リトライの UX とパイプライン統合。
4. **Secret 保管の抽象**: AWS（Secrets Manager/SSM）とオンプレ/閉域（暗号化保管）の両対応方式。
5. **AGPL × 商用 connector の配布形態確定**: 拡張点の分離ライセンス案 (a) / プロセス分離 plugin 案 (b) の
   いずれを採るか（法務確認）。
6. **ライブ方式のサンドボックス設計**: エンジン別 SELECT 限定検証、接続プール、remote 側負荷制御、
   クエリサービスのプロセス分離（ADR-032 残課題 §2 と合流）。
7. **クロスソース JOIN**: 複数 connector/リソースを跨ぐクエリ（ADR-032 残課題 §3 と関連）。
8. **レート制限・課金計測**: ライブ方式での高頻度クエリのコスト可視化（ADR-032 残課題 §7 と関連）。
