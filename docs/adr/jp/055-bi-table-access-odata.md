# ADR-055: BI ツールからの表データ接続（OData 読み取り専用エンドポイント）

## ステータス

**提案（Proposed）** — 本 ADR は実装を確定しない。BI ツール（Tableau を初出の要求として、
Power BI・Excel を含む）から KUKAN の表データへ接続する経路を比較し、判断材料を揃える。

ADR-032「MCP データクエリ基盤」が整えた「カタログ探索 → スキーマ → クエリ」は**エージェント向け**の
経路である。本 ADR が扱うのは**人間がデスクトップの BI ツールから触る**経路であり、要求の形が異なる。

## コンテキスト

KUKAN の表データは次の形で存在する。

- 正本は S3 のオリジナルファイル（CSV/TSV 等）。配信は**サーバー経由のストリーミング**（ADR-017）。
  読み取りの署名 URL は一度導入して撤去済みで、presigned URL はアップロード専用である
- ≤100MB の CSV/TSV は**プレビュー Parquet** に変換済み（ADR-014 / ADR-029）
- 行差分は DuckLake（ADR-043）。カタログは PostgreSQL の `ducklake` スキーマ
- クエリは `POST /api/v1/resources/{id}/query`（ADR-032 Part B）

ここに「Tableau から接続したい」という要求が来た。素朴には「DuckDB に対応したコネクタはあるか」と
いう問いになるが、**KUKAN には接続先になる DuckDB が存在しない**。ADR-032 の DuckDB は
クエリごとに生成され、`enable_external_access = false` でロックダウンされ、終了時に破棄される。
常設のエンドポイントではない。したがって問いは「どのプロトコルで表データを公開するか」になる。

### 調査（2026-09 時点の Tableau）

設計の前提になるため、実際に確認できた事実を記録する。**いずれもベンダーの仕様であり、変わり得る。**

| 項目                      | 確認できたこと                                                                                                                                                                                                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DuckDB コネクタ           | **存在する。** MotherDuck が `duckdb_jdbc.taco` を維持し、Tableau Exchange に掲載（v1.1.1 / 2026-02）。接続先は**ローカルの DuckDB ファイル・インメモリ・MotherDuck**                                                                                                                                    |
| 自作コネクタ（.taco）     | **Tableau Cloud へは配布できない。** パートナー製コネクタは Tableau Cloud への publish に非対応で、Cloud には Tableau 管理のコネクタしか載らない                                                                                                                                                         |

この表から、設計を決める 2 つの事実が出てくる。

1. **Tableau の OData は抽出専用で、射影の押し下げもできない。** `$select` が効かない以上、更新のたびに
   **エンティティセット全体・全列**が取られる。「BI から必要な列だけ軽く引く」という絵は描けない
2. **S3 コネクタは IAM アクセスキーを要求する。** 公開カタログの閲覧者に IAM 資格情報を配ることは
   できないので、この経路は「バケットを自分で持つ組織」専用であり、KUKAN の利用者向けにはならない

## 検討した選択肢

### A. 自作 `.taco` コネクタ（Tableau Connector SDK）

KUKAN 独自のクエリエンドポイントを JDBC ドライバ + `.taco` で包む。

- 利点: 型・方言・認証を完全に制御できる。Tableau の UI に名前付きコネクタとして出る
- 欠点: **Tableau Cloud に配布できない**（上表）。Tableau Desktop / Server 限定になる。
  JDBC ドライバ（= JVM 実装）を新たに保守する必要がある。**クライアント 1 種類にしか効かない**

### B. OData 読み取り専用エンドポイント

`/odata/` 配下にサービス文書・`$metadata`・エンティティセットを出す。

- 利点: **Tableau・Power BI・Excel が標準で読む。** ドライバのインストールが不要。
  HTTPS + トークンで完結し、既存のアクセス制御に乗る。自己記述的（`$metadata`）
- 欠点: 行指向の JSON を HTTP で運ぶため大きな表に弱い。Tableau に限れば全件抽出になる（上記）。
  `$metadata` の EDM 型へ写像する実装が要る

### C. 既存のダウンロード経路（現状のまま）

ADR-017 のサーバー経由ストリーミングで Parquet / CSV を落としてもらい、BI ツールで開く。

- 利点: **実装ゼロ。** 既にある。全件取得としては最も効率が良い（列指向・圧縮済み）
- 欠点: **Tableau では更新のたびに手作業になる。** Tableau は HTTP 上の CSV にネイティブに繋がらず、
  公開したフラットファイルは Cloud/Server で更新されない。Excel と Power BI は URL 直指定で
  更新できるので、この欠点は**Tableau だけのもの**である。
  カタログから「この表を BI で開く」という導線もない。
  ローカル .parquet を Tableau が開けるかは未確認（開けなければ CSV になる）

### C'. 全件取得を API がその場で生成してストリームする

保存済みのオブジェクトを配るのではなく、プレビュー Parquet（または DuckLake の版）から
**その場で CSV / Parquet を組み立ててレスポンスへ流す**。

- 利点: ADR-017 の既存パターンに乗る。**全バイトがアクセス制御の下を通る**。
  文字コードを UTF-8 に正規化でき（正本が Shift_JIS でも）、形式を選べる。
  **DuckLake で再構成した版は S3 にオブジェクトとして存在しないため、出すならこれしかない**
- 欠点: 応答の間ずっとタスクを占有する。生成物なのでレジューム（Range）が効かない

### D. PostgreSQL ワイヤプロトコル互換エンドポイント

Tableau の一次コネクタである PostgreSQL として見せる。

- 利点: BI ツール側の対応が最も厚い。ライブ接続ができる
- 欠点: 表データは PostgreSQL に無い（S3 の Parquet + DuckLake カタログ）。
  互換層を新規に用意・運用することになり、**公開面にデータベースプロトコルを晒す**判断も伴う。
  本 ADR の要求に対して明らかに過大

### E. S3 直結（Tableau の Amazon S3 コネクタ）

- 利点: 実装ゼロ。Parquet を列指向のまま読む
- 欠点: **IAM アクセスキーが要る**ため、公開カタログの利用者には渡せない。
  自バケットを持つ運用者向けの説明としては有効

## 決定（提案）

**B（OData）を入口として採り、全件取得は C（ファイル）へ誘導する 2 経路構成とする。**

### 1. 採用理由は「URL を貼るだけで試せる」である

最優先の要件は**手軽に試せること**とする。KUKAN のリソースページから URL をコピーし、
BI ツールに貼れば表が開く — この体験が取れるかどうかで選ぶ。

| 経路                | Tableau                                                     | Power BI | Excel  |
| ------------------- | ----------------------------------------------------------- | -------- | ------ |
| **B. OData**        | **URL 貼付で可**                                            | **可**   | **可** |
| C. CSV の URL       | **不可**（テキストファイルコネクタはローカル/UNC パス前提） | 可       | 可     |
| REST API Connector  | **JDBC ドライバ（.jar）の手動配置が先に要る**               | —        | —      |
| C. ファイルを落とす | ダウンロード作業が要る                                      | 同左     | 同左   |

**3 ツールすべてで「貼るだけ」が成立するのは OData だけ**である。A（`.taco`）と
REST API Connector はインストールを要求し、この要件の対極にある。E（S3 コネクタ）は
IAM アクセスキー、D（PostgreSQL 互換）は接続情報の設定が要る。

更新（refresh）が付いてくるのは**結果であって理由ではない**。貼った URL はそのまま
データソースとして残るので、再取得が手作業にならない。

### 1'. ゆえに「URL が見えていること」が実装の一部である

プロトコルを用意しただけでは要件を満たさない。**リソースページに OData の URL を表示し、
コピーできること**までが本 ADR の範囲である。URL は次を満たす。

- **推測でき、安定している**（リソース id で決まり、版を指定しなければ現行版）
- **公開リソースは認証なしで開ける。** Tableau の OData コネクタは
  「ユーザー名/パスワード」か「認証なし」しか持たない。公開データに対して
  トークンを要求すると、貼るだけでは終わらなくなる
- **ブラウザに貼っても読める**（JSON が返る）。何が入っているか確かめてから
  BI ツールへ持っていける

導線そのものにも条件が付く。

- **開発者向けの導線とは分ける。** 読む人が違う — Data API（ADR-032）のパネルは
  SQL を書く人のもので、URL を貼りたい人がそこを開く理由がない。リソースページに
  独立した入口を置く
- **出せないときも導線は残し、理由を言う。** Step 1 は EDM 識別子にならない見出しを
  持つリソースを丸ごと拒否する（残課題 1）ので、**出せない方が多数派**である。
  入口を黙って消すと、公開者には「隣の表にはあるのにこの表には無い」が理由不明で並ぶ。
  薄く表示したまま残し、該当する見出しを挙げる。**見出しは公開者が直せる**種類の
  問題だからである

### 2. ADR-032 のサンドボックスは転用しない

ADR-032 のサンドボックス（使い捨てインスタンス・`enable_external_access = false`・SQL 検証・
`memory_limit = 256MB` × 同時実行 1）は、**任意のユーザー SQL を封じ込める**ために存在する。
OData にはユーザー SQL が無い。クエリの形はこちらが決める。したがって:

- OData 経路は**サンドボックスを経由しない**。SQL 検証も不要（発行する SQL は KUKAN が構成する）
- 必要なのはクエリエンジンではなく**ページングできる読み出し**である

これを混同すると、「AI の 1 回の問い」向けに絞った上限（256MB・同時実行 1）を BI の全件抽出が
叩き続けることになり、両方の要求を同時に壊す。

### 3. 全件取得は OData から降ろし、ダウンロード経路へ誘導する

行数が閾値を超えるエンティティセットは、OData で全件を配らない。
~~ページングさせない（`@odata.nextLink` を返し続けない）。JSON を数百回往復するより、
1 本の応答で取り切る方が速く、サーバーも痛まない。~~（根拠と機構は Step 1 の実測で
差し替えた — 下の追記）
**誘導先は ADR-017 のサーバー経由ストリーミングであり、署名 URL ではない**（読み取りの
presigned URL は ADR-017 で撤去済み）。

> **Step 1 の実測（追記）**: 92,180 行 × 9 列をフィードで全ページ取り切ると
> **3 往復・1.94 秒・JSON 19.1MB**（元ファイル 7.13MB の 2.7 倍）。ページ単価は横ばいで
> （最終ページ 137ms 対 先頭 147ms）、100 万行でも 20 往復程度である。「数百回の往復」は
> 1,000 行ページを想定した数字で、50,000 行/ページには当たらない。また条件 1（実体化しない）は
> **フィード自身が満たした**ため、メモリの面でダウンロード経路が安全側、という関係も無い。
>
> 残る根拠は**転送量**である。JSON が元ファイルの 2.7 倍あり、更新のたびに毎回かかる。
>
> 機構も改める。`@odata.nextLink` を返さずに止めるのは**黙った打ち切り**であり、BI ツールには
> 完全な表に見えるものが渡る。Step 1 が `$filter` を無視せず 501 で拒否したのと逆向きになるので、
> **明示的に断り、誘導先を応答で示す**こと。
>
> なお**誘導先は同じものではない**。ADR-017 が流すのは正本ファイル、フィードが配るのは
> 解釈後の表（落ちた行・型・`RowId`）である。同じ表をファイルで渡すなら生成が要る
> （次段落の「その場で組み立てる場合」）。

保存済みのプレビュー Parquet をそのまま流す場合と、C' のようにその場で組み立てる場合がある。
**版（ADR-043）を DuckLake の行差分から再構成したものは S3 にオブジェクトとして存在しない**ため、
そこを出すなら生成一択になる。どちらの形でも、次の 3 点を満たすこと。

1. **実体化しない。** ADR-032 は Parquet を**インメモリテーブルへ実体化してから**ロックダウンするが、
   全件をそれに通すと web コンテナ（small = 512MB）が落ちる。チャンク単位で読み、
   バックプレッシャーに従ってレスポンスへ流す（ADR-017 のダウンロードと同じ作り）
2. **前段のタイムアウトとデプロイを織り込む。** CloudFront（ADR-027）と ALB を通るため、
   生成の途中でバイトが流れない空白があると切られる。ローリング更新で古いタスクが
   落ちるときに長い応答が途中で切れることも前提にする
3. **同時実行の上限を ADR-032 とは別に持つ。** サンドボックスの「同時実行 1」は
   AI の 1 回の問い向けの値である。全件取得をそこへ合流させると、BI の抽出が
   AI のクエリを 429 で締め出す

### 4. 公開単位

エンティティセットは**リソース単位**とし、プレビュー Parquet を持つリソース（`queryable`）のみを
公開する。版（ADR-043）は既定で現行版を出す。過去版の公開可否は残課題。

### 5. v1 は公開リソースのみ。非公開は出さない

Tableau の接続ダイアログは「ユーザー名/パスワード」か「認証なし」しか持たない（調査表）。
非公開を出すなら `/odata` に限って HTTP Basic を受けることになるが、**v1 では出さない**。

理由は認証機構の手間ではなく、**資格情報の置き場所**である。Tableau は入力された資格情報を
ワークブック／データソースに保存し、publish すれば埋め込まれる。**長命のトークンが成果物の
中に残り、そのワークブックを共有すれば一緒に渡る。** 公開リソースだけに限れば、
認証の経路そのものが不要になり、「貼るだけ」も無条件で成立する。

**将来の方向**: 出すことになったときは、アカウントの資格情報を使わせるのではなく、
**使い捨ての Basic 資格情報を期間限定で発行する**。リソースページから 1 つ発行し、
有効期限とスコープ（そのリソース、読み取りのみ）を持たせ、いつでも失効させられる形。
ワークブックが漏れても被害がその 1 リソースと期限内に収まり、アカウントには及ばない。
利用者の本物のパスワードを受けることは、その場合でもしない。

### 6. 機械アクセスとして軽く作る

この経路を叩くのは人ではなく BI ツールであり、**同じ URL を繰り返し取りに来る**。
1 リクエストあたりの仕事を小さく保つことを設計の制約とする。

- **リクエストごとの付帯処理を持たせない。** セッション、Cookie、CSRF、認可の解決は
  この経路には要らない（決定 §5 により公開リソースのみ）。既存 API のミドルウェアを
  そのまま被せず、`/odata` は独立した薄い経路にする
- **HTTP キャッシュを効かせる。** 版は不変なので `ETag` / `Last-Modified` を返し、
  変わっていなければ **304 を返す**。ETag は（リソース id, 版 id, 形式, クエリ）から
  **データを読まずに計算できる**。効き先は利用者ではなく **CloudFront からの再検証**である
  — BI ツールの抽出が条件付きリクエストを送るとは限らないが、CloudFront は TTL 切れに
  再検証しに来るので、そこで 304 を返せれば表を作り直さずに済む。
  **ただし現状の CloudFront 設定では 1 バイトもキャッシュされない**（次項）。
  **なお「不変だから長く持てる」は TTL の上限を決めない**（実装で判明）。上限を決めるのは
  取り下げ — 配信中の版のパージ、データセットの非公開化、リソースの削除 — で、
  いずれもオリジンはその瞬間から拒否するが、**エッジが既に握ったコピーは拒否に触れない**。
  古い版のパージはここに含まれない（フィードが配ったことのない版だから）
- **スキーマをページごとに引き直さない。** `$metadata` と列の対応は版ごとに決まるので、
  プロセス内にキャッシュする。**Step 1 では実装していない**（実装で判明）: この読み取りは
  実測 0.36ms で 1 ページ約 60ms に対して無視できる一方、**安価な鍵では代われない** —
  同じバイト列を解釈し直すと内容ハッシュは変わらないままプレビューが変わり、それはこの
  フィードの検証子（ETag の種）が捕まえるべき当のケースだから。内容ハッシュで鍵にした
  キャッシュは、その TTL のあいだ古い表を配る
- **特殊な数値は OData の綴りで出す。** CSV の `nan` / `inf` / `-inf` は DOUBLE 列として
  読まれるため、そのままでは `JSON.stringify` が `null` にする — ファイルが持っていた値が
  欠損として届き、`Nullable="false"` と矛盾する。OData JSON 4.01 の `"NaN"` / `"INF"` /
  `"-INF"` で出す（実装で判明）
- **応答に飾りを載せない。** クライアントが使わない OData アノテーションは出さない。
  JSON は組み立ててから返すのではなく流す
- **ログを 1 行に保つ。** ADR-032 の `query` ログは SQL まで書くが、この経路は
  全件抽出で何十回も叩かれる。1 リクエスト 1 行、行の内容は書かない

#### `/odata/*` には CloudFront の behaviour を新設する

現状の behaviour は 3 つで、**どれもこの経路には合わない**（`infra/lib/constructs/cdn.ts`）。

| パス                | ポリシー                     | この経路に使えない理由                                                                                                          |
| ------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `/_next/static/*`   | `CACHING_OPTIMIZED`          | 対象外                                                                                                                          |
| `/auth/*`, `/api/*` | **`CACHING_DISABLED`**       | `/api/` の下に置くと **`Cache-Control` を何と書いても無視される**                                                               |
| 既定（HTML）        | `minTtl 60s` / `maxTtl 300s` | `minTtl` はオリジンが「キャッシュするな」と言っても 60 秒保持する。`maxTtl` が「版は不変だから長い TTL」を 5 分で打ち止めにする |

したがって `/odata/*` 用の behaviour とキャッシュポリシーを足す。**API ではなくインフラ側の変更**である。
そのポリシーで満たすこと:

- **クエリ文字列をキャッシュキーに含める。** 落とすと `$skip=0` と `$skip=1000` が同じキーになり、
  **利用者は同じ 1,000 行を延々と受け取る**。エラーは出ない
- Cookie はキーに含めない。この経路に Cookie は無い（決定 §5）

#### ストリームがキャッシュされる条件

チャンク応答も CloudFront はキャッシュできるが、条件が付く。

- **応答が最後まで完了すること。** 途中で切れた応答は保存されない。
  決定 §3 の「ローリング更新で応答が切れる」は、ここでは「キャッシュも埋まらない」として二重に効く
- **バイトが流れ続けること。** CloudFront のオリジン応答タイムアウトは総時間ではなく
  「応答を待つ時間」と「パケット間の間隔」である。**先頭を早く出すことが、性能ではなく
  キャッシュ成立の条件になる** — 最初のバイトまでに materialize で数十秒かけてはいけない
- オブジェクトサイズの上限（30GB 程度）は、この用途では問題にならない

副産物として、**同じキーへの同時のキャッシュミスを CloudFront が 1 本にまとめる**。
朝に複数人が一斉に抽出を更新しても、オリジンでの生成は 1 回で済む。

## 影響

- **新規の公開面が増える。** 認証・レート制限・アクセス制御（`getByIdWithAccessCheck`）を
  既存の経路と同じ規則で通す必要がある
- ~~**ADR-032 の残課題 §4（一時ファイルキャッシュ）が最適化から前提条件に変わる。**~~
  **実装で不要になった（Step 1）。** `QueryService.query()` は毎回 S3 から Parquet を
  落として一時ファイルに書くが、フィードは **DuckDB に `s3://` を直接読ませ、
  必要なバイト範囲だけを取る**。実測（MinIO・100 万行・8.9MB）で 1 ページあたりの取得は
  **0.11〜0.18MB**、先頭ページでも最終ページでも同じで、一時ファイルは書かない。
  web イメージには `httpfs` / `aws` が同梱済みで、資格情報の渡し方は lake と同じ
  （AWS は `credential_chain` + `REFRESH auto`）。**ただし外部アクセスを開けたままに
  なるため、読み出し中は S3 以外を閉じる**（`disabled_filesystems` で LocalFileSystem と
  HTTPFileSystem を無効化、`lock_configuration`）。ADR-032 が「実体化してから全閉じ」
  できるのに対し、こちらは「読みながら開けたまま、他を閉じる」になる
- **同時実行の枠を ADR-032 と分ける必要がある。** `withDuckdbSlot()` の枠は
  `QUERY_MEMORY_LIMIT_MB = 256` × 1 であり、ここに BI の全件抽出を流すと
  AI のクエリが 429 で締め出される
- **全件取得が web コンテナの持ち時間を使う。** 署名 URL のように S3 へ逃がす選択肢が
  ADR-017 で閉じている以上、応答時間とタスク占有は KUKAN 側の負担になる（残課題 11）
- **公開側 UI に「BI ツールで開く」導線が増える**（決定 §1'）。リソースページに
  独立した入口を置き、出せないリソースでは理由を出す
- **`$metadata` の型写像が新しい責務になる。** 列型は ADR-032 Part A で永続化済みのスキーマを
  出所とし、DuckDB の型 → EDM 型の対応表を 1 箇所に持つ
- 既存の API・MCP・プレビューには影響しない（追加のみ）

## 実装の重さ

既存資産に乗る部分と、新たに判断が要る部分が分かれる。

**乗るもの**: 列名と型は `ResourceSchema`（ADR-032 Part A）として `resource_pipeline.metadata` に
永続化済みで、`PipelineService.getQueryTarget()` が Parquet キーと一緒に 1 クエリで返す。
可視性は `ResourceService.getByIdWithAccessCheck()`、公開可否は `isQueryable()` がある。
異プロトコルの実装例として CKAN 互換ルータ（`/api/3/action`、299 行）がある。

**重いのは行数ではなく設計判断である。** 中心は次の 2 つ（残課題 1・2）。

| 部品                                                      | 目安    | 難度   |
| --------------------------------------------------------- | ------- | ------ |
| サービス文書 + ルータ骨格                                 | ~80 行  | 低     |
| `$metadata`（CSDL XML 生成）                              | ~150 行 | 中     |
| 列名の正規化 + 衝突解決 + 対応表                          | ~120 行 | **高** |
| 型写像 + JSON 直列化                                      | ~100 行 | 中     |
| エンティティセット読み出し（ページング・行の同定）        | ~150 行 | 中     |
| ~~一時ファイルキャッシュ（ADR-032 残課題 §4）~~ 不要      | —       | —      |
| 独立セマフォ・上限・全件誘導                              | ~80 行  | 低     |
| CloudFront の behaviour + キャッシュポリシー（**infra**） | ~60 行  | 低     |
| リソースページの URL 表示                                 | ~60 行  | 低     |
| テスト（統合・列名の変種）                                | ~400 行 | 中     |

合計 1,100〜1,400 行程度、CKAN 互換ルータ（本体 299 行 + テスト 402 行）の 2 倍強。

### 段階

**Step 1（小・PoC）**: 列名がそのまま EDM 識別子として通るリソースに限り、V4 の最小実装を出す。
行の同定は合成キー、クエリオプションは `$top` / `$skip` のみ、`$filter` なし。
**Tableau・Power BI・Excel に実際に URL を貼って開くことを確かめる**（~400 行）。
ここで開かないなら、残りを作る意味がない。

> **実装時の実測（追記）**: 見積もりの ~400 行は下回らなかった。読み出しが S3 直読みに
> 変わったこと（上記）、ストリーム化（1 ページを保持しない）、抽出を 1 つの版に固定する
> 仕組み、閉じ込めとその検証が加わり、テストを含めて 2,000 行規模になっている。
> また **Step 1 の条件で出せるのは dev の公開・表形式リソースの 25.4%（260 件中 66 件）**で、
> 残りは残課題 1 の正規化待ちになる（次項）。

**Step 2**: 列名の正規化規則を決めて全リソースへ広げる。ここが本体である。

**Step 3**: 全件誘導、`$filter`（~~一時ファイルキャッシュ~~ — 影響の節を参照）。

## 残課題（未解決事項）

1. **列名の正規化規則（最重）。** **実測で、この規則が無いままだと dev の公開・表形式
   リソースの 74.6% が配信できない**（260 件中 194 件）。落第を作っている文字は
   `/` 930、`(` `)` 各 576、全角括弧 約 380、`-` 322、`[` `]` 各 280。
   OData の `$metadata` は列をプロパティ名として宣言し、
   EDM 識別子は文字で始まり以降は文字・数字・`_` に限られる。**日本語そのものは通るが**、
   日本のオープンデータの見出しは `人口（人）` `面積 (km²)` `H31.4.1現在` のように
   **括弧・空白・記号・ピリオドを含むのが常態**であり、そのままでは宣言できない。
   決めることは 3 つ: 変換規則、変換後に衝突したとき（`面積 (km2)` と `面積（km2）` が
   同じ名前になる）の解決、そして**元の見出しをどこに残すか**
   （`@Core.Description` 等のアノテーションに回すのが素直）。
   変換後の名前は人間には読みにくくなるため、**表示名と識別子を分ける**ことになる
2. **行の同定。** OData の EntityType は**キーが必須**だが、KUKAN の表に主キーがあるとは
   限らない（ADR-043 ii-b で指定できるようになっただけで、無いのが普通）。
   合成キー（行番号）を置くことになるが、それは **Parquet の行順が安定していること**を
   前提にする（`$top` / `$skip` のページングも同じ前提）。また**版が変われば行番号の意味も
   変わる**ため、版をまたいで同じキーが同じ行を指さない。指定済みの主キーがあるとき
   それを使うかどうかも未決
3. **整数と時刻の直列化**（Step 1 は Int64 を JSON 数値、ゾーンの無い timestamp に `Z` を
   付けて `Edm.DateTimeOffset` として出している。どちらも未確定のまま実装した暫定）**。** `integer` は INT64 であり、`ColumnStats` が
   「INT64 は JS の Number 安全域を超えるので文字列で持つ」としているのと同じ問題が出る。
   OData JSON の `Edm.Int64` は既定で数値、`IEEE754Compatible=true` なら文字列で、
   **どちらで出すかで BI ツール側の解釈が変わる**。`timestamp` は `Edm.DateTimeOffset` が
   オフセット必須のため、KUKAN の timestamp が何を持っているかを確かめる必要がある
4. **使い捨て Basic 資格情報の設計（将来）。** v1 では非公開を出さないと決めた（決定 §5）。
   出すことになったときの未決事項は、発行の単位（リソース単位かサイト単位か）、
   既定の有効期限、失効の導線、そして `api-token-service` の既存トークンと
   同じ仕組みに載せるか別物にするか。Basic を受ける経路は `/odata` に限る
5. **OData のバージョン。** V4（JSON）で出すのが素直だが、Tableau 以外の古いクライアントが
   V2（XML/Atom）を要求する可能性がある。V4 単独で始め、要求が出てから考える
6. **全件誘導の閾値と表現。** 何行から「ファイルへ」とするか。OData の語彙で
   **明示的に断れるか**（黙って `@odata.nextLink` を止めない — 決定 §3 の追記）。
   誘導先を正本ファイルで済ませるか、解釈後の表を生成して渡すか
   （カスタムアノテーション or エラー本文）
7. **`$filter` の対応範囲。** Tableau は使わないが Power BI は押し下げ得る。
   どの演算子まで受けるか、受けた式をどう安全に SQL へ写すか
8. **過去版の公開。** ADR-043 の版をエンティティセットとして出すか、出すなら URL の形
9. **ローカル .parquet を Tableau が開けるか**の実機確認。開けないなら誘導先は CSV になる
10. **レート制限と課金の考え方。** 全件抽出は 1 リクエストでは終わらない。
    同時実行の制限を OData 経路に独立して設けるか
11. **版で鍵にしたキャッシュ。** ADR-043 の版は不変なので、**ある版の CSV も不変**である。
    **ただし不変性は TTL の上限を決めない**（決定 §6 の追記）。取り下げ（配信中の版の
    パージ・非公開化・削除）のあともエッジが配り続けるため、長い TTL を許すなら
    invalidate と、それが失敗したときの上限をセットで決める必要がある。
    URL を版で鍵にすれば CloudFront に長い TTL で載せられ、生成コストが
    リクエストごとではなく**版ごと**になる。C' の「応答の間タスクを占有する」欠点は
    これでかなり消える。鍵の形（`/resources/{id}/versions/{v}/export.csv` 等）と
    TTL、現行版を指す URL の扱いは未定
