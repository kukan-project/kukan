# ADR-063: 表形式のファイルは、中身ではなく「表のプロファイル」で索引する

## ステータス

**提案（Proposed）— 今の OpenSearch に先に入れ、ゴールデンセットで表の検索を確かめてから確定する** — 2026-10-05

CSV/TSV の本文の索引を、ファイルの中身のチャンクから**表のプロファイル**に置き換える。プロファイルは、
列名、名称とカテゴリの列の値の一覧、数値・日付の列の範囲、行数と列数、そして自由記述の列の本文（同じ行の
文脈を添えたもの）からなる。数値のセルや、同じ値の繰り返しは索引に入れない。

そのために、列ごとに型とは別の「役割」（数値・名称・カテゴリ・識別子・自由記述など）を規則で判定し、
列スキーマに持つ。役割はフィールド一覧と MCP で示し、人が上書きできる。

ADR-061（検索を PostgreSQL に寄せる）の移行を待たず、今の OpenSearch に先に入れる。PostgreSQL へ
移すときは、同じプロファイルをそのまま使う。XLSX は ADR-057 が入ってから同じ仕組みに乗せる。

本 ADR は ADR-032 Part A（列スキーマの永続化）を拡張する。

## コンテキスト

### 1. いまの扱い

表形式のファイルは、文書のテキストと同じく、ファイルの中身を 500KB ごとのチャンクにして索引している
（`apps/worker/src/pipeline/steps/index-content.ts` の `indexTextStream`、ADR-021）。

手元の開発環境の索引を測ると、本文のバイト数の **71%** が表形式（279 リソース、約 295MB）で、
語の辞書の **67%** が数字だけの語だった。

### 2. 何が問題か

- **数値のセルは、検索の手がかりにならない。** それでも索引の大半を占める
- **同じ値が何千行も繰り返される。** 「青森市」が 1 万行あっても、意味があるのは「この表に青森市が
  出てくる」ことだけである
- **列名が重みを持たない。** 列名は先頭行に一度出るだけなので、BM25 では値の大群に埋もれる。
  表を探すときに最も情報量があるのは列名である
- **表の断片は、RAG の文脈にならない。** 500KB や 1,500 字で区切った表を AI に渡しても、
  どの列の値かが分からない。ADR-061 でも、表はパッセージにしない

### 3. 既にある部品

- 列の型の推定（ADR-029）と、列スキーマの永続化（ADR-032 Part A）。列ごとに、名前、型、欠損の数、
  異なる値の数、すべて異なるか、数値の最小と最大を持ち、表の行数も持つ
- Interpret が作るプレビュー Parquet と、worker の子プロセスで動く DuckDB（ADR-059）
- 行の中身は `query_resource`（ADR-032）で引け、表はプレビュー（ADR-048）で見られる

## 検討した選択肢

### A) 今のまま、ファイルの中身を全部索引する

§2 の問題がそのまま残る。却下する。

### B) 列名だけを索引する

最も軽い。しかし「八戸市が載っている表」のように、値で表を探すことができない。却下する。

### C) 全部の行を文にして索引する

1 行を「列名: 値 / …」の文にして、全行をパッセージにする。数値の行は文にしても手がかりにならず、
行数の多い表では索引が膨大になる。自由記述の列に限って採る（D に含める）。

### D) 表のプロファイルを索引する — 採用（提案）

列名、カテゴリの値の一覧、範囲を持ち、自由記述の列だけは行の文脈を添えて本文として索引する。
索引の大部分を占める数値と繰り返しを落としつつ、列名と値で表を探せる。

## 決定（提案）

### 1. 列の役割を、規則で判定する

列ごとに、型（ADR-029）とは別に「役割」を判定する。判定は決まった規則で行い、AI は使わない。
同じ入力からは毎回同じ結果になり、AI のない環境でも動く。誤っても検索で当たる・当たらないが変わるだけで、
データは壊れない。規則が外れた列は、人が上書きする（§決定 5）。

| 役割                 | 判定（上から順に当てる）                                                                                                       | 索引                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------ |
| 数値・日付           | 型の推定が数値・日付・真偽。または値の 9 割以上が日付の形（`2026/5/12`、`令和6年4月`）                                         | 語にしない。範囲を持つ               |
| 数値（文字列で表記） | 値の 9 割以上が数値の形。カンマ、括弧、`-` `▲` `…` などの記号や単位を含む                                                      | 語にしない                           |
| 識別子               | URL・電話番号・郵便番号の形が 8 割以上。または英数字と記号だけで値がほぼすべて異なる。または列名が「コード」「番号」「ID」など | 語にしない                           |
| 自由記述             | 句読点か、ひらがなの連なりを含み、値が長い（平均 20 字以上）か、値がほぼ異なる。または列名が「備考」「概要」「説明」など       | 行の文脈を添えて本文として索引（§3） |
| 名称                 | 日本語で、値の半分以上が異なり、異なる値が 30 以上（施設名、事業名、町丁目、住所など）                                         | 値の一覧（§2）                       |
| カテゴリ             | 上のどれでもない文字列                                                                                                         | 値の一覧（§2）                       |

手がかりは、Interpret の DuckDB で列ごとに 1 回数える。値の長さ、文字の種類（数字・英字・かな・漢字）の割合、
句読点の有無、形（数値・日付・URL・電話番号）に合う割合、異なる値の数と行数の比、列名である。
しきい値は初期値で、実データとゴールデンセットで調整する。

統計表では、数値の列に「-」「…」「（8）」「10,000」が当たり前に混じり、型の推定では文字列のまま残る。
手元の試行では、文字列と推定された列の 3 分の 1 がこれだった（§試行）。この役割を見分けないと、
カテゴリや識別子に数字が大量に紛れ込む。

### 2. プロファイルの中身

- **列名。** すべての列を入れ、最も重く扱う
- **名称とカテゴリの列の値の一覧。** 列ごとに、出現の多い順に、1 列あたり 64KB まで入れる。同じ値は
  1 回だけ入れる。値には列名を前に置き、「市区町村名: 青森市、弘前市、八戸市、…」の形にする。
  上限を個数ではなく大きさで決めるのは、事業名（1,130 種類）や町丁目（1,171 種類）のように、
  1,000 個を超える名称の列が実際にあるからである
- **数値・日付の列の範囲**（既存の最小と最大）と、行数・列数。今は表示と AI の材料に使い、
  検索の語にはしない

### 3. 自由記述の列は、行の文脈を添えて本文として索引する

- 1 行を「カテゴリの列名: 値 / … / 自由記述の列名: 値」の文にする。カテゴリの列は、異なる値の
  少ないものから最大 3 列を添える
- まったく同じ文は 1 回だけ入れる
- 行番号を持ち、出典として「何行目か」を示せるようにする
- 文を束ねて本文として索引する（今は 500KB のチャンク、ADR-061 の後はパッセージ）
- 文の量には 1 表あたりの上限を設ける（初期値は 500KB）。上限を超えた分は索引に入れず、超えたことを記録する。
  プロファイルの大きさをファイルの大きさに比例させないためである

備考欄のように、表の中に自然文が入る場合を拾うための扱いである。

### 4. Interpret で作り、列スキーマに保存する

- Interpret でプレビュー Parquet を作ったあと、同じ子プロセス（ADR-059）の DuckDB で、列ごとの
  手がかりと値の頻度を数える。型の推定が済んでおり、列ごとに読めるので、CSV を解析し直すより軽い
- 規則を直したときは、Interpret をやり直さず、既存の Parquet に判定だけを流し直す。人が上書きしたときは、
  判定も流さず、プロファイルを作り直して索引を更新する（§決定 5）
- 今の版の列スキーマ（`resource_pipeline.metadata.schema`）の各列に、型とは別の項目として次を持つ。
  正本はデータベースとする
  - `role`：規則で判定した役割（§決定 1）
  - 判定の根拠（「値の 92% が数値の形」「列名に『コード』」など）
  - 名称とカテゴリの値の一覧（§決定 2 の上限）
- 版ごとに凍結する `resource_version.schema` には、役割を入れない。凍結した記録は「その版がどう読まれたか」
  であり（ADR-046）、役割は読み方を変えない。規則を直すたびに過去の版の記録を書き換えることになるうえ、
  索引に入るのは今の版だけなので、版ごとに持つ理由もない
- MCP の `get_resource_schema` も役割と値の一覧を返す。AI が SQL を組むとき、集計してよい列か、
  値の綴りがどうかが分かる
- 自由記述の文は、ストレージの成果物として保存し、索引のときに流し読む
- Parquet のフッター（`key_value_metadata`）への写しは、今は行わない。ダウンロードした Parquet でも
  役割を伝えたい需要が見えたら、作成時の判定の写しとして足す

### 5. 役割を見せ、人が上書きできるようにする

- フィールド一覧に、型の横に役割を示す。根拠は説明として出す。フィールド一覧は今 Parquet のフッターを
  読んでいるので、役割はデータベースの列スキーマから取る
- 「数値（文字列で表記）」は、データの品質の指摘にもなる。数値として扱えない理由（混じっている記号）を
  公開する人に示す
- データセットの編集者は、管理画面で列ごとに役割を上書きできる。上書きは、主キーや確定型と同じ確定の層
  （`resource.column_settings`、Versioning-ii の仕様書 §6.1・§6.2）に置き、推定の役割より優先する。
  推定の再計算は上書きを壊さず、以後の版にもそのまま効く。画面も、複数の列をまとめて選んで 1 回で
  適用する、主キー・確定型と同じものにする
- ただし、役割の上書きでは版を立てない。確定型はバイト列の読み方を変えるので版のゲートの入力になる
  （同 §6.5）が、役割は読み方を変えず、索引と表示を変えるだけである。上書きしたら、その場でプロファイルを
  作り直して索引を更新する
- 個人情報の判断（§決定 6）で編集者が付けるフラグも、同じ確定の層に置く

### 6. 個人情報の検出と、手がかりを共有する

列ごとの手がかり（形に合う割合、列名）は、ADR-006 の `PiiScanner`（個人情報の検出）の材料にもなる。
同じ走査で数える。

- 個人情報らしい列（氏名、生年月日、個人の電話番号やメールアドレスなど）は、プロファイルの索引から外す。
  外さないと、名称の列として個人名が検索に載る
- ただし、検出の要求は検索の分類と違う。1 件でもあれば問題で、取りこぼさないことを優先する。マイナンバーや
  カード番号は検査用の数字で確かめる。施設の電話番号や所在地は公開すべき情報なので、列名と列の組み合わせで
  判断し、結果は公開を止めずに編集者への警告とする。個人情報の疑いは公開の画面には出さない
- この検出の設計（規則と AI の役割分担、警告の出し方、公開前の確認）は別の ADR とする

### 7. 今の OpenSearch に入れる形

- **列名**は、リソースの文書に項目 `columns` を足して入れる。リソースの脚の `cross_fields` に加え、
  重みは `description` と同じ 2 から始めて評価で調整する。マッピングへの追加なので、索引の作り直しは
  要らない
- **カテゴリの値の一覧と自由記述の文**は、表の本文のチャンク（content の子）の中身を、ファイルの
  中身から置き換えて入れる
- 既存の索引は、表形式のリソースを再処理して置き換える

### 8. ADR-061 への引き継ぎ

PostgreSQL へ移すときは、列名をメタデータの項目に、カテゴリの値と自由記述の文の語を文書単位の
語の集合に入れる。パッセージにするのは自由記述の文だけである。表はパッセージにしない（ADR-061）。

### 9. 検索結果での見せ方

一致の理由を「列名で一致」「値で一致」と示す（ADR-034 の `matchSource` の拡張）。一致した値で
絞った状態のテーブルプレビュー（ADR-048）を開けるようにするのは後続とする。

## 段階

1. **プロファイルを作って保存する。** 索引は変えない。実データで、大きさと列の分類の当たり外れを見る
2. **今の OpenSearch に入れる。** 合否は、ゴールデンセットの overall が今から下がらない（誤差の範囲）
   ことと、表を探すクエリで下がらないこととする。表を探すクエリが足りなければ、先にゴールデンセットに足す
3. **ADR-061 の PostgreSQL の経路に引き継ぐ**（§決定 8）

## 試行

手元の開発環境の CSV/TSV 285 件（5,352 列）に、§決定 1 の規則を当てた。スクリプトは `spike/adr-063/` にある。

| 役割                 |  列数 | 例                                                   |
| -------------------- | ----: | ---------------------------------------------------- |
| 数値・日付           | 1,805 | —                                                    |
| 数値（文字列で表記） | 1,212 | `-`、`10,000`、`（8）` が混じる人数・金額・比率      |
| カテゴリ             | 1,225 | 種別（野菜、果実）、市場（豊洲、足立、大田）、有・無 |
| 名称                 |   260 | 施設名、事業名、町丁目、大使館名、住所               |
| 識別子               |   149 | 品目番号、URL、電話番号、郵便番号                    |
| 自由記述             |   127 | 備考、利用可能時間の特記事項、アンケートの自由回答   |
| 空                   |   574 | —                                                    |

規則を 3 回直した結果である。直したのは、文字列で書かれた数値と日付、電話番号（同じ値が繰り返されるので
「値がほぼすべて異なる」では拾えない）、長い名称（長さだけでは自由記述と区別できない）だった。

残った外れは次のとおり。

- 複数行の見出しの表では、見出しの残り（「合計」など）が値に紛れ込む。見出しの扱い（ADR-046）の問題である
- 短い自由回答（「なし」「わからない」）の列が名称に入ることがある。どちらでも値は索引される
- 手元の開発環境には、試験用に作ったでたらめな値の表も含まれる。本番に近いデータでの確認は段階 1 で行う

## 影響

- **CSV の大きさの上限。** プロファイルの大きさはファイルの大きさに比例しないので、索引は CSV の大きさの
  上限を決める理由ではなくなる。上限（今は取り込み・Parquet の作成とも 100MB）を上げるかどうかは、
  取り込みの経路と、Interpret・行レベル差分（ADR-043 層 2）の時間とメモリで決める。本 ADR では決めない

- **索引の大きさ。** 表形式の分（手元で本文の 7 割）が、表ごとのプロファイルに置き換わる
- **当たらなくなる検索。** 値の一覧の上限から漏れた値と、数値・識別子のセルでは、表が当たらなくなる
- **ハイライト。** 表の本文のハイライトは、ファイルの中身ではなくプロファイルの文に付く
- **MCP。** `get_resource_schema` が列の役割と値の一覧を返すようになる
- **フィールド一覧。** 役割をデータベースから取るので、Parquet のフッターだけでは表示が完結しなくなる

## 残課題

- 役割の判定のしきい値
- コード（郵便番号、団体コードなど）で表を探す需要の扱い。識別子の列の値を一部入れるか、
  DuckDB での列の検索で補うか
- 値の一覧の上限（1 列あたり 64KB）から漏れた値の扱い
- Parquet のない CSV（Parquet を作る上限を超えたもの）の扱い。今と同じく中身の先頭を索引するか、
  先頭の一定行を見本として役割を判定するか、列名だけを入れるか
- 個人情報の検出の ADR（ADR-006 の `PiiScanner` の具体化）
- 列名をリソースの埋め込み（ADR-054）の材料に加えるか
- 数値・日付の範囲を絞り込みに使うこと（拡張メタデータの絞り込みと合わせて考える）
- 語による類似リソースの検索で、同じ列構成の表を見つける使い方
- XLSX（ADR-057 の後）
