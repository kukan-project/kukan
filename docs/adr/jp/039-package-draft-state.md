# ADR-039: データセット下書き状態（draft）による作成と公開の分離

## ステータス

**提案（Proposed）**

## コンテキスト

現在のデータセット新規作成は次の順序で進む。

1. メタデータフォームを送信 → package 作成（この瞬間から公開 = 検索・一覧に露出）
2. 編集ページでリソースを追加 → presigned URL でアップロード → パイプライン起動

この構成には3つの問題がある。

- **作成 = 公開**: リソースが揃う前の書きかけデータセットが公開される。
  作業を中断すると不完全なまま公開され続ける
- **file-first にできない**: presigned URL 発行に resourceId、resource 作成に
  packageId が必要なため、ファイルを見る前にメタデータを確定させる順序が
  強制される。データ内容を見てからメタデータを書く UX（将来の AI メタデータ
  提案を含む）が成立しない
- **アップロードと公開が同一タイミング**: リソース操作が即時反映され、
  「全部揃えてから公開」ができない

なお package → resource → upload という技術的順序自体は FK と presigned
フローの前提であり、本 ADR で変えるべき対象ではない。

## 検討した選択肢

### A) リソースの package 非依存化（ステージングアップロード）

package 作成前にファイルだけ先にアップロードできるようにする案。

- 問題点:
  - `resource.packageId` の nullable 化、または resource とは別の
    ステージングオブジェクト概念と resourceId 無しの presigned フローが必要
  - `resource_pipeline` が resourceId 前提のためパイプラインを実行できず、
    プレビュー・列スキーマが公開前に得られない
  - DB に記録が無いため中断・再開が不能。再開を DB 管理しようとすると
    「未公開状態を管理するテーブル」= draft の再発明になる
  - DB に紐付かない Storage オブジェクトの TTL 掃除を新設する必要がある

### B) クライアント側で保存まで全部保持

ファイルをブラウザに保持し、保存ボタンで package + resources を一括作成する案。

- 問題点: 保存時に全ファイルのアップロード待ちが発生（最大 100 MB × N）、
  ページリロードで全損、パイプライン素材も公開前に得られない

### C) package.state に `draft` を追加（CKAN と同じ）— 採用

- 既存の読み取り経路（公開一覧・検索インデックス同期・集計）は
  `state = 'active'` を既定フィルタとしており、draft は追加コードなしで
  ほぼ不可視になる
- organization の `purging`（ADR-028）に続く「第3状態」の前例があり、
  遷移ガードのパターンも流用できる

## 決定

**package の `state` に `draft` を追加し（`draft` / `active` / `deleted`）、
新規作成を draft で開始、公開を明示的な状態遷移とする。**

### 1. 作成フロー

- 新規作成ウィザードは draft package を**自動作成**する。トリガーは最初の
  ファイル添付または最初の保存操作とし、ページを開いただけの空 draft の
  発生を抑える
- `name`（URL スラッグ）は `unique().notNull()` のため、draft 自動作成時は
  `untitled-<ランダム接尾辞>` 形式のプレースホルダーを生成する（nullable 化は
  nameOrId 参照・インデックスに波及するため行わない）。`name` は既存の
  更新 API で変更可能であり、draft は外部から参照されないため公開前の
  リネームにリンク切れの懸念はない。**プレースホルダーのままの公開は
  許可しない**（publish 時バリデーションで明示設定を要求。ランダムな URL の
  データセットが公開されるのを防ぐ）。プレースホルダーはランダムのため
  意味のあるスラッグを占有しない
- `ownerOrg` は DB 上 nullable（必須なのは作成 API のバリデーションのみ）
  であり、draft では**未設定を許容**する。draft の編集権限は
  `creatorUserId`（作成者）と sysadmin とし、`ownerOrg` 設定後はその組織の
  編集権限者にも開く。name と同様に**公開時に `ownerOrg` を必須**とする
  ため、公開済み package の実効制約は現行と変わらない
- draft 内の各操作は UUID（`nameOrId` 参照は UUID を受ける）で行い、
  プレースホルダー name を UI に露出させない
- draft 中のリソース追加・アップロード（3-step presigned フロー）・
  パイプライン（Fetch / Extract）は**既存フローを無変更で使う**。
  プレビュー生成・列スキーマ永続化（ADR-029 / ADR-032）も通常どおり動くため、
  公開前にプレビュー確認や AI メタデータ提案（後続 ADR）の素材が揃う

### 2. 可視性

- 公開一覧・検索は検索インデックス経由（ADR-013）。draft はインデックスに
  投入しないため自動的に不可視
- DB 直接クエリは既定 `state = 'active'` フィルタにより不可視（既存実装のまま）
- ダッシュボードは作成者（および `ownerOrg` 設定後はその組織のメンバー）に
  draft を「下書き」として表示する
- **worker の Index ステップ（ADR-021）は package の state を確認し、
  draft のコンテンツをインデックスに投入しない**（現状は state を参照して
  いないため要修正）。embedding（ADR-034）も draft では生成しない

### 3. 公開遷移

- `POST /api/v1/packages/{id}/publish` を追加。`draft` → `active` のみ許可
  （ADR-028 の遷移ガードと同型）。権限は package 更新権限と同一
- 公開時に実行する同期処理:
  1. メタデータ検索インデックス投入
  2. 全 active リソースのコンテンツインデックス投入
  3. embedding ジョブ投入
- 遷移は**一方向**とする。公開後に draft へ戻す操作は提供しない
  （非公開化は `private` フラグの領分。公開済みデータセット編集の
  リビジョン管理はスコープ外 — CKAN も持たない）

### 4. ライフサイクル

- 手動削除は下書き一覧（カード）から行う。draft は一度も公開されていない
  ため**ゴミ箱（`deleted`）を経由せず、確認ダイアログ付きで直接完全削除**
  する（既存の purge CASCADE — DB / Storage / パイプラインレコード掃除 —
  を流用。restore 対象にしない）
- 放置 draft は **worker の定期ジョブで自動パージ**する。既存の croner
  スケジューラ（ヘルスチェックと同型）に日次ジョブを追加し、最終活動
  （`package.updated` と配下 `resource.updated` の最大値）から保持期間を
  超えた draft を CASCADE で完全削除する。CKAN は draft を無期限に溜め込み、
  放置 draft の堆積が既知の運用問題になっている — アップロード済みファイル
  （最大 100 MB × N）が Storage に残り続けるため、既定で有効とする
- 保持期間は system_setting のランタイム設定 `draft-retention-days` とする
  （ADR-036 の適用例。既定 30 日、`0` で無効化。閉域網等で削除が困る運用は
  管理画面から無効化できる）
- 削除時は `UPDATE ... WHERE state = 'draft' AND <stale条件> RETURNING` で
  state を原子的に再確認してから破壊的処理に入り（ADR-028 の durable claim と
  同型。公開直後の draft を競合で消さない）、`audit_log` に記録する
- 下書き一覧には最終更新日時と削除予定日を表示し、ユーザーが GC を
  予見できるようにする
- name スラッグは draft が占有する（CKAN と同じ挙動、許容。プレースホルダー
  name はランダムであり、ユーザー設定の name も GC により無期限には
  占有されない）

### 監査項目（実装時に確認）

- ダウンロード / プレビュー URL（ADR-017）: draft リソースは編集権限者のみに制限
- sitemap、CKAN 互換 API、MCP ツール（ADR-032）が active フィルタを
  通っているか
- 組織・グループのデータセット数カウント（既に `state = 'active'` で集計
  しており影響なしの見込み）

## 結果

- アップロード・保存と公開が分離され、「リソースを揃え、メタデータを確認して
  から公開」が可能になる
- 中断・再開が自然にできる（draft が DB に残る）
- ファイル内容を見てからメタデータを書く file-first UX が成立し、
  AI メタデータ提案（後続 ADR 予定）の土台となる
- 既存デプロイへの影響: 既存 package はすべて `active` / `deleted` のため
  データ移行は不要。API クライアントは state の新しい値 `draft` に備える
  必要があるが、既定フィルタにより公開 API の応答は変わらない
