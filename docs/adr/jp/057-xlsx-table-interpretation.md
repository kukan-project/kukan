# ADR-057: Excel の表をテーブルとして解釈する（読み方の指示を確定値に持つ。自動は素直な表だけ、AI は案に限る）

## ステータス

**提案（Proposed）— 公開データでの割合（コンテキスト 5）と、規則と AI が出す案の当たり方（コンテキスト 7）は測った。正解の半分（54 枚）は人が確かめた。自動にする範囲を広げるかは、1 つの表か複数かの約束（未決事項 5）を決めてから決める**

Excel（XLSX・XLS）のシートを、Interpret ステージでテーブルとして解釈し、CSV/TSV と同じく
プレビュー Parquet を作る。以降は表プレビュー・行レベル差分（ADR-043 層 2）・OData（ADR-055）・
MCP の `/query`（ADR-032）にそのまま乗る。

どのシートのどこを表として読むかは、**読み方の指示**（シート・表の範囲・見出しの行数・列名）で
表す。解釈は読み方の指示から決定的に行う。

- **見出し 1 行と矩形のデータだけでできた「素直な表」**は、規則が読み方の指示を決め、自動で表にする
- それ以外の表（複数行の見出しを持つ統計表など）は、規則が読み方の指示の**案**を作り、
  人が確かめて確定値として保存する。確定するまで表にしない
- AI は判定しない。規則と同じ形の案を出すことと、表として読むべきでないと言うことに限る。
  案は規則で検算する。実測では AI の案のほうが規則の案よりよく当たった（コンテキスト 7）ので、
  AI を設定したサイトでは、規則の案と並べて最初から示す

正本（アップロードされた Excel のバイト列）には手を触れない。Parquet は ADR-046 の言う
「解釈」の産物である。

本 ADR は ADR-046 の残課題 5（解釈の生産者を差し替え可能な口にする）のうち、Excel の構造検出を
具体化する。ADR-053 §2 が「Excel はデータとして使えるようにならない」と明記した代償に、
別の骨格で答えるものでもある。

当初の提案は、素直な表の XLSX だけを対象にし、パーサの選定を保留し、XLS を対象外としていた。
公開データの実測（コンテキスト 5）を受けて、読み方の指示を中心に据え、XLS を対象に加え、
パーサを自前の読み取りに決めた。

## コンテキスト

### 1. いま、Excel はテーブル経路に入っていない

Interpret は `isCsvFormat` で分岐し（`apps/worker/src/pipeline/steps/interpret.ts`）、
XLSX/XLS はテーブルとして解釈されない。その結果、

| 経路                 | CSV/TSV                        | XLSX/XLS                            |
| -------------------- | ------------------------------ | ----------------------------------- |
| プレビュー           | 表（Range 配信 + DuckDB-WASM） | 原本の描画と抽出テキスト（ADR-065） |
| 列のスキーマ         | 版ごとに記録                   | なし                                |
| 行レベル差分（層 2） | あり（主キー指定で変更行追跡） | なし                                |
| OData / MCP `/query` | あり                           | なし                                |
| 全文索引             | 表のテキスト                   | シートの行のテキスト                |
| AI 抄録（ADR-053）   | 表の材料                       | 原本をそのまま渡す                  |

自治体のオープンデータでは、同じ表が Excel だけで公開されていることが少なくない。
それらはカタログ上「何のデータか」は分かっても、「データとして触れる」ことができない。

### 2. 表かどうかは、フォーマットではなく中身で決まる

CSV は形式そのものが表である。Excel はそうではない。同じ拡張子の中に、

- 見出し 1 行と矩形のデータだけの、素直な表
- 表の上にタイトルや単位の注記があり、下に出典や注が付く表
- 多段の見出し、結合セル、途中の小計行を持つ統計表
- 帳票・申請様式・図表など、そもそも表でないもの

が混在する。したがって「Excel なら表」とはできず、**版ごとの解釈結果として「表だった /
表でなかった（その理由）」を記録する**必要がある。これは CSV が既に持つ仕組みと同じである —
`resource_version.schema` が空のスキーマ（`NO_TABLE`）と `reason`（`no-columns` /
`too-many-columns` など）で「解釈したが表は無かった」を表している。

### 3. 構造の誤推定は、UX ではなくデータ完全性の問題

ADR-053 §2 はこう書いた。**ヘッダー行の判定が再実行で 1 行ずれれば、行レベル差分は全行が
変更されたと報告する。** 範囲を誤って読めば、注記の行がデータに混ざり、OData で配られ、
MCP の集計に入る。

誤って表にした場合の害は、表にし損ねた場合の害よりずっと大きい。表にし損ねても、今の扱い
（原本の描画とテキスト索引）が続くだけだからである。自動の判定は**迷ったら表とみなさない**側に
倒さなければならない。

### 4. 既にある部品

| 部品                   | 実体                                                           | 本 ADR での使い道                                |
| ---------------------- | -------------------------------------------------------------- | ------------------------------------------------ |
| XLSX の読み取り        | `interpret/document/document-text.ts`（ZIP と XML の逐次読み） | セルの格子まで読むよう広げる（決定 8）           |
| XLS の読み取り         | `interpret/document/legacy/xls.ts`（BIFF のレコード）          | 同上                                             |
| CSV の解釈             | `interpret/table/csv.ts` の `interpretCsv`（DuckDB sniffer）   | 表の範囲を CSV にしてから渡す（決定 6）          |
| タイトル行の検出       | `interpret/table/csv-title-rows.ts` の `countTitleRows`        | 表の上の 1 セルだけの行を落とす                  |
| 注記行の除去           | `interpret/table/csv.ts` の `trimFooter`                       | 表の下の出典・注を落とす                         |
| 表が無かったことの記録 | `NO_TABLE` + `reason`                                          | 規則に外れた理由を残す                           |
| 人が確定した列の設定   | `resource.column_settings`（主キー、確定型）                   | 確定した読み方の指示を置く（決定 2）             |
| 版への凍結             | 版は作成時の設定を凍結する（仕様書 §6.7）                      | 確定した読み方の指示も版に凍結する               |
| 版同一性の入力         | `sameVersionIdentity`                                          | 読み方の指示の確定は版を作る（確定型と同じ扱い） |

Excel の読み取りは、文書テキストの抽出のために既に自前で持っている。今はセルの値だけを読み、
空でないセルを左から詰めた行のテキストにしている。セルの列位置、結合、書式、非表示は読んでいない。

### 5. 公開されている行政の Excel の実測（2026-11）

国のデータポータル、都道府県と市区町村のカタログ、統計の公開サイトなど 27 のサイトから、
XLSX を 120 本（790 シート）集め、構造を機械的に測って類型に分けた。類型は自動で分け、
60 シートを目で確かめた（52 枚が当たり）。割合には ±5 ポイントほどの誤差がある。

| 類型                                               | ブックの割合 |
| -------------------------------------------------- | ------------ |
| A 素直な一覧表（見出し 1 行、矩形）                | 25%          |
| B 表題・注記付きの一覧表（上下を除けば A）         | 8%           |
| C 階層見出しの統計表（複数行の見出し、表側の階層） | 55%          |
| D 1 シートに複数の表                               | 8%           |
| E 様式・帳票、F 文書・表紙・目次                   | 4%           |

読み取れたこと。

- **当初の「素直な表」の条件に通るブックは 25% だった。** 出どころで大きく割れる。国のデータ
  ポータルでは 66 本中 2 本、自治体のカタログの 1 つでは 21 本中 18 本。後者のうち 15 本は同じ
  ひな形で、それを除くと全体で 14% になる
- **外れる理由は「複数行の見出し」と「シートが複数」が大半だった。** 単一シートで外れた 56 本の
  うち 38 本が複数行の見出し、シートが複数のブックは 34 本（28%）。「表の上に表題の行が数行ある
  だけ」は少なく、B まで広げても 33% にとどまる
- **複数シートの半分は、同じ形のシートが年度や地域で並ぶ**（全体の 14%）
- **計算結果を持たない数式は 0 件だった**
- **表のシートの 12% は、A 列が空で B 列から始まる**
- **Excel に設定された構造は、見出しの終わりの候補になる。** ウィンドウ枠の固定はブックの 24%、
  オートフィルターは 18%、印刷タイトルは 18% にある。枠の固定の行は、推定した見出しの終わりと
  71% で一致した。ただし付いているのは主に C で、確定に使える精度ではない。Excel のテーブル
  （ListObject）は 3 本だけ、印刷範囲は使用範囲の全体を覆うものがほとんどで、表の範囲の
  手がかりにならない
- **XLS は少なくない。** 国のデータポータルで XLS を持つデータセットは 4,727、XLSX は 1,839。
  自治体のカタログでは XLSX のほうが多い所もある。ただしカタログで XLS と書かれたリソースの
  3 割は、中身が XLSX だった。この件数は XLS を多めに見せている

標本は府省の数をそろえて引いたので、件数の多い府省は実際より軽く入っている。県の統計書のような
大きな統計表もほとんど入っていない。

続けて XLS を 99 本集め、同じ方法で測った。**XLS は XLSX より崩れている。**

| ブック単位           | XLSX（120 本） | XLS（99 本） |
| -------------------- | -------------- | ------------ |
| 素直な表の条件に通る | 25%            | 2%           |
| C 階層見出しの統計表 | 55%            | 75%          |
| 結合セルがある       | 62%            | 83%          |
| 空でないシートが複数 | 28%            | 43%          |

XLS を対象にしても、自動で表になるものはほとんど増えない。増えるのは、人が確定する対象である。
XLS は古い公開物だけではなく、最後の保存が 2020 年以降のものが 38 本あった。

### 6. 参照できる規則と先行研究

- デジタル庁は「行政データにおける機械可読性に関するルール」（2026 年 3 月）と、その違反を
  規則で点検するツールを公開している。ツールは、非空セルのかたまりから表の範囲・見出しの行・
  表側の列を推定する。複数行の見出し、空行で分かれた表、横に並んだ表に弱いことが文書に書かれて
  いる。合計の行や値なしの記号の語彙は、規則を作るときの出発点になる。同じルールは、項目名が
  複数行に分かれているとき、各列を見分けるにはそれらの行を組み合わせた完全な項目名が要る、と
  述べている（L2-03）
- このルールは、データを作る側が守る基準である。読む側の判定の基準ではない。違反していても
  読める表があり（表題の行は L3-01 に当たるが、落とせば読める）、表の範囲や見出しの行数は
  ルールからは決まらない。使えるのは、素直な表の条件の裏付けと、表にしなかった理由を伝える
  言葉としてである（決定 3・5）
- 総務省「統計表における機械判読可能なデータの表記方法の統一ルール」（2020 年 12 月）は、
  統計表の Excel について同じ種類の妨げ（セルの結合、1 シートに複数の表、データの分断など）を
  挙げている
- LLM に表の範囲を答えさせる研究（SpreadsheetLLM、2024 年）では、境界が完全に一致する割合を
  表す F1 が、微調整なしで 0.41、微調整して 0.79 だった。シートを圧縮せずに渡すと 0.15 に落ち、
  塗りや罫線をテキストで足すと悪化した。今のモデルでの値は確かめていない

### 7. スパイクの結果（2026-11）

コンテキスト 5 の標本から 112 枚のシート（XLSX 70、XLS 42）を類型ごとに抜き取り、読み方の指示
（決定 2）の正解を付けた。表だったのは 110 枚である。規則の試作と、AI に同じ形の案を出させた
結果を、この正解と突き合わせた。「一致」は、範囲の 4 辺と見出しの行数がすべて同じことを言う。

**正解は AI が画面の表示だけを見て付けたもので、人は確かめていない。** 規則は正解の半分で
調整した。AI の案は、同じ系統のモデルが付けた正解と比べている。どちらの数字も、人が付けた
正解で確かめるまでは高めに出ていると見る。その後、54 枚を人が確かめた（下の「人が確かめた結果」）。
すぐ下の表は、確かめる前の正解に対する数字である。

| 一致した枚数（110 枚）     | 規則      | AI（小さいモデル） | AI（大きいモデル） |
| -------------------------- | --------- | ------------------ | ------------------ |
| 全体                       | 86（78%） | 99（90%）          | 100（91%）         |
| XLSX（70）/ XLS（40）      | 59 / 27   | 63 / 36            | 63 / 37            |
| A 素直な一覧表（15）       | 15        | 15                 | 15                 |
| B 表題・注記付き（19）     | 17        | 18                 | 19                 |
| C 階層見出しの統計表（56） | 43        | 51                 | 51                 |
| D 複数の表（20）           | 11        | 15                 | 15                 |
| 見出しの帯だけの一致       | 96（87%） | 108（98%）         | 107（97%）         |

規則について。

- 調整に使っていない半分では 43 枚中 33 枚（77%）が一致した
- 手がかりを単独で使ったとき、データの最初の行が当たった割合は、行の型の並び 95%、印刷タイトル
  89%、ウィンドウ枠の固定 78%、オートフィルター 67%、見出しの帯の結合の形 55% だった。
  印刷タイトルは XLS でも 9 枚中 8 枚で当たった。オートフィルターの最終行は 33% しか当たらない
- 行の型の並びと別の手がかりが一致したシートは 48 枚（44%、C では 57%）あり、データの最初の行は
  48 枚すべてで当たった。範囲の全体まで一致したのは 42 枚である。外れは表の下端・右端
  （複数の表、折り返し）と見出しの上端だった
- ウィンドウ枠の固定と印刷タイトルが一致しても、確かめにはならない。同じ作成者の設定である

AI について。

- 渡したのは、シートの先頭 35 行・末尾 10 行・途中の疎な行（先頭 14 列と末尾 2 列、セルは
  12 文字まで）、行ごとの空でないセルの数、結合の範囲、Excel の設定である。1 回の呼び出しで
  答えさせた
- **モデルの大きさによる差はほとんど無かった。** 2 つのモデルは 110 枚中 100 枚で同じ答えを
  出した。小さいモデルで推論の量を変えても、一致は 97 枚（少なく）・99 枚（既定）・100 枚（多く）で、
  かかる時間だけが 1.7 倍に開いた
- 格子の全体から数えた事実（列ごとの空でないセルの数と行の範囲、空行で分かれたかたまり、
  見せていない列の見出し）を足して渡しても、一致は 99 枚から 100 枚で、右端と下端の当たり方は
  変わらなかった。残る誤りは、見えていないことよりも、どこまでを 1 つの表と読むかの違いである
- AI の誤りは右端と下端に寄っている。渡したテキストで見えない所である。28 枚について、モデルが
  必要な行と列を自分で取りに行く形に変えると、一致は大きいモデルで 24 枚から 27 枚に、
  小さいモデルで 24 枚から 25 枚に増えた
- **規則と 2 つのモデルの答えがすべて同じだったのは 78 枚（71%）で、うち 77 枚が正解と一致した。**
  2 つのモデルの答えが割れた 10 枚では、少なくとも一方が誤りだった
- どのモデルも外した 6 枚のうち 4 枚は、正解を付けるときにも迷ったものだった。「1 つの表か、
  複数の表か」「見出しの無い右端の列を含めるか」という、約束の決め方の問題である
- 小さい表（1,300 セル以下の 8 枚）を、表そのものの CSV として書かせると、書き出した行の値は
  すべて元のセルと一致した（2 つのモデルで 661 行、6,189 個の値）。ただし標本のシートは平均
  5,600 セルあり、1 万行を超えるものもある。その大きさは出力しきれない

人が確かめた結果。

- 1 人が、2 回に分けて 54 枚を確かめた。1 回目は、案が割れた 35 枚と、規則と 2 つのモデルの
  答えが同じだった 8 枚を、値と結合だけを出した画面で見た。2 回目は、かたまりが複数あるのに
  確かめていなかった 11 枚と、1 回目の 5 枚を、罫線を線の種類ごとに描き分け、結合セルを結合した
  形で出した画面で見た
- AI が付けた正解は、1 回目の 43 枚中 8 枚、2 回目の 11 枚中 1 枚で人の答えと違った。1 回目の
  8 枚のうち 5 枚は規則の案が、2 枚は小さいモデルの案が人と同じだった。表でないとしていた
  2 枚も、人は表と読んだ
- **人が判断するには罫線が要る。** 罫線を出して見直した 5 枚のうち、2 枚で答えが変わり、1 枚は
  「決められない」になった。確かめた人は、値と結合だけの画面では決められないシートがあり、
  人の判定に罫線は必須だ、と述べた
- 人の答えに直し、決められなかった 1 枚を除くと、111 枚での一致は、規則 89 枚（80%）、
  小さいモデル 97 枚（87%）、大きいモデル 96 枚（86%）になった。規則の案と小さいモデルの案が
  同じだったのは 82 枚で、うち 79 枚が正解と一致した。規則と 2 つのモデルの答えがすべて同じ
  だった 78 枚では、76 枚である。残りの 58 枚は、AI が付けた正解のままである
- 人の答えは、次の約束に沿っていた。自分の表題や名前を持つかたまり（審級ごと、表番号ごと、
  区分ごとの表）は、列が同じでも別の表で、最初の表だけを読む。同じ表の中の行の集まり
  （都道府県のあとに指定都市）、ページごとに繰り返す見出し、ページの切れ目の注記は、1 つの表の
  中である。印刷のために列を横に折り返したものは、全体を 1 つの表と読む。行見出しを共有して
  左右に並ぶ別々の表（貸借対照表）は、左だけを読む。行が右の段へ続く段組は、答えが割れた
  （3 枚のうち 2 枚は最初の段だけ、1 枚は全体）
- **折り返しと段組には、正解が無い。** 確かめた人は、ここまで来ると人でも判断が付かない、と
  述べた。全体を選べば行見出しの列や見出しが繰り返し入り、左だけを選べば残りの行や列が落ちる。
  範囲と見出しの行数だけでは、どう選んでも正しい表にならない
- **罫線は、範囲を機械的に決める手がかりにはならなかった。** 罫線のあるセルを囲む矩形が人の
  答えと 4 辺とも一致したのは、1 回目の 43 枚中 9 枚だった（左 36、右 29、上 25、下 18）。
  表題や注記にも線が引かれ、別の表にも罫線がある。罫線の位置と線の種類をテキストにして
  小さいモデルに渡すと、一致は 97 枚から 86 枚に減った。上端が表題の行へ、下端が注記の行へ
  ずれた。コンテキスト 6 の先行研究と同じ向きである
- 「同じ列で縦に続くかたまりは 1 つの表」と指示に書いて小さいモデルに答えさせると、一致は
  97 枚から 91 枚に減った。人は、名前を持つかたまりを別の表と読んでいた

形で分けた結果。確かめた人のメモと正解に付いたメモから、矩形 1 つでは表せない形（見出しや注記が
範囲の途中にもう一度出る、列を横に折り返す、段組）のシートに印を付けた。111 枚のうち 11 枚で
ある。印は人が確かめていない。

- 表せる形の 100 枚では、一致は規則 86 枚、小さいモデル 89 枚、大きいモデル 91 枚だった。
  規則の案と小さいモデルの案が同じだったのは 78 枚で、うち 77 枚が正解と一致した
- 「素直な 1 つの表ではない」シート（表が複数あるものと、表せない形。27 枚）を見分けられるかを
  測った。規則（見出しの行が、下か右にもう一度出てくる）は 17 枚を挙げ、誤りは無かった。
  小さいモデルに形を答えさせると 27 枚を挙げ、24 枚が当たり、3 枚は素直な表を誤って挙げた。
  どちらも見落としたのは 3 枚で、うち 2 枚は行見出しの列を右に書き直した横の折り返しである
- **規則もモデルも挙げなかった 84 枚のうち、規則の案と小さいモデルの案が同じだったのは 70 枚で、
  70 枚すべてが正解と一致した。** 全体の 63% にあたる

そのほか。

- **非表示の行・列は、ほぼ表の一部だった。** 持っていた 19 本のうち、中身のある 11 本を見ると、
  10 本は表の一部（過去の時点、コードの列、内訳）で、1 本は検算の行だった
- **複数行の見出しをつないだ列名が、そのままで重複しなかったのは 36 枚中 13 枚だった。**
  重複の 9 割は、子を持たない 1 つの結合が複数の列にまたがる形である
- セルの格子の読み取り（決定 8）は、XLSX 120 本（790 シート、443 万セル）を 7.2 秒で読んだ

## 検討した選択肢

### 判定を誰が行うか

#### A) AI に判定させる

原本（または左上 N×M のセルと結合マップ）をモデルに渡し、「表か、表ならどの範囲か、見出しは
何行か」を答えさせる。崩れた表にも対応できるので、表として拾える割合は最も高い。

**採らない。** 同じ入力から同じ答えが出る保証がなく、パイプラインの決定性（ADR-046）を壊す。
もっともらしい誤りを返したとき、それを機械的に検出する手段がない。閉域網（`AI_TYPE=none`）
では機能ごと使えなくなる。そして素直な表の判定は、セルの格子を見れば規則で確かめられる —
AI に委ねても精度は上がらず、コストと非決定性だけが増える（実測でも、素直な一覧表は規則も
AI も 15 枚すべて一致した）。素直でない表では AI の案のほうがよく当たったが、それでも 10 枚に
1 枚は外した（コンテキスト 7）。外れた案がそのまま表になれば、害は大きい（コンテキスト 3）。
AI だけに任せられる精度ではない。

#### B) 規則だけで判定する

結合セルの有無・見出しの行数・矩形性・列の型の揃い方を、セルの格子から機械的に確かめる。
決定的で、理由を説明でき、閉域網でも同じに動く。

**素直な表には十分だが、多数派を救えない。** 実測では、規則だけで自動にできるのは 25〜33% で、
国のデータではほとんど通らない。

#### C) 規則が案を作り、素直な表だけ自動にし、ほかは人が確定する。AI は案を足す — 採用

- 自動で表にするのは、素直な表の条件を通ったものだけ（B と同じ）
- それ以外は、規則が読み方の指示の案を作り、人が確かめて確定する
- AI は、規則と同じ形の案を出す。案は規則で**検算**する
- 確定したものを確定値として保存し、以後はその値で決定的に解釈する

推論ではなく決定を残す形なので、再実行でぶれない。ADR-040 の「提案であって決定ではない」、
ADR-053 §2 の「提案 → 人の確認 → 確定値としての永続化」と同じ骨格である。
閉域網では AI の案が無いだけで、規則の案と人が範囲を指定する経路は残る。

### 複数行の見出しを自動で読むか

実測の多数派（C）を自動で表にできれば、効果は最も大きい。**今は自動にしない。** 見出しの
行数を 1 行誤れば、全行がずれる（コンテキスト 3）。

広げ方の候補は 2 つ見えている（コンテキスト 7）。

- 規則の中で、行の型の並びと別の手がかりが一致したとき。シートの 44% に当たり、データの最初の
  行はすべて当たった。範囲の全体は 8 枚に 1 枚が外れた
- 規則の案と AI の案が一致したとき。シートの 71% に当たり、99% が正解と一致した。AI を
  設定したサイトに限られる

どちらも、正解を AI が付けた 110 枚での数字である。人が付けた正解で確かめ、規則の案と人の確定が
一致した割合も記録したうえで、後で判断する。それまでは、一致した案を「確からしい案」として
示すにとどめる。

### Excel を読むパーサ

判定には**セルの位置と結合セルの情報**が要る。変換には値と型が要る。

| 候補                             | 結合セル     | 備考                                                                         |
| -------------------------------- | ------------ | ---------------------------------------------------------------------------- |
| 自前の読み取りを広げる           | 足せば取れる | 逐次読みと上限は既にある。XLS も読める。依存は増えない                       |
| DuckDB excel 拡張（`read_xlsx`） | 取れない     | 範囲が決まった後の読み取りにしか使えない。XLS は読めない                     |
| exceljs                          | 取れる       | XLS は読めない                                                               |
| SheetJS（xlsx）                  | 取れる       | XLS も読める。npm レジストリ上の版は古く、配布は自前 CDN（供給経路が別）     |
| ibisOffice（ADR-065）            | 取れない     | 同梱の WASM は描画専用で、セルや結合を取り出す口が無い。Node.js では動かない |

**自前の読み取りを広げる**（決定 8）。当初この選定を保留したのは、Excel を読む部品が
無かったからである。その後、文書テキストの抽出のために XLSX と XLS の読み取りを自前で持った。
足すのは同じ枠の中の属性の読み取りで、メモリの使い方も、ZIP の展開量などの上限も変わらない。

## 決定（提案）

### 1. 正本は Excel のまま。Parquet は解釈の産物

Excel を CSV に変換して正本を差し替えることはしない。表として解釈できた版にだけ、プレビュー
Parquet とスキーマが付く。解釈の規則を後から変えても、正本は変わらず、再解釈で追従できる。

### 2. 読み方の指示

どこを表として読むかを、次の値で表す。

| 項目         | 内容                                                    |
| ------------ | ------------------------------------------------------- |
| シート       | シートの名前                                            |
| 表の範囲     | 見出しを含む矩形（A1 形式）。表題と注記は範囲の外に置く |
| 見出しの行数 | 範囲の先頭から何行が見出しか                            |
| 列名         | 見出しから作った列名を置き換える名前（任意）            |

規則も、AI も、人も、この同じ形を出す。違いは誰が出したかだけである。

- 素直な表（決定 3）では、規則が出した指示をそのまま使う。保存しない（規則から毎回決まる）
- それ以外では、人が確定した指示を `resource.column_settings` に置く（主キー・確定型と同じ場所。
  人だけが書き、worker は書かない）。以後の版は確定した指示で解釈する。版は作成時の指示を
  凍結する。指示の確定・変更は版同一性の入力に加わり、新しい版を作る（確定型と同じ扱い、
  仕様書 §6.5）
- 確定した指示が新しい版の内容に合わなくなったとき（範囲の中に見出しが無い、列数が変わったなど）
  の扱いは、実装仕様書で決める。型の変化の取り込み後の確認（仕様書 §8）と同じ考え方に寄せる

**読み方の指示は、表の形を変えない。** 範囲の中のセルを、書かれた行と列のまま読む（決定 7）。

### 3. 自動で表にする「素直な表」の条件

次をすべて満たすとき、規則が読み方の指示を決め、そのシートを表として読む。

1. **表とみなせるシートが 1 枚だけ**である。ほかのシートは、空か、明らかに表でない
   （セルがごく少ない表紙、グラフだけのシートなど）。1 リソース = 1 表という版と Lake の前提を
   崩さない
2. **データ範囲に結合セルが無い**。範囲の外（上のタイトル）の結合は、タイトル行として
   落とせるなら許す
3. **見出しが 1 行**で、見出しのセルがすべて埋まり、重複しない
4. **データが矩形**である — 見出しの列数の外に値が無い
5. タイトル行と注記行を、CSV と同じ考え方の規則（`countTitleRows` / `trimFooter`）で範囲の外に
   置ける。規則は範囲を決めるところで当て、CSV の解釈には持ち込まない（決定 6）

先頭の空の行と空の列は読み飛ばす（表が A1 から始まることを求めない）。条件の細部（空行の扱い、
「明らかに表でない」のしきい値）は実装仕様書で決める。

これらの条件は、デジタル庁「行政データにおける機械可読性に関するルール」（コンテキスト 6）の
項目と重なる。条件を満たすシートは、次の項目を満たしている。

| 条件                               | ルールの項目                                                             |
| ---------------------------------- | ------------------------------------------------------------------------ |
| 1 シートに表が 1 つ                | L1-02 １シート（ファイル）に複数の表が掲載されていないか                 |
| データが矩形で、範囲の外に値が無い | L1-03 データが分断されていないか、L1-04 データ本体と無関係な情報がないか |
| 見出しのセルがすべて埋まる         | L1-05 すべての列に意味が推測できる項目名が存在するか                     |
| データ範囲に結合セルが無い         | L1-12 セルの結合をしていないか                                           |
| 見出しが 1 行で、重複しない        | L2-03 各列が一意に識別可能な項目名を持っているか                         |

ルールが求めていても、条件にしないものがある。表題の行（L3-01）は落として読む。数式（L2-06）は
計算結果があれば読む（決定 6）。

### 4. 素直でない表は、規則が案を作り、人が確定する

条件に外れたシートについて、規則は読み方の指示の案を作る。案は表にせず、編集者に見せる。

案を作る手がかり（実測で強かった順、コンテキスト 7）。

1. 行の型の並び — 文字列だけの行から、数値や日付を含む行への切り替わり。これを軸にする
2. 作成者が Excel に設定した構造 — 印刷タイトル、ウィンドウ枠の固定、Excel のテーブル。
   オートフィルターは左右の端にだけ使い、最終行には使わない
3. 見出しの帯の結合の形 — 横の結合の下に複数の子があれば階層、全幅の結合は表題。単独では弱く、
   1 の確かめに使う
4. 合計・注記・単位の語（「計」「注」「資料」「（単位：…）」など）

行の型の並びと別の手がかりが一致した案は、確からしい案として示す。AI を設定したサイトでは、
AI の案（決定 11）も最初から並べ、規則の案と一致したかどうかを示す。

複数行の見出しは、親と子の見出しを上から順につないで 1 つの列名にする。結合セルの値は、
結合の範囲のすべての列に渡す。つないだ列名が重複したら、番号を付けて一意にする（子を持たない
結合が複数の列にまたがる形が、重複の大半である）。つないだ列名は案であり、人が直せる
（読み方の指示の「列名」）。

案と、人が確定した値が一致したかどうかを記録する。一致の割合は、自動にする範囲を広げるか
どうかの材料になる（検討した選択肢「複数行の見出しを自動で読むか」）。

### 5. 表にしなかったら今の扱いのまま、理由を記録する

自動で表にせず、確定した指示も無い版は `NO_TABLE` とし、`reason` に外れた条件を記録する
（例: `merged-cells`、`multiple-sheets`、`multi-row-header`、`multiple-tables`、
`not-rectangular`、`form`）。プレビューは原本の描画のまま、全文索引も今どおり。
**表にし損ねることは失敗ではなく、表でなかったという解釈結果**である。

管理画面は、`reason` を「表として読まなかった理由」として編集者に示す。`reason` は国を問わない
言葉で持つ。日本向けの表示では、対応する項目があるものに、デジタル庁のルールの ID を添える
（`merged-cells` に L1-12、`multiple-tables` に L1-02、`multi-row-header` に L2-03、
`not-rectangular` に L1-03・L1-04）。直し方がルールの文書に書かれているので、データを作る側が
直す手がかりになる。対応は表示の層に置き、判定の規則には入れない。

### 6. 変換は CSV を経由して既存の CSV 解釈に渡す

表の範囲を、UTF-8 の中間 CSV に書き出して `interpretCsv` に渡す。

- 中間 CSV の 1 行目は列名である。見出しの帯からつないだ列名（決定 4）か、人が直した列名を
  書く。見出しの帯の行そのものは書き出さない。2 行目以降が、データの最初の行から範囲の最後の
  行までである
- **どこが表かは、読み方の指示がすでに決めている。CSV の解釈に、構造をもう一度推定させない。**
  表題の行の走査をせず（読み飛ばす行は 0）、1 行目をヘッダーと明示し、末尾の注記の推定を
  しない。末尾の注記の推定は、値の少ない末尾の行を注記とみなすので、幅の広い表の「合計」と
  金額だけの行を落としうる。`interpretCsv` に、この推定を止める指定を足す

- セルは**表示書式ではなく生の値**で書く（`1,234` ではなく `1234`）。数値書式を当てた表示文字列は
  作らない
- 日付として書式設定されたセルは ISO 8601 で書く（シリアル値のまま渡さない。1900 年
  うるう年の扱いと 1904 年基準もここで吸収する）。和暦の書式も、値は日付なので同じに書く
- 数式は**キャッシュされた計算結果**を書く。計算結果を持たない数式が範囲にあれば、表と
  みなさない（`reason: 'uncached-formulas'`）
- 結合セルは、見出しでは範囲のすべての列に値を渡し（決定 4）、データでは左上のセルだけが値を持つ
- 非表示の行と列は、範囲の中にあれば含める。実測では、ほぼ表の一部だった（コンテキスト 7）。
  含めたくない列は、人が範囲で外す

CSV を経由する理由は、型推定・確定型の適用（`read_csv` の `types` 宣言、
仕様書 §6.3）・値なしの印・文字列表記の数値の扱いが、すべて CSV の解釈に 1 か所で実装されて
いるからである。Excel 専用の経路を作ると、これらが 2 系統に分かれる。

代償として、セルが持つ型情報（文字列として入力された `00123` など）は sniffer に渡らず、
数値と推定され得る。これは CSV でも起きることで、確定型で直す。セルの型を `types` の初期値として
渡すかどうかは実装仕様書で判断する。

中間 CSV は解釈の作業ファイルであり、保存しない。

### 7. やらないこと

- **表の形を変える変換をしない。** 横持ちを縦持ちにする、省略された値を上から埋める、
  区分の行を次の行の属性として引き継ぐ、2 行で 1 件の行をまとめる、はどれも行わない。
  意味の解釈が要り、誤れば集計が変わる。作成者が書いた行と列のまま読む
- **小計・合計の行を落とさない。** 範囲の中の行は 1 つも落とさない。表の下の注記は範囲の外に
  置くもので、CSV の解釈では落とさない（決定 6）
- **様式・帳票・方眼紙・文書は読まない。** 理由を記録するだけにする
- **1 つのリソースから複数の表を出さない。** 版と Lake の前提を変える別の判断になる。
  1 シートに複数の表があるとき、人が 1 つの範囲を選んで確定することはできる。
  将来は、正本を 1 つの Excel のまま、複数の表をその派生物として 1 つのリソースに持たせる
  ことを考えている。スキーマ・列の設定・差分・OData・検索の単位が表ごとになり、版をまたいで
  どの表が同じ表かを決める必要があるので、別の ADR で扱う。そのとき確定値の形を変えずに済む
  よう、読み方の指示は表の一覧の形で保存し（当面は 1 件）、表に名前を持たせる。シートに
  ほかの表があることは記録して編集者に示す

### 8. Excel の読み取りは自前のものを広げ、XLS も対象にする

今の読み取りを、行のテキストだけでなく、位置付きのセルの格子も出せるようにする。足すもの。

- セルの列位置と型
- 結合セルの範囲
- 数値書式のうち、日付かどうか・文字列書式かどうかの区別と、日付の基準（1900 / 1904）
- 非表示のシート・行・列
- ウィンドウ枠の固定、オートフィルターの範囲、印刷タイトル、Excel のテーブル

太字・塗り・列幅は、スパイクで案の当たり方に効くと分かったときに足す。罫線は、線の位置と種類を読む。
確定の画面で人が判断するのに要るためで（決定 10）、規則の手がかりにも AI への入力にも使わない
（コンテキスト 7）。

XLS も同じ格子を出す。当初 XLS を対象外にした理由は、読めるパーサが限られることと、公開データ
での比率が下がっているという見込みだった。どちらも今は当たらない（コンテキスト 4・5）。
印刷タイトルは XLS でも読む（XLS の 3 割にあり、よく当たる）。XLS では Excel のテーブルの
読み取りを後回しにしてよい。

全文索引のための行のテキストは、今のまま変えない。

### 9. 表かどうかは、フォーマットではなく版のスキーマで分岐する

今は表プレビュー・索引・AI 抄録・提案の材料（`suggest/materials.ts`）が `isCsvFormat` で
分岐している。Excel は版ごとに表だったりそうでなかったりするので、**Excel については
「版にスキーマがあるか」で分岐する**必要がある。

- プレビュー: スキーマがあれば表、無ければ原本の描画（両方を切り替えられるようにするかは
  UI の判断）
- 全文索引: 今の行のテキストのまま変えない
- AI 抄録: スキーマがあれば表の材料に寄せられる（ADR-053 §3「原本を渡すのは、そうしないと
  中身が取れないときだけ」）。寄せるかどうかは別途判断する

### 10. 確定の画面

読み方の指示は、管理画面の「表の設定」タブ（ADR-072）で確定する。主キー・確定型と同じ下書きに
入り、同じ適用で 1 つの版になる。

範囲は、worker が読んだセルの格子（値・結合・罫線）を簡素な表で出し、その上で選ぶ。規則や AI の案は
初期値として枠で示す。原本の描画（ADR-065）は並べて見せるだけにする。原本の描画の上で範囲を
選ぶには、描画の部品が選択範囲を外へ知らせる口を持つ必要があり、今は無い。

値と結合だけの表では、人は判断できない（コンテキスト 7）。簡素な表には、罫線を元のファイルの
線の種類（細・中・太・二重・極細・点線・破線）で描き分けて引き、結合セルは結合した形で出す。
太さの違う線を同じ線で出すと、区切りを読み違える。セルを選ぶと番地と結合の範囲が分かり、
選んだ範囲をそのまま読み方の指示の範囲にできる。この形の画面で、人は 16 枚のうち 15 枚を
決められた。線の色・塗り・太字・列幅は、要ると分かったときに足す。

### 11. AI の案

AI を設定したサイトでは、素直な表の条件に外れたシートについて、AI が読み方の指示の案を出す。
規則の案と並べて編集者に示す。案を出すだけで、表にはしない。

- 入力: シートの先頭と末尾の数十行・途中の疎な行を、行番号と列の文字を付けたテキストで渡す。
  行ごとの空でないセルの数、結合の範囲、Excel の設定（枠の固定、印刷タイトルなど）、格子の全体から数えた事実（列ごとの空でないセルの数、
  空行で分かれたかたまり）を添える。規則の案そのものは渡さない（渡すと、規則の案と一致したことが
  確かめにならなくなる）。
  原本全体は渡さない。1 シートにつき 1 回の呼び出しで答えさせる
- 出力: 決まった形の JSON だけを返させる。値は生成させない

  | 項目          | 内容                                                        |
  | ------------- | ----------------------------------------------------------- |
  | `kind`        | `table` / `multiple-tables` / `form` / `document` / `other` |
  | `range`       | 表の範囲（A1 形式）。表でなければ `null`                    |
  | `headerRows`  | 見出しの行数                                                |
  | `columnNames` | 列名の案（任意。範囲の列数と同じ長さ）                      |

  `multiple-tables` のとき、`range` は最初の表（上、同じ高さなら左）を指す

- 形の確かめ: 範囲が A1 形式で、シートの使用範囲に収まり、見出しの行数が範囲の行数より小さく、
  列名の数が列数と合うこと。合わない答えは捨てる
- 検算: 案の範囲に、列の型の揃い方と、範囲のすぐ外に同じ形の行や列が続いていないかを当てる。
  通らない案は見せない
- 確定: 規則の案と同じく、人が確かめて確定する

モデルは小さいもので足り、推論の量も少なくてよい（コンテキスト 7）。格子の全体から数えた事実を
添えるのは、見えていない列や行があることをモデルに伝えるためで、当たり方を上げる効果は
確かめられていない。罫線は渡さない。渡すと当たりが減った。モデルに行と列を何度も取りに行かせる形は、当たりが増えた（28 枚で 24 枚から 27 枚）。続きの部分の
中身を読んで、同じ表かどうかを判断できるからだと考えられる。呼び出しが何往復にもなるので、
最初の案には使わない。規則の案と AI の案が割れたシートに限って読み直させる、という 2 段目の
使い方を候補に残す（未決事項 1）。

表そのものを AI に書かせることはしない。読み方の指示が決まれば、値は決定的に写せる。
大きい表は出力しきれず、同じ入力から同じ結果が出る保証も無い。

同じデータが CSV と Excel の両方で公開されているものを集めれば、CSV を正解にして、評価を
人の手を借りずに広げられる。

## 段階

| 段階     | 内容                                                                                                          | 前提     |
| -------- | ------------------------------------------------------------------------------------------------------------- | -------- |
| Step 0   | 公開データで類型の割合を測る — **済み**（コンテキスト 5）                                                     | なし     |
| スパイク | 読み取りをセルの格子まで広げ、標本（XLS を含む）で規則と AI の案の当たり方を測る — **済み**（コンテキスト 7） | Step 0   |
| Step 1   | 読み取りの拡張と、素直な表の自動の解釈（決定 1〜3・5・6・8・9）                                               | スパイク |
| Step 2   | 規則の案と、人が読み方の指示を確定する画面、確定値の適用（決定 4・10）                                        | Step 1   |
| Step 3   | AI の案と検算（決定 11）                                                                                      | Step 2   |

同じ形のシートを縦に積んで 1 つの表にすること（シートの名前が列になる）は、読み方の指示の
項目として後から足せる。Step 2 の後に、使われ方を見て判断する。

## 影響

- `apps/worker/src/pipeline/steps/interpret.ts` に Excel の分岐が加わる。依存は増えない
- Excel の読み取り（`document-text.ts`、`legacy/xls.ts`）が、行のテキストとセルの格子の 2 通りを
  出すようになる
- `resource_version` の `reason` に Excel 由来の値が加わる
- 表プレビュー・提案の材料など、`isCsvFormat` で分岐している箇所のうち Excel を扱うものは、
  版のスキーマで分岐するよう改める
- Lake・OData・MCP は Parquet とスキーマを見るので、変更は要らない見込み
- 既存の Excel の版は、再解釈で新しい解釈を得る。正本は変わらない。既存の版を一括で
  再解釈させる経路は実装仕様書で決める
- Step 2 以降: `column_settings` に読み方の指示が加わり、版同一性の入力が 1 つ増える

## 未決事項

1. **自動にする範囲を広げる条件**: 規則の中の一致、規則の案と AI の案の一致のどちらも候補に
   なる（検討した選択肢「複数行の見出しを自動で読むか」）。標本では、「素直な 1 つの表ではない」と
   規則もモデルも挙げず、2 つの案が同じ、という条件に 63% が当たり、すべて正解だった（コンテキスト 7）。
   残りの正解を人が確かめ、別の標本でも確かめてから決める。
   案が割れたシートで、AI に行と列を取りに行かせて読み直させるかも、ここで合わせて決める
2. **複数シート**: 決定 3-1 は「表とみなせるシートが 1 枚だけ」に限った。複数シートから 1 枚を
   選ぶのは読み方の指示で扱える。同じ形のシートを縦に積むことは後の判断（段階の注）。
   複数の表を 1 リソースから出すことはしない（決定 7）
3. **サイズ**: XLSX は ZIP 圧縮なので、100MB の入口に対して展開後はずっと大きくなる。
   解釈対象の上限を Excel 用に別に持つかは、スパイクの測定で決める
4. **プレビューの切り替え**: 表として解釈できた Excel で、原本の描画への切り替えを残すか
5. **1 つの表か、複数の表か**: 同じ見出しの繰り返し、「つづき」の折り返し、区分ごとのかたまりを
   どちらと読むか。規則も AI も正解も、ここで割れた。人が確かめた 54 枚の答えからは、
   「名前を持つかたまりは別の表。同じ表の中の行の集まりと、印刷のために列を横に折り返した
   ものは 1 つの表」が読み取れる（コンテキスト 7）。ただし、折り返し、段組、範囲の途中に入る
   注記や繰り返しの見出しは、範囲と見出しの行数だけではどう選んでも正しい表にならない。
   これらは、正解を 1 つに決めて当たり方を測る対象から外し、「矩形 1 つでは表せない形」として
   扱う。案を出さずに理由を示す（決定 5）のか、折り返しを戻す指定を読み方の指示に足すのか、
   列を 1 つ足せば 1 つの表にできる名前付きのかたまりを積むのかを、実装仕様書で決める
6. **見出しの列名のつなぎ方**: 区切りの文字、親が結合でなく位置だけで示される見出しの扱い、
   隣り合う同じ名前をまとめるか
7. **worker の条件でのメモリ**: 格子の読み取りの速さは測ったが、worker のメモリの上限での
   最大値は測っていない
