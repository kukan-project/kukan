# パイプライン実行時リファレンス

リソース 1 件を処理する間に、**何が・どの順で・何を条件に**書かれるかをまとめたもの。

設計判断そのものは ADR にある（ADR-043 版管理と層 2、ADR-044 実行 claim、ADR-045
オブジェクトの先行記録）。ここに書くのは**それらが実装上どう噛み合っているか**である。
不具合の多くは 1 つの機構の中ではなく、機構どうしの間で起きてきた。

| 参照       | 場所                                   |
| ---------- | -------------------------------------- |
| 実行の本体 | `apps/worker/src/pipeline/`            |
| 不変条件   | `packages/api/src/services/`           |
| 設計判断   | `docs/adr/jp/043` / `044` / `045`      |
| 掃除       | `apps/worker/src/cron/orphan-cleanup/` |

## 1. 1 回の実行

キュー（`resource-pipeline`）1 通につき、1 リソースに対して 5 ステップが記録される。Lake だけは
Extract の内側から走る（後述）。

```
claim を取る ─┬─ Fetch    内容を取得し、live ポインタを自分の鍵へ移す
              ├─ Version  正本ファイルを版として複製（層 1）
              ├─ Extract  版ファイルを解釈し、プレビュー Parquet / スキーマ / エンコーディング
              │   └─ Lake その解釈が作ったテーブルを DuckLake へ取り込む（層 2）
              └─ Index    本文を抽出して検索索引へ
claim を返す
```

`apps/worker/src/pipeline/process-resource.ts` が全体、各ステップは `steps/` にある。

**Fetch だけが致命的。** 他の 4 つは失敗を記録して次へ進む — いずれも正本ファイルから作り直せる
派生物だからである。Fetch が失敗すれば、そもそも記述する内容が無い。

**層 1 は全フォーマット。** Version は PDF も画像も ZIP も複製する。テーブル形式に限られるのは
**Lake（層 2）だけ**である。ただしフォーマットを見て弾いているのではない — 解釈がテーブルを
作らなかった実行は Lake に到達しないので、判定は構造的である。

**Version が内容を読む全ステップより前にある**（ADR-046）。bytes を先に確定させ、その解釈は
書き換わらないファイルから作る。だから解釈は何度でもやり直せる — 失敗した実行が残すのは
「まだ解釈されていない版」であって、誰も保存しなかった内容の派生物ではない。

**Extract が読むのは版ファイルであって live オブジェクトではない。** 対象の版は
「この実行の content hash を持つ active な版」で、捕捉したかどうかに依らず引ける
（`versionForContent`）。内容が変わらず捕捉をスキップした実行も、**過去に解釈が失敗した版**を
ここで拾い直す。該当する版が無ければ（捕捉が失敗した / ポインタが動いた）Extract はスキップし、
その bytes を捕捉した実行が解釈する。

**スキーマは捕捉時ではなく Extract のあとに書く。** 版行のスキーマが未割当なのは正常な状態である
（ADR-046 §3）。入力が不変で解釈が再実行可能だから、埋め直す経路が常に存在する。

**層 2 が読むのは、解釈がローカルディスクに書いた Parquet である**（ADR-046）。ストレージ上の
プレビューではない。Lake はコードとしては Extract の内側で走り、**ステップ記録は独立している**
（履歴は `started_at` 順に読むので並びは変わらない）。取り込みだけがカタログ全体のロックの下で
走り、解釈はロックの外にある — 1 セッションで通すとロックを解釈の間ずっと握ることになる。

**取り込みに失敗しても何も記録しない。** 再取り込みは版ファイルを解釈し直すので、
残すべきものが無い（§5）。

**ステップ本体は claim を持たない。** ステップが触れるのは `PipelineContext`（`types.ts`）だけで、
実行スコープの包み（`held-context.ts`）が claim を注入する。「能力を渡す場所」に条件を置くことで、
新しい呼び出し箇所が条件を引き継ぐ。

## 2. claim — 1 リソース 1 書き手

`resource_pipeline` 行が claim そのものである（1 リソース 1 行のユニーク制約）。

| 列               | 意味                                                    |
| ---------------- | ------------------------------------------------------- |
| `claim_owner`    | 今このリソースを持っている実行の id（UUID、行ではない） |
| `claim_kind`     | `run`（パイプライン実行）か `job`（パージ・再取り込み） |
| `claim_owner_at` | いつ取ったか。生存判定に使う                            |

- **取れなければ実行しない。** ジョブは遅延付きで再投入される（`CLAIM_RETRY_DELAY_S`）。
  捨てないのは、保持者が読んだ後に届いた差し替えを誰も処理しなくなるためである。
- **15 分（`CLAIM_STALE_AFTER_MS`）進捗が無ければ奪える。** 進捗＝ claim 取得時刻とステップ開始
  時刻の新しい方。`updated` は使わない — enqueue やプレビュー無効化も書く列なので、
  再アップロードを繰り返すだけで死んだ実行の窓を延長できてしまう。
- **`run` だけが止められる。** `job` は書き込みごとの所有者検査を持たないため、claim を外しても
  止まらず、排他だけが消える（ADR-044 §4）。

取り方は 3 つ。すべて `packages/api/src/services/pipeline-claim.ts` にある。

| 入口                 | 使う側                           | 取れなかったら             |
| -------------------- | -------------------------------- | -------------------------- |
| `withResourceClaim`  | パイプライン実行                 | 再投入                     |
| `withResourceClaims` | パージ・バックフィル・再取り込み | 全件取れなければ何もしない |
| `withClaimFromRun`   | 差し戻し                         | `job` が持っていれば 409   |

`withClaimFromRun` は**止めることと取ることを 1 文で行う**。2 文に分けると、その間リソースが
無主になり、待機中のジョブが「まさに取り下げようとしている内容」の上に書き始められる。

## 3. 書き込み一覧 — 何が何を条件にしているか

これがこのドキュメントの中心である。**実行が書くものは 3 種類ある。**

### (a) 実行自身の記録 — claim を条件にする

`step-tracker.ts` の全文。条件が外れれば書き込みは 0 行に着地し、実行は静かに抜ける。

| 書き込み              | 条件             | 副作用                               |
| --------------------- | ---------------- | ------------------------------------ |
| `beginRun`            | `heldBy(claim)`  | 前回のステップ記録を削除             |
| `startStep`           | `heldBy(claim)`  | 0 行なら `RunCancelledError`         |
| `completeStep` 他     | step 経由で join | ステップ行と pipeline 行の両方を検査 |
| `updateExtractResult` | `heldBy(claim)`  | 旧プレビューと旧 text head を park   |
| `mergeMetadata`       | `heldBy(claim)`  | 旧 text head を park                 |
| `updateStatus`        | `heldBy(claim)`  | —                                    |

### (b) リソースに残る書き込み — claim を条件にする（外に出せない）

実行が消えても残るもの。**ここが過去に一番間違えた場所である。**

| 書き込み             | 場所                          | 条件                                     |
| -------------------- | ----------------------------- | ---------------------------------------- |
| live ポインタの移動  | `storage-pointer.ts`          | ポインタの CAS **＋** `stillHeld(claim)` |
| 版行の insert        | `resource-version-service.ts` | `stillHeld(claim)`                       |
| 版行へのスキーマ記録 | `resource-version-service.ts` | `stillHeld(claim)` ＋ 版番号             |

`stillHeld` は `pipeline-claim.ts` の 1 つの式で、3 つとも同じものを使う。

**`FOR SHARE` が付いている理由。** 素の `EXISTS` だと claim 行は文のスナップショットから読まれ、
自分が更新する行が他に押さえられて文が待たされると、**取消より前の視界のまま書き込みが成立する**。
`cancelResourceRun` が「止めた」と返した後に、止めたはずの実行の書き込みが着地する（実測）。
共有ロックを取ると取消と順序が付き、**キルは殺す相手の 1 文が終わるのを待つ**。

### (c) DB を出る書き込み — 条件を載せる行が無い

検索索引へのチャンク投入、DuckLake への取り込み。`WHERE claim_owner = 自分` を載せる先が無いので、
**書く前に問い合わせる**（`held-context.ts` の `stillHolds`）。

**これは検査であってフェンスではない。** 答えと書き込みの間に claim は外れうる。得られるのは
窓の大きさで、チャンクごとに問えばキルは 1 チャンクで止まる。閉じ切るには索引の各文書が
「どの実行の産物か」を持つ必要があり、現時点では露出に見合わないと判断している（ADR-044 §4）。

残る窓は 2 方向:

- 遅れたチャンクが撤回内容を検索に戻す → 差し戻しは再処理を投入するので通常は上書きされる
- **遅れた削除が復元後の索引を消す** → こちらは自己修復しない（削除が再索引の後に来る）

## 4. オブジェクトの一生

ストレージのオブジェクトは、必ずこの順で扱う。

```
1. 先行記録   orphaned_object に鍵を入れる（expires_at 付き）    ← 書く前
2. 書く       putObject / copyObject
3. 参照       ポインタ列へ入れる ＝ 同じ文で先行記録を消す
4. park       置き換えられたら orphaned_object へ戻す（同じ文で）
5. 掃除       毎時 17 分、期限切れの鍵を sweep
```

**1 が無いと、書いた直後に死んだプロセスのオブジェクトは誰にも辿れない。**
**3 と 4 が同じ文でないと、ポインタも台帳記録も持たないオブジェクトが生まれる。**

sweep（`sweep-orphans.ts`）は期限切れの鍵を最大 5000 件取り、**削除の直前に「まだ誰か指して
いるか」を問う**。参照されていれば消すのは記録の方で、オブジェクトは残る。これが先行記録の
唯一の危険（消し忘れが生きたデータの削除に化ける）を自己修復に変えている。

参照元は 5 つ。**1 つでも漏らすとその列が指すオブジェクトを消す**:

`resource.storage_key` / `resource.pending_storage_key` / `resource_version.storage_key` /
`resource_pipeline.preview_key` / `resource_pipeline.metadata->>'textHeadKey'`

かつて 6 つ目だった `resource_version.lake_source_key` は撤去した（ADR-046 §4）。層 2 が読むのは
版ファイルなので、実行より長生きするオブジェクトを名指しで守る必要が無くなった。

sweep が「判定 → 削除」の間に安全なのは、**書き手が判定中の鍵を名指しできない**からである。
実行が作る鍵はすべて自分の試行のトークンを含む（`v{n}.{attempt}` など）ので、失敗して再試行
した実行は別の場所へ書く。

## 5. 層 2 に入っていない版の見つけ方

**残っているかどうかは 1 つの条件で決まる。** 「active な資源の active な版で、
`ducklake_snapshot_id` が空」。それ以外に確かめる相手が無いのは、取り込みが読むのが版ファイルで、
それは常にそこにあるからである — 版は入っているか入っていないかのどちらかしかない。

以前はここに 2 つの分岐があった。`lake_source_key` が指すプレビューと、資源の現在のプレビューで
ある。プレビューは可変で実行より長生きするので、**それがその版を記述している証明**（Extract が
読んだ bytes のハッシュとの一致、無い古い行への後方互換分岐）が必要だった。読む対象が版ファイル
になった時点で、証明する相手ごと消えた（ADR-046 §4）。

**残りの条件は「成功しえない仕事を積まない」ためだけにある。** 解釈がテーブルを作らない形式と
サイズを除かないと、PDF も超過 CSV も永久にここに残り毎時 enqueue され続ける。より新しい版が既に
取り込まれている版も同じで、取り込み側が追い越しとして拒否する。

**ハンドラは同じ述語を版 1 件に絞って引き直す**（`pendingLakeVersionSource`）。別の判断ではなく
同じ判断で、これが無いと重複メッセージの大半が 50MB を読んでから「もう終わっていた」と気づく。

毎時 37 分の sweep（`queuePendingLakeIngests`）は**キューに積むだけ**で、解釈はワーカーのハンドラが
行う。解釈にはエンコーディング検出・DuckDB・ストレージが要り、それらを `packages/api` に持ち込む
理由が無いためである。cron はプロセス単位なので**全タスクが同じ版を積む**。重複は前提で、
ハンドラは**何かを読む前に**「まだ入っていない版か」をもう一度尋ねる。

## 6. 止める / 差し戻す / パージ

破壊の度合いが違う 3 段。**それぞれ明示的に選ばせる**（ADR-044 §4）。

| 操作             | 止まるもの                     | 内容                         | 版行       |
| ---------------- | ------------------------------ | ---------------------------- | ---------- |
| 処理を中止       | プレビュー・索引・版捕捉の生成 | そのまま                     | そのまま   |
| 中止して差し戻す | 同上                           | 前の版へ復元（無ければ空に） | そのまま   |
| 版をパージ       | 同上                           | 版ファイルごと削除           | 墓標を残す |

**差し戻しは履歴を 1 段遡る。** 戻り先は「live な版より下の、最新の版」。「撤回する内容では
ない最新の版」では足りない — 差し戻しは版行を消さないので、踏み台にした版が active のまま
最新であり続け、2 度目の差し戻しが**それを選んで撤回内容を戻してしまう**。

「今どこに立っているか」はハッシュで特定する。live ポインタが名指しているのはオブジェクトで
あって版ではないため、その bytes を持つ最新の active 版が立っている場所になる。

**パージだけが層 2 を巻き戻す。** 層 2 の現在内容が追随するのは「取り込まれた最新の版」で
あって live 内容ではない。差し戻し後、層 2 は撤回された版の内容を持ったままになる — 層 2 が
層 1 の版履歴の写像であることの帰結であり、不整合ではない。消したければパージを使う。

## 7. 版の捕捉ゲート

Version ステップが版を作るのは、次の**両方**を満たすときだけ（`version-capture.ts`）。

- `currentKey === publishedKey` — この実行が公開した内容が今も live である
- `latestActiveHash !== hash` — 最新の active 版と内容が違う

版番号は**全状態の最大値 + 1**（墓標を含む）。ユニーク索引で衝突しないためである。
一方ゲートは**最新の active 版**と比べる — 墓標が live 版の上に載る状況（最新版パージ + 巻き戻し）
があり、最大行と比べると既に live な内容を再捕捉してしまう。

## 8. 定期実行

| 時刻       | 何を                                                               |
| ---------- | ------------------------------------------------------------------ |
| 毎時 17 分 | 放置アップロード URL の期限切れ → 孤児 sweep → 層 2 の孤児ファイル |
| 毎時 37 分 | 取り込み待ちの版を DB から拾い直す                                 |

## 9. 用語

| 語          | 意味                                                          |
| ----------- | ------------------------------------------------------------- |
| claim       | `resource_pipeline` 行。1 リソース 1 書き手を保証する         |
| run / job   | claim の保持者の種別。`run` だけが止められる                  |
| park        | 置き換えられた鍵を `orphaned_object` に入れ、sweep に渡すこと |
| 先行記録    | オブジェクトを作る**前**に鍵を台帳へ入れること（ADR-045）     |
| 層 1 / 層 2 | 版ファイル本体 / DuckLake の行レベル差分（ADR-043）           |
| 墓標        | パージ済みの版行。誰が・いつ・なぜを残し、内容だけ消す        |
