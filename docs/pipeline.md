# パイプライン実行時リファレンス

リソース 1 件を処理する間に、**何が・どの順で・何を条件に**書かれるかをまとめたもの。

設計判断そのものは ADR にある（ADR-043 版管理と層 2、ADR-044 実行 claim、ADR-045
オブジェクトの先行記録）。ここに書くのは**それらが実装上どう噛み合っているか**である。
不具合の多くは 1 つの機構の中ではなく、機構どうしの間で起きてきた。

| 参照       | 場所                                   |
| ---------- | -------------------------------------- |
| 実行の本体 | `apps/worker/src/pipeline/`            |
| 不変条件   | `packages/api/src/services/`           |
| 設計判断   | `docs/adr/jp/043` / `044` / `045`      |
| 掃除       | `apps/worker/src/cron/orphan-cleanup/` |

## 1. 1 回の実行

キュー（`resource-pipeline`）1 通につき、1 リソースに対して 5 ステップが記録される。Lake だけは
Interpret の内側から走る（後述）。

```
claim を取る ─┬─ Fetch      内容を取得し、live ポインタを自分の鍵へ移す
              ├─ Version    正本ファイルを版として複製（層 1）
              ├─ Interpret  版ファイルを解釈し、プレビュー Parquet / スキーマ / エンコーディング
              │   └─ Lake   その解釈が作ったテーブルを DuckLake へ取り込む（層 2）
              └─ Index      本文を抽出して検索索引へ
claim を返す
```

コードの配置は**どこから呼ばれるか**で分かれている。

| 場所                  | 中身                                                                     |
| --------------------- | ------------------------------------------------------------------------ |
| `pipeline/` 直下      | 入口 2 つと、その足場（コンテキスト・実行記録・共有ユーティリティ）      |
| `pipeline/steps/`     | `process-resource.ts` が直接呼ぶ単位（Fetch / Interpret / Lake / Index） |
| `pipeline/interpret/` | 版ファイル 1 つの解釈。2 つの入口が共有する                              |

**入口は 2 つある。** `process-resource.ts`（5 ステップ全体）と `retry-lake-ingest.ts`（層 2 の
再取り込み。Fetch と Version を飛ばして解釈だけをやり直す、§5）。どちらも `index.ts` の SQS
ハンドラから呼ばれる。解釈が `steps/` の下ではなく独立しているのはこの 2 つが共有するからで、
ZIP マニフェストの生成も解釈の一部としてここにある。

**Version には `steps/` のファイルが無い。** 版を作る処理そのものは `PipelineContext.createVersion`
（`build-context.ts`）にあり、判定だけが `version-gate.ts` に分かれている（§7）。DB 操作なので
コンテキスト側にあり、間違えやすい規則だけを IO から切り離してある。

**Fetch だけが致命的。** 他の 4 つは失敗を記録して次へ進む — いずれも正本ファイルから作り直せる
派生物だからである。Fetch が失敗すれば、そもそも記述する内容が無い。

**層 1 は全フォーマット。** Version は PDF も画像も ZIP も複製する。テーブル形式に限られるのは
**Lake（層 2）だけ**である。ただしフォーマットを見て弾いているのではない — 解釈がテーブルを
作らなかった実行は Lake に到達しないので、判定は構造的である。

**Version が内容を読む全ステップより前にある**（ADR-046）。bytes を先に確定させ、その解釈は
書き換わらないファイルから作る。だから解釈は何度でもやり直せる — 失敗した実行が残すのは
「まだ解釈されていない版」であって、誰も保存しなかった内容の派生物ではない。

**Interpret が読むのは版ファイルであって live オブジェクトではない。** 対象の版は
「この実行の content hash を持つ active な版」で、版を作ったかどうかに依らず引ける
（`versionForContent`）。内容が変わらず版を作らなかった実行も、**過去に解釈が失敗した版**を
ここで拾い直す。該当する版が無ければ（版の作成が失敗した / ポインタが動いた）Interpret はスキップし、
その bytes から版を作った実行が解釈する。

**版を作らなかった実行は、既にその bytes から作られている派生物を作り直さない。** 版ファイルは
不変なので、同じ版を解釈し直しても同じ結果にしかならない。行が記録している派生物が
この実行の内容から作られたと言い切れるとき — プレビューがあり `metadata.sourceHash` が一致し、
`metadata.contentIndexed` が真で、その版に Lake 取り込みが残っていないとき — Interpret と Index を
スキップする（`derivativesDescribe`）。どれか一つでも欠ければ走らせる（途中で失敗した実行を
再開させるため）。**版を作った実行は常に走る。** フォーマットの変更は版を作るので（下記）、
ラベルだけ変えた再実行がスキップされることはない。**`rebuildOnly` の実行も常に走る** —
行からは見えない欠落（プレビューの実体だけが消えている等）に対する修復手段そのものだからである
（ADR-044 §4）。

**ドキュメントを消した側が、行の申告を取り下げる。** `contentIndexed` は「この bytes は
コンテンツ索引に入っている」という実行の記録であり、削除がそれを残したままにすると、
再投入のために送られた実行こそがスキップする。パッケージ削除（子ドキュメントごと消える）と
「コンテンツを含む再インデックス」（全消去 → 全リソース再エンキュー）は、消したあとに
`markContentUnindexed` で行を false にする。

Lake の判定は**掃引と同じ述語**（`pendingLakeVersionSource`）に訊く。取り込み対象でない
フォーマット（ZIP のマニフェストなど）やサイズ超過の版は「未完了の仕事」ではないからである。
DuckLake 未設定の環境では取り込み自体が起きないので、この条件は判定に加わらない。

**フォーマットも同じ行から取る**（ADR-046 §6）。版定義の `format` は作成時の `resource.format` を
写した値で、以後変わらない。利用者がラベルを変えても、確定済みの bytes は作成時の規則で読み直され、
既存の版のスキーマは書き換わらない。Index は逆に**リソースのラベル**を使う — 読む対象が live
オブジェクトなので、問いが「このリソースは今なにか」だからである。

**スキーマは作成時ではなく Interpret のあとに書く。** 版定義のスキーマが未割当なのは正常な状態である
（ADR-046 §3）。入力が不変で解釈が再実行可能だから、埋め直す経路が常に存在する。

**層 2 が読むのは、解釈がローカルディスクに書いた Parquet である**（ADR-046）。ストレージ上の
プレビューではない。Lake はコードとしては Interpret の内側で走り、**ステップ記録は独立している**
（履歴は `started_at` 順に読むので並びは変わらない）。取り込みだけがカタログ全体のロックの下で
走り、解釈はロックの外にある — 1 セッションで通すとロックを解釈の間ずっと握ることになる。

**取り込みに失敗しても何も記録しない。** 再取り込みは版ファイルを解釈し直すので、
残すべきものが無い（§5）。

**ステップ本体は claim を持たない。** ステップが触れるのは `PipelineContext`（`types.ts`）だけで、
実行スコープの包み（`held-context.ts`）が claim を注入する。「能力を渡す場所」に条件を置くことで、
新しい呼び出し箇所が条件を引き継ぐ。

## 2. claim — 1 リソース 1 書き手

`resource_pipeline` 行が claim そのものである（1 リソース 1 行のユニーク制約）。

| 列               | 意味                                                    |
| ---------------- | ------------------------------------------------------- |
| `claim_owner`    | 今このリソースを持っている実行の id（UUID、行ではない） |
| `claim_kind`     | `run`（パイプライン実行）か `job`（パージ・再取り込み） |
| `claim_owner_at` | いつ取ったか。生存判定に使う                            |

- **取れなければ実行しない。** ジョブは遅延付きで再投入される（`CLAIM_RETRY_DELAY_S`）。
  捨てないのは、保持者が読んだ後に届いた差し替えを誰も処理しなくなるためである。
- **15 分（`CLAIM_STALE_AFTER_MS`）進捗が無ければ奪える。** 進捗＝ claim 取得時刻とステップ開始
  時刻の新しい方。`updated` は使わない — enqueue やプレビュー無効化も書く列なので、
  再アップロードを繰り返すだけで死んだ実行の窓を延長できてしまう。
- **`run` だけが止められる。** `job` は書き込みごとの所有者検査を持たないため、claim を外しても
  止まらず、排他だけが消える（ADR-044 §4）。

取り方は 3 つ。すべて `packages/api/src/services/pipeline-claim.ts` にある。

| 入口                 | 使う側                                                | 取れなかったら             |
| -------------------- | ----------------------------------------------------- | -------------------------- |
| `withResourceClaim`  | パイプライン実行                                      | 再投入                     |
| `withResourceClaims` | パージ・移行（v1 付与・旧巻き戻しの変換）・再取り込み | 全件取れなければ何もしない |
| `withClaimFromRun`   | 巻き戻し                                              | `job` が持っていれば 409   |

`withClaimFromRun` は**止めることと取ることを 1 文で行う**。2 文に分けると、その間リソースが
無主になり、待機中のジョブが「まさに取り下げようとしている内容」の上に書き始められる。

## 3. 書き込み一覧 — 何が何を条件にしているか

これがこのドキュメントの中心である。**実行が書くものは 3 種類ある。**

### (a) 実行自身の記録 — claim を条件にする

`step-tracker.ts` の全文。条件が外れれば書き込みは 0 行に着地し、実行は静かに抜ける。

| 書き込み                | 条件             | 副作用                                |
| ----------------------- | ---------------- | ------------------------------------- |
| `beginRun`              | `heldBy(claim)`  | 前回のステップ記録を削除              |
| `startStep`             | `heldBy(claim)`  | 0 行なら `RunCancelledError`          |
| `completeStep` 他       | step 経由で join | ステップ行と pipeline 行の両方を検査  |
| `updateInterpretResult` | `heldBy(claim)`  | 旧プレビューと旧 text head を回収予約 |
| `mergeMetadata`         | `heldBy(claim)`  | 旧 text head を回収予約               |
| `updateStatus`          | `heldBy(claim)`  | —                                     |

### (b) リソースに残る書き込み — claim を条件にする（外に出せない）

実行が消えても残るもの。**ここが過去に一番間違えた場所である。**

| 書き込み               | 場所                          | 条件                                     |
| ---------------------- | ----------------------------- | ---------------------------------------- |
| live ポインタの移動    | `storage-pointer.ts`          | ポインタの CAS **＋** `stillHeld(claim)` |
| 版定義の insert        | `resource-version-service.ts` | `stillHeld(claim)`                       |
| 版定義へのスキーマ記録 | `resource-version-service.ts` | `stillHeld(claim)` ＋ 版番号             |

`stillHeld` は `pipeline-claim.ts` の 1 つの式で、3 つとも同じものを使う。

**`FOR SHARE` が付いている理由。** 素の `EXISTS` だと claim 行は文のスナップショットから読まれ、
自分が更新する行が他に押さえられて文が待たされると、**取消より前の視界のまま書き込みが成立する**。
`cancelResourceRun` が「止めた」と返した後に、止めたはずの実行の書き込みが着地する（実測）。
共有ロックを取ると取消と順序が付き、**キルは殺す相手の 1 文が終わるのを待つ**。

### (c) DB を出る書き込み — 条件を載せる行が無い

検索索引へのチャンク投入、DuckLake への取り込み。`WHERE claim_owner = 自分` を載せる先が無いので、
**書く前に問い合わせる**（`held-context.ts` の `stillHolds`）。

**これは検査であってフェンスではない。** 答えと書き込みの間に claim は外れうる。得られるのは
窓の大きさで、チャンクごとに問えばキルは 1 チャンクで止まる。閉じ切るには索引の各文書が
「どの実行の産物か」を持つ必要があり、現時点では露出に見合わないと判断している（ADR-044 §4）。

残る窓は 2 方向:

- 遅れたチャンクが撤回内容を検索に戻す → 巻き戻しは再処理を投入するので通常は上書きされる
- **遅れた削除が復元後の索引を消す** → こちらは自己修復しない（削除が再索引の後に来る）

## 4. オブジェクトの一生

ストレージのオブジェクトは、必ずこの順で扱う。

```
1. 先行記録   orphaned_object に鍵を入れる（expires_at 付き）    ← 書く前
2. 書く       putObject / copyObject
3. 参照       ポインタ列へ入れる ＝ 同じ文で先行記録を消す
4. 回収予約   置き換えられたら orphaned_object へ戻す（同じ文で）
5. 掃除       毎時 17 分、期限切れの鍵を sweep
```

**1 が無いと、書いた直後に死んだプロセスのオブジェクトは誰にも辿れない。**
**3 と 4 が同じ文でないと、ポインタも台帳記録も持たないオブジェクトが生まれる。**

sweep（`sweep-orphans.ts`）は期限切れの鍵を最大 5000 件取り、**削除の直前に「まだ誰か指して
いるか」を問う**。参照されていれば消すのは記録の方で、オブジェクトは残る。これが先行記録の
唯一の危険（消し忘れが生きたデータの削除に化ける）を自己修復に変えている。

参照元は 5 つ。**1 つでも漏らすとその列が指すオブジェクトを消す**:

`resource.storage_key` / `resource.pending_storage_key` / `resource_version.storage_key` /
`resource_pipeline.preview_key` / `resource_pipeline.metadata->>'textHeadKey'`

かつて 6 つ目だった `resource_version.lake_source_key` は撤去した（ADR-046 §4）。層 2 が読むのは
版ファイルなので、実行より長生きするオブジェクトを名指しで守る必要が無くなった。

sweep が「判定 → 削除」の間に安全なのは、**書き手が判定中の鍵を名指しできない**からである。
実行が作る鍵はすべて自分の試行のトークンを含む（`v{n}.{token}` など）ので、失敗して再試行
した実行は別の場所へ書く。

## 5. 層 2 に入っていない版の見つけ方

**残っているかどうかは 1 つの条件で決まる。** 「active なリソースの active な版で、
`ducklake_snapshot_id` が空」。それ以外に確かめる相手が無いのは、取り込みが読むのが版ファイルで、
それは常にそこにあるからである — 版は入っているか入っていないかのどちらかしかない。

以前はここに 2 つの分岐があった。`lake_source_key` が指すプレビューと、リソースの現在のプレビューで
ある。プレビューは可変で実行より長生きするので、**それがその版を記述している証明**（Extract が
読んだ bytes のハッシュとの一致、無い古い行への後方互換分岐）が必要だった。読む対象が版ファイル
になった時点で、証明する相手ごと消えた（ADR-046 §4）。

**残りの条件は「成功しえない仕事を積まない」ためだけにある。** 解釈がテーブルを作らない形式と
サイズを除かないと、PDF も超過 CSV も永久にここに残り毎時 enqueue され続ける。より新しい版が既に
取り込まれている版も同じで、取り込み側が追い越しとして拒否する。**キーが理由で断られた版も同じで、
`lake_ingest_reason` が記録されていれば外す** — キーの妥当性は行の述語では答えられない（複合キーの
一意性は凍結スキーマに無い）ので、断った側が記録する。書き込み一度きりで、キーを変えれば新しい版が
立つので、遡って入れ直すことはしない。

形式を見るのは**版定義の `format`** であってリソースのラベルではない（§1、ADR-046 §6）。ラベルで絞ると、
PDF として確定した bytes がラベル変更だけで表として読まれる側に回る。

**ハンドラは同じ述語を版 1 件に絞って引き直す**（`pendingLakeVersionSource`）。別の判断ではなく
同じ判断で、これが無いと重複メッセージの大半が 50MB を読んでから「もう終わっていた」と気づく。

毎時 37 分の sweep（`queuePendingLakeIngests`）は**キューに積むだけ**で、解釈はワーカーのハンドラが
行う。解釈にはエンコーディング検出・DuckDB・ストレージが要り、それらを `packages/api` に持ち込む
理由が無いためである。cron はプロセス単位なので**全タスクが同じ版を積む**。重複は前提で、
ハンドラは**何かを読む前に**「まだ入っていない版か」をもう一度尋ねる。

## 6. 止める / 巻き戻す / パージ

破壊の度合いが違う 3 段。**それぞれ明示的に選ばせる**（ADR-044 §4）。

| 操作             | 止まるもの                 | 内容                         | 版                               |
| ---------------- | -------------------------- | ---------------------------- | -------------------------------- |
| 処理を中止       | プレビュー・索引・版の作成 | そのまま                     | そのまま                         |
| 中止して巻き戻す | 同上                       | 行き先の版へ復元（または空） | 行き先の内容を新しい版として発行 |
| 版をパージ       | 同上                       | 版ファイルごと削除           | 墓標を残す（下位の版へ降りる）   |

**巻き戻しは版を前へ進める**（ADR-044 §4）。行き先を名指すと、その内容の複製が v(N+1) として立ち、
`origin: 'revert'` と `restored_from` を持つ。**既存の版は状態も番号も変わらない。** 版を振り直さない
ので「行き先より上を外す」前処理が要らず、上限指定も、2 度目の巻き戻しが撤回内容へ戻る問題も無い。
**どの生存版でも行き先に指定できる。** 行き先が無い（空にする）巻き戻しはポインタを空にし、版には
触れない。

**live は「最上位の active 版」ではなく、live ポインタが名指すオブジェクトを所有する版である。**
版は自分のオブジェクトを所有し（ADR-046 §3）、誰も所有していないオブジェクトは自分のものにし、
既に所有されているものは複製する（ADR-043 §1-2）。パージ実行中はその所有者が `purging` でありうる
ので、**そのとき live な `active` 版は 1 つも無い**。

**どの版も所有していない live は正常であり、恒久的に発生する。** 未変更の再取得は毎回新しい鍵へ
書いて公開し、版を作るかの判定（§7）がそこで版を作らないためである。**そのときだけ**「そのハッシュを
持つ最新の版」が立っている場所とみなす — 推定であって、同じ bytes を持つ版が複数あれば当たるとは
限らない。パージ確認画面はその推定を出す。**予告としては正しい** — パージが同じ推定で動くので、
名指した版に起きることは画面のとおりになる。**誤りうるのは「この版が配信中の内容である」という
同定のほう**である。

**「パージ完了後にどこへ落ちるか」はこれとは別の問いで、そちらは最上位の `active` 版である。**
2 つを同じ語で呼ぶと、確認画面と実際に起きることが食い違う。

状態は `active` / `purging` / `purged` の 3 つ。**遷移図と状態ごとの資格（版ファイルはあるか・層 2 の
snapshot を保持するか・個別にパージできるか）は ADR-043 §1.1 にある。**

> **旧方式の巻き戻しが残した `superseded` 行がまだある。** 版を振り直していた頃、行き先より上の版を
> 脇へ避けるために書いていた状態で、書く経路はもう無い。読む側は変換（ADR-044 §4）が終わるまで
> これを配信中の版として数え続ける — 内容を持ち、ダウンロードでき、パージでき、行き先に指定できる。
> 自動の戻り先にならない点だけが `active` と違う。

**パージが消すのは、その版が持つ複製だけである。** 同じ bytes を持つ版が複数あるのは正常で（§7、
巻き戻しは必ず複製を作る）、それぞれが自分のオブジェクトを所有しているので、片方を消してももう
片方は同じ bytes を配り続ける。消してよいかは版ごとの判断なので自動では消さず、パージ確認
ダイアログが同内容の生存版を名指す。名指せるのは版一覧が全件返るからで、その依存は
ADR-043 §5 と残課題 13 にある。

**層 2 の現在内容が追随するのは「最後に載った `active` 版」であって live 内容ではない**（版番号の
最上位ではなく、**記録されたスナップショットが最大の版**。ADR-043 §5）。
**巻き戻しは層 2 に何も指示しない** — 発行した版が通常の取り込みでテーブルに載るので、層 2 は層 1 と
同じ経路で追いつく。降ろすのはパージだけで、テーブルの現在内容をそこへ戻す（ADR-043 §5）。
**降ろしは版行に何も書かない** — `ducklake_snapshot_id` は版の取り込み時に一度だけ書かれ、
着地したスナップショットはどの版行からも名指しされない（保持は「最新スナップショットは常に残す」）。
**戻り先は層 1 と別に引く** — live 版が
層 2 に入っているとは限らない（大きすぎる・表形式でない）ので、層 1 の戻り先で降ろすと「戻り先なし」と
読み違える。**戻り先が 1 つも無いときテーブルを落とすのはパージだけである** — パージには取得できなく
する義務があり、他のどの操作にも無い（空にする巻き戻しもテーブルをそのまま残す）。落としても失うのは
現在内容だけで、保持スナップショットの差分とタイムトラベルは残る。

## 7. 版を作るかの判定

Version ステップが版を作るのは、次の**両方**を満たすときだけ（`version-gate.ts`）。

- `currentKey === publishedKey` — この実行が公開した内容が今も live である
- 最新の active 版と、**ハッシュ・format・主キー列のどれかが違う**（`sameVersionIdentity`。巻き戻しが
  「もう行き先にいるか」を尋ねるのと同じ関数で、版の定義は 1 つしか無い — ADR-046 §3）

format と主キーが入っているのは、版が「その bytes を、この解釈で読んだもの」だからである
（ADR-046 §6、ADR-043 §5）。**誤ラベルの訂正や主キーの確定で版を作る経路はここしか無い** —
ハッシュだけを見ると、bytes の変わらない訂正は作られず、既存の版は訂正前の規則で読まれ続ける。
format を持たない版も差分として扱い、次の実行で確定させる。

**設定を変えただけでは版は立たない。** キーの確定は `resource.column_settings` に書くだけで、版を作るのは
**その書き込みが投入する rebuild 実行**である（`rebuildOnly`。外部 URL を取り直さないので bytes が動かず、
キー変更と内容変更が同じ版に混ざらない）。実行が Fetch で live オブジェクトを測り直し、このゲートが差を
見て版を作る。**投入するかどうかは設定ではなく版で決まる** — 最上位の `active` 版が既にその設定を
凍結していれば何も投入せず、していなければ投入する。だから投入に失敗して `queued` が false で返った後、
同じ設定をもう一度送るのが復旧手段になる（設定と版のずれを見つける常設の掃き出しは無い）。
**ただし実行が既に `queued` / `processing` で、しかもその記録が新しいなら投入しない** — その実行が
Version ステップに達した時点で設定を読むので、二重に積んでも版が既にある状態で着くだけである。
投入に失敗した実行は行が `error` に戻るので、この条件には掛からない。**新しさを問うのは、`queued` が
ジョブの存在証明にならないからである** — `enqueue` は行を先に書いてメッセージを後で送るので、その間に
プロセスが落ちると「行は `queued`・キューは空」が残る。判定の窓は claim の 15 分と同じ値を使う
（そこを過ぎれば他の全員が実行を死んだものとして扱うので、ここだけ待ち続けるわけにいかない）。
**ただし 2 つの状態は別の印で日付を見る** — 走行中（`processing`）は claim の生存判定式そのもの
（`claim_owner_at` と最新ステップ開始の新しい方）で、`updated` はステップ開始で動かないので、
長い実行の途中を死んだと読んで 2 本目を積んでしまう。キュー待ち（`queued`）には claim もステップも
無いので、enqueue 自身の書き込みしか印が無い。
版を 1 つも持たないリソースには何も投入しない — 最初の版が作成時に設定を凍結するからである。

**比べる相手は版が凍結した値である。** `format` と同じく、主キーもリソース側の現在設定
（`resource.column_settings.primaryKey`）を版の作成時に写して `resource_version.lake_key_columns` に
凍結し、以後書き換えない — 掃き出しが何時間後に取り込んでも、その版は自分が作られたときのキーで
入る。巻き戻しが発行する版だけは例外で、**行き先の版が凍結していたキー**を写し、同じ
トランザクションでリソース側の設定もそこへ戻す（さもないと現在設定と live の解釈が食い違い、
再送のたびに版が増える）。

版番号は**全状態の最大値 + 1**（墓標を含む）。ユニーク索引で衝突しないためである。
一方ゲートは**最新の active 版**と比べる — 墓標が live 版の上に載る状況（最新版パージ + テーブルの戻し）
があり、最大行と比べると既に live な内容をもう一度作ってしまう。

## 9. 用語

| 語          | 意味                                                                               |
| ----------- | ---------------------------------------------------------------------------------- |
| claim       | `resource_pipeline` 行。1 リソース 1 書き手を保証する                              |
| run / job   | claim の保持者の種別。`run` だけが止められる                                       |
| 回収予約    | 参照が外れた鍵を `orphaned_object` に入れ、猶予後にスイープへ渡すこと              |
| 先行記録    | オブジェクトを作る**前**に鍵を台帳へ入れること（ADR-045）                          |
| 層 1 / 層 2 | 版ファイル本体 / DuckLake の行レベル差分（ADR-043）                                |
| 版          | 版定義 ＋ 版ファイルの対                                                           |
| 版定義      | `resource_version` の 1 行。その版が何か（番号・状態・ハッシュ・スキーマ・format） |
| 版ファイル  | その版が所有する 1 オブジェクト。その版の中身                                      |
| 版の作成    | その時点の bytes を版として確定させること（所有 ＋ 番号付け。内容は解釈しない）    |
| 墓標        | パージ済みの版。版ファイルだけが消え、版定義が誰が・いつ・なぜを答え続ける         |

**版を消すのは版パージだけで、消えるのは版ファイルである。** 巻き戻しはどちらも消さず、版を 1 つ
足すだけ（遷移は ADR-043 §1.1）。リソースそのものが消えるとき（リソース削除・パッケージ／組織
パージ）は、FK CASCADE で版定義も一緒に消える — 墓標が残るのはそのリソースが生きている間である。
