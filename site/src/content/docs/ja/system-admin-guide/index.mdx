## デプロイ方法

KUKAN は2つのデプロイ方式に対応しています。手軽な Docker Compose（オンプレミス・閉域網向け）、
本番のクラウド向け AWS の順で説明します。

### Docker Compose（オンプレミス）

Docker Compose を使ったオンプレミス・閉域網デプロイに対応しています。
本番運用では最新の[リリース](https://github.com/kukan-project/kukan/releases)（`vX.Y.Z` タグ）の利用を推奨します。

```bash
git checkout vX.Y.Z   # 最新リリース
cp .env.prod.example .env.prod
# .env.prod を編集
docker compose --env-file .env --env-file .env.prod --profile prod up -d --build
```

#### アップデート

アップグレード前に[リリースノート](https://github.com/kukan-project/kukan/releases)で破壊的変更と移行手順を確認してください。

```bash
git fetch --tags
git checkout vX.Y.Z   # 新しいリリース
docker compose --env-file .env --env-file .env.prod --profile prod up -d --build
```

オンプレミス構成では以下の代替サービスを使用します。

| AWS サービス | オンプレミス代替    |
| ------------ | ------------------- |
| S3           | MinIO               |
| SQS          | ElasticMQ           |
| OpenSearch   | PostgreSQL 全文検索 |

### AWS デプロイ

KUKAN は **CloudFront（WAF + キャッシュ）→ 内部 ALB → ECS Fargate** 構成で AWS にデプロイします（ADR-027）。
デプロイは **CDK Pipelines（AWS CodePipeline）で自動化**され、CodeConnections（GitHub App）をソースに、
対象ブランチへの push を起点に各環境（dev / prd 等）を CDK Stage としてデプロイします。

環境は `infra/config/environments.ts` で定義します（`environments.example.ts` を**コピーして作成**）。

主要な AWS リソース:

- **CloudFront** — CDN・WAF・TLS 終端（最前面、ADR-027）
- **ALB（internal）** — ロードバランサー（CloudFront VPC Origin 経由でのみ到達）
- **ECS Fargate** — Web アプリケーション + Pipeline Worker
- **Aurora Serverless v2 / RDS** — PostgreSQL データベース
- **S3** — ファイルストレージ
- **SQS** — パイプラインキュー
- **OpenSearch** — 全文検索エンジン
- **AWS Backup** — 隔離バックアップ（large スケール等で有効、ADR-037）

#### バックアップとデータ保護

データ保護の設定は `scale` プリセットに統合されています（ADR-037）:

| 設定                                    | small | medium | large                 |
| --------------------------------------- | :---: | :----: | :-------------------- |
| S3 バージョニング（誤削除・上書き保護） |   —   |   ✓    | ✓                     |
| DB 自動バックアップ保持（任意時点復元） |  7日  |  14日  | 35日                  |
| AWS Backup（隔離保管・長期世代）        |   —   |   —    | 日次35日 + 月次12ヶ月 |

アップロードファイルは S3 に保存され、リージョン内の複数アベイラビリティゾーンへ自動複製されます（設計耐久性 99.999999999%）。バージョニング有効時は誤削除・上書きからの復旧も可能です。AWS Backup は S3 と DB のバックアップを独立した Backup Vault に隔離保管し、リソース本体ごと失われる事故や 35 日を超える長期世代に備えます。環境ごとの調整は `environments.ts` の `overrides.backup` で行います（`awsBackup` の有効化には `s3Versioning: true` が必要）。

#### セットアップ（初回のみ手動。以降は push で自動デプロイ）

1. 環境定義を用意（`cp infra/config/environments.example.ts infra/config/environments.ts` → `environments.ts` を編集）。**各エントリが1環境＝1パイプライン**として作られるため、単一環境なら不要なエントリ（例: `dev`）を削除する
2. AWS コンソールで CodeConnections 接続を作成し、Connection ARN を `environments.ts` のトップレベル `connectionArn`（全 env 共通の export）に設定
   - **CodeBuild** を開く → 左メニュー下部の **Settings → Connections → Create connection**（「Developer Tools」共通設定。CodeBuild 経由が分かりやすい）→ **GitHub** を選択 → 接続名（例 `kukan-github`、AWS 側の識別ラベル）を入力 → **Connect to GitHub** → **AWS Connector for GitHub** アプリをインストール・認可（**Only select repositories** を選び、デプロイ対象のリポジトリのみに絞る。最小権限）→ ステータスが **Available** になったら ARN をコピー
   - GitHub App の認可はブラウザ操作が必須（CLI/CDK で作成しても `PENDING` になり結局ブラウザ認可が必要）
3. `cdk bootstrap`（deploy の前提。各アカウント・リージョン。GlobalStack 用に us-east-1 も含める）
4. 独自ドメイン/WAF を使う場合のみ: us-east-1 の証明書/WAF を一度 standalone で作成（`npx cdk deploy -c env=prd Prd/KukanGlobalStack`）し、ARN を `certificateArn`/`webAclArn` に設定
5. `environments.ts` と `cdk.context.json` をコミット（CodeBuild の synth が checkout から読み込む）
6. パイプラインスタックを初回デプロイ（`npx cdk deploy KukanPipeline`）
7. 以降は各 env の `deployBranch` への push で自動デプロイ（パイプラインも自己変異で更新）

`environments.ts` の構造（`connectionArn` はトップレベル、env 個別設定は `environments` の中）:

```ts
// infra/config/environments.ts
export const connectionArn = 'arn:aws:codeconnections:...:connection/...' // 手順2の ARN（全 env 共通）

export const environments = {
  // account は必須（誤デプロイ防止）。同一アカウントなら全 env に同じ ID を指定
  dev: {
    account: '000000000000',
    scale: 'small',
    githubRepo: 'owner/repo',
    deployBranch: 'develop',
  },
  prd: {
    account: '000000000000',
    scale: 'large',
    githubRepo: 'owner/repo',
    deployBranch: 'main',
  },
}
```

:::caution
CodeConnections の GitHub App 承認は、コンソールでの一度きりの手動操作です（IaC 化できません）。また CDK Pipelines は cross-region 参照と非互換のため、独自ドメイン/WAF（us-east-1）は手順4で ARN を供給するか `enableWaf: false` にしてください。prd には承認ゲート（手動承認）の設定を推奨します。
:::

:::note
パイプラインの synth は CodeBuild 上で実行されます。context lookup（AZ・CloudFront プレフィックスリスト）を決定的にするため、`infra/cdk.context.json` をコミットしてください（未コミットでも synth ロールの lookup ロール権限で解決されますが非決定的）。
:::

詳細・設計判断はリポジトリの `docs/specs/phase4-deploy.md` および ADR-030（`docs/adr/jp/030-cdk-pipelines-deploy.md`）/ ADR-031（`docs/adr/jp/031-multi-environment-deploy.md`）を参照してください。

## 初期セットアップ

ユーザーが1人も存在しない間は自己登録が強制的に有効になり、**最初に登録した
ユーザーが自動的に sysadmin になります**。デプロイ後、ブラウザでサインアップ
ページを開いて初回ユーザーを登録してください。

:::caution
最初の登録が完了するまでは、URL に到達できた人が誰でも sysadmin になれます。
インターネットに公開するデプロイでは、デプロイ後すみやかに初回ユーザーを
登録してください。
:::

ブラウザを使わずに初期化する場合や、sysadmin が全員いなくなった場合の回復には
CLI を使います。

```bash
pnpm db:create-user --email admin@example.com --name admin --password <password> --role sysadmin
```

| オプション   | 説明                                                           | 必須 |
| ------------ | -------------------------------------------------------------- | ---- |
| `--email`    | メールアドレス                                                 | Yes  |
| `--name`     | ユーザー名（小文字英数字、ハイフン、アンダースコア、ピリオド） | Yes  |
| `--password` | パスワード（8文字以上）                                        | Yes  |
| `--role`     | `user` または `sysadmin`（デフォルト: `user`）                 | No   |

## ユーザー管理

システム管理者（sysadmin）は管理画面からユーザーを管理できます。

### ユーザー一覧・編集

- ユーザーの表示名・役割（user / sysadmin）の変更
- 自分自身の役割降格は不可（ロックアウト防止）

### ユーザーの削除

- ソフトデリート方式（state を deleted に変更）
- 削除時に全セッション・API トークンを即時無効化
- 監査ログ・アクティビティ履歴は保持

### 自己登録制御

新規ユーザーの自己登録は管理画面（サイト管理 → ユーザー自己登録）で
切り替えます（デフォルト: 無効）。無効の間はシステム管理者が管理画面から
ユーザーを作成します。ユーザーが1人も存在しない間は、初期セットアップの
ため設定に関係なく自己登録が有効になります。

## サイト管理設定（ランタイム設定）

一部の設定は**再デプロイなしに管理画面から変更**できます（サイト管理 → `/dashboard/admin/site`、システム管理者のみ）。変更は DB に保存されて監査ログに残り、反映まで最大 30 秒ほどかかります。

| 設定                               | 内容                                                                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 検索例チップ                       | 検索ボックス下に表示するクエリ例                                                                                                                                                     |
| セマンティック検索・類似度しきい値 | 意味の近い結果を検索に含めるかどうかと、含める「意味の近さ」の下限。緩めるとヒットが増える代わりにノイズも増え、厳しくすると精度重視になります（要: 埋め込みモデルが利用可能な構成） |
| AI メタデータ提案                  | 機能の有効化（キルスイッチ）、生成モデル ID（空欄はプロバイダ既定）、接続テスト                                                                                                      |
| ユーザー自己登録                   | 上記「[自己登録制御](#自己登録制御)」を参照                                                                                                                                          |

### AI・埋め込みモデルの選択

セマンティック検索（埋め込み）と AI メタデータ提案は、`AI_TYPE` で選んだプロバイダを使います。

- **AWS**: Bedrock（`AI_TYPE=bedrock`）
- **オンプレミス / 開発**: Ollama（`AI_TYPE=ollama`）または OpenAI 互換（`AI_TYPE=openai`）
- **無効**: `AI_TYPE=none`（NoOp）— セマンティック検索はキーワード検索にフォールバックし、AI 提案は利用不可になります

生成・埋め込みモデルは管理画面から再デプロイなしで切り替えられます。候補モデルは `AI_COMPLETION_MODELS` 環境変数（カンマ区切り）で指定します。これは**このデプロイで利用を許可するモデルのリスト**で、全プロバイダ共通に管理画面ピッカーの選択肢となり、先頭エントリが既定（「プロバイダ既定」）になります。サーバー側で利用可能でも、リストに無いモデルは候補に現れません。**Bedrock** では CDK が `environments.ts` の `bedrock.completionModels`（IAM で `InvokeModel` を許可したモデル）からこの変数を注入するため、候補を増やす場合はそこに追加して再デプロイしてください。**Ollama** では Docker Compose の `ollama-init` が列挙された全モデルを起動時に pull するため、リストのモデルは自動で利用可能になります。未設定時は組み込み既定モデルのみが候補になります（Ollama: gemma4:e4b / OpenAI 互換: gpt-4o-mini）。Ollama を GPU で動かす手順は[開発環境セットアップ](/ja/getting-started/)を参照してください。

:::caution[小規模ローカルモデルの提案品質]
オンプレミス / CPU-only 環境向けの小規模ローカルモデル（実効 4〜8B クラス、Gemma 4 E4B 等）は、**メタデータ提案の品質としては非力**です。JSON 形式は正しく返しても、説明文が要点を外す・タグが的外れ・日本語の出力が不安定といった内容面の劣化が起きやすくなります。AI 提案はあくまで**下書きの叩き台**と位置づけ、採用前に人が必ず確認・修正する運用にしてください（提案はどのフィールドも初期 OFF で、採用したものだけがメタデータに反映されます）。生成品質を重視する場合は、Bedrock（Amazon Nova Lite 以上、必要なら Claude Haiku 系）や、十分な VRAM を確保した上での上位 Ollama モデル（Gemma 4 の上位サイズ・Qwen3 系）を選んでください。生成モデルは管理画面から再デプロイなしに切り替えられます。

AWS を使わないオンプレミス構成でも、常用の商用 AI に接続して品質を確保する方法があります。`AI_TYPE=openai` のまま `OPENAI_BASE_URL` を OpenAI 互換の商用エンドポイントやゲートウェイ（LiteLLM 等）に向けると、高性能な生成モデルを利用できます（提案機能は構造化出力〈`response_format` の JSON スキーマ〉を用いるため、エンドポイント側がこれに対応している必要があります）。Claude を純正で使う場合は現状 AWS の Bedrock（`AI_TYPE=bedrock`）が唯一の経路で、Anthropic API を API キーで直接叩く専用プロバイダは未提供です。
:::

#### AI 提案が動かないとき（Bedrock）

サイト管理の **接続テスト**を押すと、実際の生成と同じ経路（構造化出力）で 1 回だけ試行し、失敗時はエラーと対処のヒントを表示します。Bedrock 特有の典型的な原因と対処:

| 症状（接続テストのエラー）                       | 原因                                               | 対処                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------ | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `not authorized to perform: bedrock:InvokeModel` | タスクロールに当該モデルの IAM 権限がない          | `environments.ts` の `bedrock.completionModels` に追加して再デプロイ                                                                                                                                                                                                                                     |
| `use case details have not been submitted`       | Anthropic の利用ユースケースフォーム未提出         | Bedrock コンソールで Anthropic の「利用ユースケース詳細」フォームを提出（アカウントに一度・約15分で有効化）                                                                                                                                                                                              |
| `aws-marketplace:Subscribe` 系の AccessDenied    | Marketplace 提供モデルがアカウント未サブスクライブ | 下記「[Marketplace モデルの初回サブスクライブ](#marketplace-モデルの初回サブスクライブ)」の手順で一度 invoke して有効化。組織で SCP により制限されている場合は、**管理アカウント**側で `aws-marketplace:Subscribe` / `ViewSubscriptions` の許可が必要（AdministratorAccess でも SCP は上書きできません） |

これらはいずれも**アプリ外（AWS 側）の設定**で、コンソールでの一度きりの作業です。Claude 等の Anthropic モデルはフォーム提出と Marketplace サブスクライブの両方が必要になる点に注意してください（Amazon Titan / Nova はどちらも不要 — 初回呼び出しで自動有効化されます）。

:::note
かつての Bedrock **Model access（モデルアクセス）** ページは廃止されました。サーバーレス基盤モデルはアカウント内で初回に呼び出した時点で自動的に有効化されるため、手動で「有効化」する操作はもうありません。アクセス制御は IAM ポリシーと SCP に一本化されています。
:::

#### Marketplace モデルの初回サブスクライブ

Cohere Embed v4 のような **AWS Marketplace 提供モデル**は自動有効化の対象外で、アカウント全体で使えるようにするには **AWS Marketplace 権限を持つユーザーが一度だけ呼び出す**必要があります。いずれかの方法で 1 回呼び出せば、以後はデプロイ済みのタスクロールからも利用できます（伝播に数分）。

- **コンソール**: Bedrock → **モデルカタログ（Model catalog）** で対象モデルを開き、**プレイグラウンド（Playground）** で任意の入力を 1 回実行する。有効化済みの一覧は [AWS Marketplace の「Manage subscriptions」](https://console.aws.amazon.com/marketplace/home#/subscriptions)で確認できます。
- **CLI**（同じことを 1 コマンドで）:

  ```bash
  aws bedrock-runtime invoke-model --region ap-northeast-1 \
    --model-id cohere.embed-v4:0 --content-type application/json \
    --body '{"texts":["test"],"input_type":"search_document"}' /dev/stdout
  ```

埋め込みモデルを切り替えた場合は、既存データに反映するためバルク再埋め込み（検索インデックスの rebuild）を実行してください。

## ヘルスチェック

外部 URL リソースの死活監視を自動で行います。

- 定期的なスケジューラーによる自動チェック
- 管理画面からヘルスチェック結果の確認
- エラーリソースの特定と対応
