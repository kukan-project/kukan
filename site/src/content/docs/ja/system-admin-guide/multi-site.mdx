1 つの運用主体が複数の KUKAN サイト(例: 複数自治体のデータカタログ)を運用する場合、
サイトごとにフル構成を複製するとコストがサイト数に比例して増えます。
マルチサイト構成では、時間課金される「箱」(データベースクラスタ、OpenSearch、VPC、
ECS クラスタ)を共有し、データと名前空間を持つ論理リソース(データベース、
検索インデックス、ストレージバケット、キュー、web/worker サービス)をサイト別に持ちます。

- サイト間の分離: サイトごとの専用 DB ロール(他サイト DB へは接続不可)、
  検索インデックス prefix、バケット、キュー
- サイトごとに独自ドメイン・ブランド(マルチブランドビルド対応後)・サイズ調整が可能
- **同一運用主体のサイト群での利用を前提**とした構成です(後述のセキュリティ境界を参照)

## AWS(CDK)

`infra/config/environments.ts` の環境エントリに `sites` を宣言すると、
その環境が SharedStack(共有の箱)+ SiteStack × N に分割されます。

```ts
prd: {
  account: '...',
  scale: 'medium',
  githubRepo: '...', deployBranch: 'main',
  sites: [
    {
      name: 'citya', // 英小文字+数字、2〜16 文字
      domainName: 'catalog.city-a.example.jp',
      hostedZoneId: 'Z...', hostedZoneName: 'city-a.example.jp',
      certificateArn: 'arn:aws:acm:us-east-1:...', // サイトドメインには必須
      webAclArn: 'arn:aws:wafv2:us-east-1:...',    // 複数サイトで共有可
    },
    { name: 'cityb', enableWaf: false },
  ],
},
```

- **opt-in 専用**: `sites` の無い環境は従来どおりの単一スタック構成のまま変わりません。
  稼働中のシングルサイト環境に `sites` を後付けしないでください(リソース置換が発生します)。
  移行する場合は新環境を並行構築して DNS を切り替えます(ブルーグリーン)
- サイトのドメインには us-east-1 の ACM 証明書 ARN が必須です(マルチサイト環境は
  証明書スタックを自動作成しません)
- デプロイ順は自動制御されます: 共有スタック → 先頭サイト(カナリア)→ 残りサイト。
  本体コードの変更は全サイトに順次展開され、特定サイトだけの変更は他サイトに影響しません
- サイズや接続プールはサイトごとに `overrides` で調整できます
  (`web` / `worker` / `dbPool` / `backup` のみ)

設定の妥当性は `cdk synth` 時に検査されます(サイト名、証明書 ARN、
共有データベースの接続数バジェット超過など)。詳細な運用手順(サイト削除時の
残存リソースとパージ、接続数の考え方)はリポジトリの
`docs/specs/phase4-deploy.md` を参照してください。

## Docker Compose(オンプレミス)

同じ「箱共有・論理個別」モデルを Docker Compose で構成する opt-in テンプレートを
`docker/multi-site/` に用意しています。共有スタック(postgres / minio / elasticmq /
opensearch / ollama / caddy)を 1 回起動し、サイトごとに web/worker のペアを
共有ネットワークに接続します。手順は同ディレクトリの README を参照してください。

通常のシングルサイト運用はリポジトリルートの `compose.yml` をそのまま使います。

## セキュリティ境界

マルチサイト構成はサイト間のハードなマルチテナント境界ではありません。

- 資格情報レベルで分離されるのはデータベースのみです。検索インデックス・バケット・
  キューの分離は命名規約と(AWS では)IAM・セキュリティグループによるもので、
  特にオンプレミス構成では共有サービス側の認証がありません
- 信頼できない第三者にサイトを提供する用途には使わず、その場合はサイトごとの
  完全分離(環境の複製)を選択してください
- 共有インフラの障害・メンテナンスは全サイトに同時に影響します。SLA 要求が
  近いサイト同士だけを同居させてください

## キャパシティの目安

- **データベース接続数**: 各サイトの接続プール上限 × 最大タスク数の合計が
  共有クラスタの `max_connections` に収まる必要があります。AWS では synth 時に
  自動検査され、超過時はエラー、70% 超で警告になります
- **OpenSearch**: 全サイトのインデックスが 1 ドメイン(オンプレでは 1 JVM)を
  共有します。AWS では medium(m6g.large.search)以上を推奨、オンプレでは
  ヒープサイズ(`OPENSEARCH_JAVA_OPTS`)をサイト数に応じて拡張してください
