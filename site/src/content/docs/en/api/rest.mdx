Base path: `/api/v1`

Auth column legend:

- **Public** — no authentication required
- **Auth** — login or API token required
- **Org** — organization member / editor / admin
- **sysadmin** — system administrator only

:::note[PUT Semantics]
PUT endpoints perform full-resource replacement. Fields not included in the request body will be cleared to `null` (or their default value).
To preserve existing values, GET the current data, apply your changes, and send the full object.
As an exception, **PUT on a dataset in draft state is a partial update** (see "Drafts" below).
:::

### Drafts

Datasets can be created as drafts and published once the publish requirements are met.
Drafts never appear in search or listings (including the CKAN-compatible API) until published.

**Create** — `POST /packages/drafts` (auth required):

Every field is optional. When `name` is omitted, a placeholder of the form
`untitled-xxxxxxxx` is auto-generated (a draft cannot be published with the placeholder).
Specifying `ownerOrg` at creation requires editor rights in that organization.

```bash
curl -X POST https://your-kukan-site/api/v1/packages/drafts \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"title": "Work-in-progress dataset"}'
```

**Publish** — `POST /packages/{nameOrId}/publish`:

One-way `draft` → `active` transition (there is no way back to draft after publishing).
Returns `400` unless all three of the following are set:

- `name` set explicitly (the auto-generated placeholder is not accepted)
- `ownerOrg` set
- `licenseId` set

Permission is the same as dataset update, and editor rights in the `ownerOrg` organization
are re-verified at publish time. Re-publishing an already `active` package is allowed and
re-runs the publish-time search index sync (idempotent — the retry entry point after a
failed sync).

**List** — `GET /packages?state=draft` (auth required):

Returns only drafts created by the caller plus drafts of organizations where the caller is
editor or above. Supported filters: `q` / `name` / `organization[]` / `private` /
`sort_by` / `sort_order` / `offset` / `limit`. Specifying `tags[]` / `groups[]` /
`res_format[]` / `license_id[]` / `creator_user_id` / `my_org` / `include_facets`
returns `400`. Rows whose deletion failed partway (deletion incomplete) are included in
the listing.

**Get, update, delete**:

- Fetch details with `GET /packages/{id}?state=draft` (auth and draft access required)
- `PUT` on a draft is a **partial update**: only the keys present in the request are
  applied, and an explicit `null` clears that field. `name: null` regenerates the
  placeholder (back to "unnamed") and `ownerOrg: null` clears the organization (both
  block publishing again). `PUT` on an `active` package remains full replacement
- `DELETE` on a draft skips the trash and **permanently deletes it immediately**
  (irreversible). If a deletion fails partway, re-running the same `DELETE` completes
  the permanent deletion

### Schema and data query

CSV/TSV resources (with a pipeline-generated preview Parquet, ≤50 MB) support **column schema
retrieval** and **read-only SQL queries**. The MCP `get_resource_schema` / `query_resource`
tools offer the same capability for AI agents.

**Get schema** — `GET /resources/{id}/schema`:

```json
{
  "id": "…",
  "queryable": true,
  "primaryKey": null,
  "schema": {
    "rowCount": 1688,
    "columns": [
      { "name": "prefecture", "type": "string", "nullable": true, "nullCount": 3 },
      {
        "name": "weight_limit",
        "type": "integer",
        "nullable": false,
        "nullCount": 0,
        "stats": { "min": "600", "max": "1350" }
      }
    ]
  }
}
```

Resources that cannot be queried (unsupported format, not yet processed) return
`queryable: false`, `schema: null`. When a schema exists but there is nothing to
query (the preview has been purged, the schema has zero columns, or the preview
has not been regenerated after the content was replaced), `schema` is still
returned with `queryable: false`. `primaryKey` lists the column names of the
resource's settled primary key (composite keys in their chosen order), or is
`null` when none is set. `type` is one of `integer` / `float` / `boolean` / `string` /
`date` / `timestamp`; `stats` is present only for numeric columns, and integer min/max are
decimal strings.

`droppedRows` counts lines of the file that are not rows of this table — the reader refuses one
written short, and a note padded out to the table's width is trimmed from the table itself — a version line at the bottom, a stray comma in the middle. Refusing them is what stops
one such line costing the file every column it has: one row two fields wide in a file of
seventy-nine is enough for the CSV sniffer to abandon the delimiter and read the whole file as a
single text column. Absent means none, or a schema written before the count existed.

`droppedLines` says where the refused ones are, first few first, numbered as the CSV reader counts
from the start of the file — 1-based, including the header and any skipped title rows, and a
record whose quoted cell holds newlines counts once rather than once per line. A note trimmed from
the table has no line to give: by then the blank lines are gone and a quoted newline has folded a
record onto one. So this list can be shorter than `droppedRows`, or absent while it counts, and it
is bounded besides.

**Whether a refused line is taken for a sign-off decides if there is a table at all.** One that is
gets dropped and the table is served; any other refused line refuses the resource a table instead:
`schema.columns` is empty, `noTableReason` is `ragged-rows`, and `droppedLines` names the lines to
look at.

Which it is, is a guess, and it rests on the shape of the line: how many values it holds against
how many the table has. Two values in a table of thirty-one columns reads as a note rather than a
row that lost twenty-nine fields; two in a table of three is the ordinary way a row breaks, and
that file is refused. The values are counted by a parser, so a quoted cell holding the delimiter
is one of them. Neither position nor type is consulted — a truncated row at the end of
a file sits exactly where a note sits, and a row with a broken value fails every cast the table
would ask of it just as prose does.

**It is a guess and not a guarantee.** A row truncated to three of six columns reads as a note by
this rule, and is dropped. Nothing in the file distinguishes the two, so `droppedRows` and
`droppedLines` exist to put the guess in front of you. A refused file is still stored and downloadable, and re-running the pipeline after
fixing it produces the table.

**Query data** — `POST /resources/{id}/query`:

```bash
curl -X POST https://your-kukan-site/api/v1/resources/{id}/query \
  -H 'Content-Type: application/json' \
  -d '{"sql": "SELECT prefecture AS city, count(*) AS n FROM data GROUP BY 1 ORDER BY n DESC LIMIT 3"}'
```

```json
{
  "id": "…",
  "columns": ["city", "n"],
  "rows": [
    { "city": "Adachi", "n": "117" },
    { "city": "Edogawa", "n": "110" },
    { "city": "Ota", "n": "86" }
  ],
  "rowCount": 3,
  "truncated": false,
  "elapsedMs": 31
}
```

Query rules:

- The data is exposed as a table named `data`. Double-quote column names that contain spaces or non-ASCII characters.
- A single `SELECT` / `WITH` statement only. Writes and DDL (`INSERT` / `UPDATE` / `DELETE` / `CREATE` / `DROP` / `ATTACH` / `COPY` / `PRAGMA`, …) are rejected.
- Runs in a throwaway in-memory DuckDB instance; all external access (files, URLs, extension loading) is disabled.

Limits and errors:

| Item              | Value                                    |
| ----------------- | ---------------------------------------- |
| Max rows          | 10,000 (`truncated: true` when exceeded) |
| Max result size   | 5 MB                                     |
| Execution timeout | 15 s (`408`)                             |
| Concurrency       | 1 (`429` when exceeded)                  |

| Error | Condition                                                       |
| ----- | --------------------------------------------------------------- |
| `400` | Invalid SQL / non-SELECT / over length / non-queryable resource |
| `404` | Resource not found / private without access                     |
| `408` | Execution timeout                                               |
| `429` | Concurrent query limit                                          |

### Versions and diffs

When a resource's file is replaced, the content it replaced is kept as a **version**. No version
is added while the content stays the same.

**List versions** — `GET /resources/{id}/versions` (newest first):

```json
{
  "id": "…",
  "versions": [
    {
      "version": 2,
      "origin": "upload",
      "state": "active",
      "isLive": true,
      "purgeFallsBackTo": 1,
      "format": "CSV",
      "size": 20481,
      "hash": "…",
      "schema": { "rowCount": 1688, "columns": [] },
      "noTableReason": null,
      "keyColumns": ["order_no", "line_no"],
      "created": "2026-08-01T09:12:44.000Z",
      "purgedAt": null
    }
  ]
}
```

| Field              | Description                                                                                                                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `origin`           | `upload` (an explicit replacement) or `fetch` (observed when the external URL was read)                                                                                                                  |
| `state`            | `active` / `superseded` (legacy rows left by the old-style revert; never written anymore) / `purging` / `purged`                                                                                         |
| `isLive`           | Whether the resource is serving this version. Not derivable from `version` or `state`                                                                                                                    |
| `purgeFallsBackTo` | Where serving would land if this version were purged. Set only when `isLive` — purging any other version does not move serving                                                                           |
| `format`           | The format this version settled as. Relabeling the resource does not change it                                                                                                                           |
| `schema`           | The version's column schema (tabular only), frozen per version                                                                                                                                           |
| `noTableReason`    | Why no table was produced (`no-columns` / `too-many-columns` / `too-large`)                                                                                                                              |
| `keyColumns`       | The primary key this version's rows were identified by, `null` for a version read without one. The resource's current setting is a different question — it is what the _next_ version will be read under |

A purged version stays in the list as a record, but `size` / `hash` / `schema` / `keyColumns`
become `null` and `purgedAt` is filled in. Downloading it returns `404`. `keyColumns` goes with them
because a primary key is only settable over columns the content has, so its names are a subset of
the withheld `schema` (a `format` is a closed vocabulary, and stays). **The reason it was purged is
not returned** — it is free text about content that has been destroyed, and this endpoint is as
readable as the resource; who purged what, when and why is in the audit log.

**Diff** — `GET /resources/{id}/versions/{v}/diff?from={v'}` (`from` defaults to the preceding
version):

Requires **editor permission** on the owning dataset — it scans both snapshots in full, so it is
not a public endpoint.

```json
{
  "available": true,
  "from": 1,
  "to": 2,
  "schemaChanged": false,
  "keyed": false,
  "addedRows": 42,
  "removedRows": 3,
  "sampleAdded": [{ "city": "Adachi", "count": "117" }],
  "sampleRemoved": []
}
```

- **`keyed` is `true` only when both ends were read under the same primary key**, and adds
  `changedRows`, `sampleChangedAfter` and `sampleChangedBefore` when it is — the two samples
  aligned by position, the older side carrying **only the columns whose value actually moved**
  (the key matched, so both sides hold it, and a column that held still is left out). Sampled
  cells are trimmed for display, so comparing the two sides does not answer whether a cell
  changed; presence in the older side does. With no key declared, or a different key at
  each end, it is `false` and **editing one row appears as one addition plus one removal** —
  nothing identifies the row as the same one
- Versions whose columns differ return
  `{"schemaChanged": true, "schemaDiff": {"added": [], "removed": [], "retyped": []}}` and no row
  comparison is attempted
- When no diff can be produced, the response is
  `{"available": false, "reason": "…", "from": …, "to": …, "reasonVersion": …}`, where `reason` is
  `no-previous-version` / `not-ingested` / `purged` / `key-missing` / `key-null` /
  `key-not-unique`. The last three mean the declared primary key did not identify that version's
  rows, so it was never loaded. `not-ingested` is not a cause: one side has no row-level snapshot
  and no key fault to name, which includes the ordinary window between a version being created and
  the load running for it. A cause may still be recorded on the version and still give this reason
  — `noTableReason` settles three of them, and the version is where they are answered
- `reasonVersion` says **which of the two the reason is about**, and it is **not necessarily the
  one asked for**: opening the version after a corrected key puts the refused one on the other end,
  and `not-ingested` is a property of one end just as easily. It is `null` only where no single
  version is the subject — nothing to compare against, and a purge, which stops the comparison the
  same way from either end
- The SQL is composed server-side from version numbers alone. This is a separate path from the
  `POST /resources/{id}/query` sandbox; user SQL never reaches it
- Responses carry `Cache-Control: private, max-age=60, must-revalidate`. An unavailable answer is
  not cached at all

| Error | Condition                                           |
| ----- | --------------------------------------------------- |
| `401` | Not authenticated                                   |
| `403` | No editor permission on the owning dataset          |
| `404` | Resource or version not found                       |
| `408` | Diff timed out                                      |
| `429` | DuckDB concurrency limit (shared with data queries) |

**Purge a version** — `POST /resources/{id}/versions/{v}/purge` (sysadmin only):

A reason is required and is recorded in the audit log. The version is claimed and `202` is
returned; a worker erases the content asynchronously. Repeating the call for the same version is
idempotent.

```bash
curl -X POST https://your-kukan-site/api/v1/resources/{id}/versions/2/purge \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"reason": "Personal data was included"}'
```

**Revert** — `POST /resources/{id}/revert`:

Stops the running job and puts the resource's content back on a given version.

```json
{ "restoreTo": 2, "ifLiveRevision": "018f…-…-…" }
```

- `restoreTo` is the **destination version number**, not how many rungs to step back. `null`
  leaves the resource with no file
- `ifLiveRevision` is the `live_revision` served by `GET /resources/{id}/pipeline-status`. It
  stops a request delayed past a newer upload from reverting content it never saw
- The same `pipeline-status` also returns `revert_target`, the default destination

After a revert the preview and the search index can still describe the old content. Rebuild them
with `POST /resources/{id}/run-pipeline` and `{"rebuildOnly": true}`, which regenerates from the
object the resource already holds rather than re-fetching the external URL.

### Column settings

The primary key a resource's rows are identified by. Declaring one makes the version diff report
edits (`keyed: true`) rather than an addition and a removal per changed row. All three require
**editor permission** — this is what a person settled about the columns, not a description of the
data.

**Read** — `GET /resources/{id}/column-settings`:

```json
{
  "id": "…",
  "primaryKey": ["order_no"],
  "carried": false,
  "schema": {
    "rowCount": 1688,
    "columns": [{ "name": "order_no", "type": "string", "nullCount": 0, "unique": true }]
  }
}
```

- `schema` is the **live version's** frozen interpretation — the same columns a `PUT` is validated
  against, so a key chosen from this list cannot be refused for naming a column that is not there
- `unique` marks the columns that identify a row on their own, so choosing one of those needs no
  check. It says nothing about a combination — a composite key has to be read out of the content
- `carried` is `false` while the newest standing version has not been read under `primaryKey` yet.
  That is the ordinary state between settling a key and the rebuild landing, not a fault

**Check** — `POST /resources/{id}/column-settings/check`, body `{"primaryKey": [...]}`:

```json
{ "id": "…", "checked": true, "primaryKey": ["order_no"], "fault": "key-not-unique" }
```

- `fault` is `null` when the key would work, or `key-missing` / `key-null` / `key-not-unique`
- `{"checked": false, "reason": "no-preview" | "preview-stale"}` means the question could not be
  answered — there is no current interpretation to read. **Not an error**: the `PUT` asks nothing
  of the content, so a key can still be settled
- Answered from the frozen per-column counts for a single-column key, and by reading the
  interpretation's Parquet for a composite one

**Settle** — `PUT /resources/{id}/column-settings`, body `{"primaryKey": [...] | null}`:

```json
{ "id": "…", "primaryKey": ["order_no"], "queued": true }
```

- `[]` and `null` both mean "no key"; the body normalizes to one spelling
- Columns are kept **in the order given**, and rows are matched regardless of it: every use of a
  key ands its columns together. The order is part of the recorded key all the same, so the same
  columns in another order count as a different key and issue a version
- **Settling a key creates a version**, because a version is these bytes read this way and the key
  is part of the reading. The bytes do not move, so the new version owns a copy of them. `queued`
  says the rebuild that issues it is on its way; `null` means none was owed; **`false` means the
  setting was stored and the rebuild could not be queued** — the two are decided separately so that
  **re-sending the same body is the repair**. Nothing sweeps for a resource whose setting and newest
  version disagree, so a caller that ignores `false` leaves a key no version is ever read under
- Versions already in layer 2 are not re-read under the new key. The boundary is the version
  itself, and diffs across it fall back to comparing whole rows
