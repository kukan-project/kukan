## Deployment

KUKAN supports two deployment methods, described below in order: the simpler Docker Compose
(on-premises / isolated networks) first, then AWS (cloud / production).

### Docker Compose (On-Premises)

Deploy on-premises or in isolated networks using Docker Compose.
For production use, we recommend the latest [release](https://github.com/kukan-project/kukan/releases) (`vX.Y.Z` tag).

```bash
git checkout vX.Y.Z   # latest release
cp .env.prod.example .env.prod
# Edit .env.prod
docker compose --env-file .env --env-file .env.prod --profile prod up -d --build
```

#### Updating

Check the [release notes](https://github.com/kukan-project/kukan/releases) for breaking changes and migration steps before upgrading.

:::caution[Releases whose notes say to stop first]
`up -d --build` recreates services one at a time. Once the new worker has applied a migration, an old web container that is still handling authentication fails sign-ins. For such releases, stop the application before bringing the new version up.

```bash
docker compose --env-file .env --env-file .env.prod --profile prod down
```

After the migration, images older than the release may no longer run against the database (for v0.22.0, every older image — 0.17.0 through 0.21.x included — fails authentication). Rolling the image back does not recover it; move forward to a newer release instead.
:::

```bash
git fetch --tags
git checkout vX.Y.Z   # the new release
docker compose --env-file .env --env-file .env.prod --profile prod up -d --build
```

Database migrations are applied automatically when the worker starts. An older image cannot always be brought back against a migrated database.

:::note[Upgrading to the release that introduces version history]
After the upgrade, a **Backfill versions** item appears on the site administrator's dashboard.
Until you run it, resources that existed beforehand keep no version of their previous content
when a file is replaced (see the
[Data Admin Guide](/en/data-admin-guide/#one-time-migration)).
:::

On-premises deployments use the following alternative services:

| AWS Service | On-Premises Alternative     |
| ----------- | --------------------------- |
| S3          | MinIO                       |
| SQS         | ElasticMQ                   |
| OpenSearch  | PostgreSQL full-text search |

### AWS Deployment

KUKAN deploys on AWS as **CloudFront (WAF + cache) → internal ALB → ECS Fargate**.
Deployment is **automated with CDK Pipelines (AWS CodePipeline)**: using a CodeConnections
(GitHub App) source, a push to the target branch deploys each environment (dev / prd, etc.)
as a CDK Stage.

Environments are defined in `infra/config/environments.ts` (**copied from** `environments.example.ts`).
Create environments **in the multi-site shape (declare `sites`)**. Even with a single site,
starting with one `sites` entry makes adding sites later non-destructive (see
[Multi-Site Operation](/en/system-admin-guide/multi-site/)). The single-site shape — no
`sites`, with site-specific settings (domain, WAF, etc.) directly on the env entry —
keeps working for **backward compatibility** but should not be used for new deployments
(the two shapes cannot be mixed). See the
[Environment Configuration Reference](/en/system-admin-guide/environment-config/) for the
full parameter list.

Key AWS resources:

- **CloudFront** — CDN, WAF, TLS termination (the front layer)
- **ALB (internal)** — load balancer (reachable only via the CloudFront VPC origin)
- **ECS Fargate** — Web application + Pipeline Worker
- **Aurora Serverless v2 / RDS** — PostgreSQL database
- **S3** — File storage
- **SQS** — Pipeline queue
- **OpenSearch** — Full-text search engine
- **AWS Backup** — Isolated backups (enabled on the large scale etc.)

#### Deploy notifications (Slack)

Setting `deployNotification: true` on an environment posts the outcome to Slack every time that
environment finishes deploying. An environment that omits it gets none of the resources.

To get a webhook URL: in [Slack app settings](https://api.slack.com/apps), **Create New App** (From scratch), turn on
**Incoming Webhooks**, then **Add New Webhook to Workspace** and pick the channel.

The stack creates the box it goes into. Deploying with `deployNotification: true` outputs the
secret's ARN on the pipeline stack; paste the URL into it once:

```bash
aws secretsmanager put-secret-value --secret-id <ARN from the output> --secret-string 'https://hooks.slack.com/services/...'
```

Until then notifications do nothing, and the deploy still succeeds. A message carries the outcome,
the deployed commit, the sites that were updated (linked when they set `domainName`), a link to the
release notes on a release, and a link to the pipeline execution.

:::caution
Turning `deployNotification` off after it has been on **deletes the pasted webhook URL with it**.
Turning it back on creates a different secret, so the URL has to be pasted again.
:::

#### Backups and data protection

Data-protection settings are integrated into the `scale` presets:

| Setting                                           | small | medium | large                    |
| ------------------------------------------------- | :---: | :----: | :----------------------- |
| S3 versioning (accidental delete/overwrite guard) |   —   |   ✓    | ✓                        |
| DB automated backup retention (point-in-time)     |  7d   |  14d   | 35d                      |
| AWS Backup (isolated custody, long-term)          |   —   |   —    | daily 35d + monthly 12mo |

Uploaded files are stored in S3 and automatically replicated across multiple availability zones in the region (11-nines design durability). With versioning enabled, accidental deletes and overwrites are also recoverable. AWS Backup keeps copies of S3 and the database in an isolated Backup Vault, covering incidents that take out the resource itself and generations beyond 35 days. Tune per environment via `overrides.backup` in `environments.ts` (enabling `awsBackup` requires `s3Versioning: true`).

Objects in storage are separated by prefix according to how they are written. They all live in
the same bucket, so one backup configuration covers them.

| Prefix       | What gets written there                                         |
| ------------ | --------------------------------------------------------------- |
| `resources/` | A resource's canonical bytes; a new object on every replacement |
| `previews/`  | Preview Parquet and the text used by the search index           |
| `lake/`      | Data files behind row diffs (DuckLake)                          |

**The prefix does not decide an object's role.** Which object is the current content and which
is a past version is decided by the database pointers (`resource.storage_key` /
`resource_version.storage_key`). At the moment an object is written it is not yet known whether
it will become a version at all — content fetched unchanged produces none.

- **The current file and every past version's file are all under `resources/`.** That is where
  storage grows, by one object per replacement
- `resources/` also holds uploads that never completed, and objects awaiting reclamation

The catalog behind row diffs lives in a `ducklake` schema of the same PostgreSQL database (no
additional environment variables).

**Do not exclude any of these prefixes from backups.** `previews/` and `lake/` are derived data
that can be rebuilt from the canonical files, but there is currently no supported procedure for
regenerating derived data that has been lost.

#### Setup (one-time manual; after that, pushes deploy automatically)

1. Prepare your environment definitions (`cp infra/config/environments.example.ts infra/config/environments.ts`, then edit `environments.ts`). **Each entry becomes one environment = one pipeline**, so delete the ones you don't need (e.g. remove `dev` for a single environment)
2. Create a CodeConnections connection in the AWS console and set its ARN as the top-level `connectionArn` export in `environments.ts` (shared by all envs)
   - Open **CodeBuild** → **Settings → Connections → Create connection** in the left nav (a shared "Developer Tools" setting; reaching it via CodeBuild is easiest) → select **GitHub** → name it (e.g. `kukan-github`, an AWS-side label) → **Connect to GitHub** → install/authorize the **AWS Connector for GitHub** app (choose **Only select repositories** and grant just the repo you deploy from — least privilege) → once status is **Available**, copy the ARN
   - The GitHub App authorization requires a browser action (creating via CLI/CDK leaves it `PENDING` until authorized in the browser)
3. `cdk bootstrap` (prerequisite for deploy; per account/region, include us-east-1 for the GlobalStack)
4. For a custom domain / WAF only: create the us-east-1 certificate/WAF once via standalone (`npx cdk deploy -c env=prd Prd/KukanGlobalStack`) and set `certificateArn`/`webAclArn` on each site entry
5. Commit `environments.ts` and `cdk.context.json` so the CodeBuild synth reads them from the checkout
6. Deploy the pipeline stack once (`npx cdk deploy KukanPipeline`)
7. After that, pushes to each env's `deployBranch` deploy automatically (the pipeline self-mutates)

Structure of `environments.ts` (`connectionArn` is top-level; per-env settings go inside `environments`):

```ts
// infra/config/environments.ts
export const connectionArn = 'arn:aws:codeconnections:...:connection/...' // ARN from step 2 (shared by all envs)

export const environments = {
  // account is required (misdeployment guard); use the same ID across envs for same-account
  dev: {
    account: '000000000000',
    scale: 'small',
    githubRepo: 'owner/repo',
    deployBranch: 'develop',
    sites: [{ name: 'main', enableWaf: false }],
  },
  prd: {
    account: '000000000000',
    scale: 'large',
    githubRepo: 'owner/repo',
    deployBranch: 'main',
    sites: [{ name: 'main', enableWaf: false }],
  },
}
```

:::caution
The CodeConnections GitHub App approval is a one-time manual console action (it cannot be expressed as IaC). Also, CDK Pipelines is incompatible with cross-region references, so a custom domain / WAF (us-east-1) requires supplying the ARNs in step 4, or set `enableWaf: false`. For prd, we recommend configuring an approval gate.
:::

:::note
The pipeline's synth runs in CodeBuild. To make context lookups (AZs, CloudFront prefix list) deterministic, commit `infra/cdk.context.json` (when absent it still resolves via the synth role's lookup-role permission, but non-deterministically).
:::

For details and design rationale, see `docs/specs/en/phase4-deploy.md` and ADR-030 (`docs/adr/en/030-cdk-pipelines-deploy.md`) / ADR-031 (`docs/adr/en/031-multi-environment-deploy.md`) in the repository.

## Initial setup

While no users exist yet, self-registration is forced on and **the first
registered user automatically becomes a sysadmin**. After deploying, open
the sign-up page in a browser and register the first user.

:::caution
Until the first registration completes, anyone who can reach the URL can
become a sysadmin. For internet-facing deployments, register the first
user promptly after deploying.
:::

For headless initialization, or to recover when no sysadmin is left, use
the CLI.

```bash
pnpm db:create-user --email admin@example.com --name admin --password <password> --role sysadmin
```

| Option       | Description                                                      | Required |
| ------------ | ---------------------------------------------------------------- | -------- |
| `--email`    | Email address                                                    | Yes      |
| `--name`     | Username (lowercase alphanumeric, hyphens, underscores, periods) | Yes      |
| `--password` | Password (8+ characters)                                         | Yes      |
| `--role`     | `user` or `sysadmin` (default: `user`)                           | No       |

## User management

System administrators (sysadmin) can manage users from the admin dashboard.

### User list & editing

- Change user display name and role (user / sysadmin)
- Cannot demote your own role (lockout prevention)

### Deleting users

- Soft-delete (sets state to deleted)
- All sessions and API tokens are immediately revoked
- Audit logs and activity history are preserved

### Self-registration control

Toggle new user self-registration from the admin dashboard (Site
Management → User Self-Registration; default: disabled). While disabled,
system administrators create users from the admin dashboard. While no
users exist, self-registration is enabled regardless of the setting so the
instance can be bootstrapped.

## Site settings (runtime)

Some settings can be **changed from the admin dashboard without redeploying** (Site Management → `/dashboard/admin/site`, system administrators only). Changes are stored in the database, recorded in the audit log, and take up to about 30 seconds to take effect.

| Setting                                | Description                                                                                                                                                                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Search example chips                   | Example queries shown under the search box                                                                                                                                                                                                  |
| Semantic search & similarity threshold | Whether to include semantically related results in search, and the minimum "closeness" required. Loosening it yields more hits but more noise; tightening favors precision (requires a configuration where an embedding model is available) |
| AI metadata suggestions                | Feature toggle (kill switch), generation model ID (blank = provider default), and a connection test                                                                                                                                         |
| Language of AI-written descriptions    | The language abstracts are written in (Japanese / English). Default Japanese. Changing it does not rewrite existing descriptions — that needs the bulk generation under "[AI-written descriptions](#ai-written-descriptions)" below         |
| User self-registration                 | See "[Self-registration control](#self-registration-control)" above                                                                                                                                                                         |

### AI and embedding model selection

Semantic search (embeddings) and AI metadata suggestions use the provider chosen by `AI_TYPE`.

- **AWS**: Bedrock (`AI_TYPE=bedrock`)
- **On-premises / development**: Ollama (`AI_TYPE=ollama`) or OpenAI-compatible (`AI_TYPE=openai`)
- **Disabled**: `AI_TYPE=none` (NoOp) — semantic search falls back to keyword search, and AI suggestions are unavailable

The generation/embedding model can be switched from the admin dashboard above without redeploying. Candidate models are set via the `AI_COMPLETION_MODELS` environment variable (comma-separated). This is **the list of models approved for the deployment**: across all providers it becomes the admin picker options, with the first entry as the default (the dashboard's "provider default"). A model being available on the server does not put it in the picker — only listed models appear. On **Bedrock**, CDK injects this variable from `bedrock.completionModels` in `environments.ts` (the models granted `InvokeModel` in IAM), so add candidates there and redeploy. On **Ollama**, Docker Compose's `ollama-init` pulls every listed model at startup, so listed models become available automatically. When unset, only the built-in default model is offered (Ollama: gemma4:e4b / OpenAI-compatible: gpt-4o-mini). To run Ollama on a GPU, see the [Getting Started guide](/en/getting-started/).

:::caution[Suggestion quality of small local models]
Small local models aimed at on-premises / CPU-only deployments (effective 4–8B class, such as Gemma 4 E4B) are **underpowered at metadata suggestion quality**. Even when they return valid JSON, the content tends to degrade — descriptions miss the point, tags are off-target, and Japanese output is unstable. Treat AI suggestions strictly as a **draft starting point** and keep a human in the loop to review and correct before adopting (every field is OFF by default; only the fields you accept are written to the metadata). Where generation quality matters, choose Bedrock (Amazon Nova Lite and up, or Claude Haiku class if needed) or a larger Ollama model given sufficient VRAM (larger Gemma 4 sizes, Qwen3-class). The generation model can be switched from the admin dashboard without redeploying.

Even on an on-premises deployment without AWS, you can secure quality by connecting to a hosted commercial AI. Keep `AI_TYPE=openai` and point `OPENAI_BASE_URL` at an OpenAI-compatible commercial endpoint or gateway (LiteLLM, etc.) to use a high-quality generation model — the suggestion feature relies on structured output (a `response_format` JSON schema), so the endpoint must support it. To use Claude natively, AWS Bedrock (`AI_TYPE=bedrock`) is currently the only path; there is no dedicated provider that calls the Anthropic API directly with an API key.
:::

#### When AI suggestions don't work (Bedrock)

The **connection test** in Site Management runs one attempt through the same path as real generation (structured output) and, on failure, shows the error plus a fix hint. Common Bedrock-specific causes:

| Symptom (connection-test error)                       | Cause                                                      | Fix                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `not authorized to perform: bedrock:InvokeModel`      | The task role lacks IAM access to the model                | Add it to `bedrock.completionModels` in `environments.ts` and redeploy                                                                                                                                                                                                                                                       |
| `use case details have not been submitted`            | The Anthropic use-case form hasn't been submitted          | Submit the Anthropic "use case details" form in the Bedrock console (once per account; ~15 min to activate)                                                                                                                                                                                                                  |
| `AccessDenied` mentioning `aws-marketplace:Subscribe` | A Marketplace-served model isn't subscribed on the account | Invoke the model once to enable it — see "[First-time subscription for Marketplace models](#first-time-subscription-for-marketplace-models)" below. If an organization SCP restricts it, grant `aws-marketplace:Subscribe` / `ViewSubscriptions` from the **management account** (an SCP overrides even AdministratorAccess) |

All of these are **out-of-app AWS setup** — one-time console actions. Note that Anthropic models (Claude, etc.) require both the use-case form and a Marketplace subscription, whereas Amazon Titan / Nova need neither (both auto-enable on first invocation).

:::note
The former Bedrock **Model access** page has been retired. Serverless foundation models are enabled automatically the first time they are invoked in your account, so there is no longer a manual "enable" step. Access control is consolidated into IAM policies and SCPs.
:::

#### First-time subscription for Marketplace models

**AWS Marketplace-served models** such as Cohere Embed v4 are not auto-enabled: to make one usable account-wide, a **user with AWS Marketplace permissions must invoke it once**. A single invocation via either method below enables it for the deployed task roles as well (propagation takes a few minutes).

- **Console**: open the model from Bedrock → **Model catalog** and run any input once in the **Playground**. Enabled subscriptions are listed under [AWS Marketplace → "Manage subscriptions"](https://console.aws.amazon.com/marketplace/home#/subscriptions).
- **CLI** (the same thing in one command):

  ```bash
  aws bedrock-runtime invoke-model --region ap-northeast-1 \
    --model-id cohere.embed-v4:0 --content-type application/json \
    --body '{"texts":["test"],"input_type":"search_document"}' /dev/stdout
  ```

If you switch the embedding model, existing data needs **the embeddings regenerated** to pick it up (see "[Reprocessing the search index](#reprocessing-the-search-index)" below).

### AI-written descriptions

Every resource you register can have an AI write a **short description from the
file's contents**, shown on its resource page. It lets a reader judge what is in
a file without opening it, and it feeds search as well (it goes into the
per-resource embedding).

**One setting turns it on: the model that should write them.** Name it and the
feature is on; leave it unset and nothing is written and nothing is billed. On
AWS it is `bedrock.summaryModel` in `environments.ts`; on Docker Compose it is
the `AI_SUMMARY_MODEL` environment variable.

```ts
// AWS (infra/config/environments.ts) — CDK injects AI_SUMMARY_MODEL from this
bedrock: {
  completionModels: [
    'jp.anthropic.claude-sonnet-4-6',
    'jp.anthropic.claude-haiku-4-5-20251001-v1:0',
    'jp.amazon.nova-2-lite-v1:0',
  ],
  summaryModel: 'jp.anthropic.claude-sonnet-4-6',
}
```

```bash
# Docker Compose (.env)
AI_SUMMARY_MODEL=jp.anthropic.claude-sonnet-4-6
```

:::caution[On Bedrock the default is not enough]
Omitting `bedrock.completionModels` leaves a single model in it, **Amazon Nova
Lite**. `summaryModel` only accepts a model from that allow-list — the
allow-list being exactly what the task role is granted `InvokeModel` on — so a
model that is not in it is rejected when the environment is synthesized, before
anything deploys.

And **Nova cannot write these abstracts**: measured, the document block goes
through but forced JSON breaks, and on a scanned document it invented the
contents (ADR-053, appendix). Rather than settling for the default model, add
the recommended one to `completionModels` as above.

The first entry of `completionModels` becomes the default for AI metadata
suggestions. Abstracts name their model separately in `summaryModel`, so the
order does not decide for them.
:::

:::tip[Per site]
In a multi-site environment (ADR-041), `bedrock` on the environment entry is
the shared setting and `sites[].bedrock` adjusts it for one site — which is how
one site gets a cheaper model — Haiku 4.5 rather than Sonnet, say — or none at
all, while the rest keep the environment's.

```ts
sites: [
  { name: 'main' }, // the environment's
  { name: 'citya', bedrock: { summaryModel: 'jp.anthropic.claude-haiku-4-5-20251001-v1:0' } },
  { name: 'cityb', bedrock: { summaryModel: undefined } }, // no abstracts here
  { name: 'cityc', bedrock: false }, // no AI here at all
]
```

On Docker Compose the same split is per-site env files: `AI_SUMMARY_MODEL` in
`docker/multi-site/sites/<site>.env`.
:::

:::caution[Turning this on costs inference money]
An abstract is generated per resource, so **the bill scales with the size of
the catalog**. That is why this is an environment variable rather than a
dashboard toggle: it belongs to whoever pays for the inference. Choosing
between models is a threefold difference in the bill and, measured, the
difference between reading a scan and inventing one — so name the model
explicitly, whatever happens to be first in `AI_COMPLETION_MODELS`. A Claude
Sonnet 4.6 class model is recommended.

Before any bulk generation runs, the dashboard **shows how many resources it
covers and what it is estimated to cost**. Read that before pressing the button.
:::

The abstract model must be one from the completion allow-list. The
**language** is a runtime setting instead (Site settings) — language is free,
the model is money.

#### Bulk generation (Site settings → Generate AI descriptions)

Ordinarily nothing is needed here: descriptions are written as resources are
registered. This card exists for **resources that predate the setting** and for
**those needing a rewrite because the model, prompt version, or language
changed**. It never re-fetches an external URL.

| Action           | Covers                                                                         |
| ---------------- | ------------------------------------------------------------------------------ |
| Generate missing | Only resources with no description yet                                         |
| Regenerate all   | Those, plus descriptions written by another model, prompt version, or language |

Either button states "N resources · estimated X–Y input / Z output tokens
(about $low–$high)" before you press it. The input range has a span because a
PDF's token count follows its page count, which cannot be seen from here (the
bounds are one page and the page limit).

Embeddings are rebuilt package by package as generation completes. Running it
twice over the same content costs nothing the second time, because it compares
rather than regenerates.

## Reprocessing the search index

The search admin page (Index management) rebuilds indexes and derived data.
Each runs asynchronously through SQS and proceeds in the background once queued.

| Action                  | Rebuilds                                                   | Fetches external URLs   | Run it when                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rebuild search index    | The metadata index                                         | No                      | Search results look inconsistent. **After an upgrade that changed a mapping or schema** (`POST /api/v1/admin/reindex-metadata`)                                                                                                          |
| Reprocess content       | Extracted text, previews, and the index, from stored files | Only ones never fetched | Full-text search or previews are missing. **Takes time in proportion to the number of resources**                                                                                                                                        |
| Regenerate embeddings   | The vectors semantic search uses                           | No                      | Semantic search was enabled after the fact, or the embedding model changed (`POST /api/v1/admin/reindex-embeddings`). Unchanged content is skipped. **The dashboard also prompts while any resource is outside semantic search** (below) |
| Re-analyse search index | The index itself, under a new analysis                     | No                      | The Japanese analysis settings moved on. **Only when the page says so** (below)                                                                                                                                                          |

None of this is ordinarily needed: the metadata index updates as datasets are
created, updated, and deleted, and text and previews are built when the pipeline
processes a file.

### Re-analysing the search index

Upgrading to a release that changed the Japanese morphological analysis puts a
**re-analysis** notice on the search admin page. The analysis is **fixed when an
index is created**, so an existing index has to be rebuilt before the new
analysis takes effect. "Rebuild" above re-sends documents to the same index and
leaves its analysis as it was, so this is the only action that applies one.

It only re-reads text already stored — **no external URL is fetched and no file
is reprocessed**. It is a one-time action per upgrade, and the notice disappears
once it completes (`POST /api/v1/admin/search/reanalyse`).

## One-time migrations

Unlike reprocessing, these run **once, at migration time**. The dashboard shows
how much work is outstanding and the item disappears when it reaches zero.

### Regenerating embeddings

While any resource sits outside semantic search, the dashboard shows a prompt.
Embeddings get one because their absence is silent: with no vector to match
against, a search does not fail — it quietly falls back to keywords alone.

Two things raise it. **Upgrading to the release that moved the unit of
embedding to the resource**, which leaves every existing vector needing to be
rebuilt, and **changing the embedding model**. The ordinary half-minute between
an edit and its generated vector does not: a package with generation still
pending is not counted.

The prompt runs the same work as "Regenerate embeddings" in the table above.

### Version backfill

Resources that predate versioning have no version. Running **Version backfill**
on the dashboard records each resource's current file as v1 and loads tabular
ones into the row-level diff. Nothing is re-fetched or re-indexed
(`GET /api/v1/admin/version-backfill-status` /
`POST /api/v1/admin/backfill-versions`).

:::caution
**Replace a file before backfilling and its previous contents are lost — no
version is kept.** Run this soon after upgrading to a release that includes
versioning.
:::

For the per-layer breakdown and the conversion of old-style reverts, see the
[Data Administrator Guide](/en/data-admin-guide/#one-time-migration).

## Reclaiming storage

Objects that nothing points at any more — a file that was replaced, for instance — are recorded
in a ledger, and **an hourly sweep deletes them once their retention period elapses**. The sweep
re-checks whether anything still points at each key immediately before deleting it, so normal
operation needs no intervention.

The ledger arrived in the same release as version history. **Objects stranded by an interrupted
operation before that are named by no record and no pointer.** This affects only deployments that
were running before this release, and finding them means listing the bucket, so it is a manual
tool rather than a scheduled job.

Run it inside the deployed container, which is where the production database and bucket are in
reach:

```bash
node apps/worker/dist/reconcile-orphans.js            # report only
node apps/worker/dist/reconcile-orphans.js --commit   # record in the ledger
```

From a checkout:

```bash
pnpm --filter @kukan/worker reconcile-orphans
pnpm --filter @kukan/worker reconcile-orphans -- --commit
```

- **It reports without acting by default.** The keys it would nominate are listed, so read them
  before running with `--commit`
- **`--commit` deletes nothing either.** It writes ledger rows; the hourly sweep does the
  deleting, and re-checks each key against the live pointers first. An object whose pointer landed
  between the listing and the sweep is kept, so a run that turns out to have been wrong costs a
  row rather than a file
- **Objects written in the last 24 hours are out of scope.** A write still in flight is
  indistinguishable from a leak in a listing, so these are reported as `tooRecent` instead
- **Repeat until both `nominated` and `tooRecent` report zero.** One pass may not be enough
- It covers `resources/` and `previews/`. Not `lake/` — DuckLake knows its own layout and
  reclaims its own files

### Password strength policy

Every route that sets a password — sign-up, a user changing their own, an administrator creating one, `pnpm db:create-user` — is held to the same two conditions:

- **at least 15 characters** (not configurable), and
- **a zxcvbn score of at least `PASSWORD_MIN_SCORE`** (default `3`, "safely unguessable").

Lowering `PASSWORD_MIN_SCORE` lets common word sequences and keyboard patterns through. Setting it to `0` disables the guessability check altogether.

:::caution
`PASSWORD_MIN_SCORE` is a development setting. **Do not set it in production.** It exists so that throwaway passwords stay usable on a local machine, and lowering it lowers the strength of your authentication by exactly that much. The length minimum applies regardless.
:::
